Migrating from iTextSharp to IronPDF: a .NET production guide

what the docs do not cover when switching PDF libraries

Framing

iTextSharp holds a historically significant position in the .NET PDF ecosystem. For many years it was one of the only mature options for programmatic PDF generation in .NET, and its Java lineage gave it deep PDF specification coverage. Teams that built on iTextSharp — particularly those targeting .NET Framework before the current generation of Chromium-based libraries existed — made a reasonable architectural choice for the time. The library's element-composition model (Document, Paragraph, PdfPTable, Chunk, Image) offered a structured way to build PDF documents in code.

The landscape has shifted. iTextSharp's .NET successor is iText 7 for .NET (also from iText Group), and the licensing model changed significantly with iText 7 — the AGPL open-source terms require application code to also be AGPL, while the commercial license carries enterprise pricing. Teams that were using the older iTextSharp under LGPL found themselves evaluating alternatives when upgrading or when the AGPL terms became a concern. Beyond licensing, the generational shift to HTML/CSS as the preferred document layout language means that maintaining element-composition templates in C# has a higher ongoing cost than maintaining HTML templates that can be authored and previewed in a browser.

This guide covers the migration from iTextSharp (or iText 7 for .NET) to IronPDF for .NET engineers evaluating or executing the switch. The migration is classified as High effort, reflecting that iTextSharp's element-composition model has no direct IronPDF equivalent — every document currently generated by composing Paragraph, PdfPTable, and Chunk objects must be redesigned as an HTML/CSS template. Manipulation operations (merge, split, sign, encrypt) map cleanly. The effort is not uniform — teams using iTextSharp only for manipulation will find the migration much closer to Medium.

What iTextSharp Is Designed to Do

iTextSharp is the .NET port of the iText PDF library, originally developed for Java. The library is not an HTML renderer — it has no Chromium engine, no CSS parser, and no HTML input capability. Instead, it constructs PDFs programmatically by composing layout elements: Document is the root container, PdfWriter creates the underlying PDF structure, and content is added via objects like Paragraph (text with font and color), PdfPTable (tables with explicit column widths and cell content), Image (embedded images), Chunk (inline text with specific formatting), and Phrase (sequences of chunks). The PDF is generated by writing these objects to the document in sequence.

iTextSharp's strengths are its deep PDF specification coverage and its ability to read and manipulate existing PDFs. The library supports AcroForm form creation and filling, digital signatures (including certified signatures and long-term validation), PDF/A compliance conversion, encryption, and granular control over PDF structure. iText 7 for .NET (the successor) modernizes the API with a more consistent object model and expanded features. The product status and current release of both iTextSharp and iText 7 for .NET should be verified in official documentation. The primary use case is server-side document generation and manipulation in applications that require precise control over PDF structure, compliance output, or complex form workflows.

Architectural Differences

iTextSharp and IronPDF approach document creation from entirely different foundations. iTextSharp constructs PDFs by writing layout elements to a Document through a PdfWriter. IronPDF generates PDFs by rendering HTML/CSS through an embedded Chromium engine. The output format is identical (PDF); the authoring model is entirely different. This is the most important architectural distinction: migrating from iTextSharp is a document template redesign project, not primarily an API swap.

Where the two libraries converge is in PDF manipulation. Both can load existing PDFs, merge documents, extract text, fill forms, apply signatures, encrypt, and produce PDF/A output — the operations that work on an already-existing PDF document rather than creating one from scratch. For these operations, the migration is a mechanical API remapping exercise. For document creation, every iTextSharp template must be re-expressed as HTML/CSS.

IronPDF's two primary types are ChromePdfRenderer (for rendering HTML to PDF) and PdfDocument (for the resulting document and all manipulation). Both implement IDisposable and require using blocks. The HTML string to PDF guide covers IronPDF's full rendering configuration. License initialization is a one-time startup call via IronPdf.License.LicenseKey; see the license setup guide.

Operation Comparisons

Document Creation (The Design-Change Operation)

iTextSharp — Element-Composition Document

using iTextSharp.text;
using iTextSharp.text.pdf;
using System.IO;

// iTextSharp constructs PDFs by composing layout elements
// PdfWriter writes to a stream; Document is the layout container
using var outputStream = new MemoryStream();
using var document = new Document(PageSize.A4, 36, 36, 36, 36); // A4, margins in points

var writer = PdfWriter.GetInstance(document, outputStream);
document.Open();

// Fonts must be explicitly created and managed
var titleFont = FontFactory.GetFont(FontFactory.HELVETICA_BOLD, 18, BaseColor.BLACK);
var bodyFont = FontFactory.GetFont(FontFactory.HELVETICA, 11, BaseColor.BLACK);

// Add content via layout element composition
document.Add(new Paragraph("Invoice #1042", titleFont));
document.Add(new LineSeparator(0.5f, 100, BaseColor.BLACK, Element.ALIGN_CENTER, -2));

// Build a table
var table = new PdfPTable(3); // 3 columns
table.WidthPercentage = 100;
table.SetWidths(new float[] { 60f, 20f, 20f }); // percentage widths

// Header row
var headerFont = FontFactory.GetFont(FontFactory.HELVETICA_BOLD, 10, BaseColor.WHITE);
var headerBg = new BaseColor(64, 64, 64);

AddTableCell(table, "Description", headerFont, headerBg);
AddTableCell(table, "Qty", headerFont, headerBg);
AddTableCell(table, "Amount", headerFont, headerBg);

// Data row
AddTableCell(table, "Consulting Services", bodyFont, BaseColor.WHITE);
AddTableCell(table, "10", bodyFont, BaseColor.WHITE);
AddTableCell(table, "$1,500.00", bodyFont, BaseColor.WHITE);

document.Add(table);

document.Add(new Paragraph("Total: $1,599.00", titleFont));
document.Close();

byte[] pdfBytes = outputStream.ToArray();

static void AddTableCell(PdfPTable table, string text, Font font, BaseColor bg)
{
    var cell = new PdfPCell(new Phrase(text, font))
    {
        BackgroundColor = bg,
        Padding = 6f
    };
    table.AddCell(cell);
}

Concrete constraints:

  • Document margins are specified in points (1 point = 1/72 inch). new Document(PageSize.A4, 36, 36, 36, 36) creates A4 with 0.5-inch margins (36 points) on all sides.
  • Fonts must be registered or created with FontFactory — system fonts are not automatically available. Font embedding is the developer's responsibility.
  • PdfPTable requires explicit column count and proportional widths. There is no automatic column sizing.
  • PdfWriter.GetInstance() and document.Open() / document.Close() are the lifecycle calls — Document implements IDisposable in iTextSharp but Close() must still be called explicitly or via using.
  • For iText 7, the API is substantially different: PdfDocument + Document + Table with iText.Layout elements. Verify the exact API in official iText 7 documentation.
  • Every document type built this way must be redesigned as HTML/CSS for IronPDF. There is no automatic conversion path.

IronPDF — HTML/CSS Equivalent

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
// Margins in mm — 36 points ≈ 12.7mm
renderer.RenderingOptions.MarginTop = 12.7;
renderer.RenderingOptions.MarginBottom = 12.7;
renderer.RenderingOptions.MarginLeft = 12.7;
renderer.RenderingOptions.MarginRight = 12.7;

// iTextSharp's element composition is replaced by HTML/CSS
// CSS handles typography, table layout, and page breaks automatically
string html = @"
<!DOCTYPE html>
<html>
<head>
<style>
  body  { font-family: Helvetica, Arial, sans-serif; font-size: 11pt; }
  h1    { font-size: 18pt; font-weight: bold; margin-bottom: 4px; }
  hr    { border: none; border-top: 0.5pt solid #000; margin: 4px 0 10px; }
  table { width: 100%; border-collapse: collapse; }
  thead tr { background: #404040; color: #fff; }
  th, td   { padding: 6px; font-size: 10pt; }
  th       { text-align: left; }
</style>
</head>
<body>
  <h1>Invoice #1042</h1>
  <hr/>
  <table>
    <thead>
      <tr><th>Description</th><th>Qty</th><th>Amount</th></tr>
    </thead>
    <tbody>
      <tr><td>Consulting Services</td><td>10</td><td>$1,500.00</td></tr>
    </tbody>
  </table>
  <p><strong>Total: $1,599.00</strong></p>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(html);
byte[] pdfBytes = pdf.BinaryData;

The iTextSharp element model's PdfPTable with explicit widths, Paragraph with FontFactory.GetFont(), and LineSeparator are replaced by HTML <table> with CSS, HTML <h1> with font-family, and <hr> respectively. Font management is handled automatically by Chromium's font stack. Column widths in the HTML table can use CSS percentages. Full rendering configuration is in the HTML string to PDF guide.

Merging PDFs

iTextSharp — PDF Merging

using iTextSharp.text;
using iTextSharp.text.pdf;
using System.IO;

// iTextSharp merging: PdfCopyFields (for form-containing PDFs)
// or PdfSmartCopy / PdfCopy for general merging
using var outputStream = new MemoryStream();
using var document = new Document();
using var copy = new PdfSmartCopy(document, outputStream);

document.Open();

string[] sourceFiles = { "document1.pdf", "document2.pdf", "document3.pdf" };

foreach (var filePath in sourceFiles)
{
    // PdfReader opens each source PDF
    using var reader = new PdfReader(filePath);
    int pageCount = reader.NumberOfPages;

    for (int pageNum = 1; pageNum <= pageCount; pageNum++) // 1-based
    {
        copy.AddPage(copy.GetImportedPage(reader, pageNum));
    }
}

document.Close();
byte[] mergedBytes = outputStream.ToArray();

Concrete constraints:

  • iTextSharp's page indices are 1-based. reader.NumberOfPages returns the total count; pages are accessed as 1 through NumberOfPages.
  • PdfSmartCopy reuses PDF objects shared across pages (reducing output size). PdfCopy is simpler but may produce larger files.
  • PdfReader should be disposed after use
  • For iText 7, the API uses PdfMerger and PdfDocument with PdfPageTree — substantially different from iTextSharp's approach.
  • PdfCopyFields is required when merging PDFs that contain AcroForm fields to preserve the form structure.

IronPDF — PDF Merging

using IronPdf;

// Load all source documents — each is IDisposable
using var pdf1 = PdfDocument.FromFile("document1.pdf");
using var pdf2 = PdfDocument.FromFile("document2.pdf");
using var pdf3 = PdfDocument.FromFile("document3.pdf");

// Single static call — N-way merge with page order preserved
using var merged = PdfDocument.Merge(pdf1, pdf2, pdf3);
byte[] mergedBytes = merged.BinaryData;
// All documents disposed at end of using blocks

PdfDocument.Merge() replaces the PdfReader / PdfSmartCopy page-iteration pattern. The 1-based page index convention in iTextSharp does not apply — IronPDF uses 0-based indices throughout. The merge and split guide covers N-way merges, page range selection, and split operations.

Filling AcroForm Fields

iTextSharp — AcroForm Filling with PdfStamper

using iTextSharp.text.pdf;
using System.IO;

// iTextSharp fills forms via PdfStamper, which wraps a PdfReader
using var inputStream = new FileStream("form-template.pdf", FileMode.Open);
using var outputStream = new MemoryStream();

using var reader = new PdfReader(inputStream);
using var stamper = new PdfStamper(reader, outputStream);

// Access the AcroForm via the stamper
var acroFields = stamper.AcroFields;

// Set field values — string-based but with iTextSharp conventions
acroFields.SetField("applicant_name", "Jane Smith");
acroFields.SetField("status_approved", "On");       // checkbox
acroFields.SetField("category", "Enterprise");       // dropdown

// Flatten removes interactivity (optional)
stamper.FormFlattening = true;

stamper.Close();
byte[] filledBytes = outputStream.ToArray();

Concrete constraints:

  • iTextSharp uses PdfStamper as the intermediary for filling forms — it wraps PdfReader and writes the modified PDF to an output stream. This is a two-stream pattern (input + output).
  • AcroFields.SetField() uses string values for all field types. Checkbox values ("On", "Off") must match the checkbox's ON value defined in the PDF template — may be "Yes", "True", or another value.
  • stamper.Close() must be called before reading from the output stream.
  • For iText 7, the API uses PdfAcroForm.GetFormFields() with a different type model

IronPDF — AcroForm Filling

using IronPdf;

// IronPDF loads directly from file — no separate reader/writer pattern
using var pdf = PdfDocument.FromFile("form-template.pdf");

// Field access by name — uniform string value for all field types
var nameField = pdf.Form["applicant_name"];
if (nameField != null)
    nameField.Value = "Jane Smith";

var approvedField = pdf.Form["status_approved"];
if (approvedField != null)
    approvedField.Value = "On";

var categoryField = pdf.Form["category"];
if (categoryField != null)
    categoryField.Value = "Enterprise";

// Flatten before save
pdf.Form.Flatten();
pdf.SaveAs("filled-form.pdf");

The PdfReader + PdfStamper two-object pattern is replaced by a single PdfDocument.FromFile() call. There is no separate input/output stream management — pdf.SaveAs() handles the output. Form filling and flattening are documented in the edit forms guide.

Digital Signatures

iTextSharp — Digital Signatures

using iTextSharp.text.pdf;
using iTextSharp.text.pdf.security;
using Org.BouncyCastle.Pkcs;
using System.IO;
using System.Security.Cryptography.X509Certificates;

// iTextSharp uses BouncyCastle for certificate handling
// Load PKCS#12 certificate
using var pfxStream = new FileStream("certificate.pfx", FileMode.Open);
var store = new Pkcs12Store(pfxStream, "pfx-password".ToCharArray());

// Locate the private key alias in the store
string alias = null;
foreach (string a in store.Aliases)
    if (store.IsKeyEntry(a)) { alias = a; break; }

var privateKey = store.GetKey(alias).Key;
var certChain = store.GetCertificateChain(alias)
    .Select(c => c.Certificate).ToArray();

// Apply signature via PdfSignatureAppearance
using var reader = new PdfReader("document.pdf");
using var outputStream = new MemoryStream();
using var stamper = PdfStamper.CreateSignature(reader, outputStream, '\0');

var appearance = stamper.SignatureAppearance;
appearance.Reason = "Approved for distribution";
appearance.Contact = "signer@example.com";
appearance.Location = "Chicago, IL";
appearance.SetVisibleSignature(
    new iTextSharp.text.Rectangle(36, 748, 250, 748 + 50), 1, "Signature1");

var signer = new MakeSignature();
MakeSignature.SignDetached(appearance,
    new PrivateKeySignature(privateKey, DigestAlgorithms.SHA256),
    certChain, null, null, null, 0, CryptoStandard.CMS);

byte[] signedBytes = outputStream.ToArray();

Concrete constraints:

  • iTextSharp requires BouncyCastle (BouncyCastle.Cryptography or BouncyCastle.NetCore) for cryptographic operations — an additional dependency that must be managed.
  • PdfStamper.CreateSignature() opens the signing session. The coordinate rectangle for the visible signature uses iTextSharp's bottom-left coordinate system (points).
  • For iText 7, the signing API uses PdfSigner and the BouncyCastle dependency is still required
  • Certified signatures, LTV enablement, and TSA timestamps add further complexity

IronPDF — Digital Signatures

using IronPdf;
using IronPdf.Signing;

using var pdf = PdfDocument.FromFile("document.pdf");

// No BouncyCastle dependency required
var signature = new PdfSignature("certificate.pfx", "pfx-password")
{
    SigningReason = "Approved for distribution",
    SigningContact = "signer@example.com",
    SigningLocation = "Chicago, IL"
};

pdf.Sign(signature);
pdf.SaveAs("signed-document.pdf");

IronPDF's signing API does not require BouncyCastle — removing that dependency is a secondary benefit of the migration. The PdfReader + PdfStamper.CreateSignature() pattern is replaced by PdfDocument.FromFile() + pdf.Sign(). Full signing configuration, visible signature appearances, and HSM support are in the digital signatures guide.

Breaking Changes & Gotchas

  • No element-composition API: iTextSharp's entire document creation model — Paragraph, PdfPTable, Chunk, Phrase, Image, FontFactory — has no IronPDF equivalent. Every document built using these classes must be redesigned as HTML/CSS. This is the dominant effort item for generation-heavy integrations.
  • Page index convention: 1-based → 0-based: iTextSharp uses 1-based page numbers throughout (reader.NumberOfPages, page arguments to AddPage()). IronPDF uses 0-based indices. Every page index reference must be decremented by one.
  • Margin unit change: points → millimeters: iTextSharp's Document constructor takes margins in points. IronPDF's RenderingOptions.Margin* uses millimeters. Convert: mm = points ÷ 2.835. A 36-point margin is approximately 12.7mm.
  • PdfReader + PdfStamper two-object pattern removed: iTextSharp's form-fill and sign pattern requires opening PdfReader on the input and PdfStamper on the output. IronPDF uses a single PdfDocument.FromFile() call with pdf.SaveAs() for output. All PdfStamper.Close() calls are removed.
  • BouncyCastle dependency removed: iTextSharp signing requires BouncyCastle. IronPDF's signing API does not. Remove the BouncyCastle NuGet reference after migration.
  • PdfPageEventHelper has no equivalent: iTextSharp's page event system (OnStartPage, OnEndPage, OnCloseDocument) is used for running headers/footers, background images, and per-page operations. In IronPDF, running headers/footers are handled by RenderingOptions.HtmlHeader/HtmlFooter. Per-page background images or stamps can be applied via IronPDF's stamping API after rendering.
  • License / AGPL concerns resolved: If the migration motivation includes iText 7's AGPL licensing, migrating removes that concern entirely — IronPDF uses a commercial license model with no AGPL restriction.
  • Namespace change: Remove all using iTextSharp.text., using iTextSharp.text.pdf., etc. Replace with using IronPdf;. Compile errors identify every affected file.
  • Disposal semantics: iTextSharp's Document and PdfReader are IDisposable but also require explicit Close() calls in some patterns. IronPDF uses standard .NET IDisposable exclusively — using blocks suffice.
  • PdfDocument naming: iText 7 for .NET has a type named PdfDocument (in iText.Kernel.Pdf). IronPDF also has PdfDocument. If both packages are present during migration, fully qualify all references.

Migration Checklist

  1. Triage iTextSharp usage into two groups: (a) document generation via element composition (Document, Paragraph, PdfPTable, Image, etc.) — High effort, requires HTML/CSS redesign; (b) manipulation on existing PDFs (PdfReader, PdfStamper, AcroFields, signatures, encryption) — Low-Medium effort, maps directly. Group (a) drives the timeline.
  2. Design HTML/CSS templates for all generated documents: For each document type built using iTextSharp's element API, produce an HTML/CSS equivalent and validate it in a browser before testing with IronPDF. Allow design time per complex template (tables with precise column widths, multi-column layouts, running headers).
  3. Install IronPDF via NuGet: dotnet add package IronPdf. Retain iTextSharp references until replacement code compiles and passes tests.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs before any render or document call. See the license setup guide.
  5. Update namespaces: Remove all using iTextSharp.text.; and using iTextSharp.text.pdf.; directives. Replace with using IronPdf;. If migrating from iText 7, also remove iText 7 namespaces. Compile errors guide the remaining work.
  6. Convert margin values from points to millimeters: For each margin value in new Document(PageSize.A4, left, right, top, bottom), divide by 2.835 to get the equivalent RenderingOptions.Margin* value in mm.
  7. Replace PdfReader + PdfStamper form-fill pattern: Replace the two-object pattern with PdfDocument.FromFile(). Replace acroFields.SetField(name, val) with pdf.Form["name"].Value = "val". Replace stamper.FormFlattening = true with pdf.Form.Flatten(). Replace stamper.Close() with pdf.SaveAs().
  8. Port merge operations: Replace the PdfSmartCopy page-iteration loop with PdfDocument.Merge(pdf1, pdf2, ...). Update page indices from 1-based to 0-based where page-specific operations are referenced.
  9. Port signing: Replace PdfStamper.CreateSignature() + BouncyCastle with new PdfSignature(certPath, password) + pdf.Sign(). Remove the BouncyCastle NuGet dependency.
  10. Port encryption: Replace PdfEncryptor.Encrypt() or equivalent with pdf.SecuritySettings.. Map permission flags to IronPDF's SecuritySettings.Allow properties.
  11. Replace PdfPageEventHelper implementations: Move running header/footer content to RenderingOptions.HtmlHeader/HtmlFooter. Per-page background operations can use IronPDF's stamping API post-render.
  12. Remove iTextSharp / iText 7 NuGet references: Once all replacements compile and tests pass, remove iTextSharp and BouncyCastle NuGet package references and perform a final clean build.

Conclusion

When staying on iTextSharp or iText 7 is technically reasonable

iTextSharp or iText 7 is technically reasonable when the application requires precise low-level control over PDF structure — not just layout, but specific PDF object manipulation, custom XMP metadata, complex font subset control, or low-level stream manipulation that HTML/CSS rendering cannot provide. It is also reasonable when the team has deep existing investment in iTextSharp templates and the element-composition model is well-understood and maintained by the current team. For applications where iText 7's AGPL licensing is not a concern and the full feature set is in active use, there is no urgent reason to migrate.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when iTextSharp's AGPL licensing in iText 7 is incompatible with the application's distribution model; when new document types are being designed and would be far simpler to build as HTML/CSS than as element-composition code; when the team maintaining iTextSharp templates turns over and institutional knowledge of the element API is lost; when async rendering, HTML rendering, or CSS3 features are new requirements; or when the absence of a BouncyCastle dependency is a security posture improvement.

What the cutover typically involves at the code level

The manipulation operations — merge, form-fill, sign, encrypt — are a systematic API remapping exercise. The generation operations — everything built with Paragraph, PdfPTable, and Image — are a template development project. The page index 1-to-0 conversion and the points-to-mm margin conversion are systematic changes that must be applied throughout. For a codebase with 5–20 iTextSharp-generated document types and heavy use of the manipulation API, a phased migration — one document type at a time, manipulation operations first — reduces risk and allows production validation at each phase.

In your current iTextSharp integration, what proportion of document generation templates have complex table structures that would require careful CSS column width and border management to reproduce — and is that complexity the factor most likely to drive the migration timeline?
