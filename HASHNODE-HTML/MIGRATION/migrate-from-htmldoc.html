Migrating from HTMLDOC to IronPDF: a .NET production guide

what the docs do not cover when switching PDF libraries

Framing

CLI-based PDF generation tools occupy a common position in legacy .NET server applications. When HTML-to-PDF was first needed, the path of least resistance was often to shell out to a command-line tool already available in the server environment — write a file, launch a process, wait for output, read the result. That approach works, and it tends to stay in place for a long time precisely because it is stable and self-contained. The friction only appears when the surrounding infrastructure changes.

Infrastructure modernization is the most common trigger. Moving from a bare-metal Windows server to Linux containers, adopting CI/CD pipelines with tighter binary dependencies, or migrating to PaaS environments where spawning arbitrary child processes is restricted — each of these exposes the assumptions baked into a shell-out integration. In addition, HTML and CSS have evolved substantially since many CLI tools were authored. Teams generating documents that use CSS Grid, web fonts, SVG graphics, or modern layout patterns often find that an older CLI renderer produces noticeably degraded output that requires progressively more template workarounds to compensate.

HTMLDOC is a long-lived open-source HTML-to-PDF tool maintained at htmldoc.org. Teams that integrated it into .NET applications typically did so via Process.Start() wrappers, writing temporary HTML files to disk and reading back the generated PDF. This guide provides the technical migration path from that integration pattern to IronPDF, which is a managed .NET library rather than an external executable.

What HTMLDOC Is Designed to Do

HTMLDOC is an open-source command-line application that converts HTML documents to PDF (and PostScript) output. Its architecture centers on its own internal HTML parser and layout engine — it does not use a browser engine or WebKit. HTMLDOC reads HTML files or URLs from the command line, applies its own CSS and layout processing, and writes PDF output to stdout or a file. It supports a range of output options via CLI flags: paper size, orientation, margins, headers and footers with token substitution, table of contents generation, and basic title page handling.

The .NET integration pattern is process-based: the application creates a temporary HTML file, builds a command-line argument string, calls Process.Start() or equivalent, and reads the resulting PDF from a file path or the process's stdout. There is no managed .NET API surface — all configuration passes through CLI arguments. HTMLDOC's rendering engine predates modern browser layout standards; CSS support is limited compared to Chromium or WebKit, and JavaScript execution is not supported. The tool is actively maintained for correctness and security fixes. Exact current version and .NET platform constraints should be verified against the official HTMLDOC repository.

Architectural Differences

IronPDF replaces the external process model entirely. Rather than invoking an executable and marshaling input/output through the filesystem or stdout, ChromePdfRenderer renders HTML in-process using a Chromium engine and returns a managed PdfDocument object. There is no child process to launch, no temporary file management, and no argument-string construction.

The rendering engine is the other significant change. HTMLDOC uses its own parser with limited CSS support and no JavaScript. IronPDF uses Chromium, which means the HTML and CSS rendered in the browser during development is what IronPDF produces in the PDF. Templates that use CSS Grid, Flexbox, CSS Variables, web fonts, SVG, or JavaScript-rendered content (charts, dynamic tables) all work without workarounds. The HTML to PDF rendering guide documents the full option set for controlling the rendering pipeline, including viewport width, background printing, and wait conditions for JavaScript.

Disposal follows standard .NET IDisposable semantics. ChromePdfRenderer and PdfDocument both implement IDisposable; the recommended pattern is using blocks. This replaces the process lifecycle management — Process.Start(), WaitForExit(), and Process.Dispose() — that an HTMLDOC wrapper requires. License activation is a one-time static call at application startup; the license key setup guide covers key formats and environment-variable approaches.

Operation Comparisons

HTML File to PDF

HTMLDOC — HTML File to PDF

A typical HTMLDOC integration in .NET wraps Process.Start() with argument construction, process management, and output file handling.

using System;
using System.Diagnostics;
using System.IO;

// HTMLDOC integration — process-based pattern
public static byte[] ConvertHtmlToPdf(string htmlFilePath)
{
    // Build a temporary output path
    var outputPath = Path.Combine(Path.GetTempPath(), $"{Guid.NewGuid()}.pdf");

    try
    {
        // Construct the HTMLDOC command
        var arguments = $"--continuous --quiet --webpage -f \"{outputPath}\" \"{htmlFilePath}\"";

        using var process = new Process
        {
            StartInfo = new ProcessStartInfo
            {
                FileName               = "/usr/bin/htmldoc",   // or path on Windows
                Arguments              = arguments,
                RedirectStandardError  = true,
                UseShellExecute        = false,
                CreateNoWindow         = true
            }
        };

        process.Start();
        process.WaitForExit(30_000);   // 30-second timeout

        if (process.ExitCode != 0)
        {
            var error = process.StandardError.ReadToEnd();
            throw new InvalidOperationException($"HTMLDOC failed (exit {process.ExitCode}): {error}");
        }

        return File.ReadAllBytes(outputPath);
    }
    finally
    {
        // Clean up the temp file regardless of success or failure
        if (File.Exists(outputPath))
            File.Delete(outputPath);
    }
}

Key constraints:

  • Binary path must be correct for every target OS; differs between Windows and Linux
  • Temporary file creation requires write permissions; temp directory must be writable in containers
  • WaitForExit() timeout must be tuned; too short produces silent failures on large documents
  • Exit code 0 does not always mean a valid PDF was produced; the output file should be validated
  • Concurrent calls create separate processes; memory and CPU pressure scales linearly with concurrency
  • JavaScript-dependent HTML content silently produces empty or malformed sections

IronPDF — HTML File to PDF

IronPDF renders the HTML file in-process with no temporary file management. The HTML file to PDF guide documents path handling and base URL resolution for locally referenced assets.

using IronPdf;
using System.IO;

// IronPdf.License.LicenseKey = "YOUR-LICENSE-KEY"; // Set at application startup

using var renderer = new ChromePdfRenderer();

// Configure paper size and margins (previously done via HTMLDOC CLI flags)
renderer.RenderingOptions.PaperSize        = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop        = 10;
renderer.RenderingOptions.MarginBottom     = 10;
renderer.RenderingOptions.MarginLeft       = 10;
renderer.RenderingOptions.MarginRight      = 10;
renderer.RenderingOptions.PrintBackground  = true;

// Render the HTML file — no temp file, no process launch
string inputPath = Path.GetFullPath("/input/report.html");
using var pdf = renderer.RenderHtmlFileAsPdf(inputPath);

// Return as bytes or save to file
byte[] pdfBytes = pdf.BinaryData;
// pdf.SaveAs("/output/report.pdf");

Relative asset paths (stylesheets, images referenced with ../ or ./) resolve against the HTML file's directory. For assets hosted at a different base URL, configure RenderingOptions.BaseUrl

HTML String to PDF

HTMLDOC — HTML String to PDF

HTMLDOC reads from files or URLs; it does not accept HTML via stdin in its standard usage. Teams generating HTML strings must write the content to a temporary file before invoking HTMLDOC, then clean up after. This adds filesystem I/O and cleanup logic to every render call.

using System;
using System.Diagnostics;
using System.IO;

public static byte[] ConvertHtmlStringToPdf(string html)
{
    // HTMLDOC does not accept HTML via stdin in standard usage
    // Must write to a temp file first
    var inputPath  = Path.Combine(Path.GetTempPath(), $"{Guid.NewGuid()}.html");
    var outputPath = Path.Combine(Path.GetTempPath(), $"{Guid.NewGuid()}.pdf");

    try
    {
        File.WriteAllText(inputPath, html, System.Text.Encoding.UTF8);

        using var process = new Process
        {
            StartInfo = new ProcessStartInfo
            {
                FileName               = "/usr/bin/htmldoc",
                Arguments              = $"--continuous --quiet --webpage -f \"{outputPath}\" \"{inputPath}\"",
                RedirectStandardError  = true,
                UseShellExecute        = false,
                CreateNoWindow         = true
            }
        };

        process.Start();
        process.WaitForExit(30_000);

        if (process.ExitCode != 0)
            throw new InvalidOperationException($"HTMLDOC conversion failed (exit {process.ExitCode})");

        return File.ReadAllBytes(outputPath);
    }
    finally
    {
        if (File.Exists(inputPath))  File.Delete(inputPath);
        if (File.Exists(outputPath)) File.Delete(outputPath);
    }
}

Key constraints:

  • Two temporary files created per render call; cleanup must handle exceptions at each step
  • HTML encoding edge cases (templates with encoding other than UTF-8) require explicit handling
  • Concurrent renders multiply temp file creation; high-throughput scenarios can saturate the temp directory
  • No base URL available for resolving relative asset references within the string

IronPDF — HTML String to PDF

IronPDF accepts HTML strings directly with no temp file step. The HTML string to PDF examples illustrate the full range of render options available, including inline style, external stylesheet links, and embedded SVG.

using IronPdf;

using var renderer = new ChromePdfRenderer();

// Accept the HTML string directly — no temp file required
string html = @"
<!DOCTYPE html>
<html>
<head>
  <style>
    body { font-family: Arial, sans-serif; margin: 20px; }
    h1   { color: #333; }
    table { border-collapse: collapse; width: 100%; }
    td, th { border: 1px solid #ccc; padding: 6px; }
  </style>
</head>
<body>
  <h1>Monthly Report</h1>
  <table>
    <tr><th>Item</th><th>Value</th></tr>
    <tr><td>Revenue</td><td>$42,000</td></tr>
    <tr><td>Expenses</td><td>$18,500</td></tr>
  </table>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("/output/monthly-report.pdf");

Encoding is handled by the managed API; no explicit UTF-8 write step is required. Base URLs for resolving relative paths within the HTML string can be provided as a second argument to RenderHtmlAsPdf()

Headers and Footers

HTMLDOC — Headers and Footers

HTMLDOC provides --header and --footer CLI flags that accept three-character format strings (left, center, right fields) using tokens such as . (blank), t (title), h (current chapter heading), 1 (page number), / (last page number), and d (date). These are limited to plain text substitution with no HTML or CSS styling.

using System.Diagnostics;

// HTMLDOC header/footer via CLI flags
// --header and --footer accept 3-char format strings: left/center/right
// Tokens: '.' = blank, '1' = page number, '/' = total pages, 'd' = date, 't' = title
// Example: center-aligned page number "Page 1 of 5"

var arguments =
    "--continuous --quiet --webpage " +
    "--header ..t " +                       // center: document title; left/right blank
    "--footer .1. " +                       // center: page number; left/right blank
    "-f \"/output/document.pdf\" " +
    "\"/input/document.html\"";

// The output headers/footers are plain text only — no CSS, no fonts, no colors

Key constraints:

  • Three-position fixed format (left/center/right only) with no layout flexibility
  • Plain text output only — no font selection, color, or image embedding in headers/footers
  • Limited token set; complex header content (conditional sections, logos) is not expressible
  • Header/footer font and size are controlled by --headfontname, --headfontsize CLI flags

IronPDF — Headers and Footers

IronPDF provides typed TextHeaderFooter and HtmlHeaderFooter objects that allow full HTML/CSS header and footer content including images, colors, and dynamic per-page data. The headers and footers guide covers both approaches, and the HTML headers and footers example shows the HTML approach in detail.

using IronPdf;

using var renderer = new ChromePdfRenderer();

// HTML header — full HTML/CSS, replaces HTMLDOC's 3-token text header
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height       = 18,
    HtmlFragment = @"
        <div style='display:flex; justify-content:space-between;
                    font-family:Arial; font-size:10px; color:#666;
                    padding:0 10px; border-bottom:1px solid #ccc;'>
            <span>Confidential — Internal Report</span>
            <span>{date}</span>
        </div>"
};

// Text footer — simpler alternative for plain-text needs
renderer.RenderingOptions.TextFooter = new TextHeaderFooter
{
    CenterText = "Page {page} of {total-pages}",
    FontSize   = 9
};

using var pdf = renderer.RenderHtmlAsPdf("<h1>Report</h1><p>Body content.</p>");
pdf.SaveAs("/output/report-with-headers.pdf");

The {page}, {total-pages}, {date}, and related tokens are substituted at render time. Unlike HTMLDOC's fixed three-column layout, HtmlHeaderFooter accepts arbitrary HTML, allowing images, multi-column layouts, and conditional content.

URL to PDF

HTMLDOC — URL to PDF

HTMLDOC accepts HTTP/HTTPS URLs directly as input arguments. It fetches the page, parses the HTML, and renders it. However, because HTMLDOC does not execute JavaScript, any content rendered client-side — single-page application content, dynamically loaded data, JavaScript-drawn charts — produces an empty or partial render.

Key constraints:

  • No JavaScript execution; SPAs and JS-rendered content produce empty or partial output
  • No session/cookie support for authenticated pages in standard usage
  • Redirect handling may differ from browser behavior
  • HTMLDOC's CSS support is limited; modern web pages often render poorly

IronPDF — URL to PDF

IronPDF's URL rendering uses Chromium, so JavaScript-rendered content, CSS animations that resolve to a stable state, and dynamic data loaded via fetch() are all captured. The URL to PDF guide covers wait conditions, cookie injection for authenticated pages, and request header configuration.

using IronPdf;

using var renderer = new ChromePdfRenderer();

// Enable JavaScript and wait for network-loaded content to resolve
renderer.RenderingOptions.EnableJavaScript = true;
renderer.RenderingOptions.WaitFor.NetworkIdle(500);   // verify WaitFor API in current docs

using var pdf = renderer.RenderUrlAsPdf("https://example.com/dashboard");
pdf.SaveAs("/output/dashboard-snapshot.pdf");

For pages behind authentication, inject session cookies via RenderingOptions.CustomCookies or use the login helper

Breaking Changes & Gotchas

  • Process model removed entirely. All Process.Start(), WaitForExit(), exit code checking, and stdout/stderr capture code is removed, not migrated. This is a simplification, but every call site that launches HTMLDOC must be identified and refactored.
  • Temporary file management removed. HTMLDOC integrations typically create and delete temporary HTML input and PDF output files. With IronPDF, this filesystem I/O disappears. Review cleanup logic carefully to avoid leaving orphaned temp files after migration.
  • CSS rendering differences. HTMLDOC uses its own layout engine with limited CSS support. Templates authored to work around HTMLDOC's CSS limitations may produce different (often better) output under Chromium. After migration, review templates and remove workarounds that were added specifically for HTMLDOC compatibility.
  • JavaScript now executes. HTMLDOC silently ignores JavaScript. IronPDF executes it via Chromium. If HTML templates contain JavaScript that modifies the DOM or triggers side effects, that JavaScript will run during PDF rendering. Verify that all scripts in render templates are safe to execute in this context.
  • Header/footer format change. HTMLDOC's --header and --footer token strings do not map to IronPDF's TextHeaderFooter or HtmlHeaderFooter objects directly. Each header/footer configuration must be individually translated to an IronPDF *HeaderFooter object with the appropriate token syntax.
  • Namespace and package. HTMLDOC has no .NET namespace. IronPDF types are under IronPdf. Add using IronPdf; to all affected files. The IronPdf NuGet package replaces the binary installation step.
  • License initialization. IronPDF requires a license key set at startup. HTMLDOC requires no license management in the application. Add the initialization call and manage the key as an environment secret.
  • Chromium binary dependency. On Linux, IronPDF requires Chromium system dependencies. Dockerfiles and server provisioning scripts that previously only needed to install the htmldoc binary now need the appropriate Chromium dependency packages.
  • Error signaling model. HTMLDOC communicates errors via process exit codes and stderr. IronPDF throws managed exceptions. Error handling code built around exit code checks must be replaced with try/catch blocks.
  • Concurrency model. HTMLDOC scales by launching multiple processes; each invocation is isolated. IronPDF scales within the managed runtime; create a new ChromePdfRenderer per thread for concurrent workloads. Memory usage per concurrent render is different from the process-per-render model.

Migration Checklist

  1. Inventory all HTMLDOC call sites. Search for Process.Start, htmldoc, and temporary file patterns. Document each call site's input type (file, URL, string), options used, and output handling.
  2. Map CLI flags to RenderingOptions. For each HTMLDOC invocation, list the CLI flags used and identify the corresponding ChromePdfRenderOptions property. Pay particular attention to margin units
  3. Add the IronPDF NuGet package. dotnet add package IronPdf. No binary installation step is required on Windows; verify Linux dependency setup in IronPDF documentation for container targets.
  4. Configure the license key. Add IronPdf.License.LicenseKey = "YOUR-KEY"; to application startup. Store the key as an environment variable or secrets manager entry. See the license key guide.
  5. Add using IronPdf; directives. Update all files that previously contained HTMLDOC process wrapper code.
  6. Replace process launch code. For each call site, remove the Process.Start() pattern and replace with a ChromePdfRenderer instantiation and the appropriate Render*AsPdf() call. Remove all temp file creation and deletion logic.
  7. Migrate render options. Translate CLI flags to RenderingOptions properties: paper size, orientation, margins, background printing, and JavaScript settings.
  8. Translate headers and footers. Rewrite HTMLDOC --header and --footer token strings as HtmlHeaderFooter or TextHeaderFooter objects. Update page number and date token syntax to IronPDF's {page}, {total-pages}, {date} format.
  9. Update error handling. Replace exit-code checks with try/catch blocks around Render*AsPdf() calls. Replace stderr capture logic with IronPDF's logging configuration if detailed diagnostics are needed.
  10. Review HTML templates. After migration, review all templates for CSS workarounds that were added to accommodate HTMLDOC's limitations. Remove or simplify workarounds now that Chromium renders the templates.
  11. Update container and deployment configuration. Add IronPDF Chromium dependency installation to Dockerfiles and deployment scripts. Remove htmldoc binary installation steps.
  12. Run output comparison. Generate PDF output from both HTMLDOC and IronPDF for each document type in the system. Compare visually. Expect layout improvements in CSS-heavy sections; investigate any regressions in text-only sections where HTMLDOC and Chromium differ.

Conclusion

When staying on HTMLDOC is technically reasonable: If the application generates simple, text-heavy documents with minimal CSS, no JavaScript, and the server environment is stable (no containerization plans, no platform migrations), HTMLDOC's process-based integration may be adequate. The open-source and no-license-cost profile is a concrete advantage for projects where commercial library procurement is a friction point.

Signals that indicate migration is worth the engineering effort: The clearest signals are rendering quality gaps — documents that require modern CSS layouts, web fonts, or JavaScript-rendered content where HTMLDOC's output is inadequate. Platform migration signals are also strong: containerization, managed PaaS deployment, or security policies that restrict child process spawning each make the process-based model increasingly difficult to sustain. Teams that are investing engineering effort in maintaining the process wrapper, handling timeout edge cases, or managing temp file cleanup in high-concurrency scenarios will find that the migration pays for itself through simplified operational code.

What the cutover typically involves at the code level: The process wrapper code is the primary removal target — Process.Start(), argument construction, exit code handling, and temp file management. The replacement is ChromePdfRenderer and a Render*AsPdf() call, which is mechanically straightforward once CLI flag-to-RenderingOptions mapping is complete. Header/footer translation requires attention because the token formats differ. The HTML to PDF rendering guide provides a reference for the full option set available to replace HTMLDOC's CLI flags.
