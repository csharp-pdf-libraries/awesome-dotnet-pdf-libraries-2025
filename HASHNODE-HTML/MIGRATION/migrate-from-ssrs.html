# Migrating from SSRS to IronPDF: what changes, what breaks, what maps

The original version of this article is published at https://ironsoftware.com/csharp/pdf/blog/migrate-from-ssrs/.

Framing

SQL Server Reporting Services has been the default choice for PDF report generation in Microsoft-stack organizations for over two decades. Its tight integration with SQL Server, Active Directory, and the broader Microsoft BI ecosystem made it the path of least resistance for teams that needed parameterized reports, scheduled delivery, and centralized management. For many organizations, SSRS was not actively chosen so much as inherited—already running on an on-premises server, already serving dozens of report consumers, already integrated into the enterprise data infrastructure.

Re-evaluation of SSRS typically surfaces as part of larger modernization efforts rather than isolated PDF library decisions. Migration to cloud infrastructure (Azure, AWS) that makes SSRS's Windows Server dependency a cost or operational concern, moves away from SQL Server toward alternative data sources, adoption of microservice architectures where a centralized report server is an architectural mismatch, or the need for more dynamic document generation—where the rendered PDF content is driven by application logic rather than a declarative report definition—are the conditions teams most often cite when assessing SSRS alternatives.

IronPDF is not a reporting platform replacement in the SSRS sense. It does not provide a report designer, a report catalog, subscription delivery, or a web portal for report consumers. It is a PDF rendering and manipulation library for use within .NET applications. This distinction is the foundation of an honest migration scoping discussion: teams moving from SSRS to IronPDF are not swapping one server for another—they are taking ownership of data retrieval, layout, and delivery that SSRS previously handled, and bringing that logic into their application tier.

What SSRS Is Designed To Do

SQL Server Reporting Services is a server-based reporting platform that generates paginated reports (RDL-format report definitions) from one or more data sources, delivers them in various formats including PDF, Excel, and Word, and offers a web-based portal for report browsing, scheduling, and subscription management. Reports are authored using SQL Server Data Tools (SSDT) or Report Builder, which produce RDL XML files defining data queries, layout, parameters, and expressions.

SSRS's architecture is service-based: the Report Server Windows Service processes report execution requests, connects to configured data sources, evaluates RDL layout definitions, and renders output to the requested format. The PDF rendering extension is built into the platform. Client applications interact with SSRS via the Report Server Web Service (SOAP API), the newer REST API (ReportingService2010 and later

Architectural Differences

IronPDF's integration model has no analog in the SSRS architecture. There is no separate server, no report catalog, no RDL format, and no designer tool. A .NET application that uses IronPDF generates PDFs in-process: the application fetches data, builds an HTML template (or assembles a document via the manipulation API), and calls the renderer. The result is a PdfDocument object that can be saved, streamed to an HTTP response, attached to an email, or further processed—all within the same application process.

This in-process model places responsibility for data retrieval and template logic squarely in the application. The HTML string to PDF rendering pipeline accepts any valid HTML; a team migrating SSRS reports typically implements an HTML templating layer (Razor, Scriban, Handlebars.NET, or simple string interpolation for straightforward layouts) that replaces RDL's expression language and tablix layout model. CSS handles pagination, headers, footers, and page numbering at the template level.

PdfDocument and ChromePdfRenderer both implement IDisposable. In a web application context, each rendering call should instantiate a ChromePdfRenderer (or reuse a shared, thread-safe instance) and wrap the returned PdfDocument in a using block. There is no equivalent to SSRS session management, subscription queuing, or report server caching—teams that relied on those features must implement analogous capabilities in the application tier if needed. The rendering options reference covers the full configuration surface for paper size, margins, JavaScript behavior, and CSS media type selection.

Operation Comparisons

Parameterized Report to PDF

SSRS — Parameterized Report Execution via Web Service:

SSRS report execution with parameters is invoked through the Report Server Web Service. A .NET application calls ExecuteReport with a parameter array and receives a byte array of the rendered PDF.

// SSRS parameterized report execution — conceptual outline
// Verify exact endpoint, binding, and method names in current SSRS documentation
using System.Net;

// ReportExecutionService is a generated SOAP proxy
// var svc = new ReportExecutionServiceSoapClient(...);
// svc.ClientCredentials.Windows.ClientCredential = CredentialCache.DefaultNetworkCredentials;

// var parameters = new ParameterValue[]
// {
//     new ParameterValue { Name = "StartDate", Value = "2025-01-01" },
//     new ParameterValue { Name = "Region", Value = "North" }
// };

// byte[] reportBytes = svc.Render(
//     reportPath: "/Reports/SalesReport",
//     format: "PDF",
//     parameters: parameters,
//     ...
// );

// System.IO.File.WriteAllBytes("output.pdf", reportBytes);

Technical constraints:

  • The calling application must have network access to the Report Server endpoint
  • Windows Authentication or Basic Auth must be configured and matched between client and server
  • SOAP proxy classes must be regenerated if the SSRS version changes
  • Report execution timeout is server-configured; long-running data queries may cause client timeouts
  • Error details from rendering failures are surfaced through SOAP faults, which require specific fault handling

IronPDF — Parameterized HTML Template to PDF:

using IronPdf;

// Data retrieval is the application's responsibility
// Example: fetch report data from a repository
var reportData = await salesRepository.GetSalesDataAsync(
    startDate: new DateTime(2025, 1, 1),
    region: "North");

// Build HTML from data using a templating approach
// Razor, Scriban, or simple string interpolation — team's choice
var htmlBuilder = new System.Text.StringBuilder();
htmlBuilder.Append(@"
    <!DOCTYPE html><html><head>
    <style>
        body { font-family: Arial, sans-serif; font-size: 11px; }
        table { width: 100%; border-collapse: collapse; }
        th { background: #4472C4; color: white; padding: 6px; }
        td { border: 1px solid #ddd; padding: 5px; }
        .total { font-weight: bold; background: #f0f0f0; }
    </style></head><body>");

htmlBuilder.Append($"<h2>Sales Report — {reportData.Region}</h2>");
htmlBuilder.Append($"<p>Period: {reportData.StartDate:yyyy-MM-dd} to {reportData.EndDate:yyyy-MM-dd}</p>");
htmlBuilder.Append("<table><tr><th>Product</th><th>Units</th><th>Revenue</th></tr>");

foreach (var row in reportData.Lines)
{
    htmlBuilder.Append($"<tr><td>{row.Product}</td><td>{row.Units}</td><td>{row.Revenue:C}</td></tr>");
}

htmlBuilder.Append("</table></body></html>");

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.Letter;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 20;

using var pdf = renderer.RenderHtmlAsPdf(htmlBuilder.ToString());
pdf.SaveAs($"SalesReport_{reportData.Region}_{DateTime.Today:yyyyMMdd}.pdf");

The application now owns the data access, the template logic, and the rendering call. The HTML string to PDF guide covers base URL configuration for templates referencing external CSS files or shared image assets like company logos.

Headers, Footers, and Page Numbers

SSRS — Report Headers and Footers:

SSRS RDL defines report headers and footers in the report definition file. Header/footer items are placed using a visual designer, and page number expressions (=Globals!PageNumber and =Globals!TotalPages) are embedded in text boxes. Headers and footers render on every page of the paginated report automatically.

Technical constraints:

  • Header/footer content is defined in RDL XML, not in application code; changes require updating the RDL file and redeploying to the report server
  • The visual designer constrains layout to predefined items (text boxes, images, lines)
  • Expressions use SSRS's VBA-like expression language, which does not transfer to any .NET templating model
  • First-page header suppression and section-specific footers require conditional expressions in RDL

IronPDF — Headers and Footers:

using IronPdf;
using IronPdf.Engines.Chrome;

var renderer = new ChromePdfRenderer();

// Text-based header with company name centered
renderer.RenderingOptions.TextHeader = new TextHeaderFooter
{
    CenterText = "ACME Corporation — Confidential",
    DrawDividerLine = true,
    FontSize = 9
};

// Footer with date on left and page numbers on right
renderer.RenderingOptions.TextFooter = new TextHeaderFooter
{
    LeftText = "Generated: {date}",
    RightText = "Page {page} of {total-pages}",
    DrawDividerLine = true,
    FontSize = 8
};

using var pdf = renderer.RenderHtmlAsPdf(reportHtml);
pdf.SaveAs("report-with-headers.pdf");

For headers and footers that require HTML content—company logos, styled typography, multi-column layouts—IronPDF supports HTML-based header and footer objects. The headers and footers guide covers text tokens for dynamic values ({page}, {total-pages}, {date}), HTML variants, and per-first-page suppression.

Delivering PDF via ASP.NET HTTP Response

SSRS — URL Access PDF Delivery:

SSRS URL Access allows a browser or server-side application to request a report rendered to PDF via an HTTP GET to the report server. The response is a PDF byte stream.

// SSRS URL Access — server-side consumption conceptual outline
// Verify current URL format in SSRS documentation for your version
using System.Net.Http;

// URL Access format (varies by SSRS version):
// https://reportserver/reportserver?
//   /Reports/SalesReport&rs:Format=PDF&StartDate=2025-01-01

// var client = new HttpClient();
// client.DefaultRequestHeaders.Authorization = ...;
// var pdfBytes = await client.GetByteArrayAsync(reportUrl);
// return File(pdfBytes, "application/pdf", "report.pdf");

Technical constraints:

  • The web application server must have network access to the SSRS report server
  • URL Access requires authentication (Windows Integrated, Forms, or Basic
  • Report parameter values are embedded in the URL query string; URL encoding must be handled correctly for special characters
  • PDF size is determined by SSRS; no application-level control over rendering options

IronPDF — Stream PDF to ASP.NET Response:

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { [HttpGet("sales")] public async Task GetSalesReport( [FromQuery] DateTime startDate, [FromQuery] string region) { // Fetch data and build HTML template var html = await BuildSalesReportHtmlAsync(startDate, region);

var renderer = new ChromePdfRenderer(); renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.Letter;

using var pdf = renderer.RenderHtmlAsPdf(html);

// Stream the PDF bytes directly to the response var pdfBytes = pdf.BinaryData; return File(pdfBytes, "application/pdf", $"SalesReport_{region}_{startDate:yyyyMMdd}.pdf"); }

The application is responsible for authentication on its own endpoints using standard ASP.NET middleware—no separate SSRS authentication configuration to maintain.

Multi-Report Merge

SSRS — Combining Multiple Reports:

SSRS does not natively support merging multiple report outputs into a single PDF at the server level. Organizations that need combined output—a cover page from one report definition appended to a data report—typically download both PDFs and combine them with a separate tool or library.

Technical constraints:

  • SSRS produces individual report outputs per execution; document assembly requires out-of-band processing
  • No API for server-side report concatenation in standard SSRS
  • Timing coordination between multiple report executions can be complex for parameterized, long-running reports

IronPDF — Merge Multiple Generated PDFs:

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.Letter;

// Generate each section in-process
using var coverPage = renderer.RenderHtmlAsPdf(coverPageHtml);
using var dataSection = renderer.RenderHtmlAsPdf(dataSectionHtml);
using var appendixSection = renderer.RenderHtmlAsPdf(appendixHtml);

// Merge into single document
using var fullReport = PdfDocument.Merge(coverPage, dataSection, appendixSection);
fullReport.SaveAs("combined-report.pdf");

The merge and split guide covers merging from streams and byte arrays as well as from PdfDocument instances, which is useful when combining in-process renders with externally sourced PDF files.

Breaking Changes & Gotchas

  • RDL is not portable. Every SSRS report definition must be redesigned as an HTML template. There is no automated conversion from RDL to HTML; the data queries, layout definitions, and expressions must be reconstructed in the application tier. Treat each report as a new development task proportional to its complexity.
  • Data access responsibility shifts entirely. SSRS handles data source connections and query execution as part of report processing. After migration, the application is responsible for all data retrieval before calling the renderer. Audit all report datasets and their associated queries; these become application-layer data access methods.
  • No report portal. If end users currently browse and run reports through the SSRS web portal, that interface must be replaced. Typical approaches include a custom report catalog page in the application, a link-based report trigger system, or an embedded iframe pointing to rendered PDFs in blob storage. None of these come from IronPDF.
  • No built-in scheduling. SSRS subscriptions and scheduled report delivery must be reimplemented using application-level schedulers (Hangfire, Quartz.NET, Azure Functions timer triggers). The PDF rendering call is straightforward; the scheduling infrastructure is the engineering work.
  • Chromium binary dependencies on Linux. IronPDF ships platform-specific Chromium binaries. Linux container deployments require system packages for Chromium operation. Minimal base images will fail without these dependencies added to the Dockerfile.
  • Disposal is mandatory. Every PdfDocument object must be disposed. SSRS delivers a byte array; there is no disposal concern in that model. The shift to IDisposable-based objects requires systematic use of using blocks.
  • Interactive report features do not translate. SSRS supports drillthrough actions, toggle visibility, sorting, and document map navigation in its HTML rendering. None of these interactive features exist in a static PDF. If report consumers rely on interactive features, assess whether the use case genuinely requires a PDF or whether a web-based report UI would serve better.
  • Thread safety in high-throughput scenarios. ChromePdfRenderer is thread-safe; however, the Chromium engine carries memory overhead per render. Refer to the official documentation the recommended pattern for high-concurrency rendering (shared renderer vs. per-request instantiation) to avoid resource exhaustion under load.

Migration Checklist

  1. Catalog all SSRS reports. List every report definition in use: name, data sources, parameter definitions, estimated complexity (simple list, tablix, matrix, chart-heavy). This inventory drives the effort estimate for template development.
  2. Assess interactive feature dependencies. For each report, determine whether end users rely on interactive SSRS features (drillthrough, toggle visibility, document map). These do not translate to PDF; some may require a separate web-based report UI to replace.
  3. Plan the scheduling and delivery replacement. If subscriptions or scheduled delivery are in use, define the application-tier scheduler before beginning PDF rendering work. Hangfire, Quartz.NET, and Azure Functions timer triggers are common approaches.
  4. Install the IronPDF NuGet package. Run dotnet add package IronPdf. Verify runtime identifier coverage for all target environments.
  5. Configure the license key. Set the IronPDF license key at application startup. See the license key setup guide for configuration options compatible with secret management practices.
  6. Migrate data access to the application tier. For each SSRS dataset, implement a corresponding data access method in the application (repository, service, or query object). Validate that the query results match SSRS dataset output.
  7. Develop HTML templates for each report type. Convert each RDL report definition to an HTML/CSS template. Begin with the simplest reports (single-table lists) and work toward complex matrix and chart reports. Validate output against SSRS reference output.
  8. Implement headers, footers, and page numbers. Configure RenderingOptions.TextHeader and TextFooter or HTML header/footer objects for reports that require company branding, report titles, and page number tokens.
  9. Implement the report delivery mechanism. For on-demand reports, implement the ASP.NET controller or service that accepts parameters, renders the PDF, and streams the response. For scheduled reports, implement the scheduler and delivery integration (email, blob storage, file share).
  10. Replace the ReportViewer control if present. If the application embeds a ReportViewer control in ASP.NET WebForms or WinForms, source and integrate a replacement PDF viewer component for the end-user display scenario.
  11. Test PDF output across all report types. Validate layout, pagination, data accuracy, header/footer content, and file size across the full report catalog. Use a representative sample of real data to surface layout edge cases.
  12. Decommission SSRS infrastructure. After all reports have been migrated and validated, schedule the SSRS server for decommission. Update monitoring, backup, and operational runbooks to remove SSRS-specific items.

Conclusion

When staying on SSRS is technically reasonable

SSRS remains a practical choice for organizations whose reporting workload fits the platform's strengths: paginated reports from SQL Server data sources, centralized report delivery via subscriptions, end-user self-service through the web portal, and integration with Power BI Report Server as a modernized successor. If the report catalog is large, the end users are accustomed to the SSRS portal, the data sources are primarily SQL Server, and the organization is not moving away from Windows Server infrastructure, the migration cost is substantial and the benefit may not justify it. SSRS's visual designer also represents a real productivity advantage for authoring complex tablix layouts that would take significantly longer to implement in HTML/CSS templates.

Signals that indicate migration is worth the engineering effort

Migration makes sense when the infrastructure context changes in ways that make SSRS's architecture a burden: cloud deployment that requires Linux containers, microservice architectures where a centralized report server is an operational outlier, or adoption of non-SQL Server data sources that SSRS cannot connect to natively. Teams generating PDFs as part of application workflows—invoice generation, document assembly, contract production—often find that SSRS's report-centric model is a poor fit for programmatic PDF generation needs, and that an in-process library handles those use cases more directly. If the SSRS server has become a maintenance liability (aging Windows Server OS, outdated SQL Server instance, unclear ownership), that operational risk is a concrete migration signal.

What the cutover typically involves at the code level

The code-level work is larger than a typical library migration because the application must absorb responsibilities that SSRS previously owned: data retrieval, template logic, scheduling, and delivery. The PDF rendering call itself is straightforward; the surrounding infrastructure is the effort. Teams that approach the migration in phases—stand up the rendering capability first with one or two simple reports, then migrate report-by-report while SSRS remains available, then decommission—tend to manage risk better than teams that attempt a full cutover. The rendering quality of Chromium-based HTML output is generally high for well-structured templates; the engineering investment is in building those templates and the data access layer that feeds them.

How does your team's current report catalog break down between simple parameterized lists and complex matrix or chart-heavy reports, and how does that ratio influence whether a phased or full-cutover migration strategy makes more sense?
