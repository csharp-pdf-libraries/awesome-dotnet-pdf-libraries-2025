Migrating from DinkToPdf to IronPDF: step-by-step for .NET developers

what changes, what breaks, and what maps cleanly

Framing

In the years before Chromium-based PDF generation became the standard, wkhtmltopdf was the most practical choice for server-side HTML-to-PDF conversion in .NET applications. It was free, capable, and — via P/Invoke wrappers — embeddable in .NET processes without spawning a subprocess. DinkToPdf emerged as a popular open-source .NET wrapper for the underlying libwkhtmltox native library, giving ASP.NET Core developers a structured API for driving wkhtmltopdf's rendering engine without managing native interop directly.

The library has been archived or moved into maintenance-only status — the product status and last release should be verified in official documentation or the project's repository. This matters because wkhtmltopdf itself, the underlying rendering engine, has been in maintenance mode for some time. The Qt WebKit rendering engine that powers it has not tracked the evolution of web standards, and the documented incompatibilities — with CSS Flexbox, Grid, custom properties, modern JavaScript, and web fonts — accumulate as application front-ends adopt modern CSS practices.

Teams that adopted DinkToPdf are now in one of two positions: still running templates that were written around wkhtmltopdf's limitations, or incrementally fighting rendering bugs as their HTML templates modernize. Either way, the migration to a Chromium-based in-process renderer is a predictable path with well-understood scope. This guide covers that path from DinkToPdf to IronPDF — the architectural shift, the API mapping, the breaking changes, and the checklist.

What DinkToPdf Is Designed to Do

DinkToPdf is an open-source .NET library that wraps the wkhtmltopdf native library (libwkhtmltox) using P/Invoke, allowing .NET applications to drive wkhtmltopdf's HTML-to-PDF rendering engine in-process without shelling out to a command-line process. The library exposes a converter interface backed by SynchronizedConverter (thread-safe, uses a global lock) and BasicConverter (not thread-safe, for single-threaded use), both accepting a HtmlToPdfDocument configuration object.

The install footprint is multi-package: the managed NuGet package plus the native libwkhtmltox binaries (.dll for Windows, .so for Linux, .dylib for macOS), which must be deployed alongside the application. The rendering engine is QtWebKit — not Chromium — which means the HTML rendering behavior follows an older WebKit snapshot rather than the current Chromium engine. The primary use case should be verified in the project's documentation, but DinkToPdf is commonly found in ASP.NET Core report generation, invoice rendering, and document export features where an open-source, zero-licensing-cost solution was chosen. The product status should be verified, as the library has not received active commits for an extended period.

Architectural Differences

DinkToPdf and IronPDF share the same high-level architecture: HTML input, in-process rendering, PDF output. The differences are in the rendering engine, the deployment model, and the API surface available after rendering.

DinkToPdf drives wkhtmltopdf (QtWebKit) in-process via P/Invoke. IronPDF drives an embedded Chromium engine in-process via its own managed wrapper. Chromium tracks current web standards; QtWebKit does not. For teams with modern CSS templates, this engine change is the primary motivation — the migration resolves rendering bugs rather than introducing them.

IronPDF's two key types are ChromePdfRenderer (rendering configuration and execution) and PdfDocument (the rendered result and its manipulation API). Unlike DinkToPdf's IConverter.Convert() which returns a byte[] immediately with no cleanup required, IronPDF's RenderHtmlAsPdf() returns a PdfDocument that implements IDisposable and must be wrapped in a using block. The PdfDocument also exposes a full document manipulation API — merge, split, sign, form-fill, encrypt — that has no equivalent in DinkToPdf. The rendering options reference covers the full configuration surface. License initialization is a one-time startup call via IronPdf.License.LicenseKey — see the license setup guide.

Operation Comparisons

HTML String to PDF

DinkToPdf — HTML String to PDF

using DinkToPdf;
using DinkToPdf.Contracts;

// DinkToPdf DI setup (Program.cs):
// services.AddSingleton(typeof(IConverter), new SynchronizedConverter(new PdfTools()));
// The native libwkhtmltox binary must also be loaded — see CustomAssemblyLoadContext pattern

public class InvoiceService
{
    private readonly IConverter _converter;

    public InvoiceService(IConverter converter)
    {
        _converter = converter;
    }

    public byte[] CreateInvoice(string htmlContent)
    {
        var doc = new HtmlToPdfDocument
        {
            GlobalSettings = new GlobalSettings
            {
                PaperSize = PaperKind.A4,
                Orientation = Orientation.Portrait,
                Margins = new MarginSettings { Top = 10, Bottom = 10, Left = 15, Right = 15 }
            },
            Objects =
            {
                new ObjectSettings
                {
                    HtmlContent = htmlContent,
                    WebSettings = new WebSettings
                    {
                        DefaultEncoding = "utf-8",
                        Background = true
                    }
                }
            }
        };

        // Returns byte[] directly — no disposal required on result
        return _converter.Convert(doc);
    }
}

Concrete constraints:

  • The native libwkhtmltox binary must be present at deployment. On Linux, this is typically a .so file deployed next to the application executable or loaded via CustomAssemblyLoadContext.
  • SynchronizedConverter serializes all conversion requests through an internal mutex — useful for thread safety but a throughput bottleneck under concurrent load.
  • wkhtmltopdf does not support CSS Flexbox, CSS Grid, calc() in some contexts, @font-face web fonts from CDN, or many CSS custom properties. Templates must be written around these constraints.
  • JavaScript rendering is unreliable — SPAs, lazy-loaded content, and animations do not render correctly.
  • The library's maintenance status means bugs are not being fixed.

IronPDF — HTML String to PDF

using IronPdf;

// IronPDF DI setup (Program.cs):
// IronPdf.License.LicenseKey = "YOUR-KEY";
// builder.Services.AddSingleton<ChromePdfRenderer>();

public class InvoiceService
{
    private readonly ChromePdfRenderer _renderer;

    public InvoiceService(ChromePdfRenderer renderer)
    {
        _renderer = renderer;
        // Configure rendering options once on the renderer
        _renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
        _renderer.RenderingOptions.PaperOrientation = IronPdf.Rendering.PdfPaperOrientation.Portrait;
        _renderer.RenderingOptions.MarginTop = 10;
        _renderer.RenderingOptions.MarginBottom = 10;
        _renderer.RenderingOptions.MarginLeft = 15;
        _renderer.RenderingOptions.MarginRight = 15;
        _renderer.RenderingOptions.PrintBackground = true;
    }

    public byte[] CreateInvoice(string htmlContent)
    {
        // PdfDocument is IDisposable — using block ensures cleanup
        using var pdf = _renderer.RenderHtmlAsPdf(htmlContent);
        return pdf.BinaryData; // Replaces IConverter.Convert() return value
    }
}

Full rendering configuration including encoding, viewport, CSS media type, and JavaScript execution options is documented in the HTML string to PDF guide. The switch to Chromium means existing wkhtmltopdf CSS workarounds can be removed — standard CSS now works as expected.

Async Rendering in ASP.NET Core

DinkToPdf — Async Context

using DinkToPdf;
using DinkToPdf.Contracts;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("documents")] public class DocumentController : ControllerBase { private readonly IConverter _converter;

public DocumentController(IConverter converter) { _converter = converter; }

[HttpGet("{id}/pdf")] public async Task GetDocument(int id) { // DinkToPdf.IConverter.Convert() is synchronous // It must be called on a background thread to avoid blocking the thread pool string html = await BuildDocumentHtmlAsync(id);

byte[] pdfBytes = await Task.Run(() => { var doc = new HtmlToPdfDocument { GlobalSettings = new GlobalSettings { PaperSize = PaperKind.A4 }, Objects = { new ObjectSettings { HtmlContent = html } } }; return _converter.Convert(doc); });

return File(pdfBytes, "application/pdf", $"document-{id}.pdf"); }

private async Task BuildDocumentHtmlAsync(int id) => await Task.FromResult($"

Document {id}

"); }

Concrete constraints:

  • IConverter.Convert() is synchronous and blocks the calling thread. In an async ASP.NET Core controller, it must be offloaded to Task.Run() to avoid blocking the thread pool — a common source of thread pool exhaustion under load.
  • SynchronizedConverter's internal lock means concurrent requests queue behind each other even on Task.Run().
  • There is no native async API.

IronPDF — Async Rendering

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("documents")] public class DocumentController : ControllerBase { private readonly ChromePdfRenderer _renderer;

public DocumentController(ChromePdfRenderer renderer) { _renderer = renderer; }

[HttpGet("{id}/pdf")] public async Task GetDocument(int id) { string html = await BuildDocumentHtmlAsync(id);

// RenderHtmlAsPdfAsync is genuinely async — no Task.Run() wrapper needed using var pdf = await _renderer.RenderHtmlAsPdfAsync(html);

return File(pdf.BinaryData, "application/pdf", $"document-{id}.pdf"); // pdf disposed when File result is written (end of using scope) }

private async Task BuildDocumentHtmlAsync(int id) => await Task.FromResult($"

Document {id}

"); }

RenderHtmlAsPdfAsync returns Task<PdfDocument> and is genuinely async — no Task.Run() wrapper is required. This eliminates the thread pool saturation risk under concurrent load. Full async usage patterns, including parallel batch rendering, are in the async rendering guide.

Headers and Footers

DinkToPdf — Headers and Footers

using DinkToPdf;
using DinkToPdf.Contracts;

public byte[] GenerateWithHeaderFooter(IConverter converter, string html)
{
    var doc = new HtmlToPdfDocument
    {
        GlobalSettings = new GlobalSettings { PaperSize = PaperKind.A4 },
        Objects =
        {
            new ObjectSettings
            {
                HtmlContent = html,
                HeaderSettings = new HeaderSettings
                {
                    FontName = "Arial",
                    FontSize = 9,
                    Center = "Monthly Report",
                    Right = "Page [page] of [toPage]",
                    Line = true,
                    Spacing = 2.812
                },
                FooterSettings = new FooterSettings
                {
                    FontSize = 8,
                    Left = "CONFIDENTIAL",
                    Center = "[date]",
                    Line = false
                }
            }
        }
    };

    return converter.Convert(doc);
}

Concrete constraints:

  • HeaderSettings and FooterSettings accept left/center/right text strings with wkhtmltopdf-specific tokens: [page], [toPage], [date], [title].
  • Font control is limited to name and size — no CSS styling, no images, no multi-column layouts.
  • For richer header/footer content, wkhtmltopdf supports an HTML file via HtmlUrl

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Full HTML allowed in header — token syntax is different from wkhtmltopdf
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 18,
    HtmlFragment = @"
        <div style='font-size:9px; font-family:Arial;
                    display:flex; justify-content:space-between;
                    padding: 0 15px;'>
          <span>Monthly Report</span>
          <span>Page {page} of {total-pages}</span>
        </div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 12,
    HtmlFragment = "<div style='font-size:8px; font-family:Arial;" +
                   "display:flex; justify-content:space-between; padding:0 15px;'>" +
                   "<span>CONFIDENTIAL</span><span>{date}</span></div>"
};

using var pdf = renderer.RenderHtmlAsPdf("<html><body><p>Body.</p></body></html>");
return pdf.BinaryData;

The token name change is the most common source of silent bugs when migrating headers and footers: [page] → {page}, [toPage] → {total-pages}, [date] → {date}. Full configuration including logo images and custom CSS is documented in the headers and footers guide.

PDF Manipulation After Rendering (New Capability)

DinkToPdf produces a byte[] and has no further manipulation API. Once the bytes are returned, any subsequent operation requires a separate library. IronPDF's PdfDocument exposes manipulation operations that were not available in the DinkToPdf model at all.

IronPDF — Post-Render Manipulation

using IronPdf;
using IronPdf.Signing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Render the main document
using var mainPdf = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Main Report</h1></body></html>");

// Load a separately generated cover page
using var coverPage = PdfDocument.FromFile("cover.pdf");

// Merge cover + main in a single call
using var merged = PdfDocument.Merge(coverPage, mainPdf);

// Digitally sign the merged output
var signature = new PdfSignature("cert.pfx", "password")
{
    SigningReason = "Approved"
};
merged.Sign(signature);

// Save the signed, merged PDF
merged.SaveAs("final-report.pdf");

This pattern — render, merge, sign — required three separate libraries when using DinkToPdf (a renderer, a merger, and a signer). In IronPDF, all three operations are on the same PdfDocument type. Merge options are in the merge and split guide, and signing options are in the digital signatures guide.

Breaking Changes & Gotchas

  • Return type change: IConverter.Convert() returns byte[]. ChromePdfRenderer.RenderHtmlAsPdf() returns PdfDocument. Every call site must be updated to access pdf.BinaryData for the bytes, and every PdfDocument must be wrapped in a using block. Missing the using block causes unmanaged resource leaks.
  • Synchronous vs async: DinkToPdf is synchronous. Using it in async ASP.NET Core handlers typically requires a Task.Run() wrapper. IronPDF provides genuine async methods — remove the Task.Run() wrappers and use RenderHtmlAsPdfAsync() directly.
  • Token syntax in headers/footers: [page] → {page}, [toPage] → {total-pages}, [date] → {date}. This is a silent error — the old tokens render as literal strings [page] in IronPDF output if not updated.
  • HtmlToPdfDocument has no equivalent: DinkToPdf's configuration object is replaced by direct property assignment on RenderingOptions. There is no configuration object to construct.
  • DI registration change: Remove SynchronizedConverter, BasicConverter, PdfTools, and CustomAssemblyLoadContext. Register ChromePdfRenderer as singleton. Update all injection points from IConverter to ChromePdfRenderer.
  • Native binary deployment: DinkToPdf requires libwkhtmltox to be deployed. IronPDF on Windows resolves Chromium via NuGet. On Linux, different system packages are required
  • CSS regression testing required: Chromium and QtWebKit render the same HTML differently. Layouts that were written around wkhtmltopdf limitations may need adjustment. Layouts that were broken in wkhtmltopdf may now render correctly without workarounds. Both types of change require a visual comparison pass.
  • License key required: IronPdf.License.LicenseKey must be set at startup. DinkToPdf has no license key. Omitting it produces watermarked output.
  • Namespace change: Replace using DinkToPdf; and using DinkToPdf.Contracts; with using IronPdf;. Compile errors guide the remaining work.
  • No IConverter interface: IronPDF does not expose a renderer interface. If the application uses IConverter for unit test mocking, create a custom interface that wraps ChromePdfRenderer for the test boundary.

Migration Checklist

  1. Inventory all IConverter.Convert() call sites: Note each call's HTML source (string vs URL), paper size, margins, orientation, and any header/footer configuration.
  2. Render-compare all templates with IronPDF before code changes: Run each HTML template through IronPDF and compare against existing DinkToPdf output. Identify layout differences that need CSS corrections versus wkhtmltopdf workarounds that can be removed.
  3. Install IronPDF via NuGet: dotnet add package IronPdf. Keep DinkToPdf in the project until replacement code compiles and tests pass.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs before any render call. See the license setup guide.
  5. Update DI registration: In Program.cs, remove SynchronizedConverter, BasicConverter, PdfTools, and CustomAssemblyLoadContext. Add builder.Services.AddSingleton<ChromePdfRenderer>().
  6. Replace IConverter injection with ChromePdfRenderer: Update all constructor parameters and field types.
  7. Replace HtmlToPdfDocument construction: For each call site, replace the HtmlToPdfDocument + GlobalSettings + ObjectSettings block with RenderingOptions property assignments on the renderer.
  8. Map GlobalSettings and ObjectSettings to RenderingOptions: Paper size, orientation, margins, background, encoding — map each property individually.
  9. Update header/footer token syntax: Replace [page] with {page}, [toPage] with {total-pages}, [date] with {date}. Update HeaderSettings/FooterSettings text config to HtmlHeaderFooter HTML fragments.
  10. Replace synchronous conversion with async render: Replace Task.Run(() => converter.Convert(doc)) with await renderer.RenderHtmlAsPdfAsync(html). Wrap PdfDocument in using. Access bytes via pdf.BinaryData.
  11. Fix CSS — remove wkhtmltopdf workarounds, add modern CSS: After step 2, apply CSS corrections identified in the render comparison. Remove any hacks that were added to work around wkhtmltopdf limitations.
  12. Remove DinkToPdf NuGet reference and native binaries: Once all call sites are updated and tests pass, remove DinkToPdf from NuGet dependencies and remove the libwkhtmltox binaries from the deployment package.

Conclusion

When staying on DinkToPdf is technically reasonable

DinkToPdf is technically reasonable only for applications with simple HTML templates that do not use modern CSS features, where the application is stable with no plans to add CSS-heavy layouts or JavaScript-rendered content, and where the MIT open-source license is a hard organizational requirement. For teams in this situation, the wkhtmltopdf rendering engine's limitations are not yet causing production friction, and the migration cost is not yet justified.

Signals that indicate migration is worth the engineering effort

The clearest signal is rendering failure: when a CSS layout that works in a browser does not render correctly in DinkToPdf, and the workaround is not acceptable. Secondary signals include the application adding JavaScript-rendered content to templates, a move to .NET versions where DinkToPdf's maintenance status creates uncertainty, containerization that makes the libwkhtmltox native binary deployment awkward, or a requirement for PDF manipulation capabilities (merge, sign, encrypt, form-fill) that DinkToPdf does not provide.

What the cutover typically involves at the code level

The API swap is mechanical and fast — for a service with 5–15 call sites, a single engineering day is typically sufficient to replace all IConverter.Convert() calls with RenderHtmlAsPdfAsync(), update the DI registration, remap GlobalSettings to RenderingOptions, and update header/footer token syntax. The rendering fidelity review — comparing Chromium output against wkhtmltopdf output for each template and resolving differences — requires additional time proportional to template complexity and the number of CSS workarounds in place.

Of the CSS workarounds your team has accumulated for wkhtmltopdf — specific Flexbox hacks, fallback fonts for web fonts, table layout overrides — how many were discovered during active feature development versus retroactively when the rendering gap was finally noticed?
