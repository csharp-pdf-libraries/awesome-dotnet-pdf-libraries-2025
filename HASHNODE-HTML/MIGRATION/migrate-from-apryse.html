Migrating from Apryse PDF to IronPDF: what changes, what breaks, what maps

from install to first PDF — the full migration path

Framing

Enterprise PDF libraries tend to accumulate institutional weight. Teams that adopt a comprehensive SDK early in a product's lifecycle often find it deeply embedded across multiple modules — document generation, signing workflows, compliance exports, form processing, and annotation handling. When those teams re-evaluate the dependency, the conversation is rarely about a single deficiency; it is about the aggregate cost and complexity of a library that was acquired at a different scale than the one the application now operates at.

Apryse (formerly PDFTron) occupies a well-established position in the enterprise PDF market. Its cross-platform SDK covers .NET, Java, JavaScript, and mobile targets, with a strong focus on PDF viewing, annotation, editing, and high-fidelity document processing. The library has been deployed in regulated industries — legal, financial, healthcare — where PDF fidelity and compliance support are non-negotiable. Teams evaluating a migration from Apryse are typically doing so because licensing costs have changed, platform requirements have shifted, or the feature set in active use is a fraction of what the library provides.

This guide is for .NET engineers scoping or executing a migration from Apryse PDF SDK to IronPDF. The migration is classified as High effort, which reflects both the breadth of Apryse's API surface and the architectural gap between its content-model approach and IronPDF's HTML rendering model. The guide is structured to surface where the migration is clean, where it requires design changes, and where it may not be appropriate.

What Apryse PDF Is Designed to Do

A commercial cross-platform PDF processing library, apryse pdf sdk (formerly pdftron sdk) is. The product status and last release should be verified in official documentation, as Apryse maintains multiple versioned SDKs across platforms. The .NET SDK distributes via NuGet packages with native binary dependencies — the exact package structure and supported .NET versions should be verified in official documentation for the target platform.

Apryse's design center is comprehensive, low-level PDF processing: direct access to the PDF document object model (pages, annotations, content streams, fonts, XObjects), PDF rendering to images, advanced form processing, digital signatures, PDF redaction, and PDF/A and PDF/UA compliance operations. The SDK also includes a PDF viewer component (PDFViewCtrl/PDFView) for embedding document display in desktop and web applications. The primary use case should be verified in official documentation, but Apryse is commonly found in enterprise document management systems, legal review platforms, and regulated document workflows. Its install footprint includes native binaries for each target platform — a meaningful operational consideration compared to pure-managed-code alternatives.

Architectural Differences

Apryse and IronPDF represent different points on the spectrum between low-level PDF control and high-level rendering convenience. Apryse exposes the PDF document model directly — callers work with PDFDoc, Page, Annot, Field, and content stream APIs that map closely to the PDF specification. IronPDF abstracts that model behind an HTML rendering pipeline: document content is expressed as HTML/CSS, rendered by Chromium, and the PDF structure is managed internally.

For document manipulation operations — merge, split, page operations, annotations, forms, signing — both libraries expose comparable higher-level APIs, and these operations port with medium effort. The gap is in content generation: any document that Apryse generates by writing to content streams or placing PDF objects directly must be re-expressed as HTML/CSS for IronPDF. That is a design change in addition to a code change, and its effort scales with document complexity.

IronPDF's two entry points are ChromePdfRenderer for rendering and PdfDocument for manipulation. PdfDocument implements IDisposable; all instances should be used within using blocks. For teams familiar with Apryse's PDFDoc, the conceptual mapping is PDFDoc → PdfDocument, but with a narrower manipulation surface and a different content generation model. The rendering options reference covers the full HTML rendering configuration. License initialization is performed once at startup — before any render or document call — via IronPdf.License.LicenseKey; see the license setup guide.

Operation Comparisons

HTML String to PDF

Apryse — HTML String to PDF

Apryse's primary SDK does not include native HTML-to-PDF rendering via Chromium in the same way IronPDF does. HTML conversion in Apryse is typically handled by a separate companion tool or conversion layer

// Apryse HTML to PDF
// General pattern:

// 1. Ensure the HTML conversion module/add-on is installed and licensed
// 2. Instantiate the HTML-to-PDF converter class (name varies by version)
// 3. Configure paper size, margins, and JavaScript wait behavior
// 4. Pass HTML string or URL to the conversion method
// 5. Obtain the resulting PDFDoc object
// 6. Save or pass the PDFDoc to further operations
// 7. Dispose the PDFDoc object

// Verify exact class names and method signatures in official Apryse documentation

Concrete constraints:

  • Apryse's HTML-to-PDF path may involve a separate licensed add-on component — confirm which packages are in the current deployment.
  • Configuration surface for rendering options should be mapped from Apryse's converter API to IronPDF's RenderingOptions for each property in use.
  • If the current workflow relies on Apryse's primary SDK for PDF manipulation and a different tool (e.g., a cloud converter or another library) for HTML rendering, only the manipulation portion maps to IronPDF's document operations.

IronPDF — HTML String to PDF

using IronPdf;

// Renderer is stateless and thread-safe for configuration; one instance per thread is safe for rendering
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;     // millimeters
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.CssMediaType = IronPdf.Rendering.PdfCssMediaType.Print;

// RenderHtmlAsPdf handles pagination, JS execution, and web fonts automatically
using var pdf = renderer.RenderHtmlAsPdf(@"
    <html>
    <head>
      <style>
        body { font-family: Arial, sans-serif; font-size: 11pt; }
        .header { border-bottom: 2px solid #333; margin-bottom: 20px; }
        table { width: 100%; border-collapse: collapse; }
        td, th { padding: 8px; border: 1px solid #ccc; }
      </style>
    </head>
    <body>
      <div class='header'><h2>Quarterly Summary</h2></div>
      <table>
        <tr><th>Region</th><th>Revenue</th></tr>
        <tr><td>North</td><td>$124,500</td></tr>
      </table>
    </body>
    </html>");

pdf.SaveAs("quarterly-summary.pdf");

Full rendering options — CSS media type, viewport, JavaScript wait conditions, web fonts — are covered in the HTML string to PDF guide. For pixel-accurate output requirements, the pixel-perfect rendering guide covers viewport and zoom configuration.

Digital Signatures

Apryse — Digital Signatures

// Apryse digital signing
// Apryse supports PKCS#7, CAdES, and PAdES signature formats
// General pattern:

using pdftron.PDF;
using pdftron.SDF;

PDFDoc doc = null;
try
{
    PDFNet.Initialize("YOUR-APRYSE-LICENSE-KEY"); // Required global init

    doc = new PDFDoc("document-to-sign.pdf");

    // Locate or create signature field
    // Configure digital ID (certificate), reason, location, contact
    // Set signing format (PKCS#7 detached is common)
    // Apply timestamp server if LTV is required
    // Sign the field — this commits the signature to the document
    // Save using incremental save mode (required to preserve existing signatures)

    doc.Save("signed.pdf", SDFDoc.SaveOptions.e_incremental);
}
finally
{
    doc?.Close();
    PDFNet.Terminate();
}

Concrete constraints:

  • PDFNet.Initialize() and PDFNet.Terminate() are required lifecycle calls; these have no equivalent in IronPDF and must be removed.
  • Apryse supports multiple signature formats (PKCS#7, CAdES, PAdES); IronPDF's signature format support should be verified in official documentation.
  • Incremental save (e_incremental) is required to preserve existing signatures when adding a new one. IronPDF always performs a full save
  • Long-Term Validation (LTV) via timestamp server configuration should be tested explicitly.

IronPDF — Digital Signatures

using IronPdf;
using IronPdf.Signing;

using var pdf = PdfDocument.FromFile("document-to-sign.pdf");

var signature = new PdfSignature("certificate.pfx", "pfx-password")
{
    SigningReason = "Document approved",
    SigningLocation = "Chicago, IL",
    // Timestamp server for LTV: TimestampServer = "http://timestamp.example.com"
};

pdf.Sign(signature);
pdf.SaveAs("signed.pdf");

Signing options including multi-signature scenarios and hardware security module integration are detailed in the digital signatures guide. For HSM-based signing, see the HSM signing guide.

PDF/A Compliance

Apryse — PDF/A Conversion

// Apryse PDF/A conversion
using pdftron.PDF;

PDFDoc doc = null;
try
{
    PDFNet.Initialize("YOUR-APRYSE-LICENSE-KEY");

    doc = new PDFDoc("source.pdf");

    // Apryse provides detailed compliance verification and conversion
    // Steps typically include:
    // 1. Run a compliance check to identify violations
    // 2. Configure the PDF/A version (1b, 2b, 3b, etc.)
    // 3. Convert the document, specifying how to handle non-conformances
    // 4. Save the compliant output

    doc.Save("output-pdfa.pdf", SDFDoc.SaveOptions.e_linearized);
}
finally
{
    doc?.Close();
    PDFNet.Terminate();
}

Concrete constraints:

  • Apryse's PDF/A module provides detailed violation reporting before and after conversion — useful for debugging source documents.
  • Specific conformance level (1b, 2b, 3b, 4) is explicitly configurable; verify which levels IronPDF supports.
  • Non-conformance handling (e.g., RGB vs CMYK color, transparency flattening, embedded font requirements) may produce different output between the two libraries.

IronPDF — PDF/A Compliance

using IronPdf;

var renderer = new ChromePdfRenderer();
using var pdf = renderer.RenderHtmlAsPdf(@"
    <html><body><p>Archival content.</p></body></html>");

// Save as PDF/A
pdf.SaveAsPdfA("archival.pdf", PdfAVersions.PdfA2);

PDF/A options and supported conformance levels are documented in the PDF/A compliance guide. If the source workflow uses Apryse's compliance validation tooling, validate IronPDF output with an independent PDF/A validator rather than assuming equivalence.

Breaking Changes & Gotchas

  • Global lifecycle: Apryse requires PDFNet.Initialize(key) and PDFNet.Terminate() as global lifecycle calls. IronPDF has no such requirement. Remove these calls; they have no equivalent and will cause compile errors in the ported code.
  • License initialization model: Apryse passes the license key to PDFNet.Initialize(). IronPDF uses IronPdf.License.LicenseKey = "key" at startup before any library call. The pattern is similar but the location differs — ensure it runs before the first PdfDocument or ChromePdfRenderer instantiation.
  • No incremental save: Apryse supports incremental save mode (e_incremental), required for adding signatures to previously signed documents without invalidating earlier signatures. IronPDF always performs a full save. If the existing workflow relies on incremental save for multi-signature chains, verify whether IronPDF's full-save behavior is acceptable for the target signing scheme.
  • Content stream access not available: Apryse exposes ContentItem, ElementWriter, and related APIs for direct content stream manipulation. IronPDF does not expose PDF content streams. Any code using these APIs must be re-expressed as HTML/CSS rendering.
  • Text extraction granularity: Apryse's TextExtractor provides per-word positional data, font, and size information. IronPDF's ExtractAllText() returns a plain string. If downstream code consumes positional text data, this is a blocking gap requiring resolution before migration.
  • PDF viewer component: Apryse's PDFViewCtrl and WebViewer are first-class products for embedding PDF display in applications. IronPDF has limited PDF viewing capability
  • Native binary packaging: Apryse distributes native binaries per platform. IronPDF also requires platform-specific binaries for Chromium on non-Windows platforms. Container and Linux deployment must be re-validated.
  • Annotation type coverage: Apryse supports the full PDF annotation type set. IronPDF's annotation support should be verified against the annotation types in active use before treating annotation migration as low-risk.
  • Namespace changes: Apryse uses pdftron.PDF. and pdftron.SDF. namespaces. IronPDF uses IronPdf.*. A full codebase search and replace is required; compilation errors will surface remaining call sites.
  • Thread safety: Apryse's PDFDoc is not thread-safe; the same applies to IronPDF's PdfDocument. Per-operation or per-request instantiation is the safe pattern in both cases.
  • PDF/A validation: Apryse includes a detailed compliance validation module that reports specific violations. IronPDF produces PDF/A output but does not include a standalone validator. Validate IronPDF output against an independent tool if compliance certification is required. See the PDF/A compliance guide.

Migration Checklist

  1. Triage Apryse API usage into three groups: (a) document load/save/manipulation — ports with medium effort; (b) content generation via content streams or ElementWriter — requires re-expression as HTML/CSS; (c) PDF viewer component — requires a separate replacement decision. Resolve Group (c) before migration begins.
  2. Confirm HTML-to-PDF component in use: If the existing workflow uses Apryse's HTML conversion add-on, identify which version and configuration are in use. Map each configuration option to IronPDF's RenderingOptions before writing code.
  3. Install IronPDF via NuGet: dotnet add package IronPdf. Retain Apryse package references until replacement code is compiled and tested.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs or equivalent before any rendering or document call. See the license setup guide.
  5. Remove PDFNet.Initialize() and PDFNet.Terminate() calls: These are Apryse-specific lifecycle methods. Remove them entirely — they have no IronPDF equivalent.
  6. Update namespaces: Replace using pdftron.PDF;, using pdftron.SDF;, and related Apryse namespaces with using IronPdf;. Use compile errors to locate all affected files.
  7. Port document load/save: Replace new PDFDoc(path) with PdfDocument.FromFile(path), doc.Save(path, flags) with pdf.SaveAs(path). Add using blocks to all PdfDocument declarations.
  8. Port merge, split, and page operations: Replace Apryse merge patterns with PdfDocument.Merge(), page extraction with PdfDocument.CopyPages(), and rotation with pdf.RotatePage().
  9. Re-express content-stream documents as HTML/CSS: For each document generated via Apryse's low-level drawing API, design an equivalent HTML template and render via ChromePdfRenderer. This is the highest-effort step; time-box it per template.
  10. Port forms, signing, and annotations: Re-implement form-fill, digital signatures, and annotation operations using IronPDF equivalents. Test each category explicitly against production-representative inputs.
  11. Validate PDF/A, PDF/UA, and security outputs: Run compliance outputs through independent validators. Do not assume behavioral equivalence.
  12. Test on all deployment targets: Apryse and IronPDF have different native binary profiles. Validate Linux and Docker deployments explicitly before promoting to production.
  13. Decommission Apryse package references: Once all tests pass, remove Apryse NuGet packages and native binaries, delete lifecycle shim code, and perform a final build verification.

Conclusion

When staying on Apryse is technically reasonable

Apryse is the correct choice when the application requires capabilities that IronPDF does not expose: the embedded PDF viewer (PDFViewCtrl / WebViewer), content stream access for low-level PDF editing, positional text extraction with font metadata, incremental save for multi-signature chains, or comprehensive PDF/X prepress compliance. If the PDF viewer is a core component of the user experience, migrating away from Apryse requires selecting and integrating a replacement viewer — a non-trivial scope that extends well beyond the PDF generation layer.

Signals that indicate migration is worth the engineering effort

Migration becomes worth scoping when an audit of the codebase shows that content-stream generation and the viewer component are not in active use; when Apryse licensing costs have changed materially; or when the application needs to standardize on a simpler, more focused PDF SDK for document generation, signing, compliance, and manipulation. Teams that find they are using only a subset of Apryse's capabilities — specifically HTML rendering, merge/split, form-fill, and signing — will find that subset maps cleanly to IronPDF's API surface.

What the cutover typically involves at the code level

The defining effort items are the removal of PDFNet.Initialize/Terminate lifecycle calls, the namespace migration from pdftron. to IronPdf., and the re-expression of any content-stream document generation as HTML/CSS templates. For integrations that use Apryse primarily for HTML rendering and document manipulation — without relying on its low-level content model or viewer — the migration is achievable in a focused engineering sprint with disciplined regression testing. For integrations with heavy content-stream usage or viewer dependency, the timeline extends significantly and a phased migration strategy (replacing components incrementally rather than in a single cutover) is typically safer.
