Migrating from GdPicture.NET SDK to IronPDF: a .NET engineering guide

API mapping, gotchas, and a migration checklist

Framing

Broad-scope document and imaging SDKs serve a different architectural need than focused PDF libraries. When an application requires not just PDF generation but also barcode reading, OCR, image processing, TWAIN scanning, document comparison, or annotation rendering in a unified SDK, a library like GdPicture.NET is a natural fit. The value proposition is a single vendor and a single integration surface for capabilities that would otherwise require three or four separate libraries.

The calculus changes when the application's actual usage profile narrows. Teams that initially adopted GdPicture.NET for its breadth often find that production traffic concentrates heavily on PDF generation and basic manipulation — and that the imaging and scanning capabilities, while available, are largely dormant. At license renewal, the scope of the license versus the scope of actual usage becomes a visible question. There is also the architectural concern: GdPicture.NET's API surface is large and its disposal requirements are specific. Applications that grew organically around GdPicture.NET sometimes carry legacy patterns — LockPage/UnlockPage, image ID lifecycles — that make the codebase harder to maintain than an equivalent narrower integration.

This guide is for .NET engineers evaluating or executing a migration from GdPicture.NET SDK to IronPDF. The migration is classified as High effort, reflecting the SDK's broad scope and the depth of API remapping required. Teams using only GdPicture.NET's PDF generation and basic manipulation features will find the actual engineering effort closer to Medium; teams using OCR, barcode, TWAIN, or image processing alongside PDF will need a separate evaluation for those capabilities.

What GdPicture.NET SDK Is Designed to Do

GdPicture.NET is a commercial document and imaging SDK published by ORPALIS. The product status and last release should be verified in official documentation. The library is distributed as a NuGet package; the install footprint and native binary requirements should be verified in official documentation, as GdPicture.NET has historically included native components for OCR, image codecs, and TWAIN access. The .NET support range should be verified in official documentation.

GdPicture.NET's design is intentionally broad: it provides capabilities across PDF creation and manipulation, image processing (resize, rotate, convert between image formats), OCR (optical character recognition with support for multiple languages), barcode reading and generation, TWAIN/WIA scanner access, document annotation (for both viewer and server-side workflows), and format conversion. The PDF-specific capabilities include creating PDFs from images, rendering PDFs to images, HTML-to-PDF conversion, form field manipulation, digital signatures, and PDF/A compliance. The primary use case should be verified in official documentation, but GdPicture.NET is commonly found in document capture, scanning, and processing workflows where image processing and PDF handling are tightly coupled.

Architectural Differences

GdPicture.NET and IronPDF differ in scope, API design, and the disposal model. GdPicture.NET's PDF API is part of a larger document processing SDK with a shared GdPicture object that manages image resources across different function groups. Its disposal model requires careful lifecycle management of image IDs and locked pages. IronPDF is a focused PDF library with two primary types: ChromePdfRenderer and PdfDocument, both following standard .NET IDisposable semantics.

The most significant architectural difference is the content generation model. GdPicture.NET creates PDFs primarily by composing image and drawing primitives onto pages — insert page, draw text at coordinates, embed image, etc. IronPDF generates PDFs by rendering HTML/CSS through an embedded Chromium engine. For manipulation operations (load existing PDF, add/remove pages, fill forms, sign, encrypt), both libraries provide comparable functionality. For PDF generation from scratch, GdPicture's drawing-primitive model must be replaced with HTML/CSS templates.

IronPDF's PdfDocument is disposed via using blocks. GdPicture.NET's PDF operations use a GdPicturePDF object with explicit CloseDocument() and Dispose() calls. The rendering options reference covers IronPDF's full HTML rendering configuration. License initialization is a one-time startup call via IronPdf.License.LicenseKey; see the license setup guide.

Operation Comparisons

PDF Generation from Drawing Primitives

GdPicture.NET — Drawing-Based PDF Generation

using GdPicture14; // Verify exact namespace in official documentation

// GdPicture PDF creation uses a GdPicturePDF object and drawing operations
var gdPdf = new GdPicturePDF();

try
{
    // Create a new PDF document
    gdPdf.NewPDF();

    // Add a page — A4 size
    gdPdf.AddPage(210f, 297f); // Width and height in mm

    // Set font properties
    gdPdf.SetPageFontName("Helvetica");
    gdPdf.SetPageFontSize(18);
    gdPdf.SetPageFontColor(0, 0, 0); // RGB

    // Draw text at absolute coordinates
    // GdPicture.NET uses a coordinate system
    gdPdf.DrawText("Invoice #1042", 15, 25); // x, y in mm

    gdPdf.SetPageFontSize(11);
    gdPdf.DrawText("Customer: Acme Corp", 15, 40);
    gdPdf.DrawText("Total: $1,599.00", 15, 55);

    // Draw a line (separator)
    gdPdf.DrawLine(15, 35, 195, 35, 0.5f); // x1, y1, x2, y2, linewidth

    // Save to file
    gdPdf.SaveAsPDF(@"C:\Output\invoice.pdf");
}
finally
{
    // GdPicture requires explicit close and dispose
    gdPdf.CloseDocument();
    gdPdf.Dispose();
}

Concrete constraints:

  • GdPicture.NET's GdPicturePDF uses drawing primitives at absolute coordinates. Verify the coordinate system origin and unit conventions (mm vs points vs pixels) in official documentation.
  • Automatic text flow, table layout, and multi-page pagination are the developer's responsibility — GdPicture has no layout engine equivalent to IronPDF's Chromium renderer.
  • CloseDocument() must be called before Dispose(). Failing to call CloseDocument() on an open document may produce file lock issues or incomplete output.
  • Method names should be verified in official documentation as they vary between GdPicture.NET versions.

IronPDF — HTML/CSS Equivalent

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;

// GdPicture's drawing-primitive approach is replaced by HTML/CSS
// CSS handles layout, spacing, and typography automatically
string html = @"
<!DOCTYPE html>
<html>
<head>
<style>
  body { font-family: Helvetica, Arial, sans-serif; font-size: 11pt; color: #000; }
  h1 { font-size: 18pt; margin: 0 0 6px; }
  hr { border: none; border-top: 0.5pt solid #000; margin: 4px 0 12px; }
  p  { margin: 4px 0; }
</style>
</head>
<body>
  <h1>Invoice #1042</h1>
  <hr/>
  <p>Customer: Acme Corp</p>
  <p>Total: $1,599.00</p>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs(@"C:\Output\invoice.pdf");
// PdfDocument disposed at end of using block — no CloseDocument() needed

Every document type built with GdPicture.NET's drawing API must be redesigned as HTML/CSS for IronPDF. HTML/CSS provides automatic text flow, table pagination, and responsive layout that requires explicit manual calculation in GdPicture's coordinate model. The HTML string to PDF guide covers rendering configuration including paper size, margins, and CSS media type.

Loading and Merging PDFs

GdPicture.NET — Load and Merge

using GdPicture14;

var gdPdf = new GdPicturePDF();

try
{
    // Load the base document
    gdPdf.LoadFromFile("document1.pdf", false); // false = not read-only

    // Append pages from a second document
    // GdPicture merges by loading the second doc and appending its pages
    using var gdPdf2 = new GdPicturePDF();
    gdPdf2.LoadFromFile("document2.pdf", false);

    // MergeWith appends pages from document2 into gdPdf
    // Verify exact method signature in official documentation
    gdPdf.MergeWith(gdPdf2);

    gdPdf2.CloseDocument();

    // Append a third document
    using var gdPdf3 = new GdPicturePDF();
    gdPdf3.LoadFromFile("document3.pdf", false);
    gdPdf.MergeWith(gdPdf3);
    gdPdf3.CloseDocument();

    gdPdf.SaveAsPDF("merged.pdf");
}
finally
{
    gdPdf.CloseDocument();
    gdPdf.Dispose();
}

Concrete constraints:

  • GdPicture.NET's MergeWith appends pages from a second PDF into the current PDF. Verify the exact method name and signature in official documentation.
  • The LoadFromFile read-only parameter affects whether the source file is locked during processing. Refer to the official documentation.
  • Every GdPicturePDF instance requires explicit CloseDocument() before Dispose() — wrap all instances in try/finally blocks.

IronPDF — Load and Merge

using IronPdf;

// PdfDocument.FromFile() loads each source document
using var pdf1 = PdfDocument.FromFile("document1.pdf");
using var pdf2 = PdfDocument.FromFile("document2.pdf");
using var pdf3 = PdfDocument.FromFile("document3.pdf");

// N-way merge in a single call — no intermediate MergeWith calls
using var merged = PdfDocument.Merge(pdf1, pdf2, pdf3);
merged.SaveAs("merged.pdf");
// All PdfDocument instances disposed at end of using blocks

IronPDF's merge model is a single static call with all source documents in argument order. Source documents are automatically disposed when their using blocks exit. The merge and split guide covers page range selection, split operations, and partial merge patterns.

PDF Rasterization (PDF to Image)

GdPicture.NET — Rasterize PDF Page to Image

using GdPicture14;

var gdPdf = new GdPicturePDF();
var gdImg = new GdPictureImaging();

try
{
    gdPdf.LoadFromFile("source.pdf", true); // read-only

    // GdPicture's image management uses integer IDs
    // RenderPageToGdPictureImage returns an image ID
    int pageCount = gdPdf.GetPageCount();

    for (int i = 1; i <= pageCount; i++) // GdPicture pages are 1-based
    {
        // Render page at specified DPI to an in-memory image
        int imageId = gdPdf.RenderPageToGdPictureImage(
            96f,   // DPI
            true,  // antiAliasing
            i);    // 1-based page number

        if (imageId != 0)
        {
            // Save image ID to file using GdPictureImaging
            gdImg.SaveAsPNG(imageId, $"page-{i}.png");

            // Release the image ID when done — critical to avoid memory leaks
            gdImg.ReleaseGdPictureImage(imageId);
        }
    }
}
finally
{
    gdPdf.CloseDocument();
    gdPdf.Dispose();
    gdImg.Dispose();
}

Concrete constraints:

  • GdPicture.NET uses integer image IDs to reference in-memory images. Every RenderPageToGdPictureImage() call returns an ID that must be released via ReleaseGdPictureImage(). Unreleased IDs cause native memory leaks.
  • Pages are 1-based in GdPicture.NET — a common off-by-one error when migrating to IronPDF's 0-based page indexing.
  • The two-object pattern (GdPicturePDF for PDF operations, GdPictureImaging for image operations) reflects GdPicture's shared resource model across different function groups.

IronPDF — PDF to Image

using IronPdf;

using var pdf = PdfDocument.FromFile("source.pdf");

// Rasterize all pages to PNG files at 96 DPI
// Returns an array of file paths for the generated images
var imagePaths = pdf.RasterizeToImageFiles("page-*.png", DPI: 96);

foreach (var path in imagePaths)
{
    Console.WriteLine($"Generated: {path}");
}
// No explicit release calls — standard .NET GC handles resources

IronPDF's rasterization API is a single method call with no integer image ID management. Pages are zero-based internally but the output file naming is configurable. Full rasterization options including resolution, image format, and page range selection are in the PDF to image guide.

Form Filling and Flattening

GdPicture.NET — AcroForm Operations

using GdPicture14;

var gdPdf = new GdPicturePDF();

try
{
    gdPdf.LoadFromFile("form-template.pdf", false);

    // GdPicture accesses form fields by name
    // Verify exact method names in official documentation
    gdPdf.SetFormFieldValue("applicant_name", "Jane Smith");
    gdPdf.SetFormFieldValue("status_approved", "On"); // checkbox

    // Flatten form — removes interactivity, embeds values as static content
    gdPdf.FlattenFormFields(); // verify method name

    gdPdf.SaveAsPDF("filled-form.pdf");
}
finally
{
    gdPdf.CloseDocument();
    gdPdf.Dispose();
}

Concrete constraints:

  • GdPicture.NET's form field methods should be verified in official documentation — method names (SetFormFieldValue, FlattenFormFields) and their overloads vary between versions.
  • Checkbox and radio button values use string conventions ("On"/"Off" or "Yes"/"No")

IronPDF — AcroForm Operations

using IronPdf;

using var pdf = PdfDocument.FromFile("form-template.pdf");

// Field access by name — uniform string value for all field types
var nameField = pdf.Form["applicant_name"];
if (nameField != null)
    nameField.Value = "Jane Smith";

var approvedField = pdf.Form["status_approved"];
if (approvedField != null)
    approvedField.Value = "On";

// Flatten before save
pdf.Form.Flatten();
pdf.SaveAs("filled-form.pdf");

The form fill API maps cleanly — both GdPicture.NET and IronPDF use name-based field access with string values. The structural change is moving from gdPdf.SetFormFieldValue("name", "val") to pdf.Form["name"].Value = "val". Full form filling and flattening documentation is in the edit forms guide.

Breaking Changes & Gotchas

  • Integer image ID lifecycle removed: GdPicture.NET's imaging model uses integer IDs for in-memory image resources that must be explicitly released via ReleaseGdPictureImage(). IronPDF uses managed .NET objects with no manual release — using blocks handle cleanup. Any code that tracks and releases GdPicture image IDs is removed entirely.
  • CloseDocument() removed: GdPicture.NET requires CloseDocument() before Dispose(). IronPDF requires only a using block or explicit Dispose(). Remove all CloseDocument() calls and replace with using blocks around PdfDocument.
  • Page indexing: 1-based → 0-based: GdPicture.NET uses 1-based page indices. IronPDF uses 0-based. Every page index reference must be decremented by one during migration — a systematic off-by-one source if missed.
  • Drawing-primitive generation requires HTML/CSS redesign: GdPicture.NET's DrawText(), DrawLine(), DrawRectangle(), and AddImage() calls have no direct IronPDF equivalent. Every document built using drawing primitives must be redesigned as HTML/CSS.
  • OCR is not in IronPDF: GdPicture.NET's OCR capability (recognizing text in scanned images) is not available in IronPDF. Teams using OCR alongside PDF must evaluate IronOCR or another OCR library separately.
  • Barcode reading is not in IronPDF: GdPicture.NET can read barcodes from images and PDFs. IronPDF does not provide barcode reading. Evaluate IronBarcode or a dedicated barcode library separately.
  • TWAIN/WIA scanning is not in IronPDF: Scanner access is entirely outside IronPDF's scope. If GdPicture.NET is used as the scanning SDK, this functionality requires a separate evaluation independent of the PDF migration.
  • Namespace change: Remove all GdPicture using directives. Replace with using IronPdf;. Compile errors identify every affected file.
  • License key required: IronPdf.License.LicenseKey must be set before any rendering or document call. GdPicture.NET uses its own license mechanism
  • GdPicturePDF type name conflict: If both packages are present during migration, verify whether GdPicturePDF creates naming conflicts. They use different type names, so conflicts are unlikely — but verify during the transition period.
  • Thread safety: GdPicture.NET's shared GdPicturePDF instances are not thread-safe — use per-operation instances. IronPDF follows the same pattern — per-operation PdfDocument instances are safest.

Migration Checklist

  1. Triage GdPicture.NET usage by capability: Separate operations into: (a) PDF load/save/merge/split/forms/encrypt — Low-Medium effort; (b) drawing-primitive PDF generation — High effort (HTML/CSS redesign); (c) PDF rasterization and image-to-PDF — Low effort; (d) OCR, barcode, scanning, image processing — Out of scope, requires separate library evaluation. Address (d) independently before committing to migration.
  2. Evaluate out-of-scope capability replacements: If OCR, barcode reading, or TWAIN scanning are in production use, identify and evaluate replacement libraries (IronOCR, IronBarcode, separate TWAIN SDK) before beginning PDF migration. These may be blockers if the team cannot accept a temporary capability gap.
  3. Design HTML/CSS templates to replace drawing-primitive generation: For each document type built using GdPicture.NET's DrawText() / DrawLine() / drawing API, produce an HTML/CSS equivalent. Validate in Chrome before testing with IronPDF.
  4. Install IronPDF via NuGet: dotnet add package IronPdf. Retain GdPicture.NET references until replacement code compiles and tests pass.
  5. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs before any render or document call. See the license setup guide.
  6. Update namespaces: Remove all GdPicture using directives. Replace with using IronPdf;. Compile errors guide the remaining work.
  7. Replace GdPicturePDF.LoadFromFile() with PdfDocument.FromFile(): Wrap all PdfDocument instances in using blocks. Remove all CloseDocument() calls.
  8. Fix page index conventions: Audit every GdPicture page index reference and decrement by one for IronPDF (1-based → 0-based).
  9. Replace merge operations: Replace gdPdf.MergeWith(doc) chains with PdfDocument.Merge(pdf1, pdf2, ...).
  10. Replace form-fill operations: Replace gdPdf.SetFormFieldValue("name", "val") with pdf.Form["name"].Value = "val". Replace FlattenFormFields() with pdf.Form.Flatten(). Test all field types.
  11. Replace rasterization: Replace RenderPageToGdPictureImage() + SaveAsPNG() + ReleaseGdPictureImage() with pdf.RasterizeToImageFiles(). Remove all integer image ID tracking.
  12. Remove GdPicture.NET NuGet reference: Once all replacements compile and tests pass, remove the GdPicture.NET package. Confirm that remaining out-of-scope capabilities (OCR, barcode, TWAIN) have been addressed by replacement libraries before removing the full SDK.

Conclusion

When staying on GdPicture.NET SDK is technically reasonable

GdPicture.NET is technically reasonable when the application actively uses multiple SDK capabilities — particularly OCR, TWAIN scanning, and image processing — in combination with PDF workflows, and when the unified vendor and support model justifies the license scope. Teams with deep investment in GdPicture.NET's imaging API, and whose PDF requirements are satisfied by drawing-primitive generation rather than HTML/CSS, have a stable integration with no immediate reason to migrate.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when the actual production usage is concentrated in PDF generation and basic manipulation while OCR, scanning, and image processing capabilities are dormant; when license renewal cost prompts a review of SDK utilization versus scope; when containerization or Linux deployment is introducing friction from GdPicture.NET's native binary dependencies; when the integer image ID management model is a maintenance burden; or when the application is adopting HTML/CSS-based document generation and GdPicture.NET's drawing-primitive model is not serving that direction.

What the cutover typically involves at the code level

The PDF load/save/merge/form/encrypt operations are direct API remapping — systematic but straightforward. The drawing-primitive generation code requires HTML/CSS redesign, proportional to the number and complexity of document types. The rasterization code simplifies considerably — RenderPageToGdPictureImage() + image ID management becomes a single RasterizeToImageFiles() call. The page index 1-to-0 conversion must be applied systematically throughout. Out-of-scope capabilities (OCR, barcode, TWAIN) must be resolved before or alongside the PDF migration — they are often the item that converts a "PDF migration" into a "platform re-architecture" depending on how integral they are to the application's core workflows.
