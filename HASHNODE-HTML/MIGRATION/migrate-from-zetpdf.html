Migrating from ZetPDF to IronPDF: step-by-step for .NET developers

what changes, what breaks, and what maps cleanly

Framing

Discontinued NuGet packages represent a specific category of technical debt in .NET applications. The package remains functional until something in the broader stack changes — a .NET version upgrade, a containerization effort, a security audit, a new feature requirement — at which point the lack of ongoing maintenance becomes the blocking issue rather than a background concern. Teams running a discontinued PDF library are effectively maintaining a fixed snapshot of that library's capabilities indefinitely, with no path to patches, framework compatibility updates, or new features.

The decision to migrate is typically forced rather than discretionary. When a .NET 8 or .NET 9 target is required and the discontinued library has not been updated to support it, the migration becomes a prerequisite for the platform upgrade. When a security scan flags an unmaintained dependency, the migration appears in the risk register. When a document generation requirement surfaces that the discontinued library cannot address — modern CSS rendering, JavaScript execution, PDF/A compliance, digital signatures — the workaround cost eventually exceeds the migration cost.

ZetPDF is a discontinued .NET PDF library distributed via NuGet. Teams running it today are managing a frozen dependency without an upstream maintenance path. This guide provides the technical migration map from ZetPDF to IronPDF, covering the likely API surface ZetPDF exposed, where those operations map in IronPDF, and what the migration involves at the code level. Because ZetPDF is discontinued and official documentation may be limited, specific API names and behaviors attributed to it should be verified against the version deployed in the application.

What ZetPDF Is Designed to Do

ZetPDF was a .NET PDF library distributed as a NuGet package, targeted at programmatic PDF generation and manipulation in .NET applications. Based on its positioning as a niche library, its architecture likely centers on a document creation API — allowing developers to construct PDF pages with text, images, shapes, and tables — and basic manipulation operations such as loading, merging, and modifying existing PDF documents. The integration model was NuGet-based, with the library distributed as a managed assembly.

The primary use cases for niche PDF libraries in this category are invoice generation, report production, form processing, and document pipeline operations in ASP.NET server applications. The rendering approach, supported .NET version range, exact feature set, and last release version should all be verified against any available ZetPDF documentation or the NuGet package history. The library is discontinued; no new releases, security patches, or framework compatibility updates are expected. Teams running ZetPDF are the authoritative source on its actual capabilities in their deployed version.

Architectural Differences

IronPDF approaches document generation through a Chromium rendering pipeline. Where ZetPDF (based on its niche library profile) likely exposes a programmatic API for constructing document content, IronPDF's primary path is to render HTML and CSS as a PDF. The developer describes document layout in HTML; the Chromium engine determines positioning, typography, and page breaks. The PdfDocument returned by ChromePdfRenderer is then available for post-processing through a unified API.

The practical consequence is that the migration involves both an API change and a content authoring change. Operations that used ZetPDF's drawing or layout API must be expressed as HTML templates in the new model. For invoice-style, report-style, and tabular documents, this is typically a net reduction in code volume — HTML <table> is more concise than programmatic table construction, and CSS handles spacing, borders, and typography more declaratively than coordinate API calls. The HTML to PDF rendering guide covers the full Chromium rendering option set.

Post-processing operations — merging, splitting, password protection, digital signatures, form editing, and PDF/A compliance — are available in the same IronPDF package that handles rendering. If ZetPDF was being supplemented by a second library for any of these operations, IronPDF may allow consolidation to a single dependency. Both the rendering and manipulation APIs operate on the same PdfDocument type, which implements standard .NET IDisposable. License setup is a static call at application startup — the license key configuration guide documents the initialization options.

IronPDF — HTML String to PDF

IronPDF accepts HTML strings directly via ChromePdfRenderer. The Chromium engine renders the full modern CSS stack including Grid, Flexbox, web fonts, and JavaScript. The HTML string to PDF guide documents all rendering configuration.

using IronPdf;

// IronPdf.License.LicenseKey = "YOUR-LICENSE-KEY"; // Set once at application startup

using var renderer = new ChromePdfRenderer();

// Configure rendering
renderer.RenderingOptions.PaperSize      = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop      = 12;
renderer.RenderingOptions.MarginBottom   = 12;
renderer.RenderingOptions.MarginLeft     = 12;
renderer.RenderingOptions.MarginRight    = 12;
renderer.RenderingOptions.PrintBackground = true;

// Accept the HTML string directly — Chromium renders it
string html = @"
<!DOCTYPE html>
<html>
<head>
  <style>
    body { font-family: 'Segoe UI', Arial, sans-serif; font-size: 11pt; }
    h1   { color: #2c3e50; }
    p    { line-height: 1.6; }
  </style>
</head>
<body>
  <h1>Quarterly Summary</h1>
  <p>Revenue this quarter reached $1.2M, a 12% increase over the prior period.</p>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(html);

// Return bytes or save to file
byte[] pdfBytes = pdf.BinaryData;
// pdf.SaveAs("/output/quarterly-summary.pdf");

ChromePdfRenderer implements IDisposable. Create one per call or per scope; do not share across threads.

IronPDF — Merge PDFs

IronPDF's PdfDocument.Merge() accepts a list of PdfDocument instances and returns a new merged document. Both rendered documents and documents loaded from disk can be merged in the same call. The merge and split guide covers page ordering, large document handling, and split operations.

using IronPdf;
using System.Collections.Generic;

// Render PDF sections from HTML
using var renderer   = new ChromePdfRenderer();
using var section1   = renderer.RenderHtmlAsPdf("<h1>Section 1</h1><p>Content.</p>");
using var section2   = renderer.RenderHtmlFileAsPdf("/input/section2.html");

// Load a pre-existing PDF (e.g., legal boilerplate)
using var boilerplate = PdfDocument.FromFile("/input/boilerplate.pdf");

// Merge all into one document — order determines page order in output
using var merged = PdfDocument.Merge(new List<PdfDocument>
{
    section1,
    section2,
    boilerplate
});

merged.SaveAs("/output/full-document.pdf");

The merged document is a new PdfDocument with an independent lifecycle. Input documents are disposed independently by their using blocks when the containing scope exits.

IronPDF — Security Settings

IronPDF exposes password and permission flags through pdf.SecuritySettings. The passwords and permissions guide documents all available permission flags and encryption options.

using IronPdf;

// Render or load the document to secure
using var renderer = new ChromePdfRenderer();
using var pdf      = renderer.RenderHtmlAsPdf("<h1>Confidential Report</h1><p>Internal only.</p>");

// Configure security settings
pdf.SecuritySettings.UserPassword              = "view-password";     // required to open
pdf.SecuritySettings.OwnerPassword             = "owner-password";    // required to change settings
pdf.SecuritySettings.AllowUserCopyPasteContent = false;
pdf.SecuritySettings.AllowUserPrinting         = IronPdf.Security.PdfPrintSecurity.FullPrintRights;
pdf.SecuritySettings.AllowUserAnnotations      = false;

pdf.SaveAs("/output/confidential-report.pdf");

Verify SecuritySettings property names and available permission enum values in current IronPDF documentation. Password-protected PDFs cannot be combined with PDF/A compliance — these are mutually exclusive output modes.

IronPDF — Digital Signatures

IronPDF applies X.509-based digital signatures via PdfSignature. The digital signatures guide covers PFX loading, visible signature block configuration, and contact/reason/location metadata. For HSM-based signing where the private key is managed in hardware, the HSM signing guide documents that integration.

using IronPdf;
using IronPdf.Signing;

// Load the finalized document to sign
using var pdf = PdfDocument.FromFile("/input/final-agreement.pdf");

// Configure and apply digital signature
var signature = new PdfSignature("/certs/company-signing.pfx", "pfxPassword")
{
    SigningContact  = "contracts@example.com",
    SigningReason   = "Executed and binding",
    SigningLocation = "Chicago, IL"
};

pdf.Sign(signature);
pdf.SaveAs("/output/final-agreement-signed.pdf");

Verify PdfSignature constructor parameters and the full property set in current IronPDF documentation.

Breaking Changes & Gotchas

  • Library is discontinued — primary migration driver. ZetPDF receives no maintenance, security patches, or .NET compatibility updates. Migration is a risk-reduction measure, not an optional optimization. The urgency depends on the application's security posture, .NET version roadmap, and feature requirements.
  • Verify .NET compatibility before platform upgrades. If a .NET version upgrade is planned alongside or after this migration, confirm that the ZetPDF version in use is incompatible with the target framework. The version incompatibility is often the proximate trigger for the migration decision.
  • All API names require verification. Because ZetPDF is discontinued and documentation may be sparse, the specific class names, method signatures, and property names in the deployed version must be verified from source code, NuGet package contents, or any surviving documentation before the mapping tables in this guide can be applied precisely.
  • No drawing API equivalent. If ZetPDF's document generation used a coordinate-based or drawing API, those code paths have no IronPDF equivalent and must be redesigned as HTML templates. Scope this work before beginning the migration.
  • Namespace change. ZetPDF types are in ZetPDF-specific namespaces. IronPDF types are under IronPdf. All using directives must be replaced.
  • Chromium dependency on Linux. ZetPDF was likely a managed assembly with no native dependency. IronPDF requires Chromium system libraries on Linux. Update Dockerfiles and deployment scripts accordingly.
  • License initialization. IronPDF requires a key set at application startup. ZetPDF may have had no license management or a different model. Add the initialization call and manage the key as an environment secret.
  • Disposal patterns. IronPDF uses standard IDisposable throughout. Verify ZetPDF's disposal model in the deployed version's code and update all lifetime management to using blocks.
  • Thread safety. ZetPDF's threading model is - from the deployed version's documentation or source. IronPDF recommends creating a new ChromePdfRenderer per thread for concurrent workloads.
  • Feature gaps. Because ZetPDF is discontinued and its exact feature set may be limited, some operations (PDF/A compliance, HSM signing, PDF/UA accessibility) may be new capabilities in IronPDF rather than direct replacements. Plan template and integration work for those cases.

Migration Checklist

  1. Extract the ZetPDF API surface from the deployed application. Before any migration work, enumerate every ZetPDF call site. Document the class names, method names, settings used, and output handling. This forms the ground truth for mapping — do not rely on assumed API names.
  2. Identify generation vs. manipulation usage. Separate call sites into document generation (creating new PDFs) and document manipulation (loading, modifying existing PDFs). Generation call sites that use a drawing API require HTML template authoring; manipulation call sites may map more directly.
  3. Author HTML templates for generation call sites. For each document type generated via ZetPDF's drawing or layout API, design and test an HTML/CSS equivalent template. Validate rendered output against existing samples before proceeding.
  4. Add the IronPDF NuGet package. dotnet add package IronPdf. For Linux targets, add Chromium dependency installation to the Dockerfile.
  5. Configure the license key. Add IronPdf.License.LicenseKey = "YOUR-KEY"; to application startup. Remove ZetPDF license initialization if any. See the license key guide.
  6. Update namespace imports. Remove ZetPDF using directives. Add using IronPdf; and required sub-namespaces to affected files.
  7. Replace generation call sites. Substitute ZetPDF generator/converter instantiation with ChromePdfRenderer and Render*AsPdf() calls using the HTML templates from Step 3.
  8. Replace manipulation call sites. Substitute ZetPDF document load, merge, split, and extraction calls with PdfDocument.FromFile() and the corresponding IronPDF operations. Verify each method name in current documentation.
  9. Migrate security and signature calls. Replace ZetPDF password and signature operations with pdf.SecuritySettings and PdfSignature. Test signed documents with an independent signature validator.
  10. Add disposal patterns. Wrap all ChromePdfRenderer and PdfDocument instances in using blocks. Audit all exception handling paths to ensure disposal under failure conditions.
  11. Update deployment configuration. Remove ZetPDF binary or package references from deployment scripts. Add IronPDF Chromium dependency installation for Linux container environments.
  12. Run output regression tests. Generate each document type with IronPDF after migration. Compare against archived ZetPDF output where available. Flag any differences for investigation before decommissioning the ZetPDF code paths.

Conclusion

When staying on ZetPDF is technically reasonable: It is not, as a general position. ZetPDF is discontinued with no maintenance path. The question is not whether to migrate but when. For applications that are stable, generate only simple documents, and have no planned .NET version upgrades or platform changes, the practical risk may be manageable in the short term — but the risk compounds with every .NET release and security disclosure.

Signals that indicate migration is worth prioritizing: An upcoming .NET version upgrade that breaks ZetPDF compatibility is the clearest forcing function. Security audits that flag unmaintained dependencies are a compliance signal. Requirements for modern CSS rendering, JavaScript execution, digital signatures, or PDF/A compliance that ZetPDF cannot address are functional signals. Teams that are already planning a platform migration have the most to gain from including the PDF library migration in the same release cycle.

What the cutover typically involves at the code level: The manipulation-oriented paths (load, merge, extract) map most directly and can be migrated systematically once the ZetPDF API surface has been extracted from the codebase. The generation paths require HTML template authoring first — the extent of this work is the primary variable in scoping the migration. Once templates are ready, the rendering call site substitution is straightforward. A phased approach — manipulation paths first, generation paths as templates are completed — provides early, measurable progress and reduces the risk of a large simultaneous cutover.
