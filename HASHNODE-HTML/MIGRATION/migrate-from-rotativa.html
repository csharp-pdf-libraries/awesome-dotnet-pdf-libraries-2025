Migrating from Rotativa to IronPDF: step-by-step for .NET developers

what changes, what breaks, and what maps cleanly

Framing

Rotativa has been a widely adopted solution for PDF generation in ASP.NET MVC applications since it was released by Giorgio Bozio. Its appeal is architectural elegance within the MVC pattern: instead of managing HTML construction and PDF conversion as separate steps, Rotativa allows a controller action to return a ViewAsPdf result that renders an existing Razor view to PDF and streams it to the browser in a single line. For teams already invested in Razor views for their web UI, this reuse of view templates for PDF output was a significant convenience.

The technical foundation underneath Rotativa is wkhtmltopdf — an open-source command-line tool that uses a QtWebKit rendering engine. wkhtmltopdf is no longer under active development, and its WebKit rendering engine has not tracked modern CSS standards for several years. Teams that have invested in modern CSS — Flexbox layouts, CSS Grid, custom properties (--variables), advanced calc() expressions, or web fonts from CDN sources — often find that their Razor views render correctly in the browser but produce layout anomalies or degraded output when processed by Rotativa's wkhtmltopdf engine. The maintenance gap between the browser's CSS capabilities and wkhtmltopdf's has widened steadily.

This guide covers the migration from Rotativa (including Rotativa.AspNetCore) to IronPDF for .NET engineers evaluating or executing the switch. Rotativa is actively maintained, but the wkhtmltopdf dependency means it inherits all of wkhtmltopdf's rendering limitations and binary packaging requirements. The migration is classified as Low effort at the code level — the controller integration pattern changes, but the Razor views themselves remain usable.

What Rotativa Is Designed to Do

Rotativa is an ASP.NET MVC/Core library that integrates HTML-to-PDF conversion directly into the MVC action result pipeline. Its primary feature is the ability to return PDF output from a controller action using the same Razor views used for HTML rendering — ViewAsPdf renders a Razor view to PDF, PartialViewAsPdf renders a partial view, ActionAsPdf invokes another controller action and converts its output, and UrlAsPdf converts a URL. The library bundles and invokes wkhtmltopdf as a subprocess, passing the rendered HTML through it.

Rotativa.AspNetCore is the ASP.NET Core version. The install footprint includes the NuGet package and the wkhtmltopdf native binary (or its installation on the server). Configuration is done at startup via RotativaConfiguration.Setup() pointing to the wkhtmltopdf binary location. Per-render options (paper size, margins, orientation, headers, footers) are passed as constructor arguments to the ViewAsPdf result class. The primary use case is invoice generation, report download, and document export directly from existing ASP.NET MVC views.

Architectural Differences

Rotativa and IronPDF both convert HTML to PDF, but their integration models differ fundamentally. Rotativa is a framework integration layer — it hooks into ASP.NET's action result pipeline to capture rendered Razor views and pipe them through wkhtmltopdf. IronPDF is a PDF library — it generates PDFs from HTML strings, files, or URLs via an injected ChromePdfRenderer, and the PDF result is then returned from the controller using standard File() result types.

IronPDF uses embedded Chromium for rendering — the same engine as Chrome and Edge — which means full CSS3 support including Flexbox, Grid, CSS variables, and modern web font loading. The responsive CSS guide covers how Chromium handles print media queries and modern layouts. IronPDF's ChromePdfRenderer is injectable as a singleton and is called explicitly in the action method. The resulting PdfDocument implements IDisposable and is returned to the browser via File(pdf.BinaryData, "application/pdf", filename). License initialization is a one-time startup call; see the license setup guide.

The shift from Rotativa to IronPDF requires making the PDF rendering step explicit in the controller — calling the renderer rather than returning a result that handles rendering implicitly. The Razor view content is obtained by rendering the view to an HTML string first, then passing that string to IronPDF. This is slightly more verbose but provides clearer control over the render pipeline and removes the wkhtmltopdf subprocess dependency.

Operation Comparisons

ViewAsPdf → Render View to HTML String + IronPDF

Rotativa — ViewAsPdf in MVC Controller

using Rotativa.AspNetCore;
using Microsoft.AspNetCore.Mvc;

[Route("invoices")] public class InvoiceController : Controller { // Rotativa.AspNetCore — return ViewAsPdf directly from action // Rotativa renders the Razor view by calling the MVC view engine internally // then pipes the rendered HTML through wkhtmltopdf subprocess [HttpGet("{id}/pdf")] public IActionResult GetInvoicePdf(int id) { var model = GetInvoiceModel(id);

// ViewAsPdf renders "Invoice" view with model and returns PDF stream // Configuration: PageSize, PageMargins, PageOrientation as constructor args return new ViewAsPdf("Invoice", model) { PageSize = Rotativa.AspNetCore.Options.Size.A4, PageMargins = new Rotativa.AspNetCore.Options.Margins(10, 10, 10, 10), PageOrientation = Rotativa.AspNetCore.Options.Orientation.Portrait, FileName = $"invoice-{id}.pdf", // wkhtmltopdf custom arguments — each must be individually evaluated CustomSwitches = "--disable-smart-shrinking --no-stop-slow-scripts" }; }

private object GetInvoiceModel(int id) => new { Id = id, Customer = "Acme Corp", Total = 1599.00m }; }

Concrete constraints:

  • ViewAsPdf implicitly invokes the MVC view engine to render the Razor view, then calls wkhtmltopdf. This implicit rendering is replaced by explicit view-to-string rendering in the IronPDF pattern.
  • CustomSwitches passes raw wkhtmltopdf CLI flags. Each flag must be individually evaluated for IronPDF equivalents — most are no longer needed because Chromium's defaults are more capable than wkhtmltopdf's.
  • wkhtmltopdf uses QtWebKit rendering — Flexbox, CSS Grid, CSS variables, and modern web fonts do not render correctly.
  • PageMargins uses millimeters — the same unit as IronPDF, so no conversion is required.
  • Rotativa renders synchronously from the request thread — no async support.

IronPDF — Explicit View-to-HTML-to-PDF

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[Route("invoices")] public class InvoiceController : Controller { private readonly ChromePdfRenderer _renderer; private readonly IRazorViewRenderer _viewRenderer; // see DI setup below

public InvoiceController(ChromePdfRenderer renderer, IRazorViewRenderer viewRenderer) { _renderer = renderer; _viewRenderer = viewRenderer; }

[HttpGet("{id}/pdf")] public async Task GetInvoicePdf(int id) { var model = GetInvoiceModel(id);

// Step 1: Render the Razor view to an HTML string string html = await _viewRenderer.RenderViewToStringAsync("Invoice", model);

// Step 2: Convert HTML to PDF with IronPDF using var pdf = await _renderer.RenderHtmlAsPdfAsync(html);

// Step 3: Return the PDF bytes as a file download return File(pdf.BinaryData, "application/pdf", $"invoice-{id}.pdf"); }

private object GetInvoiceModel(int id) => new { Id = id, Customer = "Acme Corp", Total = 1599.00m }; }

The IRazorViewRenderer helper renders a Razor view to an HTML string before passing it to IronPDF. A standard implementation using ASP.NET Core's IRazorViewEngine and ITemplateRenderer from the Razor.Templating.Engine NuGet package, or a custom implementation, handles this step. The HTML string to PDF guide covers IronPDF's rendering configuration. IronPDF's Chromium engine supports all modern CSS — remove any @media print workarounds added specifically for wkhtmltopdf compatibility.

UrlAsPdf → RenderUrlAsPdf

Rotativa — UrlAsPdf

using Rotativa.AspNetCore;
using Microsoft.AspNetCore.Mvc;

[Route("reports")] public class ReportController : Controller { [HttpGet("{id}/pdf")] public IActionResult GetReportPdf(int id) { // UrlAsPdf fetches the URL using wkhtmltopdf's own HTTP request // The URL must be accessible from the server — same-site works if // wkhtmltopdf is configured with the correct base URL return new UrlAsPdf($"https://app.example.com/reports/{id}") { PageSize = Rotativa.AspNetCore.Options.Size.A4, PageOrientation = Rotativa.AspNetCore.Options.Orientation.Portrait }; } }

Concrete constraints:

  • wkhtmltopdf's URL fetch operates in its own process with its own HTTP stack — session cookies are not automatically forwarded from the ASP.NET request. Authenticated pages require cookie forwarding via CustomSwitches.
  • wkhtmltopdf may encounter SSL certificate errors on internal HTTPS URLs.

IronPDF — RenderUrlAsPdf

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[Route("reports")] public class ReportController : Controller { private readonly ChromePdfRenderer _renderer;

public ReportController(ChromePdfRenderer renderer) { _renderer = renderer; }

[HttpGet("{id}/pdf")] public async Task GetReportPdf(int id) { // Configure cookies from the current request context for authenticated URLs _renderer.RenderingOptions.CustomCookies = new System.Collections.Generic.Dictionary { { "session_id", Request.Cookies["session_id"] ?? string.Empty } };

using var pdf = await _renderer.RenderUrlAsPdfAsync( $"https://app.example.com/reports/{id}");

return File(pdf.BinaryData, "application/pdf", $"report-{id}.pdf"); } }

IronPDF renders URLs in-process — session cookies from the ASP.NET request context can be forwarded directly. The URL to PDF guide covers cookie injection and JavaScript wait conditions.

Custom wkhtmltopdf Switches → RenderingOptions

Rotativa — CustomSwitches

// Rotativa CustomSwitches — raw wkhtmltopdf CLI flags
// These must be individually evaluated during migration
return new ViewAsPdf("Report", model)
{
    PageSize = Rotativa.AspNetCore.Options.Size.A4,
    // Common wkhtmltopdf flags and their migration notes:
    CustomSwitches =
        "--disable-smart-shrinking " +  // Chromium: not needed
        "--no-stop-slow-scripts " +     // Chromium: default behavior
        "--javascript-delay 2000 " +    // IronPDF: WaitFor.RenderDelay(2000)
        "--load-error-handling ignore " // IronPDF: no equivalent flag needed
};

Concrete constraints:

  • Every CustomSwitches flag must be individually evaluated. Most are wkhtmltopdf-specific workarounds not needed with Chromium.
  • --javascript-delay N → RenderingOptions.WaitFor.RenderDelay(N) in milliseconds.
  • --disable-smart-shrinking is a wkhtmltopdf-specific scaling behavior — not applicable to Chromium, can be removed.
  • --header-html and --footer-html flags → RenderingOptions.HtmlHeader and RenderingOptions.HtmlFooter.

IronPDF — RenderingOptions

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;

// JavaScript wait replaces --javascript-delay
renderer.RenderingOptions.WaitFor.RenderDelay(2000); // 2000 ms

// Other common mappings:
// --no-stop-slow-scripts   → Chromium default, no config needed
// --disable-smart-shrinking → Chromium has no equivalent, not needed
// --viewport-size WxH      → RenderingOptions.ViewPortWidth / ViewPortHeight
// --zoom F                 → RenderingOptions.Zoom
// --user-style-sheet path  → Inline CSS in the HTML template

using var pdf = renderer.RenderHtmlAsPdf("<html><body><p>Content</p></body></html>");
pdf.SaveAs("output.pdf");

Evaluate every CustomSwitches flag against the rendering options reference to find the RenderingOptions equivalent. Most wkhtmltopdf-specific flags have either a direct RenderingOptions equivalent or are unnecessary with Chromium's more capable defaults.

Headers and Footers

Rotativa — Headers and Footers

// Rotativa headers and footers — passed as HTML file paths to wkhtmltopdf
// wkhtmltopdf page number tokens: [page] and [toPage]
return new ViewAsPdf("Invoice", model)
{
    PageSize = Rotativa.AspNetCore.Options.Size.A4,
    // Rotativa passes HTML file paths to wkhtmltopdf --header-html / --footer-html
    // The HTML files use wkhtmltopdf's substitution tokens
    CustomSwitches = "--header-html /app/templates/header.html " +
                     "--footer-html /app/templates/footer.html"
    // header.html contains: <span class='page'></span> of <span class='topage'></span>
    // or: Page [page] of [toPage]  (depends on wkhtmltopdf version)
};

Concrete constraints:

  • Rotativa's headers/footers are passed as HTML files via CustomSwitches. IronPDF uses inline HtmlHeaderFooter.HtmlFragment strings — no separate HTML files.
  • wkhtmltopdf page number injection uses <span class='page'> / <span class='topage'> JavaScript substitution, or [page] / [toPage] tokens depending on implementation. Both must be replaced with IronPDF's {page} / {total-pages}.

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 15;

// IronPDF inline HTML fragments — no external files needed
// Token syntax: {page} and {total-pages}
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 12,
    HtmlFragment = "<div style='font-size:9px; font-family:Arial; " +
                   "text-align:right; padding:0 12px;'>Invoice — Acme Corp</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 10,
    HtmlFragment = "<div style='font-size:8px; font-family:Arial; " +
                   "text-align:center;'>Page {page} of {total-pages}</div>"
};

using var pdf = renderer.RenderHtmlAsPdf("<html><body><p>Invoice content</p></body></html>");
pdf.SaveAs("invoice.pdf");

Replace external HTML file references in CustomSwitches with inline HtmlFragment strings. Update all wkhtmltopdf page number tokens ([page]/[toPage] or <span class='page'>) to IronPDF's {page} and {total-pages}. The headers and footers guide covers all available options.

Breaking Changes & Gotchas

  • Implicit rendering → explicit view-to-string: Rotativa's ViewAsPdf renders the Razor view implicitly. IronPDF requires rendering the view to an HTML string first. Add a IRazorViewRenderer (or equivalent) helper service and inject it alongside ChromePdfRenderer.
  • [page] / [toPage] / <span class='page'> tokens: Any of these wkhtmltopdf page number injection patterns must be replaced with IronPDF's {page} and {total-pages}. Old tokens render as literal text without error — a silent rendering bug.
  • CSS Flexbox / Grid now supported: Templates that used float-based fallbacks for wkhtmltopdf compatibility can be updated to modern CSS. This is an improvement but requires review.
  • Web fonts now load reliably: Base64 font workarounds and local font fallbacks added for wkhtmltopdf can be removed.
  • CustomSwitches removed: Every wkhtmltopdf CLI flag must be individually evaluated. Most have RenderingOptions equivalents or are no longer needed.
  • wkhtmltopdf binary removal: Remove the wkhtmltopdf binary from deployment packages, Docker images, and CI/CD artifacts. Remove RotativaConfiguration.Setup() from startup. On Linux, add Chromium system library packages.
  • ActionAsPdf has no direct equivalent: ActionAsPdf invokes another controller action to get HTML content. The IronPDF equivalent requires either rendering the action's view to a string, or fetching the action's output URL and using RenderUrlAsPdf().
  • PdfDocument is IDisposable: Rotativa returned the file stream implicitly. IronPDF returns PdfDocument — wrap in using and access bytes via pdf.BinaryData.
  • Namespace change: Remove using Rotativa.AspNetCore;. Replace with using IronPdf;.
  • License key required: Rotativa is open-source. IronPDF requires IronPdf.License.LicenseKey at startup.

Migration Checklist

  1. Audit all Rotativa result types: List every ViewAsPdf, PartialViewAsPdf, UrlAsPdf, and ActionAsPdf usage. Note CustomSwitches flags and header/footer HTML file references.
  2. Add a Razor-to-string rendering helper: Implement or install a service that renders a Razor view to an HTML string (e.g., using IRazorViewEngine and ICompositeViewEngine, or the Razor.Templating.Engine NuGet package). Register it in DI.
  3. Evaluate CSS templates: Review Razor views used for PDF generation. Identify float-based layout workarounds added for wkhtmltopdf. Plan modernization to Flexbox/Grid.
  4. Install IronPDF via NuGet: dotnet add package IronPdf.
  5. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; and remove RotativaConfiguration.Setup(). See the license setup guide.
  6. Register ChromePdfRenderer in DI: Add builder.Services.AddSingleton<ChromePdfRenderer>() with RenderingOptions configured once.
  7. Replace ViewAsPdf actions: For each action, change to: (1) render view to HTML string, (2) await _renderer.RenderHtmlAsPdfAsync(html), (3) return File(pdf.BinaryData, "application/pdf", filename). Wrap PdfDocument in using.
  8. Replace UrlAsPdf actions: Map to _renderer.RenderUrlAsPdfAsync(url). Forward session cookies if needed.
  9. Update header/footer HTML: Move HTML from external files to HtmlHeaderFooter.HtmlFragment. Update page number token syntax.
  10. Evaluate CustomSwitches flags: Map each flag to a RenderingOptions property or confirm it is no longer needed with Chromium.
  11. Remove wkhtmltopdf binary: Remove from deployment artifacts, Docker images, and CI/CD build steps. Add Chromium system library packages on Linux.
  12. Remove Rotativa NuGet package: Once all replacements compile and rendering tests pass, remove Rotativa.AspNetCore.

Conclusion

When staying on Rotativa is technically reasonable

Rotativa is technically reasonable when the development team's primary concern is simplicity of integration within the MVC action result pattern — returning ViewAsPdf in one line is genuinely convenient. If the HTML templates are designed to work within wkhtmltopdf's CSS limitations (float-based layouts, no Flexbox, system fonts only), the rendering output is acceptable, and there is no need for post-render manipulation, staying on Rotativa is defensible as long as it remains maintained.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when wkhtmltopdf's CSS limitations are creating rendering problems in modern templates; when web font loading failures are causing production issues; when JavaScript-rendered content is unreliable; when the team needs async rendering under concurrent load; when post-render operations (merge, sign, encrypt) require an additional library alongside Rotativa; or when the wkhtmltopdf binary is complicating deployment across multiple platforms.

What the cutover typically involves at the code level

The most significant structural change is moving from Rotativa's implicit view rendering to an explicit view-to-string step followed by RenderHtmlAsPdf(). Once a shared view renderer helper is in place, the per-controller changes are consistent and systematic. The CustomSwitches flag evaluation is a one-time analysis. Header/footer token syntax updates and template CSS modernization are the primary template-level work items, both of which improve the template quality as a side effect.

In your current Rotativa integration, how many ViewAsPdf results rely on CSS that was intentionally constrained for wkhtmltopdf compatibility — and how much template simplification would be available if those constraints were lifted for a Chromium-based renderer?
