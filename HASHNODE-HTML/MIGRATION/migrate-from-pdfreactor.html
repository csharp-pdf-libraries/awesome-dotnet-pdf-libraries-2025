# Migrating from PDFreactor to IronPDF: a practical .NET guide

The original version of this article is published at https://ironsoftware.com/csharp/pdf/blog/migrate-from-pdfreactor/.

Framing

PDF generation is rarely a neutral technical decision in enterprise .NET stacks. Teams choose a library early, build abstractions around it, and often go years without revisiting the choice—until a trigger forces the question: maintenance windows stretching, licensing model changes, a new platform target (Linux containers, ARM, WebAssembly), or a framework upgrade that exposes undocumented assumptions in the integration layer. At that point, evaluating alternatives becomes an engineering task with real scope.

HTML-to-PDF renderers occupy a specific tier in this landscape. They promise fidelity to browser-rendered markup, which makes them attractive for teams already producing HTML templates—invoices, reports, letters—that need to be archived or delivered as fixed-layout documents. The tradeoff is a larger runtime dependency footprint and tighter coupling to a browser engine whose version lifecycle may not align with the application's release cadence.

PDFreactor sits in this category. Understanding precisely where it fits architecturally—and where IronPDF takes a different approach to the same problem—is the foundation for a credible effort estimate before any migration work begins.

What PDFreactor Is Designed To Do

PDFreactor is an HTML-to-PDF conversion engine with a strong emphasis on CSS compliance, particularly CSS Paged Media—the W3C specification that governs page layout, running headers and footers, page counters, and print-specific layout rules. It is designed for use cases where the source document is already HTML/CSS and where precise typographic and layout control is required: regulatory reports, publishing workflows, complex invoices with precise column widths, and documents that need to conform to specific paper standards.

PDFreactor's integration model is server-based. It exposes a Java-based core that can be invoked via a local or remote API call; .NET clients communicate with the engine over HTTP or via a provided client library rather than loading a managed assembly directly. This means the rendering runtime is typically a separate process or service, which changes the deployment profile relative to an in-process library. Verify current .NET client library availability and supported versions in the official PDFreactor documentation, as the integration surface may have changed across releases.

Architectural Differences

IronPDF takes a different integration path. Rather than delegating to a separate server process, it bundles a Chromium-based rendering engine that runs in-process alongside the .NET application. The consuming code references a single NuGet package; no separate server, no HTTP client, no external service to keep healthy. This changes the deployment model significantly for teams using Docker or Azure App Service, where managing a sidecar process adds operational surface area.

The HTML to PDF rendering pipeline in IronPDF is exposed through a straightforward C# API: pass an HTML string, a file path, or a live URL, and receive a PdfDocument object that can be saved, streamed, or further manipulated. The PdfDocument implements IDisposable, and correct disposal is the primary resource management concern—there is no connection pool to drain or service to shut down. For teams already comfortable with the using pattern in .NET, the mental model maps cleanly.

IronPDF's rendering options surface exposes paper size, margins, JavaScript execution timeout, media type simulation, and print-vs-screen CSS selection. Teams migrating from PDFreactor will find conceptual parity for most standard layout operations, though the specific configuration API differs: PDFreactor's CSS Paged Media extensions are handled through the HTML/CSS content itself in IronPDF's model, rather than through library-level properties. Assess any custom @page rule usage in existing templates during discovery.

Operation Comparisons

HTML String to PDF

PDFreactor — HTML String to PDF:

PDFreactor's .NET client accepts an HTML string as input and submits it to the PDFreactor service. The response is a byte array or stream representing the rendered PDF. A typical integration involves:

  • Instantiating a PDFreactor client configured with the service endpoint (localhost or remote)
  • Populating a configuration object with the HTML content, CSS references, and output options
  • Calling the conversion method and receiving binary PDF data
  • Handling HTTP-level errors in addition to rendering errors

Technical constraints to note:

  • The rendering process runs out-of-process; network latency affects throughput even on localhost
  • CSS external resource references must be resolvable by the server process, not the client machine
  • Thread safety depends on how the service handles concurrent requests, which varies by deployment

IronPDF — HTML String to PDF:

using IronPdf;

// Initialize renderer — thread-safe; can be reused across requests
var renderer = new ChromePdfRenderer();

// Configure rendering options
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 20;
renderer.RenderingOptions.EnableJavaScript = true;
renderer.RenderingOptions.WaitFor.RenderDelay(200); // ms, for JS-rendered content

// Render HTML string to PdfDocument
using var pdf = renderer.RenderHtmlAsPdf("<h1>Quarterly Report</h1><p>Content here.</p>");

// Save or stream the result
pdf.SaveAs("/output/report.pdf");

The HTML string to PDF guide covers base URL configuration for resolving relative CSS and image references—a common point of divergence when templates reference external assets. Because rendering is in-process, all file paths and URLs must be accessible from the application's execution context rather than a separate server's file system. The rendering options reference documents the full configuration surface.

URL to PDF

PDFreactor — URL to PDF:

PDFreactor can accept a URL as the source document, with the server process fetching and rendering the page. This enables rendering of authenticated pages if the service is configured with appropriate credentials or cookies.

Technical constraints:

  • The PDFreactor service must have network access to the target URL
  • Authentication (cookies, bearer tokens) must be configured server-side or passed through the client configuration
  • Rendering is synchronous from the client's perspective; long-loading pages increase response time

IronPDF — URL to PDF:

using IronPdf;

var renderer = new ChromePdfRenderer();

// Set a custom user agent if the target site requires it
renderer.RenderingOptions.CustomCssUrl = null; // leave null unless overriding stylesheets
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.Letter;

// Render a live URL — the Chromium engine fetches and renders the page in-process
using var pdf = renderer.RenderUrlAsPdf("https://example.com/report");

pdf.SaveAs("/output/page-snapshot.pdf");

The URL to PDF documentation covers cookie injection for authenticated pages and proxy configuration—scenarios that frequently arise when migrating from a server-based renderer that handled credentials differently. Note that the calling application process must have outbound HTTP access to the target host.

Headers and Footers

PDFreactor — Headers and Footers:

PDFreactor supports CSS Paged Media's @page rule with @top-left, @top-center, @bottom-right, and similar margin box properties. Headers and footers are defined in the CSS embedded in the HTML document and rendered by the engine as part of the page layout model. This approach keeps header/footer logic in the template, not the host application.

Technical constraints:

  • CSS margin box support is not fully implemented in all Chromium versions; verify specific rule coverage
  • Running elements (content floated into margin boxes via position: running()) may not port directly
  • Page counter CSS functions map conceptually but syntax differences apply

IronPDF — Headers and Footers:

using IronPdf;
using IronPdf.Engines.Chrome;

var renderer = new ChromePdfRenderer();

// Text-based header
renderer.RenderingOptions.TextHeader = new IronPdf.Engines.Chrome.TextHeaderFooter
{
    CenterText = "Confidential",
    DrawDividerLine = true,
    FontSize = 9
};

// Text-based footer with page numbers
renderer.RenderingOptions.TextFooter = new IronPdf.Engines.Chrome.TextHeaderFooter
{
    LeftText = "{date}",
    RightText = "Page {page} of {total-pages}",
    FontSize = 8
};

using var pdf = renderer.RenderHtmlAsPdf(htmlContent);
pdf.SaveAs("/output/document-with-headers.pdf");

For templates that require rich HTML in headers and footers, IronPDF supports HTML-based header/footer objects where the header content is itself an HTML string. The headers and footers guide covers both text and HTML variants, including per-first-page suppression. Teams migrating from CSS Paged Media headers should plan to reimplement header/footer logic using IronPDF's API rather than expecting the CSS margin box model to transfer directly.

PDF/A Compliance

PDFreactor — PDF/A Compliance:

PDFreactor supports output of PDF/A-compliant documents as a conversion option. The conformance level is specified in the configuration object before rendering.

Technical constraints:

  • Verify exactly which PDF/A levels (1b, 2b, 3b, etc.) are supported in the installed version
  • Embedded font requirements for PDF/A must be satisfied by the HTML/CSS content
  • Color profile embedding requirements apply; test with validators post-generation

IronPDF — PDF/A Compliance:

using IronPdf;

// Render a standard PDF first
var renderer = new ChromePdfRenderer();
using var pdf = renderer.RenderHtmlAsPdf(htmlContent);

// Convert to PDF/A-3b
pdf.SaveAsPdfA("/output/compliant.pdf", PdfAVersions.PdfA3b);

The PDF/A compliance guide covers the supported conformance levels and the validation considerations teams should apply post-conversion. PDF/A requirements around font embedding and color profiles are enforced during the save step; content that fails compliance requirements surfaces as errors at that stage rather than silently producing non-conformant output. Validate all migrated PDF/A output against an independent validator before retiring the prior integration.

Breaking Changes & Gotchas

  • No server process. The most significant architectural change is the elimination of the PDFreactor service. Any infrastructure automation (health checks, service restarts, remote API calls) tied to the PDFreactor server must be removed or replaced. The deployment becomes simpler but the application process now carries the Chromium engine weight.
  • Disposal is mandatory. PdfDocument and ChromePdfRenderer implement IDisposable. PDFreactor's client-based model does not expose the same lifecycle concern since the rendering happens remotely. Teams should audit for any code that holds PdfDocument references in long-lived objects without disposal.
  • CSS Paged Media extensions do not transfer. PDFreactor's extended support for CSS Paged Media (running elements, named page sequences, CMYK color spaces) is not available through IronPDF's Chromium renderer. Any template relying on these features requires redesign.
  • External resource resolution path changes. Templates with relative CSS or image references that were resolved from the PDFreactor server's working directory must be updated; paths and base URLs are now resolved from the application's execution context. See the base URL configuration options.
  • Thread safety model differs. ChromePdfRenderer is thread-safe for concurrent use; however, PdfDocument objects should not be shared across threads without coordination. Refer to the official documentation for the current thread safety guarantees.
  • Platform-specific native binaries. IronPDF ships platform-specific Chromium binaries via the NuGet package. Container images must include the required system libraries for Chromium operation on Linux (glibc version, font packages). This is not a concern with PDFreactor's .NET client library, which delegates rendering to the server.
  • License key required at startup. IronPDF requires a valid license key before use. PDFreactor also has a license model; ensure the provisioning approach (environment variable, appsettings.json, startup code) is updated appropriately.
  • Print vs. screen media type. IronPDF defaults to print media type for rendering. Templates previously tested in a browser (screen media) may render differently. Configure RenderingOptions.CssMediaType if templates define distinct print/screen stylesheets.

Migration Checklist

  1. Audit existing PDFreactor usage. Enumerate every call site that constructs a PDFreactor client, configures a render operation, or processes PDFreactor output. Document the full set of configuration properties used.
  2. Identify CSS Paged Media dependencies. Search HTML templates for @page rules, running(), named pages, CMYK color values, and margin box properties. Each of these represents a migration risk that requires design work, not just API remapping.
  3. Install the IronPDF NuGet package. Run dotnet add package IronPdf or add via the NuGet Package Manager. Verify the package resolves platform-specific native binaries for all target runtime identifiers (win-x64, linux-x64, etc.).
  4. Set up the license key. Configure the IronPDF license key before the first use of the library. The recommended approach is environment variable or configuration file injection; see the license key setup guide for the exact mechanism.
  5. Replace PDFreactor namespaces and using directives. Remove PDFreactor client library references and substitute using IronPdf; and related namespaces. The compiler will surface all remaining call sites for remapping.
  6. Remap core rendering calls. Replace each PDFreactor render operation with the equivalent ChromePdfRenderer.RenderHtmlAsPdf(), RenderUrlAsPdf(), or RenderHtmlFileAsPdf() call. Port configuration properties to RenderingOptions.
  7. Redesign CSS-driven headers and footers. For each template using CSS Paged Media headers/footers, implement the equivalent using RenderingOptions.TextHeader, TextFooter, or HTML header/footer objects.
  8. Update disposal patterns. Wrap all PdfDocument instantiations in using statements or call Dispose() explicitly in finally blocks. Check for any long-lived caches of PdfDocument objects.
  9. Update path resolution for external resources. Templates with relative CSS, image, or font references need a BaseUrlOrPath value passed to the render call, pointing to the directory from which relative paths should be resolved.
  10. Verify PDF/A output. If the application produces PDF/A documents, run the IronPDF output through an independent validator (veraPDF or Adobe Preflight). Do not assume conformance without external validation.
  11. Remove PDFreactor service infrastructure. Update deployment scripts, health checks, and monitoring to remove references to the PDFreactor server process. Ensure the application process now has the system library dependencies required by the Chromium binary on Linux hosts.
  12. Run regression tests across representative document set. Compare IronPDF output visually and structurally against PDFreactor output for a representative sample. Pay particular attention to multi-page layout, font embedding, and any documents that previously relied on CSS Paged Media features.

Conclusion

When staying on PDFreactor is technically reasonable

Teams with deep investment in CSS Paged Media—particularly running elements, CMYK output, or named page sequences—will find PDFreactor's compliance with the W3C specification to be a genuine technical advantage that is difficult to replicate in a Chromium-based renderer. If the template library is large, the CSS is complex, and the output has been certified against a compliance requirement tied to specific layout behavior, the engineering cost of redesigning those templates may outweigh the benefits of migration. Additionally, teams with an existing operational pattern around managing the PDFreactor service may find the in-process deployment model a less natural fit if the PDF generation workload is already isolated as a dedicated service.

Signals that indicate migration is worth the engineering effort

Migration becomes more attractive when the deployment complexity of maintaining a separate PDFreactor service creates friction—particularly in containerized or serverless environments where sidecar processes are costly to manage. If the PDFreactor .NET client library has lagged behind .NET version support, or if licensing constraints are adding cost that the usage level no longer justifies, those are concrete signals. Teams that have been working around limitations in PDFreactor's .NET integration layer (as opposed to its CSS rendering capability) often find the in-process model meaningfully easier to work with. Similarly, if the migration is occurring alongside a broader modernization effort—upgrading to .NET 8, moving to Linux containers, standardizing on async-first patterns—bundling the PDF library change into that work reduces the incremental cost.

What the cutover typically involves at the code level

The code-level work is primarily in two areas: replacing the PDFreactor client and configuration API with ChromePdfRenderer and RenderingOptions, and redesigning any templates that depend on CSS Paged Media features that do not have a direct equivalent in Chromium's print rendering model. The first area is mechanical and predictable; the second requires CSS authoring work proportional to the complexity of existing templates. For applications where templates are simple—HTML with inline styles, no advanced @page rules—the migration is largely a namespace and API replacement exercise. For applications where PDFreactor was specifically chosen for its CSS Paged Media compliance, that complexity is real and should be scoped carefully.
