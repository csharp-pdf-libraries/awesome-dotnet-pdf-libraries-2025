Migrating from HiQPdf to IronPDF: what changes, what breaks, what maps

from install to first PDF — the full migration path

Framing

Chromium-based HTML-to-PDF libraries for .NET have proliferated in response to the clear demand for server-side rendering that matches what a user sees in a browser. HiQPdf is one of the more established names in this segment — a commercial .NET library that bundles a Chromium rendering engine and exposes a .NET API for HTML-to-PDF conversion. Teams that adopted HiQPdf typically needed a managed-code integration with Chromium-quality CSS support, web font rendering, and JavaScript execution without managing external browser processes themselves.

Re-evaluation tends to happen when the surrounding requirements grow beyond what a rendering-focused library provides. Applications that initially needed only HTML-to-PDF conversion often add requirements over time: digital signatures for compliance workflows, PDF/A output for archival, form filling for document automation, or batch processing for high-throughput generation. These additions are straightforward with a library that covers the full PDF lifecycle but require additional packages or workarounds with a rendering-only library. License renewals, .NET runtime upgrades, or deployment model changes can also trigger a comparison.

This guide covers the migration from HiQPdf to IronPDF for .NET engineers evaluating or executing the switch. The product status and last release of HiQPdf should be verified in official documentation. Both libraries install via a single NuGet package — HiQPdf's single-package install footprint matches IronPDF's on Windows. The migration is classified as Medium effort because both libraries are Chromium-based HTML-to-PDF renderers with similar conceptual APIs, but the instance-versus-static API model, disposal semantics, header/footer configuration, and rendering options naming conventions all require systematic updates.

What HiQPdf Is Designed to Do

HiQPdf is a commercial .NET HTML-to-PDF library that bundles an embedded Chromium rendering engine. The library's .NET support range and last release should be verified in official documentation. It installs as a single NuGet package, which simplifies project setup. The primary API is the HtmlToPdf class, which is instantiated with optional configuration parameters and exposes conversion methods for HTML strings, HTML files, and URLs. Configuration options cover paper size, margins, orientation, header/footer content, JavaScript execution, and PDF security settings.

HiQPdf's architecture is generation-focused: the library's primary purpose is rendering HTML content to PDF. It includes basic PDF operations such as password protection and metadata, but its core differentiator is Chromium-quality HTML rendering without external process dependencies. The primary use case should be verified in official documentation, but HiQPdf is typically used in ASP.NET applications for report generation, invoice export, and HTML-to-PDF document creation where CSS fidelity with the browser is a priority.

Architectural Differences

HiQPdf and IronPDF are both Chromium-based HTML-to-PDF libraries, which means the rendering engine and output fidelity are comparable. The differences are in API design, disposal semantics, the manipulation surface available after rendering, and the async rendering model.

HiQPdf's HtmlToPdf class is instantiated per-operation or configured once and reused. Its conversion methods return a byte array directly — there is no IDisposable result object to manage. IronPDF uses a ChromePdfRenderer instance (designed for singleton DI registration) whose RenderHtmlAsPdf() method returns a PdfDocument that implements IDisposable and must always be wrapped in a using block. This disposal requirement is the most structurally pervasive change across all call sites.

IronPDF's PdfDocument additionally exposes a full manipulation surface: merge, split, form filling, digital signatures, encryption, PDF/A and PDF/UA compliance, text extraction, stamping, annotations, and redaction — all without additional libraries. The rendering options reference covers IronPDF's full configuration including paper size, margins, CSS media type, JavaScript timing, and viewport settings. License initialization is a one-time startup call; see the license setup guide.

Operation Comparisons

HTML String to PDF

HiQPdf — HTML String to PDF

using HiQPdf;

// HiQPdf uses an instantiated HtmlToPdf object with property-based configuration
var htmlToPdf = new HtmlToPdf();

// Page setup
htmlToPdf.Document.PageSize = PdfPageSize.A4;       // verify enum name
htmlToPdf.Document.PageOrientation = PdfPageOrientation.Portrait; // verify
htmlToPdf.Document.Margins.Left = 20;    // mm
htmlToPdf.Document.Margins.Right = 20;
htmlToPdf.Document.Margins.Top = 20;
htmlToPdf.Document.Margins.Bottom = 20;

// JavaScript wait — allows JS-rendered content to complete
// Verify the exact property path in official documentation
htmlToPdf.BrowserWidth = 1280; // viewport width in pixels
// htmlToPdf.JavaScriptEnabled = true; // verify property name

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #1042</h1>
  <p>Total: $1,599.00</p>
</body>
</html>";

// ConvertHtmlToMemory returns byte[] — no disposal required
byte[] pdfBytes = htmlToPdf.ConvertHtmlToMemory(html, null);

// Or save directly to file
// htmlToPdf.ConvertHtmlToFile(html, null, "invoice.pdf");

Concrete constraints:

  • HiQPdf's configuration is accessed through nested objects on the HtmlToPdf instance (Document.Margins.*, Document.PageSize, etc.). Verify exact property paths in official documentation.
  • ConvertHtmlToMemory() returns byte[] directly — no IDisposable result to manage. This changes to PdfDocument in IronPDF.
  • Margin units should be verified in official documentation — HiQPdf may use mm, points, or pixels depending on the property.
  • HiQPdf may accept null or a base URL as the second argument to ConvertHtmlToMemory() for resolving relative asset references

IronPDF — HTML String to PDF

using IronPdf;

// ChromePdfRenderer configured once, reused across calls — register as singleton
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.PaperOrientation = IronPdf.Rendering.PdfPaperOrientation.Portrait;
renderer.RenderingOptions.MarginTop = 20;    // millimeters
renderer.RenderingOptions.MarginBottom = 20;
renderer.RenderingOptions.MarginLeft = 20;
renderer.RenderingOptions.MarginRight = 20;

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #1042</h1>
  <p>Total: $1,599.00</p>
</body>
</html>";

// PdfDocument is IDisposable — always use a using block
using var pdf = renderer.RenderHtmlAsPdf(html);

byte[] pdfBytes = pdf.BinaryData;         // equivalent to ConvertHtmlToMemory()
pdf.SaveAs("invoice.pdf");                // equivalent to ConvertHtmlToFile()

The structural change at every call site is: byte[] pdfBytes = htmlToPdf.Convert() becomes using var pdf = renderer.Render() with pdf.BinaryData for byte access. Full rendering configuration is in the HTML string to PDF guide.

URL to PDF

HiQPdf — URL to PDF

using HiQPdf;

var htmlToPdf = new HtmlToPdf();
htmlToPdf.Document.PageSize = PdfPageSize.A4;
htmlToPdf.Document.Margins.Left = 15;
htmlToPdf.Document.Margins.Right = 15;
htmlToPdf.Document.Margins.Top = 15;
htmlToPdf.Document.Margins.Bottom = 15;

// JavaScript delay — allows the page to finish rendering
// Verify the exact property name in official documentation
// htmlToPdf.JavaScriptDelay = 2000; // ms

// ConvertUrlToMemory renders the URL and returns bytes
byte[] pdfBytes = htmlToPdf.ConvertUrlToMemory("https://reports.example.com/monthly");

System.IO.File.WriteAllBytes("monthly-report.pdf", pdfBytes);

Concrete constraints:

  • HiQPdf's URL rendering fetches and renders the URL using the embedded Chromium engine — the same rendering path as the HTML string converter.
  • JavaScript execution delay configuration
  • Authentication cookies should be verified in official documentation — the mechanism for injecting cookies into the URL fetch may differ from HTML rendering.

IronPDF — URL to PDF

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;

// WaitFor provides granular control over JavaScript timing
renderer.RenderingOptions.WaitFor.NetworkIdle(
    networkIdleTimeSpan: TimeSpan.FromSeconds(2));

// Cookie injection for authenticated URLs
renderer.RenderingOptions.CustomCookies =
    new System.Collections.Generic.Dictionary<string, string>
    {
        { "session_id", "your-session-token" }
    };

using var pdf = renderer.RenderUrlAsPdf("https://reports.example.com/monthly");
pdf.SaveAs("monthly-report.pdf");

IronPDF's WaitFor API provides multiple wait strategies — render delay, network idle, DOM element presence, and JavaScript expression evaluation. The URL to PDF guide covers all wait conditions and cookie injection patterns.

Headers and Footers

HiQPdf — Headers and Footers

using HiQPdf;

var htmlToPdf = new HtmlToPdf();
htmlToPdf.Document.PageSize = PdfPageSize.A4;

// HiQPdf header configuration
// HiQPdf typically provides header/footer via HTML content objects
// The exact configuration path depends on the version

// Conceptual pattern
// htmlToPdf.Header.Enabled = true;
// htmlToPdf.Header.Height = 30; // in points or mm
// htmlToPdf.Header.HtmlToPdfElement = ...; // verify how HTML content is set

// Page number token — HiQPdf uses its own syntax

byte[] pdfBytes = htmlToPdf.ConvertHtmlToMemory(
    "<html><body><p>Body content.</p></body></html>", null);

Concrete constraints:

  • HiQPdf's header/footer API structure should be verified in official documentation — the exact class hierarchy, property names, and HTML content specification method vary by version.
  • The page number token syntax used by HiQPdf's header/footer engine should be verified — it differs from IronPDF's {page} and {total-pages} tokens.
  • Header and footer height units (points vs mm) should be verified.

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 15;

// HtmlHeaderFooter takes an HTML fragment and a height in mm
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 15,   // mm
    HtmlFragment = "<div style='font-size:9px; text-align:right; " +
                   "font-family:Arial; padding:0 12px;'>" +
                   "Page {page} of {total-pages}</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 10,
    HtmlFragment = "<div style='font-size:8px; text-align:center; " +
                   "font-family:Arial;'>CONFIDENTIAL</div>"
};

using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><p>Body content.</p></body></html>");
pdf.SaveAs("document-with-headers.pdf");

IronPDF's page number tokens are {page} and {total-pages}. Verify HiQPdf's header/footer token syntax and update all header/footer HTML templates during migration — mismatched tokens render as literal strings. Full header/footer configuration is in the headers and footers guide.

Async Rendering in ASP.NET Core

HiQPdf — Synchronous Rendering in Async Context

using HiQPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("documents")] public class DocumentController : ControllerBase { [HttpGet("{id}/pdf")] public async Task GetDocument(int id) { string html = await BuildHtmlAsync(id);

// HiQPdf conversion is synchronous // If synchronous only, this blocks the ASP.NET Core thread pool var htmlToPdf = new HtmlToPdf(); htmlToPdf.Document.PageSize = PdfPageSize.A4;

// Task.Run() moves blocking work off the request thread // but does not reduce overall thread consumption byte[] pdfBytes = await Task.Run(() => htmlToPdf.ConvertHtmlToMemory(html, null));

return File(pdfBytes, "application/pdf", $"document-{id}.pdf"); }

private Task BuildHtmlAsync(int id) => Task.FromResult($"

Doc {id}

"); }

Concrete constraints:

  • HiQPdf's async support should be verified in official documentation — if conversion methods are synchronous, using them directly in an async ASP.NET Core action blocks a thread pool thread.
  • Task.Run() wrapping moves the work off the request thread but consumes a thread pool thread for the duration of the render. Under high concurrency this creates thread pool pressure.
  • Creating HtmlToPdf per-request versus sharing a configured instance

IronPDF — Async Rendering

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("documents")] public class DocumentController : ControllerBase { private readonly ChromePdfRenderer _renderer;

public DocumentController(ChromePdfRenderer renderer) { _renderer = renderer; }

[HttpGet("{id}/pdf")] public async Task GetDocument(int id) { string html = await BuildHtmlAsync(id);

// RenderHtmlAsPdfAsync is genuinely async — no Task.Run() needed using var pdf = await _renderer.RenderHtmlAsPdfAsync(html);

return File(pdf.BinaryData, "application/pdf", $"document-{id}.pdf"); }

private Task BuildHtmlAsync(int id) => Task.FromResult($"

Doc {id}

"); } ```

Replacing Task.Run(() => htmlToPdf.ConvertHtmlToMemory(...)) with await renderer.RenderHtmlAsPdfAsync() removes the thread pool pressure pattern. The async rendering guide covers concurrent rendering and parallel batch generation for high-throughput pipelines.

Breaking Changes & Gotchas

  • Return type change — byte[] to PdfDocument: HiQPdf's Convert* methods return byte[] directly. IronPDF returns PdfDocument, which implements IDisposable. Every call site must be updated to access pdf.BinaryData for bytes and every PdfDocument must be in a using block. Omitting using blocks causes unmanaged resource leaks.
  • Header/footer token syntax: HiQPdf uses its own token or macro syntax for page numbers in headers/footers
  • Configuration property paths: HiQPdf uses nested property access (Document.Margins.*, Document.PageSize). IronPDF uses flat properties directly on RenderingOptions. Every configuration line must be remapped.
  • Namespace change: Remove using HiQPdf; and related directives. Replace with using IronPdf;. Compile errors identify every affected file.
  • DI registration: HiQPdf's HtmlToPdf may be instantiated per-operation or reused
  • License key required: IronPdf.License.LicenseKey must be set at startup. HiQPdf uses its own license mechanism
  • Async rendering: If HiQPdf's conversion methods are synchronous and the current integration uses Task.Run() wrappers, replace those with await renderer.RenderHtmlAsPdfAsync().
  • Product status verification: HiQPdf's current maintenance status and .NET version support should be verified in official documentation before investing migration effort — this information affects migration urgency.
  • Linux deployment: Both libraries bundle Chromium. Verify that HiQPdf's Linux binary requirements and IronPDF's Chromium system library requirements overlap or differ for the target container or host environment.

Migration Checklist

  1. Audit all HiQPdf call sites: List every HtmlToPdf instantiation and its configuration (page size, margins, orientation, headers/footers, JavaScript delay) and the output method used (ConvertHtmlToMemory, ConvertHtmlToFile, ConvertUrlToMemory, ConvertUrlToFile).
  2. Verify HiQPdf status and .NET compatibility: Confirm the library's current maintenance posture and .NET runtime support range — this verification informs migration urgency.
  3. Install IronPDF via NuGet: dotnet add package IronPdf. Retain HiQPdf references until replacement code compiles and tests pass.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs. See the license setup guide.
  5. Register ChromePdfRenderer in DI: Add builder.Services.AddSingleton<ChromePdfRenderer>() and configure RenderingOptions once at registration.
  6. Update namespaces: Remove using HiQPdf; and related directives. Replace with using IronPdf;.
  7. Replace ConvertHtmlToMemory() calls: Map each to renderer.RenderHtmlAsPdf(html). Wrap PdfDocument in using. Access bytes via pdf.BinaryData.
  8. Replace ConvertHtmlToFile() calls: Map to renderer.RenderHtmlAsPdf(html) followed by pdf.SaveAs(path).
  9. Replace ConvertUrlToMemory() / ConvertUrlToFile() calls: Map to renderer.RenderUrlAsPdf(url). Configure WaitFor conditions from existing JavaScript delay configuration.
  10. Port header/footer configuration: Replace HiQPdf's header/footer objects with RenderingOptions.HtmlHeader/HtmlFooter. Identify and update the page number token syntax.
  11. Replace Task.Run() wrappers: Swap any await Task.Run(() => htmlToPdf.Convert*(...)) patterns with await renderer.RenderHtmlAsPdfAsync(...).
  12. Remove HiQPdf NuGet reference: Once all replacements compile and tests pass, remove the HiQPdf package reference and perform a final clean build.

Conclusion

When staying on HiQPdf is technically reasonable

HiQPdf is a reasonable choice when its HTML-to-PDF rendering meets the application's CSS fidelity requirements, the library's current .NET version support covers the target runtime, and the application's PDF requirements are limited to generation without a need for manipulation, signatures, or compliance output. Teams with a stable HiQPdf integration, established header/footer templates, and no new PDF requirements have no immediate pressure to migrate.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when new requirements include operations outside HiQPdf's rendering scope — digital signatures, PDF/A compliance, form filling, merge/split operations; when the library's maintenance status creates uncertainty about future .NET version support; when the synchronous rendering model is creating thread pool pressure in high-concurrency ASP.NET Core applications; or when a single-package approach covering the full PDF lifecycle is preferred over stitching together multiple libraries.

What the cutover typically involves at the code level

The API swap is systematic: replace HtmlToPdf instantiation with ChromePdfRenderer, remap Document. configuration properties to RenderingOptions., replace Convert method calls with renderer.Render(), add using blocks around PdfDocument instances, and update the header/footer token syntax. The most judgment-intensive step is the rendering comparison pass — validating output parity for each HTML template to confirm that margin, font, and layout behavior is consistent between the two Chromium implementations.

When you look at the current header and footer templates in your HiQPdf integration, have you identified the page number token syntax — and have you already encountered rendering differences between HiQPdf's Chromium version and the browser that your front-end developers use to design templates?
