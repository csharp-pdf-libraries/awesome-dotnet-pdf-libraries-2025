# Migrating from Sumatra PDF to IronPDF: a .NET production guide

The original version of this article is published at https://ironsoftware.com/csharp/pdf/blog/migrate-from-sumatra/.

Framing

Not every PDF library decision involves a sophisticated commercial component with a broad API surface. Some teams end up using Sumatra PDF in their .NET workflows simply because it was already installed, because it could be invoked from the command line as part of a batch process, or because a developer found it useful for printing PDFs silently on Windows workstations. These integrations tend to be narrow—a shell command invoked from Process.Start(), a scheduled task that prints PDFs to a network printer, a conversion step in a document pipeline—and they are often undocumented outside of the code that calls them.

The motivation for re-evaluating this kind of integration typically comes from one of a few directions: the application is moving to a platform where launching Windows desktop applications (Sumatra is a GUI application, even when invoked silently) is not possible—Linux servers, Docker containers, cloud functions—or the team wants to move from a shell-invocation pattern to a proper library with error propagation and in-process control, or the workflow is expanding and the limitations of a command-line-only interface have become constraints on what can be built.

Understanding what Sumatra PDF is designed for—and what it explicitly is not—is the starting point for scoping this migration accurately. The effort is generally low because the integration surface is typically narrow, but the scope depends entirely on what the existing shell commands are being used to accomplish.

What Sumatra PDF Is Designed To Do

Sumatra PDF is a free, open-source PDF viewer for Windows. It is designed for end-user document viewing with an emphasis on speed, simplicity, and a small installation footprint. Sumatra supports PDF, XPS, DjVu, CBZ, CBR, and EPUB file formats. It does not create PDFs, does not provide a programmable .NET API, and does not modify PDF content. Its extensibility is limited to command-line switches that enable silent printing, printing to specific printers, and file format display—capabilities intended for deployment and workflow automation on Windows workstations.

When .NET applications invoke Sumatra, they do so exclusively through Process.Start() or equivalent shell-execution patterns. Common uses in automated workflows include: silently printing a PDF to a named printer (-print-to), printing all pages to the default printer (-print-to-default), or launching a PDF for display to a user. There is no managed API, no NuGet package for Sumatra, no event model for detecting completion or errors beyond process exit codes, and no facility for PDF manipulation. Sumatra is an active, maintained open-source project; however, its scope is intentionally limited to viewing and printing.

Architectural Differences

IronPDF is a .NET library—not a separate application—that runs in-process alongside the calling application. It does not require Process.Start(), does not depend on a Windows GUI subsystem, and does not have a display component. For the workflows where Sumatra is being used (primarily silent printing and, less commonly, viewing), IronPDF covers the programmatic PDF manipulation side: generating, modifying, and processing PDFs in code. Printing PDFs programmatically from a .NET application without a viewer component is a separate concern; verify IronPDF's printing API in official documentation for the specific printing scenario.

The primary shift in moving from a Sumatra-based workflow to IronPDF is architectural: the shell-execution pattern (Process.Start() + wait for exit) is replaced by a library method call that returns a result or throws a typed exception. Error handling becomes first-class—no more parsing process exit codes or inferring success from the absence of an error output file. The HTML to PDF rendering pipeline provides the document generation capability that Sumatra never had; for teams whose workflow has grown beyond printing to include generating PDFs from application data, this is where IronPDF extends the capability surface.

The PdfDocument object returned by rendering or loading operations implements IDisposable. Because the previous workflow involved no managed objects—just a process exit—disposal patterns are new to the integration. Every PdfDocument should be wrapped in a using block. The rendering options surface provides configuration that has no Sumatra equivalent: paper size, margins, JavaScript, CSS media type, and header/footer layout.

Operation Comparisons

Silent PDF Printing

Sumatra PDF — Silent Print via Process.Start():

The most common automation use of Sumatra PDF in .NET applications is launching it with command-line switches for silent printing. The application starts a Sumatra process and waits for it to exit.

// Sumatra PDF silent print — current pattern
using System.Diagnostics;

public static void PrintPdfSilently(string pdfPath, string printerName)
{
    // Sumatra command-line: -print-to "PrinterName" -silent file.pdf
    var psi = new ProcessStartInfo
    {
        FileName = @"C:\Program Files\SumatraPDF\SumatraPDF.exe",
        // Note: exact argument format
        Arguments = $"-print-to \"{printerName}\" -silent \"{pdfPath}\"",
        CreateNoWindow = true,
        UseShellExecute = false
    };

    using var process = Process.Start(psi)!;
    // Wait with timeout — Sumatra has no structured completion signal
    bool exited = process.WaitForExit(timeoutMilliseconds: 30_000);

    if (!exited)
    {
        process.Kill();
        throw new TimeoutException($"PDF print process timed out for: {pdfPath}");
    }

    // Exit code 0 typically means success — but verify Sumatra's exit code documentation
    if (process.ExitCode != 0)
    {
        throw new InvalidOperationException(
            $"SumatraPDF exited with code {process.ExitCode} for file: {pdfPath}");
    }
}

Technical constraints:

  • Sumatra.exe must be installed at a known path on every machine that runs this code; portable deployments require bundling the executable
  • Windows-only; no equivalent silent-print command-line option on Linux
  • No structured error information beyond exit code; diagnosing printing failures requires log file analysis or manual investigation
  • Process lifecycle management (zombie processes, timeout handling) is entirely the caller's responsibility
  • Print job completion is not guaranteed at process exit; the process may exit before the spooler has finished

IronPDF — Programmatic PDF Printing:

IronPDF provides a managed printing API for sending PDFs to Windows printers without launching a separate process. Verify the exact method names and PrinterSettings configuration in the current IronPDF documentation, as the printing API may have changed across versions.

using IronPdf;

// Load or generate the PDF
using var pdf = PdfDocument.FromFile("document.pdf");

// IronPDF printing API
// in current IronPDF documentation before use
// pdf.Print(); // default printer
// pdf.PrintToNamedPrinter("FinancePrinter"); // named printer
// A PrinterSettings object from System.Drawing.Printing
// can be passed to configure paper tray, duplex, etc.

The shift from Process.Start() to a library call provides structured error propagation via .NET exceptions rather than exit code integers, eliminates the Sumatra installation dependency, and enables the same code to run in any environment where IronPDF's native dependencies are satisfied. For Linux or containerized environments, verify IronPDF's cross-platform printing support in official documentation, as printing to physical printers from headless Linux environments has platform-specific constraints regardless of the library used.

Loading an Existing PDF for Processing

Sumatra PDF — Reading PDFs:

Sumatra PDF can open and display existing PDFs but provides no programmatic access to document content, metadata, page count, or embedded data from .NET code. The only information a .NET application can extract from a Sumatra-based workflow is process exit codes.

Technical constraints:

  • No page count, no metadata, no text content accessible from .NET code
  • No error detail if the PDF is corrupt, password-protected, or unsupported
  • No way to conditionally branch logic based on document properties before printing
  • Display is user-facing only; no headless document inspection capability

IronPDF — Loading and Inspecting an Existing PDF:

using IronPdf;

// Open existing PDF with full document access
using var pdf = PdfDocument.FromFile("incoming-document.pdf");

// Inspect document properties before processing
Console.WriteLine($"Pages: {pdf.PageCount}");
Console.WriteLine($"Title: {pdf.MetaData.Title}");
Console.WriteLine($"Author: {pdf.MetaData.Author}");

// Extract all text — useful for routing, classification, or audit logging
string documentText = pdf.ExtractAllText();

// Conditional processing based on document properties
if (pdf.PageCount > 50)
{
    // Large document — split into chunks before printing
    // Handle accordingly
}

// Check for password protection before attempting operations
// pdf.IsEncrypted

The ability to inspect document properties in-process enables workflows that were not possible with a shell-based Sumatra invocation: routing documents based on page count, validating content before printing, logging document metadata for audit trails. The text and image extraction guide covers the full extraction API for applications that need to process PDF content, not just display or print it.

Generating PDFs from Application Data

Sumatra PDF — PDF Generation:

Sumatra PDF cannot generate PDFs. This capability is entirely outside its scope. Applications that needed both to generate and print PDFs historically used a separate library (or the operating system print-to-PDF driver) for generation and Sumatra for printing, resulting in two separate dependencies.

Technical constraints:

  • Two-tool architecture: generation tool + Sumatra for printing
  • Temporary file management between generation and print steps
  • No in-process coordination between generation result and print command
  • Generation tool must be evaluated and maintained separately

IronPDF — Generate and Process in a Single Library:

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;

// Generate from HTML template
var html = BuildDocumentHtml(documentData); // application-layer template method
using var pdf = renderer.RenderHtmlAsPdf(html);

// Option 1: Save to file
pdf.SaveAs("/output/document.pdf");

// Option 2: Stream to HTTP response (no temp file needed)
var pdfBytes = pdf.BinaryData;
// return File(pdfBytes, "application/pdf", "document.pdf"); // in ASP.NET controller

// Option 3: Print directly
// pdf.Print();

For teams that previously managed a two-tool workflow—one library for generation, Sumatra for printing—consolidating into a single managed library removes the temp-file coordination layer and the process management code. The HTML string to PDF guide covers the full range of input options including HTML strings, file paths, and live URLs.

Batch PDF Processing

Sumatra PDF — Batch Processing:

Batch printing with Sumatra is accomplished by invoking the process once per file, typically in a loop. Error handling must check each process exit code independently.

// Sumatra batch print — current pattern
using System.Diagnostics;
using System.IO;

public static void BatchPrint(IEnumerable<string> pdfPaths, string printerName)
{
    foreach (var pdfPath in pdfPaths)
    {
        var psi = new ProcessStartInfo
        {
            FileName = @"C:\Program Files\SumatraPDF\SumatraPDF.exe",
            Arguments = $"-print-to \"{printerName}\" -silent \"{pdfPath}\"",
            CreateNoWindow = true,
            UseShellExecute = false
        };

        using var process = Process.Start(psi)!;
        process.WaitForExit(30_000);

        if (process.ExitCode != 0)
        {
            // Log the failure and continue — or throw, depending on policy
            Console.Error.WriteLine($"Failed to print: {pdfPath}, exit code: {process.ExitCode}");
        }
    }
}

Technical constraints:

  • Each file spawns a separate process; high file counts create significant process management overhead
  • No parallelism without careful process count limiting
  • One process crash can leave print jobs in an indeterminate state
  • Difficult to surface structured failure information per file

IronPDF — Batch PDF Generation (async parallel):

using IronPdf;
using System.Threading.Tasks;
using System.Collections.Generic;

public static async Task BatchGenerateAsync(
    IEnumerable<(string FileName, string Html)> items,
    string outputDirectory)
{
    var renderer = new ChromePdfRenderer(); // thread-safe; share across tasks
    renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

    var tasks = items.Select(async item =>
    {
        // Each task renders independently; exceptions are per-item
        using var pdf = await renderer.RenderHtmlAsPdfAsync(item.Html);
        var outputPath = Path.Combine(outputDirectory, item.FileName);
        pdf.SaveAs(outputPath);
    });

    // Process all items; collect results
    await Task.WhenAll(tasks);
}

IronPDF's ChromePdfRenderer is thread-safe and can be shared across concurrent rendering tasks. The async rendering API allows batch operations to take advantage of parallel execution without spawning external processes. Verify concurrency limits and memory behavior under high parallelism in official documentation before deploying high-volume batch scenarios.

Breaking Changes & Gotchas

  • No viewer component. Sumatra's primary function—displaying PDFs to end users—has no replacement in IronPDF. If the application launches Sumatra to show documents to users interactively, a separate viewer component (browser-based PDF.js, a commercial viewer control, or the OS default viewer via Process.Start() without the silent flag) must be sourced for that use case.
  • Printing API must be verified. IronPDF's managed printing API exists; verify exact method names, PrinterSettings integration, and cross-platform behavior in the current official documentation before writing production code. Printing from headless Linux environments has system-level constraints that apply regardless of the library.
  • Disposal is new. The Process.Start() pattern manages no managed .NET objects; the using block on the Process object releases OS resources. With IronPDF, PdfDocument objects hold unmanaged Chromium resources and must be disposed via using. Audit every code path that produces a PdfDocument.
  • Chromium binary dependencies. IronPDF ships native Chromium binaries. Environments that run fine for a Process.Start(SumatraPDF.exe) call may not have the system library dependencies required for Chromium on Linux. Test the deployment target explicitly.
  • Installation dependency changes. The Sumatra integration depends on SumatraPDF.exe being installed at a specific path or on the PATH. IronPDF's dependency is the NuGet package, which is restored at build time. This is a simpler dependency model for most teams, but ensure the package restores correctly in CI/CD environments with limited network access.
  • License key required. IronPDF is a commercial library; a valid license key must be configured before use. Sumatra is free and open source. Budget for the license and the provisioning work.
  • Error handling must be updated throughout. Code that checks process.ExitCode != 0 must be replaced with try-catch blocks around IronPDF method calls. The error information is richer but the exception types and properties should be verified against current documentation.

Migration Checklist

  1. Identify all Process.Start() calls that invoke SumatraPDF. Search the codebase for all references to SumatraPDF, sumatra, and the common executable paths. Document the command-line arguments used in each invocation to understand what operations are being performed.
  2. Categorize by operation type. Group each invocation as: print-to-named-printer, print-to-default-printer, open-for-viewing, or other. The print operations are the primary migration target; open-for-viewing uses must be handled by a separate viewer component.
  3. Install the IronPDF NuGet package. Run dotnet add package IronPdf. Verify runtime identifier coverage for all target deployment environments.
  4. Configure the license key. Set the IronPDF license key at application startup. Refer to the license key setup guide for the available configuration approaches.
  5. Verify the printing API for each scenario. Consult current IronPDF documentation for the exact method signatures for printing to named and default printers. Verify behavior for specific printer settings (duplex, paper tray, page range) that the existing Sumatra invocations specify through command-line arguments.
  6. Replace Process.Start() print invocations with library calls. For each identified print invocation, replace the ProcessStartInfo / Process.Start() / WaitForExit() pattern with the equivalent IronPDF managed printing call.
  7. Replace exit code error handling with exception handling. Remove process.ExitCode checks and replace with try-catch blocks around IronPDF method calls. Log or propagate exception details for operational visibility.
  8. Remove the SumatraPDF.exe deployment dependency. Update deployment scripts, application configuration, and infrastructure automation to remove the Sumatra executable from the deployment package or server configuration. Verify that CI/CD pipelines no longer reference it.
  9. Test printing in the target environment. Validate that the IronPDF-based printing calls produce correct output on the target printers in the target deployment environment. Printing behavior can vary between development machines and production servers; test on representative hardware.
  10. Evaluate PDF generation capability. If the workflow currently uses a separate library for PDF generation and Sumatra for printing, assess whether consolidating both operations in IronPDF simplifies the integration. The HTML-to-PDF pipeline may replace the generation library as well.
  11. Update monitoring and alerting. Remove any monitoring or alerting tied to Sumatra process health (process count, exit code tracking, log file monitoring). Replace with .NET exception logging and application-level metrics.
  12. Validate batch scenarios. If the existing integration processes batches of files, test the IronPDF-based replacement under representative batch sizes. Verify disposal behavior, memory profile, and throughput relative to the process-per-file baseline.

Conclusion

When staying on Sumatra PDF (or a similar approach) is technically reasonable

For applications whose only PDF requirement is displaying PDFs to end users on Windows desktops, Sumatra PDF remains a capable, free, and well-maintained viewer. There is no reason to replace a working viewer integration with IronPDF, which does not provide a viewer component. Similarly, if the application's printing workflow is Windows-only, infrequent, and the Process.Start() pattern is working reliably, the migration effort may not produce sufficient return. Sumatra's zero-cost license is also a meaningful factor for teams where commercial library procurement is a friction-heavy process.

Signals that indicate migration is worth the engineering effort

The migration case is clearest when the deployment environment is changing to Linux or containers—where Sumatra does not run—or when the team wants to add PDF generation capability alongside the existing printing workflow and would prefer a single library to two. Teams that have accumulated significant process-management code around Sumatra invocations (timeout handling, retry logic, exit code parsing, temp file cleanup) often find that the total maintenance burden of that code layer exceeds what a direct library call would require. If printing failures are opaque and difficult to diagnose because Sumatra's exit codes provide insufficient information, the structured exception model of a managed library addresses that operational pain directly.

What the cutover typically involves at the code level

This is one of the lower-effort migrations in the PDF library space, because the integration surface is narrow by definition—Process.Start() calls with specific arguments, wrapped in basic error handling. The primary risk is in the printing API specifics: verifying that IronPDF's managed printing produces output equivalent to Sumatra's -print-to behavior for the printers and settings in use. For teams that add PDF generation as part of this migration, the rendering capability is additive rather than a replacement, and can be developed and deployed independently of the printing migration.
