# Migrating from Spire.PDF to IronPDF: API mapping and migration checklist

The original version of this article is published at https://ironsoftware.com/csharp/pdf/blog/migrate-from-spirepdf/.

Framing

Enterprise .NET PDF libraries tend to accumulate integration surface over years: a wrapper class here, a layout helper there, a set of utility methods that abstract away the library's coordinate model or font management quirks. By the time an organization re-evaluates its PDF stack, the question is rarely just about the library's feature set—it is about the full cost of the integration layer that has grown on top of it, and how much of that layer is solving problems introduced by the library itself rather than genuine business requirements.

Spire.PDF is a commercial .NET library that has been present in this market for many years. Teams adopt it for broad PDF capability coverage: creation, editing, form handling, text extraction, digital signatures, and format conversions in a single package. The breadth of the API can be attractive at the start of a project and can create deep integration over time. Migration decisions typically surface when licensing costs shift, when a platform change (Linux containers, .NET 6+) exposes compatibility constraints, or when new rendering requirements—particularly HTML-based templates—are not handled with the fidelity the team needs.

Understanding where Spire.PDF's programming model sits architecturally, and how IronPDF's model differs, is the prerequisite for producing an honest effort estimate. This guide provides that mapping, with code-level detail for the operations most commonly found in mature Spire.PDF integrations.

What Spire.PDF Is Designed To Do

Spire.PDF is a component library from E-iceblue that offers programmatic PDF creation and manipulation without requiring Adobe Acrobat or any other external rendering dependency. Its architecture is based on a document object model: the application constructs a PdfDocument, adds pages, and draws content using a graphics API that accepts fonts, brushes, pens, and coordinate-based positioning—similar in concept to GDI+ or WPF drawing primitives. Spire.PDF also provides APIs for reading and editing existing PDFs, extracting text and images, managing form fields, applying security settings, and signing documents.

The library is distributed as a NuGet package and targets multiple .NET versions; verify the current supported versions and Free vs. Professional tier restrictions in the official Spire.PDF documentation before beginning a migration assessment. The Free edition imposes page limits on generated documents, which is a relevant fact when auditing whether the current integration already requires a paid license. Spire.PDF is not an HTML renderer by default; HTML-to-PDF support exists in the product, but it is not the primary integration model and the fidelity of HTML rendering should be verified against the templates in use.

Architectural Differences

IronPDF's primary integration model is HTML-to-PDF: the application offers HTML markup and CSS, and a bundled Chromium engine renders it to a fixed-layout PDF. This is a fundamentally different starting point from Spire.PDF's coordinate-drawing model. In Spire.PDF, the application specifies where every element goes on the page; in IronPDF, the browser engine handles layout, text wrapping, font measurement, and pagination, and the application's job is to produce correct HTML. Teams with existing HTML templates—Razor views, Scriban layouts, T4 outputs—can feed those templates directly into IronPDF with minimal adaptation.

IronPDF also exposes document manipulation operations—merge, split, stamp, annotate, sign, encrypt—through a PdfDocument API that operates on documents regardless of how they were generated. The rendering options reference covers configuration of paper size, margins, media type, JavaScript behavior, and wait conditions. Disposal semantics follow the standard .NET IDisposable pattern: PdfDocument and ChromePdfRenderer should both be wrapped in using blocks. There is no equivalent to Spire.PDF's PdfDocument.Close() pattern; Dispose() handles all resource release, and the absence of an explicit close call in code is a common early migration mistake to catch in code review.

For document manipulation operations that have a close conceptual match in Spire.PDF—merge, add/remove pages, text extraction, form filling—the IronPDF documentation overview provides the entry point for each capability area.

Operation Comparisons

HTML to PDF

Spire.PDF — HTML to PDF:

Spire.PDF supports HTML-to-PDF conversion, though the rendering fidelity depends on the version and edition in use. A typical pattern involves using a conversion helper class or method that accepts an HTML string or file path and writes a PDF to a stream or file.

// Spire.PDF HTML to PDF — conceptual outline
// Verify exact class and method names in current Spire.PDF documentation
using Spire.Pdf;

var doc = new PdfDocument();
// Spire provides an HTML converter; exact API varies by version
// doc.LoadFromHTML(htmlContent, ...);
// or via a separate PdfConverter class depending on version
doc.SaveToFile("output.pdf");
doc.Close(); // Spire uses explicit Close(); no IDisposable on PdfDocument

Technical constraints:

  • Spire.PDF's HTML renderer is not Chromium-based; CSS3 and JavaScript support should be verified against the templates in use
  • Complex layouts, web fonts, SVG content, and JS-rendered charts may not render as expected
  • The Free edition imposes a page limit that may surface in HTML-rendered output if the input is large
  • Verify thread safety when using the converter in parallel request scenarios

IronPDF — HTML to PDF:

using IronPdf;

// ChromePdfRenderer is thread-safe; can be shared or instantiated per request
var renderer = new ChromePdfRenderer();

renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.EnableJavaScript = true;
// Wait for JS-rendered content before snapshotting
renderer.RenderingOptions.WaitFor.RenderDelay(300);

// Render HTML string — full Chromium CSS3 and JS support
using var pdf = renderer.RenderHtmlAsPdf(@"
    <!DOCTYPE html>
    <html>
    <head>
      <style>
        body { font-family: 'Segoe UI', sans-serif; }
        table { width: 100%; border-collapse: collapse; }
        td, th { border: 1px solid #ddd; padding: 8px; }
      </style>
    </head>
    <body><h1>Report</h1><p>Generated content here.</p></body>
    </html>");

pdf.SaveAs("/output/report.pdf");

The HTML string to PDF guide covers base URL configuration for resolving relative asset paths. Because the Chromium engine handles CSS layout, templates that previously required workarounds in Spire.PDF for complex table layouts or web fonts often render without modification.

Form Field Filling

Spire.PDF — Form Field Filling:

Spire.PDF exposes PDF form fields through its PdfFormWidget collection. Fields are accessed by name or index, and values are set via type-specific widget objects.

// Spire.PDF form field fill — conceptual outline
// Verify exact class names in current Spire.PDF documentation
using Spire.Pdf;
using Spire.Pdf.Widget;

var doc = new PdfDocument();
doc.LoadFromFile("form-template.pdf");

// Access form field collection
var form = doc.Form;
// Iterate or access by name
// ((PdfTextBoxFieldWidget)form.Fields["CustomerName"]).Text = "Acme Corp";

doc.SaveToFile("form-filled.pdf");
doc.Close();

Technical constraints:

  • Field access requires knowing the field name or index; names must match exactly (case sensitivity
  • Checkbox and radio button field types require type-specific widget casts
  • Digital signature fields within forms require separate handling
  • Saving over the source file in some versions may corrupt the form—test with a separate output path

IronPDF — Form Field Filling:

using IronPdf;

// Open existing PDF with form fields
using var pdf = PdfDocument.FromFile("form-template.pdf");

// Access and fill form fields by name
pdf.Form.FindFormField("CustomerName").Value = "Acme Corp";
pdf.Form.FindFormField("InvoiceDate").Value = "2025-01-15";
pdf.Form.FindFormField("Approved").Value = "true"; // checkbox

pdf.SaveAs("form-filled.pdf");

The edit and fill forms guide documents the field type coverage and the approach for reading as well as writing field values—relevant for workflows that need to round-trip form data to and from existing PDF documents.

Digital Signatures

Spire.PDF — Digital Signatures:

Spire.PDF supports applying digital signatures to PDF documents using PFX certificate files. The signature appearance and certification level are configured through a graphics-layer object placed at specific page coordinates.

// Spire.PDF digital signature — conceptual outline
// Verify exact class names in current Spire.PDF documentation
using Spire.Pdf;
using Spire.Pdf.Security;

var doc = new PdfDocument();
doc.LoadFromFile("document.pdf");

// PdfCertificate and PdfSignature classes
// var cert = new PdfCertificate("cert.pfx", "password");
// var sig = new PdfSignature(doc, doc.Pages[0], cert, "SignatureName");
// sig.ContactInfo = "signer@example.com";
// sig.Reason = "Approved";

doc.SaveToFile("signed.pdf");
doc.Close();

Technical constraints:

  • Signature field placement requires explicit coordinate specification
  • Visible signature appearance is drawn at those coordinates; invisible signatures require a zero-dimension rectangle
  • LTV (Long-Term Validation) and timestamp authority support
  • HSM integration is not standard; verify if private keys must not leave hardware

IronPDF — Digital Signatures:

using IronPdf;
using IronPdf.Signing;

using var pdf = PdfDocument.FromFile("document.pdf");

// PdfSignature accepts a PFX file path or X509Certificate2 object
var signature = new PdfSignature("certificate.pfx", "certPassword")
{
    SigningContact = "signer@example.com",
    SigningLocation = "Chicago, IL",
    SigningReason = "Document approved"
};

pdf.Sign(signature);
pdf.SaveAs("document-signed.pdf");

IronPDF supports both file-based PFX and hardware-backed certificates. The digital signatures guide covers visible and invisible signature options, multi-signature workflows, and the HSM signing guide addresses environments where private keys are stored in hardware security modules.

Text Extraction

Spire.PDF — Text Extraction:

Spire.PDF's text extraction is accessed through a PdfTextExtractor or per-page text extraction methods. Results can include coordinates for positioned text, which some workflows use for text-location-aware processing.

// Spire.PDF text extraction — conceptual outline
// Verify exact class names in current Spire.PDF documentation
using Spire.Pdf;
using Spire.Pdf.Exporting;

var doc = new PdfDocument();
doc.LoadFromFile("source.pdf");

var sb = new System.Text.StringBuilder();
for (int i = 0; i < doc.Pages.Count; i++)
{
    // PdfTextExtractOptions controls extraction behavior
    var extractor = new PdfTextExtractor(doc.Pages[i]);
    sb.AppendLine(extractor.ExtractText());
}

string allText = sb.ToString();
doc.Close();

Technical constraints:

  • Text extraction from scanned (image-based) PDFs requires OCR, which is outside Spire.PDF's scope
  • Column-based layouts may produce extraction results with unexpected reading order
  • Text with complex Unicode or right-to-left scripts

IronPDF — Text Extraction:

using IronPdf;

using var pdf = PdfDocument.FromFile("source.pdf");

// Full document extraction
string allText = pdf.ExtractAllText();

// Per-page extraction for workflows that need page context
for (int i = 0; i < pdf.PageCount; i++)
{
    string pageText = pdf.ExtractTextFromPage(i);
    // Process per-page text here
}

The text and image extraction guide covers extraction of embedded images in addition to text—useful for document auditing pipelines that previously used Spire.PDF's image extraction alongside text operations.

Breaking Changes & Gotchas

  • No Close() method. Spire.PDF's PdfDocument uses an explicit Close() call for resource release. IronPDF implements IDisposable; use using blocks throughout. Code ported without this change will leak unmanaged Chromium resources under load.
  • Coordinate drawing model does not exist in IronPDF. Any code that calls drawing methods with explicit X/Y coordinates on a PdfCanvas or XGraphics-equivalent must be rewritten as HTML/CSS. This is the highest-effort part of any Spire.PDF migration and should be scoped as new development, not porting.
  • Page count in Free edition. Spire.PDF Free imposes a page limit. If the current integration relies on the Free edition's page generation without hitting that limit, assess whether the equivalent IronPDF license tier covers the required usage level.
  • HTML rendering engine difference. Spire.PDF's HTML conversion uses its own rendering pipeline; IronPDF uses Chromium. Templates that worked acceptably in Spire may render differently in Chromium—sometimes better (more complete CSS), occasionally with layout shifts for templates that depended on Spire's quirks. Test all templates before retiring the old integration.
  • Platform-specific native binaries. IronPDF ships Chromium binaries per platform. Linux container deployments must include required system libraries (font packages, glibc version). Minimal base images (Alpine, distroless) will fail at runtime without these dependencies.
  • Thread safety model. ChromePdfRenderer is thread-safe for concurrent rendering calls; individual PdfDocument objects are not thread-safe. Audit concurrent code paths that share Spire.PDF document objects—these may need restructuring.
  • Disposal of merged source documents. When merging PDFs with PdfDocument.Merge(), the source PdfDocument objects must be disposed separately. IronPDF does not transfer ownership of source documents to the merge result.
  • Form field type coverage. Verify that IronPDF's form API covers all field types used in existing forms (text boxes, checkboxes, radio buttons, list boxes, signature fields). Coverage differences may require workarounds for specific field types.
  • License key required at application startup. IronPDF requires a valid license key before the first library call. Configure this in appsettings.json, environment variables, or startup code before the application begins processing requests.

Migration Checklist

  1. Audit all Spire.PDF call sites. Enumerate every usage of Spire.PDF APIs: document creation, drawing calls, form operations, signature operations, text extraction, and conversion methods. Categorize as drawing-model code (high effort) or document-manipulation code (low effort).
  2. Identify coordinate-drawing code. All calls to Canvas.DrawString(), DrawRectangle(), DrawImage(), or any other coordinate-based drawing method represent the high-effort portion of the migration. These must be converted to HTML/CSS templates—plan this as new development work.
  3. Audit HTML templates for rendering differences. If the existing integration uses Spire.PDF's HTML-to-PDF path, test every template against IronPDF's Chromium renderer. Document any layout differences and determine whether they represent regressions or improvements.
  4. Install the IronPDF NuGet package. Run dotnet add package IronPdf. Verify that the package resolves the correct native binary for each target runtime identifier (win-x64, linux-x64, etc.).
  5. Configure the license key. Set the IronPDF license key before any library calls. See the license key setup guide for the available configuration mechanisms.
  6. Replace namespace and using directives. Remove Spire.PDF using statements and substitute using IronPdf; and using IronPdf.Signing; as needed. The compiler will surface all remaining Spire.PDF call sites.
  7. Port document manipulation operations first. Merge, split, page management, text extraction, and security settings have the most direct equivalents and lowest migration risk. Complete and test these before tackling rendering.
  8. Rewrite drawing-model code as HTML templates. For each document type currently built with canvas drawing calls, author an HTML/CSS template and validate output. Use RenderHtmlAsPdf() with a base URL configured to resolve relative assets.
  9. Port form operations. Replace Spire.PDF form field access with PdfDocument.Form.FindFormField(). Test all field types present in existing forms (text, checkbox, radio, combo) and validate round-trip behavior.
  10. Port signature workflows. Replace PdfCertificate and Spire's PdfSignature with IronPDF's PdfSignature. Validate signed output against the same verification tooling used to validate Spire-signed documents.
  11. Update disposal patterns throughout. Replace all doc.Close() calls with using blocks or explicit Dispose() calls. Review any code that holds PdfDocument instances in class-level fields or collections.
  12. Run regression testing across the full document set. Validate every document type: visual layout, text content, form field behavior, signature validity, and PDF/A compliance for any documents subject to archival requirements. Use independent validators for compliance-sensitive output.

Conclusion

When staying on Spire.PDF is technically reasonable

Teams with a mature Spire.PDF integration that centers on coordinate-based document construction—fixed layouts, certificates, labels, barcoded documents—may find that the migration cost outweighs the benefit, particularly if the document set is stable and the Chromium-based rendering model is not needed. Spire.PDF's breadth of format support and its established track record in Chinese-market enterprise software mean it often has good support for CJK fonts and specific East Asian document standards; verify this against IronPDF before assuming parity in those scenarios. If the current integration is functioning, the .NET version support is adequate, and the licensing cost is acceptable, the status quo is a defensible position.

Signals that indicate migration is worth the engineering effort

Migration becomes compelling when the team's primary bottleneck is HTML template rendering quality: complex tables, web fonts, SVG-based charts, or JavaScript-rendered data visualizations that Spire.PDF's renderer does not handle reliably. Similarly, when the application is moving to a Linux container deployment and the Spire.PDF integration has untested platform behavior, that uncertainty is a concrete risk. Teams maintaining large volumes of custom drawing code—coordinate calculations, manual table geometry, text measurement loops—often discover that the total maintenance burden of that layer is larger than anticipated, and that a switch to HTML-based layout eliminates it structurally. If the Spire.PDF Free edition's page limits are being hit and the team is evaluating licensing cost anyway, that moment is a natural point to assess alternatives.

What the cutover typically involves at the code level

The migration divides into two workstreams. The first—document manipulation, text extraction, form handling, signatures, and security—is largely mechanical API remapping that experienced developers can execute predictably. The second—replacing coordinate-drawing document construction with HTML templates—is new development work whose scope is proportional to the number of distinct document types and the complexity of their layouts. Teams that separate these workstreams, address the manipulation code first, and treat the template development as a parallel workstream tend to deliver more predictable outcomes than teams that attempt both simultaneously.
