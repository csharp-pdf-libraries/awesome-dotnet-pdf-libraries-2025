Migrating from ABCpdf to IronPDF: a .NET engineering guide

API mapping, gotchas, and a migration checklist

Framing

PDF generation in .NET has historically involved a narrow field of commercial libraries, each with distinct rendering philosophies, licensing models, and API surface areas. Teams periodically re-evaluate their PDF stack for a range of reasons: a library reaching end-of-life, a shift in .NET target framework requirements, changes in rendering fidelity expectations, or a need to consolidate dependencies across a polyglot codebase. These evaluations are rarely triggered by a single failure — they tend to accumulate over time as workarounds pile up or as application requirements drift away from what the chosen library was originally designed to handle.

ABCpdf occupies a defined segment of that landscape. It has been commercially available for many years, accumulates a meaningful install base in enterprise .NET environments, and its v13.x line updated in January 2026 signals continued active maintenance. Teams running ABCpdf-based workloads today are typically doing so on deliberately stable infrastructure, which means that any migration decision carries non-trivial regression risk and deserves careful scoping before any code changes begin.

This guide is structured for .NET engineers who have been asked to evaluate or execute a migration from ABCpdf to IronPDF. It covers architectural differences, an effort-graded operation mapping, concrete code comparisons, a breaking-change inventory, and a checklist-level cutover plan. It is intended to remain useful regardless of whether the migration is ultimately approved.

What ABCpdf Is Designed to Do

ABCpdf is a .NET PDF library produced by WebSupergoo. Its primary capability is HTML-to-PDF rendering backed by a Chromium-based engine, combined with a document manipulation API that covers merge, split, stamping, form-filling, and text extraction. The library targets .NET Framework 2.0 and later, and it installs via NuGet. Version 13.4.1, released January 2026, is the current stable release.

The integration model follows a Doc object pattern: callers instantiate a Doc object, configure rendering properties, add content (HTML string, URL, or file path), and then save or export the resulting PDF. The object holds mutable state across operations, so a single Doc instance can accumulate pages from multiple sources before being serialized. Cleanup is handled through explicit Clear() calls or by disposing the Doc object. The primary use case is not publicly documented, but the library is commonly cited in enterprise reporting, invoice generation, and document automation contexts that require faithful HTML rendering.

Architectural Differences

IronPDF also uses a Chromium-based rendering engine and targets the same core problem space — turning HTML, CSS, and JavaScript into production-quality PDFs within .NET applications. The architectural differences are concentrated in how the two libraries structure their API surface and manage object lifetimes.

IronPDF's main entry point for rendering is the IronPdf.ChromePdfRenderer class. Rather than a stateful document object that accumulates content, the renderer is configured once and then called to produce discrete PdfDocument instances per render operation. Each PdfDocument implements IDisposable and should be wrapped in a using block. This is a meaningful departure from ABCpdf's mutable Doc model: multi-source documents in IronPDF are assembled by rendering each source independently and then merging the resulting PdfDocument objects via the merge and split API, rather than by appending to a single stateful object.

IronPDF installs as a NuGet package and resolves its Chromium dependency automatically. There is no separate binary download step on Windows. On Linux and macOS, additional system dependencies may be required depending on the host environment

Operation Comparisons

HTML String to PDF

ABCpdf — HTML String to PDF

using WebSupergoo.ABCpdf13;

// ABCpdf uses a mutable Doc object pattern
var doc = new Doc();
doc.HtmlOptions.Engine = EngineType.Chrome;
doc.HtmlOptions.Media = MediaType.Screen;

// Add HTML content — AddImageHtml returns an ID used for multi-page rendering
int id = doc.AddImageHtml("<html><body><h1>Report</h1><p>Content here.</p></body></html>");

// Loop to add additional pages if content overflows
while (true)
{
    doc.FrameRect();
    if (!doc.Chainable(id)) break;
    doc.Page = doc.AddPage();
    id = doc.AddImageToChain(id);
}

doc.Save("output.pdf");
doc.Clear(); // Explicit cleanup required

Concrete constraints:

  • The AddImageHtml / AddImageToChain chaining pattern is unique to ABCpdf and has no direct equivalent.
  • doc.HtmlOptions exposes Chromium-specific settings (viewport, media type, JS timeout) that must be re-mapped.
  • doc.Clear() must be called explicitly or the native resources are not freed.
  • Multi-page rendering requires the chain loop; IronPDF handles pagination automatically.

IronPDF — HTML String to PDF

using IronPdf;

// Configure once; renderer is reusable across calls
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;

// RenderHtmlAsPdf returns a PdfDocument — wrap in using for deterministic cleanup
using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Report</h1><p>Content here.</p></body></html>"
);

pdf.SaveAs("output.pdf");
// PdfDocument is disposed at end of using block — no manual Clear() needed

IronPDF paginates the rendered HTML automatically according to the configured paper size and margins. Full rendering option documentation is available in the HTML string to PDF guide and the rendering options reference.

URL to PDF

ABCpdf — URL to PDF

using WebSupergoo.ABCpdf13;

var doc = new Doc();
doc.HtmlOptions.Engine = EngineType.Chrome;
doc.HtmlOptions.AddLinks = true;

// AddImageUrl fetches and renders the remote page
int id = doc.AddImageUrl("https://example.com/report");

while (true)
{
    doc.FrameRect();
    if (!doc.Chainable(id)) break;
    doc.Page = doc.AddPage();
    id = doc.AddImageToChain(id);
}

doc.Save("output.pdf");
doc.Clear();

Concrete constraints:

  • HtmlOptions.AddLinks controls hyperlink retention; verify equivalent in IronPDF.
  • Network timeouts and authentication for protected URLs require separate configuration.
  • The same chain-loop pattern applies as with HTML string rendering.

IronPDF — URL to PDF

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// RenderUrlAsPdf fetches the URL and renders with the Chromium engine
using var pdf = renderer.RenderUrlAsPdf("https://example.com/report");

pdf.SaveAs("output.pdf");

IronPDF's URL rendering supports JavaScript-heavy pages, custom HTTP headers, and login cookies — details in the URL to PDF guide. For pages requiring authentication, request headers and cookies can be set on RenderingOptions before the call.

Merging PDFs

ABCpdf — Merging PDFs

using WebSupergoo.ABCpdf13;

// ABCpdf appends pages from a second document into the first Doc object
var doc = new Doc();
doc.Read("document1.pdf");

var doc2 = new Doc();
doc2.Read("document2.pdf");

// Append all pages from doc2 into doc
for (int i = 1; i <= doc2.PageCount; i++)
{
    doc.PageNumber = doc.AddPage(); // Add new page to target doc
    // Copy page content from source
}

doc.Save("merged.pdf");
doc.Clear();
doc2.Clear();

Concrete constraints:

  • ABCpdf's merge approach is page-by-page append into a mutable Doc; this is error-prone if page indices are miscalculated.
  • Content fidelity (fonts, embedded resources) during copy should be validated on representative samples.
  • Both Doc objects must be explicitly cleared.

IronPDF — Merging PDFs

using IronPdf;

// Load both source documents
using var pdf1 = PdfDocument.FromFile("document1.pdf");
using var pdf2 = PdfDocument.FromFile("document2.pdf");

// Merge returns a new PdfDocument containing all pages in order
using var merged = PdfDocument.Merge(pdf1, pdf2);

merged.SaveAs("merged.pdf");
// All three PdfDocument objects are disposed at end of using blocks

The PdfDocument.Merge() method accepts a params array of PdfDocument objects, so N-way merges are a single call. Splitting by page range is covered in the merge and split documentation.

Adding Headers and Footers

ABCpdf — Headers and Footers

ABCpdf's header and footer model is typically implemented by rendering header/footer content as page elements using stamp or HTML overlay techniques. The exact API varies by version

Concrete constraints:

  • Headers/footers are not a declarative first-class setting; they require post-processing per page.
  • Page number tokens and dynamic content require manual interpolation.
  • Approach is sensitive to page margin configuration.

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();

// HtmlHeaderFooter supports full HTML/CSS, including dynamic tokens
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 20,  // millimeters
    HtmlFragment = "<div style='font-size:9px; color:#555;'>" +
                   "Confidential — Page {page} of {total-pages}</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 15,
    HtmlFragment = "<div style='font-size:8px; text-align:center;'>" +
                   "Generated {date}</div>"
};

using var pdf = renderer.RenderHtmlAsPdf("<html><body><p>Body content.</p></body></html>");
pdf.SaveAs("with-header-footer.pdf");

IronPDF's header/footer system supports {page}, {total-pages}, {date}, and {time} tokens out of the box. Full options and HTML examples are in the headers and footers guide.

Breaking Changes & Gotchas

  • Disposal model: ABCpdf uses doc.Clear() for cleanup; IronPDF uses IDisposable / using blocks on PdfDocument. Porting without adding using statements will cause memory and resource leaks.
  • No chain loop: The AddImageHtml / AddImageToChain / Chainable pattern has no equivalent. All rendering in IronPDF produces a complete multi-page PDF in a single call.
  • Namespace changes: ABCpdf lives under WebSupergoo.ABCpdf13.; IronPDF lives under IronPdf.. A project-wide namespace search-and-replace is required before compilation.
  • Doc is not PdfDocument: The stateful Doc aggregation pattern must be replaced with a render-then-merge workflow. Code that appends to a Doc in a loop must be restructured.
  • Rendering options naming: HtmlOptions properties in ABCpdf do not map 1:1 to RenderingOptions in IronPDF. Each option (viewport width, CSS media type, JS timeout) needs individual verification.
  • Page coordinate systems: ABCpdf uses PDF user-space coordinates (points, origin bottom-left); IronPDF stamping uses a similar system but verify units and origin for any positional stamping code.
  • Thread safety: ChromePdfRenderer instances should not be shared across threads without verification. Creating a renderer per operation or per request is the documented safe pattern.
  • Linux/macOS dependencies: IronPDF's Chromium dependency on non-Windows platforms requires system libraries (libglib, libnss, etc.). Containerized deployments must account for this in the base image
  • License initialization order: IronPdf.License.LicenseKey must be set before the first render call. Late initialization causes a watermark to appear on output. See the license setup guide.
  • PDF/A output: ABCpdf's PDF/A support and IronPDF's SaveAsPdfA() target different conformance levels by default

Migration Checklist

  1. Audit current ABCpdf usage: Enumerate all Doc, HtmlOptions, AddImageHtml, AddImageToChain, and Chainable call sites. Document every option being set on HtmlOptions — these all need mapping.
  2. Install IronPDF via NuGet: dotnet add package IronPdf. Remove the ABCpdf NuGet reference only after the new implementation compiles and passes tests.
  3. Configure the license key: Add IronPdf.License.LicenseKey = "YOUR-KEY"; to application startup — Program.cs, Startup.cs, or equivalent — before any render calls. Refer to the license setup guide.
  4. Update namespaces: Replace using WebSupergoo.ABCpdf13; with using IronPdf; and using IronPdf.Rendering; as needed. Expect compilation errors to guide the remaining work.
  5. Replace rendering calls: Swap doc.AddImageHtml(html) + chain loop → renderer.RenderHtmlAsPdf(html). Swap doc.AddImageUrl(url) → renderer.RenderUrlAsPdf(url). Remove all AddImageToChain, Chainable, and FrameRect calls.
  6. Remap rendering options: For each doc.HtmlOptions. property, find the corresponding RenderingOptions. property. Prioritize: paper size, margins, viewport width, CSS media type, JS timeout, and any custom headers/footers.
  7. Update disposal pattern: Replace doc.Clear() calls with using var pdf = ... blocks. Ensure every PdfDocument and ChromePdfRenderer that is not singleton is wrapped in a using statement.
  8. Replace document assembly code: Any code that loops appending pages to a Doc must be refactored to render each source independently, then call PdfDocument.Merge().
  9. Validate security and form features: Re-test password protection, permission flags, and form-fill operations explicitly — these API surfaces differ and the differences may not surface as compile-time errors.
  10. Run regression tests against known-good PDFs: Compare output visually and structurally (page count, font rendering, image fidelity) against reference PDFs produced by ABCpdf. Automate this comparison if volume justifies it.
  11. Test on all deployment targets: If the application runs on Linux or in Docker, validate the IronPDF Chromium dependency resolution in those environments before promoting to production.
  12. Remove ABCpdf NuGet reference: Once all tests pass, remove the ABCpdf package reference and perform a final build and test pass.

Conclusion

When staying on ABCpdf is technically reasonable

ABCpdf is actively maintained, with a January 2026 release, and teams on stable .NET Framework deployments with working PDF generation workflows have limited technical motivation to migrate. If the existing ABCpdf integration covers the required feature set and the cost of regression risk outweighs the benefit of standardization, staying is a defensible choice. The library's Chromium-based engine means rendering fidelity is broadly comparable for standard HTML/CSS content.

Signals that indicate migration is worth the engineering effort

Migration becomes worth scoping when any of these conditions are present: the application is moving to a .NET version or deployment platform (Linux, container) where ABCpdf support is uncertain or limited; the team needs features that ABCpdf does not expose (HSM signing, PDF/UA, advanced async patterns); or the organization is consolidating its third-party dependency portfolio and prefers a library with a unified API across PDF, OCR, XL, and barcode processing.

What the cutover typically involves at the code level

The most labor-intensive part of the migration is eliminating the Doc mutation pattern and the AddImageHtml/AddImageToChain chain loop. Once those are replaced with ChromePdfRenderer.RenderHtmlAsPdf() and PdfDocument.Merge(), the remaining work — options remapping, disposal pattern updates, namespace changes — is mechanical. A medium-complexity ABCpdf integration typically requires two to five engineering days to port and validate, assuming representative regression test cases exist before the migration begins.
