Migrating from FO.NET to IronPDF: the .NET migration reference

technical depth for .NET teams evaluating a PDF library switch

Framing

XSL-FO (XSL Formatting Objects) was the W3C's answer to document generation in the early 2000s. The pipeline is declarative: an XSLT stylesheet transforms source XML data into an XSL-FO document, and an FO processor renders that document to PDF. For organizations that had already invested in XML-based document pipelines — publishing systems, regulated reporting, documentation toolchains — XSL-FO represented a standards-compliant, vendor-neutral approach to PDF generation. Libraries like FO.NET brought this pipeline into .NET applications without requiring a Java-based FO processor.

That landscape has changed significantly. XSL-FO has not received a W3C specification update since 2006. The browser ecosystem's evolution toward HTML5 and CSS3 made HTML/CSS the dominant language for document layout, and Chromium-based PDF renderers have made that language available server-side with high fidelity. Teams maintaining XSL-FO pipelines today are typically doing so because the pipeline was built when it was the right architectural choice and has not been revisited since — not because XSL-FO offers ongoing advantages over HTML/CSS for the same use cases.

FO.NET specifically is a .NET port of the Apache FOP (Formatting Objects Processor) project. It has been discontinued for a significant period — the last release should be verified, but the library has not received active maintenance in many years and does not support modern .NET targets. This guide is for .NET engineers evaluating or executing a migration from FO.NET (or any XSL-FO-based pipeline) to IronPDF. The migration is classified as Low effort at the code level — the FO.NET API surface is small and the IronPDF replacement calls are straightforward — but Medium-to-High in total effort because the XSL-FO document definitions and XSLT transformations must be redesigned as HTML/CSS templates.

What FO.NET Is Designed to Do

FO.NET is a discontinued .NET library that implements a subset of the XSL-FO 1.0 specification. It is a port of the Apache FOP project and processes XSL-FO XML documents to produce PDF output. The library is not an HTML renderer — it has no Chromium engine, no CSS parser, and no HTML input capability. It reads XSL-FO XML (typically produced by running an XSLT transformation over source XML data) and renders the declared formatting objects — blocks, inlines, tables, lists, page sequences — to PDF according to the XSL-FO specification.

The last release version and any .NET Framework version support should be verified in official documentation or the project repository, but FO.NET is known to have last been actively maintained targeting .NET Framework 2.x or 3.x and does not support .NET Core, .NET 5, or later targets. The install footprint is a managed .NET assembly with no native binary dependencies — which is architecturally consistent with other Apache FOP ports. The primary use case is document generation in systems already structured around XML data and XSLT transformations, where an XSL-FO pipeline was the natural fit at the time of adoption.

Architectural Differences

FO.NET and IronPDF approach document generation from fundamentally different starting points. FO.NET processes XSL-FO XML — a declarative, XML-native document description language — and renders it to PDF through a rules-based formatting engine. IronPDF renders HTML/CSS through an embedded Chromium engine. Both produce PDF output, but the input format, the authoring workflow, and the toolchain are entirely different.

In the FO.NET pipeline, a typical call sequence involves feeding an XSL-FO stream to the processor and receiving a PDF output stream. IronPDF's equivalent is passing an HTML string to ChromePdfRenderer.RenderHtmlAsPdf() and receiving a PdfDocument. The key architectural implication is that migrating from FO.NET does not require migrating an API — it requires replacing the document definition format. The XSL-FO templates and associated XSLT transformations must become HTML/CSS templates with C# data binding. This is where the migration effort concentrates.

IronPDF's PdfDocument implements IDisposable and must be wrapped in a using block. FO.NET produces output by writing to a Stream — disposal follows the stream's lifecycle. The HTML string to PDF guide covers IronPDF's rendering configuration including paper size, margins, headers/footers, and JavaScript execution. License initialization is a one-time startup call via IronPdf.License.LicenseKey; see the license setup guide.

Operation Comparisons

FO-to-PDF Pipeline (Full Pattern)

FO.NET — XSL-FO to PDF

using System.IO;
using System.Xml;
using Fonet; // FO.NET assembly

// FO.NET processes XSL-FO XML and writes PDF to a stream
// The XSL-FO XML is typically the output of an XSLT transformation over source data

// Step 1: Produce the XSL-FO XML from source data via XSLT
// (XSLT transformation using System.Xml.Xsl.XslCompiledTransform — not shown)
// Result: foXml contains valid XSL-FO markup

string foXml = ProduceFoXmlFromData(GetInvoiceData());

// Step 2: Feed XSL-FO to FO.NET processor and write PDF to stream
using var outputStream = new MemoryStream();

// FonetDriver is the FO.NET entry point
// in official documentation as the API is sparse and not widely documented
var driver = FonetDriver.Make();
driver.CloseOnExit = true;

using var foReader = new XmlTextReader(new StringReader(foXml));
driver.Render(foReader, outputStream);

byte[] pdfBytes = outputStream.ToArray();

// ---

static string ProduceFoXmlFromData(object data)
{
    // XSLT transformation produces XSL-FO XML from source data
    // This step (XslCompiledTransform) must be replaced along with FO.NET
    return @"<?xml version='1.0'?>
<fo:root xmlns:fo='http://www.w3.org/1999/XSL/Format'>
  <fo:layout-master-set>
    <fo:simple-page-master master-name='A4'
        page-width='210mm' page-height='297mm'
        margin-top='20mm' margin-bottom='20mm'
        margin-left='15mm' margin-right='15mm'>
      <fo:region-body margin-top='25mm' margin-bottom='20mm'/>
      <fo:region-before extent='20mm'/>
      <fo:region-after extent='15mm'/>
    </fo:simple-page-master>
  </fo:layout-master-set>
  <fo:page-sequence master-reference='A4'>
    <fo:static-content flow-name='xsl-region-before'>
      <fo:block font-size='9pt' text-align='right'>Invoice Header</fo:block>
    </fo:static-content>
    <fo:static-content flow-name='xsl-region-after'>
      <fo:block font-size='8pt' text-align='center'>
        Page <fo:page-number/> of <fo:page-number-citation ref-id='last-page'/>
      </fo:block>
    </fo:static-content>
    <fo:flow flow-name='xsl-region-body'>
      <fo:block font-size='18pt' font-weight='bold'>Invoice #1042</fo:block>
      <fo:block id='last-page'/>
    </fo:flow>
  </fo:page-sequence>
</fo:root>";
}

static object GetInvoiceData() => new { };

Concrete constraints:

  • FO.NET's FonetDriver API is minimal
  • XSL-FO XML must be valid according to the XSL-FO 1.0 specification. FO.NET implements a subset; unsupported formatting objects are silently skipped or may throw.
  • The XSLT transformation step (producing FO XML from data XML) is a separate concern — both the XSLT transformation and the FO processing must be replaced during migration.
  • FO.NET does not support .NET Core or any .NET 5+ target. Applications must remain on .NET Framework to continue using FO.NET.
  • Error handling and logging in FO.NET are minimal — rendering failures may produce empty or truncated PDFs without a meaningful exception.

IronPDF — HTML/CSS Equivalent

using IronPdf;
using IronPdf.Editing;

// The XSL-FO pipeline is replaced by:
// 1. An HTML/CSS template (replaces the XSL-FO document definition)
// 2. C# data binding (replaces the XSLT transformation)
// 3. IronPDF rendering (replaces FO.NET processing)

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 25;    // Matches fo:region-body margin-top (25mm)
renderer.RenderingOptions.MarginBottom = 20;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;

// fo:static-content (header region) → HtmlHeaderFooter
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 12,
    HtmlFragment = "<div style='font-size:9pt; text-align:right; font-family:Arial;'>" +
                   "Invoice Header</div>",
    DrawDividerLine = false
};

// fo:region-after with fo:page-number → HtmlFooter with {page} tokens
renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 10,
    HtmlFragment = "<div style='font-size:8pt; text-align:center; font-family:Arial;'>" +
                   "Page {page} of {total-pages}</div>"
};

// fo:flow (body content) → HTML body, built from data in C#
var invoiceData = GetInvoiceData();
string html = BuildInvoiceHtml(invoiceData);

using var pdf = renderer.RenderHtmlAsPdf(html);
byte[] pdfBytes = pdf.BinaryData;

static object GetInvoiceData() =>
    new { Number = "1042", CustomerName = "Acme Corp", Total = 1599.00m };

static string BuildInvoiceHtml(dynamic data) => $@"
<!DOCTYPE html>
<html>
<head>
<style>
  body {{ font-family: Arial, sans-serif; font-size: 11pt; }}
  h1 {{ font-size: 18pt; font-weight: bold; }}
</style>
</head>
<body>
  <h1>Invoice #{data.Number}</h1>
  <p>Customer: {data.CustomerName}</p>
  <p><strong>Total: {data.Total:C}</strong></p>
</body>
</html>";

The FO.NET pipeline's three distinct steps (source data → XSLT → XSL-FO → FO.NET → PDF) compress to two in IronPDF: data binding to HTML in C#, and HTML rendering to PDF. The HTML string to PDF guide covers rendering configuration. For documents with complex multi-page table layouts, the page breaks guide covers CSS page-break- and break- properties that replace XSL-FO's keep-together and break-before attributes.

Tables with Repeating Headers

FO.NET — Tables with fo:table-header

<!-- XSL-FO table with repeating header across pages -->
<!-- This markup is embedded in the fo:flow of the XSL-FO document -->

<fo:table table-layout="fixed" width="100%">
  <fo:table-column column-width="60mm"/>
  <fo:table-column column-width="40mm"/>
  <fo:table-column column-width="30mm"/>

  <!-- fo:table-header repeats on each page automatically -->
  <fo:table-header>
    <fo:table-row background-color="#eeeeee">
      <fo:table-cell padding="3mm" border="0.5pt solid black">
        <fo:block font-weight="bold">Description</fo:block>
      </fo:table-cell>
      <fo:table-cell padding="3mm" border="0.5pt solid black">
        <fo:block font-weight="bold">Qty</fo:block>
      </fo:table-cell>
      <fo:table-cell padding="3mm" border="0.5pt solid black">
        <fo:block font-weight="bold">Amount</fo:block>
      </fo:table-cell>
    </fo:table-row>
  </fo:table-header>

  <fo:table-body>
    <!-- Data rows generated by XSLT for-each -->
    <fo:table-row>
      <fo:table-cell padding="3mm">
        <fo:block>Consulting Services</fo:block>
      </fo:table-cell>
      <fo:table-cell padding="3mm">
        <fo:block>10</fo:block>
      </fo:table-cell>
      <fo:table-cell padding="3mm">
        <fo:block>$1,500.00</fo:block>
      </fo:table-cell>
    </fo:table-row>
  </fo:table-body>
</fo:table>

Concrete constraints:

  • XSL-FO column widths are explicit and expressed in absolute units (mm, pt, percentage). HTML CSS table-layout: fixed with explicit width on <col> or <td> elements provides equivalent control.
  • fo:table-header repeats automatically on each page. The HTML/CSS equivalent is <thead> with display: table-header-group — supported in Chromium's PDF rendering.
  • XSL-FO keep-together.within-page="always" (preventing row splits across pages) has no direct CSS equivalent; page-break-inside: avoid on <tr> is the closest approximation and behavior varies.

IronPDF — HTML Table with Repeating Header

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;

string html = @"
<!DOCTYPE html>
<html>
<head>
<style>
  body { font-family: Arial, sans-serif; font-size: 11pt; }
  table { width: 100%; table-layout: fixed; border-collapse: collapse; }
  col.desc  { width: 60%; }
  col.qty   { width: 20%; }
  col.amt   { width: 20%; }
  /* thead repeats automatically on each page in Chromium PDF rendering */
  thead tr  { background: #eee; }
  th, td    { padding: 4px 8px; border: 0.5pt solid #aaa; }
  /* Attempt to keep rows intact — behavior varies */
  tbody tr  { page-break-inside: avoid; }
</style>
</head>
<body>
  <table>
    <colgroup>
      <col class='desc'/><col class='qty'/><col class='amt'/>
    </colgroup>
    <thead>
      <tr><th>Description</th><th>Qty</th><th>Amount</th></tr>
    </thead>
    <tbody>
      <tr><td>Consulting Services</td><td>10</td><td>$1,500.00</td></tr>
      <!-- Additional rows populated from C# data binding -->
    </tbody>
  </table>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("invoice-table.pdf");

Chromium's PDF rendering repeats <thead> automatically on each page. Column widths are expressed as CSS percentages or absolute lengths. The page breaks guide covers page-break-inside, break-before, and CSS fragmentation behavior in detail.

Page Sequence Configuration

FO.NET — Page Layout via fo:simple-page-master

<!-- XSL-FO page layout definition — replaces CSS @page and RenderingOptions -->
<fo:layout-master-set>
  <fo:simple-page-master
      master-name="letter-landscape"
      page-width="279mm"
      page-height="216mm"
      margin-top="15mm"
      margin-bottom="15mm"
      margin-left="20mm"
      margin-right="20mm">
    <fo:region-body margin-top="20mm" margin-bottom="15mm"/>
    <fo:region-before extent="20mm"/>
    <fo:region-after extent="15mm"/>
  </fo:simple-page-master>
</fo:layout-master-set>

<fo:page-sequence master-reference="letter-landscape">
  <!-- page content here -->
</fo:page-sequence>

Concrete constraints:

  • fo:simple-page-master encodes page dimensions, orientation, and all margin regions in the document definition itself. In IronPDF, this configuration moves entirely to RenderingOptions properties set on the renderer before the render call.
  • Multiple page masters (e.g., first page differently sized, subsequent pages normal) require fo:page-sequence-master in XSL-FO. The HTML/CSS equivalent uses CSS @page :first and @page selectors; verify Chromium's support for these in PrintCssMediaType mode.
  • FO.NET's page dimensions accept any XSL-FO unit (mm, cm, in, pt, px). IronPDF's RenderingOptions.PaperSize accepts enum values or a PdfCustomPaperSize for non-standard sizes.

IronPDF — Page Layout via RenderingOptions

using IronPdf;

// All fo:simple-page-master configuration maps to RenderingOptions properties
var renderer = new ChromePdfRenderer();

// Letter landscape: 279mm × 216mm
renderer.RenderingOptions.CustomPaperSizeInMillimeters(279, 216);
renderer.RenderingOptions.PaperOrientation = IronPdf.Rendering.PdfPaperOrientation.Landscape;

// Margins (outer page margins — equivalent to fo:simple-page-master margin-*)
renderer.RenderingOptions.MarginTop = 15;    // mm
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.MarginLeft = 20;
renderer.RenderingOptions.MarginRight = 20;

// Region-before (header) and region-after (footer) → HtmlHeaderFooter
renderer.RenderingOptions.HtmlHeader = new IronPdf.Editing.HtmlHeaderFooter
{
    Height = 15,  // Equivalent to region-before extent
    HtmlFragment = "<div style='font-size:9pt;'>Header content</div>"
};

using var pdf = renderer.RenderHtmlAsPdf("<html><body><p>Body</p></body></html>");
pdf.SaveAs("letter-landscape.pdf");

Custom paper sizes are documented in the custom paper size guide. Landscape orientation, page rotation, and per-page orientation changes are covered in the page orientation guide.

Multi-Column Layouts

FO.NET — Multi-Column via fo:region-body

<!-- XSL-FO multi-column layout using column-count on fo:region-body -->
<fo:simple-page-master master-name="two-column"
    page-width="210mm" page-height="297mm"
    margin="15mm">
  <fo:region-body column-count="2" column-gap="8mm"/>
</fo:simple-page-master>

Concrete constraints:

  • XSL-FO multi-column layout is declared at the page master level — the entire body flows in two (or more) columns. HTML/CSS uses column-count on the body or a container element.
  • XSL-FO column balance (balancing the last page's columns) uses fox:column-fill="balance" (Apache extension). CSS uses column-fill: balance.
  • Column spans in XSL-FO require span="all" on a block. HTML/CSS uses column-span: all.

IronPDF — HTML/CSS Multi-Column Layout

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;
renderer.RenderingOptions.MarginBottom = 15;

// CSS column-count replaces fo:region-body column-count
string html = @"
<!DOCTYPE html>
<html>
<head>
<style>
  body { font-family: Arial, sans-serif; font-size: 10pt; }
  h1   { column-span: all; font-size: 16pt; margin-bottom: 12px; }
  .content {
    column-count: 2;
    column-gap: 8mm;
    column-fill: balance;
  }
</style>
</head>
<body>
  <h1>Newsletter Title</h1>
  <div class='content'>
    <p>First column content flows here automatically...</p>
    <p>Text continues and wraps to the second column...</p>
  </div>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("two-column.pdf");

CSS multi-column layout is fully supported by Chromium. Behavior for column-span, column-fill, and column breaks should be validated against the specific Chromium version embedded in IronPDF, as edge cases in fragmentation behavior vary.

Breaking Changes & Gotchas

  • Input format is entirely different: FO.NET accepts XSL-FO XML. IronPDF accepts HTML. There is no automated conversion between XSL-FO and HTML — every document template must be redesigned. This is the dominant effort item, even though the FO.NET API call itself is trivial to replace.
  • XSLT transformation step is also replaced: A typical FO.NET pipeline runs XSLT over source XML to produce XSL-FO XML, then feeds that to FO.NET. Both the XSLT transformation and the FO.NET call must be replaced. The new approach uses C# templating (Razor, Scriban, Fluid, or string interpolation) to produce HTML from a C# data model.
  • FO.NET does not support modern .NET: FO.NET targets .NET Framework 2.x/3.x. It cannot be used in .NET Core, .NET 5, or later projects. This is typically the forcing function for migration rather than an optional improvement.
  • PdfDocument is IDisposable: FO.NET writes to a Stream you provide; no disposal is required on FO.NET's part. IronPDF's RenderHtmlAsPdf() returns a PdfDocument that implements IDisposable. Every PdfDocument must be in a using block.
  • Error handling changes: FO.NET's error behavior on malformed XSL-FO is inconsistent — it may produce truncated output without a meaningful exception. IronPDF throws typed .NET exceptions for rendering failures and provides structured logging via IronPdf.Logging. Update error handling and alerting accordingly.
  • Namespace replacement: Remove all FO.NET using directives. Replace with using IronPdf;. Compile errors guide the remaining work.
  • License key required: IronPdf.License.LicenseKey must be set at startup before any render call. FO.NET is open-source with no license key requirement. Omitting IronPDF's key produces watermarked output.
  • Column widths change from absolute to relative: XSL-FO tables express column widths in absolute units (mm, pt). HTML tables work best with relative widths (percentages) when targeting variable-width containers — but in PDF rendering, the page width is fixed, so absolute units (px or mm via CSS) are also viable.
  • Multi-page table header behavior: XSL-FO's fo:table-header repeats on every page by specification. HTML's <thead> behavior in PDF rendering depends on the rendering engine. In Chromium (IronPDF), <thead> repeats correctly — but test with large tables to confirm.

Migration Checklist

  1. Inventory all XSL-FO templates and XSLT stylesheets: List every FO template in use, the XSLT transformations that produce them, the source XML data structure, and the document output characteristics (paper size, columns, header/footer content). This inventory is the template redesign scope.
  2. Select a C# HTML templating approach: Choose how HTML will be generated from data — Razor (compile-time validated, IntelliSense), Scriban (runtime-editable, Liquid-like), Fluid (Liquid, open source), or C# string interpolation (simple templates). This replaces the XSLT transformation step.
  3. Redesign FO templates as HTML/CSS: For each FO template, produce an HTML/CSS equivalent. Use fo:simple-page-master dimensions to set RenderingOptions values. Convert fo:table to HTML <table>. Convert fo:static-content regions to HtmlHeaderFooter. Validate each template in Chrome before testing with IronPDF.
  4. Install IronPDF via NuGet: dotnet add package IronPdf. Do not remove FO.NET references until replacement code is functional.
  5. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs or application startup. See the license setup guide.
  6. Replace FonetDriver.Render() calls: For each FO.NET conversion call, replace with renderer.RenderHtmlAsPdf(html). Wrap PdfDocument in a using block. Access bytes via pdf.BinaryData or save via pdf.SaveAs().
  7. Map fo:simple-page-master to RenderingOptions: Paper width/height → PaperSize or CustomPaperSizeInMillimeters(). Margins → Margin* properties. Orientation → PaperOrientation.
  8. Map fo:static-content regions to HtmlHeaderFooter: Replace fo:region-before content with RenderingOptions.HtmlHeader. Replace fo:region-after content with RenderingOptions.HtmlFooter. Update page number syntax: fo:page-number → {page}, fo:page-number-citation → {total-pages}.
  9. Test multi-page table behavior: Render documents with large tables and verify that <thead> repeats on each page and that page-break-inside: avoid on rows behaves as expected.
  10. Remove FO.NET and XSLT dependencies: Once all templates are ported and output is validated, remove FO.NET assembly references and XSLT transformation code. Remove any XML document model code that existed solely to produce FO XML.

Conclusion

When staying on FO.NET is technically reasonable

FO.NET is not technically reasonable for any new development. The library is discontinued, does not support modern .NET targets, and has no active maintenance path. The only case for staying on FO.NET is a .NET Framework application with stable, rarely-changed PDF output requirements that is not planning a runtime migration and where the cost of template redesign outweighs the risk of operating on unsupported tooling. This is a shrinking set of applications.

Signals that indicate migration is worth the engineering effort

The clearest signal is a .NET runtime migration — any application moving from .NET Framework to .NET Core, .NET 5, 6, 7, 8, or later cannot use FO.NET at all. Beyond that, migration is worth prioritizing when XSL-FO templates are difficult to maintain by the current team (few developers retain active XSL-FO expertise), when template changes require an XSLT specialist rather than a web developer, or when new document requirements involve modern CSS features that XSL-FO cannot express.

What the cutover typically involves at the code level

The FO.NET code change itself is trivial — a handful of FonetDriver calls replaced with ChromePdfRenderer calls. The real work is in two other places: template redesign (FO XML → HTML/CSS, proportional to the number and complexity of document types) and data pipeline replacement (XSLT → C# templating, proportional to transformation complexity). For organizations with a small number of document types and simple data bindings, the migration is achievable in one to two focused sprints. For organizations with many document types and complex XSLT stylesheets, a phased migration — one document type at a time — is typically the lower-risk path.
