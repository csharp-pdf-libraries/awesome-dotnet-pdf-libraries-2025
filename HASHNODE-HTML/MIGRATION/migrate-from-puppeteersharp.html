Migrating from PuppeteerSharp to IronPDF: the .NET migration reference

technical depth for .NET teams evaluating a PDF library switch

Framing

PDF generation sits at the intersection of layout fidelity, operational reliability, and platform compatibility — three concerns that commonly pull in different directions. .NET teams typically reach for a dedicated library early in a project, then revisit that choice when the solution no longer fits: scaling costs rise, deployment constraints tighten, or a new requirement (digital signatures, PDF/A compliance, server-side rendering without a display server) falls outside the original library's scope.

PuppeteerSharp occupies a specific niche in this landscape. It exposes the Chrome DevTools Protocol from managed .NET code, giving developers programmatic control over a real Chromium browser instance. For teams that already use headless Chrome for end-to-end testing, extending that infrastructure to produce PDFs is a natural step. The library is widely known, actively maintained, and carries a low learning curve for anyone familiar with the JavaScript Puppeteer API.

Re-evaluation tends to happen when the operational model becomes a constraint rather than an enabler. Shipping and managing a full Chromium binary, handling browser lifecycle across concurrent requests, or meeting compliance requirements that go beyond raw PDF output are common inflection points. This guide maps the technical landscape for teams at that crossroads — what PuppeteerSharp actually does, where IronPDF approaches the same problem differently, and what a migration involves at the code level.

What PuppeteerSharp Is Designed to Do

PuppeteerSharp is a .NET port of the Node.js Puppeteer library, maintained on GitHub by a community of contributors. Its architecture centers on a managed wrapper around the Chrome DevTools Protocol (CDP). At runtime, it downloads or locates a Chromium binary, launches a browser process, and communicates with it over a WebSocket connection. Pages are navigated, JavaScript is executed, and rendered output — including PDF — is produced by delegating to the browser's built-in Page.printToPDF DevTools command.

The library's primary design goal is browser automation, not PDF generation specifically. PDF output is one of several available operations alongside screenshots, network interception, and DOM manipulation. Because the PDF is produced by Chromium's native print pipeline, rendering fidelity for HTML/CSS content tends to be high — the same engine that renders the web produces the document. The cost of that fidelity is the requirement to host a live Chromium process, with the attendant memory footprint, startup latency, and process-management concerns. On Linux, PuppeteerSharp typically requires additional system libraries (font packages, sandbox configuration) that are not needed in a typical ASP.NET deployment. Verify current system dependency requirements in the official PuppeteerSharp documentation.

Architectural Differences

IronPDF also uses a Chromium-based rendering engine internally, but it packages that engine as a self-contained native binary distributed alongside the NuGet package rather than as a separately managed browser process. The rendering surface is not exposed as a general-purpose browser automation API; instead, the library surface is domain-specific — HTML to PDF, PDF manipulation, security operations, and document operations are first-class concerns with dedicated APIs.

From a disposal and lifecycle perspective, IronPDF's PdfDocument is a standard IDisposable type that wraps an in-memory or on-disk PDF. There is no concept of a "browser page" or "browser context" to manage. The HTML to PDF rendering pipeline accepts an HTML string, a file path, or a URL and returns a PdfDocument synchronously or asynchronously — the caller does not manage the underlying Chromium lifecycle directly.

Thread safety and concurrency models differ meaningfully. PuppeteerSharp encourages creating separate browser contexts or pages per concurrent request, which requires teams to build and manage a browser pool. IronPDF exposes async rendering and is designed for parallel use within standard ASP.NET request pipelines without explicit pooling. Both libraries ultimately depend on Chromium under the hood, so the performance characteristics under high concurrency are influenced by similar factors; the difference is primarily in where the concurrency management responsibility lies.

Operation Comparisons

HTML String to PDF

PuppeteerSharp — HTML String to PDF

A typical PuppeteerSharp workflow for rendering an HTML string to PDF involves launching a browser, opening a page, setting the page content, and invoking the print-to-PDF command.

using PuppeteerSharp;
using System.IO;
using System.Threading.Tasks;

// Download Chromium if not already present
await new BrowserFetcher().DownloadAsync();

await using var browser = await Puppeteer.LaunchAsync(new LaunchOptions
{
    Headless = true
});

await using var page = await browser.NewPageAsync();

// Set HTML content directly
await page.SetContentAsync("<h1>Hello World</h1><p>Generated via PuppeteerSharp.</p>");

// Render to PDF bytes
var pdfBytes = await page.PdfDataAsync(new PdfOptions
{
    Format = PaperFormat.A4,
    PrintBackground = true
});

await File.WriteAllBytesAsync("output.pdf", pdfBytes);

Key constraints:

  • Chromium binary must be present or downloaded at startup; adds latency on first run.
  • IBrowser and IPage are both IAsyncDisposable; omitting disposal causes browser process leaks.
  • SetContentAsync does not guarantee external resources (fonts, images) have loaded; additional waiting logic may be needed.
  • Thread safety requires separate pages or browser contexts per concurrent request.

IronPDF — HTML String to PDF

IronPDF renders an HTML string without managing a browser lifecycle. The renderer is stateless and can be called directly from any async context. See the HTML string to PDF how-to guide for rendering options including viewport, media type, and JavaScript execution.

using IronPdf;
using System;
using System.IO;

// One-time license configuration (typically in startup/DI)
License.LicenseKey = Environment.GetEnvironmentVariable("IRONPDF_LICENSE_KEY");

var renderer = new ChromePdfRenderer();

// Configure render options as needed
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.PrintBackgroundColors = true;

// Render — returns an IDisposable PdfDocument
using var pdf = renderer.RenderHtmlAsPdf("<h1>Hello World</h1><p>Generated via IronPDF.</p>");

// Save or stream the result
pdf.SaveAs("output.pdf");

// Or export to byte array for HTTP responses
byte[] pdfBytes = pdf.BinaryData;

Disposal is straightforward: PdfDocument implements IDisposable and should be wrapped in a using statement. There is no browser or page object to track.

URL to PDF

PuppeteerSharp — URL to PDF

using PuppeteerSharp;
using System.IO;
using System.Threading.Tasks;

await new BrowserFetcher().DownloadAsync();

await using var browser = await Puppeteer.LaunchAsync(new LaunchOptions { Headless = true });
await using var page = await browser.NewPageAsync();

// Navigate and wait for network activity to settle
await page.GoToAsync(
    "https://example.com",
    waitUntil: new[] { WaitUntilNavigation.Networkidle2 }
);

var pdfBytes = await page.PdfDataAsync(new PdfOptions
{
    Format = PaperFormat.A4,
    PrintBackground = true
});

await File.WriteAllBytesAsync("page.pdf", pdfBytes);

Key constraints:

  • Networkidle2 heuristic may be insufficient for SPAs with deferred data loading.
  • Browser process must remain alive for the full navigation duration.
  • Proxy configuration and authentication headers require additional CDP setup.

IronPDF — URL to PDF

IronPDF's URL rendering handles network navigation internally. The URL to PDF guide covers options for custom request headers, authentication, and JavaScript wait conditions.

using IronPdf;
using System;

License.LicenseKey = Environment.GetEnvironmentVariable("IRONPDF_LICENSE_KEY");

var renderer = new ChromePdfRenderer();

// Optionally configure HTTP headers or login cookies
// renderer.RenderingOptions.CustomCookies = ...;

using var pdf = renderer.RenderUrlAsPdf("https://example.com");

pdf.SaveAs("page.pdf");

Headers and Footers

PuppeteerSharp — Headers and Footers

PuppeteerSharp's PdfOptions supports DisplayHeaderFooter along with HeaderTemplate and FooterTemplate, which accept HTML strings using a limited subset of CSS and special tokens such as <span class='pageNumber'/>.

using PuppeteerSharp;
using System.IO;
using System.Threading.Tasks;

await using var browser = await Puppeteer.LaunchAsync(new LaunchOptions { Headless = true });
await using var page = await browser.NewPageAsync();
await page.SetContentAsync("<p>Document body content.</p>");

var pdfBytes = await page.PdfDataAsync(new PdfOptions
{
    Format = PaperFormat.A4,
    DisplayHeaderFooter = true,
    // CSS in these templates is constrained — not all properties work
    HeaderTemplate = "<div style='font-size:10px;width:100%;text-align:center;'>My Header</div>",
    FooterTemplate = "<div style='font-size:10px;width:100%;text-align:right;'><span class='pageNumber'></span></div>",
    MarginOptions = new MarginOptions { Top = "40px", Bottom = "40px" }
});

await File.WriteAllBytesAsync("output.pdf", pdfBytes);

Key constraints:

  • CSS support in header/footer templates is limited by Chromium's print CSS context.
  • External resources (web fonts, images) in header templates often fail to load.
  • Page count tokens are available but styling flexibility is constrained.

IronPDF — Headers and Footers

IronPDF provides a dedicated header/footer API with both simple text-based and full HTML-based options. The headers and footers how-to covers text headers, HTML headers, page numbering tokens, and margin control.

using IronPdf;
using System;

License.LicenseKey = Environment.GetEnvironmentVariable("IRONPDF_LICENSE_KEY");

var renderer = new ChromePdfRenderer();

// Full HTML header — rendered as a separate HTML fragment
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    HtmlFragment = "<div style='text-align:right; font-size:10px;'>Page {page} of {total-pages}</div>",
    Height = 20 // millimetres
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    HtmlFragment = "<div style='text-align:center; font-size:9px; color:#888;'>Confidential</div>",
    Height = 15
};

using var pdf = renderer.RenderHtmlAsPdf("<p>Document body content.</p>");
pdf.SaveAs("output.pdf");

Concurrent Rendering

PuppeteerSharp — Concurrent Rendering

PuppeteerSharp does not provide a built-in request pool. Teams typically implement a SemaphoreSlim-gated browser context pool or use a third-party pooling library.

using PuppeteerSharp;
using System;
using System.Collections.Concurrent;
using System.IO;
using System.Threading;
using System.Threading.Tasks;

// Minimal browser pool — production implementations are considerably more complex
public class BrowserPool : IAsyncDisposable
{
    private readonly ConcurrentBag<IBrowser> _pool = new();
    private readonly SemaphoreSlim _semaphore;
    private readonly int _maxSize;

    public BrowserPool(int maxSize)
    {
        _maxSize = maxSize;
        _semaphore = new SemaphoreSlim(maxSize, maxSize);
    }

    public async Task<byte[]> RenderAsync(string html)
    {
        await _semaphore.WaitAsync();
        try
        {
            // Acquire or create browser — simplified; production needs lifecycle management
            await using var browser = await Puppeteer.LaunchAsync(new LaunchOptions { Headless = true });
            await using var page = await browser.NewPageAsync();
            await page.SetContentAsync(html);
            return await page.PdfDataAsync(new PdfOptions { Format = PaperFormat.A4 });
        }
        finally
        {
            _semaphore.Release();
        }
    }

    public async ValueTask DisposeAsync()
    {
        foreach (var browser in _pool)
            await browser.DisposeAsync();
    }
}

Key constraints:

  • Browser process startup cost is paid once per pool slot, but memory footprint per slot is significant.
  • Crashes in one Chromium process can silently affect pool state.
  • Pool sizing requires empirical tuning for a given workload.

IronPDF — Concurrent Rendering

IronPDF's renderer is stateless and ChromePdfRenderer instances can be created per-request or shared. Async rendering is supported natively. The parallel processing examples demonstrate patterns for high-throughput scenarios.

using IronPdf;
using System;
using System.Collections.Generic;
using System.Linq;
using System.Threading.Tasks;

License.LicenseKey = Environment.GetEnvironmentVariable("IRONPDF_LICENSE_KEY");

var htmlDocuments = new List<string>
{
    "<p>Document 1</p>",
    "<p>Document 2</p>",
    "<p>Document 3</p>"
};

// Renderers are lightweight — creating one per task is acceptable
var tasks = htmlDocuments.Select(async html =>
{
    var renderer = new ChromePdfRenderer();
    using var pdf = await renderer.RenderHtmlAsPdfAsync(html);
    return pdf.BinaryData;
});

var results = await Task.WhenAll(tasks);
// results is byte[][] — one entry per document

Breaking Changes & Gotchas

  • Disposal model: PuppeteerSharp uses IAsyncDisposable throughout (IBrowser, IPage). IronPDF's PdfDocument is IDisposable (synchronous). Code that uses await using patterns must be updated to using blocks.
  • No general browser automation: IronPDF is not a browser automation library. Network request interception, DOM querying, screenshot capture of arbitrary pages, and programmatic form interaction via CDP are out of scope. Workflows that depend on these capabilities cannot be directly ported.
  • JavaScript execution model: PuppeteerSharp allows arbitrary JS execution before and after page load via EvaluateExpressionAsync. IronPDF executes JavaScript as part of the render pipeline using a configuration-based wait approach. There is no equivalent for injecting JS at arbitrary render phases.
  • Chromium binary management: PuppeteerSharp requires explicit Chromium download or path configuration. IronPDF bundles its Chromium dependency with the NuGet package. Teams that tightly control binary content in their container images may need to audit the package contents.
  • Linux deployment: PuppeteerSharp on Linux requires manual installation of Chromium sandbox dependencies and often --no-sandbox flags which have security implications. IronPDF manages these concerns internally; verify current Linux deployment requirements in the IronPDF docs.
  • Namespace changes: All types move from the PuppeteerSharp namespace to IronPdf and IronPdf.Rendering. Global using directives and namespace aliases will need updating.
  • Async vs. sync API: PuppeteerSharp's API is uniformly async. IronPDF exposes both synchronous and async methods. Teams operating in async-first codebases should use the *Async variants consistently.
  • Thread safety: PuppeteerSharp IPage instances are not thread-safe and must not be shared across concurrent calls. IronPDF ChromePdfRenderer is designed for concurrent use when instances are not shared across threads; verify latest guidance.
  • Header/footer CSS: If your PuppeteerSharp implementation relies on the constrained CSS available in Chromium's print header/footer context, behavior under IronPDF's HTML header/footer renderer may differ. Test rendered output explicitly.

Migration Checklist

  1. Swap NuGet packages: Remove PuppeteerSharp from your .csproj. Add IronPdf via NuGet. Run dotnet restore.
  2. Configure the license key: Add your IronPDF license key using License.LicenseKey = "..." at application startup, or via environment variable. See the license key setup guide for recommended patterns including appsettings.json and environment variable injection.
  3. Update namespace declarations: Replace using PuppeteerSharp; and related namespaces with using IronPdf; and using IronPdf.Rendering; as needed.
  4. Remove Chromium download logic: Delete any calls to new BrowserFetcher().DownloadAsync(). IronPDF's Chromium dependency ships with the package.
  5. Replace browser and page lifecycle: Remove Puppeteer.LaunchAsync(), browser.NewPageAsync(), and all await using browser/page dispose patterns. Replace with new ChromePdfRenderer() and a using var pdf = renderer.Render*() pattern.
  6. Remap render calls: Replace page.SetContentAsync() + page.PdfDataAsync() with renderer.RenderHtmlAsPdf(). Replace page.GoToAsync() + page.PdfDataAsync() with renderer.RenderUrlAsPdf().
  7. Migrate rendering options: Map PdfOptions properties to RenderingOptions equivalents. Pay attention to unit differences (margins: px vs mm) and enum name changes (PaperFormat.A4 → PdfPaperSize.A4).
  8. Update headers and footers: Replace PdfOptions.HeaderTemplate / FooterTemplate with RenderingOptions.HtmlHeader / HtmlFooter using the HtmlHeaderFooter object.
  9. Revise concurrency patterns: Remove browser pool implementations. Replace with per-request ChromePdfRenderer instances or shared stateless renderer patterns as appropriate.
  10. Update cookie and auth handling: Replace page.SetCookieAsync() with RenderingOptions.CustomCookies configuration.
  11. Validate output fidelity: Render a representative sample of documents from both libraries and compare output. Pay attention to fonts, CSS grid layouts, JavaScript-dependent content, and page break behavior.
  12. Test deployment environment: Verify IronPDF runs correctly in your Docker/Linux environment. On containerized Linux, confirm that the native Chromium binary bundled with IronPDF has the required system libraries available.

Conclusion

When staying on PuppeteerSharp is technically reasonable

PuppeteerSharp remains a sound choice when PDF generation is incidental to a broader browser automation workflow. Teams that already operate Chromium infrastructure for end-to-end testing or web scraping, and need PDF output as an occasional side effect, benefit from consolidating on a single tool. The library also suits scenarios where CDP-level control — network request interception, DOM inspection, custom JS injection at arbitrary render phases — is a functional requirement rather than a nice-to-have.

Signals that indicate migration is worth the engineering effort

Migration effort is likely justified when PDF operations have grown into a first-class concern: document generation volume is high, compliance requirements (PDF/A, PDF/UA, digital signatures) have emerged, or the operational complexity of managing a Chromium browser pool has become a maintenance burden. Teams discovering that PuppeteerSharp's header/footer template model is insufficient for their layout needs, or that browser process crashes are affecting PDF generation reliability, are seeing signals that a purpose-built PDF library may reduce operational overhead.

What the cutover typically involves at the code level

The mechanical migration is straightforward: remove the browser/page lifecycle management layer and replace the rendering call pattern. The most significant code changes are in concurrency infrastructure (removing browser pools), in disposal patterns (async to sync disposable), and in rendering options mapping. Headers, footers, and authentication handling require deliberate remapping rather than a line-by-line translation, but the operations themselves have direct equivalents. Teams that have tight control over their Chromium binary (for security scanning or image size reasons) will need to evaluate IronPDF's bundling model explicitly.
