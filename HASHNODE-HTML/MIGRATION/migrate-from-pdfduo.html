Migrating from PDF Duo .Net to IronPDF: API mapping and migration checklist

before-and-after code, risk assessment, and a migration checklist

Framing

A distinct migration category, discontinued pdf libraries are. Unlike active libraries where the migration is driven by feature gaps or licensing changes, a discontinued library's migration is driven by time — every new .NET runtime version, every dependency upgrade, and every security patch cycle increases the probability that the library stops working or stops compiling. Teams running discontinued PDF libraries on .NET Framework face additional pressure when the application's own .NET migration is planned, since a discontinued library with no .NET Core or .NET 5+ support becomes a blocking dependency in the modernization path.

PDF Duo .Net is listed as discontinued. The last release, original technical approach, and specific API surface are not extensively documented in widely available sources, and engineers evaluating a migration from this library should verify current product status and available documentation directly. What is clear is the pattern: a library that is no longer receiving updates will not be patched for security issues, will not be updated for new .NET runtime compatibility, and will not gain support for modern web standards if it is an HTML rendering library. These are accumulating risks that compound with each year of continued use.

This guide covers the migration from PDF Duo .Net to IronPDF. Because PDF Duo .Net's API surface is not extensively documented in widely available technical sources, the competitor-side code examples use conservative conceptual patterns with explicit "refer to the official documentation" annotations wherever specific API details cannot be confirmed. The migration effort is marked as - because the scope depends on which PDF Duo .Net capabilities are in active use and how closely they map to IronPDF equivalents.

What PDF Duo .Net Is Designed to Do

PDF Duo .Net is a discontinued .NET library for HTML-to-PDF conversion. The specific technical approach, rendering engine, .NET version support, install footprint, and primary use case should be verified in whatever documentation or source code is available — official documentation may be sparse or unavailable given the library's discontinued status. Based on the general category of .NET HTML-to-PDF conversion libraries from the era it was developed, it most likely provided an HtmlToPdf-style class that accepted HTML strings or URLs and returned PDF bytes or saved PDF files.

Discontinued status means the library is no longer receiving feature updates, security patches, or compatibility updates for new .NET runtimes. Teams still running PDF Duo .Net are maintaining a dependency against a fixed API surface, with no upstream path for addressing issues. The .NET support range — whether the library supports .NET Core, .NET 5+, or only .NET Framework — should be verified in the available project artifacts or source code.

Architectural Differences

Assuming PDF Duo .Net is an HTML-to-PDF conversion library, the conceptual operation it performs is the same as IronPDF's ChromePdfRenderer.RenderHtmlAsPdf() — HTML content in, PDF bytes out. The architectural differences that matter for migration are the rendering engine (IronPDF uses Chromium, which determines CSS support level), the disposal model (IronPDF returns PdfDocument which is IDisposable), the manipulation surface (IronPDF exposes merge, sign, forms, encryption, and compliance on the same PdfDocument), and the runtime compatibility (IronPDF supports .NET Standard 2.0 and above, covering both .NET Framework 4.6.2+ and modern .NET runtimes).

IronPDF's two central types are ChromePdfRenderer (for rendering HTML to PDF) and PdfDocument (for the resulting document and all manipulation). The HTML string to PDF guide covers IronPDF's full rendering configuration. The rendering options reference covers all available rendering parameters. License initialization is a one-time startup call via IronPdf.License.LicenseKey; see the license setup guide.

The shift to IronPDF adds Chromium-quality CSS rendering, genuine async support, a comprehensive post-render manipulation API, and an active maintenance and security update path — the last item being the most operationally important given PDF Duo .Net's discontinued status.

IronPDF — HTML String to PDF

using IronPdf;

// ChromePdfRenderer — singleton, reuse across calls
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.PaperOrientation = IronPdf.Rendering.PdfPaperOrientation.Portrait;
renderer.RenderingOptions.MarginTop = 15;    // millimeters
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #1042</h1>
  <p>Customer: Acme Corp</p>
  <p>Total: $1,599.00</p>
</body>
</html>";

// PdfDocument is IDisposable — always wrap in a using block
using var pdf = renderer.RenderHtmlAsPdf(html);

byte[] pdfBytes = pdf.BinaryData;
pdf.SaveAs("invoice.pdf");

The return type change from byte[] to PdfDocument is the most structural difference at each call site — every render result must be in a using block. Full rendering configuration is in the HTML string to PDF guide. Once PDF Duo .Net's exact API is confirmed from the existing codebase, the mapping to RenderingOptions properties is typically mechanical.

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 15;

// IronPDF page number tokens: {page} and {total-pages}
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 12,  // mm
    HtmlFragment = "<div style='font-size:9px; font-family:Arial; " +
                   "text-align:right; padding:0 12px;'>Document Title</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 10,
    HtmlFragment = "<div style='font-size:8px; font-family:Arial; " +
                   "text-align:center;'>Page {page} of {total-pages}</div>"
};

using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><p>Document body.</p></body></html>");
pdf.SaveAs("with-headers.pdf");

Regardless of PDF Duo .Net's token syntax, IronPDF uses {page} and {total-pages}. Identify all header/footer HTML or text in the existing codebase and update the tokens during migration. The headers and footers guide covers all configuration options.

Breaking Changes & Gotchas

  • API surface must be confirmed from codebase: PDF Duo .Net's documentation is sparse. The migration plan must be built from the existing application code — every call site must be identified and the API pattern confirmed before mapping to IronPDF equivalents.
  • PdfDocument is IDisposable: If PDF Duo .Net returned byte[] directly (common for libraries of this era), there was no disposal concern. IronPDF returns PdfDocument, which implements IDisposable. Every render call must produce a PdfDocument in a using block.
  • Page number token syntax: Identify the token syntax used in PDF Duo .Net's header/footer configuration and update all occurrences to IronPDF's {page} and {total-pages}.
  • Namespace change: Remove all using PDFDuo.* (or equivalent) directives. Replace with using IronPdf;. Compile errors identify every affected file.
  • License key required: PDF Duo .Net's licensing model (if any) is replaced by IronPdf.License.LicenseKey set at startup.
  • .NET runtime unblocked: If PDF Duo .Net did not support .NET Core or modern .NET, removing it unblocks the application's own runtime migration.
  • CSS rendering differences: If PDF Duo .Net used a non-Chromium rendering engine, HTML templates may render differently in IronPDF's Chromium. Review templates visually after migration — particularly any that were built to work around older rendering engine limitations.
  • Task.Run() wrappers: If the current codebase wraps synchronous PDF Duo .Net calls in Task.Run(), replace with RenderHtmlAsPdfAsync() to eliminate thread pool pressure.
  • Security vulnerability risk: A discontinued library may have unpatched security vulnerabilities. Migrating removes this risk surface.

Migration Checklist

  1. Confirm API from existing codebase: Before any planning, walk through every PDF Duo .Net call site in the application and document: class name, method signatures, property names, return types, and any token or flag usage. This is the ground truth for migration scope.
  2. Verify .NET support range: Confirm whether PDF Duo .Net supports the target .NET runtime. If it only supports .NET Framework, document this as a hard blocker for the application's .NET modernization.
  3. Install IronPDF via NuGet: dotnet add package IronPdf. Retain PDF Duo .Net reference until replacement code compiles.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs. See the license setup guide.
  5. Update namespaces: Remove PDF Duo .Net using directives. Replace with using IronPdf;.
  6. Register ChromePdfRenderer in DI: Add builder.Services.AddSingleton<ChromePdfRenderer>() with RenderingOptions configured once.
  7. Replace HTML-to-PDF conversion calls: Map each confirmed call pattern to renderer.RenderHtmlAsPdf(html). Wrap PdfDocument in using. Access bytes via pdf.BinaryData.
  8. Port header/footer configuration: Replace PDF Duo .Net's header/footer API. Update page number tokens to {page} and {total-pages}.
  9. Replace Task.Run() wrappers: If present, replace await Task.Run(() => converter.Convert(...)) with await renderer.RenderHtmlAsPdfAsync(...).
  10. Visual rendering comparison: Render every document type with IronPDF and compare against the PDF Duo .Net output. Note any CSS rendering differences — Chromium may render templates differently if PDF Duo .Net used a different engine.
  11. Remove PDF Duo .Net NuGet reference: Once all replacements compile and tests pass, remove the package reference.
  12. Proceed with .NET runtime migration if applicable: Once PDF Duo .Net is removed, the .NET Framework blocker is resolved and the application's own runtime migration can proceed.

Conclusion

When staying on PDF Duo .Net is technically reasonable

PDF Duo .Net's discontinued status makes continued use difficult to justify for any application with ongoing development or maintenance requirements. The only scenario where continued use might be accepted is a fully frozen application — no new features, no dependency updates, no runtime changes — where the cost of migration exceeds the risk of running on a discontinued library. This scenario is rare in practice; most applications receive at minimum security patches and dependency updates.

Signals that indicate migration is worth the engineering effort

The discontinued status alone is typically sufficient justification. Additional signals: security vulnerability exposure from an unpatched library; a planned .NET Framework to .NET 5+ migration that is blocked by PDF Duo .Net's runtime support; template maintenance issues from a rendering engine that doesn't match modern browser behavior; or the need for post-render PDF operations that require a second library alongside PDF Duo .Net.

What the cutover typically involves at the code level

The migration scope is determined by the codebase audit in step 1 — confirming the API surface from existing call sites. Once that is complete, the replacement is a mechanical remapping: converter class → ChromePdfRenderer, conversion method → renderer.RenderHtmlAsPdf(), byte return → PdfDocument with using, header/footer tokens updated. For applications that move to .NET 5+ simultaneously, the PDF migration is a prerequisite that should be completed and validated before the runtime migration begins.
