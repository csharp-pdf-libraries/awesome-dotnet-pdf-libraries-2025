Migrating from jsreport to IronPDF: from install to production

architecture differences, breaking changes, and migration patterns

Framing

Reporting platforms that run as separate services represent a distinct architectural pattern from in-process PDF libraries. jsreport is a full reporting platform — a Node.js server that manages templates, data engines, scheduling, report caching, and PDF rendering as a unified service. Teams that adopt jsreport are typically not just looking for a PDF rendering library; they are building a reporting infrastructure where templates are managed centrally, reports can be triggered by schedule or API call, and the rendering stack is isolated from the application server. This is a meaningful architectural investment, and migration away from it is proportionally significant.

Re-evaluation of a reporting platform dependency happens for several reasons. The Node.js service adds operational overhead — another process to deploy, monitor, and maintain alongside the .NET application. For applications where PDF generation is the sole use of jsreport (no scheduling, no central template management, no browser-based template designer), the platform's full capability set represents unused complexity. Organizations moving to simplified infrastructure, reducing their microservice surface area, or running in environments where Node.js processes are operationally inconvenient begin evaluating whether an in-process .NET library covers the actual usage profile.

This guide covers the migration from jsreport to IronPDF for .NET engineers evaluating or executing the switch. The product status and last release of jsreport should be verified in official documentation, as jsreport is actively developed and versions change frequently. The migration is classified as High effort because the scope is not just an API swap — it involves replacing a server-side reporting platform's template engine, HTTP API integration, template management workflow, and optionally its scheduling and caching features. Teams using jsreport only as an HTML-to-PDF renderer (with no scheduling, template storage, or advanced data engine) will find the migration closer to Medium.

What jsreport Is Designed to Do

jsreport is an open-source reporting platform built on Node.js. It runs as a standalone server (or as a Docker container) and exposes an HTTP API for rendering reports. The platform's rendering pipeline uses Chromium (headless Chrome) for HTML-to-PDF output, making it a Chromium-based renderer accessed over the network rather than in-process. jsreport supports multiple JavaScript templating engines for HTML generation — Handlebars, jsrender, and EJS among others — meaning templates are HTML files with embedded templating syntax that jsreport evaluates with submitted data before rendering.

Beyond rendering, jsreport provides a template management system (templates stored in a backing store), a web-based template designer and preview environment, report scheduling, authentication and authorization for report access, report output caching, and extensions for various output formats. The .NET integration is through jsreport's .NET SDK (NuGet packages: jsreport.Client, jsreport.Local for embedded local execution), which wraps the HTTP API or runs jsreport in-process via a Node.js embedded runtime. The exact .NET support range and current SDK versions should be verified in official documentation. jsreport is primarily used in enterprise reporting scenarios where centralized template management, scheduled delivery, and separation of reporting concerns from application code are valued.

Architectural Differences

jsreport and IronPDF represent two different answers to the same question: how should a .NET application produce PDF reports? jsreport answers with a full reporting platform running Node.js, either in a separate Docker container or embedded in-process via its local runner. IronPDF answers with an in-process .NET library embedding Chromium directly. Both use Chromium for HTML-to-PDF rendering — the output fidelity is comparable — but the integration model, template engine, data binding approach, and operational concerns are entirely different.

IronPDF's two primary types are ChromePdfRenderer (for rendering HTML to PDF) and PdfDocument (for the resulting document and all manipulation). Both implement IDisposable. Templates in IronPDF are any HTML string — the application is responsible for generating that HTML string from a C# data model using any templating engine (Razor, Scriban, Fluid, or string interpolation). The HTML string to PDF guide covers full rendering configuration. License initialization is a one-time startup call; see the license setup guide.

The shift from jsreport to IronPDF consolidates the Node.js rendering server into the .NET application, eliminates the HTTP round-trip to jsreport's API, and moves template management into the application's existing source control and deployment workflow. It removes jsreport's built-in template designer, scheduling, caching, and authentication features — these must be handled by the application or dropped if not needed.

Operation Comparisons

Rendering via jsreport HTTP API

jsreport — HTML to PDF via HTTP API

using jsreport.Client;
using jsreport.Types;
using System.IO;

// jsreport.Client wraps the jsreport HTTP API
// The jsreport server must be running and accessible
var rs = new ReportingService("http://localhost:5488");
// Or with authentication: new ReportingService("http://...", "user", "password")

// Report object configures the rendering request
var report = await rs.RenderAsync(new RenderRequest
{
    Template = new Template
    {
        // Content is the HTML with Handlebars/jsrender template syntax
        Content = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #{{invoiceNumber}}</h1>
  <p>Customer: {{customerName}}</p>
  <p>Total: {{total}}</p>
</body>
</html>",
        Engine = Engine.Handlebars,
        Recipe = Recipe.ChromePdf,
        ChromePdf = new ChromePdfOptions
        {
            Format = "A4",
            MarginTop = "10mm",
            MarginBottom = "10mm",
            MarginLeft = "10mm",
            MarginRight = "10mm",
            DisplayHeaderFooter = true,
            HeaderTemplate = "<div style='font-size:9px;'>Header</div>",
            FooterTemplate = "<div style='font-size:8px; text-align:center;'>" +
                             "Page <span class='pageNumber'></span> of " +
                             "<span class='totalPages'></span></div>"
        }
    },
    Data = new
    {
        invoiceNumber = "1042",
        customerName = "Acme Corp",
        total = "$1,599.00"
    }
});

// Save the response stream to file
using var outputStream = File.OpenWrite("invoice.pdf");
await report.Content.CopyToAsync(outputStream);

Concrete constraints:

  • jsreport server must be running and reachable before any render call. Under network partition or server restart, renders fail with HTTP errors.
  • Handlebars syntax ({{variable}}, {{#each items}}, {{#if condition}}) must be ported to the C# templating engine chosen for IronPDF (Razor: @Model.Variable, Scriban: {{variable}}).
  • Engine.Handlebars and Recipe.ChromePdf are jsreport SDK enum values — remove these when migrating.
  • jsreport's ChromePdfOptions.HeaderTemplate / FooterTemplate use Chromium's span class injection (<span class='pageNumber'>) — update to IronPDF's {page} / {total-pages} tokens.
  • report.Content is a stream from the HTTP response that must be read and closed after use.
  • jsreport SDK types (RenderRequest, Template, ChromePdfOptions) are all removed in the migration.

IronPDF — In-Process HTML to PDF

using IronPdf;
using IronPdf.Editing;

// ChromePdfRenderer is reusable — register as singleton in DI
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 10;     // mm
renderer.RenderingOptions.MarginBottom = 10;
renderer.RenderingOptions.MarginLeft = 10;
renderer.RenderingOptions.MarginRight = 10;

// jsreport's HtmlHeaderFooter tokens differ from IronPDF
// <span class='pageNumber'> → {page}
// <span class='totalPages'> → {total-pages}
renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 10,
    HtmlFragment = "<div style='font-size:8px; text-align:center;'>" +
                   "Page {page} of {total-pages}</div>"
};

// jsreport's Handlebars template is replaced by C# HTML generation
// Data model drives the HTML — no separate templating engine required
var data = new { InvoiceNumber = "1042", CustomerName = "Acme Corp", Total = "$1,599.00" };

string html = $@"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #{data.InvoiceNumber}</h1>
  <p>Customer: {data.CustomerName}</p>
  <p>Total: {data.Total}</p>
</body>
</html>";

// PdfDocument is IDisposable — always use a using block
using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("invoice.pdf");

The Handlebars template syntax in jsreport ({{variable}}) is replaced by C# string interpolation or a C# templating engine. The HTML string to PDF guide covers rendering configuration. The header/footer token update (<span class='pageNumber'> → {page}) affects every jsreport template that includes page numbers.

Template Engine Port (Handlebars → C# Templating)

jsreport — Handlebars Template

<!-- jsreport Handlebars template: invoice-template.html -->
<!-- This file lives in jsreport's template store -->
<!DOCTYPE html>
<html>
<head>
<style>
  body { font-family: Arial; }
  table { width: 100%; border-collapse: collapse; }
  th, td { border: 1px solid #ccc; padding: 6px; }
</style>
</head>
<body>
  <h1>Invoice #{{invoiceNumber}}</h1>
  <p>Bill to: {{customer.name}}, {{customer.address}}</p>
  <table>
    <thead>
      <tr><th>Item</th><th>Qty</th><th>Price</th></tr>
    </thead>
    <tbody>
      {{#each lineItems}}
      <tr>
        <td>{{description}}</td>
        <td>{{quantity}}</td>
        <td>${{price}}</td>
      </tr>
      {{/each}}
    </tbody>
  </table>
  <p><strong>Total: ${{total}}</strong></p>
</body>
</html>

Concrete constraints:

  • {{variable}} → Razor: @Model.Variable, Scriban: {{variable}}, string interpolation: {data.Variable}.
  • {{#each items}} ... {{/each}} → Razor: @foreach (var item in Model.Items) { ... }, Scriban: {{ for item in items }} ... {{ end }}.
  • {{#if condition}} ... {{/if}} → Razor: @if (Model.Condition) { ... }.
  • jsreport Handlebars helpers (custom functions registered in jsreport) must be replicated as C# methods or Razor helper functions.
  • The template file no longer lives in jsreport's template store — it becomes a .cshtml Razor view, a .scriban file, or an embedded resource in the .NET project.

IronPDF — Razor Template Equivalent

// Using Razor for HTML generation — strongly typed, IntelliSense, compile-time validation
// Example: using RazorLight or ASP.NET Core RazorTemplateEngine

// InvoiceViewModel.cs
public class InvoiceViewModel
{
    public string InvoiceNumber { get; set; }
    public CustomerInfo Customer { get; set; }
    public List<LineItem> LineItems { get; set; }
    public decimal Total { get; set; }
}

public class CustomerInfo
{
    public string Name { get; set; }
    public string Address { get; set; }
}

public class LineItem
{
    public string Description { get; set; }
    public int Quantity { get; set; }
    public decimal Price { get; set; }
}

// invoice.cshtml (Razor template — replaces jsreport Handlebars template)
/*
@model InvoiceViewModel
<!DOCTYPE html>
<html>
<head><style>body { font-family: Arial; } table { width:100%; border-collapse:collapse; } th,td { border:1px solid #ccc; padding:6px; }</style></head>
<body>
  <h1>Invoice #@Model.InvoiceNumber</h1>
  <p>Bill to: @Model.Customer.Name, @Model.Customer.Address</p>
  <table>
    <thead><tr><th>Item</th><th>Qty</th><th>Price</th></tr></thead>
    <tbody>
    @foreach (var item in Model.LineItems)
    {
      <tr><td>@item.Description</td><td>@item.Quantity</td><td>$@item.Price</td></tr>
    }
    </tbody>
  </table>
  <p><strong>Total: $@Model.Total</strong></p>
</body>
</html>
*/

// Rendering the Razor template to HTML, then to PDF
using IronPdf;
// (RazorLight or similar used to render the Razor template to a string)
// var html = await razorEngine.CompileRenderAsync("invoice", viewModel);

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Assuming 'html' is the rendered HTML string from RazorLight or similar
string html = "<!-- rendered from Razor template -->";

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("invoice.pdf");

For complex templates with loops and conditionals, Razor (via RazorLight, RazorTemplateEngine, or ASP.NET Core's view engine) is the most natural replacement for jsreport's Handlebars engine. The HTML string to PDF guide covers passing the rendered HTML string to RenderHtmlAsPdf(). Simpler templates with minimal logic can be migrated to C# string interpolation or Scriban without a full Razor setup.

jsreport.Local (Embedded Node.js Runner)

jsreport — jsreport.Local Embedded Runner

using jsreport.Local;
using jsreport.Types;
using jsreport.Binary;

// jsreport.Local runs a Node.js jsreport process in-process
// jsreport.Binary provides the jsreport Node.js binary as a NuGet package
var rs = new LocalReporting()
    .UseBinary(JsReportBinary.GetBinary())
    .KillRunningJsReportProcesses()
    .AsUtility()  // No web server — utility mode for embedding
    .Create();

await rs.StartAsync();

var report = await rs.RenderAsync(new RenderRequest
{
    Template = new Template
    {
        Content = "<html><body><h1>{{title}}</h1></body></html>",
        Engine = Engine.Handlebars,
        Recipe = Recipe.ChromePdf
    },
    Data = new { title = "Embedded Report" }
});

using var outputStream = File.OpenWrite("report.pdf");
await report.Content.CopyToAsync(outputStream);

await rs.KillAsync();

Concrete constraints:

  • jsreport.Local downloads and manages a Node.js process alongside the .NET application. The Node.js binary (jsreport.Binary NuGet package) adds a significant install footprint to the NuGet package.
  • rs.StartAsync() / rs.KillAsync() lifecycle calls are required — the Node.js process must be started before render calls and cleanly shut down.
  • The Node.js process runs as a child process of the .NET application — process management, crash recovery, and port conflicts are operational concerns.
  • AsUtility() disables jsreport's web server. The full server mode adds further startup complexity.
  • This entire pattern is eliminated when migrating to IronPDF.

IronPDF — Equivalent In-Process

using IronPdf;

// IronPdf.License.LicenseKey = "YOUR-KEY"; // Set once at startup

// No StartAsync(), no KillAsync(), no Node.js process
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// C# string interpolation replaces Handlebars data binding
string title = "Embedded Report";
string html = $"<html><body><h1>{title}</h1></body></html>";

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("report.pdf");
// No KillAsync() — Chromium lifecycle managed by IronPDF

The entire LocalReporting → StartAsync() → RenderAsync() → KillAsync() lifecycle is replaced by direct ChromePdfRenderer usage. No Node.js binary, no child process management, no port allocation. The jsreport.Binary, jsreport.Local, and jsreport.Client NuGet packages are all removed. The async rendering guide covers concurrent rendering patterns for high-throughput scenarios.

Batch Report Generation

jsreport — Batch via HTTP API

using jsreport.Client;
using jsreport.Types;

var rs = new ReportingService("http://localhost:5488");

var invoiceIds = new[] { 1001, 1002, 1003, 1004, 1005 };
var pdfPaths = new List<string>();

// jsreport does not have a native batch API
// Teams typically parallelize HTTP requests
var tasks = invoiceIds.Select(async id =>
{
    var report = await rs.RenderAsync(new RenderRequest
    {
        Template = new Template
        {
            Content = $"<html><body><h1>Invoice #{id}</h1></body></html>",
            Engine = Engine.None,
            Recipe = Recipe.ChromePdf
        }
    });

    string path = $"invoice-{id}.pdf";
    using var file = File.OpenWrite(path);
    await report.Content.CopyToAsync(file);
    return path;
});

string[] results = await Task.WhenAll(tasks);
// Each task is a separate HTTP round-trip to the jsreport server
// Concurrency is limited by jsreport server's worker pool

Concrete constraints:

  • Concurrent jsreport renders are limited by the jsreport server's configured worker pool size — exceeding this queues requests server-side.
  • Each render is a separate HTTP connection — overhead accumulates at scale.
  • jsreport server health, network availability, and worker pool exhaustion are failure modes for every batch item.
  • Template reuse across batch items requires template storage in jsreport's template store.

IronPDF — Batch via Async/Parallel

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

var invoiceIds = new[] { 1001, 1002, 1003, 1004, 1005 };

// Parallel in-process rendering — no HTTP overhead
var tasks = invoiceIds.Select(async id =>
{
    string html = $"<html><body><h1>Invoice #{id}</h1></body></html>";

    // RenderHtmlAsPdfAsync is genuinely async and thread-safe for concurrent calls
    using var pdf = await renderer.RenderHtmlAsPdfAsync(html);
    string path = $"invoice-{id}.pdf";
    pdf.SaveAs(path);
    return path;
});

string[] results = await Task.WhenAll(tasks);

In-process rendering eliminates HTTP overhead per batch item. The renderer is thread-safe and reused across all concurrent calls. For very high batch volumes, the parallel processing examples show concurrency patterns and thread pool configuration.

Breaking Changes & Gotchas

  • Node.js process eliminated: jsreport.Local runs a Node.js child process. Removing jsreport removes this process, its startup latency, port allocation, and crash recovery requirements. The jsreport.Binary, jsreport.Local, and jsreport.Client NuGet packages are all removed.
  • Template engine is replaced: jsreport's Handlebars/jsrender templates cannot be used directly in IronPDF. Every template must be ported to a C# templating engine. The migration effort is proportional to the number of templates and the complexity of their Handlebars helpers and conditionals.
  • Page number token syntax: jsreport's header/footer templates use Chromium's span class convention (<span class='pageNumber'>, <span class='totalPages'>). IronPDF uses {page} and {total-pages}. Every header/footer template must be updated.
  • Template management replaced: jsreport's built-in template store (filesystem or MongoDB-backed) has no IronPDF equivalent. Templates become source files in the .NET project or are loaded from a configured path.
  • Scheduling not in IronPDF: jsreport's report scheduling, subscriptions, and delayed execution must be replaced with a .NET scheduler (Hangfire, Quartz.NET, Azure Functions Timer triggers, or similar).
  • Report caching not in IronPDF: jsreport's output caching must be replaced with an application-level cache (IMemoryCache, Redis, or similar).
  • Web-based template designer removed: jsreport's browser-based template editor and live preview have no IronPDF equivalent.
  • Authentication layer removed: jsreport's user authentication and API key model for report access control is replaced by the application's own authentication layer.
  • PdfDocument is IDisposable: jsreport returns a stream; IronPDF returns PdfDocument. Every render result must be in a using block.
  • Namespace change: Remove all jsreport.* using directives. Replace with using IronPdf;.
  • License key required: Set IronPdf.License.LicenseKey at startup before any render call.

Migration Checklist

  1. Inventory all jsreport templates: List every Handlebars/jsrender template in use, its data model, helpers, conditionals, and header/footer configuration. This is the template port scope.
  2. Select a C# HTML templating engine: Choose how HTML will be generated from data — Razor (compile-time validation, IntelliSense, natural fit for ASP.NET Core), Scriban (runtime-editable, fast), Fluid (Liquid syntax, open source), or string interpolation (simple templates). Port each jsreport template to the chosen engine.
  3. Identify platform features in active use: Confirm which jsreport features are actively used — template store, scheduling, caching, authentication, report history. Each active platform feature requires a replacement strategy independent of the PDF rendering swap.
  4. Install IronPDF via NuGet: dotnet add package IronPdf. Retain jsreport SDK packages until replacement code is functional.
  5. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs. See the license setup guide.
  6. Remove jsreport SDK packages: jsreport.Client, jsreport.Local, jsreport.Binary, and any jsreport extension packages are all removed once replacement code is functional.
  7. Update namespaces: Remove all using jsreport.*; directives. Replace with using IronPdf;.
  8. Register ChromePdfRenderer in DI: Add builder.Services.AddSingleton<ChromePdfRenderer>() with RenderingOptions configured once. Inject it into services and controllers.
  9. Replace RenderAsync() call sites: For each jsreport RenderAsync() call, replace with renderer.RenderHtmlAsPdf(html) or await renderer.RenderHtmlAsPdfAsync(html). Wrap PdfDocument in a using block. Replace stream-copy pattern with pdf.SaveAs() or pdf.BinaryData.
  10. Update header/footer token syntax: In all ported header/footer HTML fragments, replace <span class='pageNumber'> with {page} and <span class='totalPages'> with {total-pages}.
  11. Replace scheduling and caching: Implement report scheduling with Hangfire, Quartz.NET, or a cloud scheduler. Implement output caching with IMemoryCache or a distributed cache.
  12. Remove jsreport infrastructure: Remove jsreport Docker container definitions from docker-compose.yml. Remove jsreport service URL from application configuration. Remove any jsreport process monitoring from infrastructure tooling.

Conclusion

When staying on jsreport is technically reasonable

jsreport is technically reasonable when its platform features — template store, web-based designer, report scheduling, report history, authentication — are in active use and provide organizational value that justifies the Node.js operational overhead. Teams with a dedicated reporting workflow, a central template library maintained by non-developers through jsreport's designer UI, and scheduled report delivery have infrastructure that would require significant work to replace piece by piece. The platform's feature breadth is its primary argument for retention.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when jsreport is being used only as an HTML-to-PDF renderer — when the template store, scheduling, designer, and authentication features are unused or underused; when Node.js process management is adding operational burden disproportionate to value; when network round-trips to the jsreport server are contributing measurably to response latency; when the reporting workload is growing and jsreport's worker pool is becoming a concurrency bottleneck; or when post-render PDF operations (merge, sign, PDF/A) require an additional library alongside jsreport.

What the cutover typically involves at the code level

The rendering API swap is mechanical — RenderAsync() calls become RenderHtmlAsPdfAsync() calls, stream copy becomes pdf.SaveAs(). The template engine port is proportional to template count and Handlebars complexity. The platform feature replacements (scheduler, cache, auth) are architectural decisions that extend beyond a simple library swap. A phased approach — replace rendering first while keeping jsreport infrastructure running, then migrate platform features one by one — reduces the risk of a large-bang migration and allows rendering output parity to be validated in production before decommissioning the jsreport server.

In your current jsreport deployment, how much of the platform's feature set — template store, scheduling, designer, authentication — is actively in use versus how much is dormant infrastructure inherited from the original reporting requirements?
