Migrating from PDFSharp to IronPDF: the engineering breakdown

effort estimation, API mapping, and production considerations

# Migrating from PDFSharp to IronPDF: the engineering breakdown

The original version of this article is published at https://ironsoftware.com/csharp/pdf/blog/migrate-from-pdfsharp/.

Framing

.NET teams that adopted PDFSharp often did so because it was freely available, carried no commercial licensing cost, and provided a low-level API that gave direct control over the PDF object model. In greenfield applications, that level of control is sometimes the right tradeoff. Over time, however, the same low-level surface area that makes PDFSharp flexible also means that generating a document with headers, footers, tables, and dynamic content requires a substantial amount of application-level layout code. Teams maintaining such codebases frequently find themselves having built an informal layout engine on top of PDFSharp rather than simply using a PDF library.

Library evaluations tend to restart when one of several conditions arises: the hand-rolled layout engine becomes a maintenance burden as requirements grow, a .NET version migration surfaces compatibility gaps, or a new developer joining the team encounters the custom abstraction layer and struggles to extend it. The question at that point is whether the underlying library still serves the team's needs or whether a different integration model would reduce the total code ownership burden.

PDFSharp and IronPDF represent different positions on the control-vs-abstraction spectrum. Understanding both positions is the prerequisite for making a migration effort estimate that a senior engineering team will trust.

What PDFSharp Is Designed To Do

PDFSharp is a low-level .NET library for programmatic PDF creation and manipulation. Its core model is drawing-surface-based: the API provides an XGraphics object against which text, shapes, images, and lines are drawn at explicit coordinates. There is no layout engine; the calling code is responsible for all positioning, font measurement, line wrapping, and page-break logic. PDFSharp also supports reading existing PDF files for limited manipulation operations.

The library is open source (MIT-licensed; verify current license status) and has historically been distributed as a NuGet package, though the exact current maintenance status, last release version, and level of .NET 6/7/8 support should be verified in the official repository before beginning a migration evaluation. PDFSharp is well-suited to applications that need to generate structurally simple PDFs—fixed layouts, certificates, labels, simple forms—where the calling code can fully specify the position of every element without requiring dynamic reflow.

Architectural Differences

IronPDF approaches PDF generation from the opposite direction. Rather than exposing a drawing surface, it uses a browser rendering engine (Chromium) to convert HTML and CSS into PDF pages. Layout, typography, text wrapping, responsive behavior, and image scaling are handled by the rendering engine. The application provides HTML markup; the library produces a PdfDocument. This model eliminates most of the custom layout code that PDFSharp-based applications accumulate over time.

The practical consequence is that teams migrating from PDFSharp are not remapping API calls one-for-one; they are replacing drawing-surface code with HTML template authoring. The HTML string to PDF pipeline accepts any valid HTML, including inline styles, external stylesheets (via base URL configuration), and JavaScript-rendered content. For teams already maintaining Razor views or T4/Scriban templates for other output formats, the migration often means reusing or adapting existing template infrastructure rather than rewriting from scratch.

IronPDF also provides document operation capabilities—merging, splitting, and page manipulation—that overlap with the subset of PDFSharp functionality teams use for combining documents. These operations are available on PdfDocument objects regardless of how they were originally rendered, which covers both the creation and manipulation use cases in a single library.

Operation Comparisons

Drawing Text (PDFSharp) → HTML Template (IronPDF)

PDFSharp — Drawing Text:

PDFSharp's text rendering requires explicit coordinate specification via XGraphics. A typical pattern:

using PdfSharp.Pdf;
using PdfSharp.Drawing;

// Create document and page
var document = new PdfDocument();
var page = document.AddPage();
page.Size = PdfSharp.PageSize.A4;

var gfx = XGraphics.FromPdfPage(page);

// Font must be created explicitly
var font = new XFont("Arial", 14, XFontStyle.Bold);
var pen = new XPen(XColors.Black, 1);

// Caller is responsible for all coordinates
gfx.DrawString("Invoice #12345", font, XBrushes.Black,
    new XRect(40, 60, page.Width - 80, 30),
    XStringFormats.TopLeft);

// Further drawing calls for each element...
document.Save("invoice.pdf");

Technical constraints:

  • Every text element requires coordinate calculation in points; dynamic content forces runtime measurement via XGraphics.MeasureString()
  • Line wrapping, vertical overflow, and pagination must be implemented manually
  • Font availability on the server must be managed explicitly; embedded fonts require additional handling
  • Tables, multi-column layouts, and indentation all require geometry calculations in calling code

IronPDF — HTML Template:

using IronPdf;

// HTML template — layout handled by the CSS engine
var html = @"
<!DOCTYPE html>
<html>
<head>
  <style>
    body { font-family: Arial, sans-serif; margin: 40px; }
    .invoice-header { font-size: 18px; font-weight: bold; }
    table { width: 100%; border-collapse: collapse; margin-top: 20px; }
    td, th { border: 1px solid #ccc; padding: 8px; font-size: 12px; }
  </style>
</head>
<body>
  <div class='invoice-header'>Invoice #12345</div>
  <table>
    <tr><th>Description</th><th>Amount</th></tr>
    <tr><td>Consulting</td><td>$1,200.00</td></tr>
  </table>
</body>
</html>";

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 20;

// Render — layout engine handles all positioning
using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("invoice.pdf");

The shift from coordinate-based to HTML-based authoring is the largest conceptual change in this migration. The HTML string to PDF guide covers base URL configuration for resolving external stylesheets and images—necessary when templates reference shared asset files rather than embedding everything inline.

Table Rendering

PDFSharp — Manual Table Rendering:

Table rendering in PDFSharp is entirely manual: the calling code computes row heights based on measured text, draws cell borders using XGraphics.DrawRectangle(), clips text to cell bounds, and handles column widths as constants or derived values. Page break logic for multi-page tables must be implemented explicitly.

Technical constraints:

  • Row height calculation requires MeasureString() for each cell to handle wrapping
  • Borders, padding, and background fills are separate drawing calls per cell
  • Multi-page tables need explicit page break detection and header row repetition logic
  • Changes to column count or content type require updates to the coordinate calculation code

IronPDF — HTML Table:

using IronPdf;

// Dynamic table generation with standard C# string building
var rows = new System.Text.StringBuilder();
foreach (var item in lineItems)
{
    // HTML escaping omitted for brevity — use proper encoding in production
    rows.Append($"<tr><td>{item.Description}</td><td>{item.Quantity}</td><td>{item.Price:C}</td></tr>");
}

var html = $@"
<html><head><style>
  table {{ width:100%; border-collapse:collapse; }}
  th, td {{ border:1px solid #999; padding:6px 10px; font-size:11px; }}
  th {{ background:#f5f5f5; }}
  tr {{ page-break-inside: avoid; }}
</style></head>
<body>
  <table>
    <tr><th>Description</th><th>Qty</th><th>Price</th></tr>
    {rows}
  </table>
</body></html>";

var renderer = new ChromePdfRenderer();
// Repeat headers across page breaks via CSS — no manual logic needed
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("line-items.pdf");

HTML tables handle multi-page pagination, header repetition (via <thead> with appropriate CSS), and cell content wrapping automatically. The page breaks guide covers the full set of CSS page break properties available for controlling how tables and other elements split across pages.

Merging and Splitting PDFs

PDFSharp — Merge:

PDFSharp provides PdfDocument import functionality that allows pages from one document to be appended to another. The pattern typically involves opening each source document, iterating pages, and importing them into the target document.

Technical constraints:

  • Imported documents must be opened with an Open mode that permits modification
  • Page count bookkeeping must be maintained manually when merging many documents
  • Error handling around source document corruption or encryption must be explicit

IronPDF — Merge and Split:

using IronPdf;

// Merge: static method accepting IEnumerable<PdfDocument>
using var docA = PdfDocument.FromFile("report-part1.pdf");
using var docB = PdfDocument.FromFile("report-part2.pdf");

using var merged = PdfDocument.Merge(docA, docB);
merged.SaveAs("report-complete.pdf");

// Split: extract a page range into a new document
using var source = PdfDocument.FromFile("large-report.pdf");
using var excerpt = source.CopyPages(0, 4); // pages 0–4 inclusive
excerpt.SaveAs("report-excerpt.pdf");

The merge and split guide covers the full set of overloads including merging from file paths, streams, and byte arrays. For large document sets, the guide includes notes on memory management when merging many documents in a loop—relevant when migrating batch processing pipelines that previously used PDFSharp's append pattern.

Digital Signatures

PDFSharp — Digital Signatures:

PDFSharp's built-in support for digital signatures is limited; verify the current state in official documentation. Some teams using PDFSharp for signed document workflows use PDFSharp in combination with a separate signing library or post-processing step.

Technical constraints:

  • Verify which signature standards (CAdES, PAdES) are supported natively
  • Certificate management and chain validation may require external tooling
  • Timestamp authority integration may not be available natively

IronPDF — Digital Signatures:

using IronPdf;
using IronPdf.Signing;

using var pdf = PdfDocument.FromFile("document-to-sign.pdf");

// Sign using a .pfx certificate file
var signature = new PdfSignature("certificate.pfx", "certPassword");
signature.SigningContact = "signing@example.com";
signature.SigningLocation = "Chicago, IL";
signature.SigningReason = "Document approval";

pdf.Sign(signature);
pdf.SaveAs("document-signed.pdf");

The digital signatures guide covers certificate sources including X.509 objects, file-based PFX, and HSM integration for environments where private keys cannot leave hardware security modules.

Breaking Changes & Gotchas

  • No coordinate-based drawing API. This is the largest conceptual break. Code that calls XGraphics.DrawString(), DrawRectangle(), DrawLine(), or DrawImage() with explicit point coordinates has no direct equivalent in IronPDF. All such code must be reexpressed as HTML/CSS, which is a redesign task rather than a refactoring task.
  • Font management changes completely. PDFSharp's XFont takes a font family name and style; fonts must be installed on the host system or embedded explicitly. IronPDF uses CSS font-family declarations with the Chromium engine handling font resolution. Web font loading via CSS @font-face is supported; see the font management documentation for details.
  • Disposal semantics are new. PDFSharp's PdfDocument should be disposed, and most examples use Save() followed by disposal—but the library does not enforce disposal via IDisposable as prominently as IronPDF does. IronPDF's PdfDocument should always be wrapped in using.
  • Text measurement is not exposed. Applications using XGraphics.MeasureString() to compute layout dimensions—for pagination logic, dynamic column widths, or word wrapping—have no equivalent API to call. The browser engine manages all of this internally. Layout logic dependent on text measurement must be refactored to use CSS-driven layout.
  • Platform binary dependencies. IronPDF ships native Chromium binaries per platform. Docker images built on minimal base images (Alpine, distroless) may lack the shared library dependencies required. Test container builds early.
  • No low-level PDF object access by default. PDFSharp's PdfDocument.Internals provides access to raw PDF dictionaries and objects. IronPDF exposes a PDF DOM access API; verify whether the level of access required by the application is available.
  • XPS support. PDFSharp includes MigraDoc and XPS-related functionality in some distributions. IronPDF has no equivalent for XPS output; verify whether the application uses those features.
  • License key required. IronPDF is a commercial library. PDFSharp is open source. Budget for license cost and provisioning in the migration plan.

Migration Checklist

  1. Inventory all XGraphics usage. Every call to XGraphics.DrawString(), DrawRectangle(), DrawLine(), DrawImage(), and MeasureString() represents layout code that must be reimplemented as HTML/CSS. This is typically the largest scope item in a PDFSharp migration.
  2. Identify documents that are rendered vs. manipulated. PDFSharp is often used for both creating PDFs from scratch and manipulating existing files (appending pages, reading content). Separate these use cases; the migration path differs for each.
  3. Create HTML templates for each document type. For each distinct document layout currently driven by XGraphics drawing code, author an equivalent HTML template. Prioritize templates by document complexity and business criticality.
  4. Install the IronPDF NuGet package. Run dotnet add package IronPdf. Verify that the runtime identifier (RID) for each target environment is covered by the package's native binary set.
  5. Configure the license key. Set up the IronPDF license before first use. See the license key setup guide for configuration approaches compatible with environment-variable-based secret management.
  6. Replace document creation call sites. Substitute new PdfDocument() + XGraphics drawing calls with new ChromePdfRenderer() + RenderHtmlAsPdf(template). Pass a BaseUrlOrPath when templates reference external CSS or images.
  7. Replace merge and split operations. Map PDFSharp page import patterns to PdfDocument.Merge() and CopyPages(). Update all disposal patterns to use using.
  8. Remap metadata and security settings. Port any PdfDocument metadata assignments (author, title, subject) and password/permissions settings to the IronPDF equivalents; verify exact property names in current documentation.
  9. Update digital signature workflows. If the application signs PDFs, port certificate loading and signing calls to IronPDF's PdfSignature API. Validate signed output with a PDF validator.
  10. Test container / server builds. Build Docker images for all target environments and verify that the Chromium binary dependencies are met. Add required system packages to the Dockerfile if needed.
  11. Run visual regression tests. Compare rendered output between the old and new implementations. Pixel-perfect fidelity is unlikely (different rendering engines), but layout, content accuracy, and page structure should be verified.
  12. Remove PDFSharp package references. Once all call sites have been migrated and tested, remove PDFSharp from the project's NuGet dependencies to eliminate any accidental continued use.

Conclusion

When staying on PDFSharp is technically reasonable

PDFSharp is a reasonable choice for teams whose PDF requirements center on coordinate-based document assembly: fixed-layout certificates, labels, simple forms, or documents where the structure is entirely static and the layout is unlikely to change. The open source license eliminates commercial cost and procurement process. If the existing codebase has mature, well-tested drawing code and the document layouts are stable, the disruption of migration may not be justified. Teams with strong PDF object model expertise who need low-level access to PDF internals will also find PDFSharp's Internals API harder to replicate.

Signals that indicate migration is worth the engineering effort

The migration signal is clearest when PDFSharp-based code has grown a large, hand-maintained layout engine: text wrapping loops, pagination calculations, manual table geometry, font measurement utilities. Each of those components represents maintenance surface that disappears when the rendering engine handles layout. Teams targeting new document types that are HTML-friendly—reports with complex tables, invoices with variable line items, HTML-exported content—find the template authoring model significantly more productive than the drawing model. If the team already authors HTML templates for email or web output, the skill set transfers directly. Platform migration (moving to Linux, deploying to containers, targeting .NET 8) is also a natural inflection point to evaluate whether the drawing-based model continues to serve the team's needs.

What the cutover typically involves at the code level

The migration is not a refactoring exercise—it is a partial rewrite of the document generation layer. The code structure changes from procedural drawing code to template authoring plus a short rendering call. Teams that budget for this as a rewrite rather than a mapping task tend to produce cleaner results. The merge, split, and document manipulation operations translate more mechanically and can often be migrated without redesign. Security settings, metadata, and output format options are similarly low-effort remappings.
