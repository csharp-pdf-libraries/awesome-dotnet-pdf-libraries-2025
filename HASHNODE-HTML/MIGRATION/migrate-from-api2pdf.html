Migrating from Api2pdf to IronPDF: API mapping and migration checklist

before-and-after code, risk assessment, and a migration checklist

Framing

Cloud-hosted PDF generation APIs occupy a specific architectural niche in .NET applications. Rather than embedding a PDF library in the application process, the calling application sends an HTTP request with HTML or URL content and receives a PDF in return. This model has genuine advantages at small scale — no native dependency management, no Chromium process management, no licensing footprint in the application itself — and teams often adopt it early in a product's life when PDF volume is low and operational simplicity is valued over performance.

Api2pdf is one of several cloud-based PDF generation services that targets this use case. It exposes a REST API that accepts HTML strings, URLs, or file payloads and returns rendered PDFs, typically leveraging Chromium under the hood. The .NET integration is via an HTTP client or a thin SDK wrapper. Teams that start with this model typically revisit it as application load increases, latency requirements tighten, data residency requirements emerge, or per-call pricing becomes a meaningful budget line.

This guide is for .NET engineers evaluating or executing a migration from Api2pdf to IronPDF. The migration is classified as Low effort compared to library-to-library migrations because the rendering pipeline is similar (both use Chromium), the operations are functionally equivalent, and the primary change is eliminating the network hop in favor of an in-process rendering call. This guide covers the architectural shift, before-and-after code comparisons, API mapping, and a cutover checklist.

What Api2pdf Is Designed to Do

Api2pdf is a cloud PDF generation service. Callers authenticate via an API key passed in an HTTP header, submit HTML content or a URL in a JSON request body, and receive a JSON response containing a download link or inline PDF bytes. The service uses Chromium for HTML rendering and supports several additional operations (LibreOffice-based DOCX/XLSX conversion, PDF merge) via distinct API endpoints. The .NET integration is typically handled by an official or community NuGet client SDK, or by constructing HTTP requests directly using HttpClient.

The service's install footprint is intentionally minimal on the client side — the application carries only the HTTP client dependency. All rendering infrastructure, Chromium process management, and resource scaling are handled by the Api2pdf service. The primary use case should be verified in official documentation, as the service has evolved its feature set over time. The product status and last release should also be verified in official documentation, as cloud API services update their feature set and pricing models independently of client SDK versioning. The .NET SDK version history should be verified in official documentation.

Architectural Differences

The most structurally significant difference between Api2pdf and IronPDF is that Api2pdf is a remote service and IronPDF is an in-process library. Every Api2pdf render call involves an HTTP round trip: the calling application serializes the request, the network delivers it to the Api2pdf infrastructure, Chromium renders the PDF on remote hardware, and the result is returned over the network. IronPDF performs the same Chromium rendering in-process, on the application host.

This architectural shift affects latency, throughput, reliability, and data handling. In-process rendering eliminates network latency for each PDF and removes the failure modes associated with outbound HTTP calls (timeouts, rate limits, third-party availability). It also means the PDF content and rendering configuration never leave the application's process boundary — a relevant consideration for documents containing PII, financial data, or regulated content.

IronPDF's ChromePdfRenderer is the equivalent of Api2pdf's rendering endpoint. Configure a RenderingOptions object once, call RenderHtmlAsPdf() or RenderUrlAsPdf(), and dispose the returned PdfDocument after use. The async rendering guide covers the Task-based async surface, which is the natural fit for web API contexts where the Api2pdf calls are already awaited. License setup via IronPdf.License.LicenseKey is a one-time startup configuration — see the license setup guide.

Operation Comparisons

HTML String to PDF

Api2pdf — HTML String to PDF (via HTTP)

using System.Net.Http;
using System.Net.Http.Json;
using System.Text.Json;

// Api2pdf REST call — the application sends an HTTP POST with the HTML payload
var client = new HttpClient();
client.DefaultRequestHeaders.Add("Authorization", "YOUR-API2PDF-KEY");

var requestBody = new
{
    html = "<html><body><h1>Report</h1><p>Content.</p></body></html>",
    inlinePdf = true,   // Return PDF bytes in response, not a download link
    fileName = "report.pdf",
    options = new
    {
        marginTop = "10mm",
        marginBottom = "10mm",
        marginLeft = "15mm",
        marginRight = "15mm"
    }
};

// POST to the Chrome HTML endpoint
var response = await client.PostAsJsonAsync(
    "https://v2.api2pdf.com/chrome/pdf/html", requestBody);

response.EnsureSuccessStatusCode();

// Parse the JSON envelope to get the PDF bytes or URL
var result = await response.Content.ReadFromJsonAsync<JsonElement>();
byte[] pdfBytes = Convert.FromBase64String(result.GetProperty("pdf").GetString()!);

await File.WriteAllBytesAsync("report.pdf", pdfBytes);

Concrete constraints:

  • Every render is a network call with associated latency (typically 500ms–2s), timeout risk, and retry requirement.
  • The API key is sent with every request — key rotation, scoping, and revocation must be managed.
  • JSON envelope parsing is required; response schema should be verified against the current Api2pdf API version.
  • Margin and option parameters are string-formatted ("10mm"); IronPDF uses numeric properties with a defined unit.
  • Any API2pdf outage or rate limit directly causes PDF generation failures in the application.

IronPDF — HTML String to PDF

using IronPdf;

// Renderer is stateless; configure once and reuse across calls
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.MarginTop = 10;     // millimeters
renderer.RenderingOptions.MarginBottom = 10;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;

// No network call — rendering is in-process via embedded Chromium
using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Report</h1><p>Content.</p></body></html>"
);

pdf.SaveAs("report.pdf");
// PdfDocument disposed at end of using block

The full set of rendering options is in the HTML string to PDF guide. The in-process rendering eliminates all HTTP client code, JSON envelope parsing, retry logic, and API key management from the PDF generation path.

URL to PDF

Api2pdf — URL to PDF (via HTTP)

using System.Net.Http;
using System.Net.Http.Json;

var client = new HttpClient();
client.DefaultRequestHeaders.Add("Authorization", "YOUR-API2PDF-KEY");

var requestBody = new
{
    url = "https://reports.example.com/monthly",
    inlinePdf = false,     // Return a temporary download URL instead
    fileName = "monthly-report.pdf",
    options = new
    {
        landscape = false,
        printBackground = true
    }
};

var response = await client.PostAsJsonAsync(
    "https://v2.api2pdf.com/chrome/pdf/url", requestBody);

response.EnsureSuccessStatusCode();

// Download the PDF from the temporary URL in the response
var result = await response.Content.ReadFromJsonAsync<System.Text.Json.JsonElement>();
string downloadUrl = result.GetProperty("FileUrl").GetString()!;

using var pdfBytes = await client.GetAsync(downloadUrl);
byte[] bytes = await pdfBytes.Content.ReadAsByteArrayAsync();
await File.WriteAllBytesAsync("monthly-report.pdf", bytes);

Concrete constraints:

  • Two network calls are required when inlinePdf = false (API call + download from temp URL).
  • Temporary download URLs have expiry times; parsing and downloading should happen promptly after the API call.
  • The URL being rendered must be accessible from Api2pdf's infrastructure — internal URLs and localhost are not reachable without a tunnel or VPN.
  • Background printing (printBackground) and other Chromium options are a flat JSON key-value structure; verify mapping to IronPDF's RenderingOptions.

IronPDF — URL to PDF

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PrintBackground = true;

// In-process Chromium fetch and render — no second download step
using var pdf = renderer.RenderUrlAsPdf("https://reports.example.com/monthly");
pdf.SaveAs("monthly-report.pdf");

Because rendering is in-process, internal URLs (behind authentication, on private networks) are accessible as long as the application host can reach them. This eliminates the Api2pdf limitation around private URL rendering. The URL to PDF guide covers request headers, cookies, and wait conditions for JavaScript-heavy pages.

Merging PDFs

Api2pdf — Merging PDFs (via HTTP)

using System.Net.Http;
using System.Net.Http.Json;

var client = new HttpClient();
client.DefaultRequestHeaders.Add("Authorization", "YOUR-API2PDF-KEY");

// Api2pdf merge accepts a list of publicly accessible PDF URLs
var requestBody = new
{
    urls = new[]
    {
        "https://storage.example.com/doc1.pdf",
        "https://storage.example.com/doc2.pdf",
        "https://storage.example.com/doc3.pdf"
    }
};

var response = await client.PostAsJsonAsync(
    "https://v2.api2pdf.com/pdf/merge", requestBody);

response.EnsureSuccessStatusCode();

// Parse response and download the merged PDF
var result = await response.Content.ReadFromJsonAsync<System.Text.Json.JsonElement>();
string mergedUrl = result.GetProperty("FileUrl").GetString()!;

using var mergedResponse = await client.GetAsync(mergedUrl);
byte[] mergedBytes = await mergedResponse.Content.ReadAsByteArrayAsync();
await File.WriteAllBytesAsync("merged.pdf", mergedBytes);

Concrete constraints:

  • Api2pdf merge requires source PDFs to be at publicly accessible URLs; local or private files must be uploaded first.
  • Network latency is additive: upload + API call + download all contribute to total operation time.
  • File URL expiry applies to the merge output as well.

IronPDF — Merging PDFs

using IronPdf;

// Source PDFs are loaded locally — no upload required
using var pdf1 = PdfDocument.FromFile("doc1.pdf");
using var pdf2 = PdfDocument.FromFile("doc2.pdf");
using var pdf3 = PdfDocument.FromFile("doc3.pdf");

// Single in-process call
using var merged = PdfDocument.Merge(pdf1, pdf2, pdf3);
merged.SaveAs("merged.pdf");

In-process merging removes the requirement to upload source documents to accessible storage before the merge operation. Large document sets can be merged without network bandwidth constraints. Merge and split patterns are documented in the merge and split guide.

Async Rendering in a Web API Context

Api2pdf — Async in ASP.NET Core

using System.Net.Http;
using System.Net.Http.Json;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { private readonly HttpClient _httpClient;

public ReportController(IHttpClientFactory httpClientFactory) { _httpClient = httpClientFactory.CreateClient("api2pdf"); }

[HttpGet("{id}")] public async Task GetReport(int id) { // Build HTML for this report string html = BuildReportHtml(id);

// API call — involves network round trip per request var response = await _httpClient.PostAsJsonAsync( "https://v2.api2pdf.com/chrome/pdf/html", new { html, inlinePdf = true });

response.EnsureSuccessStatusCode();

var result = await response.Content.ReadFromJsonAsync(); byte[] pdfBytes = Convert.FromBase64String(result.GetProperty("pdf").GetString()!);

return File(pdfBytes, "application/pdf", $"report-{id}.pdf"); }

private string BuildReportHtml(int id) => $"

Report {id}

"; }

Concrete constraints:

  • Each HTTP request to the API controller produces an outbound HTTP request to Api2pdf.
  • Concurrent report requests multiply the outbound HTTP load; Api2pdf rate limits apply.
  • Any Api2pdf latency directly increases the API controller response time.

IronPDF — Async in ASP.NET Core

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { // ChromePdfRenderer can be registered as a singleton or created per request private readonly ChromePdfRenderer _renderer;

public ReportController() { _renderer = new ChromePdfRenderer(); }

[HttpGet("{id}")] public async Task GetReport(int id) { string html = BuildReportHtml(id);

// Async render — in-process, no outbound HTTP using var pdf = await _renderer.RenderHtmlAsPdfAsync(html); byte[] pdfBytes = pdf.BinaryData;

return File(pdfBytes, "application/pdf", $"report-{id}.pdf"); }

private string BuildReportHtml(int id) => $"

Report {id}

"; } ```

RenderHtmlAsPdfAsync returns a Task<PdfDocument> and integrates directly with ASP.NET Core's async pipeline. Removing the outbound HTTP call from the request path reduces per-request latency to the rendering time only. Full async usage patterns are documented in the async rendering guide.

Breaking Changes & Gotchas

  • No HTTP client required: The entire HttpClient setup, authentication header management, request serialization, response deserialization, and retry policy for PDF calls can be removed. Teams using IHttpClientFactory with a named client for Api2pdf can remove that registration.
  • Private URL rendering: Api2pdf cannot render pages behind private network boundaries. IronPDF renders from the application host, so internal URLs, localhost addresses, and intranet pages are accessible without any tunneling.
  • Font resolution shifts to server: Api2pdf's cloud infrastructure has its own font set. IronPDF resolves fonts from the application host's system. Documents using Google Fonts or web fonts via CDN continue to work; documents relying on fonts that were available in Api2pdf's environment but not on the application host will render with fallback fonts.
  • Chromium process on application host: IronPDF runs a Chromium process on the application server. Memory and CPU consumption per render call should be benchmarked against current application resource headroom.
  • No temporary file URLs: Api2pdf returns temporary download URLs for some operations. That URL-based hand-off pattern is removed entirely. PDFs are returned as PdfDocument objects (or byte arrays / streams directly from them).
  • Linux system dependencies: On Linux, IronPDF requires additional system libraries for Chromium. Docker base images must be updated; refer to the official documentation.
  • License key at startup: IronPdf.License.LicenseKey must be set before the first render call. Forgetting to set it results in watermarked output — a runtime error not caught at compile time.
  • No rate limits, but no scaling isolation: Api2pdf's infrastructure scales with the cloud service. IronPDF scales with the application host. If PDF generation volume spikes, host resources must accommodate it. Review the parallel processing examples for concurrency patterns.
  • Error model change: Api2pdf failures surface as HTTP errors (non-2xx responses, timeout exceptions from HttpClient). IronPDF failures surface as .NET exceptions from the rendering call. Error handling code must be updated.

Migration Checklist

  1. Audit all Api2pdf HTTP calls: Enumerate every PostAsJsonAsync (or SDK method) call that targets Api2pdf endpoints. Note the endpoint, the options being set, and the response parsing pattern for each.
  2. Install IronPDF via NuGet: dotnet add package IronPdf. Retain the HttpClient / IHttpClientFactory registration for Api2pdf until replacement code is tested.
  3. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs or Startup.cs before any rendering occurs. Refer to the license setup guide.
  4. Replace HTML rendering calls: Swap POST /chrome/pdf/html → renderer.RenderHtmlAsPdf(html). Wrap the result in a using block.
  5. Replace URL rendering calls: Swap POST /chrome/pdf/url → renderer.RenderUrlAsPdf(url). Verify that all URLs being rendered are accessible from the application host.
  6. Replace merge calls: Swap POST /pdf/merge → PdfDocument.Merge(). Source PDFs no longer need to be uploaded to accessible storage first.
  7. Map rendering options: For each options.* key in the Api2pdf request body, find and set the corresponding RenderingOptions property.
  8. Replace response parsing with direct property access: Remove all JSON deserialization, base64 decoding, and temporary URL download code. Use pdf.BinaryData, pdf.Stream, or pdf.SaveAs() directly.
  9. Update error handling: Replace HTTP-specific error handling (EnsureSuccessStatusCode, HttpRequestException, timeout catches) with standard .NET exception handling around the render call.
  10. Verify font availability on deployment host: Test documents that use custom or CDN-hosted fonts. If any font rendered correctly via Api2pdf but not via IronPDF, the font may need to be installed on the host or referenced via CDN URL in the HTML.
  11. Remove Api2pdf HTTP client registration: Once all calls are replaced and tested, remove the HttpClient or IHttpClientFactory registration and API key configuration for Api2pdf.
  12. Load test rendering under production concurrency: Benchmark rendering throughput and memory consumption on the application host under expected concurrent load before promoting to production.

Conclusion

When staying on Api2pdf is technically reasonable

Api2pdf is a reasonable choice for applications with low PDF volume where operational simplicity is valued over latency or data control. If the application is already cloud-hosted with outbound internet access, PDF generation volume is low (tens or hundreds per day), and there is no data residency requirement, the cloud API model avoids the need to manage Chromium dependencies on the application host entirely. Teams with minimal DevOps capacity may prefer the zero-dependency client model.

Signals that indicate migration is worth the engineering effort

Migration effort is Low — this is one of the simpler library swaps in the PDF ecosystem. The primary signals that make it worth proceeding are: PDF generation volume has grown to where per-call pricing is material; latency requirements are tight enough that the network round trip is a problem; documents contain sensitive data that should not leave the application process; or URLs being rendered are on private networks inaccessible to the Api2pdf cloud infrastructure.

What the cutover typically involves at the code level

For most applications, each Api2pdf call site collapses from ~15–25 lines (HTTP setup, request body construction, response parsing, error handling, binary extraction) to 3–5 lines (configure renderer, call render method, use PdfDocument). The largest risk is font parity — validating that documents render identically when font resolution shifts from the Api2pdf cloud environment to the application host. A render comparison pass against a representative sample of documents before and after the switch is the recommended validation approach.
