Migrating from VectSharp to IronPDF: the engineering breakdown

effort estimation, API mapping, and production considerations

# Migrating from VectSharp to IronPDF: the engineering breakdown

The original version of this article is published at https://ironsoftware.com/csharp/pdf/blog/migrate-from-vectsharp/.

Framing

Vector graphics libraries occupy a particular niche in the .NET PDF ecosystem. They appeal to teams that need precise geometric control over document content—charts, diagrams, technical drawings, infographics—and who want to express that content in a programming model based on paths, shapes, and transformations rather than HTML and CSS. When those teams need PDF output, they reach for a library whose output format is a side effect of a graphics-first design rather than a PDF-first design.

VectSharp fits this pattern. It is an actively maintained .NET library for vector graphics that supports PDF as one of several output targets. Teams adopt it when the primary task is programmatic drawing—building chart renderers, diagram generators, or data-visualization pipelines—and PDF output is part of a multi-format delivery requirement that also includes SVG, PNG, or other raster targets.

Migration from VectSharp to IronPDF typically surfaces when the workflow evolves beyond geometric drawing: when the team needs to combine programmatic graphics with HTML-based layouts, when document-level features such as encryption, form fields, or digital signatures are required, or when the application is growing toward a server-side PDF generation platform that needs a broader manipulation API. Understanding where the two libraries overlap and where they diverge is the basis for an accurate effort estimate.

What VectSharp Is Designed To Do

VectSharp is an open-source .NET library for creating vector graphics, released under the LGPLv3 license. Its programming model is canvas-based: the application creates a Page object, obtains a Graphics context, and calls drawing methods—paths, text, images, transformations—to build up the graphic content. The library then serialises that graphic to a target format via a renderer module: PDF, SVG, raster image via SkiaSharp or ImageSharp, or a GUI canvas. The last release as of this writing was v3.2.0 in 2024; verify the current version at the official repository.

VectSharp's PDF output capability is provided through a dedicated renderer module (VectSharp.PDF) that converts the in-memory graphic representation to a PDF document. This makes it well-suited for applications that generate data-visualizations or diagrams programmatically and need to export them to PDF. It is not designed as a general-purpose PDF manipulation library: it does not read existing PDFs, fill form fields, apply encryption, sign documents, or render HTML content. The library targets .NET Standard and .NET; verify the exact supported target frameworks in the current NuGet package metadata.

Architectural Differences

IronPDF approaches PDF generation from an HTML-rendering perspective rather than a vector-drawing perspective. The primary input is HTML and CSS; the rendering engine is Chromium, which handles all layout, typography, and image placement. The output is a PdfDocument object that can be saved, streamed, further manipulated, or combined with other documents. For teams whose output requirements include data tables, structured layouts, and typographic content alongside graphics, the HTML model often reduces the total authoring effort compared to coordinate-based drawing.

The HTML string to PDF pipeline accepts any valid HTML including inline SVG, so vector graphics that are already expressible as SVG can be embedded directly in the HTML template without a separate drawing API. For applications that use VectSharp to produce SVG content, this path may allow existing SVG output to be reused within IronPDF's HTML rendering pipeline. The SVG rendering guide covers how SVG content is handled within HTML-to-PDF conversion.

IronPDF's PdfDocument implements IDisposable; all instances should be wrapped in using blocks. VectSharp's Page and Graphics objects are plain managed objects without disposable semantics—this pattern change should be reflected in every call site during migration. IronPDF also provides document manipulation capabilities (merge, split, encrypt, sign, annotate, form-fill) that are outside VectSharp's scope entirely and require no migration effort—they are additive capabilities.

Operation Comparisons

Drawing a Shape and Exporting to PDF

VectSharp — Drawing Shapes and Exporting:

VectSharp's drawing model uses a Graphics object obtained from a Page. Shapes are drawn using path and brush/fill methods. Export to PDF uses the VectSharp.PDF renderer.

// VectSharp — draw a rectangle and text, export to PDF
// Requires: VectSharp, VectSharp.PDF NuGet packages
using VectSharp;
using VectSharp.PDF;

// Create a page (width, height in points)
var page = new Page(595, 842); // A4 in points
var gfx = page.Graphics;

// Draw a filled rectangle
gfx.FillRectangle(new Point(50, 50), new Size(200, 100),
    Colour.FromRgb(0.2, 0.4, 0.8));

// Draw text — FontFamily and text size specified here
var font = new Font(FontFamily.ResolveFontFamily(FontFamily.StandardFontFamilies.Helvetica), 18);
gfx.FillText(new Point(60, 90), "Quarterly Results", font,
    Colour.FromRgb(1, 1, 1));

// Export to PDF via the PDF renderer
var doc = new Document();
doc.Pages.Add(page);
doc.SaveAsPDF("output.pdf");
// VectSharp objects are plain managed types — no IDisposable

Technical constraints:

  • All positioning is in points with explicit coordinates; text wrapping, reflowing, and pagination are entirely the caller's responsibility
  • Font availability depends on installed system fonts or fonts bundled with the application; FontFamily.ResolveFontFamily resolves at runtime
  • No support for reading or manipulating existing PDF content
  • PDF output is a format target of the graphics library; document-level PDF features (encryption, signatures, metadata) are outside VectSharp's scope

IronPDF — Equivalent Output via HTML/SVG Template:

using IronPdf;

// Equivalent output using HTML with inline SVG
// Layout and typography handled by Chromium — no coordinate math required
var html = @"
<!DOCTYPE html>
<html>
<head>
  <style>
    body { margin: 50px; font-family: Helvetica, sans-serif; }
    .chart-rect {
      display: inline-block;
      width: 200px; height: 100px;
      background: rgb(51, 102, 204);
      position: relative;
    }
    .chart-label {
      position: absolute;
      top: 30px; left: 10px;
      color: white; font-size: 18px;
    }
  </style>
</head>
<body>
  <div class='chart-rect'>
    <span class='chart-label'>Quarterly Results</span>
  </div>
</body>
</html>";

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Render — the Chromium engine handles all layout and typography
using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("output.pdf");

For teams whose VectSharp graphics are already expressible as SVG, embedding the SVG directly in the HTML template (using an <svg> element or an <img src="data:image/svg+xml,..." /> tag) is often the most direct migration path. The HTML string to PDF guide covers base URL configuration for referencing external SVG files; the SVG rendering guide documents the handling of inline and referenced SVG within the rendering pipeline.

Multi-Page Document Assembly

VectSharp — Multi-Page PDF:

In VectSharp, a multi-page document is assembled by adding multiple Page objects to a Document and calling the PDF renderer once.

using VectSharp;
using VectSharp.PDF;

var doc = new Document();

// Add pages with individual graphics
for (int i = 0; i < 5; i++)
{
    var page = new Page(595, 842);
    var gfx = page.Graphics;

    // Draw page content
    var font = new Font(
        FontFamily.ResolveFontFamily(FontFamily.StandardFontFamilies.Helvetica), 12);
    gfx.FillText(new Point(50, 50), $"Page {i + 1} content", font,
        Colour.FromRgb(0, 0, 0));

    doc.Pages.Add(page);
}

doc.SaveAsPDF("multi-page.pdf");

Technical constraints:

  • All pages share the same rendering pipeline; there is no concept of conditionally rendering pages from different sources
  • Merging content from external PDFs requires a separate library; VectSharp cannot read or append existing PDFs
  • Page count and layout are fixed at draw time; dynamic content requires drawing-time data binding

IronPDF — Multi-Page Document via HTML Pagination:

using IronPdf;

// Long HTML content paginates automatically via Chromium layout engine
var html = @"
<!DOCTYPE html>
<html>
<head>
  <style>
    body { font-family: Arial, sans-serif; font-size: 12px; margin: 40px; }
    .page-section { page-break-before: always; }
    .page-section:first-child { page-break-before: auto; }
    h2 { color: #333; }
    table { width: 100%; border-collapse: collapse; margin-top: 16px; }
    td, th { border: 1px solid #ccc; padding: 6px; }
  </style>
</head>
<body>
  <h2>Section 1</h2>
  <p>Content for section one.</p>
  <div class='page-section'>
    <h2>Section 2</h2>
    <p>Content for section two.</p>
  </div>
</body>
</html>";

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 20;

using var pdf = renderer.RenderHtmlAsPdf(html);
Console.WriteLine($"Pages generated: {pdf.PageCount}");
pdf.SaveAs("multi-page.pdf");

The page breaks guide covers the full set of CSS page break properties for controlling how content flows across pages. For documents that combine programmatically generated pages with fixed content, the merge API allows separately rendered documents to be combined into a single output file.

Adding Encryption to PDF Output

VectSharp — Encryption:

VectSharp has no built-in PDF encryption or security API. Applications that need password-protected PDFs from VectSharp output must pass the generated file through a separate library.

Technical constraints:

  • Encryption requires a dependency on a separate PDF manipulation library
  • File must be written to disk (or a stream) before encryption can be applied
  • No integrated API; the two-step process adds complexity and a second point of failure
  • Any change to the security library creates a second migration to manage

IronPDF — Encryption:

using IronPdf;

var renderer = new ChromePdfRenderer();
using var pdf = renderer.RenderHtmlAsPdf(documentHtml);

// Apply password protection directly on the generated document
pdf.SecuritySettings.OwnerPassword = "ownerSecret";
pdf.SecuritySettings.UserPassword = "userReadKey";
pdf.SecuritySettings.AllowUserPrint = true;
pdf.SecuritySettings.AllowUserCopyPasteContent = false;

pdf.SaveAs("protected-document.pdf");

Encryption, permissions, digital signatures, and metadata are all operations on the same PdfDocument object that the renderer returns. The passwords and permissions guide covers the full permission flag set. For teams migrating from VectSharp, this consolidation of generation and security into a single library is frequently cited as a simplification of the production pipeline.

Font Handling

VectSharp — Font Handling:

VectSharp resolves fonts through FontFamily objects, either from standard PDF fonts, system-installed fonts, or TTF files loaded at runtime. The Font constructor takes a FontFamily and a size in points.

using VectSharp;

// Standard PDF font (always available in PDF viewers)
var helvetica = FontFamily.ResolveFontFamily(FontFamily.StandardFontFamilies.Helvetica);
var bodyFont = new Font(helvetica, 12);

// Custom TTF font loaded from file
// FontFamily.ResolveFontFamily("path/to/custom.ttf")
var customFamily = FontFamily.ResolveFontFamily("fonts/CustomFont-Regular.ttf");
var customFont = new Font(customFamily, 14);

// Font is used directly in draw calls
// gfx.FillText(position, text, customFont, colour);

Technical constraints:

  • FontFamily.ResolveFontFamily throws at runtime if the font file is not found; deployment must include font files
  • Font metrics (advance width, ascent, descent) are available for text layout calculations; this is a VectSharp strength for custom layout engines
  • Standard PDF fonts (Helvetica, Times, Courier) do not need to be embedded; custom fonts must be bundled

IronPDF — Font Handling via CSS:

using IronPdf;

// Fonts are declared in CSS — system fonts, web fonts, or @font-face
var html = @"
<!DOCTYPE html>
<html>
<head>
  <style>
    /* System font fallback stack */
    body { font-family: 'Segoe UI', Arial, sans-serif; font-size: 12px; }

    /* Custom font via @font-face — path resolved relative to BaseUrlOrPath */
    @font-face {
      font-family: 'CustomFont';
      src: url('fonts/CustomFont-Regular.ttf') format('truetype');
    }
    .custom-text { font-family: 'CustomFont', sans-serif; font-size: 14px; }
  </style>
</head>
<body>
  <p>Body text in system font.</p>
  <p class='custom-text'>Text in custom font.</p>
</body>
</html>";

var renderer = new ChromePdfRenderer();
// BaseUrlOrPath resolves relative font and asset paths
using var pdf = renderer.RenderHtmlAsPdf(html,
    baseUrlOrPath: System.IO.Path.GetFullPath("./"));
pdf.SaveAs("font-demo.pdf");

The font management guide covers font embedding, @font-face declarations, and how Chromium resolves font paths during rendering. Font metrics are not exposed at the C# API level; text measurement is handled internally by the rendering engine.

Breaking Changes & Gotchas

  • No geometric drawing API. Every call to VectSharp's Graphics drawing methods—FillRectangle, StrokePath, FillText, DrawImage—must be reexpressed as HTML/CSS or inline SVG. This is a design task, not a porting task, and its effort is proportional to the complexity of the existing graphics.
  • Font metrics are not exposed. VectSharp provides text measurement (advance width, ascent, descent) through the Font object, which some applications use for custom layout calculations. IronPDF has no equivalent API; all text measurement is internal to the Chromium engine. Applications that use font metrics for positioning or pagination logic must redesign that logic as CSS-driven layout.
  • Multi-format output requires separate tools. VectSharp's renderer architecture allows the same Page definition to be output as SVG, PNG, or PDF by swapping the renderer. IronPDF produces PDF only; SVG and raster output require separate libraries. If multi-format output is a core requirement, this is a significant architectural constraint.
  • Disposal semantics are new. VectSharp's Page, Graphics, and Document objects are plain managed types with no IDisposable implementation. IronPDF's PdfDocument holds unmanaged Chromium resources and must be disposed via using. Every code path that produces a PdfDocument must include disposal.
  • Open-source license change. VectSharp is released under LGPLv3. IronPDF is a commercial library. Teams subject to open-source license compliance requirements must account for this change in their procurement and legal review process.
  • Chromium binary dependencies on Linux. IronPDF ships platform-specific Chromium binaries. Linux containers built on minimal base images require additional system packages. This is a new deployment concern for teams coming from VectSharp, which has no native binary dependencies.
  • No reading of existing PDFs in VectSharp. This is not a breaking change—it is a capability gap that IronPDF fills. Code paths that previously required a second library for reading PDFs can be consolidated.
  • License key required at startup. IronPDF requires a license key before the first API call. VectSharp requires no license. Plan for license key provisioning in application configuration and deployment scripts.

Migration Checklist

  1. Audit all VectSharp drawing call sites. Enumerate every use of Graphics drawing methods. Categorize by type: geometric shapes, text placement, image embedding, path drawing. Each category maps to a different HTML/CSS or SVG pattern.
  2. Identify SVG-expressible graphics. For graphics that are already representable as SVG paths and shapes, evaluate whether VectSharp's SVG renderer output can be used directly as an <svg> element inside IronPDF HTML templates. This can significantly reduce the redesign effort for chart and diagram content.
  3. Identify uses of font metrics. Search for calls to font measurement APIs (Font.MeasureText, advance width, ascent/descent). Each use represents layout logic that must be redesigned using CSS—there is no equivalent measurement API in IronPDF.
  4. Install the IronPDF NuGet package. Run dotnet add package IronPdf. Verify that the package resolves native binaries for all target runtime identifiers.
  5. Configure the license key. Set the IronPDF license key before any library call. See the license key setup guide for configuration approaches.
  6. Develop HTML/CSS templates for each document type. For each distinct page layout currently generated with VectSharp drawing code, author an HTML template. Begin with the simplest single-page documents and progress to complex multi-section outputs.
  7. Embed SVG where applicable. For charts and diagrams, evaluate using an HTML/JS charting library (Chart.js, D3.js) within the HTML template, or embed pre-generated SVG. Configure JavaScript wait conditions if chart rendering is JS-driven.
  8. Replace doc.SaveAsPDF() with IronPDF render calls. Substitute each VectSharp document save with a ChromePdfRenderer.RenderHtmlAsPdf() call followed by PdfDocument.SaveAs().
  9. Add disposal patterns throughout. Wrap every PdfDocument instantiation in a using block. Audit for any code that holds PdfDocument references across method boundaries and ensure disposal responsibility is clearly assigned.
  10. Address multi-format output requirements separately. If the application currently uses VectSharp to produce SVG and raster output in addition to PDF, those output paths remain VectSharp responsibilities or must be addressed with additional libraries. IronPDF does not replace those paths.
  11. Test output against VectSharp reference documents. Compare rendering output visually for representative documents. Pay particular attention to font rendering, color fidelity, and SVG element rendering.
  12. Remove VectSharp package references. After all PDF output paths have been migrated and validated, remove VectSharp and VectSharp.PDF from project dependencies to eliminate residual usage.

Conclusion

When staying on VectSharp is technically reasonable

VectSharp is a sound choice for applications whose primary function is programmatic vector graphics generation, particularly when multi-format output (SVG, PNG, PDF) from a single drawing definition is a core requirement. If the document content is predominantly geometric—charts, diagrams, technical illustrations—and the API's canvas model is a good fit for how the team thinks about the problem, the migration cost to an HTML-based model may not produce proportional benefit. The open-source license is also meaningful for teams where commercial library procurement is constrained. Applications with a modest, stable document set and no need for PDF-level features (encryption, signatures, form fields) have fewer reasons to migrate.

Signals that indicate migration is worth the engineering effort

Migration becomes more attractive when PDF-level features are needed alongside graphics: encryption, digital signatures, form field creation or filling, PDF/A compliance, or document manipulation (merge, split, annotate). Adding these capabilities to a VectSharp workflow requires additional libraries and integration points; IronPDF consolidates them. Similarly, when document content is increasingly HTML-like—tables, flowing text, mixed data/graphics—the HTML rendering model can reduce the volume of drawing code that must be maintained. Teams that find themselves reimplementing text wrapping, pagination, and table layout on top of VectSharp's coordinate model are often candidates for migrating to a layout-engine-based approach.

What the cutover typically involves at the code level

The migration is primarily a design exercise: translating canvas drawing instructions into HTML/CSS or SVG templates. The rendering call itself is a small number of lines; the work is in authoring templates that faithfully reproduce the visual output of the existing drawing code. For applications where the drawing logic is concentrated in a small number of document generators, the migration can be incremental—replacing one document type at a time while leaving others on VectSharp. For applications with widespread drawing calls distributed across many classes, a more systematic refactoring is needed. The absence of a one-to-one API mapping means this migration cannot be automated with a code transform; it requires deliberate template authoring and output validation.
