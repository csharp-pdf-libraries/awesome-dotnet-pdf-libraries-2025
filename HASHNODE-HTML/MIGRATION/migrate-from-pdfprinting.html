Migrating from PDFPrinting.NET to IronPDF: step-by-step for .NET developers

what changes, what breaks, and what maps cleanly

Framing

PDF printing libraries occupy a specific niche in .NET application development: they provide a managed interface for sending PDF files or PDF streams to physical or virtual printer queues, often without requiring a full PDF rendering pipeline in the application itself. Teams adopt these libraries when the core requirement is reliable programmatic printing — controlling printer selection, page range, orientation, and paper size — rather than PDF generation or manipulation. For applications that produce PDFs through some means and need to get them onto paper or a print queue without opening a viewer application, a focused printing library is a reasonable choice.

Re-evaluation of a dedicated PDF printing library typically happens when the application's requirements expand: the team needs PDF generation alongside printing, or needs to preview, manipulate, or sign the document before printing, or the library's maintenance status or .NET runtime compatibility creates operational risk. A single library that handles both generation and printing consolidates the stack.

PDFPrinting.NET's current product status, technical approach, rendering engine, .NET version support, and install footprint should be verified in official documentation — these details are not available with sufficient confidence in widely accessible technical sources to state definitively. The migration effort is classified as Low based on the assumption that the primary use case is HTML-to-PDF generation with standard configuration options, but teams should verify the library's actual scope from official sources and the existing codebase before using this guide as a planning basis.

What PDFPrinting.NET Is Designed to Do

PDFPrinting.NET is a .NET library whose technical scope should be confirmed in official documentation. Based on its name, it likely focuses on PDF printing operations — programmatically sending PDFs to print queues — and may additionally provide HTML-to-PDF generation. The .NET support range, install footprint (NuGet package structure and any native binary dependencies), and rendering engine should all be verified before planning a migration.

If PDFPrinting.NET is primarily a print-to-PDF or print-from-PDF library, its integration model likely involves configuring printer settings, selecting a target printer (physical or virtual), specifying print parameters (copies, page range, paper size, orientation, duplex), and submitting the document to the print queue. If it also provides HTML-to-PDF generation, that portion of its API maps directly to IronPDF's ChromePdfRenderer. Confirm which capabilities are in active use in the codebase before scoping the migration.

Architectural Differences

IronPDF's two central types are ChromePdfRenderer (for HTML-to-PDF generation) and PdfDocument (for loading, manipulating, and saving PDFs). Both implement IDisposable. IronPDF also provides direct PDF printing via pdf.Print(), which sends a PdfDocument to a printer queue without requiring a separate printing library. The HTML string to PDF guide covers rendering configuration. License initialization is a one-time startup call; see the license setup guide.

If PDFPrinting.NET's primary role is HTML-to-PDF generation, the architectural shift is from its generation pipeline to IronPDF's embedded Chromium renderer — full CSS3 support, in-process rendering, PdfDocument result. If PDFPrinting.NET's primary role is submitting PDFs to print queues, IronPDF's pdf.Print() method is the functional replacement for that operation. If both are in use, a single IronPDF integration replaces both. The specific architectural comparison depends on which PDFPrinting.NET capabilities are in active use

IronPDF — HTML String to PDF

using IronPdf;

// ChromePdfRenderer is reusable — register as singleton in DI
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.PaperOrientation = IronPdf.Rendering.PdfPaperOrientation.Portrait;
renderer.RenderingOptions.MarginTop = 10;     // millimeters
renderer.RenderingOptions.MarginBottom = 10;
renderer.RenderingOptions.MarginLeft = 10;
renderer.RenderingOptions.MarginRight = 10;

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Work Order #5072</h1>
  <p>Customer: Industrial Systems Inc.</p>
  <p>Status: Approved for printing</p>
</body>
</html>";

// PdfDocument is IDisposable — always use a using block
using var pdf = renderer.RenderHtmlAsPdf(html);

byte[] pdfBytes = pdf.BinaryData;
pdf.SaveAs("work-order.pdf");

The structural change at every call site is adding a using block around PdfDocument and accessing bytes via pdf.BinaryData. Full rendering configuration is in the HTML string to PDF guide.

IronPDF — Printing

using IronPdf;
using IronPdf.Printing;

// Load the PDF to print (or render it first if generating from HTML)
using var pdf = PdfDocument.FromFile("document.pdf");

// Print with default printer and default settings (silent, no dialog)
pdf.Print();

// Or configure printing options
var printOptions = new PdfPrintOptions
{
    PrinterName = "HP LaserJet P1005",   // printer name from Windows printer list
    NumberOfCopies = 1,
    FromPage = 1,                         // 1-based in PrintOptions
    ToPage = 5,
    PaperSize = System.Drawing.Printing.PaperKind.A4
};

pdf.Print(printOptions);

IronPDF's pdf.Print() submits the document to the printer queue directly, with optional PdfPrintOptions for printer selection, page range, and copies. The PDF printing guide covers all available options. If PDFPrinting.NET is the library's sole purpose, this single method replaces the entire integration.

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 15;

// IronPDF tokens: {page} and {total-pages}
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 12,   // mm — explicit height required
    HtmlFragment = "<div style='font-size:9px; font-family:Arial; " +
                   "text-align:right; padding:0 12px;'>Work Orders Report</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 10,
    HtmlFragment = "<div style='font-size:8px; font-family:Arial; " +
                   "text-align:center;'>Page {page} of {total-pages}</div>"
};

using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><p>Document content.</p></body></html>");
pdf.SaveAs("report-with-headers.pdf");

The page number token syntax update is the highest-risk silent bug in the migration — old tokens produce literal text without any error. Find every header/footer template in the codebase before starting. The headers and footers guide covers height, dividers, and token substitution.

Generate Then Print (Combined Workflow)

A common pattern for printing libraries is: generate a PDF from a template, then immediately send it to a printer. IronPDF supports this in a single pipeline.

using IronPdf;
using IronPdf.Printing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;

string html = $@"
<!DOCTYPE html>
<html>
<body>
  <h1>Work Order #5072</h1>
  <p>Technician: J. Smith | Date: {DateTime.Today:d}</p>
  <table>
    <tr><th>Task</th><th>Status</th></tr>
    <tr><td>Replace filter</td><td>Complete</td></tr>
  </table>
</body>
</html>";

// Generate and immediately print
using var pdf = renderer.RenderHtmlAsPdf(html);

var printOptions = new PdfPrintOptions
{
    PrinterName = "FloorPrinter-2F",
    NumberOfCopies = 2
};

// Print silently — no dialog
pdf.Print(printOptions);

// Also save a copy for the archive
pdf.SaveAs($"work-orders/wo-5072-{DateTime.Today:yyyyMMdd}.pdf");

Generating and printing in the same pipeline eliminates the intermediate file that many PDFPrinting.NET integrations write to disk. The PdfDocument returned by RenderHtmlAsPdf() can be printed, saved, merged, or signed without an additional round-trip to disk.

Breaking Changes & Gotchas

  • All PDFPrinting.NET API details require codebase verification: Class names, method names, and property names are not extensively available in public documentation. Confirm every identifier from the existing application code before mapping.
  • PdfDocument is IDisposable: If PDFPrinting.NET returned byte[] directly, disposal was not required. IronPDF returns PdfDocument — every render result must be in a using block.
  • Page number token syntax: Identify PDFPrinting.NET's header/footer token syntax and update all templates to IronPDF's {page} and {total-pages}. Old tokens produce literal text without error.
  • Margin unit verification: Confirm PDFPrinting.NET's margin unit before mapping to IronPDF's millimeters. 1 inch = 25.4 mm; 1 point = 0.353 mm.
  • Print API namespace and class names: IronPDF's printing is via pdf.Print() on PdfDocument with optional PdfPrintOptions. The exact property names should be verified in IronPDF documentation — particularly page range indexing convention.
  • Namespace change: Remove PDFPrinting.NET using directives. Add using IronPdf; and using IronPdf.Printing; for print operations.
  • License key required: Set IronPdf.License.LicenseKey at application startup before any rendering or printing operation.
  • Native binary removal: If PDFPrinting.NET required native binaries, remove them from deployment artifacts. IronPDF on Windows has no native binary requirement. On Linux, Chromium system library packages are required for rendering.
  • DI registration update: Replace PDFPrinting.NET's DI registration with builder.Services.AddSingleton<ChromePdfRenderer>().

Migration Checklist

  1. Verify PDFPrinting.NET in official documentation: Confirm product status, .NET support range, technical approach, rendering engine, and full API surface. Resolve all "-" items before scoping migration effort.
  2. Audit existing codebase: List every PDFPrinting.NET call site — generation, printing, configuration, headers, footers, and DI registration.
  3. Identify page number token syntax: Find all header/footer templates. Record the token syntax in use and plan replacement.
  4. Determine primary use case: Is PDFPrinting.NET used primarily for HTML generation, printing, or both? This determines which IronPDF features are the replacements.
  5. Install IronPDF via NuGet: dotnet add package IronPdf.
  6. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs. See the license setup guide.
  7. Update namespaces: Remove PDFPrinting.NET using directives. Add using IronPdf; and using IronPdf.Printing;.
  8. Register ChromePdfRenderer in DI: Add builder.Services.AddSingleton<ChromePdfRenderer>() with RenderingOptions configured once.
  9. Replace rendering calls: Map confirmed generation calls to renderer.RenderHtmlAsPdf(html). Wrap PdfDocument in using.
  10. Replace printing calls: Map printer selection, page range, and copies to PdfPrintOptions. Replace print method call with pdf.Print(options).
  11. Update header/footer tokens: Replace PDFPrinting.NET's token syntax with {page} and {total-pages}.
  12. Remove PDFPrinting.NET NuGet reference: Once all replacements compile and pass rendering and print tests, remove the package.

Conclusion

When staying on PDFPrinting.NET is technically reasonable

Staying on PDFPrinting.NET is technically reasonable when the library is actively maintained, its .NET support covers the application's target runtime, and its feature set matches current requirements without gaps. For applications whose sole requirement is sending PDFs to print queues with a specific configuration — and where HTML generation is handled elsewhere — a focused printing library is a valid architectural choice.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when PDFPrinting.NET's maintenance status is uncertain or has lapsed; when its .NET runtime support does not cover a planned retarget; when HTML generation, form filling, digital signatures, or PDF/A output are new requirements; when CSS rendering quality is limiting template design; or when consolidating PDF generation and printing into a single library would reduce operational overhead.

What the cutover typically involves at the code level

The scope depends on whether PDFPrinting.NET is used for generation, printing, or both. For generation-only usage, the migration is an API rename exercise with using block additions and token syntax updates. For printing-only usage, the migration replaces the printing API with pdf.Print(options). For combined workflows, both replacements apply. The rendering comparison pass — validating that IronPDF's Chromium output matches PDFPrinting.NET's output across all templates — is the primary quality gate, proportional to template variety.

As you plan this migration, is PDFPrinting.NET's primary value in your stack the HTML generation, the printing control, or the combination — and if one of those responsibilities could be handled by a library already in the dependency graph, does that change the migration scope?
