Migrating from Scryber.Core to IronPDF: a practical .NET guide

a .NET engineer's reference for migrating PDF libraries

Framing

Scryber.Core reintroduces a distinctive approach to PDF generation in .NET — rather than converting HTML to PDF via a browser engine, it offers its own document model built around XML/XHTML template files (.pdfx files) with CSS-like styling. Teams that adopt Scryber typically do so for its data-binding capabilities, its ability to define reusable PDF templates as structured markup files rather than code, and its open-source MIT license. The template-driven model appeals to teams that want to separate document design from application logic, similar to how RDLC or SSRS separates report layout from data retrieval.

The conditions that drive re-evaluation of Scryber.Core center on capability gaps and the distinction between its template engine and standard web technologies. Scryber's template format is proprietary XML — it is not standard HTML, and CSS support is limited to the subset Scryber implements. Teams that want to use the same HTML/CSS skills that drive web UI development, or that want to leverage CSS frameworks like Bootstrap or Tailwind in their PDF templates, find that Scryber's template format requires maintaining a separate design language. Additionally, Scryber's scope is primarily PDF generation from templates — post-render manipulation, digital signatures, PDF/A compliance, and form filling are limited or unavailable.

This guide covers the migration from Scryber.Core to IronPDF. Scryber.Core's current product status and last release should be verified in official documentation. The migration effort is classified as Low for teams whose Scryber templates map to simple HTML equivalents — though template rewriting is the primary work item, and its scope depends on how complex the existing .pdfx templates are.

What Scryber.Core Is Designed to Do

Scryber.Core is an open-source .NET library that generates PDFs from XML/XHTML template files. Templates are structured as .pdfx files — XML documents that define pages, sections, columns, tables, images, headers, footers, and text content with styling expressed in an embedded <styles> block or external CSS-like style files. Data binding is supported through a template expression syntax that accepts data context objects, enabling dynamic document generation from model data without code-behind for layout concerns.

The library integrates into .NET applications by loading a .pdfx template, binding it to a data context (plain .NET objects, DataSets, or XML data), and calling the document's ProcessDocument() method to produce a PDF output. The rendering engine is Scryber's own — it does not use Chromium, WebKit, or any browser engine. The install footprint is the NuGet package with no native binary dependencies. Primary use cases include report generation, invoice templates, and document assembly from structured markup. The exact .NET support range, product status, and last release should be verified in official documentation.

Architectural Differences

Scryber.Core and IronPDF generate PDFs through fundamentally different mechanisms. Scryber interprets its own XML template format and renders it directly to PDF using a built-in layout engine. IronPDF renders standard HTML and CSS to PDF using embedded Chromium — any HTML that displays correctly in Chrome will render correctly in IronPDF.

IronPDF's ChromePdfRenderer generates PDFs from HTML strings, HTML files, or URLs. PdfDocument handles loading, manipulating, and saving existing PDFs. Both implement IDisposable. The migration from Scryber templates to IronPDF involves converting .pdfx template files to equivalent HTML templates — often a simplification, since standard HTML and CSS are more expressive than Scryber's XML format. The HTML string to PDF guide covers all rendering configuration. License initialization is a one-time startup call; see the license setup guide.

For teams using Scryber's data binding, the IronPDF equivalent is standard .NET string interpolation, StringBuilder, or a template engine such as Scriban, Fluid, or Razor to produce the HTML string before rendering — a pattern familiar to most .NET developers. The .pdfx template file design phase becomes standard HTML/CSS design, with the benefit that the same template can be previewed in any browser before rendering.

Operation Comparisons

Template-Driven PDF Generation

Scryber.Core — Load and Render a .pdfx Template

using Scryber.Components;
using System.IO;

// Scryber.Core renders a .pdfx XML template file to PDF
// The template defines layout in XML; data is bound via a data context

// Example .pdfx template structure (abbreviated):
// <?xml version="1.0" encoding="utf-8" ?>
// <pdf:Document xmlns:pdf="http://www.scryber.co.uk/schemas/core/release/v1/Scryber.Components.xsd"
//              xmlns:styles="http://www.scryber.co.uk/schemas/core/release/v1/Scryber.Styles.xsd"
//              xmlns:data="http://www.scryber.co.uk/schemas/core/release/v1/Scryber.Data.xsd">
//   <pdf:Pages>
//     <pdf:Section>
//       <Content>
//         <pdf:H1 text="Invoice #{{model.Id}}" />
//         <pdf:Para text="Customer: {{model.Customer}}" />
//       </Content>
//     </pdf:Section>
//   </pdf:Pages>
// </pdf:Document>

var model = new { Id = 1042, Customer = "Acme Corp", Total = 1599.00m };

// Load the template file
using var doc = PDFDocument.ParseDocument("templates/invoice.pdfx");

// Bind data context — Scryber uses a params dictionary or typed context
// Verify exact data binding API in current Scryber.Core documentation
doc.Params["model"] = model; // verify parameter binding mechanism

// Render to byte array
using var stream = new MemoryStream();
doc.ProcessDocument(stream);
byte[] pdfBytes = stream.ToArray();
File.WriteAllBytes("invoice.pdf", pdfBytes);

Concrete constraints:

  • The .pdfx template format is Scryber-specific XML — not standard HTML. Templates cannot be rendered in a browser for preview.
  • Scryber's data binding syntax ({{model.Property}}) is the library's own expression language — not Razor, Liquid, or Handlebars. It must be replaced with the chosen template engine during migration.
  • PDFDocument.ParseDocument() and ProcessDocument()
  • Scryber's rendering engine is its own — CSS support covers the subset Scryber implements, not the full CSS3 specification.

IronPDF — HTML Template Rendering

using IronPdf;

// Migration approach: convert .pdfx template to HTML, bind data with .NET tools
// The HTML template can be previewed in any browser before rendering

var model = new { Id = 1042, Customer = "Acme Corp", Total = 1599.00m };

// Option 1: String interpolation for simple templates
string html = $@"
<!DOCTYPE html>
<html>
<head>
<style>
  body {{ font-family: Arial; font-size: 11pt; margin: 0; }}
  h1 {{ color: #333; }}
  table {{ width: 100%; border-collapse: collapse; margin-top: 16px; }}
  th, td {{ border: 1px solid #ccc; padding: 6px 10px; }}
  th {{ background: #f5f5f5; }}
</style>
</head>
<body>
  <h1>Invoice #{model.Id}</h1>
  <p>Customer: {model.Customer}</p>
  <p>Total: {model.Total:C}</p>
</body>
</html>";

// Option 2: Use Scriban, Fluid, or Razor for complex templates with loops/conditionals
// var template = Template.Parse(File.ReadAllText("templates/invoice.html"));
// string html = template.Render(model);

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;

// PdfDocument is IDisposable
using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("invoice.pdf");

Converting Scryber templates to HTML is the primary migration work item. The HTML equivalent is typically more concise — standard <table>, <div>, and CSS accomplish what Scryber's component elements express in more verbose XML. The resulting HTML can be verified in a browser before rendering. Full rendering configuration is in the HTML string to PDF guide.

Data Binding for Dynamic Documents

Scryber.Core — Data Binding

using Scryber.Components;
using System.Collections.Generic;

// Scryber data binding
// Scryber supports binding to plain objects, DataSets, and XML data

var invoiceData = new
{
    Id = 1042,
    Customer = "Acme Corp",
    Lines = new List<object>
    {
        new { Description = "Widget A", Qty = 10, Price = 99.99m },
        new { Description = "Widget B", Qty = 5,  Price = 249.99m }
    },
    Total = 2249.85m
};

using var doc = PDFDocument.ParseDocument("templates/invoice-lines.pdfx");
doc.Params["invoice"] = invoiceData; // verify binding mechanism

// .pdfx template would iterate lines using Scryber's data repeat component:
// <data:ForEach value="{{invoice.Lines}}" >
//   <pdf:TableRow>
//     <pdf:TableCell><pdf:Label text="{{current().Description}}" /></pdf:TableCell>
//     ...
//   </pdf:TableRow>
// </data:ForEach>

using var stream = new System.IO.MemoryStream();
doc.ProcessDocument(stream);

Concrete constraints:

  • Scryber's <data:ForEach> and expression syntax are the library's own template language. These must be replaced with equivalent iteration in the HTML template engine of choice.
  • Verify the parameter binding mechanism in current Scryber.Core documentation — the API for attaching data contexts has varied across versions.

IronPDF — Data Binding via Template Engine

using IronPdf;
using System.Collections.Generic;
// Using Scriban as the template engine — or Fluid, Handlebars, etc.
// using Scriban; // if using Scriban NuGet package

var invoiceData = new
{
    Id = 1042,
    Customer = "Acme Corp",
    Lines = new List<dynamic>
    {
        new { Description = "Widget A", Qty = 10, Price = 99.99m },
        new { Description = "Widget B", Qty = 5,  Price = 249.99m }
    },
    Total = 2249.85m
};

// HTML template with iteration (using C# interpolation with StringBuilder,
// or a template engine for production use)
var linesHtml = new System.Text.StringBuilder();
foreach (dynamic line in invoiceData.Lines)
{
    linesHtml.Append($@"
      <tr>
        <td>{line.Description}</td>
        <td style='text-align:right'>{line.Qty}</td>
        <td style='text-align:right'>{line.Price:C}</td>
      </tr>");
}

string html = $@"
<!DOCTYPE html>
<html>
<head>
<style>
  body {{ font-family: Arial; font-size: 11pt; }}
  table {{ width: 100%; border-collapse: collapse; }}
  th, td {{ border: 1px solid #ccc; padding: 6px 10px; }}
  th {{ background: #f0f0f0; font-weight: bold; }}
  .total {{ font-weight: bold; text-align: right; margin-top: 10px; }}
</style>
</head>
<body>
  <h1>Invoice #{invoiceData.Id}</h1>
  <p>Customer: {invoiceData.Customer}</p>
  <table>
    <thead>
      <tr><th>Description</th><th>Qty</th><th>Price</th></tr>
    </thead>
    <tbody>{linesHtml}</tbody>
  </table>
  <p class='total'>Total: {invoiceData.Total:C}</p>
</body>
</html>";

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("invoice-lines.pdf");

Scryber's <data:ForEach> and template expressions are replaced by standard .NET iteration and string construction — patterns familiar to any .NET developer. For complex templates, a dedicated template engine like Scriban or Fluid handles conditionals, loops, and formatting more cleanly than StringBuilder. The resulting HTML is also directly previewable in a browser. The page breaks guide covers controlling page breaks within generated content.

Headers, Footers, and Page Numbers

Scryber.Core — Headers and Footers

// Scryber.Core headers and footers are defined in the .pdfx template XML:
//
// <pdf:Section>
//   <pdf:Header>
//     <pdf:Label text="Invoice Report" />
//   </pdf:Header>
//   <pdf:Footer>
//     <pdf:Label text="Page {{model.PageIndex}} of {{model.PageCount}}" />
//   </pdf:Footer>
//   <Content>
//     ...
//   </Content>
// </pdf:Section>
//
// Verify exact element and expression names in current Scryber.Core docs.
// Scryber handles page number insertion through its own binding expressions.

Concrete constraints:

  • Scryber's header/footer elements (<pdf:Header>, <pdf:Footer>) are XML blocks in the template. These convert to HtmlHeaderFooter.HtmlFragment strings in IronPDF.
  • Scryber's page number binding expression syntax is its own — replace with IronPDF's {page} and {total-pages}.

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 15;

renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 12,
    HtmlFragment = "<div style='font-size:9px; font-family:Arial; " +
                   "text-align:right; padding:0 12px;'>Invoice Report</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 10,
    HtmlFragment = "<div style='font-size:8px; font-family:Arial; " +
                   "text-align:center;'>Page {page} of {total-pages}</div>"
};

using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><p>Invoice content here.</p></body></html>");
pdf.SaveAs("invoice-with-headers.pdf");

Scryber's <pdf:Header> and <pdf:Footer> XML blocks become HtmlHeaderFooter.HtmlFragment strings with IronPDF's {page} / {total-pages} tokens. The headers and footers guide covers height, divider lines, and token options.

Multi-Page Documents with Page Breaks

Scryber.Core — Page Breaks

// Scryber.Core — page breaks via XML section elements
// Scryber sections typically map to individual pages or column spans
//
// <pdf:Section style:page-break-after='Always'>
//   <Content>
//     <pdf:H2 text="Section One" />
//   </Content>
// </pdf:Section>
// <pdf:Section>
//   <Content>
//     <pdf:H2 text="Section Two" />
//   </Content>
// </pdf:Section>
//
// Verify exact style property names in current Scryber.Core documentation.

IronPDF — Page Breaks via CSS

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;

// CSS page-break-* properties control page breaks in Chromium rendering
string html = @"
<!DOCTYPE html>
<html>
<head>
<style>
  .section { page-break-after: always; }
  .section:last-child { page-break-after: avoid; }
</style>
</head>
<body>
  <div class='section'>
    <h2>Section One</h2>
    <p>Content for section one.</p>
  </div>
  <div class='section'>
    <h2>Section Two</h2>
    <p>Content for section two.</p>
  </div>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("multi-section.pdf");

Scryber's explicit <pdf:Section> page break elements are replaced by standard CSS page-break-after: always on wrapping <div> elements. The page breaks guide covers all supported CSS page-break properties.

Breaking Changes & Gotchas

  • Template format change is the primary work item: Scryber's .pdfx XML format has no direct equivalent in IronPDF. Every template must be rewritten as HTML + CSS. The effort scales with template complexity — simple layouts convert quickly, complex multi-column and data-heavy templates require more work.
  • Data binding engine changes: Scryber's {{expression}} template language is replaced by the .NET template engine of choice (string interpolation, Scriban, Fluid, Razor, or similar). Plan for this as a deliberate technology selection, not just a syntax rename.
  • Browser-previewable templates: After migration, HTML templates can be previewed and debugged in any browser — a significant improvement in template development workflow over .pdfx files.
  • Column layout differences: Scryber has explicit multi-column layout components (<pdf:Column>). HTML CSS multi-column (column-count, column-gap) or Flexbox replaces this
  • Page break model changes: Scryber's section-based page breaks are replaced by CSS page-break-* properties.
  • PdfDocument is IDisposable: IronPDF returns PdfDocument from render operations — wrap in using blocks.
  • Namespace change: Remove using Scryber.Components; and related namespaces. Replace with using IronPdf;.
  • License key required: Scryber.Core is MIT-licensed. IronPDF requires IronPdf.License.LicenseKey at startup.
  • No native binary dependencies (both): Scryber has no native binary requirements. IronPDF on Windows also has none. On Linux, IronPDF requires Chromium system library packages.
  • Rendering fidelity comparison required: Chromium's rendering is full CSS3. Previous Scryber templates may need CSS updates to take advantage of Flexbox or modern layout features.

Migration Checklist

  1. Inventory all .pdfx templates: List every template file in use, its data bindings, component types, columns, headers, footers, and page break strategy. This defines the template rewriting scope.
  2. Choose a .NET template engine: Select the HTML template engine for data binding (string interpolation for simple cases, Scriban, Fluid, or Razor for complex iteration and conditionals).
  3. Convert .pdfx templates to HTML: Rewrite each template as an HTML file with a <style> block. Verify output in a browser before rendering with IronPDF.
  4. Install IronPDF via NuGet: dotnet add package IronPdf.
  5. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs. See the license setup guide.
  6. Update namespaces: Remove Scryber using directives. Add using IronPdf;.
  7. Register ChromePdfRenderer in DI: Add builder.Services.AddSingleton<ChromePdfRenderer>() with RenderingOptions configured once.
  8. Replace ProcessDocument() calls: For each template, replace PDFDocument.ParseDocument() + data bind + ProcessDocument() with: template engine renders HTML string → renderer.RenderHtmlAsPdf(html). Wrap PdfDocument in using.
  9. Replace headers and footers: Convert Scryber <pdf:Header> / <pdf:Footer> blocks to HtmlHeaderFooter.HtmlFragment. Update page number tokens to {page} / {total-pages}.
  10. Replace column and section layout: Convert Scryber's column and section components to CSS multi-column or Flexbox.
  11. Visual rendering comparison: Render every document type with IronPDF and compare against Scryber output. Adjust CSS as needed.
  12. Remove Scryber NuGet packages: Once all templates are converted and rendering tests pass, remove Scryber.Core and related packages.

Conclusion

When staying on Scryber.Core is technically reasonable

Scryber.Core is technically reasonable when the team has invested significantly in .pdfx template design, when the template-first approach of defining PDF structure in XML is a deliberate architectural preference, and when the current CSS support level meets all document requirements without workarounds. Teams using Scryber for straightforward templated documents with stable layouts and no requirement for advanced CSS or post-render manipulation have the least pressure to migrate.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when CSS limitations in Scryber's rendering engine are constraining template design; when the team wants to reuse web UI CSS skills and frameworks for PDF templates; when templates need to support modern CSS features (Flexbox, Grid, CSS variables); when post-render operations (digital signatures, form filling, merge, PDF/A) are new requirements; or when preview and debugging of templates in a browser would improve the template development workflow.

What the cutover typically involves at the code level

The .pdfx template conversion is the primary work item — each template is rewritten as HTML and verified in a browser before testing with IronPDF. The code-level changes (replacing ProcessDocument() with RenderHtmlAsPdf(), updating data binding to use a .NET template engine) are straightforward once the templates are ready. The template quality gate — browser preview pass, then IronPDF rendering comparison — is the most time-proportional step.

As you review your existing .pdfx templates, how many rely on Scryber-specific layout components versus simple table and text layouts that would convert to HTML with minimal effort — and does that ratio give you a clearer picture of the migration timeline?
