Migrating from wkhtmltopdf to IronPDF: a .NET team's field guide

a step-by-step .NET migration guide for 2026

Framing

wkhtmltopdf has been one of the most widely adopted HTML-to-PDF tools in server-side .NET pipelines for over a decade. Its appeal was straightforward: a single binary that accepted HTML or URLs and produced PDF output via the command line, backed by a WebKit engine that produced reasonable output for the HTML of its era. Wrapper libraries like Pechkin, TuesPechkin, DinkToPdf, and Rotativa emerged to give .NET developers a managed API surface over the CLI, and those wrappers became embedded in thousands of ASP.NET applications.

The migration question became urgent in stages. wkhtmltopdf reached end-of-life status — the project is discontinued and no longer receiving maintenance, security patches, or WebKit updates. The rendering engine it embeds is frozen at a version of WebKit that predates modern CSS specifications. Teams that invested in CSS Grid layouts, CSS Variables, web fonts from Google Fonts, or JavaScript-rendered content discovered that wkhtmltopdf silently produced incomplete or incorrect output for those templates. The combination of a frozen, unpatched binary and CSS capability gaps creates both security risk and functional limitation that accumulate over time.

For .NET teams running wkhtmltopdf through wrapper libraries, the migration surface is well-defined: the wrapper is replaced by a managed library, CLI arguments become API properties, and the rendering engine shifts from frozen WebKit to current Chromium. This guide maps that transition in technical detail, covering what changes in the code, what requires attention in the deployment environment, and where teams typically concentrate migration effort.

What wkhtmltopdf Is Designed to Do

wkhtmltopdf is a command-line utility that converts HTML files and URLs to PDF using a headless WebKit rendering engine. The binary accepts a source (HTML file path, URL, or stdin) and an output destination (file path or stdout), along with a large set of CLI flags covering paper size, margins, orientation, headers, footers, table of contents, JavaScript execution, and output quality settings. A companion tool, wkhtmltoimage, provides HTML-to-image conversion.

In .NET applications, wkhtmltopdf is almost always accessed through a managed wrapper library rather than directly. DinkToPdf wraps the libwkhtmltox shared library via P/Invoke and exposes a managed API with settings classes. Rotativa wraps the binary via process invocation and integrates with ASP.NET MVC's ActionResult model. TuesPechkin (and its predecessor Pechkin) provided an earlier COM-based wrapper. Each wrapper translates .NET configuration objects into the appropriate CLI arguments or P/Invoke calls. The underlying rendering engine is WebKit, not Chromium — the distinction matters for CSS compatibility, as wkhtmltopdf's WebKit version does not support modern CSS specifications such as CSS Grid, Flexbox, or CSS Variables. JavaScript execution is nominally supported but limited and unreliable for complex scripts.

Architectural Differences

IronPDF is a managed .NET library that embeds a Chromium rendering engine. There is no external binary to install, no P/Invoke layer, and no wrapper library intermediary. The ChromePdfRenderer class accepts HTML strings, file paths, and URLs directly and returns a PdfDocument that implements standard .NET IDisposable. All rendering configuration passes through typed ChromePdfRenderOptions properties rather than CLI argument strings.

The rendering engine difference is the most consequential architectural change. IronPDF's Chromium-based pipeline renders HTML and CSS with full support for Grid, Flexbox, CSS Variables, web fonts, SVG, and JavaScript execution — features that wkhtmltopdf's frozen WebKit handles poorly or not at all. Templates that required layout workarounds for wkhtmltopdf's CSS limitations can be simplified after migration. The Chromium binary is bundled with or downloaded by IronPDF during initialization; on Linux, system dependencies for Chromium must be present, which replaces the wkhtmltopdf binary installation step in deployment scripts.

Post-generation document operations — merging, splitting, password protection, digital signatures, watermarking, PDF/A compliance — are available in the same IronPDF package that handles rendering. Teams currently using a secondary library alongside wkhtmltopdf for these operations may be able to consolidate to a single dependency. The merge and split documentation and the rest of IronPDF's API are accessible on a single PdfDocument object without serializing to disk between steps. License initialization is a static call at startup; see the license key configuration guide for key formats and environment-variable patterns.

Operation Comparisons

HTML String to PDF (DinkToPdf Pattern)

wkhtmltopdf / DinkToPdf — HTML String to PDF

DinkToPdf wraps libwkhtmltox via P/Invoke and is one of the most common managed wrappers for wkhtmltopdf in ASP.NET Core applications. A HtmlToPdfDocument object is constructed with GlobalSettings and ObjectSettings, and passed to the IConverter service.

using DinkToPdf;
using DinkToPdf.Contracts;
using System;

// DinkToPdf is typically registered as a singleton via DI in Startup / Program.cs
// services.AddSingleton(typeof(IConverter), new SynchronizedConverter(new PdfTools()));

public class PdfService
{
    private readonly IConverter _converter;

    public PdfService(IConverter converter)
    {
        _converter = converter;
    }

    public byte[] ConvertHtmlToPdf(string htmlContent)
    {
        var document = new HtmlToPdfDocument
        {
            GlobalSettings =
            {
                ColorMode   = ColorMode.Color,
                Orientation = Orientation.Portrait,
                PaperSize   = PaperKind.A4,
                Margins     = new MarginSettings
                {
                    Top    = 10,
                    Bottom = 10,
                    Left   = 10,
                    Right  = 10,
                    Unit   = Unit.Millimeters
                }
            },
            Objects =
            {
                new ObjectSettings
                {
                    PagesCount          = true,
                    HtmlContent         = htmlContent,
                    WebSettings         = { DefaultEncoding = "utf-8" },
                    HeaderSettings      = { FontSize = 9, Right = "Page [page] of [topage]" },
                    FooterSettings      = { FontSize = 9, Center = "Confidential" }
                }
            }
        };

        return _converter.Convert(document);
    }
}

Key constraints:

  • SynchronizedConverter uses a lock to serialize rendering; concurrency requires careful DI lifetime management
  • libwkhtmltox native binary must be present and architecture-matched (x64/x86/ARM) at application startup
  • WebKit engine does not support CSS Grid, Flexbox, or CSS Variables; templates must use workarounds
  • JavaScript execution is unreliable for scripts that perform async operations or DOM manipulation after load
  • Linux Docker deployments require the correct native binary and may require additional system library dependencies
  • [page] and [topage] header/footer tokens are specific to wkhtmltopdf's format

IronPDF — HTML String to PDF

IronPDF registers ChromePdfRenderer as a scoped or transient service (not singleton, as renderer instances should not be shared across threads). The HTML string to PDF guide covers the full options set, and the rendering options documentation details all configuration properties.

using IronPdf;

// IronPdf.License.LicenseKey = "YOUR-LICENSE-KEY"; // Set once at application startup

public class PdfService
{
    public byte[] ConvertHtmlToPdf(string htmlContent)
    {
        // Create a renderer per call or per scope — do not share across threads
        using var renderer = new ChromePdfRenderer();

        // Configure rendering options — equivalent to DinkToPdf's GlobalSettings + ObjectSettings
        renderer.RenderingOptions.PaperSize       = IronPdf.Rendering.PdfPaperSize.A4;
        renderer.RenderingOptions.PaperOrientation = IronPdf.Rendering.PdfPaperOrientation.Portrait;
        renderer.RenderingOptions.MarginTop        = 10;
        renderer.RenderingOptions.MarginBottom     = 10;
        renderer.RenderingOptions.MarginLeft       = 10;
        renderer.RenderingOptions.MarginRight      = 10;
        renderer.RenderingOptions.PrintBackground  = true;

        // HTML header/footer — replaces DinkToPdf's HeaderSettings / FooterSettings
        renderer.RenderingOptions.TextFooter = new TextHeaderFooter
        {
            CenterText = "Confidential",
            RightText  = "Page {page} of {total-pages}",  // note: {page}, not [page]
            FontSize   = 9
        };

        // Render HTML string — Chromium engine; CSS Grid, Flexbox, web fonts all supported
        using var pdf = renderer.RenderHtmlAsPdf(htmlContent);

        return pdf.BinaryData;
    }
}

The {page} and {total-pages} token format replaces wkhtmltopdf's [page] and [topage]. ChromePdfRenderer implements IDisposable; using a using block per call is the correct lifetime pattern in a DI context.

URL to PDF

wkhtmltopdf / DinkToPdf — URL to PDF

DinkToPdf renders URLs by setting ObjectSettings.Page to the target URL rather than providing HTML content directly.

using DinkToPdf;
using DinkToPdf.Contracts;

public byte[] ConvertUrlToPdf(string url, IConverter converter)
{
    var document = new HtmlToPdfDocument
    {
        GlobalSettings =
        {
            PaperSize   = PaperKind.A4,
            Orientation = Orientation.Portrait
        },
        Objects =
        {
            new ObjectSettings
            {
                Page       = url,    // URL instead of HtmlContent
                LoadSettings =
                {
                    // JavaScript delay in milliseconds — unreliable for complex pages
                    JSDelay = 200
                }
            }
        }
    };

    return converter.Convert(document);
}

Key constraints:

  • JSDelay (a fixed wait in ms) is the only JavaScript wait mechanism; it is fragile for pages with variable load times
  • Authenticated pages require cookie strings passed through LoadSettings.CustomHeaders — format is manual
  • CSS Grid and modern layout features do not render correctly; JS-heavy pages may produce empty sections
  • HTTPS certificates with non-standard CAs may require additional LoadSettings configuration

IronPDF — URL to PDF

IronPDF's RenderUrlAsPdf() navigates to the URL in Chromium and applies a declarative wait condition before capturing. The URL to PDF guide covers authentication, custom headers, and wait strategy options.

using IronPdf;
using System.Collections.Generic;

public byte[] ConvertUrlToPdf(string url)
{
    using var renderer = new ChromePdfRenderer();

    // Declarative wait — replaces JSDelay with an intent-based condition
    renderer.RenderingOptions.WaitFor.NetworkIdle(500);  // verify WaitFor API in current docs

    // Cookie injection for authenticated pages — replaces manual header string construction
    renderer.RenderingOptions.CustomCookies = new Dictionary<string, string>
    {
        { "session", "your-session-token" }
    };

    using var pdf = renderer.RenderUrlAsPdf(url);

    return pdf.BinaryData;
}

The WaitFor.NetworkIdle() condition waits for network activity to settle before capturing — a more reliable signal than a fixed millisecond delay. Verify the exact WaitFor API method names and parameters in current IronPDF documentation.

Headers and Footers (Rotativa Pattern)

wkhtmltopdf / Rotativa — Headers and Footers

Rotativa integrates with ASP.NET MVC by returning ViewAsPdf, PartialViewAsPdf, and ActionAsPdf action results. Header and footer content is specified via URL (a controller action that returns the header HTML) or via wkhtmltopdf's --header-html / --footer-html flags.

using Rotativa.AspNetCore;
using Microsoft.AspNetCore.Mvc;

public class ReportsController : Controller
{
    public IActionResult DownloadReport(int reportId)
    {
        // Rotativa renders a Razor view as PDF via wkhtmltopdf
        return new ViewAsPdf("ReportView", reportId)
        {
            PageSize        = Rotativa.AspNetCore.Options.Size.A4,
            PageOrientation = Rotativa.AspNetCore.Options.Orientation.Portrait,
            PageMargins     = new Rotativa.AspNetCore.Options.Margins(10, 10, 10, 10),
            // Header via a URL to another controller action
            CustomSwitches  = "--header-url https://example.com/pdf-header --header-spacing 5"
        };
    }
}

Key constraints:

  • Header URL must be accessible from the wkhtmltopdf process context; localhost URLs require special handling
  • Header rendering makes a second HTTP request; authentication context may not carry over
  • CustomSwitches is a raw CLI string — no type safety, changes between wkhtmltopdf versions may silently break
  • Rotativa is tightly coupled to MVC's action result model; non-controller usage requires different patterns

IronPDF — Razor View to PDF with Headers

IronPDF renders Razor views by first rendering the view to an HTML string and then calling RenderHtmlAsPdf(). The HTML string to PDF guide and the headers and footers guide cover this pattern in detail.

using IronPdf;
using Microsoft.AspNetCore.Mvc;
using Microsoft.AspNetCore.Mvc.Rendering;
using Microsoft.AspNetCore.Mvc.ViewEngines;

// This example renders a Razor view to HTML string, then to PDF with a typed header
// Inject ICompositeViewEngine and ITempDataProvider via DI as needed
public async Task<IActionResult> DownloadReport(int reportId, [FromServices] ICompositeViewEngine viewEngine)
{
    // Render the Razor view to an HTML string (standard ASP.NET Core technique)
    var viewResult = viewEngine.FindView(ControllerContext, "ReportView", false);
    await using var writer = new System.IO.StringWriter();
    var viewContext = new ViewContext(
        ControllerContext,
        viewResult.View,
        ViewData,
        TempData,
        writer,
        new HtmlHelperOptions()
    );
    await viewResult.View.RenderAsync(viewContext);
    string html = writer.ToString();

    // Render HTML to PDF with a typed HTML header — no separate HTTP request required
    using var renderer = new ChromePdfRenderer();
    renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
    {
        Height          = 15,
        HtmlFragment    = "<div style='font-size:9px; padding:0 10px;'>Company Report — Confidential</div>",
        DrawDividerLine = true
    };

    using var pdf = renderer.RenderHtmlAsPdf(html);

    return File(pdf.BinaryData, "application/pdf", $"report-{reportId}.pdf");
}

The header is defined in C# as an HtmlHeaderFooter object — no separate HTTP request, no CustomSwitches string. The Razor-to-HTML rendering step is standard ASP.NET Core and is independent of the PDF library.

Merge PDFs

wkhtmltopdf — Merge PDFs

wkhtmltopdf does not natively merge independently generated PDFs. The multi-page mode combines multiple HTML sources into a single PDF render pass, but merging pre-existing PDF files requires a separate library. In DinkToPdf workflows, teams typically use a second library (PDFsharp, iTextSharp) for post-generation merge operations.

Key constraints:

  • Multiple HTML sources in a single render pass share the same page count and header/footer context — useful but not equivalent to merging independently generated PDFs
  • Merging pre-existing PDFs (from different sources or generators) requires a second dependency
  • Two-library architecture creates separate disposal models and version management concerns

IronPDF — Merge PDFs

IronPDF's PdfDocument.Merge() combines any set of PdfDocument instances — rendered or loaded from disk — into a single document. The merge and split guide covers ordering, page handling, and large-document considerations.

using IronPdf;
using System.Collections.Generic;

// Render multiple HTML sections as separate PDFs
using var renderer = new ChromePdfRenderer();
using var coverPage = renderer.RenderHtmlAsPdf("<h1>Q4 Report</h1>");
using var bodyPages = renderer.RenderHtmlFileAsPdf("/input/q4-body.html");
using var appendix  = PdfDocument.FromFile("/input/appendix-pregenerated.pdf");

// Merge into a single document — no second library required
using var merged = PdfDocument.Merge(new List<PdfDocument> { coverPage, bodyPages, appendix });

// Save or return bytes
merged.SaveAs("/output/q4-report-complete.pdf");

The merged document is a new PdfDocument instance with its own lifecycle. Input documents remain valid after the merge call and are disposed independently by their own using blocks.

Breaking Changes & Gotchas

  • Discontinued binary — security risk. wkhtmltopdf is discontinued. The embedded WebKit receives no security patches. Any vulnerability discovered in the WebKit version shipped with wkhtmltopdf will remain unpatched indefinitely. This is the primary migration driver for most teams.
  • Header/footer token syntax change. wkhtmltopdf uses [page], [topage], [date], and [time]. IronPDF uses {page}, {total-pages}, {date}. Every header and footer template must be updated with the new token format.
  • DI lifetime change. DinkToPdf's SynchronizedConverter is registered as a singleton. IronPDF's ChromePdfRenderer should be transient or scoped — one instance per request or per thread. Sharing a renderer instance across concurrent requests is not the recommended pattern. Update DI registrations accordingly.
  • Native binary and P/Invoke removal. DinkToPdf's P/Invoke setup requires the libwkhtmltox native binary on the host, matched to the OS and architecture. This setup code and binary distribution requirement is removed entirely. Deployment scripts that copy or install libwkhtmltox should be updated.
  • Wrapper library removal. DinkToPdf, Rotativa, TuesPechkin, and similar wrapper packages are removed from the NuGet dependency tree. The IronPDF NuGet package replaces them all.
  • Namespace change. All DinkToPdf, Rotativa.AspNetCore, and related namespaces are removed. IronPDF types live under IronPdf. Update all using directives.
  • ViewAsPdf replacement. Rotativa's ViewAsPdf action result has no direct IronPDF equivalent. The Razor view must be rendered to an HTML string first (using standard ASP.NET Core view rendering), then passed to RenderHtmlAsPdf(). This is a two-step approach but separates concerns cleanly.
  • CSS rendering improvements — template review required. Modern CSS features now work. Templates that contain workarounds for wkhtmltopdf's CSS Grid or Flexbox limitations may produce different (improved) layouts. Verify all templates after migration and remove workarounds that are no longer needed.
  • JavaScript reliability change. wkhtmltopdf's JSDelay is a fixed wait; pages with variable load times produce inconsistent results. IronPDF's WaitFor API uses declarative conditions. Templates that worked around wkhtmltopdf's JavaScript limitations may now need WaitFor conditions added to handle content that previously was not being captured.
  • Linux Chromium dependencies. The wkhtmltopdf binary has its own system library dependencies on Linux. IronPDF requires Chromium system libraries, which are different in scope. Update Dockerfiles and provisioning scripts.
  • License initialization. IronPDF requires a license key set at startup. wkhtmltopdf has no license management. Add initialization code and manage the key as an environment secret.

Migration Checklist

  1. Audit all wkhtmltopdf call sites. Search for IConverter, HtmlToPdfDocument, ViewAsPdf, PartialViewAsPdf, and TuesPechkin usage. Document each call site's input type (HTML string, URL, Razor view), settings configured, and output handling.
  2. Map DinkToPdf / Rotativa settings to ChromePdfRenderOptions. For each call site, list every GlobalSettings, ObjectSettings, HeaderSettings, FooterSettings, and CustomSwitches value used. Identify the corresponding RenderingOptions property. Pay attention to margin units and paper size enum equivalents.
  3. Remove wrapper NuGet packages. Uninstall DinkToPdf, Rotativa.AspNetCore, TuesPechkin, and any related packages. Remove libwkhtmltox binary references from the project.
  4. Add the IronPDF NuGet package. dotnet add package IronPdf. For Linux container targets, add Chromium dependency installation steps to the Dockerfile.
  5. Configure the license key. Add IronPdf.License.LicenseKey = "YOUR-KEY"; to Program.cs or application startup. Store the key as an environment variable or secrets manager entry. See the license key guide.
  6. Update DI registration. Remove SynchronizedConverter singleton registration. Register ChromePdfRenderer as transient if using DI, or instantiate per call with a using block. Do not register as singleton.
  7. Replace HTML / URL render calls. Substitute converter.Convert(document) with renderer.RenderHtmlAsPdf(html) or renderer.RenderUrlAsPdf(url). Update all namespace imports to using IronPdf;.
  8. Translate headers and footers. Replace HeaderSettings and FooterSettings structs with TextHeaderFooter or HtmlHeaderFooter objects. Update all token references: [page] → {page}, [topage] → {total-pages}, [date] → {date}.
  9. Replace Rotativa ViewAsPdf actions. Render the Razor view to an HTML string using ICompositeViewEngine, then call renderer.RenderHtmlAsPdf(html) and return as File(pdf.BinaryData, "application/pdf", "filename.pdf").
  10. Add disposal patterns. Wrap all ChromePdfRenderer and PdfDocument instances in using blocks. Audit exception handling paths to ensure disposal under failure conditions.
  11. Review HTML templates. After migration, test all templates and remove CSS workarounds that were added for wkhtmltopdf's layout engine limitations. CSS Grid, Flexbox, and web fonts now work without workarounds.
  12. Remove binary deployment steps. Update Dockerfiles and deployment scripts to remove wkhtmltopdf binary installation. Add IronPDF Chromium dependency installation for Linux targets. Run a full rendering test in the container image before promoting.

Conclusion

When staying on wkhtmltopdf is technically reasonable: It is not, as a general position. wkhtmltopdf is discontinued, the embedded WebKit receives no security patches, and the CSS compatibility gaps with modern web standards are persistent and unfixable within the library. For applications that are stable, have no security requirements, generate only simple text-heavy documents with no modern CSS, and have no planned platform changes, the practical risk of staying may be low in the short term. But the risk compounds over time with no path to remediation.

Signals that indicate migration is worth prioritizing: Any security audit that flags unmaintained dependencies is an immediate signal. CSS rendering failures on templates that use Grid, Flexbox, or web fonts are a functional signal. Container platform migrations that surface the binary architecture-matching problem (x86/x64/ARM) are an operational signal. Teams that are actively working around wkhtmltopdf's JavaScript limitation with JSDelay tuning are paying an ongoing maintenance cost that migration eliminates.

What the cutover typically involves at the code level: The DinkToPdf path is the most mechanical to migrate — IConverter.Convert() becomes renderer.RenderHtmlAsPdf(), settings objects map property-by-property, and token syntax is updated. Rotativa requires slightly more work because ViewAsPdf has no equivalent action result, and Razor view rendering must be explicit. The HTML string to PDF guide covers both paths. Template review after migration is the non-mechanical work: CSS improvements mean layout changes that require validation, not just a code change.
