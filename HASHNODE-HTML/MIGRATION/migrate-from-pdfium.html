Migrating from Pdfium to IronPDF: a .NET production guide

what the docs do not cover when switching PDF libraries

Framing

PDFium is Google's open-source PDF rendering engine — the same engine embedded inside Chromium, Chrome, and several other PDF readers. In .NET applications, PDFium surfaces through a collection of community-maintained NuGet wrappers: PdfiumViewer, Docnet.Core, PDFiumSharp, and others. Teams that integrate PDFium into .NET applications are typically doing so for one of its specific strengths: rendering PDF pages to high-quality images at configurable DPI, extracting text with reasonable fidelity, or embedding a PDF viewing surface in a WinForms or WPF application.

PDFium is not an HTML-to-PDF generator. It reads and renders existing PDF content — it does not produce PDFs from HTML, CSS, or URLs. This distinction shapes the migration story entirely. Teams using PDFium purely for PDF-to-image rasterization, text extraction, and document reading are evaluating a move to a library with a higher-level managed .NET API and a broader manipulation surface. Teams that also need HTML-to-PDF generation — and are currently using PDFium alongside a separate HTML generator — can consolidate both into a single library.

The native binary management concern drives a significant share of PDFium re-evaluations. PDFium wrappers require platform-specific native binaries (Windows x64, Linux, macOS) to be deployed alongside the .NET application. Managing multi-platform binary packages, verifying binary integrity, and handling platform detection in the deployment pipeline adds operational overhead. This guide covers the migration from PDFium-based .NET integrations to IronPDF, with Medium effort reflecting the need to remap a native-interop API to a managed-code API across potentially complex PDF reading and rasterization workflows.

What Pdfium Is Designed to Do

PDFium is a C++ PDF rendering library originally developed by Foxit and open-sourced by Google in 2014. It serves as the PDF engine inside the Chromium browser. In its .NET form, PDFium is accessed through wrapper packages rather than a first-party .NET SDK — the most common are PdfiumViewer (WinForms viewer + rasterization), Docnet.Core (cross-platform .NET Standard wrapper), and PDFiumSharp (another managed wrapper). Each wrapper exposes a different API surface over the same underlying native library.

PDFium's core capabilities in .NET are: loading and parsing PDF documents, rendering individual pages to bitmaps at configurable DPI, extracting text content, reading document metadata and page dimensions, and displaying PDFs in a WinForms viewer control (via PdfiumViewer specifically). PDFium does not render HTML to PDF — it has no HTML parser, CSS engine, or JavaScript runtime. The install footprint includes managed NuGet wrapper packages plus platform-specific native binary packages for each deployment target. The exact .NET support range depends on the wrapper library chosen

Architectural Differences

PDFium wrappers and IronPDF approach the PDF problem space from complementary angles. PDFium reads and renders existing PDF content; IronPDF both generates new PDFs from HTML/CSS and manipulates existing ones. For the subset of operations that both cover — loading PDFs, rasterizing pages, extracting text — the IronPDF API is a fully managed .NET replacement with no P/Invoke boundary.

IronPDF's two central types are ChromePdfRenderer (for HTML-to-PDF generation) and PdfDocument (for loading, manipulating, and saving existing PDFs). Both implement IDisposable. For text extraction, pdf.ExtractAllText() and pdf.ExtractTextFromPage(n) replace the PDFium wrapper's text extraction API. For rasterization, pdf.RasterizeToImageFiles() replaces the page-to-bitmap pipeline. The PDF to image guide covers DPI settings and format options. License initialization is a one-time startup call; see the license setup guide.

The critical architectural improvement is removing the native binary dependency entirely on Windows. IronPDF on Windows is a fully managed library — no native binaries to package or manage. On Linux, IronPDF requires Chromium system library packages, which is a different but comparable native dependency footprint. The WinForms viewer component from PdfiumViewer has no direct equivalent in IronPDF's server-side rendering focus — if an embedded viewer is in use, this requires separate evaluation.

Operation Comparisons

Rendering a PDF Page to Image (Rasterization)

PDFium (Docnet.Core) — Page to Image

using Docnet.Core;
using Docnet.Core.Models;
using System.Drawing;
using System.Drawing.Imaging;
using System.IO;

// Docnet.Core wraps PDFium for cross-platform .NET usage
// DocLib is the main entry point and must be disposed
using var library = DocLib.Instance;
using var docReader = library.GetDocReader(
    "source.pdf",
    new PageDimensions(1080, 1920)); // max dimensions for scaling

// Page readers are created per-page and must be disposed
using var pageReader = docReader.GetPageReader(0); // 0-based page index

int pageWidth  = pageReader.GetPageWidth();
int pageHeight = pageReader.GetPageHeight();

// GetImage() returns raw BGRA byte array — no encoded format
byte[] rawBytes = pageReader.GetImage();

// Construct a Bitmap from the BGRA bytes manually
using var bmp = new Bitmap(pageWidth, pageHeight, PixelFormat.Format32bppArgb);
var bitmapData = bmp.LockBits(
    new Rectangle(0, 0, pageWidth, pageHeight),
    ImageLockMode.WriteOnly,
    PixelFormat.Format32bppArgb);
System.Runtime.InteropServices.Marshal.Copy(rawBytes, 0, bitmapData.Scan0, rawBytes.Length);
bmp.UnlockBits(bitmapData);

bmp.Save("page-0.png", ImageFormat.Png);

Concrete constraints:

  • DocLib.Instance and all reader objects are IDisposable — each must be in a using block. Failure to dispose creates native memory leaks.
  • PageDimensions in Docnet.Core sets the maximum rendering dimensions, not the DPI directly. DPI is implicit from the ratio of these dimensions to the page's point size (1 point = 1/72 inch). To target 150 DPI for an A4 page (595 × 842 points): width = 595 × (150/72) ≈ 1240 pixels.
  • GetImage() returns a raw BGRA byte array — not a PNG or JPEG. Converting to a usable image file requires manual Bitmap construction and pixel format handling.
  • The BGRA byte array is a large native allocation — for high-DPI renders of multi-page documents, memory pressure accumulates if pages are not processed and disposed sequentially.
  • PdfiumViewer provides a similar rasterization API via PdfDocument.Render() but with different method signatures. Verify the exact API of the wrapper in use.

IronPDF — Page to Image Rasterization

using IronPdf;

using var pdf = PdfDocument.FromFile("source.pdf");

// Rasterize all pages to PNG files at 150 DPI in one call
// Returns an array of file paths to the generated image files
string[] imagePaths = pdf.RasterizeToImageFiles(
    "page-*.png",   // * replaced by page number
    dpi: 150);

Console.WriteLine($"Rendered {imagePaths.Length} pages.");

// Rasterize only specific pages (0-based index range)
string[] firstThree = pdf.RasterizeToImageFiles(
    "preview-*.png",
    dpi: 72,           // screen preview at 72 DPI
    fromPage: 0,
    toPage: 2);

IronPDF's RasterizeToImageFiles() eliminates the manual BGRA-to-Bitmap conversion, the DPI-to-dimension calculation, and the per-page reader disposal pattern. DPI is specified directly. The PDF to image guide covers format options (PNG, JPEG, BMP), DPI ranges, and page selection.

Text Extraction

PDFium (Docnet.Core) — Text Extraction

using Docnet.Core;
using Docnet.Core.Models;

using var library = DocLib.Instance;
using var docReader = library.GetDocReader(
    "source.pdf",
    new PageDimensions(1080, 1920));

int pageCount = docReader.GetPageCount();
var fullText = new System.Text.StringBuilder();

for (int i = 0; i < pageCount; i++)
{
    using var pageReader = docReader.GetPageReader(i);

    // GetText() returns plain text for the page
    // Docnet.Core also provides GetCharacters() for per-character position data
    string pageText = pageReader.GetText();
    fullText.AppendLine(pageText);
}

Console.WriteLine(fullText.ToString());

Concrete constraints:

  • Docnet.Core's GetCharacters() returns a collection of character objects with bounding box positions — this granular positional data is a PDFium differentiator that IronPDF's plain text extraction does not replicate.
  • GetText() returns plain text without positional data — this maps directly to IronPDF's extraction API.
  • Each pageReader is IDisposable and must be disposed per iteration; missing a disposal in the loop creates a native resource leak per page.
  • The DocLib.Instance singleton should be verified for thread safety in the specific wrapper version in use.

IronPDF — Text Extraction

using IronPdf;

using var pdf = PdfDocument.FromFile("source.pdf");

// Extract text from the entire document in one call
string allText = pdf.ExtractAllText();

// Or extract from a specific page (0-based)
string pageZeroText = pdf.ExtractTextFromPage(0);

Console.WriteLine($"Pages: {pdf.PageCount}");
Console.WriteLine(allText);

For plain text extraction without positional requirements, IronPDF's ExtractAllText() and ExtractTextFromPage(n) are direct replacements that eliminate the per-page reader disposal loop. The extract text and images guide covers extraction options. If Docnet.Core's GetCharacters() is in use for character-level bounding box positions, verify whether IronPDF's extraction API meets that requirement before proceeding.

Document Metadata and Page Dimensions

PDFium (Docnet.Core) — Metadata and Dimensions

using Docnet.Core;
using Docnet.Core.Models;

using var library = DocLib.Instance;
using var docReader = library.GetDocReader(
    "source.pdf",
    new PageDimensions(595, 842)); // A4 dimensions at 72 DPI

// Page count
int pageCount = docReader.GetPageCount();

// PDFium metadata access varies by wrapper
// Docnet.Core: verify if metadata access is available — it may be limited
// PdfiumViewer exposes metadata through PdfDocument properties
// string title = docReader.GetMetadata("Title"); // verify method/property name

// Page dimensions in points (1pt = 1/72 inch)
using var pageReader = docReader.GetPageReader(0);
int widthPts  = pageReader.GetPageWidth();   // in points × scale
int heightPts = pageReader.GetPageHeight();
// Note: Docnet.Core returns scaled pixel dimensions based on PageDimensions
// not raw PDF point dimensions

Concrete constraints:

  • Docnet.Core returns page dimensions in pixels scaled to the provided PageDimensions constraints, not in raw PDF points. Converting back to points requires knowing the input scale factor.
  • Metadata access in Docnet.Core is limited
  • PdfiumViewer (different wrapper) may expose metadata differently.

IronPDF — Metadata and Page Information

using IronPdf;

using var pdf = PdfDocument.FromFile("source.pdf");

// Page count
int pageCount = pdf.PageCount;

// Metadata as typed properties — no string key lookup
string title    = pdf.MetaData.Title;
string author   = pdf.MetaData.Author;
string creator  = pdf.MetaData.Creator;
string subject  = pdf.MetaData.Subject;

// Page dimensions
// pdf.GetPageDimensions(0) may vary by API version
Console.WriteLine($"Pages: {pageCount}");
Console.WriteLine($"Title: {title}, Author: {author}");

// Metadata can also be written — PDFium wrappers typically read-only
pdf.MetaData.Title = "Updated Title";
pdf.SaveAs("with-metadata.pdf");

IronPDF's pdf.MetaData exposes typed properties rather than string key lookups. Metadata writing is also available, extending beyond PDFium's typical read-only scope. The metadata guide covers all available properties.

HTML to PDF Generation (New Capability)

PDFium does not generate PDFs from HTML. Teams that maintain both a PDFium integration and a separate HTML-to-PDF library can consolidate into IronPDF.

using IronPdf;

// ChromePdfRenderer for HTML-to-PDF — not available in PDFium
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;

string html = @"
<!DOCTYPE html>
<html>
<head><style>
  body { font-family: Arial; font-size: 11pt; }
  table { width: 100%; border-collapse: collapse; }
  th, td { border: 1px solid #ccc; padding: 6px; }
</style></head>
<body>
  <h1>Generated Report</h1>
  <p>This PDF was generated from HTML — not possible with PDFium.</p>
</body>
</html>";

// After rendering, text extraction and rasterization are available on the same object
using var pdf = renderer.RenderHtmlAsPdf(html);

// Extract the text we just rendered
string extractedText = pdf.ExtractAllText();
Console.WriteLine($"Extracted: {extractedText.Substring(0, 50)}...");

pdf.SaveAs("generated-report.pdf");

Applications using PDFium for reading/extraction alongside a separate HTML-to-PDF library can consolidate both into IronPDF. The HTML string to PDF guide covers rendering configuration.

Breaking Changes & Gotchas

  • WinForms viewer component not in IronPDF: PdfiumViewer's embedded WinForms PdfiumViewerControl has no IronPDF equivalent. If the application uses the viewer control for interactive PDF display, this is a potential blocking gap requiring separate evaluation of a viewer library.
  • Character-level bounding boxes not in IronPDF: Docnet.Core's GetCharacters() provides per-character bounding box positions. IronPDF's ExtractAllText() and ExtractTextFromPage() return plain text without spatial coordinates. If downstream code uses character positions for coordinate-based data extraction or layout analysis, this must be evaluated before migration.
  • Native binary removal (Windows): PDFium wrappers require platform-specific native binaries in the deployment package. IronPDF on Windows is fully managed — native binaries are removed from the package, Docker image, and CI/CD pipeline. On Linux, IronPDF requires Chromium system library packages.
  • P/Invoke / interop chain eliminated: The entire disposal chain around DocLib, DocReader, and page readers (or the equivalent in other wrappers) is replaced by a single using var pdf = PdfDocument.FromFile(...) pattern.
  • BGRA byte array pipeline eliminated: PDFium wrappers return raw BGRA pixel buffers that must be manually converted to Bitmap objects. IronPDF's rasterization writes image files directly — remove all LockBits, Marshal.Copy, and manual Bitmap construction code.
  • DPI specification model changes: PDFium wrapper DPI is specified indirectly via target pixel dimensions and the page's native point size. IronPDF specifies DPI directly via the dpi: parameter.
  • Namespace change: Remove all PDFium wrapper using directives (using Docnet.Core;, using PdfiumViewer;, etc.). Replace with using IronPdf;.
  • License key required: PDFium is open-source with no runtime key. IronPDF requires IronPdf.License.LicenseKey at startup.
  • PdfDocument naming: Docnet.Core and PdfiumViewer both have types named PdfDocument (or similar) that will conflict with IronPDF's PdfDocument if both packages are present during migration. Fully qualify all references until the old packages are removed.

Migration Checklist

  1. Audit PDFium usage by operation: Identify which wrapper is in use (Docnet.Core, PdfiumViewer, PDFiumSharp) and list every operation: rasterization, text extraction, viewer control, metadata access, character position access. The WinForms viewer and character-level position usage are the potential blocking gaps.
  2. Evaluate WinForms viewer gap: If PdfiumViewer's viewer control is in use, evaluate a standalone PDF viewer library (or IronPDF's viewer documentation) before committing to migration.
  3. Evaluate character-level position gap: If GetCharacters() (Docnet.Core) or equivalent is used, evaluate IronPDF's extraction API against the downstream requirement.
  4. Install IronPDF via NuGet: dotnet add package IronPdf. Retain PDFium wrapper references until replacement code compiles.
  5. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs. See the license setup guide.
  6. Update namespaces: Remove using Docnet.Core;, using PdfiumViewer;, or equivalent directives. Replace with using IronPdf;.
  7. Replace document load: Map wrapper's GetDocReader(path, dims) or PdfDocument.Load(path) to PdfDocument.FromFile(path). Wrap in using.
  8. Replace rasterization: Replace pageReader.GetImage() + manual Bitmap construction with pdf.RasterizeToImageFiles(pattern, dpi: n). Remove all LockBits, Marshal.Copy, and Bitmap disposal code.
  9. Replace text extraction: Map per-page GetText() loop to pdf.ExtractAllText() or pdf.ExtractTextFromPage(n).
  10. Replace metadata access: Map string-key metadata lookup to pdf.MetaData.Title, pdf.MetaData.Author, etc.
  11. Remove native binary packages: Remove PDFium native binary NuGet packages from the project. Remove native binary files from Docker images and CI/CD build steps. Add Chromium system library packages on Linux.
  12. Remove PDFium wrapper NuGet packages: Once all replacements compile and tests pass, remove all PDFium wrapper packages.

Conclusion

When staying on PDFium is technically reasonable

PDFium wrappers remain technically reasonable when the WinForms viewer component is central to the application and cannot be replaced, when character-level bounding box extraction is a core workflow requirement that IronPDF does not cover, when the open-source BSD-3 license is a hard procurement requirement, or when the current native binary management overhead is already handled by existing infrastructure and the team has no expansion plans that would require HTML generation or advanced manipulation.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when native binary management is adding deployment friction across multiple platforms; when the application's requirements have grown to include HTML-to-PDF generation, form filling, digital signatures, PDF/A compliance, or merge/split operations that require an additional library alongside PDFium; when the disposal chain around multiple reader objects is causing native resource leaks in production; or when the team wants a single managed-code library with a conventional .NET API replacing a native interop stack.

What the cutover typically involves at the code level

The rasterization pipeline replacement is the most code-dense change — the BGRA byte array → Bitmap construction code is replaced by a single RasterizeToImageFiles() call. Text extraction replaces the per-page reader loop with direct PdfDocument methods. The WinForms viewer and character-level position operations are the only cases that require evaluation before the migration proceeds. For applications using PDFium purely for rasterization and plain text extraction, the migration scope is bounded and predictable.
