Migrating from PdfiumViewer to IronPDF: from install to production

architecture differences, breaking changes, and migration patterns

Framing

PdfiumViewer is a .NET library that wraps the PDFium native rendering engine to provide two capabilities: a WinForms PDF viewer control (PdfViewer) and a programmatic API for rendering PDF pages to images. Built by pvginkel and distributed via NuGet, it was widely adopted in Windows desktop applications that needed to display PDFs in a WinForms host or produce page thumbnails without shelling out to a PDF reader executable. The library filled a real gap — prior to PdfiumViewer, embedding PDF viewing in WinForms required either Adobe Reader ActiveX controls or purchasing a commercial component.

PdfiumViewer is now archived and no longer maintained. The last release predates .NET Core, and the library targets .NET Framework. Teams running PdfiumViewer encounter the same class of problems that affect all discontinued native-wrapper libraries: no security patches, no runtime compatibility updates, increasing build toolchain friction as MSBuild evolves, and a hard blocker for any planned migration from .NET Framework to modern .NET. The native binary packaging requirement — x86, x64, and potentially ARM PDFium binaries — adds deployment overhead that teams continuing to maintain the library must manage indefinitely without upstream support.

This guide covers the migration from PdfiumViewer to IronPDF for .NET engineers evaluating or executing the switch. PdfiumViewer is not an HTML-to-PDF renderer — it is a PDF-to-image rasterizer and WinForms viewer built on PDFium. The migration is classified as Low effort for the rasterization and extraction operations, which map cleanly to IronPDF equivalents. The WinForms viewer component has no direct IronPDF equivalent and requires separate handling.

What PdfiumViewer Is Designed to Do

PdfiumViewer is a .NET Framework library that offers two primary features. First: a WinForms control (PdfViewer) that renders PDF pages inside a WinForms panel using PDFium's native rendering engine — supporting scrolling, zoom, and optional text selection. Second: a programmatic PDF document API (PdfDocument) that loads a PDF, reports page count and dimensions, and renders individual pages to System.Drawing.Bitmap objects at a specified DPI.

The library's install footprint includes the managed NuGet package plus a PdfiumViewer.Native platform package for the target architecture (x64, x86). These native packages bundle the PDFium DLL and must be included in the output directory. PdfiumViewer does not generate PDFs from HTML, does not provide merge/split, form filling, digital signatures, or encryption — its scope is entirely PDF reading and display. The product is discontinued (archived repository); the last release date and exact .NET Framework version requirements should be verified in the archived repository or existing project artifacts.

Architectural Differences

PdfiumViewer and IronPDF operate in different parts of the PDF processing lifecycle. PdfiumViewer reads and displays existing PDFs; IronPDF both generates PDFs from HTML and manipulates existing ones. For the reading operations PdfiumViewer provides — loading documents, rasterizing pages to images, extracting text — IronPDF offers managed replacements with no native binary dependency on Windows.

IronPDF's PdfDocument loads existing PDFs via PdfDocument.FromFile() or PdfDocument.FromStream(). Page rasterization uses pdf.RasterizeToImageFiles(), which specifies DPI directly rather than working through Bitmap construction. The PDF to image guide covers output formats and DPI configuration. For generating new PDFs from HTML content, ChromePdfRenderer provides Chromium-based rendering that was outside PdfiumViewer's scope entirely. License initialization is a one-time startup call; see the license setup guide.

The critical difference is the WinForms viewer control: PdfViewer is a Windows Forms control for interactive PDF display, and IronPDF has no equivalent interactive viewer component. Teams whose applications use PdfViewer for end-user document display need a separate evaluation for that component, independent of the server-side rasterization and text extraction migration.

Operation Comparisons

Loading a PDF and Rendering a Page to Bitmap

PdfiumViewer — Render Page to Bitmap

using PdfiumViewer;
using System.Drawing;
using System.Drawing.Imaging;

// PdfiumViewer.PdfDocument loads the PDF and exposes rendering
// Must be disposed — wraps native PDFium document handle
using var pdfDoc = PdfDocument.Load("source.pdf");

int pageCount = pdfDoc.PageCount;
Console.WriteLine($"Page count: {pageCount}");

// Render page 0 (0-based) to a Bitmap at 150 DPI
// PdfDocument.Render() returns System.Drawing.Bitmap
// Width and height are in pixels based on DPI × page point size
int dpi = 150;
var pageSize = pdfDoc.PageSizes[0];  // SizeF in points (1pt = 1/72 inch)
int widthPx  = (int)(pageSize.Width  * dpi / 72.0);
int heightPx = (int)(pageSize.Height * dpi / 72.0);

// Render() takes pixel dimensions, not DPI directly
using var bitmap = (Bitmap)pdfDoc.Render(
    page:   0,
    width:  widthPx,
    height: heightPx,
    dpiX:   dpi,
    dpiY:   dpi,
    rotate: PdfRotation.Rotate0,
    flags:  PdfRenderFlags.Annotations);

bitmap.Save("page-0.png", ImageFormat.Png);

Concrete constraints:

  • PdfDocument.Load() opens a native PDFium handle and must be disposed. PdfiumViewer's PdfDocument is IDisposable.
  • pdfDoc.PageSizes returns a SizeF collection in PDF points (1 point = 1/72 inch). Pixel dimensions for a target DPI must be calculated manually: pixels = points × (dpi / 72.0).
  • Render() returns System.Drawing.Image (cast to Bitmap) — this managed object wraps the rendered pixels and must also be disposed.
  • PdfiumViewer requires the platform-specific PDFium native DLL (pdfium.dll for x64 or x86) to be present in the output directory at runtime. Missing native DLL causes DllNotFoundException at runtime, not at build time.
  • The library targets .NET Framework — referencing it from a .NET Core or .NET 5+ project will fail or require a compatibility shim.

IronPDF — Render PDF Pages to Images

using IronPdf;

// Load the source PDF — IDisposable, use a using block
using var pdf = PdfDocument.FromFile("source.pdf");

Console.WriteLine($"Page count: {pdf.PageCount}");

// Rasterize all pages to PNG at 150 DPI
// DPI is specified directly — no manual pixel calculation required
string[] imagePaths = pdf.RasterizeToImageFiles(
    "page-*.png",     // output filename pattern
    dpi: 150);        // matches PdfiumViewer's dpiX/dpiY = 150

Console.WriteLine($"Rendered {imagePaths.Length} pages to disk.");

// Rasterize only page 0 (0-based, same as PdfiumViewer)
string[] singlePage = pdf.RasterizeToImageFiles(
    "first-page-*.png",
    dpi: 150,
    fromPage: 0,
    toPage: 0);

The manual DPI-to-pixel conversion (points × dpi / 72) is eliminated. PdfiumViewer's Render() call plus bitmap.Save() is replaced by a single RasterizeToImageFiles() call. The System.Drawing.Bitmap intermediary and its disposal requirement are removed. The PDF to image guide covers format options (PNG, JPEG, BMP), page ranges, and DPI settings.

// Full document text extraction via character-level API:
var fullText = new System.Text.StringBuilder();
for (int page = 0; page < pdfDoc.PageCount; page++)
{

    // Exact overload signature
    // string pageText = pdfDoc.GetPdfText(page); // verify method signature
    // fullText.AppendLine(pageText);
}

// Note: PdfiumViewer's text extraction API changed across versions
// Verify the exact method name and signature in the installed package

Concrete constraints:

  • PdfiumViewer's text extraction API changed between versions. The exact method name (GetPdfText, ExtractText, or similar) and its signature must be confirmed from the installed package version.
  • Text extraction returns plain string content — there is no structured positional data equivalent to Docnet.Core's GetCharacters().
  • The page-level loop requires a using block around pdfDoc and must not outlive the document handle.

IronPDF — Text Extraction

using IronPdf;

using var pdf = PdfDocument.FromFile("source.pdf");

// Extract all text in one call — replaces page iteration loop
string allText = pdf.ExtractAllText();

// Per-page extraction (0-based index, same convention as PdfiumViewer)
string page0Text = pdf.ExtractTextFromPage(0);

Console.WriteLine($"Document text length: {allText.Length} characters");

The page-iteration loop for text extraction is replaced by ExtractAllText(). The extract text and images guide covers extraction options and image extraction from PDF pages.

.NET Runtime Unblocking

PdfiumViewer targets .NET Framework, which makes it a hard blocker for modernizing to .NET 5+.

<!-- Before: project locked to .NET Framework by PdfiumViewer dependency -->
<Project Sdk="Microsoft.NET.Sdk.WinForms">
  <PropertyGroup>
    <TargetFramework>net472</TargetFramework>
  </PropertyGroup>
  <ItemGroup>
    <!-- PdfiumViewer only works on .NET Framework -->
    <PackageReference Include="PdfiumViewer" Version="2.13.0" />
    <PackageReference Include="PdfiumViewer.Native.x86_x64.v8-xfa"
                      Version="2018.4.8.356" />
  </ItemGroup>
</Project>
<!-- After: project can target modern .NET after PdfiumViewer removal -->
<Project Sdk="Microsoft.NET.Sdk.WinForms">
  <PropertyGroup>
    <!-- .NET 8 WinForms — IronPDF is .NET Standard 2.0 compatible -->
    <TargetFramework>net8.0-windows</TargetFramework>
  </PropertyGroup>
  <ItemGroup>
    <PackageReference Include="IronPdf" Version="x.x.x" />
    <!-- No native binary package required on Windows -->
  </ItemGroup>
</Project>
// After migration — works identically on .NET 8 WinForms
using IronPdf;

using var pdf = PdfDocument.FromFile("source.pdf");
string[] pages = pdf.RasterizeToImageFiles("preview-*.png", dpi: 96);
// Use rendered images in PictureBox or other WinForms controls

Removing PdfiumViewer and adding IronPDF unblocks the project's .NET runtime upgrade. For WinForms projects migrating to net8.0-windows, IronPDF works without compatibility shims. Note: the PdfViewer WinForms control must be replaced separately (see Breaking Changes).

HTML to PDF Generation (New Capability)

PdfiumViewer has no HTML rendering capability. Adding IronPDF makes HTML-to-PDF available alongside the replaced rasterization and extraction operations.

using IronPdf;

// HTML to PDF — not possible with PdfiumViewer
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;

using var generated = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Report</h1><p>Generated from HTML.</p></body></html>");

// Rasterize the generated PDF to images for display in WinForms
string[] previewImages = generated.RasterizeToImageFiles(
    "report-preview-*.png", dpi: 96);

generated.SaveAs("report.pdf");

Applications that display PDF content in WinForms using PdfiumViewer's viewer can use IronPDF to rasterize pages and display them in PictureBox controls during the transition period while the viewer replacement is evaluated. The HTML string to PDF guide covers generation configuration.

Breaking Changes & Gotchas

  • PdfViewer WinForms control not in IronPDF: The interactive WinForms PDF viewer control (PdfViewer) has no IronPDF equivalent. Applications that use this control for interactive user-facing PDF display must evaluate a standalone viewer component independently of the server-side migration. A temporary workaround during transition is to rasterize pages with IronPDF and display in PictureBox controls, though this loses interactivity.
  • System.Drawing.Bitmap intermediary removed: PdfiumViewer's Render() returns System.Drawing.Bitmap. IronPDF's RasterizeToImageFiles() writes files to disk. Code that processes the returned Bitmap in-memory must be updated to read the image file, or IronPDF's stream-based output options should be verified.
  • DPI calculation code removed: The manual width = pageSize.Width * dpi / 72 calculation is replaced by the dpi: parameter. Remove all manual dimension calculation code.
  • Native binary packages eliminated: PdfiumViewer.Native.x86_x64.* or equivalent packages are removed from the project. Remove PDFium DLL files from deployment artifacts, Docker images, and CI/CD steps. On Linux, add Chromium system library packages.
  • Discontinued library risks: PdfiumViewer's discontinued status means no security patches, no .NET runtime compatibility updates, and increasing build toolchain friction. These are operational risks that grow with time.
  • PdfDocument name collision: PdfiumViewer has a type named PdfDocument. IronPDF also has a type named PdfDocument. If both packages are present during the migration transition, fully qualify all PdfDocument references.
  • Namespace change: Remove using PdfiumViewer;. Replace with using IronPdf;.
  • License key required: PdfiumViewer is open-source with no runtime key. IronPDF requires IronPdf.License.LicenseKey at startup.
  • .NET Framework → modern .NET unblocked: Removing PdfiumViewer unblocks retargeting to net8.0-windows or net8.0. This is typically the primary engineering motivation.

Migration Checklist

  1. Audit usage of PdfViewer control: Determine whether the WinForms viewer control is in active use. If so, identify a replacement viewer strategy (standalone viewer library, browser-hosted viewer, or rasterize-to-PictureBox workaround) before beginning the library migration.
  2. Audit rasterization and extraction call sites: List every pdfDoc.Render() call with its DPI and page parameters, and every text extraction call.
  3. Install IronPDF via NuGet: dotnet add package IronPdf. Retain PdfiumViewer references until replacement code compiles.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in application startup. See the license setup guide.
  5. Update namespaces: Remove using PdfiumViewer;. Add using IronPdf;. Fully qualify any PdfDocument references during the transition.
  6. Replace PdfDocument.Load(path): Map to PdfDocument.FromFile(path) wrapped in a using block.
  7. Replace rasterization calls: Map each pdfDoc.Render(page, w, h, dpiX, dpiY, ...) to pdf.RasterizeToImageFiles(pattern, dpi: n, fromPage: p, toPage: p). Remove manual DPI calculation code. Update downstream code to read from file path instead of System.Drawing.Bitmap.
  8. Replace text extraction: Map per-page GetPdfText() calls to pdf.ExtractTextFromPage(n). Replace full-document loops with pdf.ExtractAllText().
  9. Retarget .NET project: Update <TargetFramework> from net4xx to net8.0-windows (for WinForms) or net8.0. Resolve any other .NET Framework-only dependencies that surface after retargeting.
  10. Remove native binary packages: Remove PdfiumViewer.Native.* NuGet packages. Remove PDFium DLL files from all deployment artifacts. On Linux, add Chromium system library packages.
  11. Remove PdfiumViewer NuGet package: Once all replacements compile and tests pass, remove the package.
  12. Resolve PdfViewer viewer replacement: If the viewer control was in use, complete the viewer replacement after the rasterization/extraction migration is stable.

Conclusion

When staying on PdfiumViewer is technically reasonable

PdfiumViewer is discontinued, making "staying" a short-term position for most teams. Continued use is most defensible when the application is fully frozen — no new development, no dependency upgrades, no .NET runtime migration planned — and the PdfViewer WinForms control is providing user-facing value that would require significant effort to replace. Even in this scenario, the discontinued status means accumulating security and compatibility risk without upstream resolution.

Signals that indicate migration is worth the engineering effort

The discontinued status and .NET Framework-only constraint together make migration worth planning for any application with active development. Concrete triggers: a planned .NET Framework to .NET 5+ migration where PdfiumViewer is a hard blocker; deployment pipeline changes that require removing PdfiumViewer.Native binary packages; new PDF requirements (HTML generation, form filling, digital signatures) that would require another library alongside PdfiumViewer; or security scanner alerts on the discontinued dependency.

What the cutover typically involves at the code level

The rasterization API swap is the most substantial code change — Render() plus manual pixel calculation plus Bitmap.Save() becomes a single RasterizeToImageFiles() call. Text extraction replaces a page loop with ExtractAllText(). The project retargeting follows once PdfiumViewer is removed. The PdfViewer viewer control, if in use, is the only open-ended work item that may extend the migration timeline beyond a focused sprint.

In your current PdfiumViewer integration, has the discontinued status caused any concrete issues — failed builds, incompatible runtime versions, security scanner alerts — or is the migration being planned preemptively before those problems arrive?
