Migrating from Telerik Reporting to IronPDF: a .NET engineering guide

API mapping, gotchas, and a migration checklist

Framing

Telerik Reporting is Progress Software's enterprise reporting platform for .NET — a suite that spans a Visual Studio Report Designer, a Web Report Designer, a standalone Report Book format, and a runtime that renders report definitions to multiple output formats including PDF, Excel, Word, and HTML. Teams adopt Telerik Reporting when the requirements are centered on the report design experience: structured layouts with data regions, subreports, parameters, crosstabs, charts, and designer tooling that non-developers or business analysts can operate without writing code.

The conditions that lead engineering teams to re-evaluate Telerik Reporting typically fall into two categories. The first is scope: Telerik Reporting is optimized for structured data-driven reports — tabular layouts, data regions, and parameter-driven queries. Teams whose PDF output requirements are primarily document generation from HTML templates (invoices, letters, contracts, branded documents) often find the report designer model is a heavier abstraction than the requirement justifies. The second is cost and dependency: Telerik Reporting is a commercial product with per-developer licensing and a large install footprint that includes report viewer controls, report server components, and designer tooling. When the application's PDF needs are narrow, the full platform weight may not be warranted.

This guide covers the migration from Telerik Reporting to IronPDF for .NET engineering teams evaluating the switch. The migration effort is classified as High — Telerik Reporting is a full platform with report definition files, a data binding model, designer tooling, and a viewer component. The code-level migration is straightforward; replacing the report design workflow is the principal challenge.

What Telerik Reporting Is Designed to Do

Telerik Reporting is a report authoring and rendering platform. Reports are defined in TRDX (XML) or TRDP (binary) report definition files created in the Visual Studio Report Designer or the Web Report Designer. Report definitions describe data sources (SQL, object, Entity Framework, JSON, XML), data regions (table, list, crosstab, chart, map), parameters with UI prompts, subreports, calculated fields, and layout. The runtime processes a report definition, binds it to data at render time, paginates the result, and exports it to a specified format.

The platform distributes as a set of NuGet packages covering the report processor, viewer controls (WinForms, WPF, ASP.NET Core, Blazor), REST report service, and report server. The install footprint is substantial — a typical ASP.NET Core integration includes report processor packages, a viewer JavaScript component, and optionally the REST service. The primary use case is structured business reporting: financial dashboards, operational reports, invoice runs, and executive summaries designed and maintained through the visual designer tooling. Telerik Reporting supports .NET 10 with current-version release support; verify specific .NET version support in official Progress documentation.

Architectural Differences

Telerik Reporting and IronPDF approach PDF output through fundamentally different models. Telerik Reporting is a reporting platform — it processes a declarative report definition, binds data, paginates, and exports. IronPDF is a PDF library — it generates PDFs from HTML/CSS rendered by embedded Chromium, and manipulates existing PDF documents.

IronPDF's ChromePdfRenderer generates PDFs from HTML strings, HTML files, or URLs. PdfDocument handles loading, manipulating, signing, and saving existing PDFs. Both implement IDisposable. The HTML string to PDF guide covers rendering configuration; for PDF-centric reports, the PDF reporting guide addresses common report patterns. License initialization is a one-time startup call; see the license setup guide.

The architectural distinction is that IronPDF has no report designer, no declarative report definition format, and no data binding engine. HTML templates with data bound by a .NET template engine (Razor, Scriban, Fluid) replace the TRDX/TRDP report file. Charts and crosstabs must be implemented as HTML/CSS or SVG rather than as Telerik Reporting's dedicated charting data regions. Teams migrating primarily to reduce dependency weight for simple PDF output will find IronPDF's integration lighter; teams that need the designer-driven workflow and structured data region model will need to evaluate whether that requirement can be met differently.

Operation Comparisons

Report Definition Rendering → HTML Template Rendering

Telerik Reporting — Render Report to PDF

using Telerik.Reporting;
using Telerik.Reporting.Processing;

// Telerik Reporting — render a TRDX report definition to PDF bytes
// The report definition file contains layout, data source, and parameters

// Load the report definition from file
var reportSource = new UriReportSource
{
    Uri = "Reports/InvoiceReport.trdx"  // path to .trdx file
};

// Set report parameters
reportSource.Parameters.Add("InvoiceId", 1042);
reportSource.Parameters.Add("CustomerId", 7);

// Create the report processor and render
var processor = new ReportProcessor();
var renderingResult = processor.RenderReport("PDF", reportSource, null);

// renderingResult.DocumentBytes contains the PDF output
byte[] pdfBytes = renderingResult.DocumentBytes;
File.WriteAllBytes("invoice.pdf", pdfBytes);

// RenderingResult is IDisposable — dispose after use
renderingResult.Dispose();

Concrete constraints:

  • ReportProcessor.RenderReport() is synchronous. For ASP.NET Core, wrapping in Task.Run() is a common workaround; async rendering is not natively supported in all versions.
  • UriReportSource resolves paths relative to the application base directory — path management is an operational concern in deployment.
  • Report parameters are strongly typed in the report definition; parameter name mismatches cause runtime errors, not compile-time errors.
  • The TRDX report definition encapsulates layout, data source connection, and query — changes to any of these require designer tooling to edit the definition file.
  • Chart and crosstab data regions render in the processor; there is no equivalent in a plain HTML template without a charting library.

IronPDF — HTML Template Rendering

using IronPdf;

// IronPDF — render an HTML template to PDF
// Data binding is done before rendering using a .NET template engine
// Example below uses C# string interpolation; production code would use
// Razor, Scriban, or Fluid for complex templates with loops and conditionals

var invoice = new
{
    Id = 1042,
    Customer = "Acme Corp",
    Date = DateTime.Today,
    Lines = new[]
    {
        new { Description = "Widget A", Qty = 10, UnitPrice = 99.99m },
        new { Description = "Widget B", Qty = 5,  UnitPrice = 249.99m }
    },
    Total = 2249.85m
};

// Build HTML with data — in production, load from a .html template file
var lineRows = string.Concat(invoice.Lines.Select(l =>
    $"<tr><td>{l.Description}</td>" +
    $"<td style='text-align:right'>{l.Qty}</td>" +
    $"<td style='text-align:right'>{l.UnitPrice:C}</td></tr>"));

string html = $@"
<!DOCTYPE html>
<html>
<head>
<style>
  body {{ font-family: Arial; font-size: 11pt; }}
  h1 {{ color: #333; }}
  table {{ width: 100%; border-collapse: collapse; margin-top: 16px; }}
  th, td {{ border: 1px solid #ddd; padding: 6px 10px; }}
  th {{ background: #f5f5f5; }}
  .total {{ font-weight: bold; text-align: right; margin-top: 12px; }}
</style>
</head>
<body>
  <h1>Invoice #{invoice.Id}</h1>
  <p>Customer: {invoice.Customer} &nbsp;|&nbsp; Date: {invoice.Date:d}</p>
  <table>
    <thead><tr><th>Description</th><th>Qty</th><th>Unit Price</th></tr></thead>
    <tbody>{lineRows}</tbody>
  </table>
  <p class='total'>Total: {invoice.Total:C}</p>
</body>
</html>";

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;

// PdfDocument is IDisposable — always use a using block
using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("invoice.pdf");

The report definition file and ReportProcessor are replaced by an HTML template and renderer.RenderHtmlAsPdf(). Data binding that Telerik Reporting handled declaratively is now explicit C# — either string interpolation for simple cases, or a template engine for complex iteration. Templates are previewable in any browser before rendering. Full rendering configuration is in the HTML string to PDF guide.

Headers, Footers, and Page Numbers

Telerik Reporting — Headers and Footers

// In Telerik Reporting, headers and footers are report sections defined
// in the report designer — ReportHeaderSection, ReportFooterSection,
// PageHeaderSection, PageFooterSection. They are configured visually
// and contain text boxes, images, and expressions.
//
// Page number expressions in a TextBox:
//   = PageNumber           — current page (1-based)
//   = PageCount            — total pages
//   = "Page " & PageNumber & " of " & PageCount
//
// These expressions are evaluated by the report processor at render time.
// There is no API equivalent — they are defined only in the designer.

Concrete constraints:

  • Telerik Reporting's page number expressions (= PageNumber, = PageCount) are evaluated by the report processor only within the context of a rendered report definition. There is no code-level equivalent.
  • Page and report header/footer sections are designer-configured — migrating them means converting the section content to HTML fragment strings.

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 22;     // leave room for header
renderer.RenderingOptions.MarginBottom = 15;

// IronPDF page number tokens: {page} and {total-pages}
// These replace Telerik's = PageNumber and = PageCount expressions
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 14,
    HtmlFragment = "<div style='font-size:9px; font-family:Arial; " +
                   "text-align:right; padding:0 14px;'>" +
                   "Acme Corp — Confidential</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 10,
    HtmlFragment = "<div style='font-size:8px; font-family:Arial; " +
                   "text-align:center;'>Page {page} of {total-pages}</div>"
};

using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><p>Report content here.</p></body></html>");
pdf.SaveAs("report-with-headers.pdf");

Telerik Reporting's PageHeaderSection and PageFooterSection contents become HtmlHeaderFooter.HtmlFragment strings. The = PageNumber / = PageCount expressions become {page} / {total-pages} tokens. The headers and footers guide covers height, dividers, and all available token substitutions.

Parameterized Reports → Parameterized Controllers

Telerik Reporting — Report Parameters

using Telerik.Reporting;
using Telerik.Reporting.Processing;

// Report parameters are defined in the report definition.
// At render time, parameter values are supplied at the call site.
// The report engine applies them to data source queries automatically.

var reportSource = new UriReportSource { Uri = "Reports/SalesReport.trdx" };

// Parameters correspond to declared parameters in the report definition
// Mismatch between name or type causes a runtime exception
reportSource.Parameters.Add("StartDate", new DateTime(2025, 1, 1));
reportSource.Parameters.Add("EndDate",   new DateTime(2025, 12, 31));
reportSource.Parameters.Add("RegionId",  3);

var processor = new ReportProcessor();
var result = processor.RenderReport("PDF", reportSource, null);
byte[] pdfBytes = result.DocumentBytes;
result.Dispose();

Concrete constraints:

  • Report parameter names are string-typed at the call site — misspelling "StartDate" causes a runtime error, not a compile error.
  • The report definition's data source uses the parameter values to filter queries. Replicating this in IronPDF means performing the data fetch in application code before template rendering.

IronPDF — Parameterized Controller Action

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports/sales")] public class SalesReportController : ControllerBase { private readonly ChromePdfRenderer _renderer; private readonly ISalesRepository _salesRepo;

public SalesReportController(ChromePdfRenderer renderer, ISalesRepository salesRepo) { _renderer = renderer; _salesRepo = salesRepo; }

// Parameters are route/query params — type-safe at the action level [HttpGet("pdf")] public async Task GetSalesReport( [FromQuery] DateTime startDate, [FromQuery] DateTime endDate, [FromQuery] int regionId) { // Fetch data with parameters applied — type-safe in application code var sales = await _salesRepo.GetSalesAsync(startDate, endDate, regionId);

// Build HTML from data string html = BuildSalesReportHtml(sales, startDate, endDate);

using var pdf = await _renderer.RenderHtmlAsPdfAsync(html);

return File(pdf.BinaryData, "application/pdf", $"sales-{startDate:yyyyMMdd}-{endDate:yyyyMMdd}.pdf"); }

private static string BuildSalesReportHtml(IEnumerable sales, DateTime start, DateTime end) { // Build HTML string from data — or use a Razor/Scriban template engine return $"

Sales Report

" + $"

{start:d} – {end:d}

"; } }

Report parameters become type-safe action method parameters. The data query that Telerik Reporting's data source performed is now explicit in the application layer. The async rendering guide covers concurrent rendering in ASP.NET Core.

Merging Multiple Report Sections

using IronPdf;

// In Telerik Reporting, a ReportBook combines multiple report instances.
// The IronPDF equivalent: render each section separately, then merge.

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Section 1: Cover page
using var cover = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Annual Report 2025</h1><p>Acme Corp</p></body></html>");

// Section 2: Financial summary (data-driven)
string summaryHtml = BuildFinancialSummaryHtml();
using var summary = renderer.RenderHtmlAsPdf(summaryHtml);

// Section 3: Appendix
using var appendix = renderer.RenderHtmlAsPdf(
    "<html><body><h2>Appendix A</h2><p>Supporting data.</p></body></html>");

// Merge all sections into a single PDF — equivalent to ReportBook
using var fullReport = PdfDocument.Merge(cover, summary, appendix);
fullReport.SaveAs("annual-report-2025.pdf");

static string BuildFinancialSummaryHtml() =>
    "<html><body><h2>Financial Summary</h2><p>Data here.</p></body></html>";

Telerik Reporting's ReportBook — which combines multiple report instances into a single PDF — is replaced by rendering each section separately and merging with PdfDocument.Merge(). The merge and split guide covers N-way merges and page-level operations.

Breaking Changes & Gotchas

  • Report definition files replaced: TRDX/TRDP files have no equivalent in IronPDF. Every report must be rewritten as an HTML template. This is the primary effort item.
  • Designer tooling removed: The Visual Studio Report Designer and Web Report Designer have no IronPDF equivalent. Report layout is now authored in HTML/CSS, previewable in a browser.
  • Data binding model changes: Telerik Reporting's declarative data sources are replaced by explicit application-layer data fetching. Report parameters become type-safe action or method parameters.
  • Chart data regions: Telerik Reporting's built-in chart rendering has no IronPDF equivalent. Charts must be rendered as SVG, embedded images, or via a JavaScript charting library (Chart.js, D3) in the HTML.
  • Crosstab / pivot regions: No declarative equivalent in IronPDF. Pivot logic must be implemented in C# to produce an HTML table.
  • Report Viewer control removed: Telerik's WinForms, WPF, ASP.NET Core, and Blazor viewer controls have no IronPDF equivalent. If interactive report viewing is required, evaluate a separate viewer component.
  • REST Report Service removed: Telerik's report server and REST service are replaced by standard ASP.NET Core controller actions that call IronPDF.
  • Page number token syntax: Telerik's = PageNumber / = PageCount expressions become {page} / {total-pages}. Old expressions render as literal text without error.
  • PdfDocument is IDisposable: Wrap every render result in a using block.
  • Namespace change: Remove using Telerik.Reporting; and using Telerik.Reporting.Processing;. Replace with using IronPdf;.
  • License key required: Set IronPdf.License.LicenseKey at startup. Telerik has its own licensing model — both keys must be managed during the transition period.
  • High effort — plan in phases: Migrate simple tabular reports first. Reserve complex crosstabs and charts for later phases after the pattern is established.

Migration Checklist

  1. Inventory all report definitions: List every TRDX/TRDP file, its data source, parameters, data regions (tables, crosstabs, charts), and subreport references. This defines the migration scope.
  2. Classify by complexity: Tag each report as simple (tabular data), medium (multiple sections, calculated fields), or complex (crosstab, charts, subreports). Migrate simple reports first.
  3. Choose a .NET template engine: Select the HTML data binding approach — string interpolation for simple cases, Razor, Scriban, or Fluid for iteration-heavy templates.
  4. Install IronPDF via NuGet: dotnet add package IronPdf.
  5. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs. See the license setup guide.
  6. Register ChromePdfRenderer in DI: Add builder.Services.AddSingleton<ChromePdfRenderer>() with RenderingOptions configured for common paper size and margins.
  7. Convert report definitions to HTML templates: For each report, author an HTML/CSS template that reproduces the layout. Verify in a browser before rendering with IronPDF.
  8. Move data fetch to application layer: Replace Telerik data sources with explicit repository/service calls in the controller or service. Map report parameters to typed action parameters.
  9. Replace page headers/footers: Convert PageHeaderSection and PageFooterSection content to HtmlHeaderFooter.HtmlFragment. Update page number expressions to {page} / {total-pages}.
  10. Handle charts and crosstabs: Implement chart output as SVG, embedded image, or a JavaScript charting library. Implement crosstab pivot logic in C# before HTML generation.
  11. Replace ReportBook usage: Map to PdfDocument.Merge() calls after rendering each section.
  12. Phase out Report Viewer and REST Service: Replace viewer endpoints with File(pdf.BinaryData, ...) action results. Decommission the REST report service once all report endpoints are migrated.

Conclusion

When staying on Telerik Reporting is technically reasonable

Telerik Reporting is technically reasonable when the designer tooling is actively used by non-developer stakeholders — business analysts, report designers, or operations staff who create and modify reports through the Web Report Designer without writing code. It is also appropriate when the application requires multi-format export (Excel, Word, HTML) beyond PDF, when the crosstab and charting data regions are central to the report output, and when the interactive viewer components in WinForms, WPF, or Blazor are providing end-user value that cannot easily be replaced.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when the application's PDF output requirements are primarily document generation from HTML templates with no designer-driven workflow; when the Telerik license cost is disproportionate to the subset of features in use; when modern CSS rendering quality is a concern; when the REST report service and viewer components are adding infrastructure complexity that the team wants to remove; or when consolidating the PDF generation and manipulation stack to a single library simplifies the dependency surface.

What the cutover typically involves at the code level

Each report definition is converted to an HTML template; its data source becomes an explicit repository call; its parameters become typed action parameters; its page header/footer becomes an HtmlHeaderFooter configuration. For tabular reports this conversion is mechanical. For crosstabs and charts, additional implementation work is required in C#. The phase approach — simple tabular reports first, complex regions later — manages risk and provides early validation of the pattern before tackling the most complex definitions.

As you map your report inventory to complexity tiers, what proportion of your TRDX files are straightforward tabular layouts versus reports that depend on crosstab, chart, or subreport features — and does that ratio inform whether a full migration or a hybrid approach (IronPDF for new reports, Telerik for complex legacy ones) is the more pragmatic path?
