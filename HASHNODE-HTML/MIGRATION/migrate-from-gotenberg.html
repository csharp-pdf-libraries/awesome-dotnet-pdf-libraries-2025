Migrating from Gotenberg to IronPDF: the engineering breakdown

effort estimation, API mapping, and production considerations

Framing

Containerized document conversion services represent one of the more pragmatic architectural patterns in document generation: run a self-hosted HTTP service that wraps a headless browser, send it HTML over HTTP, receive PDF bytes back. This approach keeps PDF generation concerns entirely separate from the application, avoids native binary dependencies in the application host, and gives infrastructure teams a single service to scale independently. Gotenberg is one of the most widely deployed implementations of this pattern in the self-hosted ecosystem.

Teams re-evaluate this architecture for several reasons. The HTTP round-trip adds latency that is often acceptable for low-volume generation but becomes measurable in high-throughput pipelines. The separate service introduces a network dependency — failure modes include service unavailability, timeouts, and network partitions that do not exist in an in-process rendering library. Infrastructure cost and operational overhead (deploying, monitoring, and maintaining a separate container) add up for teams that are otherwise not operating microservice infrastructure. And for applications that need to perform post-render PDF operations (merge multiple rendered PDFs, apply digital signatures, fill forms, add watermarks), the Gotenberg model requires receiving bytes over HTTP and then feeding them into a separate manipulation library — increasing the dependency count.

This guide is for .NET engineers evaluating or executing a migration from Gotenberg to IronPDF. The migration is classified as Low effort because both systems use Chromium under the hood for HTML rendering — rendering output is highly consistent — and the conceptual operation (HTML in, PDF out) is identical. The migration work is essentially replacing HTTP client calls with in-process method calls and updating the request/response handling to work with managed .NET objects rather than byte[] from HTTP.

What Gotenberg Is Designed to Do

Gotenberg is an open-source, self-hosted HTTP API server for document conversion. It runs as a Docker container and exposes HTTP endpoints that accept document content (HTML, Office files, PDFs, images) and return converted output. The HTML-to-PDF conversion endpoint wraps Chromium in headless mode — the same rendering engine used by IronPDF. Gotenberg also includes a LibreOffice integration for Office-format conversions (DOCX, XLSX, etc. to PDF). The product status and last release should be verified at the project's GitHub repository; Gotenberg is actively maintained as of the training data for this article.

In a .NET application, Gotenberg is used by constructing multipart/form-data HTTP requests containing the HTML content, CSS files, assets, and configuration, sending those requests to the Gotenberg container via HttpClient, and processing the returned PDF bytes. The .NET integration layer is entirely custom — there is no official .NET SDK for Gotenberg, though community packages exist. Configuration is passed as HTTP headers or form fields rather than as API calls. Gotenberg does not provide an API for PDF manipulation after rendering — merge, sign, form-fill, and encrypt operations require a separate library in the .NET application.

Architectural Differences

The architectural difference between Gotenberg and IronPDF is the boundary between the application and the rendering engine. In the Gotenberg pattern, the rendering engine runs in a separate Docker container and is accessed over HTTP. In IronPDF, the rendering engine runs in-process within the .NET application. Both use Chromium for HTML-to-PDF rendering, so the output fidelity is comparable — the same HTML and CSS renders consistently in both systems.

IronPDF's two central types are ChromePdfRenderer (rendering) and PdfDocument (manipulation). ChromePdfRenderer accepts an HTML string, an HTML file path, or a URL, and returns a PdfDocument implementing IDisposable. The HTML string to PDF guide covers the full rendering configuration — paper size, margins, CSS media type, JavaScript execution, and web font handling — which replaces Gotenberg's HTTP header configuration. The rendering options reference covers all available rendering parameters in detail. License initialization is a one-time startup call via IronPdf.License.LicenseKey; see the license setup guide.

The operational shift from Gotenberg to IronPDF removes the external HTTP dependency, eliminates network latency from the generation path, and consolidates rendering and manipulation into a single library. It introduces a different set of operational concerns: IronPDF on Linux requires Chromium system library packages in the application container (rather than running in a separate Chromium container), and memory usage for the Chromium process is shared with the application rather than isolated in a separate service.

Operation Comparisons

HTML String to PDF

Gotenberg — HTML String to PDF via HTTP

using System.Net.Http;
using System.Net.Http.Headers;

// Gotenberg is called via HTTP multipart/form-data
// No official .NET SDK — all configuration is via HTTP headers and form fields

public class GotenbergPdfService
{
    private readonly HttpClient _httpClient;
    private readonly string _gotenbergBaseUrl;

    public GotenbergPdfService(HttpClient httpClient, string gotenbergBaseUrl)
    {
        _httpClient = httpClient;
        _gotenbergBaseUrl = gotenbergBaseUrl; // e.g., "http://gotenberg:3000"
    }

    public async Task<byte[]> ConvertHtmlToPdfAsync(string html)
    {
        using var content = new MultipartFormDataContent();

        // Gotenberg requires an index.html file in the multipart form
        var indexHtmlContent = new StringContent(html);
        indexHtmlContent.Headers.ContentType =
            new MediaTypeHeaderValue("text/html");
        content.Add(indexHtmlContent, "files", "index.html");

        // Paper size: A4 (8.27 x 11.69 inches — Gotenberg uses inches)
        content.Add(new StringContent("8.27"), "paperWidth");
        content.Add(new StringContent("11.69"), "paperHeight");

        // Margins in inches
        content.Add(new StringContent("0.5"), "marginTop");
        content.Add(new StringContent("0.5"), "marginBottom");
        content.Add(new StringContent("0.5"), "marginLeft");
        content.Add(new StringContent("0.5"), "marginRight");

        // JavaScript execution wait — milliseconds (Gotenberg: waitDelay)
        content.Add(new StringContent("500ms"), "waitDelay");

        var endpoint = $"{_gotenbergBaseUrl}/forms/chromium/convert/html";
        using var response = await _httpClient.PostAsync(endpoint, content);

        response.EnsureSuccessStatusCode();

        return await response.Content.ReadAsByteArrayAsync();
    }
}

Concrete constraints:

  • Gotenberg's API is stateless HTTP — every call must include all configuration as form fields or headers. There is no persistent renderer state.
  • Paper dimensions are specified in inches (Gotenberg uses Chromium's print options, which accept paperWidth/paperHeight in inches). IronPDF uses millimeters — convert: mm = inches × 25.4. A 0.5 inch margin is 12.7mm.
  • HTML assets (CSS files, images, fonts) must be bundled into the multipart form as additional files when they are referenced relative to the HTML. Alternatively, assets must be served at absolute URLs.
  • Gotenberg's waitDelay accepts duration strings ("500ms", "2s") — map these to RenderingOptions.WaitFor.RenderDelay() in milliseconds.
  • HTTP timeouts, retry logic, circuit breakers, and DNS resolution are failure modes in the Gotenberg path with no equivalent in IronPDF's in-process model.
  • Gotenberg returns application/pdf bytes directly in the response body — no response object model.

IronPDF — HTML String to PDF In-Process

using IronPdf;

// ChromePdfRenderer is stateful and reusable — register as singleton in DI
var renderer = new ChromePdfRenderer();

// Configuration replaces Gotenberg's multipart form fields
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 12.7;    // 0.5 inches in mm
renderer.RenderingOptions.MarginBottom = 12.7;
renderer.RenderingOptions.MarginLeft = 12.7;
renderer.RenderingOptions.MarginRight = 12.7;
renderer.RenderingOptions.WaitFor.RenderDelay(500); // 500ms JS wait

string html = @"
<!DOCTYPE html>
<html>
<head>
<style>body { font-family: Arial, sans-serif; }</style>
</head>
<body>
  <h1>Invoice #1042</h1>
  <p>Total: $1,599.00</p>
</body>
</html>";

// PdfDocument is IDisposable — use a using block
using var pdf = renderer.RenderHtmlAsPdf(html);
byte[] pdfBytes = pdf.BinaryData;

// Or save directly:
// pdf.SaveAs("invoice.pdf");

The inch-to-millimeter conversion is the most common source of subtle layout differences when migrating from Gotenberg. Multiply Gotenberg's inch values by 25.4 to get IronPDF millimeter equivalents. Full rendering configuration is documented in the HTML string to PDF guide.

URL to PDF

Gotenberg — URL to PDF

using System.Net.Http;

public async Task<byte[]> ConvertUrlToPdfAsync(string url)
{
    using var content = new MultipartFormDataContent();

    // Gotenberg URL rendering uses the /forms/chromium/convert/url endpoint
    // The URL is passed as a form field, not as the request URL
    content.Add(new StringContent(url), "url");

    content.Add(new StringContent("8.27"), "paperWidth");
    content.Add(new StringContent("11.69"), "paperHeight");

    // Wait for a specific DOM element before capturing (Gotenberg: waitForExpression)
    content.Add(new StringContent(
        "document.querySelector('.dashboard-loaded') !== null"),
        "waitForExpression");

    var endpoint = $"{_gotenbergBaseUrl}/forms/chromium/convert/url";
    using var response = await _httpClient.PostAsync(endpoint, content);
    response.EnsureSuccessStatusCode();

    return await response.Content.ReadAsByteArrayAsync();
}

Concrete constraints:

  • Gotenberg's waitForExpression accepts a JavaScript expression that evaluates to a truthy value when the page is ready. This maps to IronPDF's RenderingOptions.WaitFor.JavaScriptExpression() or element-based wait conditions.
  • Cookie injection for authenticated URLs requires custom HTTP headers in the Gotenberg request
  • Gotenberg's failOnConsoleExceptions flag raises HTTP errors on JavaScript console exceptions — this behavior must be evaluated against the target URL before migration.

IronPDF — URL to PDF

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Replace Gotenberg's waitForExpression with IronPDF's WaitFor conditions
renderer.RenderingOptions.WaitFor.HtmlElement(".dashboard-loaded");

// Cookie injection for authenticated URLs
renderer.RenderingOptions.CustomCookies =
    new System.Collections.Generic.Dictionary<string, string>
    {
        { "session_id", "your-session-token" }
    };

using var pdf = renderer.RenderUrlAsPdf("https://app.example.com/dashboard");
byte[] pdfBytes = pdf.BinaryData;

IronPDF's WaitFor API supports element-based, expression-based, network-idle, and fixed-delay wait conditions — more granular than Gotenberg's waitDelay/waitForExpression. The URL to PDF guide covers cookie injection and wait condition configuration.

Headers and Footers

Gotenberg — Headers and Footers

using System.Net.Http;
using System.Net.Http.Headers;

public async Task<byte[]> ConvertWithHeaderFooterAsync(string html)
{
    using var content = new MultipartFormDataContent();

    // Main content
    var indexContent = new StringContent(html);
    indexContent.Headers.ContentType = new MediaTypeHeaderValue("text/html");
    content.Add(indexContent, "files", "index.html");

    // Gotenberg header/footer are separate HTML files in the multipart form
    // They use Chromium's special page header/footer HTML contract
    string headerHtml = @"<!DOCTYPE html>
<html><head>
<style>html { font-size: 9px; font-family: Arial; }</style>
</head><body>
<span class='title'></span> — Page <span class='pageNumber'></span>
of <span class='totalPages'></span>
</body></html>";

    var headerContent = new StringContent(headerHtml);
    headerContent.Headers.ContentType = new MediaTypeHeaderValue("text/html");
    content.Add(headerContent, "files", "header.html");

    string footerHtml = @"<!DOCTYPE html>
<html><head>
<style>html { font-size: 8px; font-family: Arial; }</style>
</head><body>
<span style='text-align:center;'>CONFIDENTIAL</span>
</body></html>";

    var footerContent = new StringContent(footerHtml);
    footerContent.Headers.ContentType = new MediaTypeHeaderValue("text/html");
    content.Add(footerContent, "files", "footer.html");

    content.Add(new StringContent("true"), "printBackground");

    var endpoint = $"{_gotenbergBaseUrl}/forms/chromium/convert/html";
    using var response = await _httpClient.PostAsync(endpoint, content);
    response.EnsureSuccessStatusCode();

    return await response.Content.ReadAsByteArrayAsync();
}

Concrete constraints:

  • Gotenberg follows Chromium's PDF print header/footer contract: the header and footer HTML files use <span class='pageNumber'>, <span class='totalPages'>, <span class='pageLabel'>, and <span class='title'> CSS classes for injected values.
  • Font size in Gotenberg header/footer HTML must be set on the html element in points — the root font size affects all relative units in the header/footer template.
  • Header and footer HTML files are bundled as separate files in the multipart form alongside the main index.html.

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// IronPDF's HtmlHeaderFooter is configured on the renderer
// Token syntax: {page} and {total-pages} replace Gotenberg's span classes
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 15,  // mm
    HtmlFragment = "<div style='font-size:9px; font-family:Arial; " +
                   "display:flex; justify-content:space-between; padding:0 12px;'>" +
                   "<span></span>" +
                   "<span>Page {page} of {total-pages}</span></div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 10,
    HtmlFragment = "<div style='font-size:8px; font-family:Arial; " +
                   "text-align:center;'>CONFIDENTIAL</div>"
};

string html = "<html><body><p>Document body.</p></body></html>";
using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("document-with-headers.pdf");

The token syntax change is the most common source of silent header/footer rendering bugs during migration. Gotenberg uses Chromium's span class injection (<span class='pageNumber'>) while IronPDF uses its own token format ({page}, {total-pages}). Full header/footer configuration is in the headers and footers guide.

Async in ASP.NET Core (Replacing HTTP Client Pattern)

Gotenberg — ASP.NET Core Controller

using System.Net.Http;
using System.Net.Http.Headers;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { private readonly HttpClient _httpClient; private readonly string _gotenbergUrl;

public ReportController(IHttpClientFactory factory) { _httpClient = factory.CreateClient("gotenberg"); _gotenbergUrl = "http://gotenberg:3000"; }

[HttpGet("{id}/pdf")] public async Task GetReport(int id) { string html = await BuildReportHtmlAsync(id);

using var content = new MultipartFormDataContent(); var htmlContent = new StringContent(html); htmlContent.Headers.ContentType = new MediaTypeHeaderValue("text/html"); content.Add(htmlContent, "files", "index.html");

content.Add(new StringContent("8.27"), "paperWidth"); content.Add(new StringContent("11.69"), "paperHeight");

// Network call to Gotenberg container — adds latency and failure mode using var response = await _httpClient.PostAsync( $"{_gotenbergUrl}/forms/chromium/convert/html", content);

response.EnsureSuccessStatusCode();

byte[] pdfBytes = await response.Content.ReadAsByteArrayAsync(); return File(pdfBytes, "application/pdf", $"report-{id}.pdf"); }

private Task BuildReportHtmlAsync(int id) => Task.FromResult($"

Report {id}

"); }

Concrete constraints:

  • The HTTP round-trip to Gotenberg adds network latency to every PDF generation request. Under concurrent load, this latency compounds.
  • HttpClient configuration (timeouts, retry policies, circuit breakers) is part of the operational surface area that does not exist with in-process rendering.
  • IHttpClientFactory is the correct pattern for HttpClient lifetime management in ASP.NET Core — do not use new HttpClient() directly.
  • The multipart form construction is boilerplate that repeats across every call site.

IronPDF — ASP.NET Core Controller

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { private readonly ChromePdfRenderer _renderer;

// ChromePdfRenderer injected as singleton — configured once in Program.cs public ReportController(ChromePdfRenderer renderer) { _renderer = renderer; }

[HttpGet("{id}/pdf")] public async Task GetReport(int id) { string html = await BuildReportHtmlAsync(id);

// In-process rendering — no HTTP call, no network dependency using var pdf = await _renderer.RenderHtmlAsPdfAsync(html);

return File(pdf.BinaryData, "application/pdf", $"report-{id}.pdf"); }

private Task BuildReportHtmlAsync(int id) => Task.FromResult($"

Report {id}

"); }

// In Program.cs: // builder.Services.AddSingleton(sp => // { // var r = new ChromePdfRenderer(); // r.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4; // r.RenderingOptions.MarginTop = 12.7; // // ... configure once // return r; // }); ```

The ASP.NET Core controller shrinks significantly — the multipart form construction, HttpClient call, and response handling are replaced by a single awaited render call. RenderHtmlAsPdfAsync is genuinely async with no Task.Run() wrapper needed. The async rendering guide covers concurrency and parallel batch generation.

Breaking Changes & Gotchas

  • Inch-to-millimeter unit conversion: Gotenberg's paper dimensions and margins are configured in inches (following Chromium's print API). IronPDF uses millimeters. Convert: mm = inches × 25.4. A common value: 1 inch = 25.4mm, 0.5 inches = 12.7mm. This is a silent layout difference if not converted.
  • Header/footer token syntax: Gotenberg's headers and footers use Chromium's span class injection (<span class='pageNumber'>, <span class='totalPages'>). IronPDF uses {page} and {total-pages} token strings. Old tokens render as literal text in IronPDF.
  • PdfDocument is IDisposable: Gotenberg returns byte[] from HTTP — no disposal needed. IronPDF returns PdfDocument, which implements IDisposable. Every render call must produce a PdfDocument in a using block.
  • Network error handling removed: All HttpResponseMessage.EnsureSuccessStatusCode() calls, HttpRequestException handlers, timeout configurations, and retry policies related to the Gotenberg HTTP call are removed. Replace with try/catch around render calls for IronPDF exceptions.
  • Asset handling changes: Gotenberg bundles CSS files, images, and fonts as multipart form parts. IronPDF uses RenderingOptions.BaseUrl to resolve relative references to a base URL, or assets must be embedded in the HTML as base64 data URIs.
  • No IHttpClientFactory needed: The DI registration for the Gotenberg HttpClient (named or typed) is removed. Replace with builder.Services.AddSingleton<ChromePdfRenderer>().
  • waitDelay string format: Gotenberg accepts duration strings ("500ms", "2s"). IronPDF's WaitFor.RenderDelay() accepts an integer in milliseconds.
  • LibreOffice conversions: Gotenberg's LibreOffice integration (DOCX, XLSX, PPT → PDF) uses LibreOffice, not Chromium. IronPDF's equivalent document conversion capabilities should be verified in official documentation. This is the one Gotenberg capability area where the migration path is not a direct equivalent.
  • Container image changes: The application's Docker image no longer needs to reference or connect to a Gotenberg container. Instead, add the Chromium system library packages to the application container. Verify required packages in IronPDF's Linux deployment guide.
  • License key required: IronPdf.License.LicenseKey must be set before any render call. Gotenberg is open-source with no license key requirement. Omitting IronPDF's key produces watermarked output.

Migration Checklist

  1. Audit all Gotenberg HTTP call sites: List every HttpClient.PostAsync() call to Gotenberg, its configuration (paper size, margins, wait conditions, header/footer files), and its downstream usage of the returned bytes.
  2. Convert paper and margin values from inches to millimeters: For each paperWidth, paperHeight, marginTop, marginBottom, marginLeft, marginRight value in current Gotenberg calls, multiply by 25.4 to get the RenderingOptions equivalent in mm.
  3. Install IronPDF via NuGet: dotnet add package IronPdf.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs before any render call. See the license setup guide.
  5. Register ChromePdfRenderer in DI: Add a singleton registration in Program.cs with the renderer configured using the converted RenderingOptions values from step 2. Remove the IHttpClientFactory registration for the Gotenberg client.
  6. Replace HttpClient.PostAsync() calls: For each Gotenberg call site, replace the multipart form construction, HTTP send, and ReadAsByteArrayAsync() with renderer.RenderHtmlAsPdf(html) or await renderer.RenderHtmlAsPdfAsync(html). Wrap PdfDocument in a using block.
  7. Update header/footer templates: Replace <span class='pageNumber'> with {page} and <span class='totalPages'> with {total-pages} in all header/footer HTML fragments. Move these fragments from separate multipart files to RenderingOptions.HtmlHeader/HtmlFooter.
  8. Update asset references: Replace multipart file bundling for CSS/images with a RenderingOptions.BaseUrl pointing to the asset server, or embed assets as base64 data URIs in the HTML.
  9. Map wait conditions: Replace waitDelay: "500ms" with RenderingOptions.WaitFor.RenderDelay(500). Replace waitForExpression with RenderingOptions.WaitFor.JavaScriptExpression("...").
  10. Remove HTTP error handling: Delete EnsureSuccessStatusCode(), HttpRequestException catch blocks, and timeout/retry policies specific to Gotenberg. Add try/catch for IronPDF's rendering exceptions.
  11. Update container configuration: Remove the Gotenberg container from docker-compose.yml or infrastructure definitions. Add Chromium system library packages to the application container image. Verify required packages for the Linux distribution in use.
  12. Verify LibreOffice conversion paths: If Gotenberg's LibreOffice endpoints (DOCX/XLSX → PDF) are in use, verify IronPDF's equivalent document conversion capability and test with representative files.

Conclusion

When staying on Gotenberg is technically reasonable

Gotenberg is technically reasonable when the deployment architecture already has infrastructure investment in separate document processing services, when memory isolation between the application and the Chromium rendering process is a hard requirement (Gotenberg in its own container keeps OOM conditions from affecting the application), when the team's operational expertise is in container orchestration rather than library management, or when LibreOffice-based Office document conversion is a first-class requirement with no acceptable .NET alternative. Organizations that have built reliable, monitored Gotenberg infrastructure with established health checks and horizontal scaling have a working system with low pressure to change.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when Gotenberg's HTTP latency is measurable in high-throughput generation pipelines; when the separate container creates operational overhead disproportionate to the application's scale; when the application needs post-render PDF manipulation (merge, sign, form-fill, encrypt) and is currently routing PDF bytes through a second manipulation library; when the team wants to simplify the deployment surface by reducing external service dependencies; or when Gotenberg's lack of .NET SDK is creating boilerplate that accumulates across call sites.

What the cutover typically involves at the code level

For a typical ASP.NET Core application with 5–20 Gotenberg call sites, the migration reduces to: inch-to-mm conversion for configuration values, multipart form construction → RenderingOptions property assignment, HttpClient.PostAsync() → renderer.RenderHtmlAsPdfAsync(), ReadAsByteArrayAsync() → pdf.BinaryData, and header/footer token syntax updates. The DI registration changes from a named HttpClient to a singleton ChromePdfRenderer. Error handling changes from HTTP status codes to .NET exceptions. A developer familiar with both systems can typically complete the API swap in a day; the rendering comparison pass (validating output parity, particularly for complex CSS or JavaScript-driven templates) requires additional time proportional to template complexity.

In your current Gotenberg deployment, how much of the HTTP latency, retry complexity, and container operational overhead has accumulated — and is that overhead now larger than the effort of the migration itself?
