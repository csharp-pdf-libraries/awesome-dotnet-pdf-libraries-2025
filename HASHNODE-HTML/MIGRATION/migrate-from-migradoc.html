Migrating from MigraDoc to IronPDF: a .NET team's field guide

a step-by-step .NET migration guide for 2026

Framing

MigraDoc is one of the most established open-source PDF generation libraries in the .NET ecosystem, part of the PDFsharp family from empira Software. It has been in use since the early .NET Framework era and accumulated a generation of applications in its adoption window — particularly in the German-speaking enterprise software market, but with wide international usage as well. Teams that built on MigraDoc did so because it provided a mature, well-documented document object model for PDF generation without a commercial license requirement, and because its companion library PDFsharp allowed low-level PDF manipulation alongside the high-level document model.

The conditions that prompt re-evaluation of MigraDoc have evolved. The library's document model — composing Document, Section, Paragraph, Table, and TextFrame objects in C# code — becomes expensive to maintain as the complexity and variety of document types grows. Modern document requirements tend to be expressed in HTML and CSS from the design phase, and translating those designs back into MigraDoc's element API introduces friction and limits iteration speed. New document types are often prototyped in HTML by front-end developers who have no exposure to MigraDoc's API. When the rendering model no longer matches the design workflow, teams begin comparing alternatives.

This guide covers the migration from MigraDoc to IronPDF for .NET engineers evaluating or executing the switch. MigraDoc is actively maintained; the last release and .NET support range should be verified in official documentation or the PDFsharp/MigraDoc GitHub repository. The migration is classified as Low-to-Medium effort overall — manipulation operations are minimal in MigraDoc and map cleanly, while document generation requires redesign as HTML/CSS. The actual effort is proportional to the number and complexity of MigraDoc document templates in the codebase.

What MigraDoc Is Designed to Do

MigraDoc is an open-source .NET library published by empira Software as part of the PDFsharp suite. It provides a document object model for creating PDFs: the application constructs a Document object, adds Section objects with page layout configuration, and populates sections with content elements — Paragraph, Table, TextFrame, Image, and others. MigraDoc then renders this document model to PDF using PDFsharp as the rendering backend. MigraDoc is not an HTML renderer — it has no Chromium dependency, no CSS parser, and no HTML input capability.

The library distributes via NuGet; the install footprint and current .NET support range (including .NET Core, .NET 5, and later versions) should be verified in official documentation. MigraDoc is MIT-licensed and actively maintained. The primary use case is server-side document generation in applications where a managed, dependency-light PDF library is preferred — reports, invoices, contracts, and any document that a development team is comfortable maintaining in C# element-composition code. MigraDoc does not provide document manipulation beyond what PDFsharp supports directly, and it has limited form, signature, and compliance features.

Architectural Differences

MigraDoc and IronPDF approach document generation from different starting points. MigraDoc builds PDFs by composing layout elements — Paragraph, Table, Image — into a Document object that is rendered by PDFsharp. IronPDF generates PDFs by rendering HTML/CSS through an embedded Chromium engine. Both produce PDF output, but the authoring language and rendering pipeline are entirely different.

The manipulation surface in MigraDoc is thin — most document operations (merge, sign, encrypt) require dropping to PDFsharp directly. IronPDF's PdfDocument exposes a comprehensive manipulation API covering merge, split, forms, signatures, encryption, PDF/A compliance, text extraction, and stamping. Both IronPDF types — ChromePdfRenderer and PdfDocument — implement IDisposable and require using blocks. MigraDoc's PdfDocumentRenderer (the rendering bridge) and PDFsharp's PdfDocument also implement IDisposable, so the pattern is familiar.

The HTML string to PDF guide covers IronPDF's full rendering configuration including paper size, margins, CSS media type, and JavaScript execution. For documents with complex multi-page tables, the page breaks guide covers CSS fragmentation. License initialization is a one-time startup call via IronPdf.License.LicenseKey; see the license setup guide.

Operation Comparisons

Document Creation (The Central Design Change)

MigraDoc — Element-Composition Document

using MigraDoc.DocumentObjectModel;
using MigraDoc.DocumentObjectModel.Tables;
using MigraDoc.Rendering;
using PdfSharp.Pdf;

// MigraDoc builds PDFs by composing a document object model
// PdfDocumentRenderer bridges MigraDoc's model to PDFsharp's output

// Create the MigraDoc document
var document = new Document();

// Add a section with page layout
var section = document.AddSection();
section.PageSetup.PageFormat = PageFormat.A4;
section.PageSetup.LeftMargin = Unit.FromMillimeter(20);
section.PageSetup.RightMargin = Unit.FromMillimeter(20);
section.PageSetup.TopMargin = Unit.FromMillimeter(20);
section.PageSetup.BottomMargin = Unit.FromMillimeter(20);

// Define a paragraph style for the title
var titleStyle = document.Styles.AddStyle("InvoiceTitle", "Normal");
titleStyle.Font.Size = 18;
titleStyle.Font.Bold = true;
titleStyle.Font.Color = Colors.Black;

// Add title paragraph
var titleParagraph = section.AddParagraph("Invoice #1042", "InvoiceTitle");

// Add a horizontal rule via a frame or paragraph border — MigraDoc uses borders
var separator = section.AddParagraph();
separator.Format.Borders.Bottom = new Border
{
    Width = Unit.FromPoint(0.5),
    Color = Colors.Black
};

// Add a table
var table = section.AddTable();
table.Borders.Width = 0.5;

// Add columns with explicit widths
table.AddColumn(Unit.FromMillimeter(100));
table.AddColumn(Unit.FromMillimeter(30));
table.AddColumn(Unit.FromMillimeter(40));

// Header row
var headerRow = table.AddRow();
headerRow.Shading.Color = Color.FromRgb(64, 64, 64);
var headerFont = document.Styles["Normal"].Font.Clone();
headerFont.Color = Colors.White;

headerRow.Cells[0].AddParagraph("Description").Format.Font.ApplyFont(headerFont);
headerRow.Cells[1].AddParagraph("Qty").Format.Font.ApplyFont(headerFont);
headerRow.Cells[2].AddParagraph("Amount").Format.Font.ApplyFont(headerFont);

// Data row
var dataRow = table.AddRow();
dataRow.Cells[0].AddParagraph("Consulting Services");
dataRow.Cells[1].AddParagraph("10");
dataRow.Cells[2].AddParagraph("$1,500.00");

// Render to PDF using PdfDocumentRenderer
var renderer = new PdfDocumentRenderer(false);
renderer.Document = document;
renderer.RenderDocument();

renderer.PdfDocument.Save("invoice.pdf");

Concrete constraints:

  • MigraDoc uses Unit for measurements — Unit.FromMillimeter(), Unit.FromPoint(), Unit.FromCentimeter(). These must be converted to IronPDF's millimeter-based Margin* properties.
  • Column widths in table.AddColumn(Unit) must be redesigned as CSS column widths — either absolute (width: 100mm) or relative (width: 60%).
  • Style definitions (document.Styles.AddStyle()) must be re-expressed as CSS classes.
  • PdfDocumentRenderer is the bridge between MigraDoc's model and PDFsharp's output — it is removed entirely when migrating to IronPDF.
  • Verify exact method names and property paths in official MigraDoc documentation as the API varies between versions and between MigraDoc Foundation and MigraDoc Community editions.

IronPDF — HTML/CSS Equivalent

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;    // mm — matches MigraDoc's TopMargin
renderer.RenderingOptions.MarginBottom = 20;
renderer.RenderingOptions.MarginLeft = 20;
renderer.RenderingOptions.MarginRight = 20;

// MigraDoc's element composition is replaced by HTML/CSS
// CSS handles typography, table layout, borders, and column widths automatically
string html = @"
<!DOCTYPE html>
<html>
<head>
<style>
  body   { font-family: Arial, sans-serif; font-size: 11pt; }
  h1     { font-size: 18pt; font-weight: bold; margin-bottom: 4px; }
  hr     { border: none; border-top: 0.5pt solid #000; margin: 4px 0 10px; }
  table  { width: 100%; border-collapse: collapse; table-layout: fixed; }
  col.desc { width: 57%; }
  col.qty  { width: 17%; }
  col.amt  { width: 26%; }
  thead tr { background: #404040; color: #fff; }
  th, td   { border: 0.5pt solid #999; padding: 4px 6px; font-size: 10pt; }
  th       { text-align: left; }
</style>
</head>
<body>
  <h1>Invoice #1042</h1>
  <hr/>
  <table>
    <colgroup>
      <col class='desc'/><col class='qty'/><col class='amt'/>
    </colgroup>
    <thead>
      <tr><th>Description</th><th>Qty</th><th>Amount</th></tr>
    </thead>
    <tbody>
      <tr><td>Consulting Services</td><td>10</td><td>$1,500.00</td></tr>
    </tbody>
  </table>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("invoice.pdf");

MigraDoc's table.AddColumn(Unit.FromMillimeter(100)) calls become CSS <col> elements with width percentages, maintaining equivalent column proportions. Unit.FromMillimeter(20) margins map directly to RenderingOptions.MarginTop/Bottom/Left/Right = 20. Style definitions move from document.Styles.AddStyle() to CSS classes. The HTML string to PDF guide covers rendering configuration. For multi-page documents with large tables, the page breaks guide covers page-break-inside: avoid and CSS fragmentation.

Headers and Footers with Page Numbers

MigraDoc — Headers and Footers

using MigraDoc.DocumentObjectModel;

var document = new Document();
var section = document.AddSection();
section.PageSetup.PageFormat = PageFormat.A4;

// Enable headers and footers on the section
section.PageSetup.DifferentFirstPageHeaderFooter = false;

// Access the primary header
var header = section.Headers.Primary;
var headerParagraph = header.AddParagraph();
headerParagraph.AddText("Acme Corp — Monthly Report");
headerParagraph.Format.Alignment = ParagraphAlignment.Right;
headerParagraph.Format.Font.Size = 9;

// Access the primary footer
var footer = section.Footers.Primary;
var footerParagraph = footer.AddParagraph();
footerParagraph.Format.Alignment = ParagraphAlignment.Center;
footerParagraph.Format.Font.Size = 8;

// MigraDoc uses special field syntax for page numbers
footerParagraph.AddText("Page ");
footerParagraph.AddPageField();   // inserts current page number
footerParagraph.AddText(" of ");
footerParagraph.AddNumPagesField(); // inserts total page count

// Add body content
section.AddParagraph("Report body content.");

Concrete constraints:

  • MigraDoc's AddPageField() / AddNumPagesField() methods insert live page number fields — this is MigraDoc's equivalent of IronPDF's {page} and {total-pages} tokens.
  • Headers and footers are configured per-section via section.Headers.Primary / section.Footers.Primary — a different first-page header uses section.PageSetup.DifferentFirstPageHeaderFooter = true.
  • Header/footer content is expressed using MigraDoc's paragraph and text API — replace with HTML fragments in IronPDF.

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 15;

// HtmlHeaderFooter replaces MigraDoc's section.Headers/Footers API
// {page} replaces AddPageField(); {total-pages} replaces AddNumPagesField()
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 12,  // mm
    HtmlFragment = "<div style='font-size:9pt; font-family:Arial; " +
                   "text-align:right; padding:0 12px;'>" +
                   "Acme Corp — Monthly Report</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 10,
    HtmlFragment = "<div style='font-size:8pt; font-family:Arial; " +
                   "text-align:center;'>Page {page} of {total-pages}</div>"
};

string html = "<html><body><p>Report body content.</p></body></html>";
using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("report-with-headers.pdf");

AddPageField() → {page} and AddNumPagesField() → {total-pages} is a direct conceptual mapping. Full header/footer configuration including divider lines, height, and HTML fragment content is covered in the headers and footers guide.

PDF Merging (via PDFsharp vs IronPDF)

MigraDoc / PDFsharp — Merging PDFs

using PdfSharp.Pdf;
using PdfSharp.Pdf.IO;

// MigraDoc doesn't provide a merge API — PDFsharp is used directly
// PdfSharp's merge requires opening each document and importing pages

using var outputDocument = new PdfSharp.Pdf.PdfDocument();

string[] sourceFiles = { "document1.pdf", "document2.pdf", "document3.pdf" };

foreach (var filePath in sourceFiles)
{
    // PdfReader.Open() opens a PDF in import mode
    using var inputDocument = PdfReader.Open(filePath, PdfDocumentOpenMode.Import);

    for (int pageIndex = 0; pageIndex < inputDocument.PageCount; pageIndex++)
    {
        // AddPage() with an existing page imports it into the output document
        outputDocument.AddPage(inputDocument.Pages[pageIndex]);
    }
}

outputDocument.Save("merged.pdf");

Concrete constraints:

  • PDFsharp's merge requires PdfDocumentOpenMode.Import — documents opened in this mode cannot be modified, only imported.
  • Pages are imported one at a time in a loop — there is no N-way static merge helper.
  • PDFsharp's PdfDocument is IDisposable — using blocks apply to both the output and all input documents.
  • Verify behavior with PDFs containing interactive forms or signatures — PDFsharp's import may not preserve all PDF features.

IronPDF — PDF Merging

using IronPdf;

using var pdf1 = PdfDocument.FromFile("document1.pdf");
using var pdf2 = PdfDocument.FromFile("document2.pdf");
using var pdf3 = PdfDocument.FromFile("document3.pdf");

// Static merge in a single call — replaces the page-import loop
using var merged = PdfDocument.Merge(pdf1, pdf2, pdf3);
merged.SaveAs("merged.pdf");

The PDFsharp page-import loop is replaced by PdfDocument.Merge(). All source documents are loaded with FromFile() and wrapped in using blocks. The merge and split guide covers N-way merges, page range selection, and split operations.

Multi-Section Documents (Cover Page + Content)

MigraDoc — Multi-Section with Cover

using MigraDoc.DocumentObjectModel;
using MigraDoc.Rendering;

var document = new Document();

// Section 1: Cover page — different margins, no header/footer
var coverSection = document.AddSection();
coverSection.PageSetup.PageFormat = PageFormat.A4;
coverSection.PageSetup.TopMargin = Unit.FromMillimeter(60);
coverSection.PageSetup.LeftMargin = Unit.FromMillimeter(40);
coverSection.PageSetup.RightMargin = Unit.FromMillimeter(40);

var titlePara = coverSection.AddParagraph("Annual Report 2025");
titlePara.Format.Font.Size = 28;
titlePara.Format.Font.Bold = true;
titlePara.Format.Alignment = ParagraphAlignment.Center;

// Section 2: Report content — standard margins with header/footer
var contentSection = document.AddSection();
contentSection.PageSetup.PageFormat = PageFormat.A4;
contentSection.PageSetup.LeftMargin = Unit.FromMillimeter(20);
contentSection.PageSetup.RightMargin = Unit.FromMillimeter(20);
contentSection.PageSetup.TopMargin = Unit.FromMillimeter(20);
contentSection.PageSetup.BottomMargin = Unit.FromMillimeter(20);

var footer = contentSection.Footers.Primary;
var footerPara = footer.AddParagraph();
footerPara.AddText("Page ");
footerPara.AddPageField();

contentSection.AddParagraph("This is the report body.");

var pdfRenderer = new PdfDocumentRenderer(false);
pdfRenderer.Document = document;
pdfRenderer.RenderDocument();
pdfRenderer.PdfDocument.Save("annual-report.pdf");

Concrete constraints:

  • MigraDoc's multi-section documents allow each section to have different page setup, margins, and header/footer configurations.
  • The PdfDocumentRenderer renders all sections into a single PDF — page numbering can be configured to restart per section.
  • Sections in MigraDoc that require different page sizes or orientations can be combined in one document model.

IronPDF — Multi-Section via Render + Merge

using IronPdf;
using IronPdf.Editing;

// Section 1: Cover page — rendered separately with custom margins
var coverRenderer = new ChromePdfRenderer();
coverRenderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
coverRenderer.RenderingOptions.MarginTop = 60;   // mm — matches MigraDoc cover section
coverRenderer.RenderingOptions.MarginLeft = 40;
coverRenderer.RenderingOptions.MarginRight = 40;
coverRenderer.RenderingOptions.MarginBottom = 40;

using var coverPdf = coverRenderer.RenderHtmlAsPdf(@"
<!DOCTYPE html>
<html>
<body style='text-align:center; font-family:Arial;'>
  <h1 style='font-size:28pt; font-weight:bold; margin-top:0;'>Annual Report 2025</h1>
</body>
</html>");

// Section 2: Content — standard margins with footer
var contentRenderer = new ChromePdfRenderer();
contentRenderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
contentRenderer.RenderingOptions.MarginTop = 20;
contentRenderer.RenderingOptions.MarginBottom = 15;
contentRenderer.RenderingOptions.MarginLeft = 20;
contentRenderer.RenderingOptions.MarginRight = 20;
contentRenderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 10,
    HtmlFragment = "<div style='font-size:8pt; font-family:Arial;'>Page {page}</div>"
};

using var contentPdf = contentRenderer.RenderHtmlAsPdf(@"
<!DOCTYPE html>
<html>
<body style='font-family:Arial;'>
  <p>This is the report body.</p>
</body>
</html>");

// Merge cover and content into a single document
using var merged = PdfDocument.Merge(coverPdf, contentPdf);
merged.SaveAs("annual-report.pdf");

Multi-section documents with different page layouts are handled by rendering each section separately and merging the results. This replaces MigraDoc's document.AddSection() pattern. A cover page example is documented in the cover page example.

Breaking Changes & Gotchas

  • Element-composition model has no IronPDF equivalent: MigraDoc's Document, Section, Paragraph, Table, Image, and TextFrame objects have no direct IronPDF equivalent. Every document built using this API must be redesigned as HTML/CSS. This is the dominant effort item.
  • Unit.FromMillimeter() measurement system: MigraDoc uses Unit for all measurements. IronPDF's RenderingOptions.Margin* uses plain double values in millimeters. Unit.FromMillimeter(20) becomes MarginTop = 20. Unit.FromPoint(n) converts as mm = points / 2.835.
  • Style system replaced: MigraDoc's document.Styles.AddStyle() hierarchy is replaced by CSS <style> blocks. Named styles become CSS classes.
  • AddPageField() / AddNumPagesField(): These method calls are replaced by {page} and {total-pages} token strings embedded in the HtmlHeaderFooter.HtmlFragment.
  • PdfDocumentRenderer removed: The PdfDocumentRenderer bridging class is removed entirely. IronPDF's ChromePdfRenderer is its functional replacement — but the input format changes from a MigraDoc Document to an HTML string.
  • Multi-section becomes render + merge: MigraDoc's multi-section documents (different margins per section) are handled in IronPDF by rendering each section separately and merging the resulting PdfDocument objects.
  • PDFsharp merge loop replaced: The PdfReader.Open() + page-import loop pattern from PDFsharp is replaced by PdfDocument.Merge().
  • Namespace change: Remove using MigraDoc.DocumentObjectModel;, using MigraDoc.Rendering;, using PdfSharp.*;, and related directives. Replace with using IronPdf;.
  • License key required: MigraDoc is MIT-licensed with no runtime key. IronPDF requires IronPdf.License.LicenseKey at startup. Omitting it produces watermarked output.
  • Disposal semantics: MigraDoc's PdfDocumentRenderer.PdfDocument and PDFsharp's PdfDocument are IDisposable. IronPDF follows the same pattern — add using blocks consistently.

Migration Checklist

  1. Inventory all MigraDoc Document / Section constructions: List every document type, its sections, paragraph styles, table configurations, image embeds, and header/footer content. This is the HTML/CSS redesign scope.
  2. Design HTML/CSS templates: For each document type, produce an HTML/CSS equivalent and validate it in a browser. Translate Unit.FromMillimeter(n) margin values directly to CSS or RenderingOptions.Margin*. Map column widths from absolute mm to CSS percentages.
  3. Install IronPDF via NuGet: dotnet add package IronPdf. Retain MigraDoc and PDFsharp references until replacement code compiles and tests pass.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs. See the license setup guide.
  5. Update namespaces: Remove using MigraDoc.;, using PdfSharp.; directives. Replace with using IronPdf;.
  6. Register ChromePdfRenderer in DI: Add builder.Services.AddSingleton<ChromePdfRenderer>() with RenderingOptions configured once.
  7. Replace PdfDocumentRenderer.RenderDocument() calls: Map to renderer.RenderHtmlAsPdf(html). Wrap PdfDocument in a using block.
  8. Port header/footer configuration: Replace section.Headers.Primary content with RenderingOptions.HtmlHeader. Replace section.Footers.Primary content with RenderingOptions.HtmlFooter. Replace AddPageField() with {page} and AddNumPagesField() with {total-pages}.
  9. Replace multi-section documents: Render each section separately with section-specific RenderingOptions, then merge with PdfDocument.Merge().
  10. Replace PDFsharp merge loop: Replace the PdfReader.Open() + page-import loop with PdfDocument.Merge(pdf1, pdf2, ...).
  11. Port encryption: Replace PDFsharp's PdfSecuritySettings with IronPDF's pdf.SecuritySettings.*.
  12. Remove MigraDoc and PDFsharp NuGet references: Once all replacements compile and tests pass, remove MigraDoc, PDFsharp, PDFsharp.MigraDoc, and related packages.

Conclusion

When staying on MigraDoc is technically reasonable

MigraDoc is technically reasonable when the application's document types are stable, the team is comfortable maintaining C# element-composition code, the document requirements do not involve modern CSS features (Flexbox, Grid, web fonts, SVG), and MigraDoc's MIT licensing and no-native-dependency profile are constraints worth preserving. Teams with a small, stable set of document templates maintained by developers who know the API have a working system with no immediate pressure to change.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when new document types are being designed in HTML/CSS by front-end developers whose workflow does not include MigraDoc; when existing templates are becoming expensive to modify because the element-composition model does not match design specifications expressed in CSS; when .NET runtime upgrades reveal MigraDoc compatibility questions; when async rendering, Chromium-quality CSS, or compliance output (PDF/A, PDF/UA) are new requirements; or when the team wants to reduce the PDFsharp + MigraDoc dual-library dependency to a single package.

What the cutover typically involves at the code level

The manipulation operations — merge, encrypt, page operations — are a mechanical remapping, and the PDFsharp page-import loop simplifies considerably. The document generation operations require HTML/CSS template development proportional to the number and complexity of document types. For a codebase with 5–15 MigraDoc-generated document types and a development team comfortable with HTML/CSS, the template development is typically the most time-consuming phase. Validating each template visually in a browser before testing with IronPDF reduces the feedback loop significantly.

Looking at your current MigraDoc templates, how many distinct document types are in active maintenance — and how often do design changes require an engineer who understands MigraDoc's API rather than someone who can work in HTML and CSS?
