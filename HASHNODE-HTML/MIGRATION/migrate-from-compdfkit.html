Migrating from ComPDFKit to IronPDF: from install to production

architecture differences, breaking changes, and migration patterns

Framing

Cross-platform PDF SDKs that support both mobile and desktop .NET targets occupy a distinct segment of the library market. Teams building applications that span iOS, Android, Windows, and macOS often choose a single vendor whose SDK covers all targets under one licensing arrangement. The trade-off is that the SDK's API surface must accommodate constraints from the most restrictive target platforms, which can make the desktop or server-side API feel more constrained than a library purpose-built for .NET server workloads.

ComPDFKit is one such cross-platform PDF SDK. It targets mobile platforms alongside Windows and macOS, and it maintains .NET bindings to support .NET application development. Teams that adopted it for a cross-platform mobile project and are now building a separate server-side .NET document processing pipeline may find themselves evaluating whether the SDK designed for cross-platform GUI applications is the right fit for a headless server workload.

This guide covers what .NET engineers need to evaluate when migrating from ComPDFKit to IronPDF. It addresses the architectural differences between the two SDKs, an effort-graded operation mapping, code comparisons for representative operations, and a migration checklist. The migration is classified as Medium effort, reflecting that the core PDF operations map reasonably well while the surrounding API surface — initialization model, object lifecycles, platform-specific configuration — requires careful porting.

What ComPDFKit Is Designed to Do

ComPDFKit is a commercial cross-platform PDF SDK developed by Compdfkit (ComPDFKit). The product is active and the last release should be verified in official documentation. It targets Android, iOS, Windows, macOS, and Web, with .NET bindings available for Windows and macOS desktop development. The install footprint should be verified in official documentation, as cross-platform SDKs of this type often distribute via platform-specific NuGet packages with native binaries.

ComPDFKit's primary design goal is comprehensive PDF processing across platforms: document rendering and display, annotation, form filling, digital signatures, text and content extraction, and basic document manipulation. The SDK is used in enterprise mobile and desktop document management applications where consistent behavior across platforms matters. The rendering approach and whether Chromium is used for any HTML-to-PDF functionality should be verified in official documentation. The primary use case should be verified in official documentation; the SDK is most commonly cited in document viewer, annotation workflow, and mobile document capture contexts.

Architectural Differences

ComPDFKit and IronPDF occupy different positions in the PDF SDK landscape. ComPDFKit is optimized for rendering existing PDFs for human viewing and annotation across mobile and desktop platforms. IronPDF is optimized for generating PDFs from HTML/CSS in server-side .NET applications and manipulating them programmatically. For server-side document generation workloads, the two libraries approach the problem from different starting points.

IronPDF's primary entry point for document generation is ChromePdfRenderer, which renders HTML/CSS to PDF using an embedded Chromium instance. For loading and manipulating existing PDFs, PdfDocument is the central type. Both implement IDisposable and should be used within using blocks. The rendering options reference covers the full Chromium rendering configuration, including paper size, margins, JavaScript execution, and CSS media type. License initialization — IronPdf.License.LicenseKey — must be performed at application startup before any library call; see the license setup guide.

The key architectural difference is that ComPDFKit's API is shaped around the requirements of interactive PDF viewing and annotation (document initialization, page rendering to bitmaps, annotation editing, real-time user interaction), while IronPDF's API is shaped around server-side document generation and batch processing. Teams using ComPDFKit primarily for programmatic form-fill, signing, and extraction operations will find those capabilities map more directly to IronPDF than teams using ComPDFKit's viewer and annotation capabilities.

//    (document class name varies — commonly CPDFDocument or similar)
// 3. Perform operations on the document object
// 4. Save the document to file or stream
// 5. Release or dispose the document object per the SDK's lifecycle requirements

// Note: ComPDFKit's exact .NET API surface should be verified in official documentation
// as the library has multiple platform-specific bindings

Concrete constraints:

  • ComPDFKit likely requires SDK initialization before any document operations
  • Document class names and method signatures vary by platform binding — use the Windows or .NET-specific documentation, not the mobile platform docs.
  • The SDK's native binary dependencies affect how the library must be deployed in server environments.
  • Disposal semantics (whether the document class implements IDisposable) should be verified — improper cleanup of native resources causes memory leaks.

IronPDF — Loading and Saving

using IronPdf;

// No SDK initialization required — set license key once at startup
IronPdf.License.LicenseKey = "YOUR-LICENSE-KEY";

// Load an existing PDF — PdfDocument wraps all document operations
using var pdf = PdfDocument.FromFile("input.pdf");

Console.WriteLine($"Page count: {pdf.PageCount}");

// Modify the document — example: remove the last page
if (pdf.PageCount > 1)
    pdf.RemovePage(pdf.PageCount - 1);

// Save to a new file
pdf.SaveAs("output.pdf");
// PdfDocument disposed automatically at end of using block

IronPDF requires no global SDK initialization. The using block handles resource cleanup deterministically. Output and save options are documented in the export and save guide.

IronPDF — HTML String to PDF

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 10;    // millimeters
renderer.RenderingOptions.MarginBottom = 10;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;

// Chromium renders the HTML — full CSS3, web fonts, and JavaScript supported
using var pdf = renderer.RenderHtmlAsPdf(@"
    <html>
    <head>
      <style>body { font-family: Arial; font-size: 11pt; }</style>
    </head>
    <body>
      <h1>Document Title</h1>
      <p>Generated content.</p>
    </body>
    </html>");

pdf.SaveAs("output.pdf");

The full rendering configuration including JavaScript execution, CSS media type, web font handling, and viewport settings is documented in the HTML string to PDF guide. For documents requiring precise page break control, the page breaks guide covers CSS-based pagination.

// 3. Iterate or access fields by name or index

Concrete constraints:

  • Field access by name vs index: verify whether ComPDFKit uses fully qualified field names for nested fields.
  • Checkbox and radio button value conventions vary by library — test explicitly against actual production form templates.
  • Whether form flattening is available as a first-class operation should be verified in official documentation.
  • The .NET-specific form API may differ from the mobile SDK docs — use the .NET documentation.

IronPDF — Form Filling

using IronPdf;

using var pdf = PdfDocument.FromFile("form-template.pdf");

// Access all fields to inspect available names and types
foreach (var field in pdf.Form.Fields)
{
    Console.WriteLine($"Name: {field.Name}, Value: {field.Value}");
}

// Set values by field name
var applicantName = pdf.Form["applicant_name"];
if (applicantName != null)
    applicantName.Value = "Jane Smith";

// Checkbox — value convention varies by PDF template
var approvedField = pdf.Form["approved"];
if (approvedField != null)
    approvedField.Value = "On";

pdf.SaveAs("filled.pdf");

// Optional: flatten to remove interactivity
// pdf.Form.Flatten();
// pdf.SaveAs("flat.pdf");

The edit forms guide covers all supported field types, value conventions for checkboxes and radio buttons, and form flattening.

// 4. Apply the signature using the configured digital ID

// Note: ComPDFKit's signing API is designed for interactive workflows

// verified specifically in the .NET documentation.

Concrete constraints:

  • ComPDFKit's signing API may be oriented toward interactive user signing rather than batch server-side signing
  • Certificate format support (PFX/P12 vs other formats) should be verified against the IronPDF implementation.
  • Timestamp server support for Long-Term Validation should be explicitly tested.

IronPDF — Digital Signatures

using IronPdf;
using IronPdf.Signing;

using var pdf = PdfDocument.FromFile("unsigned.pdf");

// Configure the signature with a PFX/P12 certificate
var signature = new PdfSignature("certificate.pfx", "pfx-password")
{
    SigningReason = "Document approved",
    SigningLocation = "Chicago, IL"
    // For LTV: TimestampServer = "http://timestamp.example.com"
};

pdf.Sign(signature);
pdf.SaveAs("signed.pdf");

Full signing configuration including HSM-based signing and timestamping is in the digital signatures guide. For hardware security module scenarios, see the HSM signing guide.

Breaking Changes & Gotchas

  • SDK initialization: ComPDFKit likely requires a global initialization call at startup (class and method name
  • License key model change: ComPDFKit's license may be passed to the SDK initializer. IronPDF uses IronPdf.License.LicenseKey = "key" as a standalone startup call. Set it before any PdfDocument or ChromePdfRenderer instantiation.
  • Cross-platform vs server-focused API: ComPDFKit's .NET API is shaped by the need to also support mobile platforms. Some methods that exist in the mobile SDK may not be available in the .NET version, and vice versa. Confirm that every ComPDFKit method being used in the current implementation is available in the .NET-specific documentation.
  • Viewer component gap: If the application embeds ComPDFKit's PDF viewer for user-facing document display, that component requires a separate replacement. IronPDF does not provide an interactive document viewer. This is the single largest scope extension if a viewer is in use.
  • Annotation API orientation: ComPDFKit's annotation API is designed for interactive user workflows — real-time annotation creation and editing in a viewer. IronPDF's annotation API is for programmatic server-side annotation. The mapping is functional for batch annotation but may require restructuring for interactive workflows.
  • Native binary dependencies: ComPDFKit uses native binaries per platform. IronPDF also uses Chromium native binaries on non-Windows platforms. Container and Linux deployments must be re-validated — the required system packages differ.
  • Disposal pattern: ComPDFKit's document disposal model should be verified in official documentation. IronPDF's PdfDocument implements IDisposable; wrap all instances in using blocks.
  • Thread safety: Assume neither SDK's document types are safe to share across threads without explicit documentation to the contrary. Per-operation instantiation is the safe default.
  • Text extraction granularity: If the existing integration uses positional text extraction from ComPDFKit, verify whether pdf.ExtractAllText() provides sufficient data. IronPDF returns plain text without per-word positions or font metadata.
  • Namespace changes: ComPDFKit uses its own namespace. Replace all ComPDFKit using directives with using IronPdf;. Compile errors will surface call sites.

Migration Checklist

  1. Audit ComPDFKit usage in the .NET project: Distinguish between viewer/annotation features (require separate replacement decision) and server-side programmatic features (form-fill, sign, merge, extract). Scope each group separately.
  2. Verify ComPDFKit HTML rendering availability: Confirm whether HTML-to-PDF is available in the .NET SDK. If not, document generation currently handled via a separate tool must be migrated to ChromePdfRenderer.
  3. Install IronPDF via NuGet: dotnet add package IronPdf. Retain ComPDFKit references until replacement code compiles and tests pass.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; before any library call. See the license setup guide.
  5. Remove SDK initialization calls: Locate all ComPDFKit SDK initialization and termination calls and remove them. IronPDF requires no global lifecycle management.
  6. Update namespaces: Replace all ComPDFKit using directives with using IronPdf;. Compile errors identify remaining call sites.
  7. Port document load/save: Replace the ComPDFKit document load pattern with PdfDocument.FromFile(path), save with pdf.SaveAs(path). Add using blocks to all PdfDocument instances.
  8. Port merge, split, and page operations: Replace ComPDFKit equivalents with PdfDocument.Merge(), PdfDocument.CopyPages(), and pdf.RemovePage().
  9. Port form-fill operations: Map ComPDFKit form field access to IronPDF's pdf.Form["name"] and field.Value assignment. Test checkbox and radio button value conventions explicitly against production templates.
  10. Port signing and security: Re-implement digital signatures via PdfSignature and encryption via pdf.SecuritySettings. Test against actual certificate and permission requirements.
  11. Validate on deployment targets: If the application runs on Linux or in Docker, verify IronPDF's Chromium system dependencies in the target environment before deploying.
  12. Remove ComPDFKit package references: Once all tests pass, remove ComPDFKit NuGet packages and native binaries and perform a final build verification.

Conclusion

When staying on ComPDFKit is technically reasonable

ComPDFKit is the appropriate choice when the application requires a unified SDK that spans mobile (iOS, Android) and desktop .NET platforms under a single license. Its PDF viewer component is a core product for applications that embed document display for end users. If the application's PDF requirements are centered on interactive viewing, user-facing annotation, and real-time document editing — rather than server-side batch generation — ComPDFKit's design is a better fit for that use case.

Signals that indicate migration is worth the engineering effort

Migration becomes worth scoping when the .NET server-side workload has grown to the point where a dedicated server-focused PDF library is preferable over a cross-platform SDK; when HTML/CSS-based document generation is the primary requirement and ComPDFKit's HTML rendering support for server contexts is limited; or when the application is containerizing and the mobile-oriented native binary footprint creates deployment friction.

What the cutover typically involves at the code level

The most impactful structural changes are removing the SDK initialization lifecycle calls, updating namespaces, and replacing document load/save patterns with IronPDF equivalents. For integrations that use only programmatic document operations (merge, form-fill, sign, encrypt), the migration is achievable in a focused sprint once the HTML template work (if any) is complete. For applications that also rely on the ComPDFKit viewer, that component requires a separate assessment — it represents a distinct product capability with no straightforward swap.
