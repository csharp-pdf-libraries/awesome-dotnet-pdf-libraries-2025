Migrating from TX TextControl to IronPDF: step-by-step for .NET developers

what changes, what breaks, and what maps cleanly

Framing

TX Text Control is a word-processing component suite from Text Control GmbH, providing WYSIWYG document editing controls for WinForms, WPF, and ASP.NET Core, alongside a server-side document processing API. It has been a commercial product since the early 1990s and occupies a specific position in the .NET component ecosystem: applications that need to embed a fully functional, Microsoft Word-compatible document editor — with tracked changes, mail merge, text frames, and form fields — typically inside a desktop or web application.

Teams re-evaluate TX Text Control in two scenarios. The first: the application's document requirements have narrowed to PDF generation and manipulation, and the full word-processing component suite (editor control, WYSIWYG UI, format import/export for DOCX/RTF/HTML) is no longer needed — only the PDF output side. The second: the application is modernizing its PDF generation from a document-model approach (where content is built by manipulating a TXTextControl.ServerTextControl object) to an HTML-first approach (where content is authored as HTML/CSS and rendered to PDF by a Chromium engine). The engineering effort for either transition is High, because TX Text Control's document model is deeply integrated into the content-building code.

This guide covers the migration from TX Text Control's server-side PDF generation to IronPDF for .NET engineers scoping the work. TX Text Control's current product status and exact .NET version support should be verified in official documentation; the product is understood to target modern .NET. The migration effort is High — reflecting the depth of document-model API integration typical in TX Text Control deployments.

What TX TextControl Is Designed to Do

TX Text Control offers a word-processing document model for .NET applications. The core component, TXTextControl.ServerTextControl, is a server-side (non-visual) text processing engine that can load, create, and export documents without a UI. The visual components (TXTextControl.WinForms.TextControl, TXTextControl.Web.TextControl) provide WYSIWYG editing surfaces. Documents are manipulated through a rich object model covering text formatting, paragraph properties, tables, text frames, headers, footers, fields (including mail merge fields), tracked changes, and annotations.

PDF export is one of TX Text Control's output formats — the ServerTextControl can export a loaded or programmatically built document to PDF via Save() with a PDF stream type. The library also provides mail merge (template documents with merge fields populated from a data source), form field reading and filling, DOCX/RTF/HTML import and export, and digital signatures on PDF output. The install footprint includes licensed NuGet packages; the exact package structure and pricing model should be verified in official documentation. Primary use cases are document management applications, automated document generation with mail merge, and applications requiring embedded WYSIWYG document editing.

Architectural Differences

TX Text Control and IronPDF generate PDFs through different document models. TX Text Control builds a rich document object in memory — loading a DOCX template or constructing content programmatically through its text processing API — and exports that document object to PDF. IronPDF generates PDFs from HTML/CSS rendered by embedded Chromium; existing PDF documents are loaded and manipulated through PdfDocument.

IronPDF's ChromePdfRenderer accepts HTML strings, files, or URLs. For TX Text Control use cases built around loading DOCX templates, IronPDF's DOCX to PDF guide covers direct DOCX conversion without requiring the document object model. For mail merge workflows, the IronPDF equivalent is an HTML template engine (Razor, Scriban, Fluid) that performs data binding before rendering. Both ChromePdfRenderer and PdfDocument implement IDisposable. License initialization is a one-time startup call; see the license setup guide.

The critical architectural point is that TX Text Control's richest capabilities — the WYSIWYG editor control, tracked changes, real-time collaboration, and the full OOXML document object model — have no equivalent in IronPDF. IronPDF is a PDF generation and manipulation library, not a word processor or document editor. Teams migrating only the PDF export portion of a TX Text Control integration will find a bounded scope; teams migrating the entire document editing workflow face a much larger architectural change.

Operation Comparisons

Server-Side Document Build → PDF

TX TextControl — Build Document and Export to PDF

using TXTextControl;
using System.IO;

// TX TextControl ServerTextControl — server-side document processing
// No UI; used for document manipulation and export
using var tc = new ServerTextControl();
tc.Create();  // initialize the text control

// Load existing DOCX template
tc.Load("templates/invoice-template.docx", StreamType.WordprocessingML);

// Manipulate content — navigate to merge fields or bookmarks
// and replace with data values
// (exact API for field navigation varies
foreach (TextField field in tc.TextFields)
{
    if (field.Name == "CustomerName")
        field.Text = "Acme Corp";
    if (field.Name == "InvoiceTotal")
        field.Text = "$1,599.00";
}

// Export to PDF
using var pdfStream = new MemoryStream();
tc.Save(pdfStream, BinaryStreamType.AdobePDF);
byte[] pdfBytes = pdfStream.ToArray();
File.WriteAllBytes("invoice.pdf", pdfBytes);

Concrete constraints:

  • ServerTextControl is IDisposable and requires tc.Create() before use — Dispose() must be called to release unmanaged resources.
  • TX Text Control's OOXML-based field model requires navigating a document object hierarchy. The exact API for field access (TextFields, MergeFields, bookmarks) should be verified in current documentation.
  • ServerTextControl is typically not thread-safe — a new instance per thread or per request is required in web applications. Pooling is complex.
  • TX Text Control's PDF export renders the document model's full OOXML fidelity — font rendering, paragraph spacing, text frames, and table cell shading all depend on the text control's internal layout engine.

IronPDF — HTML Template to PDF

using IronPdf;

// For templates loaded from DOCX without field editing, use DOCX-to-PDF directly
// For templates with data binding, convert to HTML template and use RenderHtmlAsPdf

// Option A: Direct DOCX to PDF (for static documents or pre-filled DOCX)
using var docxPdf = PdfDocument.FromDocx("templates/invoice-template.docx");
docxPdf.SaveAs("invoice-from-docx.pdf");

// Option B: HTML template with data binding (replaces mail merge workflow)
var invoice = new { Customer = "Acme Corp", Total = "$1,599.00", Id = 1042 };

string html = $@"
<!DOCTYPE html>
<html>
<head>
<style>
  body {{ font-family: Arial; font-size: 11pt; }}
  table {{ width: 100%; border-collapse: collapse; }}
  th, td {{ border: 1px solid #ccc; padding: 6px 10px; }}
</style>
</head>
<body>
  <h1>Invoice #{invoice.Id}</h1>
  <p>Customer: {invoice.Customer}</p>
  <p>Total: {invoice.Total}</p>
</body>
</html>";

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;

// PdfDocument is IDisposable — always use a using block
using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("invoice.pdf");

For TX Text Control workflows that load a DOCX and export it unchanged, IronPDF's direct DOCX conversion covers the use case. For workflows that load a DOCX template and populate fields, the IronPDF equivalent is an HTML template with data bound by a .NET template engine. The HTML string to PDF guide covers all rendering configuration.

Mail Merge → HTML Template Engine

TX TextControl — Mail Merge

using TXTextControl;
using TXTextControl.DocumentServer;

// TX TextControl MailMerge — merge a DOCX template with a data source
// MailMerge is a separate class in the DocumentServer component
using var mailMerge = new MailMerge();
// Attach a ServerTextControl
mailMerge.TextComponent = new ServerTextControl();
((ServerTextControl)mailMerge.TextComponent).Create();

// Load DOCX template with merge fields ({{CustomerName}}, etc.)
mailMerge.LoadTemplate("templates/letter-template.docx",
    DocumentServer.FileFormat.InternalUnicodeFormat);

// Provide data as DataTable, DataSet, or IEnumerable
var data = new System.Data.DataTable("Customers");
data.Columns.Add("CustomerName");
data.Columns.Add("Address");
data.Rows.Add("Acme Corp", "123 Main St");

// Merge — produces one output per row
mailMerge.Merge(data, true);

// Export merged document to PDF
using var output = new MemoryStream();
((ServerTextControl)mailMerge.TextComponent).Save(
    output, BinaryStreamType.AdobePDF);
byte[] pdfBytes = output.ToArray();

// Verify exact API — MailMerge and ServerTextControl disposal
((ServerTextControl)mailMerge.TextComponent).Dispose();

Concrete constraints:

  • The MailMerge and ServerTextControl lifecycle management is complex
  • TX Text Control's merge fields are double-brace {{FieldName}} tokens in DOCX templates — these are OOXML-embedded fields, not plain text.
  • Batch merge (one PDF per data row) requires loop management and intermediate stream handling.

IronPDF — HTML Template with Data Binding

using IronPdf;
using System.Collections.Generic;

// Mail merge equivalent: HTML template + .NET data binding + RenderHtmlAsPdf
// One PDF per customer — same loop as TX TextControl batch merge

var customers = new List<(string Name, string Address)>
{
    ("Acme Corp", "123 Main St"),
    ("Beta Industries", "456 Oak Ave")
};

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 20;

// Render one PDF per customer — async for throughput
var renderTasks = customers.Select(async c =>
{
    string html = $@"
    <!DOCTYPE html>
    <html>
    <body style='font-family: Arial; font-size: 11pt;'>
      <p>Dear {c.Name},</p>
      <p>Address: {c.Address}</p>
      <p>Thank you for your business.</p>
    </body>
    </html>";

    using var pdf = await renderer.RenderHtmlAsPdfAsync(html);
    // Return bytes — PdfDocument is disposed by using block
    return (Customer: c.Name, Bytes: pdf.BinaryData);
});

var results = await Task.WhenAll(renderTasks);
foreach (var result in results)
    File.WriteAllBytes($"letter-{result.Customer}.pdf", result.Bytes);

TX Text Control's MailMerge class and DOCX template merge fields are replaced by HTML string construction with C# interpolation (or a template engine for more complex field logic). The async pattern allows parallel rendering of multiple documents — applicable when the batch size warrants it. The async rendering guide covers concurrent rendering patterns.

IronPDF — Digital Signature

using IronPdf;
using IronPdf.Signing;

// Generate PDF first, then sign — or sign on an existing PDF
var renderer = new ChromePdfRenderer();
using var pdf = renderer.RenderHtmlAsPdf("<html><body><p>Document</p></body></html>");

var sig = new PdfSignature("cert.pfx", "pfx-password")
{
    SigningReason   = "Approved for distribution",
    SigningLocation = "Chicago, IL"
};
pdf.Sign(sig);
pdf.SaveAs("signed-document.pdf");

// Or sign an existing PDF
using var existing = PdfDocument.FromFile("existing.pdf");
existing.Sign(sig);
existing.SaveAs("existing-signed.pdf");

IronPDF's PdfSignature and pdf.Sign() replace TX Text Control's export-time signing. The digital signatures guide covers X.509 certificate configuration, visual signature appearance, and multi-signature documents.

DOCX to PDF (Direct Conversion)

For TX Text Control workflows that load a DOCX file and export it to PDF without document model manipulation, IronPDF supports direct DOCX-to-PDF conversion.

using IronPdf;

// Direct DOCX to PDF — replaces ServerTextControl.Load() + Save(PDF)
// No document model manipulation required

using var pdf = PdfDocument.FromDocx("reports/quarterly-report.docx");
pdf.SaveAs("quarterly-report.pdf");

// Or render to memory
byte[] pdfBytes = pdf.BinaryData;

// For DOCX files with complex formatting, verify fidelity against
// TX TextControl output — rendering engines differ

When the TX Text Control integration simply loads a DOCX and exports to PDF without field manipulation, PdfDocument.FromDocx() is the most direct replacement. The DOCX to PDF guide covers format support and fidelity considerations.

Breaking Changes & Gotchas

  • WYSIWYG editor control not in IronPDF: TX Text Control's WinForms, WPF, and ASP.NET Core editor controls are not replaceable with IronPDF. If the application embeds a document editor for end-user authoring, this is outside IronPDF's scope.
  • Tracked changes not in IronPDF: TX Text Control's tracked change model has no equivalent. If reviewed documents with tracked changes are a core workflow, this is a potential blocking gap.
  • Document model → HTML: TX Text Control's programmatic document construction (adding paragraphs, tables, text frames via object model) is replaced by HTML/CSS construction. This is architecturally the most significant change.
  • Mail merge field tokens: TX Text Control uses DOCX merge fields embedded in the OOXML format. The HTML template equivalent uses whatever token syntax the chosen template engine provides.
  • ServerTextControl thread safety: TX Text Control typically requires a new instance per thread. ChromePdfRenderer is designed to be registered as a singleton in DI.
  • DOCX rendering fidelity: For direct DOCX-to-PDF conversion, verify rendering fidelity between TX Text Control's output and IronPDF's DOCX renderer against all document templates.
  • PdfDocument is IDisposable: Wrap render results in using blocks. TX Text Control's ServerTextControl is also IDisposable — the disposal pattern is not new, but the call site structure changes.
  • Namespace change: Remove using TXTextControl; and using TXTextControl.DocumentServer;. Replace with using IronPdf;.
  • License key required: Set IronPdf.License.LicenseKey at startup. TX Text Control has its own per-developer licensing — manage both during transition.

Migration Checklist

  1. Scope the WYSIWYG and tracked changes dependency: Determine whether the migration covers only server-side PDF generation, or also the editor components and tracked changes. The latter is outside IronPDF's scope and requires separate planning.
  2. Audit all ServerTextControl and MailMerge usage: List every tc.Load(), tc.Save(PDF), field/merge field population, form field access, and signature call.
  3. Choose the content strategy per call site: For load-and-export-unchanged DOCX workflows, plan PdfDocument.FromDocx(). For mail merge workflows, plan HTML template + template engine.
  4. Choose a .NET template engine: Select the HTML data binding approach for mail merge replacement — string interpolation, Razor, Scriban, or Fluid.
  5. Install IronPDF via NuGet: dotnet add package IronPdf.
  6. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs. See the license setup guide.
  7. Update namespaces: Remove TX Text Control using directives. Add using IronPdf;.
  8. Register ChromePdfRenderer in DI: Add builder.Services.AddSingleton<ChromePdfRenderer>() (singleton is thread-safe, unlike ServerTextControl).
  9. Replace DOCX-to-PDF paths: Map tc.Load(docx) + tc.Save(PDF) to PdfDocument.FromDocx(path) where no field manipulation is needed.
  10. Replace mail merge paths: Convert DOCX templates to HTML. Replace merge field population with template engine data binding. Wrap PdfDocument in using.
  11. Replace signature calls: Map tc.Save(stream, PDF, sigSettings) to new PdfSignature() + pdf.Sign().
  12. Rendering fidelity comparison: Compare IronPDF output against TX Text Control output for all document templates. Adjust HTML/CSS as needed.

Conclusion

When staying on TX TextControl is technically reasonable

TX Text Control is technically reasonable when the application's core value is WYSIWYG document editing — embedded word-processor controls where end users author or review documents. If tracked changes, real-time collaboration, or inline editing are functional requirements, TX Text Control provides capabilities that have no IronPDF equivalent. It is also appropriate when DOCX export from the application (not just import-to-PDF) is a hard requirement.

Signals that indicate migration is worth the engineering effort

Migration of the PDF generation portion is worth scoping when the application uses TX Text Control exclusively for server-side document-to-PDF conversion and the editor controls are not in the request path; when HTML-first document generation would give the team more flexibility than the document object model; when modern CSS rendering would improve output quality over TX Text Control's OOXML-based layout; or when reducing the licensed component footprint is an architectural objective.

What the cutover typically involves at the code level

The bounded migration path is server-side PDF export: ServerTextControl.Load() + Save(PDF) is replaced by PdfDocument.FromDocx() for static DOCX files, and by HTML template + RenderHtmlAsPdf() for data-driven documents. Mail merge is the most involved conversion — DOCX merge field templates become HTML templates with a .NET template engine. For each content path, the rendering fidelity comparison pass confirms layout parity.
