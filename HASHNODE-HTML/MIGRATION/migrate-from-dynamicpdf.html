Migrating from DynamicPDF to IronPDF: the engineering breakdown

effort estimation, API mapping, and production considerations

Framing

Commercial .NET PDF libraries that have been in the market for an extended period tend to accumulate rich feature sets alongside legacy API surfaces. Teams that adopted such libraries early in their application's life often find themselves carrying abstractions — element-based document layout engines, custom page composition models, proprietary form definition formats — that made sense at adoption time but require ongoing maintenance as the underlying requirements evolve. When HTML and CSS became the dominant paradigm for describing document layout, libraries built around programmatic element composition started to feel like an alternative to an ecosystem most developers already knew.

DynamicPDF (ceTe Software) occupies this position in the .NET PDF market. It is an actively maintained commercial library that provides both a programmatic document generation model (layout engine with elements like Label, Table, FormattedTextArea) and a separate set of tools for PDF manipulation, merging, and form processing. Teams using DynamicPDF have access to a mature, well-documented API, and migrations away from it are typically driven not by library quality but by architectural shifts — moving toward HTML/CSS-based generation, consolidating vendor relationships, or targeting .NET Standard 2.0 / .NET 6+ with a library that has broad compatibility.

This guide is for .NET engineers scoping or executing a migration from DynamicPDF to IronPDF. The migration is classified as Medium effort, reflecting that the manipulation operations (merge, split, form-fill, sign) map cleanly, while the programmatic document generation requires redesign as HTML/CSS templates. Teams with a primarily manipulation-focused integration will find the effort closer to Low; teams with extensive layout engine usage will find it closer to High.

What DynamicPDF Is Designed to Do

DynamicPDF is a commercial .NET PDF library published by ceTe Software. It is actively maintained, distributed via NuGet, and supports .NET Standard 2.0, which provides compatibility with .NET Framework, .NET Core, and .NET 5+ targets. The last release version should be verified in official documentation, as ceTe Software maintains a regular release cadence. The install footprint should be verified in official documentation; DynamicPDF offers separate NuGet packages for different functional areas (generation, merger, rasterizer, viewer).

DynamicPDF's primary design is a document layout engine: the Document class accepts Page objects, each composed of Element subclasses — Label, FormattedTextArea, Image, Table, Line, Rectangle, Hyperlink, Barcode, and many others. This layout engine handles text flow, pagination, and element positioning without requiring the developer to work at PDF coordinate level. DynamicPDF also provides a merger API (PdfMerger, PdfTextReplacer) and a forms API for reading and filling AcroForm fields. The primary use case should be verified in official documentation, but DynamicPDF is commonly found in enterprise document generation pipelines, invoicing systems, report generation, and document assembly workflows where structured layout and programmatic control are preferred over HTML rendering.

Architectural Differences

In the content generation model, the architectural difference between dynamicpdf and ironpdf is. DynamicPDF uses a structured layout engine: the application builds a document by composing Element objects on Page objects, and the engine handles rendering to PDF. IronPDF uses an HTML rendering pipeline: the application provides HTML/CSS, and Chromium renders it to PDF. Both approaches produce the same output format, but the development model, the skill set required, and the resulting template assets are different.

For PDF manipulation operations, both libraries expose comparable APIs. DynamicPDF's PdfMerger maps to IronPDF's PdfDocument.Merge(). DynamicPDF's form field access maps to IronPDF's pdf.Form. The rendering options reference covers IronPDF's full HTML rendering configuration surface, which replaces DynamicPDF's Page and Element composition model for document generation. The async rendering guide covers IronPDF's Task-based async API, which is the natural fit for ASP.NET Core report generation contexts where DynamicPDF's synchronous generation is currently used with Task.Run() wrappers.

IronPDF's two central types are ChromePdfRenderer and PdfDocument. Both implement IDisposable; PdfDocument must be used in a using block. DynamicPDF's Document does not implement IDisposable in the same way

Operation Comparisons

Document Generation (Layout Engine vs HTML)

DynamicPDF — Element-Based Document Generation

using ceTe.DynamicPDF;
using ceTe.DynamicPDF.PageElements;

// DynamicPDF builds documents by composing Element objects on Pages
var document = new Document();

var page = new Page(PageSize.Letter);
document.Pages.Add(page);

// Label: text at a specified position (x, y, width, height)
var titleLabel = new Label("Quarterly Summary Report",
    x: 50, y: 50, width: 500, height: 30,
    font: Font.Helvetica, fontSize: 18);
page.Elements.Add(titleLabel);

// Table: structured data with column widths
var table = new Table2(x: 50, y: 100, width: 500);
table.Columns.Add(new Column(150)); // Region column
table.Columns.Add(new Column(150)); // Revenue column
table.Columns.Add(new Column(100)); // YoY column

var headerRow = table.Rows.Add(20, Font.HelveticaBold, 10, RgbColor.White, RgbColor.Gray);
headerRow.Cells.Add("Region");
headerRow.Cells.Add("Revenue");
headerRow.Cells.Add("YoY %");

var dataRow = table.Rows.Add(20, Font.Helvetica, 10, RgbColor.Black, RgbColor.White);
dataRow.Cells.Add("North");
dataRow.Cells.Add("$124,500");
dataRow.Cells.Add("+8%");

page.Elements.Add(table);

// Draw saves the document to a file path
document.Draw(@"C:\Output\report.pdf");

Concrete constraints:

  • All positioning is coordinate-based (x, y from top-left of the page). Overflow handling, pagination, and element stacking require explicit calculation or DynamicPDF's flow layout elements (FormattedTextArea, OverflowLabel).
  • Font objects use DynamicPDF's type system (Font.Helvetica, Font.HelveticaBold). Custom or embedded fonts use separate registration paths.
  • Table2 (or Table depending on version
  • Every document type built using this model must be redesigned as HTML/CSS for IronPDF.

IronPDF — Equivalent HTML Rendering

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.Letter;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;

// DynamicPDF's Label/Table element model is replaced by HTML and CSS
string html = @"
<!DOCTYPE html>
<html>
<head>
<style>
  body { font-family: Helvetica, Arial, sans-serif; font-size: 10pt; }
  h1 { font-size: 18pt; margin-bottom: 16px; }
  table { width: 100%; border-collapse: collapse; margin-top: 8px; }
  thead th { background: #888; color: white; padding: 6px; text-align: left; }
  tbody td { padding: 6px; border-bottom: 1px solid #ccc; }
</style>
</head>
<body>
  <h1>Quarterly Summary Report</h1>
  <table>
    <thead>
      <tr><th>Region</th><th>Revenue</th><th>YoY %</th></tr>
    </thead>
    <tbody>
      <tr><td>North</td><td>$124,500</td><td>+8%</td></tr>
    </tbody>
  </table>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs(@"C:\Output\report.pdf");

Replacing DynamicPDF's element layout with HTML is the dominant effort item in this migration. HTML/CSS provides automatic text flow, table pagination, and responsive layout that requires explicit configuration in DynamicPDF's element model. The HTML string to PDF guide covers the full rendering configuration. For reports with large tables that must break across pages, the page breaks guide covers CSS-based page break control.

PDF Merging

DynamicPDF — Merging PDFs

using ceTe.DynamicPDF.Merger;

// DynamicPDF uses a dedicated PdfMerger class for file-level operations
var merger = new PdfMerger();

// Add source documents — MergeDocument wraps each input
merger.Append(new MergeDocument(@"C:\Files\document1.pdf"));
merger.Append(new MergeDocument(@"C:\Files\document2.pdf"));
merger.Append(new MergeDocument(@"C:\Files\document3.pdf"));

// Draw writes the merged output
merger.Draw(@"C:\Output\merged.pdf");

Concrete constraints:

  • PdfMerger is in the ceTe.DynamicPDF.Merger namespace — a separate import from the core document generation namespace.
  • MergeDocument is the input wrapper; it can also accept page ranges for partial merges.
  • The merger has no IDisposable implementation
  • Error handling for corrupt or unsupported source files surfaces as exceptions at Draw() time.

IronPDF — Merging PDFs

using IronPdf;

// All PdfDocument instances implement IDisposable
using var pdf1 = PdfDocument.FromFile("document1.pdf");
using var pdf2 = PdfDocument.FromFile("document2.pdf");
using var pdf3 = PdfDocument.FromFile("document3.pdf");

// Single call — N-way merge in argument order
using var merged = PdfDocument.Merge(pdf1, pdf2, pdf3);
merged.SaveAs("merged.pdf");

IronPDF consolidates merge, split, and page operations on the PdfDocument type. The merge and split guide covers partial merges, page range extraction, and split-by-page-count patterns.

Filling PDF Forms

DynamicPDF — Form Filling

using ceTe.DynamicPDF.Merger;

// DynamicPDF form filling uses MergeDocument's form field access
var mergeDoc = new MergeDocument(@"C:\Forms\form-template.pdf");

// Access fields from the PDF's AcroForm
var form = mergeDoc.Form;

// Set text field value
var nameField = form.Fields["applicant_name"] as PdfFormTextField;
if (nameField != null)
    nameField.Value = "Jane Smith";

// Set checkbox — DynamicPDF uses a checked boolean or On/Off value
// Verify exact API in official documentation
var checkField = form.Fields["approved"];
if (checkField != null)
    checkField.Value = "On";

// Flatten removes interactivity
// mergeDoc.Form.Flatten();

mergeDoc.Draw(@"C:\Output\filled-form.pdf");

Concrete constraints:

  • DynamicPDF's form field access is through MergeDocument.Form.Fields[name]
  • Typed field classes may be available; verify PdfFormTextField and related types in official documentation.
  • The form filling API is in the Merger package, not the core document generation package.

IronPDF — Form Filling

using IronPdf;

using var pdf = PdfDocument.FromFile(@"C:\Forms\form-template.pdf");

// Field access by name — uniform string value for all types
var nameField = pdf.Form["applicant_name"];
if (nameField != null)
    nameField.Value = "Jane Smith";

var approvedField = pdf.Form["approved"];
if (approvedField != null)
    approvedField.Value = "On"; // Verify exact value per template

pdf.SaveAs(@"C:\Output\filled-form.pdf");

// Flatten:
// pdf.Form.Flatten();
// pdf.SaveAs("flat.pdf");

Full field type support, value conventions, and flattening behavior are documented in the edit forms guide. The move from DynamicPDF's MergeDocument-based form access to IronPDF's PdfDocument.Form is the primary structural change in this operation.

Headers and Footers

DynamicPDF — Headers and Footers

using ceTe.DynamicPDF;
using ceTe.DynamicPDF.PageElements;

var document = new Document();

// DynamicPDF handles headers/footers as elements positioned on each page
// or via template pages that are applied across all pages
// A common pattern uses a PageTemplate
var template = new PageTemplate();

// Header text element — positioned in the header zone
var header = new Label("CONFIDENTIAL | Q1 2026",
    x: 50, y: 10, width: 500, height: 20,
    font: Font.Helvetica, fontSize: 9);
template.Elements.Add(header);

// Page number in footer zone
var pageNum = new PageNumberingLabel("Page %%CP%% of %%TP%%",
    x: 50, y: 770, width: 500, height: 20,
    font: Font.Helvetica, fontSize: 8);
template.Elements.Add(pageNum);

document.Template = template;

var page = new Page(PageSize.Letter);
page.Elements.Add(new Label("Body content here.", 50, 100, 500, 20));
document.Pages.Add(page);

document.Draw("report-with-header.pdf");

Concrete constraints:

  • DynamicPDF uses PageNumberingLabel with %%CP%% (current page) and %%TP%% (total pages) tokens — these differ from IronPDF's {page} and {total-pages} tokens.
  • PageTemplate is the pattern for applying consistent headers/footers across all pages — a design-time configuration.
  • Header/footer element positions are absolute coordinates measured from the page edge.

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.Letter;

// HTML fragments with automatic token resolution per page
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 18,
    HtmlFragment = "<div style='font-size:9px; font-family:Helvetica, Arial;'>" +
                   "CONFIDENTIAL | Q1 2026</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 12,
    HtmlFragment = "<div style='font-size:8px; font-family:Helvetica, Arial; text-align:center;'>" +
                   "Page {page} of {total-pages}</div>"
};

using var pdf = renderer.RenderHtmlAsPdf("<html><body><p>Body content.</p></body></html>");
pdf.SaveAs("report-with-header.pdf");

IronPDF's header/footer model supports full HTML including images, multi-column layouts, and CSS styling. Token names differ from DynamicPDF: %%CP%% → {page}, %%TP%% → {total-pages}. Full configuration is in the headers and footers guide.

Breaking Changes & Gotchas

  • Layout engine has no equivalent: DynamicPDF's Element-based layout engine (Label, Table2, FormattedTextArea, Image, Barcode) does not map to any IronPDF API. Every document built using the layout engine must be redesigned as HTML/CSS. This is the largest single source of migration effort.
  • %%CP%% / %%TP%% token syntax: DynamicPDF uses %%CP%% for current page and %%TP%% for total pages in PageNumberingLabel. IronPDF uses {page} and {total-pages}. Replacing these in header/footer configuration is a simple text substitution but must be done systematically.
  • Separate NuGet packages: DynamicPDF splits functionality across multiple NuGet packages (core, merger, rasterizer, etc.). IronPDF consolidates all operations in a single package. References to DynamicPDF merger-specific classes (PdfMerger, MergeDocument) may be in different namespaces from the core document generation classes.
  • Document.Draw() vs pdf.SaveAs(): DynamicPDF uses Draw() for output; IronPDF uses SaveAs(). This is a simple rename but affects every output call site.
  • Disposal pattern: DynamicPDF's Document and PdfMerger should be verified for IDisposable implementation in official documentation. IronPDF's PdfDocument and ChromePdfRenderer both implement IDisposable — wrap all instances in using blocks.
  • Namespace change: Replace using ceTe.DynamicPDF;, using ceTe.DynamicPDF.PageElements;, using ceTe.DynamicPDF.Merger; with using IronPdf;. Compile errors guide the remaining work.
  • License key required: IronPdf.License.LicenseKey must be set before the first render call. DynamicPDF uses its own license mechanism
  • Thread safety: DynamicPDF's document objects are not thread-safe — assume the same for IronPDF. Per-operation instantiation is the safe default.
  • Barcode elements: DynamicPDF includes a first-class Barcode element class. IronPDF does not provide barcode generation natively — embed barcodes via HTML <img> tags using a separate barcode generation library (IronBarcode or similar).
  • Linux deployment: DynamicPDF's Linux support should be verified in official documentation. IronPDF on Linux requires Chromium system libraries. Validate container base images before deploying.

Migration Checklist

  1. Triage DynamicPDF usage by package: Separate document generation (core, layout engine) from merger operations. Scope each group independently — layout engine code requires HTML/CSS redesign while merger code maps mechanically.
  2. Design HTML/CSS templates to replace element layouts: For each document type built using DynamicPDF's Document/Page/Element model, produce an HTML template and validate it in a browser before testing with IronPDF.
  3. Install IronPDF via NuGet: dotnet add package IronPdf. Retain DynamicPDF references until replacement code compiles and tests pass.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs before any render call. See the license setup guide.
  5. Update namespaces: Replace all using ceTe.DynamicPDF.*; directives with using IronPdf;. Compile errors identify every affected file.
  6. Replace Document.Draw() with ChromePdfRenderer.RenderHtmlAsPdf() + pdf.SaveAs(): For each generation call, provide the HTML template and wrap the PdfDocument result in a using block.
  7. Replace PdfMerger with PdfDocument.Merge(): Remove MergeDocument wrappers, load sources via PdfDocument.FromFile(), and call PdfDocument.Merge().
  8. Port header/footer configuration: Replace PageTemplate + PageNumberingLabel with RenderingOptions.HtmlHeader/HtmlFooter. Update token syntax: %%CP%% → {page}, %%TP%% → {total-pages}.
  9. Port form-fill operations: Replace MergeDocument.Form.Fields[name] with pdf.Form["name"] and uniform field.Value assignment. Test all field types.
  10. Port security and signing: Re-implement encryption and digital signatures using pdf.SecuritySettings and PdfSignature. Verify permission flag and certificate format mapping.
  11. Address barcode requirements: Replace DynamicPDF barcode elements with HTML <img> tags referencing barcode images generated by a separate library.
  12. Remove DynamicPDF NuGet packages: Once all replacements compile and tests pass, remove all ceTe.DynamicPDF.* package references and perform a final build verification.

Conclusion

When staying on DynamicPDF is technically reasonable

DynamicPDF is a reasonable choice when the application's document generation requires DynamicPDF's structured element layout engine — particularly for complex table-driven reports with multi-page flow, barcodes, and precise coordinate control — and the team prefers a layout-engine model over HTML/CSS templating. Teams already invested in DynamicPDF's API and with stable, non-HTML document templates have little immediate pressure to migrate.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when the application is adding document types that are more naturally expressed as HTML/CSS than as DynamicPDF element compositions; when JavaScript-rendered content, web fonts, or modern CSS are needed in PDF output; when a single-package .NET PDF solution is preferred over DynamicPDF's multi-package model; or when the team's skill set is shifting toward web-technology templating and maintaining the DynamicPDF layout engine knowledge is a staffing concern.

What the cutover typically involves at the code level

The merger and form-fill portions of a DynamicPDF migration are mechanical: namespace updates, PdfMerger → PdfDocument.Merge(), and Draw() → SaveAs(). The layout engine portion is a template development project: producing HTML/CSS equivalents for each Document/Page/Element composition, which requires design work proportional to template complexity. A realistic estimate for a medium-sized integration (10–20 document types, primarily tabular reports) with existing DynamicPDF layout templates is two to four weeks for the HTML template development phase, plus one week for the API remapping phase.
