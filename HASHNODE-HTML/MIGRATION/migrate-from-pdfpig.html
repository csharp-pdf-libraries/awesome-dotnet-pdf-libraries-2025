Migrating from PdfPig to IronPDF: a .NET engineering guide

API mapping, gotchas, and a migration checklist

Framing

An open-source, MIT-licensed library focused entirely on reading and parsing existing PDF documents, pdfpig occupies a specific and valuable position in the .net pdf ecosystem: it is. Teams that adopt PdfPig do so for its extraction capabilities — particularly its structured access to text with per-word and per-character bounding box coordinates, which makes it a natural fit for document analysis, content indexing, data extraction pipelines, and machine learning preprocessing workflows where positional layout information matters.

Re-evaluation of PdfPig typically arises when application requirements expand beyond reading into creation, manipulation, or compliance. PdfPig does not generate PDFs, does not merge or split documents, does not sign or encrypt, and does not produce PDF/A output. Teams that originally adopted it for a specific extraction use case often find, as the application grows, that they are assembling a stack of libraries — PdfPig for reading, another library for generation, a third for signing — and the total integration surface becomes more complex than a single library would require.

This guide covers the migration from PdfPig to IronPDF for .NET engineers evaluating the switch, or for teams adding IronPDF alongside PdfPig as a consolidation strategy. PdfPig is a PDF parser and reader, not an HTML renderer — the migration story centers on replacing its extraction API with IronPDF equivalents, with the important caveat that PdfPig's per-word and per-letter bounding box data is a genuine differentiator that IronPDF's plain text extraction does not replicate.

What PdfPig Is Designed to Do

PdfPig (NuGet package UglyToad.PdfPig) is an open-source .NET library for reading and parsing PDF documents. Published under the MIT license, it is actively maintained on GitHub. The library provides: loading PDF documents from file or stream, extracting text as a structured collection of Word objects (each with bounding box coordinates), extracting individual Letter objects with precise per-character positions, reading document metadata (title, author, producer, creation date), accessing page dimensions, extracting embedded images, and reading PDF annotations and form field names.

PdfPig's primary differentiator is its structured extraction model — text is returned not as a flat string but as a hierarchy of Page, Word, and Letter objects, each carrying position information (bounding boxes in PDF coordinate space). This makes it directly usable for spatial text analysis, coordinate-based data extraction, table detection, and NLP preprocessing pipelines where layout matters. PdfPig does not generate PDFs from any source (HTML, document model, or otherwise), does not provide merge/split operations, and does not offer security or compliance features.

Architectural Differences

PdfPig and IronPDF approach PDF processing from different starting points. PdfPig is a PDF reader — it parses the PDF byte structure and exposes document content as structured .NET objects. IronPDF both generates PDFs from HTML/CSS via embedded Chromium and reads/manipulates existing PDFs through a managed API.

IronPDF's PdfDocument.FromFile() loads existing PDFs. pdf.ExtractAllText() and pdf.ExtractTextFromPage(n) extract plain text. pdf.RasterizeToImageFiles() renders pages to images. For PDF generation, ChromePdfRenderer.RenderHtmlAsPdf() uses Chromium for full CSS3 rendering. The extract text and images guide covers IronPDF's extraction options. License initialization is a one-time startup call; see the license setup guide.

The critical architectural difference is extraction granularity. PdfPig's Word and Letter objects carry bounding box coordinates — the text and its spatial position. IronPDF's extraction returns plain text strings without positional data. For applications where the text content alone is sufficient (search indexing, content comparison, document summarization), IronPDF's extraction API is a clean replacement. For applications where coordinate positions drive downstream logic (table detection, form field location, layout analysis), this is a potential blocking gap that must be evaluated before committing to migration.

Operation Comparisons

Opening a PDF and Extracting Text

PdfPig — Text Extraction

using UglyToad.PdfPig;
using UglyToad.PdfPig.Content;

// PdfPig.PdfDocument is IDisposable — use a using block
using var document = PdfDocument.Open("source.pdf");

int pageCount = document.NumberOfPages;
Console.WriteLine($"Pages: {pageCount}");

var fullText = new System.Text.StringBuilder();

// PdfPig pages are 1-based (page 1 is the first page)
for (int pageNum = 1; pageNum <= pageCount; pageNum++)
{
    Page page = document.GetPage(pageNum);

    // GetWords() returns IEnumerable<Word> — each Word has:
    //   word.Text          — the word string
    //   word.BoundingBox   — the PDF coordinate bounding box
    //   word.Letters       — per-character Letter objects with individual boxes
    foreach (Word word in page.GetWords())
    {
        fullText.Append(word.Text).Append(' ');
    }
    fullText.AppendLine();
}

Console.WriteLine(fullText.ToString());

Concrete constraints:

  • PdfPig uses 1-based page numbers — document.GetPage(1) returns the first page, not page index 0. IronPDF uses 0-based indices throughout — all page indices must be decremented by 1 during migration.
  • page.GetWords() returns structured Word objects with bounding box coordinates (word.BoundingBox in PDF coordinate space). IronPDF's ExtractAllText() returns a flat string — positional data is not preserved.
  • page.Letters provides per-character Letter objects with individual bounding boxes — the most granular extraction PdfPig offers. There is no IronPDF equivalent.
  • PdfPig's coordinate system has origin at the bottom-left of the page (PDF coordinate space). Downstream code that uses bounding box coordinates must account for this if migrating to a different coordinate model.
  • PdfDocument is IDisposable in PdfPig — the using pattern is already correct.

IronPDF — Text Extraction

using IronPdf;

// IronPDF uses 0-based page indices (PdfPig uses 1-based)
using var pdf = PdfDocument.FromFile("source.pdf");

int pageCount = pdf.PageCount;
Console.WriteLine($"Pages: {pageCount}");

// Extract all text in one call — returns flat string, no positional data
string allText = pdf.ExtractAllText();

// Or extract per page — note: 0-based index (not 1-based like PdfPig)
for (int i = 0; i < pageCount; i++)
{
    string pageText = pdf.ExtractTextFromPage(i); // i=0 is first page
    Console.WriteLine($"Page {i + 1}: {pageText.Length} chars");
}

The page indexing convention change from 1-based (PdfPig) to 0-based (IronPDF) affects every page-level operation. Systematically decrement all page index arguments by 1. The extract text and images guide covers all extraction options including image extraction.

Structured Word Extraction with Bounding Boxes

PdfPig — Structured Extraction (Position-Aware)

using UglyToad.PdfPig;
using UglyToad.PdfPig.Content;
using UglyToad.PdfPig.Geometry;

// PdfPig structured extraction — positional word data
using var document = PdfDocument.Open("invoice.pdf");
Page firstPage = document.GetPage(1);

// Use case: find all text in a specific region of the page
// PdfPig coordinates: origin at bottom-left, y increases upward
// A4 page is 595 × 842 points
// Define a region: right-side column from y=600 to y=700
var targetRegion = new PdfRectangle(297, 600, 595, 700);

var wordsInRegion = new System.Collections.Generic.List<string>();
foreach (Word word in firstPage.GetWords())
{
    // Check if word's bounding box intersects the target region
    if (word.BoundingBox.IntersectsWith(targetRegion))
    {
        wordsInRegion.Add(word.Text);
    }
}

Console.WriteLine($"Words in region: {string.Join(", ", wordsInRegion)}");

// PdfPig also supports per-letter extraction for precise positioning:
foreach (Letter letter in firstPage.Letters)
{
    // letter.Value         — the character
    // letter.GlyphRectangle — bounding box for this character
    // letter.FontSize      — rendered font size
    // letter.Font.Name     — font name
}

Concrete constraints:

  • PdfPig's spatial text extraction is its primary differentiator. Applications that use bounding boxes to locate invoice totals, form field values, table cells, or other positionally-meaningful content cannot directly migrate this logic to IronPDF's plain text extraction.
  • PdfRectangle coordinates are in PDF units (points), origin at bottom-left. Any coordinate-based downstream logic is tightly coupled to this model.
  • page.Letters provides font name, font size, and rendering matrix per character — this data is useful for font analysis and rendering reproduction.
  • This is the migration's hardest gap: if coordinate-based extraction is the core use case, evaluate whether IronPDF's extraction meets requirements before proceeding.

IronPDF — Plain Text Extraction (No Positional Data)

using IronPdf;

using var pdf = PdfDocument.FromFile("invoice.pdf");

// IronPDF extracts plain text — no bounding box coordinates
// Appropriate for: full-text search, content comparison, NLP preprocessing
// NOT appropriate for: coordinate-based region extraction, table detection

string pageText = pdf.ExtractTextFromPage(0); // 0-based; was page 1 in PdfPig

// For workflows that only need text content, this is a direct replacement
Console.WriteLine(pageText);

// IronPDF can also extract images from the PDF
var images = pdf.ExtractAllImages();
Console.WriteLine($"Extracted {images.Count} images.");

If the downstream workflow uses only the text content — for search indexing, content validation, or document comparison — IronPDF's ExtractTextFromPage() is a functional replacement. For workflows that require spatial positioning, the gap must be addressed architecturally. Options include retaining PdfPig alongside IronPDF for extraction-only operations, or evaluating whether IronPDF's API surface includes coordinate-based extraction. The extract text and images guide covers all current extraction options.

Reading Metadata

PdfPig — Document Metadata

using UglyToad.PdfPig;

using var document = PdfDocument.Open("source.pdf");

// PdfPig exposes metadata via the Information property
var info = document.Information;

string title    = info.Title;
string author   = info.Author;
string subject  = info.Subject;
string keywords = info.Keywords;
string creator  = info.Creator;
string producer = info.Producer;
// Creation and modification dates
string created  = info.CreationDate;
string modified = info.ModifiedDate;

Console.WriteLine($"Title:   {title}");
Console.WriteLine($"Author:  {author}");
Console.WriteLine($"Creator: {creator}");

Concrete constraints:

  • PdfPig returns dates as strings — parsing them to DateTime requires format handling.
  • document.Information returns null or empty properties if the PDF has no Info dictionary.

IronPDF — Document Metadata

using IronPdf;

using var pdf = PdfDocument.FromFile("source.pdf");

// IronPDF metadata via typed properties — same pattern as PdfPig
string title    = pdf.MetaData.Title;
string author   = pdf.MetaData.Author;
string subject  = pdf.MetaData.Subject;
string keywords = pdf.MetaData.Keywords;
string creator  = pdf.MetaData.Creator;

Console.WriteLine($"Title:   {title}");
Console.WriteLine($"Author:  {author}");

// IronPDF also allows writing metadata — PdfPig is read-only
pdf.MetaData.Title  = "Updated Title";
pdf.MetaData.Author = "Updated Author";
pdf.SaveAs("updated-metadata.pdf");

Metadata reading maps directly between libraries — both expose typed properties rather than string key lookups. The property names are consistent. IronPDF additionally allows writing metadata, which extends beyond PdfPig's read-only scope. The metadata guide covers all available properties.

HTML to PDF Generation (New Capability)

PdfPig does not generate PDFs. Teams using PdfPig for extraction alongside a separate generation library can consolidate both into IronPDF.

using IronPdf;

// HTML to PDF generation — not available in PdfPig
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Generated Report</h1>
  <p>This PDF was generated from HTML — not possible with PdfPig.</p>
  <p>After generating, extraction and manipulation are available on the same object.</p>
</body>
</html>";

using var generated = renderer.RenderHtmlAsPdf(html);

// Text extraction is available on the generated document immediately
string extractedText = generated.ExtractAllText();
Console.WriteLine($"Generated and extracted: {extractedText.Length} chars");

generated.SaveAs("generated-and-extracted.pdf");

Applications that used PdfPig for extraction and a separate library for generation can consolidate both operations into IronPDF. The HTML string to PDF guide covers generation configuration.

Breaking Changes & Gotchas

  • Page index convention: 1-based → 0-based: PdfPig uses 1-based page numbering throughout — document.GetPage(1) is the first page. IronPDF uses 0-based indices — pdf.ExtractTextFromPage(0) is the first page. Every page index reference must be decremented by 1. This is the most systematic gotcha in the migration.
  • Bounding box data not preserved: PdfPig's Word.BoundingBox and Letter.GlyphRectangle provide spatial coordinates for each extracted text element. IronPDF's extraction returns plain text strings without positional data. This is the primary potential blocking gap — evaluate carefully if downstream code uses bounding boxes.
  • No per-letter font data: PdfPig's Letter objects expose font name, size, and rendering matrix. IronPDF's extraction does not provide per-character font metadata.
  • PdfDocument naming: PdfPig's primary type is UglyToad.PdfPig.PdfDocument. IronPDF's type is IronPdf.PdfDocument. If both packages are present during migration, fully qualify all PdfDocument references.
  • document.NumberOfPages → pdf.PageCount: Property name change. Also note the indexing difference — NumberOfPages of 5 means pages are accessed at indices 1–5 in PdfPig, vs 0–4 in IronPDF.
  • Namespace change: Remove using UglyToad.PdfPig; and related namespaces. Replace with using IronPdf;.
  • License key required: PdfPig is MIT-licensed with no runtime key. IronPDF requires IronPdf.License.LicenseKey at startup.
  • PDF coordinate system: PdfPig uses PDF coordinate space (origin bottom-left, y increases upward). Any downstream code that processes bounding box coordinates assumes this orientation. If migrating to a different system, coordinate transformations may be needed.
  • IDisposable pattern: PdfPig's PdfDocument is IDisposable — the using pattern is already established. IronPDF follows the same pattern.

Migration Checklist

  1. Evaluate the bounding box gap first: Before any code changes, confirm whether downstream systems use PdfPig's word/letter bounding box coordinates. This is the only potential blocking gap in the migration. If only plain text is needed, proceed. If spatial positioning is required, evaluate IronPDF's extraction API or plan to retain PdfPig for extraction.
  2. Audit all PdfPig call sites: List every PdfDocument.Open(), GetPage(), GetWords(), Letters, Information.*, and any annotation/form access. Record the page index used at each call.
  3. Install IronPDF via NuGet: dotnet add package IronPdf. Retain PdfPig until replacement code compiles.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs. See the license setup guide.
  5. Update namespaces: Remove using UglyToad.PdfPig; and sub-namespaces. Add using IronPdf;. Fully qualify any PdfDocument type that is ambiguous.
  6. Replace PdfDocument.Open(path): Map to PdfDocument.FromFile(path) in a using block.
  7. Replace page access and text extraction: Replace document.GetPage(n) + page.GetWords() loop with pdf.ExtractTextFromPage(n-1). Replace full-document loops with pdf.ExtractAllText(). Decrement all page indices by 1.
  8. Replace metadata access: Map document.Information.Title → pdf.MetaData.Title, etc.
  9. Replace image extraction: Map PdfPig's image extraction to pdf.ExtractAllImages().
  10. Add HTML generation if consolidating: If a separate HTML-to-PDF library is also being replaced, register ChromePdfRenderer in DI and migrate generation call sites.
  11. Remove PdfPig NuGet package: Once all replacements compile and tests pass, remove UglyToad.PdfPig.
  12. Verify page index correctness: Run extraction tests on multi-page documents and confirm the correct page content is returned at each index.

Conclusion

When staying on PdfPig is technically reasonable

PdfPig is actively maintained and MIT-licensed — there is no maintenance or licensing pressure driving migration. Staying on PdfPig is technically reasonable when structured text extraction with bounding box coordinates is the core use case, when the open-source licensing model is a hard requirement, and when the application's PDF requirements are limited to reading and extraction without generation, manipulation, or compliance. For document analysis, NLP preprocessing, and spatial text extraction workflows, PdfPig's granular extraction model is a genuine capability that has no direct equivalent in IronPDF.

Signals that indicate migration is worth the engineering effort

Migration (or library consolidation) is worth scoping when PdfPig is used alongside one or more other PDF libraries and reducing the integration surface to a single library is a goal; when new requirements (HTML generation, form filling, signing, PDF/A, encryption) extend beyond PdfPig's read-only scope; when async rendering support is needed; or when the application is being simplified and a single library that handles both extraction and generation would reduce dependency management overhead.

What the cutover typically involves at the code level

For plain text extraction use cases, the migration is a systematic remapping: PdfDocument.Open() → PdfDocument.FromFile(), GetWords() loop → ExtractAllText(), and a careful decrement of all page indices from 1-based to 0-based. The page index change is the most pervasive systematic edit. For applications where bounding box data drives downstream logic, the migration requires an architectural decision about whether that logic can be adapted to work with plain text.

In your current PdfPig integration, how many call sites use word.BoundingBox or page.Letters for spatial logic versus how many simply iterate word.Text — and does that ratio suggest a full migration or a hybrid approach where PdfPig handles extraction and IronPDF handles generation?
