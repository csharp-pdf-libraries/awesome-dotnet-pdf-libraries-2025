Migrating from QuestPDF to IronPDF: a .NET team's field guide

a step-by-step .NET migration guide for 2026

Framing

PDF generation requirements in .NET applications tend to evolve. Early in a project, a library that makes it easy to produce structured, data-driven documents — invoices, reports, certificates — fits well. As applications grow, requirements often expand to include browser-rendered content, compliance standards like PDF/A, or operational features like digital signing that were not part of the original scope. The library that served the initial use case may or may not fit the expanded requirements.

QuestPDF has gained adoption in the .NET ecosystem as a fluent, code-first document composition library. Its API encourages developers to think about document structure in terms of components and layout constraints rather than in terms of HTML or coordinate systems. For teams comfortable with C# and averse to embedding HTML in application code, that design point is appealing.

Migration considerations arise in a few recurring scenarios: a team needs HTML-based rendering to match web output, the document generation surface has expanded to include URL capture or web-content archiving, compliance requirements demand features (PDF/A, digital signatures, redaction) that are outside QuestPDF's scope, or the fluent composition model has become a maintenance liability as document templates grow in complexity. This guide provides a neutral technical map of both libraries and what a migration involves.

What QuestPDF Is Designed to Do

QuestPDF is a .NET library for programmatic PDF document composition. Its architecture centers on a fluent C# API that represents documents as a tree of layout elements: containers, columns, rows, text blocks, images, and tables. Developers construct document structure entirely in C# code without writing HTML or CSS. The library's rendering engine translates the component tree into PDF output, handling pagination and element placement according to the layout constraints defined in the API.

QuestPDF's primary design goal is deterministic, code-driven document layout. This suits use cases where document structure is well-defined and data-driven: invoices with predictable column layouts, reports with structured sections, certificates with fixed template positions. Because the API is pure C#, documents are composed using the same language constructs as the rest of the application — loops, conditionals, and LINQ are natural tools. The library is open source, actively maintained, and supports .NET 6 and later. Its install footprint includes native binaries shipped alongside the NuGet packages, which affects container image sizing and deployment pipeline configuration.

Architectural Differences

Wider than in most same-category migrations, because the two libraries operate from different source models, the architectural gap between questpdf and ironpdf is. QuestPDF renders from a C# component tree; IronPDF renders from HTML. This is not a surface-level API difference — it reflects a fundamental difference in authoring model.

IronPDF's HTML to PDF rendering pipeline uses Chromium internally. A developer provides HTML — as a string, a file, or a URL — and the library produces a PdfDocument. CSS, JavaScript, web fonts, and SVG are supported as part of the rendering surface. For teams whose source of truth is an HTML template (Razor views, Blazor components, static HTML files), this maps directly. For teams whose documents are authored entirely as C# component trees with no HTML representation, migration requires either building HTML equivalents of existing templates or adopting a hybrid approach where some documents are ported and others are retained.

From an architectural standpoint, IronPDF's ChromePdfRenderer is a stateless service object that accepts input and produces a PdfDocument. The document object is IDisposable and carries standard PDF manipulation methods — merge, split, sign, apply passwords. QuestPDF's execution model is different: document generation is driven by implementing IDocument and calling Document.Create(), with the full document tree evaluated at generation time. Neither is inherently superior; the right fit depends on whether the authoring model matches the team's workflow.

Operation Comparisons

Basic Structured Document

QuestPDF — Structured Document

QuestPDF documents are composed by implementing IDocument and building a component tree inside Compose().

using QuestPDF.Fluent;
using QuestPDF.Helpers;
using QuestPDF.Infrastructure;

// QuestPDF license must be set at startup
QuestPDF.Settings.License = LicenseType.Community; // or Professional/Enterprise

public class InvoiceDocument : IDocument
{
    private readonly InvoiceModel _model;

    public InvoiceDocument(InvoiceModel model)
    {
        _model = model;
    }

    public DocumentMetadata GetMetadata() => DocumentMetadata.Default;

    public void Compose(IDocumentContainer container)
    {
        container.Page(page =>
        {
            page.Size(PageSizes.A4);
            page.Margin(2, Unit.Centimetre);

            page.Header().Text($"Invoice #{_model.InvoiceNumber}").FontSize(20).Bold();

            page.Content().Table(table =>
            {
                table.ColumnsDefinition(cols =>
                {
                    cols.RelativeColumn(3); // Description
                    cols.RelativeColumn(1); // Amount
                });

                foreach (var item in _model.LineItems)
                {
                    table.Cell().Text(item.Description);
                    table.Cell().AlignRight().Text($"{item.Amount:C}");
                }
            });

            page.Footer().AlignCenter().Text(text =>
            {
                text.Span("Page ");
                text.CurrentPageNumber();
                text.Span(" of ");
                text.TotalPages();
            });
        });
    }
}

// Usage
var document = new InvoiceDocument(model);
document.GeneratePdf("invoice.pdf");

Key constraints:

  • The entire document structure is C# code; HTML/CSS knowledge is not required.
  • Pagination is handled automatically by QuestPDF's layout engine.
  • Unit testing layout is straightforward because the component tree is inspectable C#.
  • The authoring model does not translate to HTML; porting requires building HTML equivalents.

IronPDF — Structured Document

IronPDF renders from HTML, so the invoice template is expressed as an HTML string (or Razor view). The HTML string to PDF guide covers template patterns for data-driven documents.

using IronPdf;
using System;
using System.Text;

License.LicenseKey = Environment.GetEnvironmentVariable("IRONPDF_LICENSE_KEY");

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20; // mm
renderer.RenderingOptions.MarginBottom = 20;
renderer.RenderingOptions.MarginLeft = 20;
renderer.RenderingOptions.MarginRight = 20;

// Build HTML — typically from a Razor template or StringBuilder
var html = new StringBuilder();
html.Append("<html><head><style>");
html.Append("body { font-family: Arial, sans-serif; font-size: 12px; }");
html.Append("table { width: 100%; border-collapse: collapse; }");
html.Append("th, td { padding: 8px; text-align: left; border-bottom: 1px solid #ddd; }");
html.Append("td.amount { text-align: right; }");
html.Append("</style></head><body>");
html.Append($"<h1>Invoice #{model.InvoiceNumber}</h1>");
html.Append("<table><tr><th>Description</th><th>Amount</th></tr>");

foreach (var item in model.LineItems)
{
    html.Append($"<tr><td>{System.Web.HttpUtility.HtmlEncode(item.Description)}</td>");
    html.Append($"<td class='amount'>{item.Amount:C}</td></tr>");
}

html.Append("</table></body></html>");

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    HtmlFragment = "<div style='text-align:center;font-size:10px;'>Page {page} of {total-pages}</div>",
    Height = 15
};

using var pdf = renderer.RenderHtmlAsPdf(html.ToString());
pdf.SaveAs("invoice.pdf");

For complex templates, Razor views or a templating engine like Scriban or Fluid are common approaches — the HTML is generated separately and passed to RenderHtmlAsPdf.

Page Headers and Footers with Page Numbers

QuestPDF — Headers and Footers

using QuestPDF.Fluent;
using QuestPDF.Helpers;
using QuestPDF.Infrastructure;

// Inside IDocument.Compose():
container.Page(page =>
{
    page.Size(PageSizes.A4);
    page.Margin(1.5f, Unit.Centimetre);

    page.Header()
        .PaddingBottom(10)
        .Row(row =>
        {
            row.RelativeItem().Text("Company Name").FontSize(14).Bold();
            row.ConstantItem(100).Text(text =>
            {
                text.Span("Page ");
                text.CurrentPageNumber();
                text.Span(" / ");
                text.TotalPages();
            });
        });

    page.Content().Text("Document body content here.");

    page.Footer()
        .AlignCenter()
        .Text("Confidential — For internal use only")
        .FontSize(9)
        .FontColor(Colors.Grey.Medium);
});

Key constraints:

  • Header and footer are part of the page component definition; they are tightly coupled to the layout tree.
  • Page number tokens are available via CurrentPageNumber() and TotalPages() fluent methods.
  • Styling is applied via the fluent API; the complete styling vocabulary is QuestPDF-specific.

IronPDF — Headers and Footers

IronPDF's header/footer model is configuration on the renderer, separate from the document HTML. The HTML headers and footers example covers advanced patterns.

using IronPdf;
using System;

License.LicenseKey = Environment.GetEnvironmentVariable("IRONPDF_LICENSE_KEY");

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    HtmlFragment = @"
        <div style='display:flex; justify-content:space-between; font-size:11px; padding:0 10px;'>
            <span>Company Name</span>
            <span>Page {page} / {total-pages}</span>
        </div>",
    Height = 20
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    HtmlFragment = "<div style='text-align:center; font-size:9px; color:#888;'>Confidential — For internal use only</div>",
    Height = 15
};

using var pdf = renderer.RenderHtmlAsPdf("<p>Document body content here.</p>");
pdf.SaveAs("output.pdf");

Merging Multiple Documents

QuestPDF — Merging Documents

QuestPDF does not include a native API for merging separately generated PDFs. Teams typically use a third-party library such as PdfSharpCore or iTextSharp for merge operations, or structure their documents to include all content in a single generation pass.

// QuestPDF does not merge PDFs natively.
// A common pattern generates all sections in one Document.Create() call:
using QuestPDF.Fluent;
using QuestPDF.Infrastructure;

var combinedPdf = Document.Create(container =>
{
    // Section 1
    container.Page(page =>
    {
        page.Content().Text("Section 1");
    });

    // Section 2
    container.Page(page =>
    {
        page.Content().Text("Section 2");
    });
});

combinedPdf.GeneratePdf("combined.pdf");
// If sections are generated by different code paths, a separate merging library is needed.

Key constraints:

  • No native cross-document merge; all content must be in one generation call, or a third dependency is added.
  • This is a meaningful gap for architectures that generate documents independently and assemble them downstream.

IronPDF — Merging Documents

IronPDF supports merging natively. The merge and split guide covers static and dynamic merge scenarios.

using IronPdf;
using System;
using System.Collections.Generic;

License.LicenseKey = Environment.GetEnvironmentVariable("IRONPDF_LICENSE_KEY");

var renderer = new ChromePdfRenderer();

// Generate individual documents
using var section1 = renderer.RenderHtmlAsPdf("<p>Section 1 content.</p>");
using var section2 = renderer.RenderHtmlAsPdf("<p>Section 2 content.</p>");

// Merge into a single document
using var merged = PdfDocument.Merge(new List<PdfDocument> { section1, section2 });
merged.SaveAs("combined.pdf");

Custom Fonts

QuestPDF — Custom Fonts

using QuestPDF.Fluent;
using QuestPDF.Infrastructure;

// QuestPDF uses font families registered via FontManager
// Custom font registration
container.Page(page =>
{
    page.Content()
        .Text("Custom font text")
        .FontFamily("MyCustomFont"); // Font must be registered at startup
});

Key constraints:

  • Fonts must be registered with QuestPDF's font manager before use.
  • Font availability is controlled at the application layer, not in a stylesheet.

IronPDF — Custom Fonts

IronPDF respects web fonts declared in HTML/CSS. The web fonts and icons guide covers local font files, Google Fonts, and icon font integration.

using IronPdf;
using System;

License.LicenseKey = Environment.GetEnvironmentVariable("IRONPDF_LICENSE_KEY");

var renderer = new ChromePdfRenderer();

// Custom font via CSS @font-face
var html = @"
<html>
<head>
<style>
@font-face {
    font-family: 'MyCustomFont';
    src: url('/fonts/MyCustomFont.woff2') format('woff2');
}
body { font-family: 'MyCustomFont', sans-serif; font-size: 14px; }
</style>
</head>
<body><p>Custom font text rendered by IronPDF.</p></body>
</html>";

// Use SetBaseUrlAs to resolve relative paths for local assets
using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("custom-font.pdf");

Breaking Changes & Gotchas

  • Authoring model change: This is the most significant migration challenge. QuestPDF's C# component tree has no direct equivalent in IronPDF. Every document template must be rewritten as HTML/CSS. Teams without existing HTML templates should budget substantial time for this work.
  • Pagination behavior: QuestPDF's layout engine controls pagination automatically based on content height and page constraints. IronPDF relies on Chromium's CSS pagination, which uses page-break-before, page-break-after, and page-break-inside CSS properties. Complex layouts may paginate differently after migration; test thoroughly.
  • Font handling: QuestPDF uses registered font families. IronPDF uses CSS @font-face or system fonts. Teams that use custom fonts must verify that font files are accessible at render time and correctly referenced in CSS.
  • Unit system: QuestPDF uses configurable units (cm, mm, points). IronPDF's margin and dimension configuration uses millimetres. CSS properties inside HTML use standard CSS units (px, em, rem, mm). Be explicit about unit conversions.
  • Namespace changes: Replace QuestPDF.Fluent, QuestPDF.Infrastructure, QuestPDF.Helpers with IronPdf and IronPdf.Rendering.
  • License model: QuestPDF uses QuestPDF.Settings.License = LicenseType.*. IronPDF uses IronPdf.License.LicenseKey = "...". Both must be set at application startup.
  • Testing approach: QuestPDF layouts are pure C# and straightforward to unit test with component inspection. IronPDF's HTML/CSS output is best validated by rendering to PDF and comparing output — a visual regression testing approach. Teams that rely heavily on unit tests for layout should plan for test infrastructure changes.
  • Native binary footprint: Both libraries ship native binaries in their NuGet packages. IronPDF's Chromium-based renderer is typically larger than QuestPDF's native rendering library. Audit container image sizes if base image size is a constraint.
  • Multi-package installation: Verify the current IronPDF installation requirements — some rendering scenarios may require platform-specific packages. Review the IronPDF docs for current guidance.

Migration Checklist

  1. Swap NuGet packages: Remove QuestPDF from your .csproj. Add IronPdf (and any platform-specific packages per current documentation). Run dotnet restore.
  2. Configure the license key: Replace QuestPDF.Settings.License = LicenseType.* with IronPdf.License.LicenseKey = "..." at application startup. See the license setup guide.
  3. Update namespaces: Replace using QuestPDF.Fluent, using QuestPDF.Infrastructure, using QuestPDF.Helpers with using IronPdf and using IronPdf.Rendering.
  4. Inventory document templates: List all IDocument implementations. Categorize by complexity: simple text, table-based layouts, image-heavy, custom-font documents. This inventory drives the porting effort estimate.
  5. Build HTML equivalents: For each IDocument implementation, create an HTML/CSS template that produces equivalent visual output. Razor partial views or a templating engine (Scriban, Fluid, Handlebars.NET) are common approaches for keeping C# logic and HTML templates cleanly separated.
  6. Replace generation calls: Replace document.GeneratePdf(path) with renderer.RenderHtmlAsPdf(html); pdf.SaveAs(path). Replace document.GeneratePdf() (bytes) with pdf.BinaryData.
  7. Migrate headers and footers: Replace page.Header() and page.Footer() component trees with RenderingOptions.HtmlHeader and HtmlFooter configurations. Map page number tokens from QuestPDF's fluent methods to IronPDF's {page} / {total-pages} syntax.
  8. Remap font handling: Replace QuestPDF font manager registrations with CSS @font-face declarations in your HTML templates.
  9. Update page setup: Map page.Size(), page.Margin(), and orientation settings to RenderingOptions.PaperSize, MarginTop/Bottom/Left/Right, and PaperOrientation.
  10. Handle merge/split operations: Remove any third-party merge libraries used to supplement QuestPDF. Replace with PdfDocument.Merge() and the IronPDF split API.
  11. Validate pagination: Test complex multi-page documents. Add page-break-before, page-break-after, or page-break-inside: avoid CSS rules where QuestPDF's automatic pagination produced specific break behavior.
  12. Update test coverage: Replace component-tree unit tests with rendered-output comparison tests. Establish a baseline PDF snapshot for each document template and validate against it in CI.

Conclusion

When staying on QuestPDF is technically reasonable

QuestPDF is a defensible choice when documents are exclusively data-driven with well-defined structure, the team prefers authoring document layout in C# rather than HTML/CSS, and compliance requirements (PDF/A, digital signatures) are not on the roadmap. Applications that already have extensive unit test coverage of QuestPDF component trees benefit from keeping that investment intact. If the document surface area is stable and the current output quality meets requirements, migration introduces risk without proportional benefit.

Signals that indicate migration is worth the engineering effort

Migration becomes worth evaluating when documents need to match web-rendered output (Razor views, Blazor components), when compliance requirements like PDF/A or digital signatures emerge, or when the team needs to capture URL-based content as PDFs. Teams that find themselves maintaining both QuestPDF and a separate PDF manipulation library for merge, split, or security operations — because QuestPDF does not cover those cases — may find a consolidation argument. Growth in template complexity, particularly templates that would benefit from CSS layout primitives like grid or flexbox, is another signal.

What the cutover typically involves at the code level

The primary work is template rewriting. There is no shortcut for converting a C# component tree to HTML/CSS; each IDocument implementation requires an HTML equivalent. In practice, teams often accelerate this by introducing a Razor templating step — generating HTML from existing data models using view templates, then passing that HTML to IronPDF. Supporting infrastructure changes (license configuration, namespace updates, generation call replacement) are mechanical. The highest-risk areas are complex table layouts and documents with precise pagination requirements; these warrant the most explicit testing effort.
