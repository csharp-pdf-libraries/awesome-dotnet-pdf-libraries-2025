Migrating from GrabzIt to IronPDF: API mapping and migration checklist

before-and-after code, risk assessment, and a migration checklist

Framing

Cloud-based document generation APIs occupy a distinct niche in the .NET PDF landscape. Rather than shipping a rendering engine alongside the application, these services handle all rendering infrastructure on their end — the application sends content, receives a file back, and pays per request or per volume. GrabzIt is one of the more established services in this space, providing screenshot and PDF capture from URLs and HTML via an HTTP API with official .NET client SDKs. Teams choose this model to eliminate deployment concerns: no native binaries, no Chromium dependencies, no infrastructure to maintain.

Re-evaluation of cloud PDF services follows familiar patterns. Per-request pricing that was negligible at low volume becomes visible as document generation scales. Sending HTML content containing business data to a third-party service raises data residency and confidentiality questions that grow harder to navigate under regulations like GDPR or sector-specific compliance requirements. Network round-trips add latency that compounds under concurrent load, and service availability becomes a dependency in the application's reliability calculus. When any of these factors tip past a threshold, teams begin evaluating whether an in-process rendering library would better serve the application's current operating model.

This guide covers the migration from GrabzIt to IronPDF for .NET engineers evaluating or executing the switch. GrabzIt's .NET SDK targets .NET Standard 2.0, making it compatible across .NET Framework and .NET Core / .NET 5+ targets. IronPDF also supports .NET Standard 2.0 and above. The migration is classified as Low effort because both systems use Chromium for HTML rendering — output fidelity is highly consistent — and the conceptual operation (HTML in, PDF out) is identical. The migration work is replacing SDK API calls with in-process renderer calls and updating how results are handled.

What GrabzIt Is Designed to Do

GrabzIt is a commercial cloud service providing web capture capabilities: URL screenshots, HTML-to-image conversion, HTML-to-PDF conversion, web scraping, and video capture. Its .NET SDK (GrabzIt.Client on NuGet) wraps GrabzIt's HTTP API, handling authentication, request construction, and result retrieval. The .NET Standard 2.0 target makes the SDK compatible with both .NET Framework and modern .NET runtimes. The install footprint should be verified in official documentation, but the managed SDK has no native binary dependencies — all rendering work happens on GrabzIt's cloud infrastructure.

The PDF-specific workflow in GrabzIt's .NET SDK involves creating a GrabzItClient with API credentials, calling HTMLToPDF() or URLToPDF() with options, and either saving to disk or retrieving bytes. GrabzIt's options model covers paper size, orientation, margins, page breaks, and JavaScript delay. The service handles Chromium rendering on its own servers and returns the completed PDF. GrabzIt's architecture is entirely asynchronous — results can be retrieved via callback URL or polled. The primary use case should be verified in official documentation, but GrabzIt is typically used for web archiving, report generation from URLs, and HTML-to-PDF export where infrastructure simplicity is the priority.

Architectural Differences

GrabzIt and IronPDF share Chromium as the rendering engine — the same HTML and CSS that GrabzIt renders in its cloud infrastructure, IronPDF renders in-process in the application. The architectural difference is the boundary: GrabzIt renders remotely and the application receives bytes over HTTP; IronPDF renders locally and the application works with a PdfDocument object directly.

IronPDF's two primary types are ChromePdfRenderer (for rendering HTML to PDF) and PdfDocument (for the resulting document and all manipulation operations). Both implement IDisposable. The HTML string to PDF guide covers the full rendering configuration — paper size, margins, CSS media type, JavaScript execution, and web font handling — which replaces GrabzIt's HTMLToPDFOptions. The rendering options reference covers all available rendering parameters. License initialization is a one-time startup call via IronPdf.License.LicenseKey; see the license setup guide.

The shift from GrabzIt to IronPDF removes the network dependency entirely, changes the failure mode from HTTP errors to .NET exceptions, and makes post-render PDF operations (merge, sign, form-fill, encrypt) available without an additional library. It introduces a different operational consideration: IronPDF on Linux requires Chromium system library packages in the application container, whereas GrabzIt's managed SDK has no binary dependencies.

Operation Comparisons

HTML String to PDF

GrabzIt — HTML String to PDF

using GrabzIt;
using GrabzIt.Parameters;

// GrabzItClient requires API key credentials
// Keys are obtained from the GrabzIt account dashboard
var grabzIt = new GrabzItClient("YOUR_APPLICATION_KEY", "YOUR_APPLICATION_SECRET");

// Configure PDF options
var options = new HTMLToPDFOptions
{
    Format = PDFPageSize.A4,
    Orientation = PDFPageOrientation.Portrait,
    // Margins in mm
    MarginTop = 10,
    MarginBottom = 10,
    MarginLeft = 10,
    MarginRight = 10,
    // Allow JavaScript to execute before capture
    JavaScriptTime = 500  // milliseconds
};

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #1042</h1>
  <p>Total: $1,599.00</p>
</body>
</html>";

// HTMLToPDF configures the capture request
grabzIt.HTMLToPDF(html, options);

// SaveTo sends the request to GrabzIt's cloud and saves the result
// This is a synchronous blocking call — waits for the cloud render to complete
grabzIt.SaveTo("invoice.pdf");

Concrete constraints:

  • GrabzItClient requires API credentials (applicationKey, applicationSecret) obtained from the GrabzIt dashboard. Remove all credential management code during migration.
  • SaveTo() sends the configured request to GrabzIt's cloud infrastructure and blocks until the result is received. Under concurrent load, multiple threads each block on separate HTTP round-trips.
  • GetResult() retrieves the PDF as a byte[] without saving to disk — the in-memory equivalent of SaveTo().
  • All rendering happens on GrabzIt's servers — the HTML content is transmitted over the network, raising data handling considerations.
  • GrabzIt also supports a callback/webhook model for non-blocking async capture

IronPDF — HTML String to PDF

using IronPdf;

// ChromePdfRenderer is stateful and reusable — register as singleton in DI
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.PaperOrientation = IronPdf.Rendering.PdfPaperOrientation.Portrait;
renderer.RenderingOptions.MarginTop = 10;     // millimeters
renderer.RenderingOptions.MarginBottom = 10;
renderer.RenderingOptions.MarginLeft = 10;
renderer.RenderingOptions.MarginRight = 10;
renderer.RenderingOptions.WaitFor.RenderDelay(500); // 500ms JavaScript wait

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #1042</h1>
  <p>Total: $1,599.00</p>
</body>
</html>";

// PdfDocument is IDisposable — always use a using block
using var pdf = renderer.RenderHtmlAsPdf(html);

// Access bytes or save directly
byte[] pdfBytes = pdf.BinaryData;         // equivalent to GrabzIt's GetResult()
pdf.SaveAs("invoice.pdf");                // equivalent to GrabzIt's SaveTo()

The credential removal is the first structural change — GrabzItClient construction with API keys is replaced by a ChromePdfRenderer instance with no credentials. Full rendering configuration is in the HTML string to PDF guide. Verify GrabzIt's margin unit (mm or points) against the existing configuration before mapping to IronPDF's millimeter-based Margin* properties.

URL to PDF

GrabzIt — URL to PDF

using GrabzIt;
using GrabzIt.Parameters;

var grabzIt = new GrabzItClient("YOUR_APPLICATION_KEY", "YOUR_APPLICATION_SECRET");

var options = new URLToPDFOptions
{
    Format = PDFPageSize.A4,
    // Wait for JavaScript to execute before capture
    WaitForElement = ".report-loaded",  // CSS selector
    // Custom cookies for authenticated pages
    // Cookies = "session=abc123",       // verify property name and format
};

// URLToPDF captures the live URL via GrabzIt's cloud infrastructure
grabzIt.URLToPDF("https://reports.example.com/dashboard", options);
byte[] pdfBytes = grabzIt.GetResult();

Concrete constraints:

  • GrabzIt's URL capture uses its own cloud Chromium instances to fetch and render the target URL. Authentication cookies must be passed in the request options
  • WaitForElement (or equivalent property
  • The target URL must be publicly accessible from GrabzIt's servers (or the application must provide authentication credentials). URLs behind corporate VPNs or local networks are not accessible.
  • GetResult() returns null if the capture fails — check for null before using the byte array.

IronPDF — URL to PDF

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// WaitFor element replaces GrabzIt's WaitForElement option
renderer.RenderingOptions.WaitFor.HtmlElement(".report-loaded");

// Cookie injection for authenticated URLs
renderer.RenderingOptions.CustomCookies =
    new System.Collections.Generic.Dictionary<string, string>
    {
        { "session", "abc123" }
    };

using var pdf = renderer.RenderUrlAsPdf("https://reports.example.com/dashboard");
byte[] pdfBytes = pdf.BinaryData;

Unlike GrabzIt's cloud fetch, IronPDF's URL rendering runs the Chromium engine in-process — the application server must be able to reach the target URL directly. URLs behind authentication can be handled via cookie injection rather than requiring the URL to be publicly accessible. The URL to PDF guide covers cookie injection, custom headers, and all WaitFor conditions.

Async in ASP.NET Core

GrabzIt — Blocking ASP.NET Core Integration

using GrabzIt;
using GrabzIt.Parameters;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { [HttpGet("{id}/pdf")] public IActionResult GetReport(int id) { // GrabzIt's SDK uses a synchronous blocking model // Direct use in an async ASP.NET Core action blocks the thread pool var grabzIt = new GrabzItClient( "YOUR_APPLICATION_KEY", "YOUR_APPLICATION_SECRET");

grabzIt.HTMLToPDF( $"

Report {id}

", new HTMLToPDFOptions { Format = PDFPageSize.A4 });

byte[] pdfBytes = grabzIt.GetResult();

if (pdfBytes == null) return StatusCode(503, "PDF generation failed");

return File(pdfBytes, "application/pdf", $"report-{id}.pdf"); } }

Concrete constraints:

  • GrabzItClient.GetResult() is synchronous and blocks until the HTTP round-trip to GrabzIt's servers completes. In an ASP.NET Core controller, this blocks a thread for the duration of the network call.
  • GrabzItClient is typically instantiated per-request when using inline credentials
  • GetResult() returns null on failure — production code must null-check before using the result.
  • Creating a new GrabzItClient per request carries initialization overhead; consider whether a shared instance is safe.

IronPDF — Async ASP.NET Core Integration

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { private readonly ChromePdfRenderer _renderer;

// Singleton renderer injected via DI — configured once in Program.cs public ReportController(ChromePdfRenderer renderer) { _renderer = renderer; }

[HttpGet("{id}/pdf")] public async Task GetReport(int id) { string html = $"

Report {id}

";

// RenderHtmlAsPdfAsync is genuinely async — no blocking using var pdf = await _renderer.RenderHtmlAsPdfAsync(html);

return File(pdf.BinaryData, "application/pdf", $"report-{id}.pdf"); } }

// Program.cs registration: // builder.Services.AddSingleton(sp => { // var r = new ChromePdfRenderer(); // r.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4; // return r; // });

RenderHtmlAsPdfAsync is genuinely async — it does not block the thread pool waiting on a network call. The per-request GrabzItClient instantiation pattern is replaced by a singleton ChromePdfRenderer registered in DI. The async rendering guide covers concurrent rendering patterns and batch generation.

Post-Render PDF Operations (New Capability)

GrabzIt returns bytes — all post-render operations require a separate PDF manipulation library in the .NET application. With IronPDF, the same PdfDocument instance returned by the renderer exposes the full manipulation API.

using IronPdf;
using IronPdf.Signing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Render section PDFs from individual HTML templates
using var section1 = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Section 1</h1></body></html>");
using var section2 = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Section 2</h1></body></html>");
using var section3 = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Section 3</h1></body></html>");

// Merge all sections into a single document
using var merged = PdfDocument.Merge(section1, section2, section3);

// Apply a digital signature to the merged document
var signature = new PdfSignature("cert.pfx", "pfx-password")
{
    SigningReason = "Approved for distribution",
    SigningContact = "approver@example.com"
};
merged.Sign(signature);

merged.SaveAs("signed-report.pdf");

Post-render operations like multi-section merge and digital signatures previously required a separate PDF library to process GrabzIt's byte output. With IronPDF, these operations are available on the PdfDocument directly. The merge and split guide and digital signatures guide cover these operations.

Breaking Changes & Gotchas

  • Credential removal: GrabzItClient requires applicationKey and applicationSecret at construction. IronPDF uses IronPdf.License.LicenseKey set once at startup — no per-instance credentials. Remove all credential storage and injection for the GrabzIt client.
  • GetResult() null safety: GrabzIt's GetResult() returns null on failure. IronPDF throws a typed .NET exception on rendering failure. Remove all if (pdfBytes == null) null checks after GetResult() and replace with try/catch around render calls.
  • PdfDocument is IDisposable: GrabzIt returns byte[] — no disposal required. IronPDF returns PdfDocument, which implements IDisposable. Every render call must produce a PdfDocument in a using block. Missing using blocks cause unmanaged resource leaks.
  • Network dependency removed: All HTTP error handling related to GrabzIt (HttpRequestException, timeout logic, service availability checks) is removed. Replace with exception handling for IronPDF rendering errors.
  • URL accessibility changes: GrabzIt's cloud fetches URLs from its own servers — URLs accessible from the public internet but not from the application host work with GrabzIt but not with IronPDF's in-process renderer. Internal URLs that were inaccessible to GrabzIt's cloud are now accessible with IronPDF.
  • Screenshot and scraping capabilities not in scope: GrabzIt provides web screenshot (to image), HTML-to-image, video capture, and web scraping capabilities. IronPDF does not provide any of these. If the application uses these GrabzIt capabilities, they require a separate evaluation and replacement strategy independent of the PDF migration.
  • Async model change: GrabzIt's polling and webhook async models are replaced by await RenderHtmlAsPdfAsync(). Remove all polling loops and webhook handlers related to GrabzIt capture.
  • Linux deployment: GrabzIt's SDK has no native binary dependencies. IronPDF on Linux requires Chromium system library packages in the container or host environment. Add these to the container image and verify in the Linux deployment guide.
  • License key required: IronPdf.License.LicenseKey must be set before any render call. GrabzIt uses its own API key model — both require startup key configuration but through different mechanisms.
  • Namespace change: Remove using GrabzIt; and using GrabzIt.Parameters;. Replace with using IronPdf;.

Migration Checklist

  1. Audit all GrabzIt call sites: List every HTMLToPDF() and URLToPDF() call, its options configuration, and whether it uses SaveTo() or GetResult(). Separately note any screenshot, scraping, or video capture usage — those require independent evaluation.
  2. Evaluate non-PDF GrabzIt capabilities: If screenshot, web scraping, or video capture features are in active use, identify replacement tools before beginning PDF migration. These are out of IronPDF's scope and are separate migration tracks.
  3. Install IronPDF via NuGet: dotnet add package IronPdf.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs before any render call. See the license setup guide.
  5. Remove GrabzIt credential management: Delete all applicationKey / applicationSecret storage, configuration values, and injection. Remove GrabzItClient construction from DI registration and all call sites.
  6. Register ChromePdfRenderer in DI: Add builder.Services.AddSingleton<ChromePdfRenderer>() in Program.cs with RenderingOptions configured once.
  7. Update namespaces: Remove using GrabzIt; and using GrabzIt.Parameters;. Replace with using IronPdf;.
  8. Replace HTMLToPDF() + SaveTo() / GetResult() calls: Map each to renderer.RenderHtmlAsPdf(html) or await renderer.RenderHtmlAsPdfAsync(html). Wrap PdfDocument in a using block. Replace SaveTo() with pdf.SaveAs() and GetResult() with pdf.BinaryData.
  9. Replace URLToPDF() calls: Map to renderer.RenderUrlAsPdf(url). Configure WaitFor conditions from URLToPDFOptions.WaitForElement. Inject cookies via RenderingOptions.CustomCookies.
  10. Remove null checks on GetResult(): Replace if (pdfBytes == null) error paths with try/catch around render calls.
  11. Remove GrabzIt HTTP error handling: Delete timeout configurations, retry policies, and service availability checks specific to GrabzIt.
  12. Update container configuration: On Linux, add Chromium system library packages to the application container image. Remove any GrabzIt-specific environment variable or API key configuration from the deployment pipeline.

Conclusion

When staying on GrabzIt is technically reasonable

GrabzIt is technically reasonable when its non-PDF capabilities — web screenshots, video capture, web scraping — are in active production use and would require significant effort to replace; when the application's PDF volume is low enough that per-request pricing is not a meaningful cost; when the team's operational model strongly favors zero in-process dependencies and is comfortable with external service reliability; or when rendering must occur from a network location (capturing publicly accessible URLs) rather than from the application's own network context.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when PDF generation volume has grown to the point where per-request cloud pricing is visible in the budget; when data handling policies — GDPR, sector-specific compliance, internal data classification — make sending document content to a third-party service difficult to justify; when GrabzIt's network latency is contributing measurably to request response times; when the application needs post-render operations (merge, sign, encrypt) that currently require a second library; or when the application's URL rendering uses internal URLs that GrabzIt's cloud cannot reach.

What the cutover typically involves at the code level

For a typical application using GrabzIt only for HTML-to-PDF and URL-to-PDF, the migration is bounded and systematic: remove credential management, replace client construction with DI-registered renderer, map options properties to RenderingOptions, replace API calls with renderer calls, add using blocks, replace null checks with exception handling, and update the Linux container image. A developer familiar with both APIs can typically complete the replacement in a day per call site cluster. The rendering comparison pass — validating output parity across all templates — is proportional to the variety of HTML templates in use.

In your current GrabzIt integration, has the combination of per-request cost, network latency, and data handling overhead become significant enough to justify the migration effort — or is one of those factors the clear primary driver?
