Migrating from Kaizen.io to IronPDF: the .NET migration reference

technical depth for .NET teams evaluating a PDF library switch

Framing

Cloud-based HTML-to-PDF APIs follow a common architectural pattern: the application sends HTML content over HTTP to a third-party service, the service renders the document using a headless browser or document engine, and the application receives PDF bytes in response. This model removes rendering infrastructure from the application host but introduces an external dependency for every PDF generation request. The operational and data handling implications of that dependency accumulate over time in ways that are not always apparent at initial adoption.

Re-evaluation of cloud PDF services typically happens for one of several reasons. Per-request pricing that was negligible at low volume becomes visible at scale. Sending HTML content — which may contain customer data, business logic, or proprietary templates — to a third-party service raises data residency and confidentiality questions that become harder to answer under compliance frameworks like GDPR or HIPAA. Network latency compounds under concurrent load. And when post-render PDF operations are required (merge, sign, form-fill, encrypt), the application needs a separate library alongside the cloud service, increasing the dependency count and integration surface.

This guide covers the migration from a cloud-based PDF API (Kaizen.io) to IronPDF for .NET engineers evaluating or executing the switch. Because Kaizen.io's specific API surface, .NET SDK details, rendering engine, and current product status should be verified directly in official documentation, this article relies on the general pattern of cloud PDF API migration and places "-" wherever specific claims cannot be made confidently. The migration is classified as Low effort because the conceptual operation is identical (HTML in, PDF out) and the migration work is primarily replacing HTTP client calls with in-process method calls.

What Kaizen.io Is Designed to Do

The product status, last release, technical approach, rendering engine, .NET support, install footprint, and primary use case for Kaizen.io should be verified directly in official documentation, as the product's specifics are not sufficiently established in widely available technical sources to state with confidence. The guidance below applies to the general architecture of cloud-based HTML-to-PDF services, which Kaizen.io appears to represent based on available context.

Cloud PDF generation services typically expose an HTTP REST API where the application sends HTML content (as a string, file, or URL reference), along with configuration parameters for paper size, margins, orientation, headers, footers, and rendering options. The service's servers handle the rendering using a headless browser or document engine, and the response contains the PDF as binary data or a download URL. The .NET integration is typically via HttpClient calls or a vendor-provided .NET SDK that wraps the HTTP API. There are no native binary dependencies in the application — all rendering infrastructure runs on the vendor's servers. The primary use case is PDF generation for teams that prefer to offload rendering infrastructure entirely rather than embed it in the application.

Architectural Differences

A cloud PDF API and IronPDF represent opposite ends of the infrastructure spectrum for PDF generation. The cloud service runs rendering infrastructure remotely — the application sends content over HTTP and receives bytes back. IronPDF embeds Chromium in-process in the .NET application — the application calls a method and receives a PdfDocument object directly.

IronPDF's two primary types are ChromePdfRenderer (for rendering HTML to PDF) and PdfDocument (for the resulting document and all manipulation). Both implement IDisposable and require using blocks. Configuration that in a cloud API is expressed as HTTP request parameters (paper size, margins, orientation) is expressed in IronPDF as properties on RenderingOptions. The HTML string to PDF guide covers the full rendering configuration. The rendering options reference covers all available parameters. License initialization is a one-time startup call; see the license setup guide.

The shift from a cloud PDF API to IronPDF removes the network dependency from every render call, changes failure modes from HTTP errors to .NET exceptions, eliminates per-request API pricing, and consolidates PDF rendering and manipulation into a single in-process library. It introduces a different operational concern: IronPDF's Chromium engine adds to the application's memory footprint and, on Linux, requires Chromium system library packages in the container.

Operation Comparisons

HTML String to PDF (Generic Cloud API Pattern)

Cloud PDF API (Kaizen.io) — HTML to PDF via HTTP

using System.Net.Http;
using System.Net.Http.Headers;
using System.Text;
using System.Text.Json;

// Generic pattern for cloud PDF API integration
// Verify Kaizen.io's actual endpoint, authentication method, and request format
// in official documentation — this illustrates the general HTTP API pattern

public class CloudPdfService
{
    private readonly HttpClient _httpClient;
    private const string ApiBaseUrl = "https://api.kaizen.io"; // verify
    private const string ApiKey = "YOUR_API_KEY"; // verify auth mechanism

    public CloudPdfService(HttpClient httpClient)
    {
        _httpClient = httpClient;
        // Verify whether Kaizen.io uses Bearer tokens, API key headers, or another mechanism
        _httpClient.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", ApiKey); // verify format
    }

    public async Task<byte[]> HtmlToPdfAsync(string html, PdfOptions options)
    {
        // Verify the exact request structure in Kaizen.io official documentation
        var requestBody = new
        {
            html = html,
            options = new
            {
                paperSize = options.PaperSize,      // e.g., "A4"
                marginTop = options.MarginTop,       // verify unit (mm, in, px)
                marginBottom = options.MarginBottom,
                marginLeft = options.MarginLeft,
                marginRight = options.MarginRight,
                landscape = options.Landscape        // verify parameter name
            }
        };

        var json = JsonSerializer.Serialize(requestBody);
        using var content = new StringContent(json, Encoding.UTF8, "application/json");

        // Verify the exact endpoint path in official documentation
        using var response = await _httpClient.PostAsync($"{ApiBaseUrl}/pdf", content);
        response.EnsureSuccessStatusCode(); // throws on HTTP error

        return await response.Content.ReadAsByteArrayAsync();
    }

    public record PdfOptions(
        string PaperSize = "A4",
        int MarginTop = 10,
        int MarginBottom = 10,
        int MarginLeft = 10,
        int MarginRight = 10,
        bool Landscape = false);
}

Concrete constraints:

  • Verify the exact API endpoint URL, request body format, authentication mechanism (API key header, Bearer token, HMAC), and response format in Kaizen.io official documentation.
  • response.EnsureSuccessStatusCode() throws HttpRequestException on non-2xx responses — all cloud render failures surface as HTTP exceptions.
  • API credentials (key, token) must be managed as secrets — remove all credential storage related to Kaizen.io during migration.
  • Network round-trips add latency to every render call; under concurrent load, multiple threads wait on separate HTTP connections.
  • The API may impose rate limits or request size limits

IronPDF — In-Process HTML to PDF

using IronPdf;

// ChromePdfRenderer is reusable — register as singleton in DI
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 10;     // millimeters
renderer.RenderingOptions.MarginBottom = 10;
renderer.RenderingOptions.MarginLeft = 10;
renderer.RenderingOptions.MarginRight = 10;

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #1042</h1>
  <p>Customer: Acme Corp</p>
  <p>Total: $1,599.00</p>
</body>
</html>";

// PdfDocument is IDisposable — use a using block
using var pdf = renderer.RenderHtmlAsPdf(html);

// Equivalent to ReadAsByteArrayAsync() from the HTTP response
byte[] pdfBytes = pdf.BinaryData;

// Or save directly
pdf.SaveAs("invoice.pdf");

The HttpClient.PostAsync() / ReadAsByteArrayAsync() pattern is replaced by a direct method call. API credentials are removed. HTTP error handling (EnsureSuccessStatusCode(), HttpRequestException) is replaced by exception handling for IronPDF rendering errors. Full configuration is in the HTML string to PDF guide.

URL to PDF

Cloud PDF API — URL to PDF

using System.Net.Http;
using System.Text;
using System.Text.Json;

// Generic cloud PDF API URL rendering pattern
// Verify Kaizen.io's URL rendering endpoint and parameters in official documentation

public async Task<byte[]> UrlToPdfAsync(string url)
{
    // URL is passed to the cloud service, which fetches and renders it
    // The target URL must be publicly accessible from the cloud service's servers
    var requestBody = new
    {
        url = url,
        options = new
        {
            paperSize = "A4",   // verify parameter name and format
            // JavaScript wait
            // waitForSelector = ".content-loaded", // example
        }
    };

    var json = JsonSerializer.Serialize(requestBody);
    using var content = new StringContent(json, Encoding.UTF8, "application/json");
    using var response = await _httpClient.PostAsync($"{ApiBaseUrl}/pdf/url", content); // verify endpoint
    response.EnsureSuccessStatusCode();

    return await response.Content.ReadAsByteArrayAsync();
}

Concrete constraints:

  • Cloud services fetch the target URL from their own infrastructure — the URL must be publicly accessible from the internet, not from internal or VPN-protected networks.
  • Verify the URL rendering endpoint path and parameter format in official documentation.
  • Cookie injection for authenticated URLs requires vendor-specific mechanisms

IronPDF — URL to PDF

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// WaitFor configuration replaces cloud service wait parameters
renderer.RenderingOptions.WaitFor.HtmlElement(".content-loaded");

// Cookie injection for authenticated URLs
renderer.RenderingOptions.CustomCookies =
    new System.Collections.Generic.Dictionary<string, string>
    {
        { "session_id", "your-session-token" }
    };

using var pdf = renderer.RenderUrlAsPdf("https://reports.example.com/monthly");
byte[] pdfBytes = pdf.BinaryData;

Unlike cloud API URL rendering, IronPDF's in-process renderer can access URLs that are only reachable from the application's network — including internal services, staging environments, or URLs behind authentication without requiring them to be publicly exposed. The URL to PDF guide covers all wait conditions and cookie injection.

ASP.NET Core Controller Integration

Cloud PDF API — ASP.NET Core Controller

using System.Net.Http;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { private readonly CloudPdfService _pdfService;

public ReportController(CloudPdfService pdfService) { _pdfService = pdfService; }

[HttpGet("{id}/pdf")] public async Task GetReport(int id) { string html = await BuildReportHtmlAsync(id);

try { // Network call to cloud PDF service — adds latency byte[] pdfBytes = await _pdfService.HtmlToPdfAsync( html, new CloudPdfService.PdfOptions("A4", 15, 15, 15, 15));

return File(pdfBytes, "application/pdf", $"report-{id}.pdf"); } catch (HttpRequestException ex) { // Cloud service HTTP errors require explicit handling return StatusCode(503, $"PDF generation failed: {ex.Message}"); } }

private Task BuildReportHtmlAsync(int id) => Task.FromResult($"

Report {id}

"); }

Concrete constraints:

  • The CloudPdfService dependency is registered with an IHttpClientFactory-backed HttpClient — remove this DI registration during migration.
  • HttpRequestException catch block for cloud API failures must be replaced with exception handling for IronPDF rendering errors.
  • Service availability is an implicit dependency: if the cloud API is down, PDF generation fails.

IronPDF — ASP.NET Core Controller

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { private readonly ChromePdfRenderer _renderer;

// Singleton renderer injected via DI public ReportController(ChromePdfRenderer renderer) { _renderer = renderer; }

[HttpGet("{id}/pdf")] public async Task GetReport(int id) { string html = await BuildReportHtmlAsync(id);

// In-process rendering — no network call using var pdf = await _renderer.RenderHtmlAsPdfAsync(html);

return File(pdf.BinaryData, "application/pdf", $"report-{id}.pdf"); }

private Task BuildReportHtmlAsync(int id) => Task.FromResult($"

Report {id}

"); }

// Program.cs: // builder.Services.AddSingleton(sp => { // var r = new ChromePdfRenderer(); // r.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4; // r.RenderingOptions.MarginTop = 15; // return r; // }); // Remove: builder.Services.AddHttpClient(...);

The CloudPdfService HTTP wrapper is replaced by a singleton ChromePdfRenderer. HttpRequestException handling is replaced with try/catch for rendering exceptions. Genuine async rendering via RenderHtmlAsPdfAsync() is available. The async rendering guide covers concurrent rendering under load.

Post-Render PDF Operations (New Capability)

Cloud APIs typically return bytes with no post-render manipulation API. With IronPDF, the rendered PdfDocument exposes the full manipulation surface.

using IronPdf;
using IronPdf.Signing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Render multiple report sections
using var intro = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Executive Summary</h1><p>...</p></body></html>");
using var details = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Detail Analysis</h1><p>...</p></body></html>");
using var appendix = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Appendix</h1><p>...</p></body></html>");

// Merge sections into a single document
using var merged = PdfDocument.Merge(intro, details, appendix);

// Encrypt with password
merged.SecuritySettings.UserPassword = "viewerpassword";

// Apply digital signature
var signature = new PdfSignature("cert.pfx", "pfx-password")
{
    SigningReason = "Approved for release",
    SigningContact = "compliance@example.com"
};
merged.Sign(signature);

merged.SaveAs("complete-report-signed.pdf");

Operations like merge, encrypt, and sign previously required a separate manipulation library to process the cloud API's byte output. With IronPDF, these are available directly on PdfDocument. The merge and split guide and digital signatures guide cover these operations.

Breaking Changes & Gotchas

  • Credential management removed: API keys or bearer tokens for the cloud PDF service are removed entirely. Replace with IronPdf.License.LicenseKey set once at startup before any render call.
  • PdfDocument is IDisposable: Cloud APIs return byte[] — no disposal required. IronPDF returns PdfDocument, which implements IDisposable. Every render call must produce a PdfDocument in a using block.
  • HTTP error handling removed: EnsureSuccessStatusCode(), HttpRequestException catch blocks, timeout configurations, and retry policies specific to the cloud API are removed. Replace with exception handling for IronPDF rendering errors.
  • URL accessibility changes: Cloud services render URLs from their own servers — publicly accessible URLs work, internal URLs do not. IronPDF renders from the application host — internal URLs that were inaccessible to the cloud service are now accessible.
  • Kaizen.io-specific parameters: Verify the exact parameter names and units used by Kaizen.io for paper size, margins, orientation, and JavaScript wait — then map each to the corresponding RenderingOptions property. Mismatched units (mm vs points vs inches) produce silent layout differences.
  • Namespace change: Remove using System.Net.Http; and any Kaizen.io SDK namespaces. Replace with using IronPdf;.
  • IHttpClientFactory registration removed: The DI registration for the Kaizen.io HttpClient (named or typed) is removed. Replace with builder.Services.AddSingleton<ChromePdfRenderer>().
  • Linux deployment: Cloud APIs have no binary dependencies in the application. IronPDF on Linux requires Chromium system library packages in the container. Add these to the container image.
  • Data residency change: HTML content previously transmitted to Kaizen.io's servers stays in-process. This is architecturally favorable for compliance requirements but requires confirming that the new rendering behavior is acceptable under any existing data handling agreements.

Migration Checklist

  1. Verify Kaizen.io's API surface: Before planning the migration, review Kaizen.io's official documentation to confirm the exact endpoint structure, authentication method, request/response format, and any SDK availability. Resolve all "-" items in this guide.
  2. Audit all Kaizen.io call sites: List every location where the cloud PDF API is called, its request parameters (paper size, margins, wait conditions), and how the response is consumed (byte array, file save, stream).
  3. Map API parameters to RenderingOptions: For each Kaizen.io request parameter, identify the corresponding RenderingOptions property and verify unit conventions (mm vs inches vs points).
  4. Install IronPDF via NuGet: dotnet add package IronPdf.
  5. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs before any render call. See the license setup guide.
  6. Remove Kaizen.io credential management: Delete all API key storage, configuration entries, and HttpClient authentication configuration for the cloud service.
  7. Remove cloud API HttpClient DI registration: Delete the IHttpClientFactory / AddHttpClient<>() registration for the cloud PDF service. Replace with builder.Services.AddSingleton<ChromePdfRenderer>().
  8. Update namespaces: Remove cloud API SDK using directives. Replace with using IronPdf;.
  9. Replace HTTP call pattern: For each cloud API call site, replace HttpClient.PostAsync() + ReadAsByteArrayAsync() with renderer.RenderHtmlAsPdf(html). Wrap PdfDocument in using. Access bytes via pdf.BinaryData or save via pdf.SaveAs().
  10. Update URL rendering calls: Replace URL rendering HTTP calls with renderer.RenderUrlAsPdf(url). Configure WaitFor conditions and cookie injection as needed.
  11. Remove HTTP error handling: Delete EnsureSuccessStatusCode() and HttpRequestException catch blocks for the cloud API. Add try/catch for IronPDF rendering exceptions.
  12. Update Linux container image: Add Chromium system library packages to the application container image. Verify required packages for the Linux distribution in use.

Conclusion

When staying on Kaizen.io is technically reasonable

A cloud PDF API is technically reasonable when the team's operational model strongly favors zero in-process binary dependencies, when PDF generation volume is low enough that per-request pricing is not a meaningful cost, when rendering must occur from a location (public internet) rather than from the application's network context, or when the simplicity of offloading rendering infrastructure to a vendor is valued over the control of in-process rendering. Teams with stable, low-volume PDF generation and no post-render manipulation requirements have less pressure to migrate.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when PDF generation volume has grown to the point where per-request cloud pricing is visible; when data handling policies make transmitting document content to a third-party service difficult to justify; when network latency is contributing to response times; when post-render operations (merge, sign, form-fill, encrypt) require an additional library alongside the cloud API; or when the application needs to render internal URLs that the cloud service's servers cannot reach.

What the cutover typically involves at the code level

For a typical ASP.NET Core application with a small number of Kaizen.io call sites, the migration is bounded and systematic: remove credential management, replace HttpClient + HTTP calls with DI-registered renderer calls, add using blocks, remove HTTP error handling, update Linux container configuration. A developer familiar with both the cloud API and IronPDF can typically complete the replacement quickly for each call site. The rendering comparison pass — validating output parity across all templates — is proportional to template variety and CSS complexity.

As you review your Kaizen.io integration, have you quantified the cumulative network latency across all PDF generation calls per day — and is that latency a factor in the user experience that would justify the migration effort?
