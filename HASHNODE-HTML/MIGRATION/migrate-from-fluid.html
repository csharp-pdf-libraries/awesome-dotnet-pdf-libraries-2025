Migrating from Fluid (Templating) to IronPDF: from install to production

architecture differences, breaking changes, and migration patterns

Framing

A common presence in .NET PDF generation pipelines that predate first-class HTML-to-PDF libraries, liquid template engines are. The pattern is well-established: a Liquid template describes the document layout as HTML with variable placeholders; a template engine — often Fluid (sebastienros/fluid), the leading .NET Liquid implementation — renders it to an HTML string; that HTML string is then passed to a PDF library or third-party service. This two-step pipeline works, but it introduces dependencies at both layers — the template engine and the PDF renderer — with all the integration surface area that entails.

Teams re-evaluating this pipeline usually arrive at a specific inflection point. The PDF library in the second step may be outdated, the external PDF service being called may be creating latency or data residency concerns, or the templating layer may be over-engineered for what is essentially a string interpolation requirement. In each case, the question is whether the Liquid templating layer is a necessary abstraction or a historical artifact that can be replaced by something more native to the development workflow — Razor templates, C# string interpolation, or another .NET-native approach.

This guide is for .NET engineers who are using Fluid (the Fluid.Core NuGet package, which implements the Liquid template language for .NET) to generate HTML that is then converted to PDF, and who are evaluating whether to simplify or replace that pipeline. The migration path discussed here is: replacing the Fluid-rendered-HTML-to-PDF flow with a more direct HTML-generation approach paired with IronPDF for rendering. The migration effort is Low because the HTML output that Fluid produces is entirely compatible with IronPDF's Chromium renderer — the question is only whether Fluid itself remains in the pipeline.

What Fluid Is Designed to Do

Fluid (sebastienros/fluid) is an open-source .NET implementation of the Liquid template language. It is actively maintained and available via the Fluid.Core NuGet package. The last release should be verified in official documentation or the project's GitHub repository. Fluid supports .NET Standard 2.0 and higher, making it compatible across .NET Framework and .NET Core / .NET 5+ targets.

Fluid's design is a text templating engine — it renders Liquid templates (.liquid files or inline strings containing {{ variable }} expressions, {% if %} / {% for %} tags, and filters) against a data model, producing rendered text output. That output is most commonly HTML, but Fluid itself is format-agnostic. The library has no PDF-specific functionality — it produces strings. In a PDF generation pipeline, Fluid occupies only the template-rendering step; a separate library (IronPDF, wkhtmltopdf wrapper, cloud service, etc.) is always required to convert the rendered HTML to PDF. The install footprint is a single managed NuGet package with no native dependencies. Fluid is typically used where designers or non-developers manage document templates, as the Liquid syntax is deliberately approachable, and where the template must be edited independently of application deployment.

Architectural Differences

Fluid and IronPDF operate at different layers of a PDF generation pipeline. Fluid is a template renderer — it produces HTML strings. IronPDF is a PDF renderer — it consumes HTML strings (or URLs, files) and produces PDF documents. They are not direct competitors; in many integrations, both are present simultaneously. The architectural question this guide addresses is whether Fluid belongs in the pipeline at all, and what changes when it is retained, simplified, or removed.

IronPDF's ChromePdfRenderer accepts any valid HTML string and renders it to a PdfDocument using an embedded Chromium engine. Whether that HTML was generated by Fluid, Razor, Scriban, C# string interpolation, or a static file is irrelevant to the renderer. The HTML string to PDF guide covers the full rendering configuration. PdfDocument implements IDisposable and must be wrapped in a using block. License initialization is a one-time startup call; see the license setup guide.

The practical architectural question is which templating approach produces the best maintainability, testability, and toolchain integration for the team. Liquid (Fluid) provides designer-friendly templates with runtime-editable template files and an intentionally restricted syntax. Razor provides full C# integration, compile-time validation, IntelliSense, and the full .NET toolchain but requires a build step and developer involvement for template changes. Scriban and Handlebars.NET sit between the two in complexity. IronPDF is compatible with all of them — the HTML it receives does not need to know how it was generated.

Operation Comparisons

Fluid Template Render + PDF Conversion (Current Pattern)

Current Pattern — Fluid + PDF Service or Library

using Fluid;
using System.Net.Http;
using System.Net.Http.Json;

// The Fluid pipeline has two steps:
// 1. Render the Liquid template to HTML
// 2. Convert the HTML to PDF (via cloud service, wkhtmltopdf wrapper, or other library)

// Step 1: Render Liquid template to HTML using Fluid
var parser = new FluidParser();

string liquidTemplate = @"
<!DOCTYPE html>
<html>
<head><style>
  body { font-family: Arial, sans-serif; }
  table { width: 100%; border-collapse: collapse; }
  th { background: #eee; padding: 8px; }
  td { padding: 8px; border-bottom: 1px solid #ddd; }
</style></head>
<body>
  <h1>Invoice #{{ invoice.number }}</h1>
  <p>Customer: {{ invoice.customer_name }}</p>
  <table>
    <tr><th>Description</th><th>Amount</th></tr>
    {% for item in invoice.line_items %}
    <tr><td>{{ item.description }}</td><td>{{ item.amount | currency }}</td></tr>
    {% endfor %}
  </table>
  <p><strong>Total: {{ invoice.total | currency }}</strong></p>
</body>
</html>";

if (parser.TryParse(liquidTemplate, out var template, out string error))
{
    var model = new TemplateContext();
    model.SetValue("invoice", new
    {
        number = "INV-1042",
        customer_name = "Acme Corp",
        line_items = new[]
        {
            new { description = "Consulting", amount = 1500.00 },
            new { description = "Hosting", amount = 99.00 }
        },
        total = 1599.00
    });

    string html = await template.RenderAsync(model);

    // Step 2: Convert HTML to PDF — placeholder for whatever PDF tool is used
    // e.g., HttpClient call to cloud service, wkhtmltopdf wrapper, etc.
    // byte[] pdfBytes = await pdfService.ConvertAsync(html);
}

Concrete constraints:

  • Fluid's RenderAsync() is async and returns the rendered HTML string — this is already awaitable and fits naturally in async pipelines.
  • Custom Liquid filters (e.g., | currency) must be registered on the FluidParser or template options before parsing. If filters encapsulate display logic, that logic must be reproduced in any replacement templating approach.
  • Template files can be loaded from disk, a database, or a CMS — this is a key Fluid capability for runtime-editable templates without redeployment. Razor requires a build step and deployment for template changes.
  • The PDF conversion step (Step 2) is entirely decoupled from Fluid. Swapping the PDF step does not require any changes to the Fluid layer.

IronPDF — Retain Fluid, Replace PDF Rendering Step

using Fluid;
using IronPdf;

// Fluid stays in the pipeline for template rendering
// IronPDF replaces the PDF conversion step

var parser = new FluidParser();

// Register custom filters if needed
// parser.RegisterFilter("currency", (input, args, ctx) => ...);

string liquidTemplate = LoadTemplateFromFile("invoice.liquid"); // or from DB/CMS

if (parser.TryParse(liquidTemplate, out var template, out string parseError))
{
    var context = new TemplateContext();
    context.SetValue("invoice", GetInvoiceData(1042));

    // Fluid renders HTML — same as before
    string html = await template.RenderAsync(context);

    // IronPDF renders the HTML to PDF — replaces the old PDF conversion step
    var renderer = new ChromePdfRenderer();
    renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
    renderer.RenderingOptions.MarginTop = 15;
    renderer.RenderingOptions.MarginBottom = 15;
    renderer.RenderingOptions.MarginLeft = 15;
    renderer.RenderingOptions.MarginRight = 15;

    using var pdf = renderer.RenderHtmlAsPdf(html);
    pdf.SaveAs("invoice.pdf");
}

static string LoadTemplateFromFile(string name) =>
    System.IO.File.ReadAllText(name);
static object GetInvoiceData(int id) =>
    new { number = $"INV-{id}", customer_name = "Acme Corp",
          line_items = Array.Empty<object>(), total = 0.0 };

This is the lowest-disruption migration path — Fluid stays in the pipeline and only the PDF rendering step changes. The HTML that Fluid produces is fully compatible with IronPDF's Chromium renderer. Full rendering configuration is in the HTML string to PDF guide. For templates with complex multi-page layouts, the page breaks guide covers CSS-based pagination.

Replacing Fluid with Razor Templates

Pattern — Replace Fluid with Razor + IronPDF

// For ASP.NET Core applications, Razor provides C#-native templating
// with compile-time validation, IntelliSense, and the full .NET toolchain
// Template changes require a build and deployment — unlike Fluid's runtime editing

// InvoiceViewModel.cs
public class InvoiceViewModel
{
    public string Number { get; set; } = "";
    public string CustomerName { get; set; } = "";
    public List<LineItem> LineItems { get; set; } = new();
    public decimal Total { get; set; }
}

public record LineItem(string Description, decimal Amount);
// invoice.cshtml (Razor view — not executed here, shown for comparison)
// @model InvoiceViewModel
// <h1>Invoice #@Model.Number</h1>
// <p>Customer: @Model.CustomerName</p>
// <table>
//   @foreach (var item in Model.LineItems) {
//     <tr><td>@item.Description</td><td>@item.Amount.ToString("C")</td></tr>
//   }
// </table>
// <p><strong>Total: @Model.Total.ToString("C")</strong></p>
using IronPdf;
using Microsoft.AspNetCore.Mvc;
using Microsoft.AspNetCore.Mvc.Rendering;
using Microsoft.AspNetCore.Mvc.ViewEngines;

// Razor-to-string rendering in ASP.NET Core for use with IronPDF
public class PdfGenerationService
{
    private readonly IRazorViewEngine _viewEngine;
    private readonly IServiceProvider _serviceProvider;
    private readonly ChromePdfRenderer _renderer;

    public PdfGenerationService(
        IRazorViewEngine viewEngine,
        IServiceProvider serviceProvider,
        ChromePdfRenderer renderer)
    {
        _viewEngine = viewEngine;
        _serviceProvider = serviceProvider;
        _renderer = renderer;
    }

    public async Task<byte[]> GenerateInvoicePdfAsync(InvoiceViewModel model)
    {
        // Render Razor view to HTML string using the view engine
        string html = await RenderViewToStringAsync("Invoice", model);

        // IronPDF renders the HTML to PDF
        using var pdf = await _renderer.RenderHtmlAsPdfAsync(html);
        return pdf.BinaryData;
    }

    private async Task<string> RenderViewToStringAsync(
        string viewName, object model)
    {
        // Standard Razor-to-string rendering pattern for ASP.NET Core
        // Implementation uses ICompositeViewEngine — omitted for brevity
        // Numerous open-source helpers provide this (e.g., RazorLight)
        await Task.CompletedTask;
        return $"<html><body><h1>{viewName}</h1></body></html>"; // Placeholder
    }
}

Concrete constraints:

  • Rendering Razor views to strings outside of an HTTP request context requires ICompositeViewEngine or a library like RazorLight — the standard ASP.NET Core view engine is request-scoped.
  • Razor templates require redeployment for content changes; this is a fundamental difference from Fluid's runtime-editable approach.
  • C# compile-time validation of template bindings is a significant quality-of-life improvement over Liquid's runtime binding errors.

IronPDF — Async Rendering After Razor or Fluid

using IronPdf;

// Regardless of how HTML is generated (Fluid, Razor, interpolation)
// the IronPDF rendering call is always the same
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// html is the output of whichever templating approach is used
string html = "<!DOCTYPE html><html><body><p>Document content.</p></body></html>";

using var pdf = await renderer.RenderHtmlAsPdfAsync(html);
byte[] pdfBytes = pdf.BinaryData;

The async rendering guide covers RenderHtmlAsPdfAsync, thread safety, and parallel batch generation for high-volume document pipelines.

Fluid Template with Headers and Footers (IronPDF Approach)

Current Pattern — Headers/Footers in Fluid Template

<!-- In a Fluid/Liquid template, headers and footers are often embedded
     as positioned elements using CSS @page and fixed positioning -->

<!DOCTYPE html>
<html>
<head>
<style>
  /* Common pattern: use fixed-position elements as headers/footers */
  @page { margin-top: 50px; margin-bottom: 40px; }
  .header {
    position: fixed; top: 0; left: 0; right: 0;
    height: 30px; font-size: 9px; border-bottom: 1px solid #ccc;
    padding: 5px 15px; display: flex; justify-content: space-between;
  }
  .footer {
    position: fixed; bottom: 0; left: 0; right: 0;
    height: 25px; font-size: 8px; text-align: center;
    border-top: 1px solid #ccc; padding: 5px;
  }
  .content { margin-top: 50px; margin-bottom: 40px; }
</style>
</head>
<body>
  <div class="header">
    <span>{{ company.name }}</span>
    <span>{{ document.title }}</span>
  </div>
  <div class="footer">Page <span class="page-number"></span></div>
  <div class="content">
    <h1>{{ document.title }}</h1>
    <!-- Template body -->
  </div>
</body>
</html>

Concrete constraints:

  • CSS position: fixed headers and footers are a common workaround when the PDF library does not have a first-class header/footer API.
  • CSS counter(page) for page numbers in @page rules has inconsistent support across rendering engines — behavior must be tested in the specific PDF library being used.
  • Embedding headers and footers in the Fluid template couples the header/footer content to the template file, making global header changes require updates across all templates.

IronPDF — First-Class Headers and Footers

using IronPdf;
using IronPdf.Editing;
using Fluid;

var parser = new FluidParser();
string liquidTemplate = System.IO.File.ReadAllText("document-body.liquid");

if (parser.TryParse(liquidTemplate, out var template, out _))
{
    var context = new TemplateContext();
    context.SetValue("document", new { title = "Q1 Report" });
    context.SetValue("company", new { name = "Acme Corp" });

    // Fluid renders only the body — no header/footer markup needed in the template
    string bodyHtml = await template.RenderAsync(context);

    var renderer = new ChromePdfRenderer();
    renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

    // Headers and footers configured centrally on the renderer
    // {page} and {total-pages} are resolved automatically per page
    renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
    {
        Height = 15,
        HtmlFragment = "<div style='font-size:9px; display:flex; " +
                       "justify-content:space-between; padding:0 15px;'>" +
                       "<span>Acme Corp</span><span>Q1 Report</span></div>",
        DrawDividerLine = true
    };

    renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
    {
        Height = 12,
        HtmlFragment = "<div style='font-size:8px; text-align:center;'>" +
                       "Page {page} of {total-pages}</div>"
    };

    using var pdf = renderer.RenderHtmlAsPdf(bodyHtml);
    pdf.SaveAs("report.pdf");
}

Separating header/footer configuration from the Liquid template simplifies template maintenance and centralizes common document chrome. Full header/footer configuration including advanced HTML layouts is in the headers and footers guide.

Post-Render PDF Operations (New Capability)

Fluid's role is HTML generation — it has no PDF manipulation capability. Once Fluid's output is passed to IronPDF, the full PdfDocument API becomes available for operations that were previously impossible in a pure Fluid-based pipeline.

using IronPdf;
using IronPdf.Signing;
using Fluid;

// Step 1: Generate individual PDF sections using Fluid templates
var parser = new FluidParser();

async Task<PdfDocument> RenderSectionAsync(string templateFile, object data)
{
    if (parser.TryParse(System.IO.File.ReadAllText(templateFile),
        out var template, out _))
    {
        var ctx = new TemplateContext();
        ctx.SetValue("data", data);
        string html = await template.RenderAsync(ctx);

        var renderer = new ChromePdfRenderer();
        renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
        // PdfDocument returned — caller is responsible for disposal
        return renderer.RenderHtmlAsPdf(html);
    }
    throw new InvalidOperationException("Template parse error");
}

// Step 2: Compose multiple sections and apply post-render operations
using var coverPage = await RenderSectionAsync("cover.liquid", new { title = "Annual Report" });
using var body = await RenderSectionAsync("body.liquid", new { data = GetBodyData() });
using var appendix = await RenderSectionAsync("appendix.liquid", new { tables = GetTables() });

// Merge into a single document
using var merged = PdfDocument.Merge(coverPage, body, appendix);

// Apply digital signature to the merged document
var signature = new PdfSignature("cert.pfx", "password")
{
    SigningReason = "Approved for distribution"
};
merged.Sign(signature);

merged.SaveAs("signed-annual-report.pdf");

static object GetBodyData() => new { };
static object GetTables() => new { };

Operations like multi-section merge, digital signing, and PDF/A output are unavailable in a Fluid-only pipeline. With IronPDF in the rendering step, they become available without additional libraries. The merge and split guide and digital signatures guide cover these operations in detail.

Breaking Changes & Gotchas

  • Fluid is not being replaced — the PDF rendering step is: The most common misframe in this migration is treating it as "replacing Fluid with IronPDF." Fluid and IronPDF are at different layers. The lowest-disruption migration replaces only the PDF conversion step while leaving Fluid in place.
  • Disposal of PdfDocument: Fluid's RenderAsync() returns a string — no disposal. IronPDF's RenderHtmlAsPdf() returns PdfDocument, which implements IDisposable. Every PdfDocument must be in a using block. This is a structural change in all code paths that produce PDFs.
  • License key required: IronPdf.License.LicenseKey must be set at startup before any render call. Fluid has no license requirement (MIT licensed). Omitting IronPDF's key produces watermarked output.
  • CSS fixed-position headers/footers: If the current Liquid templates use CSS position: fixed as a header/footer workaround, evaluate moving to RenderingOptions.HtmlHeader/HtmlFooter. This simplifies templates (no fixed-position markup needed) and provides reliable page numbering via {page} tokens.
  • Removing cloud PDF service removes HTTP error handling: If the current pipeline posts to a cloud PDF service, HTTP error handling (EnsureSuccessStatusCode, network timeout retry) is in the critical path. IronPDF renders in-process and throws .NET exceptions on failure — update error handling accordingly.
  • Razor vs Fluid tradeoff is unresolved: IronPDF is compatible with both. The choice between retaining Fluid, migrating to Razor, or adopting another templating approach (Scriban, Handlebars.NET) depends on team composition, template ownership, and deployment constraints. This guide does not advocate one over another.
  • Liquid filter logic migration: Custom Liquid filters registered in the Fluid pipeline encapsulate display logic. If Fluid is removed, that logic must move to the C# model layer, a view helper, or a Razor helper. Inventory all custom filters before deciding to remove Fluid.
  • Template editability: Fluid templates can be loaded from files, a database, or a CMS and rendered without redeployment. If this capability is in use — for instance, customer-editable templates or content-managed documents — removing Fluid means losing it unless a replacement runtime-editable approach is adopted.

Migration Checklist

  1. Map the current pipeline: Identify every place where Fluid templates are used to generate HTML that is subsequently converted to PDF. Determine whether the PDF step calls a cloud service (HTTP), a wkhtmltopdf wrapper, another library, or nothing yet.
  2. Decide whether to retain Fluid: If templates are runtime-editable (loaded from files, DB, or CMS), retain Fluid and replace only the PDF rendering step. If templates are code-adjacent and developer-maintained, evaluate Razor or string interpolation as a replacement.
  3. Install IronPDF via NuGet: dotnet add package IronPdf. Do not remove Fluid until the pipeline is tested.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs before any render call. See the license setup guide.
  5. Replace the PDF conversion step: For each location where Fluid's HTML output is passed to a cloud API or other PDF library, replace it with renderer.RenderHtmlAsPdf(html) or await renderer.RenderHtmlAsPdfAsync(html). Wrap PdfDocument in a using block.
  6. Register ChromePdfRenderer in DI: Add builder.Services.AddSingleton<ChromePdfRenderer>() and configure rendering options (paper size, margins, etc.) once at registration or startup.
  7. Move headers and footers from templates to RenderingOptions: If templates use CSS position: fixed for headers/footers, replace with RenderingOptions.HtmlHeader/HtmlFooter. Remove fixed-position markup from Liquid templates.
  8. Update page number approach: Replace CSS counter(page) with {page} and {total-pages} tokens in HtmlHeaderFooter.HtmlFragment.
  9. Remove cloud PDF service HTTP code: Remove HttpClient setup, JSON request/response parsing, temporary URL download logic, and retry/circuit-breaker policies specific to the old PDF service.
  10. Update error handling: Replace HTTP error handling with try/catch around render calls. IronPDF errors surface as .NET exceptions.
  11. Validate rendering output: Compare IronPDF output against previous PDF output for each template. Focus on font rendering, table layout, page breaks, and header/footer placement.
  12. Remove superseded PDF library or API dependency: Once all pipeline steps are replaced and tests pass, remove the old PDF library NuGet references or API client code.

Conclusion

When retaining Fluid alongside IronPDF is the right call

The simplest and often best outcome is retaining Fluid for template rendering and adding IronPDF as the PDF rendering step. This is the right call when templates are runtime-editable and managed by non-developers or a content system, when the Liquid template syntax is established in the team's workflow, or when the existing templates are complex and well-tested and the cost of rewriting them in Razor is not justified. The two libraries solve different problems and coexist naturally.

Signals that replacing Fluid is worth the engineering effort

Replacing Fluid with Razor or another approach becomes worth evaluating when the team is entirely developer-composed and runtime editability is not used, when compile-time binding validation is valued over template flexibility, or when the template complexity has grown to the point where Liquid's intentional limitations (no arbitrary C# execution, restricted filter logic) are causing workarounds. These are team and workflow decisions more than technical ones — neither Fluid nor Razor is universally superior.

What the cutover typically involves at the code level

If only the PDF step is being replaced (Fluid retained), the work is bounded and mechanical: replace cloud API calls or old PDF library calls with renderer.RenderHtmlAsPdf(html), add using blocks, configure RenderingOptions, and shift header/footer markup out of templates into HtmlHeaderFooter objects. If Fluid is also being replaced, the work expands proportionally to the number of Liquid templates and the complexity of custom filters that must be reproduced in the new templating approach.

In your current Fluid-based pipeline, are the Liquid templates edited by developers as part of the normal build process, or are they edited at runtime by non-developers or a content management system — and how much does that distinction shape which migration path makes sense for your team?
