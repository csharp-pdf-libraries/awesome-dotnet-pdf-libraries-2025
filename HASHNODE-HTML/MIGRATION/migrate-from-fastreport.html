# Migrating from FastReport to IronPDF: API mapping and migration checklist

The original version of this article is published at https://ironsoftware.com/csharp/pdf/blog/migrate-from-wdone-fastreport/.

Framing

Report-generation libraries occupy a different position in the .NET PDF ecosystem than general-purpose PDF manipulation libraries. They offer a designer-based workflow: a report template (usually in a proprietary XML format) is authored visually, bound to a data source at runtime, and rendered to PDF or another output format by a report engine. The appeal is that non-developer stakeholders can modify report layouts without touching application code, and complex banded layouts—headers, data bands, group footers, page totals—are handled by the engine rather than by application logic.

FastReport is a long-established .NET report engine in this category, with versions spanning WinForms, ASP.NET, and .NET Core environments. Teams that adopted it typically did so when the reporting requirements were data-centric and layout-complex, and when the visual designer was a key productivity tool for the team or its business stakeholders. Migration conversations arise when platform requirements shift—Linux container deployment, .NET 6+ targets, microservice architectures—or when the team's document generation needs have evolved beyond the report-generation model toward HTML-template-driven workflows that are more natural for web-centric teams.

The high migration effort designation for this transition reflects the depth of the FastReport integration rather than the complexity of any individual API. Teams often have large report template catalogs, data binding configurations that span multiple data sources, and custom expressions embedded in template files. Understanding the full scope of that integration is the essential first step.

What FastReport Is Designed To Do

FastReport is a report engine that generates paginated reports from banded templates bound to application data. Its architecture centers on an frx report template file (an XML format) that defines bands—report header, page header, data band, group header/footer, page footer, report summary—along with the objects placed within each band: text labels, data fields, images, charts, barcodes, and sub-reports. At runtime, the application loads a template, passes data objects (typically DataSet, DataTable, or custom objects), and calls the engine to execute the report, which iterates over the data and produces a paginated output document.

FastReport distributions include a visual report designer (either as a standalone tool or embeddable in a WinForms or WPF application) that allows templates to be edited without recompiling the application. The engine supports exporting to PDF, HTML, Excel, RTF, and other formats. FastReport has separate product editions targeting .NET Framework, .NET Core, and ASP.NET Core; verify the current supported .NET versions, licensing model, and product naming in the official FastReport documentation, as the product family has evolved over time.

Architectural Differences

IronPDF generates PDFs from HTML rather than from banded report templates. There is no report designer, no frx file format, and no concept of data bands. The application is responsible for constructing HTML output from its data—using a templating engine such as Razor, Scriban, Handlebars.NET, or direct string construction—and then passing that HTML to ChromePdfRenderer. The Chromium engine handles all layout, pagination, and typography.

This is a meaningful architectural shift. In FastReport, the template is an artifact separate from the code; in an IronPDF workflow, the template is either a Razor view, a template file consumed by a templating library, or code that builds HTML strings. The HTML string to PDF pipeline covers the core rendering call; the rendering options reference covers paper size, margins, CSS media type, JavaScript behavior, and header/footer configuration.

Disposal semantics are explicit: PdfDocument and ChromePdfRenderer implement IDisposable and should be wrapped in using blocks. FastReport's Report object also requires explicit disposal (it implements IDisposable); teams familiar with FastReport's disposal requirements will find IronPDF's model conceptually similar, though the specific call sites differ. IronPDF does not provide a visual designer or a data binding layer; those responsibilities shift entirely to the application.

Operation Comparisons

Data-Bound Report to PDF

FastReport — Data-Bound Report Execution:

FastReport renders a report by loading an frx template, registering data sources, and calling the render method. The engine handles iteration over data rows and band placement.

// FastReport — data-bound report to PDF
// Requires: FastReport.Net or FastReport.Core NuGet package
using FastReport;
using FastReport.Export.Pdf;

// Load report template from file
using var report = new Report();
report.Load("SalesReport.frx");

// Register data — DataTable, DataSet, or business object
// report.RegisterData(dataTable, "SalesData");
// Alternatively, pass via Report.Dictionary.RegisterData
report.Dictionary.RegisterData(salesDataTable, "SalesData");

// Prepare (execute data binding and layout engine)
report.Prepare();

// Export to PDF
var pdfExport = new PDFExport();
pdfExport.OpenAfterExport = false;
report.Export(pdfExport, "output.pdf");
// Report implements IDisposable; using block handles disposal

Technical constraints:

  • The frx template must be deployed alongside the application; template changes require a new deployment unless the designer is embedded in the application
  • Data binding requires matching registered data source names exactly to the names referenced in the template bands
  • Running totals, group aggregates, and cross-band expressions are evaluated by the engine; logic is in the template, not in application code
  • Report execution is synchronous; async rendering requires wrapping in Task.Run()

IronPDF — Data-Bound HTML Template to PDF:

using IronPdf;
using System.Text;

// Application is responsible for data retrieval
// (previously handled by FastReport data binding)
var salesData = await salesRepository.GetSalesDataAsync(reportParams);

// Build HTML using any templating approach — Razor, Scriban, or string building
// This example uses StringBuilder for clarity; Razor/Scriban is preferred for complex layouts
var html = new StringBuilder();
html.Append(@"
<!DOCTYPE html><html><head>
<style>
  body { font-family: Arial, sans-serif; font-size: 11px; margin: 30px; }
  h2 { color: #1a3c5e; border-bottom: 1px solid #ccc; padding-bottom: 6px; }
  table { width: 100%; border-collapse: collapse; margin-top: 12px; }
  th { background: #1a3c5e; color: white; padding: 6px 8px; text-align: left; }
  td { border-bottom: 1px solid #eee; padding: 5px 8px; }
  .subtotal { font-weight: bold; background: #f5f5f5; }
  .grand-total { font-weight: bold; background: #dce6f1; }
</style></head><body>");

html.Append($"<h2>Sales Report — {salesData.Period}</h2>");
html.Append("<table><tr><th>Region</th><th>Product</th><th>Units</th><th>Revenue</th></tr>");

// Group aggregates calculated in C# before template render
foreach (var group in salesData.LinesByRegion)
{
    foreach (var line in group.Lines)
    {
        html.Append($"<tr><td>{group.Region}</td><td>{line.Product}</td>" +
                    $"<td>{line.Units}</td><td>{line.Revenue:C}</td></tr>");
    }
    // Group subtotal — calculated in application, not in template engine
    html.Append($"<tr class='subtotal'><td colspan='2'>{group.Region} Subtotal</td>" +
                $"<td>{group.TotalUnits}</td><td>{group.TotalRevenue:C}</td></tr>");
}

html.Append($"<tr class='grand-total'><td colspan='2'>Grand Total</td>" +
            $"<td>{salesData.GrandTotalUnits}</td><td>{salesData.GrandTotalRevenue:C}</td></tr>");
html.Append("</table></body></html>");

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.Letter;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 20;

using var pdf = renderer.RenderHtmlAsPdf(html.ToString());
pdf.SaveAs($"SalesReport_{salesData.Period}.pdf");

The HTML string to PDF guide covers base URL configuration for templates that reference external CSS files or shared image assets. The key difference from FastReport's model is that aggregation logic—running totals, group subtotals, cross-band calculations—is now computed in application code before the HTML is constructed, rather than in template expressions evaluated by the report engine.

Page Headers and Footers

FastReport — Page Headers and Footers:

FastReport templates define a PageHeaderBand and PageFooterBand that render at the top and bottom of every page. Objects within these bands can reference page number globals ([Page#], [TotalPages#]) using FastReport's expression syntax.

// FastReport header/footer are defined in the frx template XML, not in C# code.
// The template designer places text objects with expressions:
// - "[Page#] of [TotalPages#]" for page numbers
// - "[Date]" for the report date
// These expressions are evaluated at render time by the FastReport engine.
// In C#, no additional code is needed for headers/footers if defined in the template.

// However, dynamic header content (e.g., report title based on runtime data)
// can be set via report parameters:
using FastReport;

using var report = new Report();
report.Load("ReportWithHeader.frx");
// Set a parameter that the header band text object references
report.Parameters.FindByName("ReportTitle").Value = "Q3 Sales Summary";
report.Dictionary.RegisterData(data, "SalesData");
report.Prepare();
// Export as before...

Technical constraints:

  • Header/footer content is primarily controlled in the template, not in C#; changing header text requires designer access or direct XML editing of the frx file
  • Multi-line, image-containing, or complex-layout headers require drawing objects in the designer
  • Per-section headers (different header content for different report sections) require conditional band expressions

IronPDF — Page Headers and Footers:

using IronPdf;
using IronPdf.Engines.Chrome;

var renderer = new ChromePdfRenderer();

// Text header with company name and dynamic date
renderer.RenderingOptions.TextHeader = new TextHeaderFooter
{
    CenterText = "ACME Corporation — Quarterly Sales Report",
    DrawDividerLine = true,
    FontSize = 9
};

// Footer with left-aligned date and right-aligned page numbers
renderer.RenderingOptions.TextFooter = new TextHeaderFooter
{
    LeftText = "Generated: {date}",
    RightText = "Page {page} of {total-pages}",
    DrawDividerLine = true,
    FontSize = 8
};

using var pdf = renderer.RenderHtmlAsPdf(reportHtml);
pdf.SaveAs("report-with-headers.pdf");

The headers and footers guide covers HTML-based header and footer objects for scenarios requiring logos, multi-column layout, or styled typography in headers and footers—capabilities that go beyond the text token model shown above.

Streaming PDF via ASP.NET

FastReport — ASP.NET Core PDF Export:

FastReport has ASP.NET Core integration packages that allow report generation within an MVC controller. The report is executed and exported to a memory stream, then returned as a file response.

// FastReport ASP.NET Core — conceptual outline
// Verify exact package name and API for the ASP.NET Core edition
using FastReport;
using FastReport.Export.Pdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] public class ReportController : ControllerBase { [HttpGet("monthly-report")] public IActionResult GetMonthlyReport([FromQuery] string period) { using var report = new Report(); report.Load("MonthlyReport.frx"); // Register data, set parameters... report.Prepare();

using var stream = new System.IO.MemoryStream(); var pdfExport = new PDFExport(); report.Export(pdfExport, stream); stream.Position = 0;

return File(stream.ToArray(), "application/pdf", $"Report_{period}.pdf"); } }

Technical constraints:

  • PDFExport and Report both require disposal; ensure using blocks are correctly structured around the memory stream
  • The frx file must be accessible from the web application's file system; deployment packaging must include template files
  • Report execution is CPU-intensive; under concurrent load, thread-pool exhaustion can occur without careful async design

IronPDF — ASP.NET Core PDF Response:

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { private readonly ISalesRepository _salesRepository;

public ReportController(ISalesRepository salesRepository) { _salesRepository = salesRepository; }

[HttpGet("monthly")] public async Task GetMonthlyReport([FromQuery] string period) { // Data retrieval — application's responsibility var data = await _salesRepository.GetMonthlyDataAsync(period);

// HTML template construction (ideally via injected template engine) var html = BuildReportHtml(data);

var renderer = new ChromePdfRenderer(); renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4; renderer.RenderingOptions.MarginTop = 20; renderer.RenderingOptions.MarginBottom = 20;

// Async render — does not block thread pool using var pdf = await renderer.RenderHtmlAsPdfAsync(html);

return File(pdf.BinaryData, "application/pdf", $"Report_{period}.pdf"); }

private string BuildReportHtml(MonthlyData data) { // Template construction here return $"

{data.Period} Report

"; } }

The async rendering API keeps request threads free while Chromium processes the render. This pattern replaces FastReport's synchronous export call with an awaitable operation, which improves throughput under concurrent load without the thread-pool management overhead of Task.Run() wrappers.

Digital Signatures on Report Output

FastReport — Signing PDF Export:

FastReport's PDF export includes options for applying digital signatures to the generated output. The exact API depends on the edition and version; refer to the official documentation.

// FastReport PDF signing — conceptual outline
// Verify exact PDFExport properties in current documentation
using FastReport;
using FastReport.Export.Pdf;

using var report = new Report();
report.Load("Document.frx");
report.Prepare();

var pdfExport = new PDFExport();
// Digital signature properties
// pdfExport.Certificate = new X509Certificate2("cert.pfx", "password");
// pdfExport.Signed = true;

report.Export(pdfExport, "signed-output.pdf");

Technical constraints:

  • Signature configuration is on the export object, not on a post-processing step; the signature is applied during render
  • Certificate management and hardware security module (HSM) support
  • Signing options are coupled to the export configuration; changing the certificate requires changing export configuration

IronPDF — Digital Signatures:

using IronPdf;
using IronPdf.Signing;

// Generate the report PDF first
var renderer = new ChromePdfRenderer();
using var pdf = renderer.RenderHtmlAsPdf(reportHtml);

// Apply signature as a post-render step — decoupled from generation
var signature = new PdfSignature("certificate.pfx", "certPassword")
{
    SigningContact = "approver@example.com",
    SigningLocation = "Chicago, IL",
    SigningReason = "Report certified"
};

pdf.Sign(signature);
pdf.SaveAs("certified-report.pdf");

Signatures are applied after rendering, which decouples certificate management from template configuration. The digital signatures guide covers visible and invisible signature variants; for environments with hardware-backed certificates, the HSM signing guide describes the integration approach.

Breaking Changes & Gotchas

  • No template format. Every FastReport frx template must be redesigned as an HTML template. There is no migration tool, no automated converter, and no format bridge. Treat each template as a new development task whose effort scales with the template's complexity. Templates with many bands, nested sub-reports, and complex expressions take longer than simple list reports.
  • Data binding moves to the application. FastReport's data binding layer—RegisterData, dataset traversal, field references in expressions—is replaced by application code that fetches data and passes it to the template engine. This is a meaningful shift: running totals, group aggregates, and cross-band calculations that FastReport evaluates automatically must be computed in C# before HTML construction.
  • No visual designer. Stakeholders who currently modify report layouts using the FastReport designer need a new workflow after migration. HTML/CSS templates in source control, accessible to developers, replace the designer. For organizations with non-developer report editors, this is a significant process change.
  • Report expressions do not transfer. FastReport's expression language ([DataSource.Field], [Page#], built-in functions like Sum(), Avg()) has no equivalent in IronPDF. All expression logic must be reimplemented in application code or a template engine.
  • Chromium binary dependencies. IronPDF ships native Chromium binaries. Linux container deployments require system packages for Chromium. This is a new deployment consideration.
  • Report disposal pattern similarity. FastReport's Report implements IDisposable. IronPDF's PdfDocument and ChromePdfRenderer also implement IDisposable. Teams familiar with the FastReport disposal pattern should apply the same discipline to IronPDF objects, but note that the specific objects requiring disposal are different.
  • Async model. FastReport report execution is synchronous; IronPDF provides both synchronous and async rendering methods. ASP.NET Core applications should prefer RenderHtmlAsPdfAsync() to avoid blocking request threads.
  • License key required. IronPDF requires a license key configured at startup. FastReport also has licensing requirements; migration includes provisioning the new license and removing the old one.

Migration Checklist

  1. Inventory the full template catalog. List every frx file in production. For each, record: band count, data source count, sub-report references, expression complexity, chart and barcode usage. This inventory is the foundation for the effort estimate.
  2. Categorize templates by migration complexity. Simple list reports with one data band are Low effort. Reports with multiple groups, running totals, sub-reports, charts, or complex expressions are High effort. Allocate development time accordingly.
  3. Plan data access migration. For each report's data sources, design corresponding data access methods in the application layer. FastReport's RegisterData pattern of passing DataTable or DataSet objects maps to service or repository methods that return typed objects or DTOs.
  4. Choose a templating engine. Select the HTML templating approach for new report templates: Razor (if already in use in the application), Scriban, Handlebars.NET, or direct string building. Consistency across templates reduces maintenance overhead.
  5. Install the IronPDF NuGet package. Run dotnet add package IronPdf. Verify runtime identifier coverage.
  6. Configure the license key. Set the IronPDF license key at application startup before any rendering calls. See the license key setup guide for configuration options.
  7. Develop and validate HTML templates, report by report. Begin with the simplest reports. For each, implement the data access method, author the HTML template, and validate output against the FastReport reference. Proceed to more complex reports after simple ones are confirmed.
  8. Implement aggregation and grouping logic. All FastReport expression-based calculations (group subtotals, running totals, grand totals) must be implemented as application-level computations before the HTML template is constructed. Write and unit-test this logic independently of the rendering.
  9. Configure headers and footers. Replace PageHeaderBand and PageFooterBand with RenderingOptions.TextHeader/Footer or HTML header/footer objects. Map FastReport expression tokens to IronPDF's {page}, {total-pages}, {date} equivalents.
  10. Port signature and security configurations. If reports are currently signed or encrypted via PDFExport configuration, implement equivalent PdfSignature and SecuritySettings code as post-render steps on the PdfDocument.
  11. Update ASP.NET integration. Replace FastReport export streams with pdf.BinaryData returned to FileContentResult. Switch synchronous report execution to async render calls (RenderHtmlAsPdfAsync()).
  12. Decommission FastReport dependencies. After all templates are migrated and tested in production, remove the FastReport NuGet packages. Update deployment manifests to remove frx template file distribution requirements.

Conclusion

When staying on FastReport is technically reasonable

FastReport remains a technically sound choice when the visual designer is a meaningful part of the team's workflow—particularly when report layout changes are made by non-developers who rely on the designer to modify templates without touching application code. The banded layout model is well-suited for complex paginated data reports with group headers, running totals, sub-reports, and built-in chart objects that would require significant HTML authoring effort to reproduce. If the template catalog is large, stable, and business-critical, and the current .NET version support is adequate, the migration cost is high relative to the operational risk of a large-scale template rewrite. FastReport's built-in chart and barcode objects are also genuine capabilities that require additional dependencies (charting libraries, barcode generators) to replicate in an HTML-based workflow.

Signals that indicate migration is worth the engineering effort

Migration becomes compelling when the team's development workflow is already HTML-centric—using Razor for web views, maintaining CSS design systems, building HTML email templates—and the FastReport model sits outside that workflow as an island. Teams that find themselves writing bridge code between application data models and FastReport's DataSet-centric binding model often accumulate technical debt in that layer. If the application is moving to Linux containers or a .NET version where the specific FastReport edition is not supported, that is a hard technical driver. Similarly, when the requirement has evolved from "generate a paginated data report" to "generate a richly formatted HTML document with some tabular data," the HTML rendering model is a more natural fit.

What the cutover typically involves at the code level

The code-level migration has two distinct workstreams. The first is data plumbing: replacing FastReport's data binding with application-layer data access and passing results to a template engine. The second is template development: translating each frx band layout into an HTML/CSS template. The first workstream is mechanical and predictable; the second scales with the complexity of the template catalog. Teams that execute the migration report-by-report—keeping FastReport active for unmigrated reports while new HTML templates are developed and validated—tend to manage risk better than teams that attempt a simultaneous cutover of the entire catalog.

As you evaluate this migration, how does the ratio of simple list reports to complex grouped/aggregated reports in your catalog affect your assessment of the total development effort?
