Migrating from PeachPDF to IronPDF: what changes, what breaks, what maps

from install to first PDF — the full migration path

Framing

PDF generation in .NET has long been served by a fragmented ecosystem of libraries — some commercial, some open-source, some maintained actively and some effectively dormant. Teams re-evaluate their PDF library for a variety of reasons that have little to do with dissatisfaction: a library reaches end-of-life, a new platform target (Linux containers, MAUI, Blazor Server) falls outside the library's support matrix, or a security audit surfaces an unmaintained transitive dependency. In some cases the trigger is simpler: a developer who originally integrated the library has left the team, the license model changed, or the output quality no longer meets a compliance requirement.

Niche PDF libraries occupy an interesting position in this landscape. They are typically lightweight and fast to integrate, and they often solve a narrow problem extremely well. The trade-off is that their feature surface is intentionally constrained, maintenance cadence depends heavily on a small maintainer group, and ecosystem documentation is thinner than that of larger commercial offerings. When a project's requirements outgrow that narrow surface, migration becomes a practical engineering decision rather than a preference.

PeachPDF is one such niche library in the .NET space. Teams considering a move to IronPDF are usually doing so because they need broader format support, more predictable rendering of modern HTML/CSS, or a commercially backed support contract. This guide maps the technical path from PeachPDF to IronPDF at the code level, without advocating for the switch itself.

What PeachPDF Is Designed to Do

PeachPDF is a .NET PDF generation library focused on converting HTML content to PDF output. Its architecture centers on an HTML rendering pipeline that parses markup and applies CSS layout rules to produce paginated PDF documents. The integration model is straightforward: the library exposes a small API surface that accepts HTML strings or file paths and returns either a byte array or a stream representing the generated PDF.

The primary use case is server-side document generation — invoices, reports, and formatted correspondence — where the input is already in HTML form and the output needs to be a reasonably faithful PDF rendering of that markup. PeachPDF's install footprint is relatively small, which makes it attractive for microservices and containerized deployments where binary size matters. Note: the library's current maintenance status, supported .NET versions, and latest release should be verified against official documentation and the library's source repository before making migration decisions.

Architectural Differences

IronPDF approaches HTML-to-PDF rendering by embedding a Chromium-based rendering engine rather than implementing its own layout engine. This architectural choice means that the rendering pipeline behaves consistently with how a modern browser would display the same HTML and CSS. JavaScript is executed as part of the render cycle, web fonts resolve through standard browser mechanics, and CSS Grid and Flexbox layout behave as a developer would expect from browser testing.

The practical consequence for migration is that HTML-to-PDF rendering in IronPDF produces output that is tightly coupled to Chromium's rendering behavior. Teams moving from a library with a custom layout engine may see layout differences — particularly in edge cases around floats, absolute positioning, or print media queries — that require template adjustments even when the API swap itself is straightforward.

IronPDF's integration model is also broader than a typical niche library. Beyond HTML input, it accepts URLs, DOCX files, images, and Markdown as source formats. Its document operations layer supports merging, splitting, stamping, signing, and password-protecting PDFs after generation. The disposal model follows standard .NET IDisposable patterns: PdfDocument objects should be disposed after use, and the library exposes async rendering paths for high-throughput pipeline scenarios. License activation is handled at application startup via a static call; see the license setup guide for the precise initialization pattern.

Operation Comparisons

HTML String to PDF

PeachPDF — HTML String to PDF

PeachPDF's typical API pattern for rendering an HTML string involves instantiating a renderer class, passing HTML content, and retrieving the output as bytes or a file. The exact class and method names should be verified in the library's current documentation.

Key constraints:

  • Rendering engine is not Chromium-based; CSS support may lag behind modern browser behavior
  • JavaScript execution support level is - in official documentation
  • Async rendering availability is -

IronPDF — HTML String to PDF

IronPDF renders HTML strings via ChromePdfRenderer, which wraps a Chromium engine and returns a PdfDocument that must be disposed after use. The HTML string to PDF guide covers the full API including render options, wait-for conditions, and output configuration.

using IronPdf;

// Initialize license before first use (typically in application startup)
// IronPdf.License.LicenseKey = "YOUR-LICENSE-KEY";

using var renderer = new ChromePdfRenderer();

// Optional: configure rendering options
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 10;
renderer.RenderingOptions.MarginBottom = 10;

// Render HTML string to PDF
using var pdf = renderer.RenderHtmlAsPdf("<h1>Hello, PDF</h1><p>Migration complete.</p>");

// Save to file
pdf.SaveAs("/output/document.pdf");

// Or retrieve as byte array
byte[] pdfBytes = pdf.BinaryData;

ChromePdfRenderer is thread-safe for concurrent rendering when each thread holds its own instance. The PdfDocument returned implements IDisposable; wrapping it in a using block prevents native resource leaks.

HTML File to PDF

PeachPDF — HTML File to PDF

PeachPDF's file-based API accepts a path to an HTML file on disk. Asset resolution (images, stylesheets referenced by relative paths) depends on the library's base URL handling

Key constraints:

  • Base URL resolution for local assets may differ from browser behavior
  • No JavaScript execution during render
  • File encoding handling

IronPDF — HTML File to PDF

IronPDF resolves local file paths using the file's directory as the implicit base URL, which means relative stylesheet and image references resolve as expected. The rendering options guide covers the full set of pre-render configuration available.

using IronPdf;
using System.IO;

using var renderer = new ChromePdfRenderer();

// Render a local HTML file; relative asset paths resolve against the file's directory
string htmlFilePath = Path.GetFullPath("report.html");
using var pdf = renderer.RenderHtmlFileAsPdf(htmlFilePath);

pdf.SaveAs("/output/report.pdf");

If assets are hosted on a remote base URL, ChromePdfRenderOptions.CustomCssUrl and related properties allow explicit base URL configuration

Headers and Footers

PeachPDF — Headers and Footers

PeachPDF's header/footer mechanism is - in official documentation. Common patterns in lightweight HTML-to-PDF libraries include injecting header/footer HTML into the template itself using CSS @page rules, or providing a string-substitution API with page number tokens.

Key constraints:

  • @page CSS-based headers may not render consistently across non-Chromium engines
  • Page count tokens and dynamic content often require workarounds
  • Per-page conditional headers (e.g., first page different) may not be supported

IronPDF — Headers and Footers

IronPDF provides typed header/footer objects that are applied after rendering, independent of the HTML template. Both TextHeaderFooter (simple text with tokens) and HtmlHeaderFooter (full HTML markup rendered per page) are supported. The headers and footers guide documents available token substitutions and per-section configuration.

using IronPdf;

using var renderer = new ChromePdfRenderer();

// Configure an HTML-based footer with page numbering
renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 15,
    // {page} and {total-pages} are substituted at render time
    HtmlFragment = "<div style='text-align:right; font-size:10px;'>Page {page} of {total-pages}</div>",
    DrawDividerLine = true
};

using var pdf = renderer.RenderHtmlAsPdf("<h1>Annual Report</h1><p>Content follows.</p>");
pdf.SaveAs("/output/report-with-footer.pdf");

The header/footer is decoupled from the HTML content, which avoids the need for @page CSS workarounds and produces consistent output across page counts that aren't known at template-authoring time.

Merge PDFs

PeachPDF — Merge PDFs

PeachPDF's merge capability is - in official documentation. Teams using PeachPDF for merge operations may be relying on a secondary library (PdfSharp, iTextSharp) for post-generation document assembly.

Key constraints:

  • Merge support and API surface -
  • If merge is not native, migration may simplify the dependency graph by consolidating to a single library

IronPDF — Merge PDFs

IronPDF's PdfDocument.Merge() static method accepts a collection of PdfDocument instances and returns a new merged document. The merge and split guide covers both merge and split operations.

using IronPdf;
using System.Collections.Generic;

// Load existing PDFs from disk
using var doc1 = PdfDocument.FromFile("/input/part1.pdf");
using var doc2 = PdfDocument.FromFile("/input/part2.pdf");
using var doc3 = PdfDocument.FromFile("/input/part3.pdf");

// Merge into a single document; Merge() returns a new PdfDocument
using var merged = PdfDocument.Merge(new List<PdfDocument> { doc1, doc2, doc3 });

merged.SaveAs("/output/merged.pdf");

Page ordering is determined by the list order. Individual PdfDocument inputs remain valid after the merge call; dispose each one when finished.

Breaking Changes & Gotchas

  • Rendering engine change. Moving from PeachPDF's layout engine to Chromium means CSS rendering behavior will differ. Templates that relied on non-standard CSS quirks, custom font fallback behavior, or specific float/clear behavior may produce different layouts and require adjustments.
  • Chromium binary dependency. IronPDF ships with or downloads a Chromium binary. In containerized environments (Docker, Kubernetes) this means the image requires additional Linux dependencies. The IronPDF documentation lists required system packages for Debian/Ubuntu-based images
  • Namespace change. All IronPDF types live under the IronPdf namespace. Any using directives referencing PeachPDF namespaces must be updated.
  • License initialization. IronPDF requires a license key to be set at startup. Deployments that previously required no license management will need to add this initialization step and manage the key as a configuration secret.
  • Disposal semantics. PdfDocument and ChromePdfRenderer implement IDisposable. Code patterns that do not dispose these objects will leak native resources, especially under load. PeachPDF's disposal behavior is -; if it does not use native resources, existing code may not follow dispose patterns and will need updating.
  • Thread safety model. IronPDF recommends creating separate ChromePdfRenderer instances per thread or per request rather than sharing a single instance. Verify the concurrency model documented for the version in use.
  • JavaScript execution overhead. Because IronPDF executes JavaScript via Chromium, render times for HTML that triggers heavy JS (charts, data tables) will be higher than a non-JS rendering path. Async rendering and the WaitFor API provide control over this—see async rendering.
  • Missing PeachPDF-specific features. Any PeachPDF-specific convenience APIs (if they exist) that do not have direct IronPDF equivalents will need to be reimplemented using IronPDF's primitives.

Migration Checklist

  1. Audit current usage. Enumerate every call site that uses PeachPDF. Categorize by operation (render, save, merge, etc.) to scope the migration surface.
  2. Swap the NuGet package. Remove the PeachPDF package reference and add IronPdf via NuGet: dotnet add package IronPdf.
  3. Configure the license key. Add IronPdf.License.LicenseKey = "YOUR-KEY"; to application startup. Store the key in environment configuration, not in source. See the license setup guide.
  4. Update using directives. Replace all PeachPDF namespace imports with using IronPdf; and related sub-namespaces as needed.
  5. Remap rendering calls. Replace PeachPDF renderer instantiation and render calls with ChromePdfRenderer and the appropriate Render*AsPdf() method.
  6. Add disposal patterns. Wrap ChromePdfRenderer and PdfDocument in using blocks or call Dispose() explicitly. Audit all code paths including exception handling.
  7. Remap output methods. Update byte array, stream, and file save calls to IronPDF equivalents (BinaryData, ToStream(), SaveAs()).
  8. Migrate headers/footers. If PeachPDF headers/footers were CSS @page based, refactor to HtmlHeaderFooter or TextHeaderFooter objects on RenderingOptions.
  9. Test JavaScript-dependent templates. If HTML templates use JavaScript (charts, dynamic tables), test render output with IronPDF and adjust WaitFor settings as needed.
  10. Validate in target deployment environment. If deploying to Linux or Docker, verify Chromium system dependencies are installed. Run rendering tests in the target container image before promoting to production.
  11. Compare output PDFs. Use a visual diff tool or automated acceptance test to compare PeachPDF output against IronPDF output for representative documents. Flag any layout regressions for template adjustment.
  12. Update logging and monitoring. IronPDF supports custom logging; configure it to integrate with existing observability infrastructure.

Conclusion

Technically reasonable: If PeachPDF is actively maintained, its .NET target compatibility covers your deployment platform, and your document generation requirements are limited to basic HTML-to-PDF rendering without complex JavaScript, digital signatures, or compliance formats, there may be no engineering justification for migration, When staying on PeachPDF is. The existing integration is known, tested, and stable. Switching libraries carries real engineering cost and introduces regression risk that must be weighed against concrete gains.

Signals that indicate migration is worth the engineering effort: The clearest signals are platform blockers (PeachPDF does not support your target .NET version or OS), rendering correctness issues with modern CSS that cannot be resolved by template changes, and requirements for features (PDF/A compliance, digital signatures, DOCX input, URL rendering) that PeachPDF does not provide. A secondary signal is maintenance risk: if the library has no recent releases and no active issue responses, any future bug—especially a security-relevant one—may go unaddressed.

What the cutover typically involves at the code level: The rendering call sites are the primary change surface. In typical applications, this is a small number of service or utility classes. The mechanical steps are a NuGet swap, namespace updates, renderer class replacement, disposal pattern addition, and output method remapping. The less mechanical work — template adjustments for CSS rendering differences and deployment environment changes for Chromium dependencies — is where teams typically spend more time. A phased approach that runs both libraries in parallel on a subset of documents, with output comparison, reduces production risk.
