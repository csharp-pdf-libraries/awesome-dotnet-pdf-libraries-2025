Migrating from ExpertPdf to IronPDF: a .NET production guide

what the docs do not cover when switching PDF libraries

Framing

ExpertPdf has been a fixture in the .NET HTML-to-PDF space for well over a decade. Its long .NET Framework compatibility range — stretching from .NET Framework 2.0 through current versions — made it a natural choice for teams building on early .NET stacks and needing reliable HTML rendering without rebuilding their infrastructure. Libraries with that kind of longevity accumulate broad adoption in legacy codebases, and migration decisions are often deferred precisely because "it still works."

Re-evaluation tends to arrive from one of several directions. Modern CSS (Flexbox, Grid, custom properties) adoption in front-end templates exposes rendering gaps in libraries whose HTML engines were designed for an older web. Requirements for PDF/A compliance, digital signatures, parallel rendering, or PDF manipulation operations add surface area that was not part of the original adoption decision. And as applications migrate to .NET 6, 7, 8, or containerized Linux deployments, the integration patterns from the early .NET Framework era — synchronous rendering, single-threaded converters, large per-request setup overhead — begin to show friction.

This guide covers the migration from ExpertPdf to IronPDF for .NET engineers evaluating or executing the switch. Both libraries are HTML-to-PDF renderers, which makes the conceptual mapping straightforward. The migration is classified as Medium effort, reflecting differences in rendering engine generation, API surface, configuration model, and the disposal patterns that must be updated throughout the codebase.

What ExpertPdf Is Designed to Do

ExpertPdf is a commercial .NET library for HTML-to-PDF conversion. It is actively maintained and supports a broad range of .NET targets — from .NET Framework 2.0 through current .NET versions. The last release should be verified in official documentation. The library installs via NuGet; the install footprint should be verified in official documentation.

ExpertPdf's primary API is the HtmlToPdfConverter class, which is instantiated and configured via properties, then used to convert an HTML string or URL to a PDF byte array or file. The converter accepts configuration for paper size, orientation, margins, header/footer content, JavaScript execution, and authentication. The library has historically used its own HTML rendering engine, though Chromium-based rendering options have been added in more recent versions

Architectural Differences

ExpertPdf and IronPDF both accept HTML as input and produce PDF output. The differences in architecture — rendering engine generation, configuration model, and post-render manipulation surface — are the primary drivers of the Medium effort classification.

ExpertPdf's HtmlToPdfConverter is instantiated per-operation or reused across operations with reconfiguration between calls. IronPDF uses ChromePdfRenderer, which holds rendering configuration as persistent properties on RenderingOptions — the renderer instance is designed to be configured once and reused as a singleton. Both produce a document result, but ExpertPdf returns a byte[] directly from its conversion methods, while IronPDF's RenderHtmlAsPdf() returns a PdfDocument that implements IDisposable and must be wrapped in a using block.

The most operationally significant difference for teams with complex requirements is IronPDF's manipulation surface. ExpertPdf focuses on HTML-to-PDF conversion; IronPDF's PdfDocument additionally exposes merge, split, form filling, digital signatures, encryption, PDF/A and PDF/UA compliance, text extraction, stamping, annotations, and redaction — all on the same type without additional libraries. The rendering options reference covers IronPDF's full configuration surface. License initialization is a one-time startup call; see the license setup guide.

Operation Comparisons

HTML String to PDF

ExpertPdf — HTML String to PDF

using ExpertPdf.HtmlToPdf;

// ExpertPdf uses an instantiated converter with property-based configuration
var converter = new HtmlToPdfConverter();

// Paper size and orientation
converter.PdfDocumentOptions.PdfPageSize = PdfPageSize.A4;
converter.PdfDocumentOptions.PdfPageOrientation = PdfPageOrientation.Portrait;

// Margins in points
converter.PdfDocumentOptions.LeftMargin = 20;
converter.PdfDocumentOptions.RightMargin = 20;
converter.PdfDocumentOptions.TopMargin = 20;
converter.PdfDocumentOptions.BottomMargin = 20;

// JavaScript execution — delay allows JS to complete before capture
converter.PdfDocumentOptions.EnableJavascript = true;
converter.JavascriptTimeout = 5000; // milliseconds

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Monthly Report</h1>
  <p>Generated: 2026-02-25</p>
</body>
</html>";

// GetPdfBytesFromHtmlString returns byte[] directly — no disposal required
byte[] pdfBytes = converter.GetPdfBytesFromHtmlString(html);

System.IO.File.WriteAllBytes("report.pdf", pdfBytes);

Concrete constraints:

  • HtmlToPdfConverter properties configure the converter. Verify exact property paths (PdfDocumentOptions.*, JavascriptTimeout, etc.) in official documentation as they may differ by version.
  • The conversion methods (GetPdfBytesFromHtmlString, GetPdfBytesFromUrl) return byte[] directly — no IDisposable result to manage.
  • Margin units should be verified in official documentation; ExpertPdf has used different unit conventions across versions.
  • The rendering engine used (custom HTML renderer vs Chromium) affects CSS fidelity. Verify which engine is active in the current version.

IronPDF — HTML String to PDF

using IronPdf;

// Renderer is configured once and reused — register as singleton in DI
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.PaperOrientation = IronPdf.Rendering.PdfPaperOrientation.Portrait;
renderer.RenderingOptions.MarginTop = 20;     // millimeters
renderer.RenderingOptions.MarginBottom = 20;
renderer.RenderingOptions.MarginLeft = 20;
renderer.RenderingOptions.MarginRight = 20;

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Monthly Report</h1>
  <p>Generated: 2026-02-25</p>
</body>
</html>";

// PdfDocument is IDisposable — always use a using block
using var pdf = renderer.RenderHtmlAsPdf(html);

// Access bytes or save directly
byte[] pdfBytes = pdf.BinaryData;
pdf.SaveAs("report.pdf");

The shift from ExpertPdf's byte[] return to IronPDF's PdfDocument return is the most structurally significant change in this operation. The using block is mandatory. Full rendering configuration is documented in the HTML string to PDF guide.

URL to PDF with Authentication

ExpertPdf — URL to PDF with Login

using ExpertPdf.HtmlToPdf;

var converter = new HtmlToPdfConverter();
converter.PdfDocumentOptions.PdfPageSize = PdfPageSize.A4;

// ExpertPdf supports form-based login before rendering
// This allows rendering of pages behind authentication
converter.LoginUser = "username";
converter.LoginPassword = "password";
// converter.LoginUrl = "https://app.example.com/login"; // verify property name

// Alternatively, inject cookies directly
// converter.PdfDocumentOptions.HttpRequestCookies = "session=abc123"; // verify

byte[] pdfBytes = converter.GetPdfBytesFromUrl("https://app.example.com/dashboard");
System.IO.File.WriteAllBytes("dashboard.pdf", pdfBytes);

Concrete constraints:

  • ExpertPdf's login automation submits a form before rendering the target URL — useful for applications without cookie-based session injection. The exact property names (LoginUser, LoginPassword, LoginUrl) should be verified in official documentation.
  • Cookie injection is an alternative path for session-based authentication
  • IronPDF does not provide form-based login automation; authentication must be handled via cookie injection or pre-authenticated URL rendering.

IronPDF — URL to PDF with Cookie Authentication

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Inject an authentication cookie obtained from the application's login flow
renderer.RenderingOptions.CustomCookies =
    new System.Collections.Generic.Dictionary<string, string>
    {
        { "session_id", "your-session-token" },
        { ".AspNetCore.Cookies", "your-auth-cookie-value" }
    };

// WaitFor ensures JS-rendered dashboard content is loaded before capture
renderer.RenderingOptions.WaitFor.NetworkIdle(networkIdleTimeSpan: TimeSpan.FromSeconds(2));

using var pdf = renderer.RenderUrlAsPdf("https://app.example.com/dashboard");
pdf.SaveAs("dashboard.pdf");

IronPDF's URL rendering supports cookie injection, custom HTTP headers, and network idle wait conditions. Applications that relied on ExpertPdf's form-based login automation must obtain session cookies through the application's own login API before calling IronPDF. The URL to PDF guide covers authentication patterns and the WaitFor configuration.

Headers and Footers

ExpertPdf — Headers and Footers

using ExpertPdf.HtmlToPdf;

var converter = new HtmlToPdfConverter();
converter.PdfDocumentOptions.PdfPageSize = PdfPageSize.A4;

// ExpertPdf header configuration
converter.PdfDocumentOptions.ShowHeader = true;
converter.PdfDocumentOptions.HeaderHeight = 30; // points or mm

// Header HTML content
converter.PdfDocumentOptions.HtmlToPdfHeader = new HtmlToPdfElement(
    0, 0, 0, 30,
    "<div style='font-size:9px; text-align:right;'>Page &p; of &P;</div>",
    converter.PdfDocumentOptions.PdfPageSize, PdfPageOrientation.Portrait
);

// Footer
converter.PdfDocumentOptions.ShowFooter = true;
converter.PdfDocumentOptions.HtmlToPdfFooter = new HtmlToPdfElement(
    0, 0, 0, 20,
    "<div style='font-size:8px; text-align:center;'>CONFIDENTIAL</div>",
    converter.PdfDocumentOptions.PdfPageSize, PdfPageOrientation.Portrait
);

byte[] pdfBytes = converter.GetPdfBytesFromHtmlString(
    "<html><body><p>Body content.</p></body></html>");

Concrete constraints:

  • ExpertPdf uses HtmlToPdfElement objects that wrap an HTML string with position and size parameters. Verify exact constructor signature and parameter order in official documentation.
  • Page number tokens in ExpertPdf use &p; and &P; syntax — different from IronPDF's {page} and {total-pages}.
  • HtmlToPdfElement constructor parameters (x, y, width, height) use the same unit system as the rest of ExpertPdf

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// HtmlHeaderFooter accepts a full HTML fragment — no position parameters needed
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 15,  // millimeters
    HtmlFragment = "<div style='font-size:9px; text-align:right; font-family:Arial;'>" +
                   "Page {page} of {total-pages}</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 12,
    HtmlFragment = "<div style='font-size:8px; text-align:center; font-family:Arial;'>" +
                   "CONFIDENTIAL</div>"
};

using var pdf = renderer.RenderHtmlAsPdf("<html><body><p>Body content.</p></body></html>");
pdf.SaveAs("document-with-header.pdf");

The token syntax change is the most common source of silent header/footer bugs during migration: ExpertPdf's &p; and &P; become {page} and {total-pages} in IronPDF. The HtmlHeaderFooter model eliminates the HtmlToPdfElement position parameters — height is set in millimeters and the HTML fragment handles its own internal layout. Full configuration is in the headers and footers guide.

Async in ASP.NET Core

ExpertPdf — Async Context

using ExpertPdf.HtmlToPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("documents")] public class DocumentController : ControllerBase { [HttpGet("{id}/pdf")] public async Task GetDocument(int id) { string html = await BuildHtmlAsync(id);

// ExpertPdf's conversion methods are synchronous // Task.Run() prevents blocking the ASP.NET Core thread pool byte[] pdfBytes = await Task.Run(() => { var converter = new HtmlToPdfConverter(); converter.PdfDocumentOptions.PdfPageSize = PdfPageSize.A4; return converter.GetPdfBytesFromHtmlString(html); });

return File(pdfBytes, "application/pdf", $"document-{id}.pdf"); }

private Task BuildHtmlAsync(int id) => Task.FromResult($"

Document {id}

"); }

Concrete constraints:

  • HtmlToPdfConverter.GetPdfBytesFromHtmlString() is synchronous — using it directly in an async ASP.NET Core action blocks the thread pool under concurrent load.
  • The Task.Run() pattern moves the blocking work off the request thread but does not reduce overall thread consumption — it shifts the problem rather than solving it.
  • Instantiating HtmlToPdfConverter per request may carry setup overhead; verify whether it is safe and performant to reuse a converter instance across requests.

IronPDF — Async in ASP.NET Core

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("documents")] public class DocumentController : ControllerBase { private readonly ChromePdfRenderer _renderer;

public DocumentController(ChromePdfRenderer renderer) { _renderer = renderer; }

[HttpGet("{id}/pdf")] public async Task GetDocument(int id) { string html = await BuildHtmlAsync(id);

// Genuinely async — no Task.Run() wrapper required using var pdf = await _renderer.RenderHtmlAsPdfAsync(html);

return File(pdf.BinaryData, "application/pdf", $"document-{id}.pdf"); }

private Task BuildHtmlAsync(int id) => Task.FromResult($"

Document {id}

"); } ```

RenderHtmlAsPdfAsync returns Task<PdfDocument> and integrates directly into the async pipeline. The singleton ChromePdfRenderer is configured once and injected through DI — no per-request construction overhead. The async rendering guide covers concurrency and parallel batch generation.

Breaking Changes & Gotchas

  • Return type change — byte[] to PdfDocument: ExpertPdf's conversion methods return byte[] directly. IronPDF returns PdfDocument. Every call site must be updated to access pdf.BinaryData for the bytes and every PdfDocument must be in a using block. Missing using blocks cause unmanaged resource leaks.
  • Header/footer token syntax: ExpertPdf uses &p; and &P; for current page and total pages. IronPDF uses {page} and {total-pages}. This is a silent error — old tokens render as literal strings in IronPDF output.
  • HtmlToPdfElement replaced by HtmlHeaderFooter: ExpertPdf's header/footer API uses position and size parameters for element placement. IronPDF's HtmlHeaderFooter accepts only an HTML fragment and a height value — internal layout is handled by the HTML/CSS.
  • No form-login automation: ExpertPdf supports automated form-based login before rendering authenticated pages. IronPDF does not. Applications relying on this feature must obtain session cookies through the application's own auth flow before passing them to IronPDF.
  • Rendering engine version and fidelity: If the ExpertPdf version in use employs its older HTML renderer rather than Chromium, the rendering comparison between ExpertPdf and IronPDF output will reveal layout differences. Templates written for the older engine may require CSS updates. This is the most variable factor in estimating migration effort.
  • Namespace change: Replace using ExpertPdf.HtmlToPdf; and related ExpertPdf namespaces with using IronPdf;. Compile errors guide the remaining work.
  • DI registration: ExpertPdf's HtmlToPdfConverter is often instantiated per-operation. IronPDF's ChromePdfRenderer is intended to be a singleton: builder.Services.AddSingleton<ChromePdfRenderer>(). Update DI configuration and all constructor injections.
  • License key required: IronPdf.License.LicenseKey must be set before the first render call. ExpertPdf uses its own license mechanism
  • Async availability: ExpertPdf has synchronous conversion methods. IronPDF provides RenderHtmlAsPdfAsync() and RenderUrlAsPdfAsync(). Replace Task.Run() wrappers with the native async methods.
  • Thread safety: Assume HtmlToPdfConverter is not thread-safe unless official documentation states otherwise. ChromePdfRenderer is designed for reuse

Migration Checklist

  1. Audit all HtmlToPdfConverter call sites: List every instantiation, its configuration (paper size, margins, orientation, header/footer, authentication), and its output method (GetPdfBytesFromHtmlString, GetPdfBytesFromUrl).
  2. Identify which ExpertPdf rendering engine is in use: Determine whether the version in use employs the Chromium-based renderer or the older HTML engine. This determines the scope of the rendering fidelity review in step 3.
  3. Render-compare all templates with IronPDF: Before any code changes, render each HTML template with IronPDF and compare against ExpertPdf output. Identify and document layout differences — these are the CSS updates to make after the API swap.
  4. Install IronPDF via NuGet: dotnet add package IronPdf. Retain ExpertPdf references until replacement code compiles and tests pass.
  5. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs or Startup.cs. See the license setup guide.
  6. Register ChromePdfRenderer in DI: Add builder.Services.AddSingleton<ChromePdfRenderer>() and update all constructor injections.
  7. Update namespaces: Replace using ExpertPdf.HtmlToPdf; and related directives with using IronPdf;. Compile errors identify every affected file.
  8. Replace GetPdfBytesFromHtmlString() calls: Map each to renderer.RenderHtmlAsPdf(html). Wrap PdfDocument in using. Access bytes via pdf.BinaryData or save via pdf.SaveAs(path).
  9. Replace GetPdfBytesFromUrl() calls: Map to renderer.RenderUrlAsPdf(url). Configure WaitFor if JavaScript timing was previously handled via JavascriptTimeout.
  10. Port header/footer configuration: Replace HtmlToPdfElement with HtmlHeaderFooter. Update page number tokens: &p; → {page}, &P; → {total-pages}.
  11. Replace Task.Run() wrappers: Swap await Task.Run(() => converter.GetPdfBytesFromHtmlString(...)) for await renderer.RenderHtmlAsPdfAsync(html).
  12. Address form-login authentication: For any URL render that used ExpertPdf's LoginUser/LoginPassword automation, implement an equivalent session cookie acquisition flow and inject cookies via RenderingOptions.CustomCookies.
  13. Remove ExpertPdf NuGet reference: Once all replacements compile and tests pass, remove the ExpertPdf package and perform a final build verification.

Conclusion

When staying on ExpertPdf is technically reasonable

ExpertPdf is a reasonable choice when its current rendering engine meets the CSS fidelity requirements of existing templates, the form-based login automation is a key feature for rendering authenticated pages without a separate session acquisition step, and the application's PDF requirements do not extend into the manipulation, compliance, and signing areas that ExpertPdf does not cover. Teams with a stable ExpertPdf integration and no immediate rendering or platform pressure have no urgent migration trigger.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when templates use modern CSS (Flexbox, Grid, custom properties, web fonts) and rendering fidelity is a friction point with the current ExpertPdf version; when new requirements include digital signatures, PDF/A compliance, form filling, or PDF manipulation that require a separate library alongside ExpertPdf; when the synchronous API is causing thread pool exhaustion in high-concurrency ASP.NET Core applications; or when Linux and container deployment targets are creating compatibility uncertainty.

What the cutover typically involves at the code level

The API swap is mechanical for the core rendering path: register ChromePdfRenderer in DI, replace HtmlToPdfConverter instantiation with injected renderer, map property names to RenderingOptions, replace conversion method calls with renderer.Render*(), add using blocks, and update output access. The header/footer token update (&p;/&P; → {page}/{total-pages}) is a simple text substitution. The form-login replacement requires adding a cookie acquisition step that is architecture-specific. The rendering fidelity review — validating output parity for each template — is the most judgment-intensive step and scales with template complexity and ExpertPdf engine generation.

When you look at the rendering output from ExpertPdf today, are there layouts that you know render incorrectly compared to Chrome — and has the workaround cost for those layouts factored into any previous migration discussions?
