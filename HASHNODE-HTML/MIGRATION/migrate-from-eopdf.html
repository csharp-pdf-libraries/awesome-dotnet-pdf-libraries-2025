Migrating from EO.Pdf to IronPDF: what changes, what breaks, what maps

from install to first PDF — the full migration path

Framing

Chromium-based HTML-to-PDF libraries occupy a well-defined segment of the .NET PDF market. They promise that the same HTML and CSS that renders in a browser will render in the generated PDF — a significant step forward from the Qt WebKit era. Teams that adopted EO.Pdf typically did so because it provided this Chromium rendering capability in a .NET-native package without requiring external process management or complex binary deployment. The value proposition is familiar to anyone who has fought rendering bugs in older wkhtmltopdf wrappers.

Re-evaluation happens for a range of reasons. EO.Pdf's API surface is relatively narrow — it excels at HTML-to-PDF conversion but has a smaller footprint for PDF manipulation operations (merge, split, form-fill, sign, encrypt) than some alternatives. Teams that initially needed only HTML rendering and subsequently added requirements for digital signatures, PDF/A compliance, form processing, or parallel batch generation sometimes find they are stitching together multiple libraries to cover the full lifecycle. Platform compatibility can also be a factor: EO.Pdf on .NET 5+ requires explicit installation of System.Drawing.Common, which is marked as unsupported on non-Windows platforms in .NET 6+ and can introduce friction in Linux and container deployments.

This guide covers the migration from EO.Pdf (v26.0.34, December 2025) to IronPDF for .NET engineers evaluating or executing the switch. The migration is classified as Low effort because both libraries use Chromium rendering, the API concepts are nearly identical, and the primary work is a configuration mapping exercise. The guide is structured to be useful whether or not migration ultimately proceeds.

What EO.Pdf Is Designed to Do

EO.Pdf is a commercial .NET library published by Essential Objects. It is actively maintained — version 26.0.34 was released in December 2025. The library's primary capability is HTML-to-PDF conversion using an embedded Chromium rendering engine, which provides CSS3, JavaScript, web font, and SVG support consistent with a current Chromium browser. EO.Pdf installs via NuGet; the install footprint should be verified in official documentation, as the library bundles Chromium binaries and the package size is significant.

The library's API is centered on the HtmlToPdf static class, which exposes ConvertUrl() and ConvertHtml() methods returning a PdfDocument. Additional static options classes (HtmlToPdfOptions, PageSize, PageMargins) configure paper size, margins, orientation, JavaScript execution, and other rendering parameters. EO.Pdf supports basic PDF operations including password protection and metadata. On .NET 5+ projects targeting non-Windows platforms, System.Drawing.Common must be explicitly installed and may require additional configuration, as the assembly is marked unsupported on non-Windows in .NET 6+. The primary use case should be verified in official documentation, but EO.Pdf is most commonly used for server-side report generation and HTML-to-PDF export in ASP.NET applications.

Architectural Differences

EO.Pdf and IronPDF share the same high-level approach: both use an embedded Chromium engine to render HTML/CSS to PDF in-process. The architectural differences are in API design, the manipulation surface available after rendering, and the deployment dependencies.

EO.Pdf's API is primarily static — HtmlToPdf.ConvertUrl() and HtmlToPdf.ConvertHtml() are static methods that accept options objects and return a PdfDocument. IronPDF uses an instance-based model: ChromePdfRenderer holds rendering configuration as mutable properties on RenderingOptions, and rendering calls produce PdfDocument instances. Both PdfDocument types implement IDisposable, but EO.Pdf's returned documents are often used without explicit disposal

The most significant architectural difference is the manipulation API available after rendering. EO.Pdf's PdfDocument provides a limited set of operations. IronPDF's PdfDocument exposes merge, split, page operations, form filling, digital signatures, encryption, PDF/A and PDF/UA compliance, text extraction, stamping, and annotations — all on the same type. The rendering options reference covers IronPDF's full rendering configuration. License initialization is a one-time startup call via IronPdf.License.LicenseKey; see the license setup guide.

Operation Comparisons

HTML String to PDF

EO.Pdf — HTML String to PDF

using EO.Pdf;

// EO.Pdf uses a static API — no renderer instance required
// Options are configured in an HtmlToPdfOptions object
var options = new HtmlToPdfOptions
{
    // Paper size via PageSize property
    PageSize = new PdfPageSize(PdfPageSizes.A4),

    // Margins in points (1 point = 1/72 inch)
    PageMargins = new PdfPageMargins
    {
        Left = 36,   // ~12.7mm
        Right = 36,
        Top = 36,
        Bottom = 36
    }
};

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #1042</h1>
  <p>Total: $500.00</p>
</body>
</html>";

// Static conversion method — no instance to dispose
PdfDocument pdfDoc = HtmlToPdf.ConvertHtml(html, options);

// Save to file
pdfDoc.Save("invoice.pdf");

Concrete constraints:

  • The API is static — there is no ChromePdfRenderer instance to configure and reuse. Options are constructed per-call or reused across calls.
  • PdfPageMargins units are in points (1/72 inch), not millimeters. IronPDF's RenderingOptions.Margin* properties use millimeters — the value must be converted (multiply points by 0.353 to get mm, or divide mm by 0.353 to get points).
  • PdfDocument.Save(path) is the output method. GetPdfBytes() returns a byte array.
  • Disposal of the returned PdfDocument should be verified in EO.Pdf official documentation — the API is not consistently used with using blocks in EO.Pdf samples.

IronPDF — HTML String to PDF

using IronPdf;

// Instance-based renderer — configure once, reuse across calls
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 12.7;    // millimeters (~36 points)
renderer.RenderingOptions.MarginBottom = 12.7;
renderer.RenderingOptions.MarginLeft = 12.7;
renderer.RenderingOptions.MarginRight = 12.7;

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #1042</h1>
  <p>Total: $500.00</p>
</body>
</html>";

// PdfDocument is IDisposable — always use a using block
using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("invoice.pdf");

The unit conversion from EO.Pdf's point-based margins to IronPDF's millimeter-based margins is the most common source of layout differences when migrating. Convert: mm = points × 0.3528. Full rendering configuration is in the HTML string to PDF guide.

URL to PDF

EO.Pdf — URL to PDF

using EO.Pdf;

var options = new HtmlToPdfOptions
{
    PageSize = new PdfPageSize(PdfPageSizes.A4),
    // JavaScript is executed by default in EO.Pdf's Chromium engine
    // For pages that require explicit wait time:
    // options.JSDelay = 2000; // milliseconds
};

// Static conversion — fetches and renders the URL in-process
PdfDocument pdfDoc = HtmlToPdf.ConvertUrl("https://reports.example.com/monthly", options);
pdfDoc.Save("monthly-report.pdf");

Concrete constraints:

  • EO.Pdf's URL rendering uses an embedded Chromium browser — JavaScript execution is default, same as IronPDF.
  • For pages with async content loading, a JavaScript delay or wait condition must be configured. Verify the exact property name (JSDelay or equivalent) in official documentation.
  • Authentication cookies, custom request headers, and proxy configuration should be verified in official documentation.
  • The returned PdfDocument disposal behavior should be verified.

IronPDF — URL to PDF

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// For pages with JavaScript-driven content, configure a wait condition
renderer.RenderingOptions.WaitFor.RenderDelay(2000); // milliseconds

// Optional: inject authentication cookie before rendering
renderer.RenderingOptions.CustomCookies =
    new System.Collections.Generic.Dictionary<string, string>
    {
        { "session_id", "your-session-value" }
    };

using var pdf = renderer.RenderUrlAsPdf("https://reports.example.com/monthly");
pdf.SaveAs("monthly-report.pdf");

IronPDF's WaitFor configuration provides fine-grained control over JavaScript execution timing — wait for a specific DOM element, a network idle state, or a fixed delay. The URL to PDF guide covers cookie injection, custom headers, and wait conditions. The JavaScript wait conditions guide covers WaitFor in detail.

Output to Byte Array (Memory Stream Pattern)

EO.Pdf — Byte Array Output

using EO.Pdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { [HttpGet("{id}")] public IActionResult GetReport(int id) { string html = BuildReportHtml(id);

var options = new HtmlToPdfOptions { PageSize = new PdfPageSize(PdfPageSizes.A4) };

// EO.Pdf ConvertHtml is synchronous PdfDocument pdfDoc = HtmlToPdf.ConvertHtml(html, options);

// GetPdfBytes() returns the PDF as a byte array byte[] bytes = pdfDoc.GetPdfBytes();

return File(bytes, "application/pdf", $"report-{id}.pdf"); }

private string BuildReportHtml(int id) => $"

Report {id}

"; }

Concrete constraints:

  • HtmlToPdf.ConvertHtml() is synchronous. In async ASP.NET Core controllers, this blocks the calling thread. A Task.Run() wrapper is the workaround — creating thread pool pressure under load.
  • GetPdfBytes() returns the full PDF in memory. Verify whether PdfDocument holds a reference to the bytes or copies them — relevant for large PDF memory management.
  • EO.Pdf has no native async rendering API

IronPDF — Async Byte Array Output

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { private readonly ChromePdfRenderer _renderer;

public ReportController(ChromePdfRenderer renderer) { _renderer = renderer; }

[HttpGet("{id}")] public async Task GetReport(int id) { string html = BuildReportHtml(id);

// RenderHtmlAsPdfAsync is genuinely async — no Task.Run() needed using var pdf = await _renderer.RenderHtmlAsPdfAsync(html);

return File(pdf.BinaryData, "application/pdf", $"report-{id}.pdf"); // pdf disposed when response is written }

private string BuildReportHtml(int id) => $"

Report {id}

"; }

RenderHtmlAsPdfAsync returns Task<PdfDocument> and is genuinely async — removing the need for Task.Run() wrappers in ASP.NET Core controllers. The async rendering guide covers concurrency and batch generation patterns.

PDF Password Protection

EO.Pdf — Password Protection

using EO.Pdf;

var options = new HtmlToPdfOptions
{
    PageSize = new PdfPageSize(PdfPageSizes.A4)
};

PdfDocument pdfDoc = HtmlToPdf.ConvertHtml(
    "<html><body><p>Confidential</p></body></html>", options);

// EO.Pdf password protection via Security property
pdfDoc.Security.UserPassword = "viewpassword";
pdfDoc.Security.OwnerPassword = "adminpassword";

// Permission flags restrict what users can do with the PDF
// pdfDoc.Security.AllowPrinting = false; // verify exact property name

pdfDoc.Save("secure.pdf");

Concrete constraints:

  • EO.Pdf's Security property is set directly on the returned PdfDocument. Verify exact permission flag property names in official documentation.
  • The security model follows the PDF specification's owner/user password distinction — owner password controls permissions, user password controls opening.

IronPDF — Password Protection

using IronPdf;

var renderer = new ChromePdfRenderer();

using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><p>Confidential</p></body></html>");

// SecuritySettings on PdfDocument mirrors the PDF permission model
pdf.SecuritySettings.UserPassword = "viewpassword";
pdf.SecuritySettings.OwnerPassword = "adminpassword";
pdf.SecuritySettings.AllowUserPrinting = IronPdf.Security.PdfPrintSecurity.FullPrintRights;

pdf.SaveAs("secure.pdf");

Password encryption and all permission flag configurations are documented in the passwords and permissions guide. The property naming convention differs from EO.Pdf's Security.* — map each permission flag individually.

Breaking Changes & Gotchas

  • Static vs instance API: EO.Pdf uses a static HtmlToPdf class with static conversion methods. IronPDF uses a ChromePdfRenderer instance with rendering configuration stored as properties. Every call site must shift from HtmlToPdf.ConvertHtml(html, options) to renderer.RenderHtmlAsPdf(html) with options pre-set on the renderer.
  • Margin unit change — points to millimeters: EO.Pdf's PdfPageMargins uses points (1 point = 1/72 inch). IronPDF's RenderingOptions.Margin* uses millimeters. This is a silent rendering difference that changes page layout. Convert: mm = points × 0.3528. A 36-point margin (common EO.Pdf default) is approximately 12.7mm.
  • PdfDocument type name collision: Both EO.Pdf and IronPDF define a class named PdfDocument. If both packages are present during the migration transition, all references must be fully qualified. Use IronPdf.PdfDocument vs EO.Pdf.PdfDocument until the EO.Pdf reference is removed.
  • PdfDocument disposal: EO.Pdf's PdfDocument disposal behavior should be verified in official documentation. IronPDF's PdfDocument implements IDisposable and must be wrapped in using blocks. Omitting using blocks causes unmanaged resource leaks.
  • No native async in EO.Pdf: EO.Pdf's conversion methods are synchronous. If the existing ASP.NET Core integration uses Task.Run() wrappers, replace them with await renderer.RenderHtmlAsPdfAsync().
  • System.Drawing.Common dependency removed: EO.Pdf on .NET 5+ requires explicit installation of System.Drawing.Common, which is unsupported on non-Windows in .NET 6+. IronPDF does not require System.Drawing.Common. Migrating removes this cross-platform compatibility concern.
  • License key required: IronPdf.License.LicenseKey must be set before the first render call. EO.Pdf uses a separate license mechanism
  • Namespace change: Replace using EO.Pdf; and related EO.Pdf namespaces with using IronPdf;. Compile errors identify every affected file.
  • DI registration pattern: EO.Pdf's static API requires no DI registration. IronPDF's ChromePdfRenderer is typically registered as a singleton: builder.Services.AddSingleton<ChromePdfRenderer>().

Migration Checklist

  1. Audit all EO.Pdf call sites: List every HtmlToPdf.ConvertHtml() and HtmlToPdf.ConvertUrl() call, the HtmlToPdfOptions being configured, and the output method used (Save() or GetPdfBytes()).
  2. Convert margin values from points to millimeters: For each PdfPageMargins value in the existing code, multiply by 0.3528 to get the equivalent millimeter value for IronPDF's RenderingOptions.Margin* properties.
  3. Install IronPDF via NuGet: dotnet add package IronPdf. Retain EO.Pdf references until replacement code compiles and tests pass.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs or Startup.cs before any render call. See the license setup guide.
  5. Register ChromePdfRenderer in DI: In Program.cs, add builder.Services.AddSingleton<ChromePdfRenderer>(). Update constructor injections throughout the application.
  6. Update namespaces: Replace using EO.Pdf; and related EO.Pdf using directives with using IronPdf;. Fully qualify PdfDocument during transition to avoid the type name conflict.
  7. Replace HtmlToPdf.ConvertHtml() calls: Map each call to renderer.RenderHtmlAsPdf(html) with the renderer configured via RenderingOptions properties. Wrap the result in a using block.
  8. Replace HtmlToPdf.ConvertUrl() calls: Map to renderer.RenderUrlAsPdf(url). Configure WaitFor if JavaScript delay was previously set via HtmlToPdfOptions.JSDelay.
  9. Replace pdfDoc.GetPdfBytes() with pdf.BinaryData: Replace pdfDoc.Save(path) with pdf.SaveAs(path).
  10. Replace Task.Run() wrappers with async rendering: In any ASP.NET Core async controller, replace Task.Run(() => HtmlToPdf.ConvertHtml(...)) with await renderer.RenderHtmlAsPdfAsync(html).
  11. Verify render output: Run side-by-side comparisons of EO.Pdf and IronPDF output for each template. Focus on margin/layout differences from the unit conversion and any header/footer behavior changes.
  12. Remove EO.Pdf NuGet reference: Once all call sites are replaced and tests pass, remove EO.Pdf from NuGet dependencies and perform a final build verification.

Conclusion

When staying on EO.Pdf is technically reasonable

EO.Pdf is a reasonable choice for applications whose PDF requirements are limited to HTML-to-PDF conversion with password protection — the core of its feature set. If the application targets Windows-only .NET deployments and the System.Drawing.Common dependency is not a concern, and if PDF manipulation operations (merge, sign, form-fill) are not required, EO.Pdf's simple static API and Chromium rendering may continue to serve the use case well. Teams satisfied with its feature coverage and familiar with its API have low immediate pressure to migrate.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when the application adds PDF operations beyond EO.Pdf's core rendering scope — digital signatures, PDF/A compliance, form filling, or batch manipulation; when the System.Drawing.Common dependency is creating friction in Linux or container deployments; when EO.Pdf's synchronous API is causing thread pool issues in high-concurrency ASP.NET Core applications; or when a single-package approach covering the full PDF lifecycle is preferred. The Low migration effort classification means the API swap is well-defined and time-bounded.

What the cutover typically involves at the code level

For a typical ASP.NET Core application using EO.Pdf, the migration reduces to: add DI registration for ChromePdfRenderer, map HtmlToPdfOptions settings to RenderingOptions properties (with the points-to-mm conversion for margins), replace static HtmlToPdf. calls with instance renderer.Render() calls, add using blocks around PdfDocument instances, and replace GetPdfBytes() / Save() with BinaryData / SaveAs(). For a codebase with 5–20 EO.Pdf call sites, this is typically a one-day engineering task excluding the rendering comparison pass.
