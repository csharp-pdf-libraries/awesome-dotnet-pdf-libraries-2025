Migrating from TuesPechkin to IronPDF: a practical .NET guide

a .NET engineer's reference for migrating PDF libraries

Framing

TuesPechkin was a .NET wrapper library around wkhtmltopdf, the open-source HTML-to-PDF command-line tool built on QtWebKit. Its distinguishing contribution over earlier wkhtmltopdf wrappers was thread safety management: it handled the wkhtmltopdf library's requirement to be initialized and operated on a single dedicated thread, surfacing this complexity behind a simple IConverter interface that could be called from any thread in a multi-threaded ASP.NET application. Teams that adopted TuesPechkin during the mid-2010s did so to avoid the threading and lifetime management problems that plagued raw wkhtmltopdf interop.

TuesPechkin is discontinued. The last release predates .NET Core, and the project is no longer maintained. Teams running TuesPechkin face the overlapping risks common to discontinued native-wrapper libraries: the underlying wkhtmltopdf tool is itself no longer under active development, its QtWebKit rendering engine has not tracked modern CSS standards, and the wrapper that manages its threading lifetime has no maintainer to address runtime compatibility issues on modern .NET or deployment environments. Any application still running TuesPechkin has been accumulating technical debt against both the wrapper and the engine simultaneously.

This guide covers the migration from TuesPechkin to IronPDF. TuesPechkin's API is clean and well-defined — the core interface is IConverter.Convert(IDocument) returning byte[]. The migration involves replacing this interface with IronPDF's ChromePdfRenderer, updating document configuration objects to RenderingOptions, and removing the wkhtmltopdf binary and thread management infrastructure. The migration effort is classified as Low.

What TuesPechkin Is Designed to Do

TuesPechkin is a managed .NET wrapper that offers thread-safe access to the wkhtmltopdf native library (wkhtmltox.dll on Windows). The library's primary interface is IConverter, with the ThreadSafeConverter implementation managing a dedicated thread for wkhtmltopdf operations. Document conversion is requested by constructing an HtmlToPdfDocument object — which contains an ObjectSettings collection — and calling converter.Convert(document), which returns the PDF as a byte[].

ObjectSettings carries the conversion configuration: the HTML content (via HtmlContent for strings, Page for URLs, or PageUrl for file paths), page size and margins in PaperSettings, header and footer configuration in HeaderSettings and FooterSettings, and miscellaneous rendering options. The install footprint includes the TuesPechkin NuGet package plus a companion package (TuesPechkin.Wkhtmltox.Win64 or similar) that bundles the wkhtmltopdf native DLL for the target platform. The primary use case is HTML string and URL to PDF conversion in ASP.NET applications. The exact .NET support range should be verified — as a discontinued project, compatibility with modern .NET may require runtime shims.

Architectural Differences

TuesPechkin and IronPDF both convert HTML to PDF but differ fundamentally in architecture. TuesPechkin is a managed wrapper over a native library (wkhtmltopdf/wkhtmltox.dll) that uses QtWebKit for rendering. The wrapper manages the native library's thread affinity requirements. IronPDF uses embedded Chromium for rendering — full CSS3 support, in-process, no dedicated thread management required.

IronPDF's ChromePdfRenderer is the functional replacement for TuesPechkin's IConverter. It accepts HTML strings, files, and URLs via named methods rather than a polymorphic IDocument parameter. PdfDocument implements IDisposable and is returned from every render operation; pdf.BinaryData replaces TuesPechkin's byte[] return. The HTML string to PDF guide covers all rendering configuration. License initialization is a one-time startup call; see the license setup guide.

The most significant operational change is removing the thread management infrastructure. TuesPechkin's ThreadSafeConverter and WinAnyCPUEmbeddedDeployment (or platform-specific deployment classes) are removed entirely. ChromePdfRenderer is registered as a singleton in DI and called directly from any thread — the threading concern is no longer the application's responsibility.

Operation Comparisons

HTML String to PDF

TuesPechkin — HTML String to PDF

using TuesPechkin;

// TuesPechkin — configure once at startup (typically in DI or static initializer)
// WinAnyCPUEmbeddedDeployment bundles the wkhtmltopdf DLL in the NuGet package
IDeployment deployment = new WinAnyCPUEmbeddedDeployment(
    new StaticDeployment(Path.GetTempPath()));

// ThreadSafeConverter manages wkhtmltopdf's single-thread requirement
// Registered as a singleton — must be kept alive for the application lifetime
IConverter converter = new ThreadSafeConverter(
    new PdfToolset(deployment));

// Per-conversion: construct a document with settings
var document = new HtmlToPdfDocument
{
    GlobalSettings =
    {
        ProduceOutline = false,
        DocumentTitle = "Invoice",
        PaperSize = PaperKind.A4,
        Margins =
        {
            All  = 10,          // mm
            Unit = Unit.Millimeters
        }
    },
    Objects =
    {
        new ObjectSettings
        {
            HtmlText = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #1042</h1>
  <p>Customer: Acme Corp</p>
</body>
</html>",
            // Header/footer configured here if needed
            // HeaderSettings = { ... }
        }
    }
};

// Returns byte[] directly — no disposal required on the result
byte[] pdfBytes = converter.Convert(document);
File.WriteAllBytes("invoice.pdf", pdfBytes);

Concrete constraints:

  • ThreadSafeConverter must be created once and kept alive as a singleton. Disposing and recreating it for each request is incorrect and causes errors.
  • WinAnyCPUEmbeddedDeployment and platform-specific deployment classes manage the extraction and loading of the wkhtmltopdf native DLL. This is Windows-only; Linux deployment requires a separately installed wkhtmltopdf binary and a different deployment class.
  • TuesPechkin uses wkhtmltopdf internally — no CSS Flexbox, Grid, CSS variables, or modern web font loading.
  • PaperKind is the System.Drawing.Printing.PaperKind enum, or a TuesPechkin-specific enum
  • Header/footer configuration in ObjectSettings.HeaderSettings and FooterSettings uses wkhtmltopdf-style properties.
  • IConverter.Convert() is synchronous and blocks the calling thread until wkhtmltopdf completes.

IronPDF — HTML String to PDF

using IronPdf;

// ChromePdfRenderer — registered as singleton in DI, thread-safe
// No deployment class, no dedicated thread management needed
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.PaperOrientation = IronPdf.Rendering.PdfPaperOrientation.Portrait;
renderer.RenderingOptions.MarginTop = 10;     // mm — same unit as TuesPechkin
renderer.RenderingOptions.MarginBottom = 10;
renderer.RenderingOptions.MarginLeft = 10;
renderer.RenderingOptions.MarginRight = 10;

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #1042</h1>
  <p>Customer: Acme Corp</p>
</body>
</html>";

// PdfDocument is IDisposable — always wrap in using
using var pdf = renderer.RenderHtmlAsPdf(html);

// Equivalent of converter.Convert(doc) → byte[]
byte[] pdfBytes = pdf.BinaryData;
File.WriteAllBytes("invoice.pdf", pdfBytes);
// Or: pdf.SaveAs("invoice.pdf");

converter.Convert(document) maps to renderer.RenderHtmlAsPdf(html). The HtmlToPdfDocument / ObjectSettings configuration hierarchy collapses to RenderingOptions properties. The ThreadSafeConverter / WinAnyCPUEmbeddedDeployment infrastructure is removed entirely — ChromePdfRenderer is a straightforward singleton. Full rendering configuration is in the HTML string to PDF guide.

URL to PDF

TuesPechkin — URL to PDF

using TuesPechkin;

// TuesPechkin URL conversion — uses ObjectSettings.Page instead of HtmlText
var document = new HtmlToPdfDocument
{
    GlobalSettings = { PaperSize = PaperKind.A4 },
    Objects =
    {
        new ObjectSettings
        {
            // URL conversion: set Page instead of HtmlText
            Page = "https://reports.example.com/q3"
            // wkhtmltopdf fetches the URL using its own HTTP client
            // SSL and authentication handling is limited
        }
    }
};

byte[] pdfBytes = converter.Convert(document);

Concrete constraints:

  • wkhtmltopdf fetches the URL using its own HTTP client — session cookies are not forwarded from the ASP.NET request by default.
  • SSL certificate errors on internal HTTPS URLs are common.

IronPDF — URL to PDF

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Forward session cookies for authenticated URLs
renderer.RenderingOptions.CustomCookies =
    new System.Collections.Generic.Dictionary<string, string>
    {
        { "session_id", "your-session-token" }
    };

using var pdf = renderer.RenderUrlAsPdf("https://reports.example.com/q3");
byte[] pdfBytes = pdf.BinaryData;

TuesPechkin's ObjectSettings.Page = url maps to renderer.RenderUrlAsPdf(url). Cookie injection is explicit and reliable. The URL to PDF guide covers authentication and JavaScript wait conditions.

Headers and Footers with Page Numbers

TuesPechkin — Headers and Footers

using TuesPechkin;

// TuesPechkin headers and footers via ObjectSettings
var document = new HtmlToPdfDocument
{
    GlobalSettings =
    {
        PaperSize = PaperKind.A4,
        Margins   = { All = 15, Unit = Unit.Millimeters }
    },
    Objects =
    {
        new ObjectSettings
        {
            HtmlText = "<html><body><p>Document content</p></body></html>",
            HeaderSettings = new HeaderSettings
            {
                // wkhtmltopdf HTML header — an HTML string
                // wkhtmltopdf page number tokens: [page] and [toPage]
                HtmlUrl = "file:///app/templates/header.html",
                // OR: Center = "Page [page] of [toPage]" (text-based footer)
                Spacing = 5  // mm between header and content
            },
            FooterSettings = new FooterSettings
            {
                Center = "Page [page] of [toPage]",  // text-based footer
                // Or: HtmlUrl for HTML footer file
                Spacing = 5
            }
        }
    }
};

byte[] pdfBytes = converter.Convert(document);

Concrete constraints:

  • TuesPechkin uses wkhtmltopdf's [page] and [toPage] tokens (or [sitepage] / [sitepages]) — all must be replaced with IronPDF's {page} / {total-pages}.
  • wkhtmltopdf supports both text-based (Center, Left, Right) and HTML file-based headers/footers. Text tokens differ from HTML-based tokens.
  • HTML header/footer files must be file paths accessible to wkhtmltopdf process — HtmlUrl takes a file:// URI.

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 15;

// IronPDF tokens: {page} and {total-pages}
// Replace all [page] / [toPage] occurrences from TuesPechkin/wkhtmltopdf
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 12,
    HtmlFragment = "<div style='font-size:9px; font-family:Arial; " +
                   "text-align:right; padding:0 12px;'>Report Header</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 10,
    HtmlFragment = "<div style='font-size:8px; font-family:Arial; " +
                   "text-align:center;'>Page {page} of {total-pages}</div>"
};

using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><p>Document content.</p></body></html>");
pdf.SaveAs("document-with-headers.pdf");

TuesPechkin's HeaderSettings and FooterSettings map to HtmlHeaderFooter.HtmlFragment. External HTML header files (HtmlUrl) become inline HTML fragments — no file management required. The [page] / [toPage] tokens become {page} / {total-pages}. The headers and footers guide covers all configuration options.

ASP.NET Core DI Pattern

TuesPechkin — ASP.NET Core Singleton Setup

// TuesPechkin — startup configuration in ASP.NET Core
// ThreadSafeConverter must be a singleton, carefully lifecycle-managed

using TuesPechkin;

// In Program.cs / Startup.cs:
var deployment = new WinAnyCPUEmbeddedDeployment(
    new StaticDeployment(Path.GetTempPath()));

var converter = new ThreadSafeConverter(new PdfToolset(deployment));

// Register as singleton — not a standard IServiceCollection pattern
// Often stored as a static field or in a wrapper service
builder.Services.AddSingleton<IConverter>(converter);

// In controller:
// [FromServices] IConverter _converter
// byte[] pdf = _converter.Convert(document);
// IronPDF — ASP.NET Core DI replacement
// Program.cs:
IronPdf.License.LicenseKey = "YOUR-KEY"; // startup license init

builder.Services.AddSingleton<ChromePdfRenderer>(sp =>
{
    var r = new ChromePdfRenderer();
    r.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
    r.RenderingOptions.MarginTop = 10;
    r.RenderingOptions.MarginBottom = 10;
    return r;
});

// In controller:
// ChromePdfRenderer _renderer (injected)
// using var pdf = _renderer.RenderHtmlAsPdf(html);
// return File(pdf.BinaryData, "application/pdf", "output.pdf");

The ThreadSafeConverter singleton and its WinAnyCPUEmbeddedDeployment setup are replaced by a standard builder.Services.AddSingleton<ChromePdfRenderer>() call. The async-capable RenderHtmlAsPdfAsync() replaces the synchronous Convert() call. No deployment class, no dedicated thread, no DLL extraction management. The async rendering guide covers concurrent rendering patterns for high-throughput endpoints.

Breaking Changes & Gotchas

  • Discontinued status — act on both layers: TuesPechkin and wkhtmltopdf are both unmaintained. CSS limitations have been accumulating and will not improve.
  • ThreadSafeConverter lifecycle removed: The entire singleton management, deployment class instantiation, and thread management infrastructure is removed. ChromePdfRenderer is a standard DI singleton.
  • WinAnyCPUEmbeddedDeployment removed: The wkhtmltopdf DLL extraction and deployment step is eliminated. Remove from startup code, Docker images, and CI/CD artifact packaging.
  • [page] / [toPage] tokens: Every occurrence in header/footer HTML must be updated to {page} / {total-pages}. Old tokens produce literal text without error.
  • HtmlToPdfDocument / ObjectSettings → RenderingOptions: The two-level document/object configuration hierarchy collapses to a flat RenderingOptions object.
  • IConverter.Convert() is synchronous: TuesPechkin's conversion blocks. IronPDF's RenderHtmlAsPdfAsync() is genuinely async — replace Task.Run() wrappers where present.
  • PdfDocument is IDisposable: TuesPechkin's Convert() returns byte[] with no disposal. IronPDF returns PdfDocument — wrap in using.
  • CSS Flexbox / Grid now supported: Templates constrained to float-based layouts for wkhtmltopdf compatibility can be updated to modern CSS.
  • Web fonts now load reliably: Base64-embedded font workarounds added for wkhtmltopdf can be removed.
  • Namespace change: Remove using TuesPechkin;. Replace with using IronPdf;.
  • License key required: TuesPechkin is open-source. IronPDF requires IronPdf.License.LicenseKey at startup.
  • Linux deployment: TuesPechkin's deployment model for Linux uses a separately installed wkhtmltopdf binary. IronPDF on Linux requires Chromium system library packages — a different but comparable native dependency profile.

Migration Checklist

  1. Audit all IConverter.Convert() call sites: List every HtmlToPdfDocument construction — GlobalSettings values, ObjectSettings.HtmlText / Page / PageUrl, HeaderSettings, FooterSettings, and any [page] / [toPage] token usage.
  2. Identify ThreadSafeConverter / deployment class locations: Find every WinAnyCPUEmbeddedDeployment, ThreadSafeConverter, PdfToolset instantiation in startup code, static fields, and DI registrations.
  3. Install IronPDF via NuGet: dotnet add package IronPdf.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; at application startup, before any render calls. See the license setup guide.
  5. Remove deployment class and converter infrastructure: Delete WinAnyCPUEmbeddedDeployment, PdfToolset, and ThreadSafeConverter instantiation code.
  6. Register ChromePdfRenderer in DI: Replace the IConverter singleton registration with builder.Services.AddSingleton<ChromePdfRenderer>().
  7. Update namespaces: Remove using TuesPechkin;. Add using IronPdf;.
  8. Replace Convert(document) calls: Map ObjectSettings.HtmlText → renderer.RenderHtmlAsPdf(html), ObjectSettings.Page → renderer.RenderUrlAsPdf(url). Wrap PdfDocument in using. Access bytes via pdf.BinaryData.
  9. Replace GlobalSettings configuration: Map PaperSize, Margins, and orientation to RenderingOptions.* properties.
  10. Replace headers and footers: Convert HeaderSettings / FooterSettings to HtmlHeaderFooter.HtmlFragment. Update [page] / [toPage] tokens to {page} / {total-pages}.
  11. Remove wkhtmltopdf binary packages: Remove TuesPechkin.Wkhtmltox.* NuGet packages. Remove the wkhtmltopdf DLL from deployment artifacts. Add Chromium system library packages on Linux.
  12. Remove TuesPechkin NuGet packages: Once all replacements compile and rendering tests pass, remove all TuesPechkin packages.

Conclusion

When staying on TuesPechkin is technically reasonable

TuesPechkin is discontinued, making continued use indefensible for any application with active development, dependency updates, or a planned .NET runtime upgrade. The only scenario where staying is technically defensible is a completely frozen application with no planned changes — no new features, no dependency upgrades, no .NET version migration — where the rendering output is adequate for the current requirements and the cost of migration is genuinely not yet justified. In practice, this window shortens with every .NET release and every deployment environment change.

Signals that indicate migration is worth the engineering effort

The discontinued status of both TuesPechkin and wkhtmltopdf is sufficient justification for any active application. Additional concrete triggers: CSS rendering limitations are blocking modern template designs; JavaScript-heavy content is rendering unreliably; web font loading is failing in production; the ThreadSafeConverter singleton is causing threading issues under load; the wkhtmltopdf binary is complicating deployment or container builds; or the team is planning a .NET runtime upgrade and wants to reduce in-flight risk.

What the cutover typically involves at the code level

The API translation is mechanical: delete the deployment class and converter infrastructure, register ChromePdfRenderer as a singleton, replace converter.Convert(doc) calls with renderer.RenderHtmlAsPdf(html), add using blocks, update header/footer token syntax, and remove the wkhtmltopdf binary. The rendering comparison pass — confirming that IronPDF's Chromium output matches what wkhtmltopdf produced across all templates — is the quality gate. For templates that were constrained by wkhtmltopdf's CSS limitations, the comparison pass often surfaces layout improvements rather than problems.

In your current TuesPechkin integration, has the ThreadSafeConverter singleton lifecycle ever caused issues under concurrent load — and does removing that threading complexity, along with the deployment class infrastructure, represent a meaningful simplification of your application's startup and request path?
