Migrating from Nutrient.io to IronPDF: a practical .NET guide

a .NET engineer's reference for migrating PDF libraries

Framing

Nutrient.io is the current brand for what was formerly PSPDFKit — one of the most comprehensive commercial PDF SDKs available across mobile, web, and server platforms. Teams that adopted PSPDFKit or Nutrient typically had requirements that extended well beyond PDF generation: interactive viewer components, annotation management, real-time collaboration, certified digital signatures, and cross-platform consistency across iOS, Android, web, and server environments. The platform's breadth is its primary value proposition, and that breadth carries a corresponding price point and integration surface.

Re-evaluation of an enterprise PDF platform happens for several reasons. Organizations that originally adopted Nutrient for its cross-platform viewer and annotation capabilities sometimes find that the server-side generation requirements have evolved to favor an HTML/CSS rendering approach over Nutrient's document model. When the viewer and annotation features are not the primary dependency — when the integration is primarily server-side HTML-to-PDF generation, document manipulation, and compliance output — the operational and licensing overhead of an enterprise cross-platform SDK may exceed the requirements. Teams evaluate whether a focused server-side library covers the actual production usage.

This guide covers the migration from Nutrient.io (PSPDFKit for .NET) to IronPDF for .NET engineers evaluating or executing the switch. The migration is classified as High effort because Nutrient's feature surface is broad — viewer components, annotation tools, real-time collaboration, and certified signature workflows extend significantly beyond IronPDF's server-side PDF scope. Teams using Nutrient primarily for server-side generation and basic manipulation will find effort closer to Medium. Teams using viewer components or annotation UIs will encounter gaps that require separate resolution.

What Nutrient.io Is Designed to Do

A commercial enterprise PDF SDK published by PSPDFKit GmbH, nutrient.io (formerly pspdfkit) is. It provides native SDKs for iOS, Android, macOS, Windows, and web (JavaScript), as well as a .NET server-side component. The .NET support range and current SDK versions should be verified in official documentation; Nutrient is actively maintained. The install footprint includes managed NuGet packages and, on some platforms, native binary components

Nutrient's .NET server-side SDK covers PDF generation from documents, HTML content (via an embedded rendering engine), comprehensive document manipulation (merge, split, page operations), AcroForm creation and filling, digital signatures (including certified signatures and long-term validation), PDF/A and PDF/UA compliance, annotation creation and manipulation, text extraction, redaction, and watermarking. The platform's server-side component is designed to complement its client-side viewer — workflows where a user annotates a document in a Nutrient viewer are processed server-side using the same SDK. The primary use case is enterprise document processing pipelines where document fidelity across interactive client and headless server contexts is a requirement.

Architectural Differences

Nutrient.io's .NET server component and IronPDF are both server-side PDF libraries for .NET, and their manipulation feature sets overlap substantially. The architectural differences are at the platform level (Nutrient is a cross-platform SDK with client-side viewer components; IronPDF is a focused .NET server library) and at the generation level.

IronPDF's two central types are ChromePdfRenderer (for rendering HTML to PDF) and PdfDocument (for all manipulation). Both implement IDisposable and require using blocks. Configuration for generation lives on RenderingOptions; manipulation operations are methods on PdfDocument. The HTML string to PDF guide covers IronPDF's full rendering configuration. The rendering options reference covers all rendering parameters. License initialization is a one-time startup call; see the license setup guide.

The critical scope difference: Nutrient's interactive viewer component (the JavaScript/native viewer that displays PDFs in a browser or mobile app with annotation tools) has no equivalent in IronPDF. If viewer functionality is part of the current integration, it requires a separate evaluation and replacement strategy independent of the server-side PDF migration.

Operation Comparisons

Loading, Merging, and Saving PDFs

Nutrient.io — PDF Manipulation

// Nutrient.io (.NET SDK) — PDF manipulation
// Verify exact class names, method signatures, and namespace in official documentation
// as the API may differ between SDK versions and the PSPDFKit → Nutrient transition

// Conceptual pattern:
// using PSPDFKit;           // or NutrientSDK
// using PSPDFKit.Document;  // verify namespace

// Initialize SDK — Nutrient requires a license key initialization
// NutrientSDK.Initialize("YOUR-LICENSE-KEY"); // verify method name

// Load a PDF document
// using var doc1 = Document.FromFile("document1.pdf"); // verify class and method
// using var doc2 = Document.FromFile("document2.pdf");

// Merge documents
// Nutrient may use an 'Operations' pattern or a dedicated merge method
// var mergedDoc = Document.Merge(doc1, doc2); // verify

// Save merged result
// mergedDoc.Save("merged.pdf"); // verify method name

// Page operations
// int pageCount = doc1.PageCount; // verify property name
// doc1.RemovePage(0);             // verify method and index convention (0 or 1 based)

Concrete constraints:

  • Nutrient's exact class names, namespace structure, and method signatures should be verified in official documentation — PSPDFKit / Nutrient has undergone branding changes and SDK versions differ.
  • Verify whether Nutrient's document types implement IDisposable and what the correct disposal pattern is.
  • Verify page index convention (0-based or 1-based) in official documentation — IronPDF uses 0-based throughout.
  • License initialization mechanism and required startup call should be verified in official documentation.

IronPDF — PDF Manipulation

using IronPdf;

// IronPdf.License.LicenseKey = "YOUR-KEY"; // set once at startup in Program.cs

using var pdf1 = PdfDocument.FromFile("document1.pdf");
using var pdf2 = PdfDocument.FromFile("document2.pdf");
using var pdf3 = PdfDocument.FromFile("document3.pdf");

// N-way merge in a single static call
using var merged = PdfDocument.Merge(pdf1, pdf2, pdf3);

// Page operations (0-based index)
int pageCount = merged.PageCount;
merged.RemovePage(0);             // remove first page (0-based)
merged.RotatePage(0, IronPdf.Rotation.Clockwise90); // rotate new first page

merged.SaveAs("merged.pdf");

IronPDF's PdfDocument.Merge() consolidates N documents in a single call with no page-iteration loop. Page operations are all 0-based. The merge and split guide covers N-way merges, page range extraction, and split patterns.

Concrete constraints:

IronPDF — Form Filling

using IronPdf;

using var pdf = PdfDocument.FromFile("form-template.pdf");

// Uniform string-based field access — all field types use .Value
var nameField = pdf.Form["applicant_name"];
if (nameField != null) nameField.Value = "Jane Smith";

var approvedField = pdf.Form["status_approved"];
if (approvedField != null) approvedField.Value = "On";  // checkbox

var categoryField = pdf.Form["category"];
if (categoryField != null) categoryField.Value = "Enterprise";

// Flatten form fields — removes interactivity before final save
pdf.Form.Flatten();
pdf.SaveAs("filled-form.pdf");

IronPDF's form API uses uniform string values for all field types. The edit forms guide covers field types, value conventions, and flattening.

Concrete constraints:

  • Nutrient's signing API includes certified signatures, LTV enablement, and TSA timestamp configuration — features that go beyond basic approval signing. Verify whether IronPDF covers the specific signing requirements before committing to migration.
  • Verify the exact signature type enumeration (approval, certified, CAdES, PAdES) in Nutrient's documentation and map each to IronPDF equivalents.
  • The async signing pattern in Nutrient (if applicable) should be verified and mapped to IronPDF's synchronous signing model.

IronPDF — Digital Signatures

using IronPdf;
using IronPdf.Signing;

using var pdf = PdfDocument.FromFile("document.pdf");

// Configure signature from PKCS#12 certificate
var signature = new PdfSignature("cert.pfx", "pfx-password")
{
    SigningReason = "Approved for distribution",
    SigningContact = "approver@example.com",
    SigningLocation = "Chicago, IL"
};

// Apply signature
pdf.Sign(signature);
pdf.SaveAs("signed-document.pdf");

IronPDF's approval signature workflow is a direct replacement. For advanced signing features — certified signatures, LTV, TSA timestamps

Breaking Changes & Gotchas

  • Interactive viewer component not in IronPDF: Nutrient's browser and mobile PDF viewer (with annotation toolbar, markup tools, comment threads) has no equivalent in IronPDF. Applications using the viewer component must evaluate a separate viewer solution independent of the server-side PDF migration. This is frequently the blocking item that prevents full platform migration.
  • Real-time collaboration not in IronPDF: Nutrient's document collaboration features (real-time annotation sync, comment resolution) are not available in IronPDF.
  • Advanced signing features require verification: Nutrient's certified signatures, LTV enablement, and TSA timestamp workflows should be individually verified against IronPDF's signing API before classifying as migratable. These are the most common source of migration scope underestimation.
  • Namespace change: Remove all Nutrient / PSPDFKit using directives. Replace with using IronPdf;. Compile errors identify every affected file.
  • **Page index convention
  • SDK initialization model: Nutrient requires SDK initialization with a license key — the mechanism differs from IronPDF's IronPdf.License.LicenseKey property. Update the startup initialization call.
  • Disposal semantics: Verify Nutrient's document disposal pattern and replace with IronPDF's standard using var pdf = PdfDocument.FromFile(...) pattern.
  • Annotation type coverage: Verify that the annotation types used in the current integration (text annotations, ink annotations, stamps, highlights, polygons, etc.) are available in IronPDF's annotation API before planning the migration scope.
  • Cross-platform mobile SDK out of scope: Nutrient's iOS, Android, and macOS native SDKs are outside IronPDF's scope. If the .NET migration is part of a broader cross-platform initiative, the mobile and web SDKs require separate replacement strategies.
  • PdfDocument is IDisposable: Ensure all PdfDocument instances are in using blocks throughout the migration.

Migration Checklist

  1. Triage by capability area: Separate current Nutrient usage into: (a) server-side generation and basic manipulation — migratable; (b) forms, signatures, PDF/A — migratable with verification; (c) certified/LTV signing, specific annotation types
  2. Resolve viewer and collaboration gaps: If Nutrient's interactive viewer is in active use, identify a replacement solution before beginning the server-side migration. This is typically the decision that determines whether full platform migration is viable.
  3. Verify advanced signing coverage: Test certified signatures, LTV, and TSA requirements against IronPDF's signing API before committing. These are the most common unexpected blockers in enterprise PDF migrations.
  4. Install IronPDF via NuGet: dotnet add package IronPdf. Retain Nutrient references until replacement code compiles and passes tests.
  5. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs. See the license setup guide.
  6. Update namespaces: Remove all Nutrient / PSPDFKit using directives. Replace with using IronPdf;.
  7. Replace document load/save: Map Nutrient's document load and save to PdfDocument.FromFile() and pdf.SaveAs(). Wrap in using blocks.
  8. Replace merge and page operations: Map Nutrient's merge to PdfDocument.Merge(). Replace page add/remove/rotate operations. Verify page index convention and adjust from 1-based to 0-based if needed.
  9. Port form filling: Replace Nutrient's form field access with pdf.Form["name"].Value = "value". Replace flatten with pdf.Form.Flatten().
  10. Port digital signatures: Replace Nutrient's signing with PdfSignature + pdf.Sign(). Escalate certified/LTV/TSA workflows to the verification step.
  11. Port PDF/A and PDF/UA: Replace Nutrient's compliance conversion with pdf.SaveAsPdfA() and pdf.SaveAsPdfUa().
  12. Remove Nutrient NuGet packages: Once all verified replacements compile and tests pass, remove Nutrient / PSPDFKit NuGet packages and perform a final build.

Conclusion

When staying on Nutrient.io is technically reasonable

Nutrient.io is technically reasonable when the interactive viewer component, annotation UI, or real-time collaboration features are central to the application's user experience and would require significant separate investment to replace. Cross-platform requirements (iOS, Android, macOS, web, and .NET all from a single vendor) remain a strong argument for Nutrient's ecosystem. For enterprise applications where PSPDFKit / Nutrient has been deeply integrated into document workflow — certified signatures with LTV, compliance validation, annotation round-tripping between viewer and server — the platform's unified scope reduces integration risk.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when server-side generation and basic manipulation represent the majority of Nutrient's actual usage — when the viewer, collaboration, and advanced signing features are licensed but unused; when the HTML/CSS generation model is preferred over Nutrient's document generation approach; when async rendering, Chromium-quality CSS, or simplified deployment are new requirements; or when a significant portion of the licensing cost is driven by platform capabilities that are not in active use.

What the cutover typically involves at the code level

For server-side-only integrations — load, save, merge, forms, basic signing, PDF/A — the migration is a mechanical namespace and API rename exercise with the page index convention check as the systematic gotcha. Advanced signing and annotation workflows require feature-by-feature verification. The viewer component, if in use, is an architectural decision that drives the migration timeline more than any API surface consideration. A phased approach — server-side generation first, manipulation second, advanced features verified and migrated third — allows production validation at each phase without a full cutover commitment.
