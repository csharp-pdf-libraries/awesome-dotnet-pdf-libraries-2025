Migrating from RawPrint to IronPDF: a .NET engineering guide

API mapping, gotchas, and a migration checklist

Framing

Largely invisible to web application developers but critical to a specific class of line-of-business applications: point-of-sale terminals, shipping label printers, receipt systems, warehouse inventory tools, and any workflow where documents must reach a physical printer without the intermediary of a print dialog, libraries oriented around raw printer communication occupy a niche that is. In the .NET ecosystem, these libraries typically wrap the Windows spooler API or send raw printer control language (PCL, ESC/P, ZPL) directly to a print queue.

When these libraries reach end-of-life, the migration question is more complex than a simple API swap. Teams must evaluate whether their underlying requirement was "print a document" or "generate a document," because the answer determines the category of replacement. Libraries designed for programmatic PDF generation are not direct substitutes for raw print spooler wrappers — they solve adjacent problems with meaningful overlap but also genuine gaps.

RawPrint is a library in this category that appears to have been discontinued. When a library is discontinued and targets a legacy framework version, the migration calculus shifts: the question is no longer whether to migrate but how quickly, and toward what. This guide maps what is known about RawPrint's purpose, where IronPDF's capabilities intersect and diverge, and what a migration looks like for teams whose primary need is document generation for distribution.

What RawPrint Is Designed to Do

RawPrint is a .NET library built to send raw data directly to a Windows printer, bypassing the standard GDI print pipeline. Its primary use case is sending pre-formatted printer command streams — typically in PCL, ESC/P, PostScript, or ZPL — directly to a print spooler queue without the operating system applying any transformation. This is important in contexts where the printer has its own rendering engine and the application must deliver exact byte sequences: label printers, receipt printers, and some industrial document printers operate this way.

The library targets .NET Framework 4.0. It is distributed as a NuGet package. Its integration model is low-level: the developer provides a stream or byte array containing the raw printer language data, specifies a printer name, and the library delivers that data to the Windows print spooler using the appropriate Win32 API calls (OpenPrinter, StartDocPrinter, WritePrinter). RawPrint does not generate documents, render HTML, or produce PDF. It is a transport mechanism for data that has already been rendered elsewhere. Verify current package status and documentation — the library appears to have been discontinued and official documentation may be unavailable.

Architectural Differences

IronPDF and RawPrint address different layers of the document pipeline, which makes this migration more architectural than technical. RawPrint operates at the delivery layer: it takes already-rendered printer data and submits it to a print queue. IronPDF operates at the generation layer: it takes HTML source and produces a PDF document object that can be saved, streamed, signed, encrypted, or submitted for printing through the operating system's PDF printing subsystem.

For teams whose workflow is: generate a print-ready byte stream → deliver to printer, migrating to IronPDF changes both steps. The generation step moves to HTML-to-PDF rendering via Chromium. The delivery step — submitting to a physical printer — is handled through the operating system's print infrastructure, which can accept PDF files from .NET using System.Printing or PrintDocument. IronPDF itself does not include a print spooler API; it produces PDF documents.

Where the architectures do intersect is in PDF as an intermediate format. Many printer workflows that previously sent raw PCL streams are now redesigned to generate PDF (a more portable and archivable format) and then print that PDF via the OS spooler. IronPDF's HTML to PDF pipeline with rendering options for paper size, margins, and DPI is well-suited to this pattern. The resulting PDF can be saved, archived, emailed, or submitted for printing — which is a capability expansion relative to raw print-only workflows.

Sending Raw Data to a Printer

RawPrint — Raw Print Submission

RawPrint's core function is submitting a raw data stream to a Windows print queue. The following conceptual outline reflects the typical pattern; verify against any surviving documentation or source code.

// Conceptual pattern
// RawPrint is discontinued; official documentation may be unavailable.

// Step 1: Prepare the raw printer data (PCL, ZPL, ESC/P, PostScript, etc.)
//         This data has been formatted elsewhere — RawPrint is only the transport.
byte[] rawPrinterData = BuildRawPrinterData(); // Returns pre-formatted bytes

// Step 2: Identify the target printer by name
string printerName = "\\\\PrintServer\\LabelPrinter01";

// Step 3: Submit via RawPrint (API names
// RawPrint.RawPrinterHelper.SendBytesToPrinter(printerName, rawPrinterData);

Key constraints:

  • Windows-only; depends on Win32 print spooler APIs.
  • No document generation — data must already be in a printer-ready format.
  • The application is responsible for generating correct PCL/ZPL/ESC/P command sequences.
  • No concept of PDF, HTML, or cross-platform operation.
  • .NET Framework 4.0 target; incompatible with modern .NET SDK-style projects without compatibility shims.

IronPDF — Generating a Document for Printing

IronPDF generates a PDF from HTML. Printing that PDF to a physical printer is handled by the operating system using standard .NET printing APIs. The HTML to PDF guide covers the rendering side; OS printing is handled separately.

using IronPdf;
using System;
using System.Diagnostics; // For OS-level print via Process

License.LicenseKey = Environment.GetEnvironmentVariable("IRONPDF_LICENSE_KEY");

var renderer = new ChromePdfRenderer();

// Configure for a typical label or receipt layout
// Adjust paper size to match physical label dimensions
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.Custom;
renderer.RenderingOptions.CustomPaperWidth = 101.6; // mm — 4-inch label
renderer.RenderingOptions.CustomPaperHeight = 152.4; // mm — 6-inch label
renderer.RenderingOptions.MarginTop = 3;
renderer.RenderingOptions.MarginBottom = 3;
renderer.RenderingOptions.MarginLeft = 3;
renderer.RenderingOptions.MarginRight = 3;

// Build HTML for the label/receipt content
var html = @"
<html>
<head>
<style>
  body { font-family: Arial, sans-serif; font-size: 11px; margin: 0; padding: 0; }
  .barcode { font-family: 'Free 3 of 9', monospace; font-size: 32px; }
  .label-header { font-weight: bold; font-size: 13px; }
</style>
</head>
<body>
  <div class='label-header'>ACME LOGISTICS</div>
  <div>Order: #1042318</div>
  <div>Ship To: 123 Main St, Springfield, IL 62701</div>
  <div class='barcode'>*1042318*</div>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(html);

// Option A: Save and open with OS default PDF viewer / printer
var tempPath = System.IO.Path.GetTempFileName() + ".pdf";
pdf.SaveAs(tempPath);
// Process.Start(new ProcessStartInfo(tempPath) { UseShellExecute = true });

// Option B: Use pdf.BinaryData for downstream handling (email, archive, print API)
byte[] pdfBytes = pdf.BinaryData;

Generating a Receipt-Style Narrow Document

RawPrint — Receipt Generation

Receipt generation in a RawPrint context typically involves constructing ESC/P or similar thermal printer command sequences manually, then submitting them via the print spooler.

// Conceptual outline — RawPrint sends pre-built ESC/P data
// ESC/P command sequences must be built by the application

var receiptData = new System.Text.StringBuilder();
// Initialize printer (ESC @ = initialize)
receiptData.Append("\x1B\x40");
// Center align (ESC a 1)
receiptData.Append("\x1B\x61\x01");
// Bold on (ESC E 1)
receiptData.Append("\x1B\x45\x01");
receiptData.AppendLine("RECEIPT");
// Bold off
receiptData.Append("\x1B\x45\x00");
receiptData.AppendLine("Item 1........$10.00");
receiptData.AppendLine("Item 2........$15.00");
receiptData.AppendLine("-------------------");
receiptData.AppendLine("Total.........$25.00");
// Cut paper (ESC i)
receiptData.Append("\x1D\x56\x41");

byte[] rawBytes = System.Text.Encoding.ASCII.GetBytes(receiptData.ToString());
// RawPrint.RawPrinterHelper.SendBytesToPrinter("ThermalPrinter", rawBytes);

Key constraints:

  • ESC/P command construction is tedious and printer-model-specific.
  • No visual preview — output can only be verified on the physical printer.
  • Character encoding must match printer expectations exactly.

IronPDF — Receipt-Style Document

IronPDF generates a receipt-style PDF that can be printed, archived, emailed, or displayed in a preview UI. Custom paper sizes are supported. See the custom paper size guide for narrow receipt dimensions.

using IronPdf;
using System;

License.LicenseKey = Environment.GetEnvironmentVariable("IRONPDF_LICENSE_KEY");

var renderer = new ChromePdfRenderer();

// 80mm thermal receipt width
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.Custom;
renderer.RenderingOptions.CustomPaperWidth = 80;  // mm
renderer.RenderingOptions.CustomPaperHeight = 200; // mm — adjust dynamically
renderer.RenderingOptions.MarginTop = 5;
renderer.RenderingOptions.MarginBottom = 5;
renderer.RenderingOptions.MarginLeft = 3;
renderer.RenderingOptions.MarginRight = 3;

var html = @"
<html>
<head>
<style>
  body { font-family: monospace; font-size: 10px; width: 100%; text-align: center; }
  .total { font-weight: bold; border-top: 1px solid #000; margin-top: 4px; padding-top: 4px; }
  table { width: 100%; }
  td.amount { text-align: right; }
</style>
</head>
<body>
  <div><strong>RECEIPT</strong></div>
  <table>
    <tr><td>Item 1</td><td class='amount'>$10.00</td></tr>
    <tr><td>Item 2</td><td class='amount'>$15.00</td></tr>
  </table>
  <div class='total'>Total: $25.00</div>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("receipt.pdf");

Memory Stream Output

RawPrint — Memory Stream Output

RawPrint is designed to submit data to a physical printer, not to produce in-memory document objects. Memory stream output is not a primary use case. If raw print data needs to be stored, it is typically buffered as a byte array before submission.

// No direct memory stream API in RawPrint
// Raw bytes are prepared and submitted; no PdfDocument-equivalent object
byte[] rawData = BuildRawPrinterData();
// Store or submit rawData directly — no document object model

IronPDF — Memory Stream Output

IronPDF can output to a MemoryStream directly, suitable for HTTP responses, message bus payloads, or in-memory processing. The PDF memory stream guide covers both saving to and loading from streams.

using IronPdf;
using System;
using System.IO;

License.LicenseKey = Environment.GetEnvironmentVariable("IRONPDF_LICENSE_KEY");

var renderer = new ChromePdfRenderer();

using var pdf = renderer.RenderHtmlAsPdf("<p>Document content.</p>");

// Option A: Get MemoryStream directly
MemoryStream pdfStream = pdf.Stream;

// Option B: Get byte array
byte[] pdfBytes = pdf.BinaryData;

// Example: return as HTTP response in ASP.NET Core

Breaking Changes & Gotchas

  • Fundamentally different scope: RawPrint sends pre-rendered data to a printer. IronPDF generates PDF documents. If the core requirement is raw spooler access for PCL/ZPL/ESC/P printing, IronPDF does not replace that capability. Teams must evaluate whether their requirement can be re-expressed as PDF generation.
  • No Windows spooler integration: IronPDF has no equivalent to OpenPrinter / WritePrinter Win32 API wrappers. Submitting the generated PDF to a physical printer requires a separate mechanism — typically System.Printing.PrintQueue, PrintDocument, or a shell invocation.
  • Thermal and label printers: Some thermal printers accept PDF via their host software or OS driver. Others expect specific command languages (ZPL, ESC/P). If the target printer does not support PDF input, IronPDF cannot bridge that gap. Verify printer firmware and driver capabilities before committing to a PDF-based architecture.
  • Document authoring requirement: RawPrint assumes document rendering happens elsewhere. Migrating to IronPDF means taking on HTML/CSS authoring for document templates. This is a scope addition, not just a dependency swap.
  • Cross-platform printer access: On Linux and macOS, the Windows spooler APIs that RawPrint wraps do not exist. IronPDF's cross-platform PDF generation, combined with CUPS or platform-equivalent printing infrastructure, enables cross-platform print workflows that were not possible with RawPrint.
  • Framework upgrade: RawPrint targets .NET Framework 4.0. IronPDF supports .NET Framework 4.6.2+ and modern .NET SDK targets. If the host application is also on .NET Framework 4.0, a framework upgrade may be a prerequisite.
  • No namespace migration path: There is no type-for-type namespace mapping. This is an architectural change, not a refactor. Plan accordingly.
  • Testing: RawPrint workflows are difficult to test without physical hardware. IronPDF output can be tested programmatically — rendered PDFs can be inspected, diff'd, or verified via text extraction. Migration may improve testability of the document pipeline overall.

Migration Checklist

  1. Assess the printer requirement: Determine whether the target printer can accept PDF input via its OS driver or host software. If not, IronPDF-based migration may require an intermediate PDF-to-printer-language conversion step.
  2. Remove RawPrint NuGet dependency: Remove the RawPrint package reference from your .csproj. Run dotnet restore.
  3. Add IronPDF: Install IronPdf via NuGet. Verify platform-specific package requirements in the current IronPDF documentation.
  4. Configure the license key: Add IronPdf.License.LicenseKey = Environment.GetEnvironmentVariable("IRONPDF_LICENSE_KEY"); to your application startup.
  5. Upgrade .NET target if required: RawPrint targets .NET Framework 4.0. If your project has not already been upgraded, you will need to target at least .NET Framework 4.6.2 or a modern .NET SDK version to use IronPDF. Factor framework upgrade work into the migration estimate.
  6. Design HTML document templates: Build HTML/CSS equivalents for each print document format (receipts, labels, reports). Configure RenderingOptions.CustomPaperWidth and CustomPaperHeight to match physical label or receipt dimensions.
  7. Implement PDF generation: Replace raw byte construction with ChromePdfRenderer.RenderHtmlAsPdf(html). Use pdf.BinaryData or pdf.Stream for any downstream byte handling that previously received raw printer data.
  8. Implement print submission: Add OS-level print submission logic if physical printing is required. On Windows, System.Printing.PrintQueue or Process.Start with a PDF print verb are common approaches. This is outside IronPDF but is the replacement for the spooler submission that RawPrint provided.
  9. Validate on target printers: Test the PDF output on each physical printer in the environment. Confirm that paper size, margin, and font rendering match the previous output. Label printers in particular may require dimension fine-tuning.
  10. Add archival and compliance features if applicable: If the migration unlocks new requirements (archive print history as PDF/A, apply digital signatures to documents), implement those capabilities using IronPDF's security and compliance APIs.
  11. Update test coverage: Add automated tests that render each document template and verify output. PDF text extraction can be used to validate data fields; visual comparison tools can validate layout.
  12. Remove platform-specific Win32 assumptions: Audit the codebase for other direct Win32 print API calls that may have been used alongside RawPrint. These may also need to be replaced or wrapped for cross-platform compatibility.

Conclusion

When staying on RawPrint is technically reasonable

RawPrint is discontinued, which means staying on it is only reasonable as a short-term deferral strategy, not a long-term position. The clearest case for short-term deferral is when the application is already scheduled for replacement, when the printer infrastructure is locked to command-language formats (ZPL, ESC/P) that require a raw submission path regardless, or when a framework migration is a prerequisite that needs to be scoped separately. In all of these cases, the dependency on RawPrint introduces ongoing risk that should be tracked explicitly.

Signals that indicate migration is worth the engineering effort

Migration urgency is higher than for active libraries because the discontinued status means no security patches, no .NET compatibility updates, and no community support. The most compelling signals for accelerating migration are: the host application targeting modern .NET (which RawPrint cannot support), a requirement for cross-platform or containerized deployment, an expanding document scope that now includes archival, signing, or compliance requirements, or the emergence of printer hardware that accepts PDF natively.

What the cutover typically involves at the code level

This migration is architectural rather than mechanical. The removal of RawPrint is straightforward; what replaces it requires new work. Teams will need to: (a) build HTML/CSS templates for each print document type, (b) integrate ChromePdfRenderer for PDF generation, and (c) implement OS-level print submission for any workflows that must drive a physical printer. The first item is where the majority of the effort lies. Teams with existing web templates (Razor views, HTML invoice templates) for the same document types can often reuse that work. Teams whose documents exist only as ESC/P or ZPL command streams must rebuild templates from scratch. The resulting PDF-based pipeline typically has better testability, broader format support, and a path to compliance features that were unavailable with a raw-print-only approach.
