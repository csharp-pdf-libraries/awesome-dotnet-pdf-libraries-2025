Migrating from PDFmyURL to IronPDF: the .NET migration reference

technical depth for .NET teams evaluating a PDF library switch

Framing

PDFmyURL is one of the longer-running cloud-based URL-to-PDF services, offering an API for converting web pages and HTML content to PDF via HTTP requests. Teams that integrated PDFmyURL into .NET applications did so at a time when embedding a full Chromium rendering engine in-process was operationally complex, and a simple HTTP API that accepted a URL and returned a PDF was an attractive solution. The integration pattern is familiar: configure an HttpClient, POST the target URL or HTML content, receive the PDF bytes in the response.

The conditions that drive re-evaluation of cloud URL-to-PDF services have compounded over time. PDFmyURL's API sends the target URL (or raw HTML) to PDFmyURL's servers for rendering — meaning that any content submitted for PDF generation traverses a third-party network boundary. For applications generating PDFs from private customer data, authenticated internal pages, or documents subject to data residency requirements, this transmission model has become harder to justify under compliance frameworks including GDPR, HIPAA, and SOC 2. Additionally, PDFmyURL can only render URLs that are publicly accessible from its own infrastructure, which excludes staging environments, authenticated endpoints, and internal services.

This guide covers the migration from PDFmyURL to IronPDF for .NET engineers evaluating or executing the switch. PDFmyURL's current product status, .NET SDK availability, and specific API surface should be verified in official documentation, as these details may have changed. The migration is classified as Low effort — both services use Chromium-based rendering, the output is highly consistent, and the migration work is replacing HTTP client calls with in-process method calls.

What PDFmyURL Is Designed to Do

PDFmyURL is a cloud-based HTML-to-PDF conversion service that uses Chromium for rendering. It accepts either a URL or raw HTML content via its HTTP API and returns a PDF. The service has been commercially available for many years. The .NET integration is via HTTP client calls; an official .NET SDK may exist

The primary use case is converting publicly accessible web pages or HTML documents to PDF without managing any local rendering infrastructure. PDFmyURL handles Chromium deployment, updates, and scaling on its own servers. Configuration options typically include paper size, orientation, margins, JavaScript execution wait time, and header/footer templates — the exact parameter names and formats should be verified in official documentation. PDFmyURL does not provide PDF manipulation, merging, form filling, digital signatures, or compliance output.

Architectural Differences

PDFmyURL and IronPDF both use Chromium for rendering, meaning HTML templates, CSS layouts, JavaScript execution, and web fonts that work in PDFmyURL will render consistently in IronPDF. The architecture differs entirely in where the Chromium engine runs: on PDFmyURL's remote servers (accessed via HTTP), or embedded in-process within the .NET application (IronPDF).

IronPDF's two primary types are ChromePdfRenderer (for HTML and URL rendering) and PdfDocument (for the result and all manipulation). Both implement IDisposable and require using blocks. The HTML string to PDF guide covers rendering configuration. For URL rendering with JavaScript wait conditions and cookie injection, the URL to PDF guide covers all options. License initialization is a one-time startup call; see the license setup guide.

The key operational changes: HTML content and URLs no longer leave the application for rendering; network latency is removed from every render call; URLs only accessible from the application's own network (internal services, staging, authenticated pages) can now be rendered without exposing them publicly; and post-render PDF operations (merge, sign, encrypt, form-fill) become available on the rendered PdfDocument without a second library.

Operation Comparisons

URL to PDF

PDFmyURL — URL to PDF via HTTP API

using System.Net.Http;
using System.Collections.Generic;

// PDFmyURL HTTP API pattern
// and authentication mechanism in official documentation

public class PdfMyUrlClient
{
    private readonly HttpClient _httpClient;
    private const string ApiEndpoint = "https://pdfmyurl.com/api";
    private const string ApiKey = "YOUR_PDFMYURL_API_KEY";

    public PdfMyUrlClient(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }

    public async Task<byte[]> UrlToPdfAsync(string targetUrl, PdfOptions options)
    {
        // PDFmyURL accepts form-encoded or JSON parameters
        var parameters = new Dictionary<string, string>
        {
            { "license",     ApiKey },         // verify auth parameter name
            { "url",         targetUrl },       // the URL to convert
            { "page_size",   options.PageSize },       // e.g., "A4"
            { "orientation", options.Orientation },    // e.g., "portrait"
            { "margin_top",    options.MarginTop.ToString() },    // verify unit
            { "margin_bottom", options.MarginBottom.ToString() },
            { "margin_left",   options.MarginLeft.ToString() },
            { "margin_right",  options.MarginRight.ToString() },
        };

        using var formContent = new FormUrlEncodedContent(parameters);
        using var response = await _httpClient.PostAsync(ApiEndpoint, formContent);
        response.EnsureSuccessStatusCode();

        return await response.Content.ReadAsByteArrayAsync();
    }

    public record PdfOptions(
        string PageSize = "A4",
        string Orientation = "portrait",
        int MarginTop = 10,
        int MarginBottom = 10,
        int MarginLeft = 10,
        int MarginRight = 10);
}

Concrete constraints:

  • The target URL must be publicly accessible from PDFmyURL's servers. Internal URLs, authenticated pages, and staging environments are not reachable unless explicitly exposed.
  • All request parameters — field names, units, encoding format (form-encoded vs JSON), and API endpoint — must be verified in official documentation before planning the migration mapping.
  • response.EnsureSuccessStatusCode() throws on HTTP errors from the PDFmyURL API. These are network/service errors, not rendering errors.
  • API key management (secrets storage, rotation) is an operational concern that is eliminated during migration.
  • PDFmyURL's servers fetch and render the target URL on their infrastructure — JavaScript-heavy pages that depend on cookies, session state, or network-restricted resources may not render as expected.

IronPDF — URL to PDF

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.PaperOrientation = IronPdf.Rendering.PdfPaperOrientation.Portrait;
renderer.RenderingOptions.MarginTop = 10;    // mm
renderer.RenderingOptions.MarginBottom = 10;
renderer.RenderingOptions.MarginLeft = 10;
renderer.RenderingOptions.MarginRight = 10;

// WaitFor replaces PDFmyURL's JS wait parameter
renderer.RenderingOptions.WaitFor.HtmlElement(".page-loaded");

// Cookies for authenticated URLs — PDFmyURL cannot reach private URLs at all
renderer.RenderingOptions.CustomCookies =
    new System.Collections.Generic.Dictionary<string, string>
    {
        { "session_id", "your-session-token" }
    };

// IronPDF renders from the application server — internal URLs are reachable
using var pdf = renderer.RenderUrlAsPdf("https://reports.internal.example.com/q3");
byte[] pdfBytes = pdf.BinaryData;
pdf.SaveAs("q3-report.pdf");

The most significant operational improvement is URL accessibility: IronPDF renders from the application's own network, so internal services, staging environments, and authenticated URLs that PDFmyURL's cloud servers cannot reach become directly renderable. The URL to PDF guide covers all wait conditions, cookie injection, and authentication strategies.

HTML String to PDF

PDFmyURL — HTML String Submission

using System.Net.Http;
using System.Collections.Generic;

// PDFmyURL HTML submission
public async Task<byte[]> HtmlToPdfAsync(string html)
{
    var parameters = new Dictionary<string, string>
    {
        { "license", ApiKey },
        // PDFmyURL may accept HTML via a different parameter than URL
        // Verify the exact field name for raw HTML submission
        { "html",    html },      // verify parameter name
        { "page_size", "A4" },
    };

    using var content = new FormUrlEncodedContent(parameters);
    using var response = await _httpClient.PostAsync(ApiEndpoint, content);
    response.EnsureSuccessStatusCode();

    return await response.Content.ReadAsByteArrayAsync();
}

Concrete constraints:

  • Submitting raw HTML to PDFmyURL transmits the HTML content (potentially including customer data, business logic, or PII) to PDFmyURL's servers. This is the data residency concern.
  • Verify the exact parameter name for HTML content submission in official documentation.
  • Large HTML payloads may encounter API request size limits

IronPDF — HTML String to PDF

using IronPdf;

// Singleton renderer — register in DI and inject
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 10;
renderer.RenderingOptions.MarginBottom = 10;
renderer.RenderingOptions.MarginLeft = 10;
renderer.RenderingOptions.MarginRight = 10;

// HTML content never leaves the application process
string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Confidential Report</h1>
  <p>Customer: Acme Corp. Balance: $12,500. Status: Active.</p>
</body>
</html>";

// Data stays in-process — no HTTP transmission to third party
using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("confidential-report.pdf");

The HTML content — which may contain PII, financial data, or proprietary business logic — remains in-process and never traverses a network boundary. This is the primary compliance argument for the migration. Full rendering configuration is in the HTML string to PDF guide.

ASP.NET Core Integration

PDFmyURL — ASP.NET Core Controller

using Microsoft.AspNetCore.Mvc;
using System.Net.Http;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { private readonly PdfMyUrlClient _pdfClient;

public ReportController(PdfMyUrlClient pdfClient) { _pdfClient = pdfClient; }

[HttpGet("{id}/pdf")] public async Task GetReport(int id) { string reportUrl = $"https://app.example.com/reports/{id}";

try { // Network call to PDFmyURL — latency + external service dependency byte[] pdfBytes = await _pdfClient.UrlToPdfAsync( reportUrl, new PdfMyUrlClient.PdfOptions("A4", "portrait"));

return File(pdfBytes, "application/pdf", $"report-{id}.pdf"); } catch (HttpRequestException ex) { return StatusCode(503, $"PDF service unavailable: {ex.Message}"); } } }

Concrete constraints:

  • PdfMyUrlClient is registered via IHttpClientFactory — this DI registration is removed during migration.
  • The report URL must be publicly accessible at app.example.com for PDFmyURL to reach it.
  • HttpRequestException reflects service unavailability — PDF generation fails if PDFmyURL is down.

IronPDF — ASP.NET Core Controller

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("reports")] public class ReportController : ControllerBase { private readonly ChromePdfRenderer _renderer;

public ReportController(ChromePdfRenderer renderer) { _renderer = renderer; }

[HttpGet("{id}/pdf")] public async Task GetReport(int id) { // Internal URL — accessible from the application's own network // No need to expose this endpoint publicly for PDF generation string reportUrl = $"https://reports.internal.example.com/{id}";

using var pdf = await _renderer.RenderUrlAsPdfAsync(reportUrl);

return File(pdf.BinaryData, "application/pdf", $"report-{id}.pdf"); } }

// Program.cs: // IronPdf.License.LicenseKey = "YOUR-KEY"; // builder.Services.AddSingleton(sp => { // var r = new ChromePdfRenderer(); // r.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4; // return r; // }); // Remove: builder.Services.AddHttpClient(...);

The PdfMyUrlClient DI registration is replaced by ChromePdfRenderer singleton. The report URL can be an internal address (not public internet). HttpRequestException handling is removed. The async rendering guide covers concurrent rendering in high-traffic ASP.NET Core applications.

Post-Render Operations (New Capability)

using IronPdf;
using IronPdf.Signing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// PDFmyURL: renders a URL, returns bytes, no manipulation surface
// IronPDF: renders a URL, returns PdfDocument with full manipulation

using var rendered = renderer.RenderUrlAsPdf(
    "https://reports.internal.example.com/annual");

// Merge with a cover page rendered from HTML
using var cover = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Annual Report 2025</h1><p>Confidential</p></body></html>");
using var combined = PdfDocument.Merge(cover, rendered);

// Add password protection
combined.SecuritySettings.UserPassword = "annual2025";
combined.SecuritySettings.AllowUserPrinting = IronPdf.Security.PdfPrintSecurity.FullPrintAllowed;

// Sign with certificate
var sig = new PdfSignature("cert.pfx", "pfx-password")
{
    SigningReason = "Annual report distribution"
};
combined.Sign(sig);

combined.SaveAs("annual-report-2025-signed.pdf");

Post-render operations that previously required a second library are available on the rendered PdfDocument. The merge and split guide and digital signatures guide cover these operations.

Breaking Changes & Gotchas

  • URL accessibility model inverted: PDFmyURL renders from its own servers — only public internet URLs are accessible. IronPDF renders from the application's host — internal URLs accessible from the app server become renderable. URLs that were previously public for PDFmyURL rendering may no longer need to be public.
  • API credentials removed entirely: PDFmyURL API key configuration, storage, and any key rotation process are all removed. Replace with IronPdf.License.LicenseKey at startup.
  • PdfDocument is IDisposable: PDFmyURL returns byte[] — no disposal. IronPDF returns PdfDocument requiring using blocks.
  • HTTP error handling removed: EnsureSuccessStatusCode(), HttpRequestException catch blocks, retry policies, and timeout configuration for PDFmyURL are removed.
  • Margin unit verification: PDFmyURL's margin unit convention (mm, pixels, or points) must be verified before mapping to IronPDF's millimeter-based Margin* properties.
  • Header/footer token syntax: Verify PDFmyURL's page number token syntax and update all header/footer HTML to use IronPDF's {page} and {total-pages}.
  • IHttpClientFactory registration removed: The typed or named HttpClient registration for PDFmyURL is replaced by builder.Services.AddSingleton<ChromePdfRenderer>().
  • Namespace change: Remove PDFmyURL SDK using directives (if an SDK exists). Add using IronPdf;.
  • Linux deployment: PDFmyURL's client has no binary dependencies. IronPDF on Linux requires Chromium system library packages in the container.
  • Data residency change: HTML content and URLs submitted to PDFmyURL traversed a third-party network. IronPDF renders in-process — this eliminates the third-party data transmission entirely.

Migration Checklist

  1. Verify PDFmyURL API surface: Review official documentation to confirm endpoint, authentication, request format, margin units, JavaScript wait parameters, and header/footer token syntax before mapping to IronPDF equivalents.
  2. Audit all PDFmyURL call sites: List every location where the API is called — URL rendering, HTML rendering, configuration parameters used.
  3. Map PDFmyURL parameters to RenderingOptions: Verify margin unit and convert if needed. Map each parameter name to the corresponding RenderingOptions property.
  4. Install IronPDF via NuGet: dotnet add package IronPdf.
  5. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs. See the license setup guide.
  6. Remove PDFmyURL credential management: Delete API key storage, configuration entries, and any key rotation logic.
  7. Remove IHttpClientFactory registration: Delete AddHttpClient<PdfMyUrlClient>(). Replace with builder.Services.AddSingleton<ChromePdfRenderer>().
  8. Update namespaces: Remove PDFmyURL using directives. Add using IronPdf;.
  9. Replace URL rendering calls: Map to renderer.RenderUrlAsPdf(url). Evaluate whether URLs that were previously public still need to be public, or can now be internal.
  10. Replace HTML rendering calls: Map to renderer.RenderHtmlAsPdf(html). Add using block. Access bytes via pdf.BinaryData.
  11. Update header/footer tokens: Identify PDFmyURL's page number token syntax and update to {page} / {total-pages}.
  12. Remove HTTP error handling: Delete EnsureSuccessStatusCode() and HttpRequestException catch blocks specific to PDFmyURL. Update Linux container image with Chromium system libraries.

Conclusion

When staying on PDFmyURL is technically reasonable

PDFmyURL is technically reasonable when the team's operational model favors zero in-process binary dependencies, when all generated PDFs come from publicly accessible URLs that PDFmyURL's servers can render correctly, when data residency requirements do not restrict sending HTML content to a third-party cloud service, and when PDF volume is low enough that per-request pricing is not a concern. Teams with simple URL-to-PDF workflows and no post-render manipulation requirements have the least pressure to migrate.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping when compliance requirements restrict transmitting HTML document content (especially content including customer data) to third-party servers; when internal or authenticated URLs that PDFmyURL cannot reach need to be rendered; when network latency from cloud round-trips is measurable in user-facing response times; when post-render operations (merge, sign, PDF/A, form-fill) require an additional library; or when PDFmyURL service availability has caused production incidents.

What the cutover typically involves at the code level

The migration is bounded: remove credential management, swap IHttpClientFactory registration for ChromePdfRenderer singleton, replace HTTP call patterns with renderer method calls, add using blocks, update header/footer tokens, remove HTTP error handling, update the Linux container image. For applications with a concentrated set of PDFmyURL call sites, the API replacement is straightforward. The rendering comparison pass — validating that Chromium output in IronPDF matches the Chromium output from PDFmyURL across all URL and HTML templates — is the quality gate. Because both use Chromium, the comparison pass is typically faster than migrations from non-Chromium services.

As you evaluate this migration, how many of the URLs currently submitted to PDFmyURL for rendering could move to internal, non-public addresses if the rendering happened from the application's own network — and would that architectural simplification have any value to the operations team?
