Migrating from Telerik Document Processing to IronPDF: a .NET team's field guide

a step-by-step .NET migration guide for 2026

Framing

Frequently acquired as part of a broader UI component or platform suite, document processing libraries in enterprise .net ecosystems are. Telerik's document processing components follow this pattern: teams that adopt Telerik for its UI controls — grids, charts, schedulers — often inherit the document processing layer as part of the same license. The PDF component gets integrated with relatively low ceremony, and the integration stabilizes into a known, tested state.

Re-evaluation tends to surface at platform inflection points. A .NET version upgrade, a move from Windows-hosted IIS to Linux containers, or a shift from monolithic deployment to microservices can expose assumptions that were reasonable for an earlier architecture. Teams working on .NET 6 migrations in 2025 or later may find that Telerik Document Processing's component compatibility requirements warrant verification — the library's support for newer .NET targets, Linux rendering, and modern CSS should be confirmed against current Telerik documentation before committing to a new platform.

A second driver is functional scope. Telerik Document Processing covers document manipulation well — reading, modifying, and assembling PDFs from lower-level primitives — but HTML-to-PDF rendering that matches modern browser output is a distinct capability, and the two are not equivalent. Teams whose document generation needs have moved toward HTML template-based workflows (Razor views, React-rendered dashboards, CSS-styled reports) sometimes find that their existing PDF library was not selected for that use case and does not serve it as directly as alternatives.

What Telerik Document Processing Is Designed to Do

Telerik Document Processing (part of Telerik UI for various platforms, also available as a standalone library) is a suite of .NET components covering multiple document formats: PDF, Word (DOCX), Excel (XLSX), and ZIP. The PDF component — RadPdfProcessing — provides a programmatic model for creating, reading, and modifying PDF documents. The API exposes a RadFixedDocument model with pages, content streams, form fields, annotations, and digital signature support. Content is added to pages through a FixedContentEditor that draws text, images, shapes, and tables at specified positions.

The integration model is NuGet-based, and because the core library is a purely managed .NET assembly, it carries no native binary dependencies. This makes it straightforward to deploy on any OS target without platform-specific package management. The library is actively maintained as part of the Telerik ecosystem. Primary use cases include PDF generation from structured data (financial reports, invoices, regulatory filings), PDF manipulation (reading, merging, modifying existing documents), and form field operations. For HTML-to-PDF scenarios, Telerik Document Processing does not include a built-in HTML renderer; those scenarios typically require a separate Telerik component or an external library. Note: current .NET version support, available features in the latest release, and exact package structure should be verified against Telerik's official documentation.

Architectural Differences

IronPDF and Telerik Document Processing serve overlapping but architecturally distinct models. Telerik's RadPdfProcessing is a document model library: content is constructed through API calls that manipulate an in-memory PDF structure (RadFixedDocument, FixedContentEditor), similar to operating on the PDF specification directly. This gives fine-grained control over the output at the cost of requiring the developer to describe layout through code rather than markup.

IronPDF's primary path is rendering-first: HTML and CSS are the authoring language, and the Chromium engine produces the PDF. The PdfDocument returned by ChromePdfRenderer is then available for the same categories of post-processing that Telerik's document model enables — merging, splitting, stamping, signing, encrypting. For HTML template rendering scenarios, IronPDF's approach requires no drawing API code at all; the layout is expressed as markup. For programmatic layout — content at specific coordinates — IronPDF does not expose a drawing API equivalent to FixedContentEditor.

The deployment trade-off is the inverse of Telerik's. Telerik's managed-only assembly deploys with no native dependencies. IronPDF requires a Chromium component, which introduces OS-level dependencies on Linux and carries a larger deployment footprint. For teams already running Chromium-based tooling or deploying on standard cloud infrastructure, this is typically a configuration step rather than a fundamental constraint. For teams in restricted environments where subprocess spawning is limited or where image size is tightly budgeted, the Chromium dependency warrants evaluation. License initialization is a static startup call; the license setup guide covers both key injection and environment-variable patterns.

Operation Comparisons

Programmatic Document Creation (FixedContentEditor)

Telerik Document Processing — FixedContentEditor

Telerik's RadPdfProcessing creates documents through a RadFixedDocument / RadFixedPage / FixedContentEditor hierarchy. Content is positioned at coordinates using editor.DrawText(), editor.DrawImage(), and table layout helpers. The model is close to the PDF specification's content stream model.

// Telerik RadPdfProcessing — conceptual pattern
// Requires: Telerik.Documents.Fixed (or suite package)
// Verify exact class names and method signatures in Telerik documentation

// using Telerik.Windows.Documents.Fixed.Model;
// using Telerik.Windows.Documents.Fixed.Model.Editing;

// var document = new RadFixedDocument();
// var page     = document.Pages.AddPage();
// page.Size    = new Size(595, 842); // A4 in points

// using var editor = new FixedContentEditor(page);
// editor.Position.Translate(50, 50);

// // Draw text
// editor.TextProperties.FontSize = 18;
// editor.DrawText("Invoice #1234");

// editor.Position.Translate(50, 90);
// editor.TextProperties.FontSize = 11;
// editor.DrawText("Bill To: Jane Smith");

// // Save to stream
// var provider = new Telerik.Windows.Documents.Fixed.FormatProviders.Pdf.PdfFormatProvider();
// using var stream = new MemoryStream();
// provider.Export(document, stream);

Key constraints:

  • Content placement requires manual coordinate tracking; the developer manages layout geometry
  • Table construction requires explicit cell sizing and positioning
  • No HTML or CSS involvement; output is entirely determined by API call sequence
  • FixedContentEditor implements IDisposable; must be disposed after use
  • Changing layout requires recalculating coordinates; dynamic content (variable-length text fields) requires measurement and reflow logic

IronPDF — HTML-Based Document Creation

IronPDF replaces coordinate-based drawing with HTML/CSS template rendering. For invoice and report layouts, the HTML approach typically produces equivalent output with significantly less layout management code. The HTML to PDF examples illustrate common document patterns including tables and multi-section layouts.

using IronPdf;

// IronPdf.License.LicenseKey = "YOUR-LICENSE-KEY"; // Set at application startup

using var renderer = new ChromePdfRenderer();

// Configure paper size and margins
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop    = 15;
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.MarginLeft   = 15;
renderer.RenderingOptions.MarginRight  = 15;

// Express the document as HTML/CSS — no coordinate math required
string invoiceHtml = @"
<!DOCTYPE html>
<html>
<head>
  <style>
    body     { font-family: Helvetica, Arial, sans-serif; font-size: 11pt; margin: 0; }
    h1       { font-size: 18pt; margin-bottom: 4px; }
    .meta    { font-size: 10pt; color: #555; margin-bottom: 20px; }
    table    { width: 100%; border-collapse: collapse; }
    th, td   { border: 1px solid #ccc; padding: 6px 10px; }
    th       { background: #f5f5f5; font-weight: bold; }
  </style>
</head>
<body>
  <h1>Invoice #1234</h1>
  <div class='meta'>Bill To: Jane Smith &nbsp;|&nbsp; Date: 2026-02-25</div>
  <table>
    <tr><th>Item</th><th>Qty</th><th>Unit Price</th><th>Total</th></tr>
    <tr><td>Widget A</td><td>10</td><td>$25.00</td><td>$250.00</td></tr>
    <tr><td>Service B</td><td>3</td><td>$120.00</td><td>$360.00</td></tr>
  </table>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(invoiceHtml);
pdf.SaveAs("/output/invoice-1234.pdf");

Layout changes (different field counts, variable line items, conditional sections) are handled by generating different HTML strings rather than recalculating coordinates. Templating engines (Razor, Scriban, Fluid) integrate naturally with this approach.

Load and Manipulate Existing PDFs

Telerik Document Processing — Load and Modify

Telerik's PdfFormatProvider loads an existing PDF into a RadFixedDocument, which exposes the document's pages, content streams, form fields, and annotations for modification. Text can be appended to pages, pages can be reordered, and form fields can be accessed by name.

Key constraints:

  • Complex content modification (editing existing text in the content stream) may be limited; appending content to pages is generally more reliable
  • Form field access uses a typed collection; verify field type handling for all field types in use
  • Large PDF handling

IronPDF — Load and Manipulate

IronPDF loads existing PDFs via PdfDocument.FromFile(). Post-load operations including text extraction, stamping, form field editing, merging, and signing are available through the document's API. The editing PDFs examples cover common manipulation patterns.

using IronPdf;
using IronPdf.Editing;

// Load an existing PDF for modification
using var pdf = PdfDocument.FromFile("/input/contract-draft.pdf");

// Stamp additional content onto page 0 (first page)
var stampHtml = new HtmlStamper
{
    Html      = "<div style='color:red; font-size:24px; opacity:0.4;'>DRAFT</div>",
    Opacity   = 40,
    Rotation  = -45,
    VerticalAlignment   = VerticalAlignment.Middle,
    HorizontalAlignment = HorizontalAlignment.Center
};
pdf.ApplyStamp(stampHtml);

// Add metadata
pdf.MetaData.Title  = "Contract Draft v2";
pdf.MetaData.Author = "Documents Team";

// Save modified document
pdf.SaveAs("/output/contract-draft-stamped.pdf");

Verify class names (HtmlStamper, ApplyStamp) and their property names against current IronPDF documentation, as the stamp API surface has evolved across versions.

Digital Signatures

Telerik Document Processing — Digital Signatures

Telerik's RadPdfProcessing supports digital signatures via signature fields added programmatically to the document. A SignatureField is placed on a page, and a X509Certificate2-based signature is applied. Verify current TSA (timestamp authority) and LTV support in Telerik documentation.

Key constraints:

  • Signature field placement requires coordinate specification
  • Certificate loading uses X509Certificate2; PFX and certificate store sources are both supported
  • Signature appearance customization (visible signature block content)

IronPDF — Digital Signatures

IronPDF's PdfSignature API applies cryptographic signatures to existing PDF documents. The digital signatures guide documents certificate configuration, visible signature block options, and contact/reason/location metadata. For environments where the signing certificate's private key is managed in hardware (HSM), the HSM signing guide covers that integration pattern.

using IronPdf;
using IronPdf.Signing;

// Load the document to sign
using var pdf = PdfDocument.FromFile("/input/final-contract.pdf");

// Configure the digital signature using a PFX certificate
var signature = new PdfSignature("/certs/company-signing.pfx", "pfxPassword")
{
    SigningContact  = "contracts@example.com",
    SigningReason   = "Execution of agreement",
    SigningLocation = "Chicago, IL"
};

// Apply signature and save
pdf.Sign(signature);
pdf.SaveAs("/output/final-contract-signed.pdf");

Verify the PdfSignature constructor parameters and the full set of available properties in current IronPDF documentation. Timestamp server configuration for long-term validation should also be confirmed.

PDF/A Compliance

Telerik Document Processing — PDF/A Output

Telerik's PdfFormatProvider supports exporting documents to PDF/A format via export settings. The available PDF/A profiles (PDF/A-1b, PDF/A-2b, etc.) should be verified in Telerik documentation.

Key constraints:

  • PDF/A requires all fonts to be embedded; documents with non-embeddable fonts will fail validation
  • Color space requirements (no device-dependent color in PDF/A-1) may affect existing document colors
  • PdfFormatProvider.ExportSettings.IsEncrypted must be false for PDF/A compliance — PDF/A and encryption are mutually exclusive

IronPDF — PDF/A Compliance

IronPDF saves documents in PDF/A format via pdf.SaveAsPdfA(). The PDF/A guide documents supported profiles and the requirements for compliant output including font embedding and color space handling.

using IronPdf;

using var renderer = new ChromePdfRenderer();
using var pdf = renderer.RenderHtmlAsPdf("/input/archive-document.html");

// Save as PDF/A-2b
pdf.SaveAsPdfA("/output/archive-document-pdfa2b.pdf", IronPdf.Rendering.PdfAVersions.PdfA2B);

// Or convert an existing PDF to PDF/A
using var existing = PdfDocument.FromFile("/input/legacy-report.pdf");
existing.SaveAsPdfA("/output/legacy-report-pdfa.pdf", IronPdf.Rendering.PdfAVersions.PdfA2B);

Test compliance output against veraPDF or another PDF/A validator before deploying to production archival workflows. Verify the exact profile enum names and available options in current IronPDF documentation.

Breaking Changes & Gotchas

  • No FixedContentEditor equivalent. Telerik's coordinate-based drawing model has no direct equivalent in IronPDF. Code paths using FixedContentEditor.DrawText(), DrawImage(), table drawing, and Position.Translate() must be refactored into HTML/CSS templates. This is the primary effort concentration for teams with significant programmatic document generation code.
  • Rendering engine introduction. Telerik Document Processing's core library has no native dependencies. IronPDF introduces a Chromium component, which changes the deployment model: Linux targets need OS-level dependencies installed, and the first-run or cold-start behavior includes Chromium initialization. Teams moving to Linux containers must account for this in Dockerfile authoring.
  • Namespace change. Telerik types are under Telerik.Windows.Documents.Fixed and related namespaces. IronPDF types are under IronPdf. All using directives and any reflection-based type resolution must be updated.
  • License model change. Telerik uses a license key typically validated at runtime against a Telerik license server or an embedded license assembly. IronPDF uses a static string key set at startup. Key management patterns differ; update secrets management accordingly.
  • FixedContentEditor disposal. Telerik's FixedContentEditor implements IDisposable and must be disposed explicitly. IronPDF's equivalent is ChromePdfRenderer, which also implements IDisposable. Update disposal patterns throughout.
  • Form API surface. Telerik's AcroForm.FormFields collection uses a typed field hierarchy. IronPDF's form API uses a different accessor pattern. Verify field access, value setting, and flattening behavior in current IronPDF documentation before migrating form-heavy code.
  • Annotation API surface. Telerik provides annotation reading and writing. IronPDF supports annotations but with a different API surface. Verify IronPDF's current annotation capabilities and property names.
  • Thread safety. Telerik's thread-safety model for document manipulation should be verified in their documentation. IronPDF recommends separate ChromePdfRenderer instances per thread. Audit concurrent access patterns in the existing code.
  • PDF/A + encryption mutual exclusion. Both Telerik and IronPDF enforce that PDF/A documents cannot be encrypted. If existing workflows attempt to create encrypted PDF/A documents, this constraint will surface as a validation error in either library.

Migration Checklist

  1. Categorize Telerik Document Processing usage. Separate code into: programmatic generation via FixedContentEditor, document manipulation (load, merge, split, sign), and form operations. The generation category drives the majority of the migration effort.
  2. Author HTML templates for generation use cases. For each document type built with FixedContentEditor, design and test an equivalent HTML/CSS template. Verify rendered output against existing sample documents before writing any migration code.
  3. Swap NuGet packages. Remove Telerik Document Processing package references. Add IronPDF: dotnet add package IronPdf. Verify that any other Telerik document format packages (DOCX, XLSX) that are needed independently remain referenced.
  4. Configure license key. Add IronPdf.License.LicenseKey = "YOUR-KEY"; to application startup. Remove Telerik license initialization. See the license configuration guide for environment-variable setup patterns.
  5. Update namespace imports. Replace all using Telerik.Windows.Documents.Fixed.* and related directives with using IronPdf; and required sub-namespaces.
  6. Migrate generation code to HTML rendering. Replace RadFixedDocument / FixedContentEditor construction with ChromePdfRenderer.RenderHtmlAsPdf() calls using the templates from Step 2. Remove all coordinate math and DrawText() / DrawImage() calls.
  7. Migrate document manipulation. Replace PdfFormatProvider.Import() with PdfDocument.FromFile(). Update merge, split, extract, and stamp calls to IronPDF equivalents. Verify each method name against current IronPDF documentation.
  8. Migrate form field code. Replace AcroForm.FormFields access with IronPDF's form API. Cover all field types present in production forms. Test value-setting, flattening, and save behavior explicitly.
  9. Migrate digital signature code. Replace Telerik's RadSignatureField and signing workflow with PdfSignature. Verify contact, reason, location, and timestamp options in current IronPDF documentation.
  10. Update disposal patterns. Replace FixedContentEditor using blocks with ChromePdfRenderer and PdfDocument using blocks. Audit all exception handling paths to ensure disposal under error conditions.
  11. Update deployment configuration. Add Chromium dependency installation to Dockerfiles and Linux deployment scripts. Remove Telerik-specific deployment steps and license file management.
  12. Run full regression and compliance validation. Execute the document generation and manipulation test suite. For any PDF/A output, validate against veraPDF. For signed documents, verify signature validity with an independent validator.

Conclusion

When staying on Telerik Document Processing is technically reasonable: If the application makes extensive use of FixedContentEditor-based document construction, the team is fluent in Telerik's document model, and the existing license already addresses the PDF component without disproportionate cost, the migration overhead may not be justified in the near term. Teams that also rely on Telerik's DOCX or XLSX processing components have an additional consolidation argument for staying in the Telerik ecosystem. Telerik Document Processing is actively maintained, so there is no urgency driven by discontinuation risk.

Signals that indicate migration is worth the engineering effort: The primary signals are a shift toward HTML template-based document generation (Razor views, React-rendered content) where Telerik's drawing API creates friction; a new requirement for HTML-to-PDF rendering that Telerik's core library does not address natively; Linux or container deployment goals that benefit from a simpler deployment model; or a commercial decision to reduce the Telerik suite footprint to only UI components that are actively used.

What the cutover typically involves at the code level: The manipulation-oriented code paths (load, merge, split, sign, form fill) migrate as direct API substitutions and can be executed in a focused sprint. The generation code paths built on FixedContentEditor require the template authoring step first; once HTML templates are ready, the renderer call substitution is mechanical. A phased approach — migrating manipulation paths in a first phase, generation paths in a second phase as templates are completed — provides measurable progress and reduces the risk of a large, single-phase cutover on document generation infrastructure.
