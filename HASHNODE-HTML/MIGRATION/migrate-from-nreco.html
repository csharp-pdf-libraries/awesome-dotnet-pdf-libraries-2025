Migrating from NReco PDF Generator to IronPDF: step-by-step for .NET developers

what changes, what breaks, and what maps cleanly

Framing

NReco PDF Generator occupies a category of .NET PDF library that was widely adopted during the era before Chromium-based in-process rendering was available. As a thin managed wrapper around wkhtmltopdf — the open-source command-line tool that uses a QtWebKit rendering engine — it allowed .NET developers to convert HTML to PDF by shelling out to a native binary, avoiding the need to manage a full headless browser process directly. For applications that needed basic HTML-to-PDF conversion without commercial licensing costs, it was a practical choice.

The rendering engine underlying wkhtmltopdf (QtWebKit) is no longer under active development and has not tracked modern web standards for several years. The CSS limitations are well documented: Flexbox layout, CSS Grid, modern position: sticky, advanced calc() expressions, and various CSS3 features either render incorrectly or are not supported. Web fonts from Google Fonts or CDN-hosted sources frequently fail to load due to network isolation or SSL certificate handling issues in the wkhtmltopdf binary. As design systems and front-end frameworks have moved to modern CSS, the gap between wkhtmltopdf's rendered output and what a browser shows has widened. Teams maintaining HTML templates for wkhtmltopdf-based generation often find themselves maintaining a second, older CSS layer specifically for the PDF output path.

This guide covers the migration from NReco PDF Generator (and wkhtmltopdf) to IronPDF for .NET engineers evaluating or executing the switch. NReco PDF Generator is no longer actively maintained; the last release should be verified but the library is effectively discontinued. IronPDF uses Chromium for rendering — the same engine as Chrome and Edge — which eliminates the CSS compatibility gap. The migration is classified as Low effort because the API surface of NReco PDF Generator is minimal (it's a thin wrapper), and the conceptual operation is identical: HTML string or URL in, PDF bytes out.

What NReco PDF Generator Is Designed to Do

NReco PDF Generator is a .NET library that wraps the wkhtmltopdf command-line binary to provide HTML-to-PDF conversion. It is not a rendering engine itself — it packages and invokes wkhtmltopdf as a subprocess, passing HTML content and configuration options via command-line arguments, and captures the PDF output. The library distributes via NuGet with the wkhtmltopdf binary bundled; this bundled binary approach was one of NReco's conveniences over managing the wkhtmltopdf binary separately.

The primary API is the HtmlToPdfConverter class, which accepts an HTML string or a URL and returns a byte[] containing the PDF output. Configuration is passed through PdfPageOptions — paper size, margins, orientation, and a subset of wkhtmltopdf's command-line options. Headers and footers are configured as separate HTML strings. The library does not provide PDF manipulation, signing, encryption, form filling, or compliance features — its scope is limited to the conversion step. The product status is effectively discontinued; the last release date and any active maintenance should be verified, but NReco PDF Generator is no longer receiving updates.

Architectural Differences

NReco PDF Generator and IronPDF both convert HTML to PDF, but the architecture, rendering engine, and API design differ in important ways. NReco PDF Generator shells out to the wkhtmltopdf process — every conversion spawns a subprocess, writes temporary files, and reads the output. The rendering engine is QtWebKit, which is based on a vintage WebKit snapshot that stopped tracking modern CSS standards around 2016. IronPDF embeds Chromium in-process — no subprocess, no temporary files, a current rendering engine.

IronPDF's two central types are ChromePdfRenderer (for rendering HTML to PDF) and PdfDocument (for the resulting document and all manipulation). Both implement IDisposable. The API conceptually parallels NReco's HtmlToPdfConverter but the underlying model is fundamentally different — ChromePdfRenderer is a reusable instance designed for singleton registration in DI, not a per-call utility. The HTML string to PDF guide covers IronPDF's full rendering configuration. For responsive and modern CSS layouts that were unreliable in wkhtmltopdf, the responsive CSS guide covers Chromium's rendering behavior. License initialization is a one-time startup call; see the license setup guide.

The shift from NReco to IronPDF eliminates the subprocess spawn, the temporary file I/O, and the wkhtmltopdf native binary from the deployment package. It replaces QtWebKit's rendering with Chromium's. On Windows, IronPDF has no native binary requirements. On Linux, Chromium system library packages are required — replacing wkhtmltopdf's Linux binary with a different set of native dependencies.

Operation Comparisons

HTML String to PDF

NReco PDF Generator — HTML String to PDF

using NReco.PdfGenerator;

// HtmlToPdfConverter is NReco's primary type
// Each instance can be reused but typically instantiated per call
var htmlToPdf = new HtmlToPdfConverter();

// Configuration via properties
htmlToPdf.PageSize = PageSize.A4;              // wkhtmltopdf page size
htmlToPdf.Orientation = PageOrientation.Portrait;
htmlToPdf.Margins.Left = 15;    // millimeters
htmlToPdf.Margins.Right = 15;
htmlToPdf.Margins.Top = 15;
htmlToPdf.Margins.Bottom = 15;

// CustomWkHtmlArgs allows passing wkhtmltopdf command-line flags directly
// htmlToPdf.CustomWkHtmlArgs = "--disable-smart-shrinking";

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #1042</h1>
  <p>Customer: Acme Corp</p>
  <p>Total: $1,599.00</p>
</body>
</html>";

// GeneratePdf() spawns a wkhtmltopdf subprocess and returns byte[]
// This is a synchronous, blocking call
byte[] pdfBytes = htmlToPdf.GeneratePdf(html);

System.IO.File.WriteAllBytes("invoice.pdf", pdfBytes);

Concrete constraints:

  • GeneratePdf() spawns a wkhtmltopdf subprocess for every call. Under concurrent load, multiple processes are spawned simultaneously — each with its own memory footprint and startup overhead.
  • wkhtmltopdf writes temporary files to disk during conversion. The temp path must be writable, and cleanup relies on the process completing normally.
  • CustomWkHtmlArgs passes raw wkhtmltopdf command-line flags. Every custom flag must be re-evaluated for IronPDF equivalence or removal.
  • JavaScript rendering in wkhtmltopdf is unreliable for dynamic content. The --enable-javascript flag exists but --javascript-delay values must be tuned per template.
  • Web fonts loaded from CDN URLs frequently fail due to wkhtmltopdf's SSL and network handling. Teams often inline base64-encoded fonts or use system fonts to work around this.
  • CSS Flexbox, Grid, position: sticky, and various CSS3 properties do not render correctly in wkhtmltopdf's QtWebKit engine.

IronPDF — HTML String to PDF

using IronPdf;

// ChromePdfRenderer is reusable — register as singleton in DI
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.PaperOrientation = IronPdf.Rendering.PdfPaperOrientation.Portrait;
renderer.RenderingOptions.MarginTop = 15;     // millimeters — same unit as NReco
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Invoice #1042</h1>
  <p>Customer: Acme Corp</p>
  <p>Total: $1,599.00</p>
</body>
</html>";

// PdfDocument is IDisposable — always use a using block
using var pdf = renderer.RenderHtmlAsPdf(html);

byte[] pdfBytes = pdf.BinaryData;          // equivalent to GeneratePdf()
pdf.SaveAs("invoice.pdf");

Margin units are the same (millimeters) — no conversion required. The key structural change at each call site is adding a using block around the PdfDocument result. CustomWkHtmlArgs flags must be individually evaluated and mapped to RenderingOptions equivalents; flags with no equivalent can usually be removed because Chromium's defaults are more capable than wkhtmltopdf's. Full rendering configuration is in the HTML string to PDF guide.

Headers and Footers

NReco PDF Generator — Headers and Footers

using NReco.PdfGenerator;

var htmlToPdf = new HtmlToPdfConverter();
htmlToPdf.PageSize = PageSize.A4;
htmlToPdf.Margins.Top = 20;
htmlToPdf.Margins.Bottom = 15;

// NReco passes headers/footers as HTML strings to wkhtmltopdf
// wkhtmltopdf uses its own substitution variables for page numbers
htmlToPdf.PageHeaderHtml = @"
<div style='font-size:9px; font-family:Arial; text-align:right; padding:0 10px;'>
  Acme Corp — Monthly Report
</div>";

// wkhtmltopdf substitution variables:
// [page]   → current page number
// [toPage] → total page count
// [date]   → current date
// [title]  → page title
htmlToPdf.PageFooterHtml = @"
<div style='font-size:8px; font-family:Arial; text-align:center;'>
  Page [page] of [toPage]
</div>";

byte[] pdfBytes = htmlToPdf.GeneratePdf(
    "<html><body><p>Document body.</p></body></html>");

Concrete constraints:

  • wkhtmltopdf's page number substitution uses square bracket syntax: [page], [toPage], [date], [title]. These are wkhtmltopdf-specific and work only in the header/footer HTML strings, not in the main document body.
  • Header and footer HTML is rendered as a separate wkhtmltopdf "page" — it has its own CSS scope and does not inherit styles from the main document.
  • Header/footer height is determined by the HTML content height — wkhtmltopdf does not provide explicit height configuration in NReco's API.

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 15;

// IronPDF token syntax differs from wkhtmltopdf's square bracket variables
// wkhtmltopdf [page]   → IronPDF {page}
// wkhtmltopdf [toPage] → IronPDF {total-pages}
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height = 12,  // mm — explicit height control
    HtmlFragment = "<div style='font-size:9px; font-family:Arial; " +
                   "text-align:right; padding:0 10px;'>" +
                   "Acme Corp — Monthly Report</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height = 10,
    HtmlFragment = "<div style='font-size:8px; font-family:Arial; text-align:center;'>" +
                   "Page {page} of {total-pages}</div>"
};

using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><p>Document body.</p></body></html>");
pdf.SaveAs("document-with-headers.pdf");

The token syntax change is the most common source of silent header/footer bugs during migration. wkhtmltopdf uses [page] and [toPage]; IronPDF uses {page} and {total-pages}. Old tokens render as literal text in IronPDF output. Full header/footer configuration including DrawDividerLine, explicit Height in mm, and HTML fragment content is in the headers and footers guide.

CSS Compatibility Improvement (wkhtmltopdf → Chromium)

NReco / wkhtmltopdf — CSS Limitations

using NReco.PdfGenerator;

var htmlToPdf = new HtmlToPdfConverter();
htmlToPdf.PageSize = PageSize.A4;

// wkhtmltopdf / QtWebKit CSS limitations:
// - No Flexbox (display: flex does not render correctly)
// - No CSS Grid (display: grid not supported)
// - Limited calc() support
// - Google Fonts CDN loading frequently fails
// - CSS variables (--custom-property) not supported
// - SVG rendering is incomplete for complex SVGs
// - position: sticky not supported

// Teams using wkhtmltopdf often maintain two CSS stylesheets:
// one for browser preview and one for PDF output
// The PDF CSS avoids Flexbox/Grid and uses float-based layouts

string html = @"
<!DOCTYPE html>
<html>
<head>
<style>
  /* Float-based layout — required for wkhtmltopdf compatibility */
  .container { overflow: hidden; }
  .col-left  { float: left;  width: 60%; }
  .col-right { float: right; width: 40%; }
  .clearfix::after { content: ''; display: table; clear: both; }
  /* Cannot use: display: flex, display: grid, var(--color), Google Fonts @import */
</style>
</head>
<body>
  <div class='container clearfix'>
    <div class='col-left'><p>Left column content</p></div>
    <div class='col-right'><p>Right column content</p></div>
  </div>
</body>
</html>";

byte[] pdfBytes = htmlToPdf.GeneratePdf(html);

Concrete constraints:

  • Float-based layouts in wkhtmltopdf templates should be replaced with Flexbox or Grid when migrating — Chromium supports both fully.
  • Google Fonts and CDN-hosted fonts can be used with IronPDF. Remove base64 font workarounds added specifically for wkhtmltopdf compatibility.
  • CSS variables (--color, --spacing) work correctly in Chromium. Remove any workarounds that expanded CSS variables to hard-coded values.
  • JavaScript-rendered content is fully supported in Chromium with appropriate WaitFor configuration. Remove --enable-javascript --javascript-delay wkhtmltopdf flags and configure RenderingOptions.WaitFor instead.

IronPDF — Modern CSS Without Restrictions

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;

// Chromium supports all modern CSS — no workarounds needed
string html = @"
<!DOCTYPE html>
<html>
<head>
<style>
  /* Full Flexbox support — replace float-based layouts */
  .container { display: flex; gap: 20px; }
  .col-left  { flex: 3; }
  .col-right { flex: 2; }
  /* CSS variables work correctly */
  :root { --primary: #1a73e8; }
  h1 { color: var(--primary); }
</style>
</head>
<body>
  <div class='container'>
    <div class='col-left'><p>Left column content</p></div>
    <div class='col-right'><p>Right column content</p></div>
  </div>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("modern-layout.pdf");

Migrating from wkhtmltopdf to Chromium allows HTML templates to be simplified — float-based fallbacks replaced by Flexbox, base64 font workarounds removed, CSS variables enabled. The responsive CSS guide covers Chromium's layout behavior and print media query support.

Async Rendering in ASP.NET Core

NReco PDF Generator — Synchronous in ASP.NET Core

using NReco.PdfGenerator;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("documents")] public class DocumentController : ControllerBase { [HttpGet("{id}/pdf")] public async Task GetDocument(int id) { string html = await BuildHtmlAsync(id);

// HtmlToPdfConverter.GeneratePdf() is synchronous — spawns subprocess // Must be wrapped in Task.Run() to avoid blocking the ASP.NET Core thread pool var htmlToPdf = new HtmlToPdfConverter { PageSize = PageSize.A4 }; byte[] pdfBytes = await Task.Run(() => htmlToPdf.GeneratePdf(html));

return File(pdfBytes, "application/pdf", $"document-{id}.pdf"); }

private Task BuildHtmlAsync(int id) => Task.FromResult($"

Document {id}

"); }

Concrete constraints:

  • GeneratePdf() is synchronous and blocks the calling thread until the wkhtmltopdf process completes. Using it directly in an async action blocks a thread pool thread.
  • Task.Run() moves the blocking work off the request thread but still consumes a thread pool thread for the duration. Under high concurrency this creates thread pool pressure.
  • Each concurrent request spawns a new wkhtmltopdf process — process startup overhead compounds at scale.

IronPDF — Async ASP.NET Core

using IronPdf;
using Microsoft.AspNetCore.Mvc;

[ApiController] [Route("documents")] public class DocumentController : ControllerBase { private readonly ChromePdfRenderer _renderer;

public DocumentController(ChromePdfRenderer renderer) { _renderer = renderer; }

[HttpGet("{id}/pdf")] public async Task GetDocument(int id) { string html = await BuildHtmlAsync(id);

// RenderHtmlAsPdfAsync — genuinely async, no Task.Run() wrapper needed using var pdf = await _renderer.RenderHtmlAsPdfAsync(html);

return File(pdf.BinaryData, "application/pdf", $"document-{id}.pdf"); }

private Task BuildHtmlAsync(int id) => Task.FromResult($"

Document {id}

"); } ```

Task.Run(() => htmlToPdf.GeneratePdf(...)) is replaced by await renderer.RenderHtmlAsPdfAsync(...). No subprocess spawn, no Task.Run(), no thread pool pressure. The async rendering guide covers concurrent rendering and batch generation patterns.

Breaking Changes & Gotchas

  • Header/footer token syntax: wkhtmltopdf uses [page] and [toPage]. IronPDF uses {page} and {total-pages}. This is a silent rendering bug — old tokens render as literal text without error.
  • Return type change — byte[] to PdfDocument: GeneratePdf() returns byte[] directly. IronPDF returns PdfDocument, which implements IDisposable. Every call site must be updated to access pdf.BinaryData for bytes and every PdfDocument must be in a using block.
  • CSS Flexbox / Grid now supported: Templates that used float-based layouts to work around wkhtmltopdf's Flexbox limitation can be updated to use Flexbox or Grid. This is an improvement but may require template review to ensure layouts are correct in Chromium.
  • Web fonts now work reliably: CDN-hosted Google Fonts and other web fonts that were blocked in wkhtmltopdf load correctly in Chromium. Remove base64 font inlining workarounds if they were added specifically for wkhtmltopdf.
  • CustomWkHtmlArgs removed: Every custom wkhtmltopdf flag in CustomWkHtmlArgs must be individually evaluated. Most flags have RenderingOptions equivalents or are no longer needed because Chromium's defaults are more capable.
  • No subprocess management needed: wkhtmltopdf's subprocess spawn, temp file cleanup, and process timeout considerations are all eliminated. Remove any Task.Run() wrappers around GeneratePdf() calls.
  • PdfDocument is IDisposable: NReco returns byte[] — no disposal. IronPDF returns PdfDocument, which must be in a using block.
  • Namespace change: Remove using NReco.PdfGenerator;. Replace with using IronPdf;.
  • License key required: NReco PDF Generator was free to use. IronPDF requires IronPdf.License.LicenseKey at startup.
  • wkhtmltopdf binary removal: Remove the wkhtmltopdf binary from the deployment package, Docker images, and CI/CD artifact steps. On Linux, add Chromium system library packages to the container image.

Migration Checklist

  1. Audit all HtmlToPdfConverter call sites: List every instantiation, its PageSize/Margins/Orientation configuration, PageHeaderHtml, PageFooterHtml, and any CustomWkHtmlArgs flags. The CustomWkHtmlArgs flags require individual evaluation.
  2. Update HTML templates for Chromium compatibility: Review each template for float-based layout workarounds (now replaceable with Flexbox), base64 font inlining (now removable), CSS variable workarounds (now removable), and any JS delay tuning.
  3. Install IronPDF via NuGet: dotnet add package IronPdf. Retain NReco references until replacement code compiles and tests pass.
  4. Configure the license key at startup: Set IronPdf.License.LicenseKey = "YOUR-KEY"; in Program.cs. See the license setup guide.
  5. Register ChromePdfRenderer in DI: Add builder.Services.AddSingleton<ChromePdfRenderer>() with RenderingOptions configured once.
  6. Update namespaces: Remove using NReco.PdfGenerator;. Replace with using IronPdf;.
  7. Replace GeneratePdf(html) calls: Map each to renderer.RenderHtmlAsPdf(html). Add using blocks around PdfDocument. Access bytes via pdf.BinaryData.
  8. Update header/footer token syntax: Replace [page] with {page} and [toPage] with {total-pages} in all header/footer HTML strings.
  9. Map CustomWkHtmlArgs flags: For each flag, find the RenderingOptions equivalent or confirm it is no longer needed. Common mappings: --javascript-delay n → WaitFor.RenderDelay(ms), --disable-smart-shrinking → not needed in Chromium.
  10. Remove Task.Run() wrappers: Replace await Task.Run(() => htmlToPdf.GeneratePdf(...)) with await renderer.RenderHtmlAsPdfAsync(...).
  11. Remove wkhtmltopdf binary: Remove the wkhtmltopdf binary from all deployment artifacts, Docker images, and CI/CD build steps. On Linux, add Chromium system library packages.
  12. Remove NReco NuGet reference: Once all replacements compile and tests pass, remove NReco.PdfGenerator from the project.

Conclusion

When staying on NReco PDF Generator is technically reasonable

NReco PDF Generator is effectively discontinued, which significantly reduces the arguments for retention. The only scenario where continued use might be considered is when the application is in full maintenance mode with no new PDF requirements, no active CSS template maintenance, and no plans to update to modern .NET runtimes. For any application with ongoing development, the combination of discontinued status, wkhtmltopdf's CSS limitations, and the subprocess architecture presents accumulating technical debt.

Signals that indicate migration is worth the engineering effort

Migration is worth scoping immediately for any application actively developing new document templates, given that wkhtmltopdf's CSS limitations are incompatible with modern front-end tooling. The discontinued status removes the option of waiting for upstream fixes. Additionally: when float-based CSS workarounds are complicating template maintenance; when web font loading failures are causing production incidents; when JavaScript-rendered content is unreliable in wkhtmltopdf; when async rendering under concurrent load is creating thread pool pressure; or when post-render operations require an additional library.

What the cutover typically involves at the code level

The API swap is minimal — NReco PDF Generator's surface area is small. The primary work is: adding using blocks to all render results, updating header/footer token syntax, evaluating CustomWkHtmlArgs flags, removing Task.Run() wrappers, and removing the wkhtmltopdf binary from the deployment. The secondary work is HTML template review — taking advantage of Chromium's CSS capabilities to simplify layouts that were built around wkhtmltopdf's limitations. Teams often find that the template simplification produces cleaner, more maintainable templates as a side effect of the migration.

In your current NReco integration, how many CSS workarounds — float-based layouts, base64 fonts, suppressed CSS3 features — are in the templates specifically to accommodate wkhtmltopdf, and how much template maintenance time would be recovered by removing them?
