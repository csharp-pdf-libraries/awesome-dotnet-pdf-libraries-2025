Rotativa vs IronPDF: what the docs do not cover

what the docs do not cover

Problem Framing

ASP.NET MVC introduced a natural question early in its lifecycle: if views already produce HTML, why can't the same view produce a PDF? Rotativa was the answer that most MVC teams reached for. It leverages wkhtmltopdf to convert the rendered output of an MVC action or Razor view directly to a PDF response, using the ActionResult pattern developers already knew. The model is intuitive—return a ViewAsPdf instead of a View, and the framework handles the rest.

The appeal is significant: no separate templating system, no HTML assembly code, no intermediate file. The Razor view that produces the HTML response can also produce the PDF response with a single line change. For teams on ASP.NET MVC with simple document requirements, this elegance is genuinely useful. The friction appears later, when the CSS in the view relies on Flexbox or Grid that wkhtmltopdf cannot render, when the application migrates to ASP.NET Core and the MVC integration layer no longer applies cleanly, or when the PDF byte array needs to be merged, encrypted, or signed before being sent to the client.

Understanding Rotativa requires understanding the two layers it wraps: the wkhtmltopdf rendering engine (which determines what CSS and JavaScript the output can contain) and the MVC ActionResult abstraction (which determines where in the request pipeline the conversion happens). Both layers have constraints that the quick-start README does not surface. This article covers what happens after the happy path.

What Rotativa Is Designed To Do

Rotativa is an open-source .NET library that converts ASP.NET MVC Razor views to PDF documents using the wkhtmltopdf native library. The primary API is a set of ActionResult-derived classes: ViewAsPdf (renders a named view to PDF), PartialViewAsPdf (renders a partial view), and UrlAsPdf (fetches a URL and converts the response). These action results are returned directly from MVC controller actions; the framework renders the view, pipes the HTML to wkhtmltopdf, captures the PDF output, and streams it as the HTTP response.

Rotativa targets ASP.NET MVC (Rotativa) and ASP.NET Core (Rotativa.AspNetCore—a separate package). The library bundles platform-specific wkhtmltopdf binaries for Windows and Linux; macOS binary inclusion varies by version. Configuration mirrors wkhtmltopdf's command-line API: paper size, orientation, margins, header and footer HTML, JavaScript enable/disable, and custom wkhtmltopdf arguments. The output is a PDF byte stream served as an HTTP response or, for non-HTTP contexts, returned as a byte[]. Rotativa does not provide PDF manipulation: there is no merge, encrypt, sign, form-fill, or extract API. The PDF is a terminal output from the rendering pipeline.

Rotativa.AspNetCore (the Core variant) requires additional configuration for the binary path because the embedded binary path conventions changed between MVC and Core. Teams migrating from MVC to Core frequently encounter this as an integration friction point.

The wkhtmltopdf engine that Rotativa wraps has a well-documented rendering history: it was among the first widely accessible HTML-to-PDF tools for server-side .NET, and it enabled a generation of MVC applications to add PDF export with minimal effort. The trade-off was always rendering fidelity—wkhtmltopdf froze its WebKit version at a point where CSS Flexbox and Grid were either not implemented or only partially available. Applications built in that era used table-based layouts for PDF templates specifically because that was what the engine could handle. Those constraints are still in effect; the engine has not been updated to support the CSS that modern .NET web applications take for granted.

What IronPDF Is Designed To Do

IronPDF is a commercial .NET library for PDF generation and manipulation. It is not MVC-specific and does not integrate with the ActionResult pipeline—it is an in-process library that accepts HTML strings, file paths, or URLs and returns a PdfDocument object. In ASP.NET Core, the typical pattern is to render a Razor view to an HTML string via IViewRenderService (or equivalent), pass that string to ChromePdfRenderer.RenderHtmlAsPdfAsync(), and return the PdfDocument.BinaryData as a FileContentResult.

The rendering engine is Chromium rather than wkhtmltopdf. The HTML string to PDF guide documents the primary API; the resulting PdfDocument supports merge, split, encrypt, sign, annotate, form-fill, and text extraction without requiring a second library. ChromePdfRenderer is thread-safe and can serve concurrent requests; PdfDocument implements IDisposable. IronPDF targets .NET Framework 4.x and .NET 6+ on Windows, Linux, and macOS, distributed as a NuGet package with platform-native Chromium binaries resolved at restore time.

Key Limitations of Rotativa

Product Status

Rotativa is an open-source community project. The core Rotativa package (for classic MVC) has not received active updates in several years; Rotativa.AspNetCore is more recently maintained. Verify current maintenance activity at the respective GitHub repositories. The wkhtmltopdf version bundled in the NuGet package is fixed; rendering engine updates require a new package release from the maintainer. This means that CSS rendering capabilities are frozen at whatever wkhtmltopdf version was current when the package was last updated—there is no mechanism for the application to adopt a newer rendering engine without changing the library.

Missing Capabilities

Rotativa converts views to PDF byte streams. It provides no API for reading existing PDFs, merging documents, encrypting output, applying digital signatures, filling form fields, extracting text or images, or applying watermarks. Any post-generation operation requires a second library. Additionally, Rotativa is MVC-specific—it has no use case outside an ASP.NET MVC or Core HTTP request pipeline. Applications that generate PDFs in background jobs, console applications, worker services, or Azure Functions cannot use Rotativa's ActionResult model without significant architectural changes that effectively replicate what IViewRenderService does anyway.

The absence of a manipulation API is particularly consequential for compliance-driven workflows. An invoice that must be digitally signed before delivery, a contract that must be encrypted with a per-recipient key, or a report that must be merged with a cover page and then watermarked all require Rotativa to be paired with one or more additional libraries. Each additional library adds a dependency to manage, a disposal pattern to implement correctly, and an error model to integrate.

Technical Constraints

The wkhtmltopdf rendering engine does not support CSS Grid or Flexbox. JavaScript execution is limited to what wkhtmltopdf's WebKit engine provides; async-rendered content is frequently not captured. Header and footer HTML in Rotativa is configured via HeaderText, FooterText, and related properties—or via a separate URL whose HTML is fetched by wkhtmltopdf, requiring the application to serve that URL. This additional HTTP dependency (wkhtmltopdf fetching the header/footer URL from the same application) creates request-within-request complexity in development environments and a potential failure point in Docker environments where the application may not be accessible from within the wkhtmltopdf process's network namespace.

Under concurrent ASP.NET Core request load, the wkhtmltopdf native library's threading model limits throughput. The SynchronizedConverter approach (serialising calls) is the common mitigation but creates a request queue under load. Applications that generate PDFs as part of high-throughput request handlers—report exports, bulk invoice generation—encounter this ceiling under real load conditions that are difficult to reproduce in development. Verify current concurrency handling in the Rotativa.AspNetCore package.

Support Model

Support is community-driven via GitHub Issues. There is no commercial support tier. Rendering issues that originate in wkhtmltopdf behaviour—rather than the Rotativa wrapper—cannot be resolved through Rotativa alone; the wkhtmltopdf project itself is largely dormant, which means CSS rendering bugs have no upstream fix path.

Architectural Fit

Rotativa is architecturally well-suited for classic ASP.NET MVC applications with stable, simple Razor view templates whose CSS is compatible with wkhtmltopdf, where PDF generation only occurs in HTTP request handlers, and where post-generation manipulation is not required. It is a poor fit for ASP.NET Core applications that have migrated from MVC (the Core variant has additional setup friction), applications using modern CSS frameworks or component libraries built on Flexbox, background PDF generation workloads, and any workflow that needs to manipulate the generated PDF before serving it.

The most precise description of Rotativa's architectural fit is: it is the right tool for an application that existed in the MVC era, used table-based CSS layouts, and has not changed its PDF requirements since then. It is the wrong tool for a greenfield application in 2025 that wants to use the same CSS frameworks its web views use.

Operation Comparisons

Razor View to PDF in ASP.NET MVC

Rotativa — View to PDF Action Result:

// Rotativa ViewAsPdf — classic ASP.NET MVC
// Package: Rotativa (NuGet)
using Rotativa;
using Rotativa.Options;
using System.Web.Mvc;

public class InvoiceController : Controller
{
    // GET /invoice/download/42
    public ActionResult Download(int id)
    {
        var invoice = _invoiceService.GetInvoice(id);

        // ViewData or model passed to the Razor view exactly as with a normal View()
        // wkhtmltopdf renders the view HTML and returns PDF bytes as the response
        return new ViewAsPdf("InvoiceTemplate", invoice)
        {
            FileName = $"Invoice-{id}.pdf",
            PageSize = Size.A4,
            PageOrientation = Orientation.Portrait,
            Margins = new Margins(15, 15, 15, 15), // top, right, bottom, left (mm)
            // wkhtmltopdf constraint: CSS Grid/Flexbox in InvoiceTemplate.cshtml
            // will NOT render correctly
        };
    }
}

Technical constraints:

  • The Razor view is rendered by the MVC pipeline before being passed to wkhtmltopdf; view rendering is subject to the full MVC pipeline including layout, partial views, and @Html helpers
  • CSS in the view or its layout that uses Grid, Flexbox, or CSS custom properties will produce incorrect output
  • The FileName property sets the Content-Disposition header for download; for inline display omit it
  • wkhtmltopdf fetches external resources (stylesheets, images) from the URL; in development environments this requires the dev server to be accessible
  • The resulting ActionResult cannot be manipulated before being sent; if encrypt or merge is needed, a different approach is required

IronPDF — Razor View to PDF in ASP.NET Core:

using IronPdf;
using Microsoft.AspNetCore.Mvc;

// IViewRenderService renders Razor to HTML string — IronPDF converts it to PDF
// This approach works in HTTP handlers, background jobs, and console apps equally
[ApiController]
[Route("invoice")]
public class InvoiceController : ControllerBase
{
    private readonly IViewRenderService _viewRenderer;
    private static readonly ChromePdfRenderer Renderer = new ChromePdfRenderer();

    public InvoiceController(IViewRenderService viewRenderer)
    {
        _viewRenderer = viewRenderer;
        Renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
        Renderer.RenderingOptions.MarginTop = 15;
        Renderer.RenderingOptions.MarginBottom = 15;
        Renderer.RenderingOptions.CssMediaType = IronPdf.Rendering.PdfCssMediaType.Print;
    }

[HttpGet("download/{id}")] public async Task Download(int id) { var invoice = await _invoiceService.GetInvoiceAsync(id);

// Render Razor to HTML string — full CSS3 support in Chromium string html = await _viewRenderer.RenderToStringAsync("InvoiceTemplate", invoice);

// In-process Chromium render — no wkhtmltopdf binary needed using var pdf = await Renderer.RenderHtmlAsPdfAsync(html);

return File(pdf.BinaryData, "application/pdf", $"Invoice-{id}.pdf"); } }

The IViewRenderService pattern for rendering Razor views to strings is well-documented for ASP.NET Core; the resulting HTML string is then passed to IronPDF's HTML string to PDF guide rendering path. Because the HTML string is an in-memory value, Chromium does not need to fetch it over a network request—eliminating the request-within-request complication that affects Rotativa's header/footer URL model.

Adding Headers and Footers

Rotativa — Headers and Footers:

// Rotativa header/footer configuration
using Rotativa;

// Option 1: Simple text tokens
return new ViewAsPdf("ReportView", model)
{
    PageSize = Rotativa.Options.Size.A4,
    // wkhtmltopdf token syntax
    HeaderText = "Company Name | Confidential",
    FooterText = "Page [page] of [toPage]",
    FooterFontSize = 8,
    FooterTextCenter = "Page [page] of [toPage]"
};

// Option 2: HTML header from a URL — wkhtmltopdf fetches this URL
// return new ViewAsPdf("ReportView", model)
// {
//     HeaderUrl = Url.Action("HeaderPartial", "Pdf", null, Request.Scheme)
// };

Technical constraints:

  • HeaderUrl requires wkhtmltopdf to make an additional HTTP request to the specified URL at render time; in development environments this requires the application to be listening on the expected host/port from wkhtmltopdf's perspective
  • Text token syntax ([page], [toPage]) is wkhtmltopdf-specific and does not correspond to any standard
  • HTML headers defined via HeaderUrl render in the same limited wkhtmltopdf engine; modern CSS in headers is equally constrained
  • Rotativa.AspNetCore header/footer configuration may differ from classic Rotativa

IronPDF — Headers and Footers:

using IronPdf;
using IronPdf.Engines.Chrome;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Text footer with standard IronPDF tokens
renderer.RenderingOptions.TextFooter = new TextHeaderFooter
{
    RightText = "Page {page} of {total-pages}",
    LeftText = "Confidential",
    FontSize = 8,
    DrawDividerLine = true
};

// HTML header with full CSS3 support — no URL request needed
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    HtmlFragment = @"<div style='font-family:Arial;font-size:10px;
                     display:flex;justify-content:space-between;
                     border-bottom:1px solid #ccc;padding-bottom:4px;'>
                     <span>Company Name</span>
                     <span>{date}</span></div>"
};

string html = await _viewRenderer.RenderToStringAsync("ReportView", model);
using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("report.pdf");

IronPDF's HTML headers accept inline HTML fragments without requiring a separate HTTP endpoint. The headers and footers guide documents both text-based and HTML-based variants, the full token reference, and first-page suppression for cover page scenarios.

Generating PDF in a Background Worker (Non-HTTP Context)

Rotativa — Background Worker:

Rotativa's ViewAsPdf requires an MVC ControllerContext to render the Razor view. Outside of an HTTP request handler—in a background worker, a IHostedService, or a console application—the ControllerContext is not available and Rotativa cannot render views.

// Rotativa cannot be used outside an HTTP request handler.
// ViewAsPdf requires ControllerContext which is only available during an HTTP request.
// For background PDF generation, a different approach is required:
// Option 1: Use a separate HTML templating engine (Razor outside MVC, Scriban, etc.)
//           to produce an HTML string, then pass it to wkhtmltopdf directly.
// Option 2: Use a library that is not bound to the HTTP request pipeline.

Technical constraints:

  • No ControllerContext available outside HTTP request handlers
  • No documented API for generating PDFs from arbitrary HTML strings outside the ActionResult model
  • Background job PDF generation requires replacing Rotativa with a different library or a direct wkhtmltopdf invocation

IronPDF — Background Worker PDF Generation:

using IronPdf;
using Microsoft.Extensions.Hosting;
using System.Threading;
using System.Threading.Tasks;

public class ReportGenerationWorker : BackgroundService
{
    // ChromePdfRenderer is thread-safe and safe to share
    private static readonly ChromePdfRenderer Renderer = new ChromePdfRenderer();

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            // Fetch pending report requests from a queue
            var requests = await _reportQueue.DequeueAsync(stoppingToken);

            foreach (var request in requests)
            {
                // Template rendering using any approach — not tied to MVC
                string html = _templateEngine.Render("MonthlyReport", request.Data);

                // In-process Chromium render — no HTTP context required
                using var pdf = await Renderer.RenderHtmlAsPdfAsync(html);

                // Encrypt before saving
                pdf.SecuritySettings.OwnerPassword = "ownerPass";
                await _fileStorage.SaveAsync(
                    $"reports/{request.Id}.pdf",
                    pdf.BinaryData,
                    stoppingToken);
            }

            await Task.Delay(TimeSpan.FromSeconds(30), stoppingToken);
        }
    }
}

IronPDF has no dependency on the HTTP request pipeline. The async rendering guide covers RenderHtmlAsPdfAsync() and its integration with .NET's async model. The same ChromePdfRenderer instance can serve both HTTP request handlers and background workers concurrently, with no synchronisation required from the application side.

Applying Encryption After Generation

Rotativa — Post-Generation Encryption:

Rotativa returns a byte[] from the ExecuteResult method. Encryption requires passing that byte array to a separate library. In the ActionResult model, this interception point requires either subclassing ViewAsPdf or switching to a service-based approach outside the action result pattern.

// Rotativa has no encrypt API.
// One workaround: use ViewAsPdf.BuildFile() to get the byte[] in-controller,
// then pass to a second library before returning the FileContentResult.

// using Rotativa;
// var pdfBytes = new ViewAsPdf("InvoiceTemplate", model).BuildFile(ControllerContext);
// var encryptedBytes = SomeOtherLibrary.Encrypt(pdfBytes, "password");
// return File(encryptedBytes, "application/pdf", "invoice.pdf");

Technical constraints:

  • BuildFile() method availability and exact signature
  • Introduces a second library with its own API and disposal requirements
  • Each additional post-generation step (encrypt, watermark, merge) compounds the dependency count

IronPDF — Inline Encryption:

using IronPdf;

string html = await _viewRenderer.RenderToStringAsync("InvoiceTemplate", model);

var renderer = new ChromePdfRenderer();
using var pdf = await renderer.RenderHtmlAsPdfAsync(html);

// Encryption on the same PdfDocument object — no second library
pdf.SecuritySettings.OwnerPassword = "ownerSecret";
pdf.SecuritySettings.UserPassword = "userReadKey";
pdf.SecuritySettings.AllowUserPrint = true;
pdf.SecuritySettings.AllowUserCopyPasteContent = false;

return File(pdf.BinaryData, "application/pdf", "invoice.pdf");

The passwords and permissions guide documents the full permission flag set. The encryption applies to the same PdfDocument returned by the renderer—no byte array handoff to a second library is required.

Commonly Reported Limitations

  • CSS Grid and Flexbox failures. The wkhtmltopdf engine does not render modern CSS layout features. Views that use Bootstrap 4/5 Flexbox utilities, CSS Grid layouts, or CSS custom properties produce incorrect output—elements collapse, overlap, or disappear. This is the most commonly reported friction point for teams that upgrade their CSS frameworks while keeping Rotativa. The failure mode is typically silent layout corruption rather than an exception, which means it may not surface during automated tests that check for PDF generation success rather than visual correctness.
  • Rotativa.AspNetCore setup complexity. The original Rotativa was designed for classic MVC. The Core variant requires configuring the wkhtmltopdf binary path explicitly because the conventions for embedded native resources changed between frameworks. Teams migrating MVC applications to ASP.NET Core often spend significant time reconfiguring the binary path before rendering works. The RotativaConfiguration.Setup() call and the binary path resolution differ between local development, Docker containers, and cloud deployment targets.
  • Header/footer URL dependency. When HTML-based headers or footers are used, wkhtmltopdf fetches the header URL as a separate HTTP request. In environments where the application is not accessible on localhost (Docker networking, reverse proxies, integration test hosts), this fetch fails silently, producing PDFs with missing headers. This is a non-obvious failure mode that appears only in certain deployment configurations and can be difficult to reproduce outside that environment.
  • Non-HTTP context limitation. Rotativa's ViewAsPdf requires a ControllerContext. Background jobs, hosted services, console utilities, Azure Functions, and scheduled tasks cannot use Rotativa. Teams that initially implement PDF generation only in HTTP handlers and later need to move that logic to a background worker discover this architectural constraint at migration time. The workaround—maintaining a service that initiates an HTTP request to the MVC endpoint solely to trigger PDF generation—is architecturally unsound.
  • byte[] output with no manipulation API. The final output is bytes. Merging a generated invoice with a cover page, encrypting before delivery, or signing for compliance all require a second library and an additional integration layer. Each additional requirement compounds the multi-library overhead. Teams often end up with Rotativa (generation) + iTextSharp (merge/sign) + another library (encrypt), each with different APIs, licensing models, and maintenance trajectories.

Conclusion

When staying on Rotativa is technically reasonable

Rotativa is appropriate for classic ASP.NET MVC applications with stable, simple Razor view templates whose CSS is fully compatible with wkhtmltopdf, where PDF generation occurs only in HTTP request handlers, and where post-generation manipulation is not required. For teams that have been using Rotativa successfully for years on MVC and whose requirements have not changed, the migration cost to a different library is hard to justify solely on the basis of CSS engine modernity.

When migration becomes a capability or architectural mismatch

Migration is forced by any of four events: the CSS templates adopt modern layout features (Grid, Flexbox, component libraries built on them), the application migrates from classic MVC to ASP.NET Core and the Core variant introduces setup friction, PDF generation needs to happen in a background job or hosted service outside the HTTP pipeline, or the workflow requires post-generation operations (encrypt, sign, merge) that necessitate a second library.

How IronPDF approaches the same problem differently

IronPDF is not an MVC-specific library. HTML input comes from wherever the application produces it—Razor rendered to a string, a template engine, a StringBuilder, or any other source. The Chromium engine handles the full CSS3 feature set. The PdfDocument result carries a complete manipulation API, so generation, encryption, signing, and merging happen in one library without an intermediate byte array handoff. The HTML string to PDF guide documents the decoupled rendering path that works in HTTP handlers and background workers equally.
