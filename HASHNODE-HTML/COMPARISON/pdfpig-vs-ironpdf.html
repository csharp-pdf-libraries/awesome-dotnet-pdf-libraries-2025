PdfPig vs IronPDF: what changes when you switch

a technical comparison for modern .NET teams (2026)

Problem Framing

PDF processing in .NET splits along a fundamental axis: reading and extracting versus generating and manipulating. Libraries that excel at one end of this axis are often limited or absent at the other. This matters because application requirements frequently start on one side and migrate toward the other—a data pipeline that initially only extracts text from uploaded PDFs may later need to annotate, redact, or re-export those documents.

PdfPig is a read-oriented open-source .NET library. Its design prioritises accurate text extraction with positional data, PDF object model access, and document inspection. It does not generate PDFs from HTML or provide a high-level manipulation API. For teams with pure read workloads—indexing, classification, extraction, OCR preprocessing—it provides a well-documented, permissively licensed, managed .NET option that avoids native binary dependencies. For teams whose requirements include any generation or post-read manipulation, a different library is required.

The evaluation framework for this comparison should be: what is the dominant operation in the pipeline? If it is reading existing PDFs for content extraction, PdfPig is a technically sound choice. If it is generating PDFs from application data—or a mix of both—understanding the architectural separation between read-only and write-capable libraries prevents later refactoring. The architectural cost of discovering this boundary after committing to a read-only library is non-trivial: the team must either add a second library with a different object model and disposal lifecycle, or migrate the entire PDF integration to a library that covers both directions. Neither path is free, and neither is as frictionless as choosing the right scope at the outset.

It is also worth noting that PdfPig's commitment to being a managed-only, no-native-binary library is a deliberate design choice that has deployment advantages in some environments. Container images that avoid native binary dependencies are smaller and easier to audit. Applications with strict AppSec policies around native code execution may prefer a pure managed library for read workloads. Understanding this design intent helps set realistic expectations about where PdfPig's boundaries are and why they exist.

What PdfPig Is Designed To Do

PdfPig is an open-source .NET library (Apache 2.0 license) for reading and extracting content from PDF documents. It provides managed C# APIs for opening PDF files, iterating pages, extracting text with positional (x, y, width, height) and font metadata, extracting embedded images, reading document structure (bookmarks, metadata, annotations), querying the PDF object model at a low level, and inspecting font resources. PdfPig is a fully managed assembly with no native binary dependencies; it implements PDF parsing and rendering in C# without P/Invoke.

The library targets .NET Standard 2.0, which gives it compatibility with .NET Framework 4.6.1+, .NET Core 2.0+, and .NET 5+. It is distributed via NuGet as UglyToad.PdfPig. PdfPig does not generate PDFs from HTML, does not create new PDF documents from scratch, and does not provide document manipulation operations (merge, encrypt, sign, form fill, annotate). It is a reader and inspector. The library is community-maintained on GitHub.

PdfPig's text extraction model is one of its distinguishing features relative to many .NET PDF libraries. Rather than returning a flat string, it provides structured access at the word, character, and glyph level—each word carries its bounding box in the PDF coordinate space, its font name and size, the writing direction, and confidence information. This makes PdfPig particularly useful for applications that need to reconstruct document structure from extracted content: table detection algorithms, reading order reconstruction for multi-column layouts, data extraction from form-like documents, and training datasets for machine learning models. For search indexing pipelines that need only the text string, the positional model is surplus to requirements; for layout analysis pipelines, it is the primary value.

The library also exposes the raw PDF object model—cross-reference tables, object streams, content streams, and resource dictionaries—which allows applications that need deep PDF parsing to access the underlying structure. This is unusual for .NET PDF libraries, most of which hide the object model behind a higher-level API. For forensic analysis, format validation, or custom extraction tasks where standard APIs fall short, this low-level access is a meaningful capability.

What IronPDF Is Designed To Do

IronPDF is a commercial .NET library that approaches PDF from the generation and manipulation direction. The ChromePdfRenderer accepts HTML strings, file paths, and URLs and converts them to PdfDocument objects using a bundled Chromium engine. The same PdfDocument object supports text extraction, image extraction, merge, split, encrypt, sign, annotate, stamp, form-fill, and format conversion. Disposal follows standard .NET patterns: PdfDocument implements IDisposable, ChromePdfRenderer is thread-safe.

The extract text and images guide documents both text and image extraction. For read-oriented workflows, IronPDF loads existing PDFs via PdfDocument.FromFile() and exposes the same extraction API regardless of whether the document was rendered by IronPDF or originated from an external source. The PDF to image rasterization guide covers page-level rendering to image formats at configurable DPI. IronPDF targets .NET Framework 4.x and .NET 6+ and ships as a single NuGet package with platform-native Chromium binaries for Windows, Linux, and macOS.

Key Limitations of PdfPig

Product Status

PdfPig is an actively maintained open-source project under the Apache 2.0 license. It receives regular updates from community contributors. The project is independent—not backed by a commercial vendor—which means long-term maintenance depends on community health. Verify recent commit frequency and issue response patterns before adopting for production critical paths.

Missing Capabilities

PdfPig does not generate PDFs. It does not convert HTML to PDF, create new documents from scratch, merge existing PDFs, encrypt documents, apply digital signatures, fill form fields, add annotations, apply watermarks, or perform any write operation on PDF content. It is a reader, and this is by design—the project scope is explicitly limited to extraction and inspection. Applications that start with PdfPig for extraction and later need generation, manipulation, or security operations must adopt a separate library for those capabilities. The two-library pattern (PdfPig for reading, another library for writing) works but creates dual object model surface area and dual disposal patterns to manage.

Additionally, PdfPig does not perform OCR. For scanned PDFs—documents that are image-only, with no embedded text layer—PdfPig extracts nothing useful from the text extraction APIs. Identifying whether a PDF is a scan versus a text-layer document requires inspecting the page content before calling extraction methods. OCR on scanned PDFs requires a separate library entirely (such as IronOCR or Tesseract.NET).

Technical Constraints

PdfPig is a pure managed assembly, which is a deployment advantage. However, text extraction accuracy from complex PDFs—multi-column layouts, rotated text, ligature-heavy fonts, scanned content (which PdfPig cannot read at all)—depends on the PDF's internal structure. PDFs with non-standard encoding or without embedded ToUnicode tables may produce garbled or missing text. Scanned PDFs contain no extractable text; OCR is outside PdfPig's scope. PdfPig does not provide character-level rendering or rasterization; it is not a PDF renderer. PDF rasterization (rendering pages to images) is not a PdfPig capability.

Thread safety for concurrent document reading should be verified in current documentation. The typical pattern—one PdfDocument instance per open document, with access from a single thread—is safe, but sharing a single PdfDocument across concurrent threads requires verification.

Support Model

Support is community-driven via GitHub Issues. There is no commercial support tier, no SLA, and no escalation path for production incidents. For a free open-source library, this is expected; teams should account for self-sufficiency in debugging extraction issues. For production systems where PDF text extraction is on a critical path, the absence of a commercial support model is a risk factor that should be weighed against the zero licensing cost.

Architectural Fit

PdfPig is architecturally well-suited for .NET applications that need accurate text extraction from existing PDFs, content indexing pipelines, document classification systems, and OCR preprocessing workflows where the PDF has a text layer. It is not appropriate as the sole PDF library for applications that generate, manipulate, or write to PDFs in any form. It is also not appropriate for applications that require rasterization (rendering pages to images), which is a common adjacent requirement in document processing pipelines.

Operation Comparisons

Text Extraction with Positional Data

PdfPig — Text Extraction with Positions:

// PdfPig text extraction with positional data
// Package: UglyToad.PdfPig
using UglyToad.PdfPig;
using UglyToad.PdfPig.Content;

// PdfDocument implements IDisposable
using var document = PdfDocument.Open("source.pdf");

Console.WriteLine($"Page count: {document.NumberOfPages}");

// Pages are 1-indexed in PdfPig
for (int pageNum = 1; pageNum <= document.NumberOfPages; pageNum++)
{
    var page = document.GetPage(pageNum);

    // Each word has its bounding box and font information
    foreach (Word word in page.GetWords())
    {
        // BoundingBox gives {X, Y, Width, Height} with bottom-left origin
        Console.WriteLine(
            $"[{word.BoundingBox.Left:F1},{word.BoundingBox.Bottom:F1}] {word.Text}");
    }
}

Technical constraints:

  • PdfPig uses a bottom-left coordinate origin (standard PDF coordinate system); convert to top-left if the downstream system expects that orientation
  • GetWords() uses heuristic word-boundary detection; complex scripts or unusual spacing may produce unexpected word groupings
  • Text from scanned PDFs (image-only content) is not extractable; GetWords() returns empty for pages with no text layer
  • PDFs lacking embedded ToUnicode maps may produce character substitution errors in extracted text
  • Rotated text blocks may have non-intuitive bounding box positions; verify for rotated page PDFs

IronPDF — Text Extraction:

using IronPdf;

// PdfDocument.FromFile loads any PDF; not limited to IronPDF-generated documents
using var pdf = PdfDocument.FromFile("source.pdf");

// Full document text as a single string
string allText = pdf.ExtractAllText();

// Per-page text extraction (zero-indexed)
for (int i = 0; i < pdf.PageCount; i++)
{
    string pageText = pdf.ExtractTextFromPage(i);
    Console.WriteLine($"--- Page {i + 1} ({pageText.Length} chars) ---");
    Console.WriteLine(pageText);
}

IronPDF's text extraction returns strings rather than positional word objects. The extract text and images guide documents both text and embedded image extraction. For workflows that require character-level bounding boxes—layout analysis, table reconstruction—PdfPig's positional model is more granular than IronPDF's string-oriented extraction.

Extracting Embedded Images from a PDF

PdfPig — Image Extraction:

// PdfPig image extraction from existing PDF
using UglyToad.PdfPig;
using UglyToad.PdfPig.Content;
using System.IO;

using var document = PdfDocument.Open("source.pdf");

int imageIndex = 0;
for (int pageNum = 1; pageNum <= document.NumberOfPages; pageNum++)
{
    var page = document.GetPage(pageNum);

    // GetImages() returns IPdfImage objects with raw bytes
    foreach (IPdfImage image in page.GetImages())
    {
        // image.RawBytes contains the compressed image data
        // image.TryGetPng() attempts to decode as PNG
        if (image.TryGetPng(out byte[]? pngBytes) && pngBytes != null)
        {
            File.WriteAllBytes($"extracted_{pageNum}_{imageIndex++}.png", pngBytes);
        }
        else
        {
            // Raw bytes may be in JPEG, JPEG2000, or other formats
            // Verify image format from image.InlineImage / image.RawMemoryPressure
            File.WriteAllBytes($"raw_{pageNum}_{imageIndex++}.bin", image.RawBytes.ToArray());
        }
    }
}

Technical constraints:

  • TryGetPng() may fail for images in formats PdfPig does not decode natively (JPEG2000, JBIG2); raw bytes are available but require separate decoding
  • Image metadata (dimensions, color space, DPI) is available via properties on IPdfImage; verify exact property names in current documentation
  • Inline images and XObject images are both exposed via GetImages() but may behave differently for large documents
  • PdfPig performs no image decompression for formats it does not support; raw bytes must be processed by a separate image library

IronPDF — Image Extraction:

using IronPdf;
using System.IO;

using var pdf = PdfDocument.FromFile("source.pdf");

// Extract all embedded images from the entire document
var images = pdf.ExtractAllImages();

for (int i = 0; i < images.Count; i++)
{
    // Images returned as System.Drawing.Image
    images[i].Save($"extracted_{i}.png",
        System.Drawing.Imaging.ImageFormat.Png);
}

// Per-page image extraction
var pageImages = pdf.ExtractImagesFromPage(0);

The extract text and images guide documents the extraction API for both text and images. The extracted image objects are standard .NET types, simplifying downstream processing without requiring a separate image decoding library.

HTML to PDF (IronPDF Only)

PdfPig has no HTML-to-PDF capability. This operation is included because it represents the most common capability gap that teams encounter when PdfPig's read-only scope no longer covers an expanded requirement.

IronPDF — HTML to PDF with Headers and Footers:

using IronPdf;
using IronPdf.Engines.Chrome;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 20;

// Text-based footer with page number tokens
renderer.RenderingOptions.TextFooter = new TextHeaderFooter
{
    RightText = "Page {page} of {total-pages}",
    FontSize = 8,
    DrawDividerLine = true
};

var html = @"
<!DOCTYPE html><html><head>
<style>
  body { font-family: Arial, sans-serif; font-size: 12px; margin: 20px; }
  h1 { color: #1a3c6e; }
  table { width: 100%; border-collapse: collapse; }
  th { background: #1a3c6e; color: white; padding: 8px; }
  td { padding: 6px; border-bottom: 1px solid #e0e0e0; }
</style></head><body>
<h1>Analysis Report</h1>
<table>
  <tr><th>Metric</th><th>Value</th><th>Status</th></tr>
  <tr><td>Accuracy</td><td>98.2%</td><td>Pass</td></tr>
  <tr><td>Recall</td><td>94.7%</td><td>Pass</td></tr>
</table>
</body></html>";

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("analysis-report.pdf");

The headers and footers guide covers both text-based and HTML-based header/footer variants, the full token reference ({page}, {total-pages}, {date}), and per-page customisation. The same PdfDocument that HTML renders into can then be encrypted, signed, or merged without additional libraries.

Merging and Securing a Document (IronPDF, Not Available in PdfPig)

PdfPig — Merge and Encrypt:

PdfPig provides no merge, encrypt, or sign capability. These operations require a separate library.

// PdfPig has no document merge or encryption API.
// For a workflow that reads content from PDFs and then produces a new,
// combined, secured output, PdfPig alone is insufficient.
// A second library (IronPDF or another manipulation-capable library)
// must handle the write path.

IronPDF — Merge, Encrypt, and Sign in One Library:

using IronPdf;
using IronPdf.Signing;
using System.Linq;

// Extract content from existing PDFs using IronPDF's read API
using var sourceA = PdfDocument.FromFile("report-a.pdf");
using var sourceB = PdfDocument.FromFile("report-b.pdf");

// Merge into a single document
using var merged = PdfDocument.Merge(sourceA, sourceB);

// Apply permissions
merged.SecuritySettings.OwnerPassword = "ownerPass";
merged.SecuritySettings.AllowUserCopyPasteContent = false;

// Digitally sign the merged document
var signature = new PdfSignature("certificate.pfx", "certPass")
{
    SigningReason = "Final report compilation"
};
merged.Sign(signature);

merged.SaveAs("final-report-signed.pdf");

All three operations—merge, encrypt, sign—execute on the same PdfDocument object in one library. The digital signatures guide documents the signing API; the merge guide documents the merge API.

Commonly Reported Limitations

  • Text extraction accuracy on complex PDFs. PdfPig's text extraction is accurate for PDFs with standard encoding and embedded ToUnicode maps. PDFs generated by some older tools, or with custom encoding tables, may produce incorrect Unicode output. Multi-column layouts require post-processing of the extracted word positions to reconstruct reading order. The DefaultPageSegmentationAlgorithm and RecursiveXYCut page segmentation strategies affect how words are grouped into lines and blocks; the right choice depends on the document layout being processed.
  • No generation capability. The most commonly cited limitation in community discussions is the absence of any PDF generation or write capability. Teams that start with PdfPig for extraction and later need to produce PDFs must either adopt a second library or migrate. This is an architectural constraint, not a bug—it is a deliberate scope boundary. The presence of this limitation in issue trackers and community discussions is consistent: it is frequently requested as a feature and consistently declined as out of scope.
  • JPEG2000 and JBIG2 image extraction. Image extraction for PDFs containing JPEG2000 or JBIG2-encoded images may return raw compressed bytes that require a separate image library to decode. The TryGetPng() method returns false for these formats; the raw bytes are accessible but require additional processing. This is a common format encountered in PDFs generated by modern office software and in legal/government document repositories.
  • Scanned PDF limitation. PdfPig cannot extract text from scanned PDFs. This is frequently the first limitation encountered in production document pipelines, where a portion of uploaded documents turn out to be scans. OCR is not in PdfPig's scope; it requires a separate OCR library. Teams building document intake pipelines typically need a scan-detection step before routing to text extraction or OCR paths.
  • Reading order on complex layouts. PdfPig provides word positions but not document reading order. Multi-column layouts, tables, sidebars, and footnotes require the calling application to implement a reading-order algorithm using the bounding box data. Several page segmentation algorithms are available in PdfPig, but no algorithm handles all layout types correctly. Testing against a representative sample of the target document types is essential before deploying to production.
  • Community-only support. There is no commercial support escalation path. For production systems where PDF processing is on a critical path, the community-only support model means debugging unexpected extraction behaviour requires self-sufficiency or community forum engagement. Response time on GitHub Issues depends on community availability and is not guaranteed.

Conclusion

When staying on PdfPig is technically reasonable

PdfPig is technically sound for applications whose PDF operations are entirely read-oriented: text extraction, document inspection, metadata reading, image extraction, and content indexing. The Apache 2.0 license, pure managed assembly, and free distribution make it a low-friction choice for open-source projects, budget-constrained teams, and environments with strict native binary policies. For search indexing pipelines, classification systems, and OCR preprocessing workflows where no write operations are needed, PdfPig provides a well-maintained, accurate extraction library. The character-level positional extraction model is a genuine advantage for layout analysis applications that need to reason about where text sits on the page, not just what the text says.

Teams running PdfPig in container environments benefit from the pure managed assembly model: no platform-native binary to manage, no architecture-specific build matrix to maintain in CI/CD, and a smaller container image footprint compared to libraries that bundle Chromium or other native engines. For read-only workloads at scale, this architectural simplicity is a meaningful operational advantage.

When migration becomes a capability or architectural mismatch

The migration case is binary: any requirement to generate PDFs, manipulate existing PDFs, encrypt, sign, form-fill, or annotate documents is outside PdfPig's scope entirely. There is no configuration or extension point that adds write capability to PdfPig; the application must add a second library. If the read and write operations share the same document pipeline, managing two libraries with different object models and disposal semantics adds overhead that a single comprehensive library avoids.

The scanned-PDF limitation is the other common forcing function. Applications that process arbitrary user-uploaded documents frequently encounter scanned PDFs. Once OCR is required, the pipeline is already using a second library for OCR; if that second library also provides generation and manipulation, the case for PdfPig as a separate extraction layer weakens.

How IronPDF approaches the same problem differently

IronPDF covers both read and write operations in a single library. For read-only workflows that may eventually require write operations, IronPDF provides future flexibility without a library swap. The text extraction API is string-oriented rather than positional—a simplification compared to PdfPig's word-level model. For workflows that genuinely need character-level bounding boxes for layout analysis, PdfPig's extraction model remains more granular; IronPDF's extraction is optimised for retrieving text content rather than spatial layout analysis.

The deployment trade-off is the inverse of PdfPig's advantage: IronPDF bundles a Chromium engine, which adds to the package size and introduces a native binary that must be resolved at restore time. For generation-and-manipulation workloads, this is the expected cost of a modern rendering engine. The extract text and images guide documents IronPDF's extraction capabilities; the merge, encrypt, and sign capabilities cover the write operations that PdfPig cannot provide.

When your PDF processing pipeline encounters a scanned document with no text layer, what is the current downstream behaviour—silent empty-string output, exception, or explicit error routing—and does that behaviour reflect a deliberate architectural decision?
