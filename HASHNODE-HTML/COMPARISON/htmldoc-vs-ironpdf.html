HTMLDOC vs IronPDF: technical depth for .NET decision makers

technical depth for .NET decision makers

Problem Framing

Not every PDF generation requirement calls for a browser-quality rendering engine. Teams working in Unix/Linux environments have long used command-line tools to convert HTML documents to PDF — tools that predate the web platform's rendering complexity and that prioritize simplicity and portability over CSS fidelity. HTMLDOC sits in this category: a C-based command-line program that parses HTML 3.2/4-era markup and produces PDF or PostScript output using its own rendering engine, without a JavaScript runtime, without a browser's CSS layout engine, and without a NuGet package.

The question teams face when they discover HTMLDOC in a legacy pipeline — or evaluate it for a new one — is not whether it works, but whether the HTML subset it supports is sufficient for the application's actual templates. Teams whose documents use tables, basic text formatting, and images may find HTMLDOC adequate. Teams whose templates use CSS Grid, Flexbox, CSS variables, web fonts loaded from URLs, or JavaScript-populated content will find HTMLDOC incapable of rendering those constructs. The rendering engine was written against HTML 3.2/4 and a limited CSS subset; it is not a browser, and its output for modern web CSS is unpredictable.

For .NET applications, HTMLDOC adds another architectural dimension: there is no .NET library or NuGet package. Integration requires launching HTMLDOC as a subprocess via Process.Start(), managing the executable's presence on the host, parsing exit codes, and capturing output. This subprocess model is functional but introduces operational overhead — binary deployment, error propagation through exit codes, and concurrency management — that does not exist with a managed library. The comparison in this article is specifically between HTMLDOC's subprocess integration model and IronPDF's in-process .NET API.

What HTMLDOC Is Designed to Do

HTMLDOC is an open-source (GPL) command-line program and C library for converting HTML documents to PDF (versions 1.1–1.4) and PostScript. It was created by Michael Sweet, also the author of the CUPS print system. HTMLDOC is distributed for Linux, macOS, and Windows; on Linux it is commonly available in distribution package repositories.

HTMLDOC's HTML parser supports HTML 3.2 and a subset of HTML 4. Supported elements include tables, images (JPEG, PNG, GIF), headings, paragraphs, ordered and unordered lists, definition lists, preformatted text, and basic text formatting. CSS support is limited to a subset of inline and embedded styles — background colors, basic font properties, and table borders. CSS layout constructs introduced after HTML 3.2 — Grid, Flexbox, multi-column, CSS transforms, CSS variables — are not supported. There is no JavaScript engine; content that requires JavaScript execution to populate will render as the static DOM state, which for JavaScript-rendered pages typically means empty or incomplete content.

HTMLDOC is invoked via command line: htmldoc [options] file.html -o output.pdf. Options cover paper size (--size), margins (--top, --bottom, --left, --right), page header and footer templates (--header, --footer), encryption (--encryption), and document metadata. The output can be a PDF file, PostScript, or HTML (for table-of-contents generation). HTMLDOC can process multiple HTML files into a single PDF in sequence. It is not a PDF manipulation library — it does not read, merge, sign, encrypt existing PDFs, or fill forms.

What IronPDF Is Designed to Do

IronPDF is a commercial .NET PDF library built on embedded Chromium for HTML-to-PDF generation, distributed as a managed NuGet package targeting .NET Standard 2.0 and above. ChromePdfRenderer accepts HTML strings, HTML files, and URLs and produces PDFs using the full Chromium rendering engine — CSS3, Flexbox, Grid, CSS variables, web fonts, SVG, and JavaScript with configurable wait conditions. No subprocess launch, no binary staging, no exit code parsing. The rendering options guide covers the complete configuration surface.

PdfDocument provides manipulation operations on existing PDFs: text and image extraction, AcroForm reading and filling, form creation, document merge and split, page manipulation, password encryption, digital signatures (PKCS#12 and HSM-backed), PDF/A and PDF/UA compliance output, metadata, watermarks, find-and-replace text, redaction, annotations, bookmarks, compression, and linearization. License initialization is a one-time startup call; see the license setup guide. IronPDF runs on Windows, Linux, macOS, and in Docker containers.

Key Limitations of HTMLDOC

Product Status

HTMLDOC is an active open-source project maintained on GitHub under the GPL license. Development continues, though the pace is slower than commercial library vendors. The core HTML parsing and rendering engine targets HTML 3.2/4 — this is not a version lag but a design scope; HTMLDOC is not evolving toward modern CSS rendering. Verify the current release version and any recent feature additions in the HTMLDOC GitHub repository.

Missing Capabilities

HTMLDOC does not support modern CSS. CSS Grid, Flexbox, CSS variables, CSS custom properties, CSS animations, media queries, and CSS transforms are not supported by HTMLDOC's rendering engine. Web fonts loaded via @font-face from URLs or Google Fonts are not resolved. Any template that relies on these constructs will produce incorrect, incomplete, or garbled output. JavaScript execution is absent — dynamic content that requires a JavaScript runtime to render will appear as the static HTML state or not at all.

HTMLDOC is not a PDF manipulation library. It cannot read, sign, encrypt, merge, or modify existing PDF files. AcroForm filling, digital signatures, PDF/A compliance output, text extraction, redaction, and compression are all absent — these require a separate library if needed.

Technical Constraints

From a .NET application, HTMLDOC is accessed exclusively via subprocess invocation (Process.Start()). The HTMLDOC executable must be present on the host system at a known path — on Linux this may be a package install (apt-get install htmldoc), on Windows it requires the HTMLDOC installer or binary deployment. This binary must be versioned, deployed, and updated separately from the .NET application. Error detection requires checking the process exit code and capturing stderr; HTMLDOC's exit codes are not self-documenting, requiring the operator to consult the HTMLDOC manual for interpretation.

Concurrent PDF generation from multiple ASP.NET Core requests each spawns a separate subprocess. HTMLDOC does not expose a shared in-process rendering context — each conversion is a cold-start subprocess with process startup overhead. Controlling concurrency requires application-level semaphore management, similar to other subprocess-based tools.

Support Model

HTMLDOC is supported through the open-source community — GitHub issues, mailing lists, and community forums. There is no commercial support tier, no SLA, and no guaranteed response time. For production-critical PDF generation pipelines where vendor support is required, HTMLDOC's support model is a significant consideration.

Architectural Fit

HTMLDOC is best suited for simple, structured HTML documents using HTML 3.2/4-era constructs in environments where a browser-quality renderer is not available or desirable — lightweight Linux pipelines, simple document conversion without CSS complexity, and systems where the GPL license is acceptable. It is not suited for templates using modern CSS layout, JavaScript-rendered content, authenticated URL rendering, or any workflow requiring PDF manipulation alongside generation.

Operation Comparisons

HTML File to PDF via Subprocess vs In-Process API

HTMLDOC — HTML File to PDF via Process.Start()

using System.Diagnostics;
using System.IO;

// HTMLDOC — invoke the htmldoc CLI as a subprocess from .NET
// The htmldoc binary must be installed and accessible at the configured path
// On Linux: typically /usr/bin/htmldoc after 'apt-get install htmldoc'
// On Windows: verify install path in official HTMLDOC documentation

string htmldocPath  = "/usr/bin/htmldoc";       // Linux path; Windows path differs
string inputHtml    = "/tmp/invoice.html";       // pre-generated HTML file on disk
string outputPdf    = "/tmp/invoice.pdf";

// HTMLDOC command-line arguments
// --size: paper format (a4, letter, legal)
// --top/--bottom/--left/--right: margins in points or inches
// --header: page header template (. = left empty, t = title, D = date)
// --footer: page footer (/. = page number right)
// --no-title: suppress generated title page
// --quiet: suppress informational messages
string arguments = $"--webpage " +
                   $"--size A4 " +
                   $"--top 1cm --bottom 1cm --left 1cm --right 1cm " +
                   $"--header ... " +    // three chars: left/center/right header slot
                   $"--footer .D/ " +    // date center, page number right
                   $"--no-title " +
                   $"--quiet " +
                   $"-f \"{outputPdf}\" " +
                   $"\"{inputHtml}\"";

var psi = new ProcessStartInfo
{
    FileName               = htmldocPath,
    Arguments              = arguments,
    UseShellExecute        = false,
    RedirectStandardError  = true,
    RedirectStandardOutput = true,
    CreateNoWindow         = true
};

using var process = Process.Start(psi)
    ?? throw new InvalidOperationException("Failed to launch HTMLDOC.");

// HTMLDOC writes errors to stderr, progress to stdout
string errorOutput = await process.StandardError.ReadToEndAsync();
await process.WaitForExitAsync();

// HTMLDOC exit code 0 = success, non-zero = error
// Exact error code meanings require consulting the HTMLDOC manual
if (process.ExitCode != 0)
{
    throw new Exception(
        $"HTMLDOC failed (exit {process.ExitCode}): {errorOutput}");
}

Console.WriteLine($"PDF generated: {outputPdf}");
  • HTMLDOC requires an HTML file on disk — it cannot accept HTML from stdin in typical usage; the HTML must be written to a temporary file before invoking HTMLDOC.
  • --webpage mode treats the HTML as a web page (single document without table-of-contents generation); --book mode is for multi-chapter structured documents.
  • The header/footer template uses a three-character code for left/center/right slots: . (empty), t (title), D (date), / (page number), 1 (page 1), C (chapter title)
  • HTMLDOC does not support CSS Grid, Flexbox, @font-face from URL, CSS variables, or JavaScript — any of these in the HTML file produces undefined output.
  • On Linux Docker images without HTMLDOC installed, apt-get install htmldoc must be added to the Dockerfile; on Windows, the HTMLDOC installer or binary must be staged.
  • Concurrent calls from ASP.NET Core each spawn a new subprocess — manage concurrency with a SemaphoreSlim if needed.

IronPDF — HTML File to PDF

using IronPdf;

// IronPDF — in-process HTML file to PDF, no subprocess
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop    = 10;
renderer.RenderingOptions.MarginBottom = 10;
renderer.RenderingOptions.MarginLeft   = 10;
renderer.RenderingOptions.MarginRight  = 10;

// HTML file rendered in-process via Chromium — full CSS3, Flexbox, Grid supported
using var pdf = await renderer.RenderHtmlFileAsPdfAsync("/tmp/invoice.html");
await System.IO.File.WriteAllBytesAsync("/tmp/invoice.pdf", pdf.BinaryData);

No subprocess, no binary staging, no exit code parsing. Chromium is embedded in the NuGet package. The HTML file to PDF guide covers base URL resolution, resource loading, and all rendering options. Modern CSS Grid, Flexbox, and JavaScript execution are fully supported.

HTML String to PDF

HTMLDOC — HTML String via Temporary File

using System.Diagnostics;
using System.IO;

// HTMLDOC — HTML string to PDF via temporary file
// HTMLDOC does not accept HTML from stdin in typical usage;
// the HTML string must be written to a temp file first

string html = @"
<!DOCTYPE html>
<html>
<head><style>
  body { font-family: Helvetica; font-size: 11pt; }
  table { border-collapse: collapse; width: 100%; }
  td, th { border: 1px solid #000; padding: 4px 8px; }
</style></head>
<body>
  <h1>Quarterly Report</h1>
  <table>
    <tr><th>Quarter</th><th>Revenue</th></tr>
    <tr><td>Q1</td><td>$280K</td></tr>
    <tr><td>Q2</td><td>$310K</td></tr>
  </table>
</body>
</html>";

// Write to temp file — HTMLDOC requires a file path argument
string tempHtml = Path.GetTempFileName() + ".html";
string tempPdf  = Path.GetTempFileName() + ".pdf";

try
{
    await File.WriteAllTextAsync(tempHtml, html, System.Text.Encoding.UTF8);

    var psi = new ProcessStartInfo
    {
        FileName               = "/usr/bin/htmldoc",
        Arguments              = $"--webpage --size A4 --quiet -f \"{tempPdf}\" \"{tempHtml}\"",
        UseShellExecute        = false,
        RedirectStandardError  = true,
        CreateNoWindow         = true
    };

    using var process = Process.Start(psi)!;
    await process.WaitForExitAsync();

    if (process.ExitCode != 0)
    {
        string err = await process.StandardError.ReadToEndAsync();
        throw new Exception($"HTMLDOC failed: {err}");
    }

    byte[] pdfBytes = await File.ReadAllBytesAsync(tempPdf);
    // use pdfBytes...
    Console.WriteLine($"Generated {pdfBytes.Length} bytes.");
}
finally
{
    // Clean up temporary files
    if (File.Exists(tempHtml)) File.Delete(tempHtml);
    if (File.Exists(tempPdf))  File.Delete(tempPdf);
}
  • Two temporary files must be managed: one for the HTML input, one for the PDF output.
  • Path.GetTempFileName() creates a zero-byte temp file — the .html extension must be appended manually to avoid HTMLDOC's extension-based content type detection.
  • Temporary file cleanup must be ensured in a finally block to prevent accumulation on the host under concurrent load.
  • UTF-8 content with non-ASCII characters in the HTML may not render correctly if HTMLDOC's CSS/font handling does not support the character set

IronPDF — HTML String to PDF

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop    = 10;
renderer.RenderingOptions.MarginBottom = 10;

string html = @"
<!DOCTYPE html>
<html>
<head><style>
  body  { font-family: Helvetica; font-size: 11pt; }
  table { border-collapse: collapse; width: 100%; }
  td, th { border: 1px solid #000; padding: 4px 8px; }
</style></head>
<body>
  <h1>Quarterly Report</h1>
  <table>
    <tr><th>Quarter</th><th>Revenue</th></tr>
    <tr><td>Q1</td><td>$280K</td></tr>
    <tr><td>Q2</td><td>$310K</td></tr>
  </table>
</body>
</html>";

// No temp file required — HTML string rendered directly in-process
using var pdf = await renderer.RenderHtmlAsPdfAsync(html);
byte[] pdfBytes = pdf.BinaryData;
Console.WriteLine($"Generated {pdfBytes.Length} bytes.");

No temporary files, no cleanup, no file path management. The HTML string to PDF guide covers inline CSS, embedded images, JavaScript wait conditions, and all rendering options.

Headers, Footers, and Page Numbers

HTMLDOC — Headers and Footers via CLI Options

using System.Diagnostics;

// HTMLDOC — headers and footers configured via command-line template strings
// Header/footer templates are three-character codes for left/center/right slots

string arguments =
    "--webpage " +
    "--size A4 " +
    "--top 1.5cm --bottom 1.5cm " +
    // Header: empty left | document title center | date right
    "--header .t. " +
    // Footer: empty left | page number center | empty right
    "--footer .1. " +
    "--quiet " +
    "-f output.pdf input.html";

var psi = new ProcessStartInfo
{
    FileName              = "/usr/bin/htmldoc",
    Arguments             = arguments,
    UseShellExecute       = false,
    RedirectStandardError = true,
    CreateNoWindow        = true
};

using var process = Process.Start(psi)!;
await process.WaitForExitAsync();
if (process.ExitCode != 0)
    throw new Exception(await process.StandardError.ReadToEndAsync());
  • HTMLDOC's header/footer system uses preset template tokens — the developer cannot inject arbitrary HTML or CSS into headers/footers, only select from the available slot codes (., t, D, 1, C, etc.).
  • Custom company branding, logos in headers, or styled footers are not achievable with HTMLDOC's template system — only predefined content tokens are available.
  • Margin dimensions set by --top and --bottom determine the space available for headers and footers; insufficient margin causes overlap with body content.

IronPDF — HTML Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop    = 22;
renderer.RenderingOptions.MarginBottom = 15;

// Full HTML header — arbitrary content, CSS styling, branding
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height          = 14,
    HtmlFragment    = "<div style='font-family:Arial; font-size:9pt; display:flex; " +
                      "justify-content:space-between; padding:0 14px;'>" +
                      "<span>Acme Corp — Confidential</span>" +
                      "<span>{date}</span></div>",
    DrawDividerLine = true
};

// HTML footer with page numbers via tokens
renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height       = 10,
    HtmlFragment = "<div style='font-family:Arial; font-size:8pt; " +
                   "text-align:center;'>Page {page} of {total-pages}</div>"
};

using var pdf = await renderer.RenderHtmlAsPdfAsync(
    "<html><body><h1>Report</h1><p>Content here.</p></body></html>");
pdf.SaveAs("report.pdf");

IronPDF headers and footers are full HTML fragments — logos, CSS Flexbox layout, custom fonts, and any HTML element are supported. The headers and footers guide covers height, dividers, and per-section options.

Post-Generation Manipulation (IronPDF only)

HTMLDOC produces a PDF file and has no manipulation API. Signing, encrypting, merging, or form-filling the output requires a second library.

using IronPdf;
using IronPdf.Signing;

// Generate PDF from HTML in-process
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

using var pdf = await renderer.RenderHtmlAsPdfAsync(
    "<html><body><h1>Contract #5521</h1><p>Binding terms apply.</p></body></html>");

// Sign the generated document
var sig = new PdfSignature("company-cert.pfx", "cert-password")
{
    SigningReason   = "Approved",
    SigningLocation = "Chicago, IL"
};
pdf.Sign(sig);

// Compress for delivery
pdf.CompressImages(75);

pdf.SaveAs("contract-5521-signed.pdf");

Generation, signing, and compression chain on the same PdfDocument without an intermediate file or a second library. The digital signatures guide and PDF compression guide cover these operations.

Commonly Reported Limitations

  • HTMLDOC's HTML parser targets HTML 3.2/4 — templates using <div> with CSS Grid or Flexbox layout, <svg>, <canvas>, or JavaScript-populated content will produce incorrect, empty, or garbled output; this is not a bug but a design boundary.
  • Tables in HTMLDOC can exhibit rendering inconsistencies with complex CSS borders and cell spacing
  • The subprocess integration model requires HTMLDOC to be installed on every application host (development, staging, CI, production containers), and version mismatches between environments can produce output differences; managing the binary version as part of the application's dependency manifest requires deliberate CI pipeline configuration.
  • HTMLDOC's header/footer template system offers only predefined token codes (title, date, page number, chapter) — custom HTML, images, or CSS-styled branding in headers and footers are not supported.
  • HTMLDOC's character encoding handling for non-ASCII content (UTF-8 documents with international characters) requires verification — the tool's support for Unicode beyond the Latin character set is limited compared to a browser-based renderer.

Conclusion

When HTMLDOC is technically reasonable

HTMLDOC is technically reasonable for simple document conversion workflows on Linux/Unix systems where templates are intentionally constrained to HTML 3.2/4-era constructs, the GPL license is compatible with the application's distribution model, and the team has an established subprocess invocation pattern. Lightweight pipeline tools that process simple structured HTML — reports with headings, paragraphs, and basic tables — may find HTMLDOC adequate if the templates have been validated against HTMLDOC's rendering engine. In environments where installing a managed library is not possible and a system package is preferable, HTMLDOC's availability in Linux package repositories is an advantage.

When the architectural mismatch becomes significant

The mismatch becomes significant when templates use modern CSS constructs (Grid, Flexbox, custom properties, web fonts, or SVG); when JavaScript execution is required for content population; when arbitrary HTML in headers and footers (branding, logos, styled company headers) is needed; when PDF manipulation (signing, merging, compliance output) is required alongside generation; when the subprocess integration model's overhead (binary deployment, temp file management, exit code parsing) is disproportionate to the PDF generation requirement; or when commercial support and SLA are required for a production pipeline.

How IronPDF approaches the same problem space

IronPDF processes HTML through embedded Chromium in-process — the same rendering engine used by modern browsers, accepting the same CSS templates a web developer would write and preview in Chrome. No subprocess, no temp file management, no binary staging. PdfDocument covers manipulation operations (signing, merging, compliance, form filling) alongside generation in a single NuGet. The IronPDF documentation overview covers both generation and manipulation.
