GdPicture.NET SDK vs IronPDF: from install to production — compared

a technical comparison for modern .NET teams (2026)

Document processing SDKs in the enterprise .NET space have a tendency to accumulate capability over time. A library that started as an imaging toolkit adds PDF support; a PDF library adds OCR; an OCR library adds barcode scanning. The result is multi-purpose SDKs that cover a wide surface area but may not treat any single capability as a primary design concern. When teams evaluate these SDKs for a specific pipeline — say, high-fidelity HTML-to-PDF generation for a reporting system — the breadth of the SDK may obscure that the specific operation they care most about is not the library's strongest implementation.

The discipline of evaluating a multi-capability SDK against a single pipeline requirement requires asking not "does this SDK do X" but "how does this SDK do X, and is that implementation appropriate for our specific workload." A library that does PDF generation, OCR, barcode scanning, and image processing may generate PDFs adequately for simple documents but fall short for complex HTML templates with JavaScript-rendered data visualizations. The evaluation surface that matters is narrow: the team's actual use case, not the full feature matrix.

GdPicture.NET SDK and IronPDF overlap in PDF generation and manipulation, but they originate from different design centers and their approach to key operations differs in ways that affect pipeline fit. The comparison below examines those differences with an emphasis on production implications.

What GdPicture.NET SDK Is Designed To Do

GdPicture.NET is a commercial .NET SDK developed by ORPALIS that combines document imaging, PDF processing, OCR, barcode reading and writing, document cleanup, and format conversion in a single package. The SDK targets ISVs and enterprise teams building document-centric applications: scanning solutions, document management systems, archival pipelines, and workflows that involve processing physical or digital documents from intake to storage.

The PDF capabilities within GdPicture.NET include document creation via a document object model, HTML-to-PDF conversion (using an internal renderer), PDF viewing via a Windows Forms or WPF viewer component, form field management, annotation support, digital signing, encryption, redaction, text extraction, OCR on scanned PDFs, PDF/A compliance, and barcode operations. The SDK is a broad toolkit rather than a PDF-specialist library; its strength is in scenarios that require imaging, scanning, and PDF operations in the same pipeline.

GdPicture.NET is NuGet-distributed and supports a range of .NET versions; current compatibility with .NET 6/7/8 and Linux should be verified in official documentation given the SDK's Windows-imaging heritage.

What IronPDF Is Designed To Do

IronPDF is a .NET PDF library built around a Chromium rendering engine. Its primary workflow — converting HTML, CSS, and JavaScript into PDFs — is designed for teams whose content lives as web templates, making it possible to reuse browser-tested layouts for server-side document generation. The rendering options guide covers the rendering configuration surface: paper size, margins, viewport, CSS media type, and JavaScript execution timing.

IronPDF's manipulation layer adds the document operations that production pipelines require after rendering: merge, split, page management, headers and footers, digital signatures with HSM support, encryption and permissions, PDF/A and PDF/UA compliance, form creation and filling, text and image extraction, redaction, watermarking, compression, and linearization. These operate under a consistent PdfDocument model regardless of whether the source was rendered by IronPDF or loaded from an existing file.

Deployment targets include Windows, Linux, macOS, and container environments including Docker, Azure, and AWS Lambda. The Chromium engine runs in-process with no external service dependency.

Key Limitations of GdPicture.NET SDK

Product Status

GdPicture.NET is a commercially maintained SDK from ORPALIS with an active development history. Version updates are released periodically; verify current release cadence and .NET version support in official documentation. The SDK's multi-capability scope means individual components may have different update frequencies; the PDF module and the OCR module, for instance, may not share the same development pace.

Missing Capabilities

GdPicture.NET's HTML-to-PDF renderer is its own implementation, not a Chromium-class browser engine. Teams that need to convert web templates using JavaScript-populated content, CSS Grid and custom properties, modern web fonts, or front-end framework output will find the internal renderer's CSS and JavaScript coverage limited relative to a dedicated browser-engine-based library. The rendering gap is structural — it cannot be resolved through configuration — and widens as web design practices evolve.

The SDK's PDF capabilities are part of a larger multi-purpose package; teams that need only PDF generation and manipulation pay the package weight and licensing cost of the broader SDK for capabilities they may not use.

Technical Constraints

GdPicture.NET's imaging capabilities have historically had Windows-native dependencies (GDI+, DirectX scanning interfaces). Modern .NET and Linux support for the PDF subsystem specifically should be validated against the target deployment environment before committing. Container deployments (Docker on Linux) require verifying which SDK modules function correctly on Linux and which have implicit Windows dependencies.

The SDK's package size reflects its multi-capability scope. In serverless or container-constrained environments where image size and cold-start time are concerns, a broad SDK like GdPicture.NET may impose more overhead than a PDF-focused library.

Support Model

ORPALIS provides commercial support with licensing. Support tiers, SLA options, and response time commitments should be verified in current official documentation. Community resources are proportionally smaller than for developer-forum-driven ecosystems.

Architectural Fit

GdPicture.NET fits well when the pipeline genuinely requires imaging, scanning, OCR, barcode operations, and PDF processing in a single dependency. Organizations building document capture and processing workflows — intake from scanner, OCR, data extraction, archival as PDF — benefit from the SDK's integrated capability set. The fit weakens for pipelines that are primarily generation-focused: converting HTML templates to PDFs at scale, where the SDK's HTML renderer becomes the bottleneck and the imaging capabilities are unused overhead.

GdPicture.NET — HTML to PDF

// Verify exact class names and method signatures in official documentation

// 1. Create a GdPicturePDF object
// 2. Call the HTML rendering method with the HTML string or URL
// 3. Configure page dimensions and rendering options
// 4. Save to file or stream

// Example pattern:

// Set document properties

// HTML import

// pdf.ImportFromHtml("<html><body><h1>Hello</h1></body></html>");

pdf.Dispose();

Technical constraints:

  • GdPicture.NET's HTML renderer is its own implementation; CSS Grid, CSS custom properties, and JavaScript-rendered content will not render with browser-level fidelity.
  • JavaScript execution for dynamic content population: verify support level in official documentation.
  • External CDN resources (web fonts, remote stylesheets) require network access from the render context; behavior on restricted server environments needs testing.
  • The GdPicturePDF class holds unmanaged resources; explicit Dispose() is required
  • Thread safety: create a new GdPicturePDF instance per thread or verify thread safety in concurrent scenarios.

IronPDF — HTML to PDF

using IronPdf;

// Chromium-based renderer — full CSS3 and JavaScript support
var renderer = new ChromePdfRenderer();

// Configure for print output
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.CssMediaType = IronPdf.Rendering.PdfCssMediaType.Print;
renderer.RenderingOptions.MarginTop    = 15;
renderer.RenderingOptions.MarginBottom = 15;

// Render HTML string — dispose PdfDocument when done
using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Report</h1><p>Data content here.</p></body></html>"
);

pdf.SaveAs("output.pdf");

IronPDF's Chromium engine processes the full CSS pipeline — including Grid, Flexbox, custom properties, and print media queries — before PDF capture. The pixel-perfect HTML to PDF guide covers how viewport and CSS media type settings interact. For JavaScript-rendered charts or dynamic tables, the JavaScript execution guide describes timing controls for capturing content after JS execution completes.

IronPDF — PDF Text Extraction

using IronPdf;

using var pdf = PdfDocument.FromFile("document.pdf");

// Extract all text across all pages
string fullText = pdf.ExtractAllText();

// Extract from a specific page (0-based)
string page1Text = pdf.ExtractTextFromPage(0);

// Extract all images embedded in the document
var images = pdf.ExtractAllImages();

System.IO.File.WriteAllText("extracted.txt", fullText);

IronPDF uses 0-based page indexing consistently throughout the API. The text and image extraction guide covers both text and image extraction paths, including per-page extraction and the resolution settings for image output.

IronPDF — Barcode in PDF (via HTML)

using IronPdf;

// Embed a barcode in a PDF by rendering it as HTML
// Barcodes can be generated via IronBarcode (separate Iron Software product)
// and embedded as base64 images in the HTML template

string htmlWithBarcode = @"
<html>
<body>
  <h1>Shipping Label</h1>
  <img src='data:image/png;base64,{BARCODE_BASE64}' alt='Barcode' />
  <p>Tracking: 1Z999AA10123456784</p>
</body>
</html>";

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.Custom;
renderer.RenderingOptions.CustomPaperWidthMm  = 100;
renderer.RenderingOptions.CustomPaperHeightMm = 150;

using var pdf = renderer.RenderHtmlAsPdf(htmlWithBarcode);
pdf.SaveAs("shipping_label.pdf");

IronPDF embeds barcodes in PDFs via the HTML rendering path — barcode images are injected into the HTML template as base64 data URIs or referenced image files. The barcode in PDF example demonstrates this integration pattern with the IronBarcode library for barcode generation.

Commonly Reported Limitations

GdPicture.NET:

  • HTML rendering fidelity is a consistently reported gap for teams with templates using modern CSS. Developers migrating from browser-preview workflows describe needing to simplify or restructure templates to work within GdPicture's internal renderer, which increases template maintenance burden.
  • The SDK's 1-based page indexing convention is reported as a friction point for developers accustomed to 0-based conventions elsewhere in .NET; off-by-one errors in page operations are a recurring debugging issue.
  • Linux and Docker deployment requires careful validation; the SDK's imaging components have historical dependencies on Windows GDI, and teams report that not all PDF module features function correctly on Linux without additional configuration.
  • The broad multi-capability scope of the SDK means that updates to one module may not be synchronized with another; teams have reported that OCR improvements in a version did not correspond to PDF rendering improvements.
  • Resource management requires explicit Dispose() calls; GdPicture objects hold unmanaged resources, and missing disposal in error paths produces memory leaks that are not always immediately visible in development but surface under production load.

Conclusion

When staying on GdPicture.NET is technically reasonable

Teams that genuinely need OCR, barcode reading, document imaging, and PDF processing in a single SDK will find GdPicture.NET's integrated scope valuable. Document capture pipelines that process scanned physical documents — reading barcodes on intake, OCR-ing content, extracting data, and archiving as PDF — benefit from having all those operations in one dependency managed by one vendor. If the HTML rendering requirement is absent or limited to simple templates, the rendering gap is less consequential.

When migration becomes a capability or architectural mismatch

When HTML-to-PDF generation is the primary pipeline operation and templates use JavaScript-rendered content, modern CSS frameworks, or web fonts, GdPicture.NET's internal renderer produces unreliable output that cannot be corrected through configuration. Teams running on Linux containers or modern .NET runtimes need explicit validation that all required PDF features function in that environment; the SDK's Windows-imaging heritage introduces uncertainty. If the multi-capability scope is unused — if the team needs PDF operations only, without OCR or image processing — carrying the full SDK weight adds package size and licensing cost without compensating benefit.

How IronPDF approaches the same problem

IronPDF scopes to PDF generation and manipulation exclusively, using Chromium as the rendering engine and providing a consistent managed .NET API for all document operations. Teams with GdPicture.NET deployments that primarily use the PDF module can migrate the rendering and manipulation operations to IronPDF while evaluating alternative OCR and imaging solutions separately if those capabilities are needed. The IronPDF docs overview provides a structured view of the full PDF capability surface to assist in scoping a transition.

For teams operating multi-purpose document SDKs, how often does using a single vendor for OCR, imaging, and PDF generation simplify the dependency graph versus how often it creates a capability bottleneck in the specific area that matters most for a given project?
