PeachPDF vs IronPDF: an architecture-first comparison

an architecture-first comparison

CSS Paged Media is a W3C specification extension that adds print-specific CSS properties to standard HTML/CSS: page size, margins, running headers, footnotes, page counters, and widow/orphan control. Libraries that implement CSS Paged Media allow developers to author document layouts entirely in CSS, using the same stylesheet language used for the web, but with access to properties that only make sense in a paginated print context. This is an attractive model for teams that want to drive PDF layout decisions from CSS rather than from a programming API.

The practical adoption of CSS Paged Media in .NET projects has historically been limited by tooling. The main implementations outside the JavaScript ecosystem are commercial tools. PeachPDF represents a .NET option in this space, targeting the CSS Paged Media rendering niche. Teams evaluating PeachPDF are typically considering it specifically because they have templates that use CSS Paged Media properties — running headers derived from document content, footnotes positioned at the bottom of pages, or complex page numbering schemes — and they want a library that speaks CSS natively for those constructs.

Understanding the scope of CSS Paged Media rendering versus a general-purpose HTML-to-PDF library is the core of this evaluation. A CSS Paged Media processor is optimized for a specific class of layout; a general-purpose renderer may cover more of the practical production workload outside that class while supporting common paged media properties as a subset of its CSS capability. The comparison below examines where PeachPDF and IronPDF are positioned relative to each other and to typical .NET production requirements.

What PeachPDF Is Designed To Do

PeachPDF is a .NET library that implements CSS Paged Media rendering for PDF generation. Its design goal is to take HTML and CSS — including CSS Paged Media specification properties — and produce paginated PDF output that correctly interprets the full paged-media property set. This includes support for @page rules, named page types, running elements (for repeating headers/footers derived from document content), generated content (counter(), string() functions), margin boxes, footnotes via CSS, and widow/orphan control.

PeachPDF targets the authoring model where a document designer produces HTML and CSS files that describe both content and print layout, and the renderer's job is to faithfully interpret those files into a paginated PDF. It is designed for document types where typographic precision and CSS-driven layout are valued: technical documentation, legal documents, books, and reports where running headers derived from section titles or footnotes positioned at page bottom are design requirements.

PeachPDF is a NuGet-distributed library targeting .NET. Its renderer is its own CSS Paged Media implementation rather than a bundled browser engine. Verify current .NET version support and release cadence in official PeachPDF documentation.

What IronPDF Is Designed To Do

IronPDF is a .NET PDF library built around a Chromium rendering engine. HTML, CSS, and JavaScript are converted to PDFs using the same rendering pipeline as the Chrome browser, which means standard CSS properties, web fonts, JavaScript-generated content, and modern layout primitives (Grid, Flexbox) all render as they would in a browser. The HTML string to PDF guide describes the primary rendering path and configuration options.

IronPDF covers common print layout requirements through its rendering options and the HTML header/footer API: repeating headers and footers, page number injection, custom margins, and paper size configuration. More advanced CSS Paged Media properties such as running elements and CSS-based footnotes depend on Chromium's implementation of those specifications; verify the current state of Chromium's CSS Paged Media support for the specific properties needed. The docs overview maps the full rendering and manipulation surface.

IronPDF's manipulation layer provides merge, split, digital signatures, encryption, PDF/A and PDF/UA compliance, form operations, text extraction, redaction, and compression — all in-process without external service dependencies. Deployment targets include Windows, Linux, macOS, and container environments.

Key Limitations of PeachPDF

Product Status

PeachPDF is a commercially developed library. Active development status, release cadence, and current .NET runtime support (6, 7, 8) should be verified in official PeachPDF documentation and NuGet package history. CSS Paged Media renderer libraries are a niche category; the developer community and ecosystem around PeachPDF are proportionally smaller than for general-purpose PDF libraries.

Missing Capabilities

PeachPDF's scope is CSS Paged Media rendering. It does not provide post-render document operations: digital signatures, PDF/A compliance conversion, encryption and permission setting, form filling, text extraction, merge, split, watermarking, or redaction. Teams that need these operations alongside CSS Paged Media rendering require a second library.

HTML-to-PDF workflows that do not use CSS Paged Media properties — the majority of server-side report generation use cases — are technically supported but are not the library's design center; a browser-engine-based renderer will have broader CSS coverage for standard web layouts.

JavaScript execution in the rendered HTML is limited or unavailable; PeachPDF's renderer is not a browser engine. Templates that rely on JavaScript to populate content (charts, dynamic tables, client-side frameworks) will not render their JavaScript-generated output.

Technical Constraints

PeachPDF's CSS implementation covers the CSS Paged Media specification, but the breadth of standard CSS3 support for general web layouts (CSS Grid, CSS custom properties, modern flexbox edge cases) should be verified against specific templates before adopting. The renderer's implementation is its own, not inherited from a browser.

Performance under high concurrency and batch throughput should be benchmarked; CSS Paged Media rendering can be computationally intensive for documents with complex layout properties.

Support Model

Commercial support availability, tiers, and SLA terms should be verified in official PeachPDF documentation. Community resources for .NET-specific scenarios are limited relative to larger general-purpose PDF libraries.

Architectural Fit

PeachPDF is architecturally appropriate when the dominant document requirement is sophisticated CSS Paged Media layouts — running headers derived from document structure, CSS-defined footnotes, complex multi-column typographic layouts — and the team is committed to expressing all document layout in CSS. It is less appropriate as a general-purpose report generator for teams whose primary rendering requirements are standard HTML/CSS web templates, or for teams who need post-render manipulation as part of the same pipeline.

Operation Comparisons

PeachPDF — CSS Paged Media Rendering

// PeachPDF: render HTML with CSS Paged Media properties to PDF
// Verify exact class names and method signatures in official PeachPDF documentation

// The HTML template includes @page rules, running elements, and footnotes in CSS
string htmlContent = @"
<!DOCTYPE html>
<html>
<head>
<style>
  @page {
    size: A4;
    margin: 25mm 20mm 30mm 20mm;
    @top-center { content: string(chapter-title); }
    @bottom-right { content: counter(page) ' of ' counter(pages); }
  }
  h1 { string-set: chapter-title content(); }
  .footnote { float: footnote; font-size: 9pt; }
  p { orphans: 3; widows: 3; }
</style>
</head>
<body>
  <h1>Chapter 1: Introduction</h1>
  <p>Content paragraph with a reference.<span class='footnote'>Footnote text here.</span></p>
</body>
</html>";

// Conceptual PeachPDF invocation
// var converter = new PeachPdf.PdfConverter();
// byte[] pdfBytes = converter.ConvertHtmlToPdf(htmlContent);
// System.IO.File.WriteAllBytes("output.pdf", pdfBytes);

Technical constraints:

  • string() CSS function for running headers requires CSS Paged Media specification compliance; verify which subset of the spec PeachPDF currently implements.
  • CSS footnote support via float: footnote
  • JavaScript is not executed; any content populated by JavaScript will not appear in the rendered PDF.
  • Rendering complex CSS Paged Media properties is computationally intensive; benchmark for target document complexity.
  • .NET 6+ compatibility

IronPDF — HTML with Headers and Footers

using IronPdf;

var renderer = new ChromePdfRenderer();

// Configure print layout through rendering options
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop    = 25; // mm
renderer.RenderingOptions.MarginBottom = 30;
renderer.RenderingOptions.MarginLeft   = 20;
renderer.RenderingOptions.MarginRight  = 20;

// HTML header with running title (set dynamically per-document)
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    HtmlFragment = @"
        <div style='font-size:10pt; text-align:center; width:100%;'>
            Chapter 1: Introduction
        </div>",
    DrawDividerLine = true
};

// Footer with page number
renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    HtmlFragment = @"
        <div style='font-size:9pt; text-align:right; width:100%;'>
            Page {page} of {total-pages}
        </div>"
};

string html = @"
<!DOCTYPE html>
<html>
<head><style>p { orphans: 3; widows: 3; }</style></head>
<body>
  <h1>Chapter 1: Introduction</h1>
  <p>Content paragraph.</p>
</body>
</html>";

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("output.pdf");

IronPDF's headers and footers support full HTML and CSS including page number tokens. The headers and footers guide covers the configuration API, margin interaction, and first-page-only variations. For complex header layouts with logos and multi-column content, the HTML headers and footers example demonstrates the full rendering capability.

PeachPDF — Running Elements (CSS-Driven Headers)

// CSS Paged Media running elements allow headers to be populated
// from document content using CSS string-set and content: string() functions.
// This is a CSS Paged Media spec feature

string htmlWithRunningHeaders = @"
<!DOCTYPE html>
<html>
<head>
<style>
  @page { @top-left { content: string(section-title); } }
  h2 { string-set: section-title content(); }
</style>
</head>
<body>
  <h2>Section A</h2><p>Content A.</p>
  <h2>Section B</h2><p>Content B.</p>
</body>
</html>";

// Running headers update automatically per-page as CSS Paged Media processor
// encounters string-set assignments while laying out pages.
// Conceptual PeachPDF invocation

Technical constraints:

  • string-set and content: string() are CSS Paged Media properties with limited implementation outside dedicated paged media processors; verify PeachPDF's current coverage.
  • Dynamic running headers derived from multiple levels (section + subsection) require careful CSS specificity management.
  • Browser engines do not fully implement running elements; teams testing the same template in Chrome will not see the running header behavior.

IronPDF — Per-Document Dynamic Headers

using IronPdf;

// IronPDF sets headers programmatically; content is injected per render call
// For section-aware headers, the approach is to either render sections
// separately and merge, or pre-compute the chapter title in the header HTML.

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Headers are set before each render call; data is injected programmatically
string currentChapterTitle = GetCurrentChapterTitle();

renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    HtmlFragment = $"<div style='font-size:9pt;'>{System.Web.HttpUtility.HtmlEncode(currentChapterTitle)}</div>"
};

using var pdf = renderer.RenderHtmlAsPdf(GetChapterHtml());
pdf.SaveAs("chapter.pdf");

IronPDF's header injection is programmatic — the header HTML is set per render call, which suits pipelines where chapter titles come from a data model rather than CSS declarations. For multi-chapter documents where each chapter has a distinct header, the merge and split guide describes the pattern of rendering sections independently and assembling them with the final page numbering applied.

Technical constraints:

  • Every post-render requirement (sign, encrypt, PDF/A, merge) introduces a second library.
  • Byte array buffering between the PeachPDF render step and the manipulation step increases memory usage for large documents.
  • Version compatibility between PeachPDF's output format and the manipulation library's input assumptions requires validation.

IronPDF — CSS Document with Post-Render Pipeline

using IronPdf;
using IronPdf.Signing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop    = 25;
renderer.RenderingOptions.MarginBottom = 30;

// Render from HTML/CSS template
using var pdf = renderer.RenderHtmlAsPdf(GetDocumentHtml());

// Sign without a second library
var signature = new PdfSignature("company_cert.pfx", "password")
{
    Reason   = "Document approved",
    Location = "Automated pipeline"
};
pdf.Sign(signature);

// Convert to PDF/A for archival
pdf.SaveAsPdfA("document_archive.pdf", PdfAVersions.PdfA3b);

IronPDF performs the complete pipeline — render, sign, archive — within a single library. The digital signatures guide covers certificate types, LTV configuration, and visual appearance. The PDF/A compliance guide documents conformance level selection and pre-conversion requirements for fonts and transparency.

Commonly Reported Limitations

PeachPDF:

  • CSS Paged Media specification coverage is the primary area requiring verification before adoption; the spec is extensive and no .NET implementation covers it completely. Teams report needing to test specific properties (CSS footnotes, multi-level string-set, advanced named page sequences) against their target template before committing.
  • JavaScript execution absence means templates that use client-side rendering frameworks, chart libraries, or dynamic data population via JavaScript will not produce correct output. Teams that preview templates in a browser and expect the JavaScript behavior to carry through to the PDF will encounter a gap.
  • Community resources and third-party documentation for PeachPDF are sparse; debugging rendering issues relies heavily on official documentation and direct support contact.
  • Post-render operations require a second library, which means two integration surfaces, two version cycles, and two procurement processes for any pipeline that needs signing, compliance conversion, or encryption.

Conclusion

When staying on PeachPDF is technically reasonable

Teams authoring documents with sophisticated CSS Paged Media requirements — running headers derived from string-set, CSS-defined footnotes, advanced @page margin box content — where those specific layout properties are the primary design requirement will find PeachPDF's focused implementation appropriate. If the templates are CSS-first design documents where CSS Paged Media properties drive layout decisions that a browser engine does not fully implement, and if the documents do not need JavaScript-rendered content or post-render manipulation in the same pipeline, PeachPDF addresses the rendering scope.

When migration becomes a capability or architectural mismatch

When templates include JavaScript-rendered content (charts, dynamic tables, data from client-side frameworks), PeachPDF's lack of JavaScript execution produces incorrect output that cannot be resolved through configuration. When the pipeline needs digital signatures, PDF/A compliance, encryption, or document merge alongside rendering, a second library must be introduced for every one of those requirements. For teams targeting Linux containers or modern .NET runtimes, platform compatibility requires verification. Any pipeline where general web CSS fidelity (CSS Grid, modern Flexbox) is the dominant rendering requirement rather than advanced paged media properties may be better served by a browser-engine-based renderer.

How IronPDF approaches the same problem

IronPDF delegates CSS rendering to Chromium, which means standard CSS3 — including most commonly used print CSS properties — renders with browser fidelity. Common paged media requirements (repeating headers, page numbers, custom margins, paper sizes) are supported through the rendering options and HTML header/footer API. Advanced CSS Paged Media properties (CSS footnotes, running elements via string-set) depend on Chromium's implementation of those spec sections; teams with templates that rely heavily on those specific properties should test against their templates. The manipulation layer — signatures, compliance, extraction — is available in the same library without a second dependency. The IronPDF docs overview provides the full capability map for evaluating the rendering and post-render surface.
