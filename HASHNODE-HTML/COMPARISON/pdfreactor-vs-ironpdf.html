PDFreactor vs IronPDF: a .NET engineer reference for 2026

a .NET engineer reference for 2026

Problem Framing

HTML-to-PDF conversion addresses a wider range of rendering approaches than the term suggests. At one end sits a headless browser engine — Chromium or WebKit — that renders HTML exactly as a browser would, then captures the output as a PDF. At the other end sits a CSS Paged Media engine that implements the W3C CSS Paged Media specification: a formal standard for describing how web content should be laid out on paginated print media. These two approaches produce different outputs from the same HTML source, are optimized for different authoring workflows, and are the right choice in different contexts.

CSS Paged Media engines — of which PDFreactor is one of the most capable — are optimized for content where print layout is specified precisely using CSS @page rules, @media print queries, footnotes, running headers, cross-references, and other print-specific CSS constructs. Authors who write CSS for PDFreactor are targeting the W3C print specification rather than the browser rendering model. The output tends to be typographically precise, highly compliant with PDF/A and PDF/UA standards, and suitable for publishing workflows (technical documentation, books, regulated compliance documents). Teams that reach for PDFreactor typically have content professionals who know CSS Paged Media rather than web developers writing responsive layouts.

Chromium-based renderers — of which IronPDF is one — apply browser rendering logic to the HTML and CSS and capture what the browser would display. This approach inherits the full web platform: Flexbox, Grid, CSS variables, JavaScript, web fonts via Google Fonts, and every CSS feature that modern browsers support. It is the right fit for teams whose templates are already styled for browser rendering, who preview documents in Chrome before rendering, and who are generating PDFs from web application output rather than from typesetting-focused source documents. Understanding which model the application's templates and authoring workflow target is the first decision; library comparison comes second.

What PDFreactor Is Designed to Do

PDFreactor is a commercial CSS-to-PDF formatting engine developed by RealObjects GmbH. It implements the W3C CSS Paged Media specification, XSL-FO (XSL Formatting Objects), CSS Generated Content for Paged Media, and SVG rendering. Its core function is converting HTML and XML documents to PDF using CSS @page rules to control page size, margins, headers, footers, running elements, footnotes, page counters, and hyphenation — all expressed as CSS rather than as library API calls.

PDFreactor is accessible as a Java-based local server, a Docker container, and a cloud service; all modes expose a REST API. The .NET integration uses PDFreactor's official .NET client library, which wraps HTTP calls to the PDFreactor service. This means PDFreactor is not an in-process .NET library — it is a service that the .NET application calls via HTTP. PDFreactor produces high-quality typographic output with strong support for PDF/A (1a, 1b, 2a, 2b, 2u, 3a, 3b, 3u), PDF/UA accessibility, PDF/X, digital signatures, tagged PDFs, and WCAG compliance. It is commonly used for technical documentation, regulated document generation, book typesetting, government compliance documents, and accessibility-critical workflows.

PDFreactor is not a general PDF manipulation library. It does not read existing PDFs, fill forms, extract text, merge documents, or encrypt PDFs at the manipulation layer. Its scope is document conversion: HTML/XML in, PDF out. Commercial licensing applies; verify current pricing and edition options in RealObjects documentation.

What IronPDF Is Designed to Do

IronPDF is a .NET PDF library built on embedded Chromium for HTML-to-PDF generation, distributed as a managed NuGet package. ChromePdfRenderer renders HTML strings, HTML files, and URLs to PDF using the full Chromium rendering engine — CSS3, Flexbox, Grid, CSS variables, web fonts, SVG, and JavaScript with configurable wait conditions. The rendering options guide covers the configuration surface for paper size, margins, headers, footers, and rendering behavior.

Beyond generation, PdfDocument provides a manipulation API for existing PDFs: text extraction, image extraction, AcroForm reading and filling, form creation, document merge and split, page manipulation, password encryption, digital signatures (PKCS#12 and HSM-backed), PDF/A and PDF/UA compliance output, metadata, watermarks, redaction, and compression. Both types implement IDisposable. License initialization is a one-time startup call; see the license setup guide. IronPDF runs on Windows, Linux, macOS, and in Docker containers as a managed NuGet package — no REST service required.

Key Limitations of PDFreactor

Product Status

PDFreactor is an actively maintained commercial product from RealObjects GmbH with a long release history. It targets the professional typesetting and document conversion market and receives regular updates tracking W3C specification evolution. Verify current .NET client version compatibility, supported PDFreactor server version, and Docker image availability in official RealObjects documentation.

Missing Capabilities

PDFreactor is a conversion engine, not a PDF manipulation library. It does not read existing PDF documents, extract text or images, fill AcroForm fields, apply encryption to existing files, merge or split documents, add watermarks to existing PDFs, or perform redaction. Teams that need both HTML-to-PDF generation and post-generation PDF manipulation must introduce a second library for the manipulation surface. PDFreactor also does not execute JavaScript in the same way a browser does — it processes the CSS Paged Media specification, which does not include a JavaScript runtime as a rendering dependency.

Technical Constraints

PDFreactor is an external service, not an in-process .NET library. The .NET client sends conversion requests over HTTP to a PDFreactor server (local, Docker, or cloud). This introduces network latency per conversion, a service dependency that must be deployed and maintained alongside the application, and a potential single point of failure if the PDFreactor server is unavailable. The service requires a running Java runtime (JVM) unless the Docker image is used, adding operational complexity relative to a managed NuGet package.

CSS Paged Media authoring is a specialized skill set distinct from general web CSS. Developers familiar with Flexbox, CSS Grid, and responsive design will require learning CSS @page, named pages, running headers, footnote handling, and the W3C Paged Media module. Templates written for browser rendering may not produce the intended output under PDFreactor without adaptation.

Support Model

PDFreactor is commercially supported by RealObjects GmbH. Support tier details, SLA commitments, and enterprise options should be verified in current RealObjects documentation. The product has active developer community resources and comprehensive specification-level documentation.

Architectural Fit

PDFreactor is best suited for applications where document output must conform precisely to W3C Paged Media standards, where PDF/A and PDF/UA compliance at the highest conformance levels is a hard requirement, where content professionals with CSS Paged Media expertise maintain the document templates, and where the operational overhead of a service-based conversion engine is acceptable. It is less suited for applications whose templates are authored for browser rendering, for teams whose developers know web CSS but not CSS Paged Media, for architectures that cannot tolerate a service dependency for document generation, or for applications that also need post-generation PDF manipulation.

Operation Comparisons

HTML to PDF via CSS Paged Media

PDFreactor — HTML to PDF with @page Rules

using RealObjects.PDFreactor.Webservice.Client;
using System.IO;

// PDFreactor .NET client — wraps HTTP calls to the PDFreactor service
// The PDFreactor server must be running (local, Docker, or cloud)
// Verify current client API in official PDFreactor .NET SDK documentation

var config = new Configuration
{
    // Document input: inline HTML
    Document = @"
<!DOCTYPE html>
<html>
<head>
  <title>Annual Report 2025</title>
  <style>
    /* CSS Paged Media — @page rule defines page layout */
    @page {
      size: A4;
      margin: 20mm 15mm 25mm 15mm;
      /* Running header via CSS generated content */
      @top-right {
        content: 'Annual Report 2025 — Page ' counter(page) ' of ' counter(pages);
        font-size: 8pt;
        font-family: Arial;
      }
      /* Footer with page numbers */
      @bottom-center {
        content: counter(page);
        font-size: 8pt;
      }
    }
    /* Named page for cover */
    @page cover {
      margin: 0;
      background: #2c3e50;
    }
    .cover-page { page: cover; }

    body { font-family: Arial; font-size: 11pt; }
    h1   { font-size: 24pt; margin-bottom: 6pt; }
    /* Footnote CSS — PDFreactor supports CSS footnotes */
    .footnote { float: footnote; font-size: 8pt; }
  </style>
</head>
<body>
  <div class='cover-page'>
    <h1 style='color:white; padding:80mm 20mm;'>Annual Report 2025</h1>
  </div>
  <h2>Executive Summary</h2>
  <p>Revenue grew 12% year-over-year.
     <span class='footnote'>Figures are preliminary and unaudited.</span>
  </p>
</body>
</html>",
    // Output format
    OutputFormat = OutputFormat.PDF,
    // PDF/A conformance
    ConformanceLevel = ConformanceLevel.PDFA1A
};

// Send to PDFreactor service
var pdfReactor = new PDFreactor("http://localhost:9423/service/rest");
byte[] pdfBytes = pdfReactor.Convert(config).Document;

await File.WriteAllBytesAsync("annual-report.pdf", pdfBytes);
  • The PDFreactor server must be running before this call executes — if the service is unavailable, the conversion fails; no fallback is available in the .NET client.
  • CSS @page rules, running headers/footers, named pages, and footnotes are first-class features — this is where PDFreactor's W3C compliance depth is most visible.
  • counter(pages) (total page count) requires a processing pass to determine — PDFreactor handles this via its two-pass rendering model.
  • JavaScript execution is not part of the conversion pipeline — templates that depend on JavaScript to populate content must be pre-processed server-side before sending to PDFreactor.
  • Verify current Configuration property names and PDFreactor client constructor in the official .NET SDK documentation — these have evolved across PDFreactor versions.

IronPDF — HTML to PDF via Browser CSS

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop    = 20;
renderer.RenderingOptions.MarginBottom = 25;
renderer.RenderingOptions.MarginLeft   = 15;
renderer.RenderingOptions.MarginRight  = 15;

// HTML header — applies to every page automatically
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height          = 10,
    HtmlFragment    = "<div style='font-size:8pt; font-family:Arial; " +
                      "text-align:right;'>Annual Report 2025 — Page {page} of {total-pages}</div>",
    DrawDividerLine = false
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height       = 8,
    HtmlFragment = "<div style='font-size:8pt; text-align:center;'>{page}</div>"
};

string html = @"
<!DOCTYPE html>
<html>
<head>
  <style>
    body { font-family: Arial; font-size: 11pt; }
    h1   { font-size: 24pt; }
    .cover { background:#2c3e50; color:white; padding:80mm 20mm; height:297mm;
             page-break-after: always; }
  </style>
</head>
<body>
  <div class='cover'><h1>Annual Report 2025</h1></div>
  <h2>Executive Summary</h2>
  <p>Revenue grew 12% year-over-year.</p>
</body>
</html>";

using var pdf = await renderer.RenderHtmlAsPdfAsync(html);
pdf.SaveAs("annual-report.pdf");

IronPDF renders using Chromium — the same CSS a browser renders. Headers and footers are declared on RenderingOptions once and applied to every page. The HTML string to PDF guide covers all rendering options. CSS Paged Media constructs like float: footnote are not Chromium-native features — templates must use browser-compatible CSS instead.

PDF/A Compliance Output

PDFreactor — PDF/A Conformance

using RealObjects.PDFreactor.Webservice.Client;

// PDFreactor — PDF/A-1a output (highest conformance level)
// PDFreactor validates conformance during conversion and reports violations

var config = new Configuration
{
    Document = "<html><body><p>Archived Document</p></body></html>",
    // Font embedding, color spaces, and tagged structure are enforced by PDFreactor
    // when a conformance level is specified — violations are reported as errors
    ConformanceLevel = ConformanceLevel.PDFA1A,
    OutputFormat     = OutputFormat.PDF
};

var pdfReactor = new PDFreactor("http://localhost:9423/service/rest");
// Verify return type — may be a result object with the PDF bytes
var result   = pdfReactor.Convert(config);
byte[] bytes = result.Document;  // verify property name in current SDK

await System.IO.File.WriteAllBytesAsync("archived-pdfa.pdf", bytes);
  • PDFreactor enforces PDF/A constraints during conversion — non-conformant CSS (e.g., RGB color without an output intent) is caught and reported.
  • PDF/A-1a (full accessibility) requires a tagged document structure — PDFreactor generates tags from semantic HTML elements automatically.
  • Font embedding is handled by PDFreactor; the source HTML must reference fonts that PDFreactor can access from its server environment.
  • Verify the exact ConformanceLevel enum values and result type in current PDFreactor .NET SDK documentation.

IronPDF — PDF/A Compliance

using IronPdf;

// Generate from HTML and convert to PDF/A in one pipeline
var renderer = new ChromePdfRenderer();
using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Archived Document</h1><p>Archive content here.</p></body></html>");

// SaveAsPdfA converts the rendered document to PDF/A conformance
pdf.SaveAsPdfA("archived-pdfa.pdf");

// Or convert an existing document:
using var existing = PdfDocument.FromFile("existing.pdf");
existing.SaveAsPdfA("existing-pdfa.pdf");

SaveAsPdfA() converts any PdfDocument to PDF/A conformance, handling font embedding and color profile requirements automatically. The PDF/A guide covers conformance level options.

PDF/UA Accessibility Output

PDFreactor — PDF/UA Accessibility

using RealObjects.PDFreactor.Webservice.Client;

// PDFreactor — PDF/UA (ISO 14289) accessibility output
// PDFreactor generates tagged PDF structure from semantic HTML
// ARIA attributes and HTML landmark elements are reflected in the tag tree

var config = new Configuration
{
    Document = @"
<!DOCTYPE html>
<html lang='en'>
<head>
  <title>Accessible Report</title>
</head>
<body>
  <main>
    <h1>Q3 Financial Report</h1>
    <p>Revenue: $1.2M</p>
    <table>
      <caption>Quarterly Breakdown</caption>
      <thead><tr><th scope='col'>Month</th><th scope='col'>Revenue</th></tr></thead>
      <tbody>
        <tr><td>July</td><td>$380K</td></tr>
        <tr><td>August</td><td>$410K</td></tr>
        <tr><td>September</td><td>$410K</td></tr>
      </tbody>
    </table>
  </main>
</body>
</html>",
    // PDF/UA requires tagged PDF — PDFreactor generates tags from semantic HTML
    ConformanceLevel = ConformanceLevel.PDFUA1,
    OutputFormat     = OutputFormat.PDF
};

var pdfReactor = new PDFreactor("http://localhost:9423/service/rest");
byte[] bytes = pdfReactor.Convert(config).Document;
await System.IO.File.WriteAllBytesAsync("accessible-report.pdf", bytes);
  • PDFreactor maps semantic HTML elements (<h1>, <table>, <caption>, <th scope>) to PDF structure tags automatically — the quality of accessibility output depends on the semantic quality of the HTML source.
  • PDF/UA-1 compliance requires proper tagging, reading order, alt text for images, and language declaration — PDFreactor validates these constraints during conversion.

Post-Generation PDF Manipulation (IronPDF only)

PDFreactor converts documents to PDF but does not manipulate existing PDFs. Teams that need signing, encryption, form filling, or merging after generation must use a second library with PDFreactor.

using IronPdf;
using IronPdf.Signing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Generate PDF in-process
using var pdf = await renderer.RenderHtmlAsPdfAsync(
    "<html><body><h1>Contract #2025-144</h1><p>Terms apply.</p></body></html>");

// Sign immediately — no round-trip, no second library
var sig = new PdfSignature("company-cert.pfx", "cert-password")
{
    SigningReason   = "Approved",
    SigningLocation = "Chicago, IL"
};
pdf.Sign(sig);

// Encrypt for recipient
pdf.SecuritySettings.UserPassword  = "view-password";
pdf.SecuritySettings.OwnerPassword = "admin-password";

pdf.SaveAs("contract-signed-encrypted.pdf");

Generation and post-generation manipulation chain on the same PdfDocument. The digital signatures guide and passwords and permissions guide cover these operations.

Commonly Reported Limitations

  • PDFreactor templates must be authored using CSS Paged Media conventions — developers familiar with responsive web CSS need to learn @page rules, named pages, running elements, and CSS counters before templates produce the intended output; this is a non-trivial learning curve relative to browser-preview HTML templates.
  • JavaScript-dependent content (charts rendered by chart.js, dynamically populated tables, React/Vue/Angular components) cannot be rendered by PDFreactor's engine, which does not include a JavaScript runtime — dynamic content must be serialized server-side before being passed to PDFreactor.
  • The REST service dependency means PDFreactor's availability is a prerequisite for every document generation call — service restarts, version upgrades, and network partitions between the application and the PDFreactor service are operational risks that do not exist with an in-process library.
  • PDFreactor's .NET client library wraps HTTP calls; teams using ASP.NET Core should ensure the client is configured to use a shared HttpClient instance and follows IHttpClientFactory patterns to avoid socket exhaustion.
  • PDFreactor does not provide PDF manipulation (merge, sign, extract) — teams whose workflow includes post-generation operations must introduce a second library, splitting the PDF responsibility across two vendor relationships.

Conclusion

When PDFreactor is technically reasonable

PDFreactor is technically reasonable for workflows where CSS Paged Media authoring is the established practice: publishing houses, government document generation, technical documentation systems, accessibility-critical compliance documents, and applications where documents must conform to PDF/A-1a, PDF/UA-1, or PDF/X with rigorous validation during the conversion step. Teams with content professionals who know CSS Paged Media and whose templates already use @page, named pages, and CSS counters will find PDFreactor's rendering faithful and specification-complete. The depth of its accessibility output — driven by mapping semantic HTML structure to PDF tags — is a genuine differentiator for regulated accessibility requirements.

When the architectural mismatch becomes significant

The mismatch becomes significant when templates are authored for browser rendering (Flexbox, Grid, responsive breakpoints, JavaScript-populated content) and the CSS Paged Media authoring model is not in use; when JavaScript execution is required for content population; when the service dependency and its operational overhead are constraints; when post-generation PDF manipulation (signing, encryption, merging, form filling) is required without a second library; or when an in-process NuGet package is required for deployment simplicity.

How IronPDF approaches the same problem space

IronPDF uses Chromium — the browser rendering model — which means any template that renders correctly in Chrome will render consistently in IronPDF. PDF/A and PDF/UA compliance are available as post-render operations on the generated PdfDocument. Manipulation operations (signing, encryption, merging) chain on the same object without a service dependency or a second library. The IronPDF documentation overview covers both generation and manipulation.

For teams evaluating PDFreactor: are the document templates currently authored using CSS Paged Media (@page rules, running headers, CSS counters, footnotes) or are they authored as browser-rendered HTML with standard web CSS — and does the answer to that question determine which rendering model is the better fit?
