RawPrint vs IronPDF: from install to production — compared

a technical comparison for modern .NET teams (2026)

Problem Framing

Printing in .NET applications addresses two architecturally distinct scenarios that share almost no implementation surface. The first is GDI-mediated printing: a document — PDF, HTML, image, or other format — is rendered by the application and handed to the Windows print spooler, which manages the rendering pipeline, printer driver translation, and delivery to the printer. The second is raw printing: the application sends a pre-formed byte stream directly to a printer port, bypassing the Windows rendering pipeline entirely. In the second model, the printer receives commands in its own native language — ZPL for Zebra label printers, ESC/POS for receipt printers, TSPL for TSC printers — and interprets them without any GDI involvement. The two models are not interchangeable: a ZPL command stream sent through GDI will produce garbage output, and a rendered document sent raw to a label printer will likely be ignored or produce incorrect output.

RawPrint is a .NET utility library for the second scenario: it provides a thin managed wrapper around the Windows OpenPrinter / StartDocPrinter / WritePrinter API calls that allow application code to send raw byte arrays directly to a named printer port. Its primary users are teams building label printing (Zebra, Eltron, TSPL), receipt printing (ESC/POS for POS hardware), and industrial print automation workflows where the application generates the command language payload and sends it verbatim to the printer.

IronPDF's printing path sits entirely within the first scenario: it generates a PDF from HTML or loads an existing PDF, then sends it to a printer via the Windows GDI pipeline, which handles driver translation and spooler management. The comparison in this article is not a direct competition — the tools solve different problems. It is relevant to teams who need to print PDF files on printers that also support raw protocols, to teams evaluating whether raw printing or GDI-mediated printing is the right model for their deployment, and to teams who reach for one tool thinking it covers the other scenario.

What RawPrint Is Designed to Do

RawPrint is a lightweight .NET NuGet library that offers a managed API for sending raw byte streams directly to Windows printer ports without engaging the GDI print spooler's rendering pipeline. The library wraps the Windows winspool.drv P/Invoke calls — OpenPrinter, StartDocPrinter, StartPagePrinter, WritePrinter, EndPagePrinter, EndDocPrinter, ClosePrinter — behind a clean managed interface that eliminates the need to write the P/Invoke declarations manually.

Based on available information, the core API includes Printer.PrintRawFile(printerName, filePath, docName) for sending a file's bytes directly to a named printer, and Printer.SendBytesToPrinter(printerName, bytes, docName) for sending an in-memory byte array. These methods allow application code to dispatch ZPL (Zebra Programming Language), EPL (Eltron Programming Language), TSPL (TSC Printer Language), ESC/POS (Epson Standard Code for Point of Sale), and any other raw printer command language payload without Windows intercepting, re-rendering, or reformatting the stream.

RawPrint is Windows-only — it wraps the Windows print spooler API. It does not generate documents, render HTML, process PDFs, or perform any content transformation. Its sole function is to deliver a pre-formed byte payload to a named Windows printer destination. Verify current NuGet package name (there are several packages in the ecosystem providing similar Win32 raw print wrappers — ensure the one being adopted is actively maintained), .NET version support (.NET Standard vs .NET 6+), and API surface in official documentation or the package repository before integrating.

What IronPDF Is Designed to Do

IronPDF is a .NET PDF library built on embedded Chromium for HTML-to-PDF generation, paired with a programmatic printing API. ChromePdfRenderer generates PDFs from HTML strings, HTML files, and URLs with full CSS3 fidelity — Flexbox, Grid, web fonts, SVG, and JavaScript execution. PdfDocument handles manipulation of existing PDFs: text extraction, image extraction, AcroForm filling, merge, split, signing, encryption, PDF/A compliance, and more.

For printing, IronPDF's PdfDocument.Print() method sends a PDF to a physical printer via the Windows GDI pipeline — printer selection, copy count, duplex, and page range are configurable from code, and no Adobe Acrobat or external viewer is required. The printing guide covers the full PdfPrintSettings configuration surface. License initialization is a one-time startup call; see the license setup guide. IronPDF supports Windows, Linux, and macOS; programmatic printing to physical printers is a Windows-centric operation (printer driver availability depends on the OS).

Key Limitations of RawPrint

Product Status

Multiple NuGet packages exist in the .NET ecosystem that wrap the Windows raw print API

Missing Capabilities

RawPrint is exclusively a print dispatch utility. It does not generate PDFs, render HTML, create documents from data, extract content from existing files, or perform any document transformation. Any workflow requiring document generation before printing must use a separate library entirely — RawPrint has no document creation surface whatsoever. It also cannot render a PDF to a printer through the GDI pipeline; it can only forward pre-formed byte payloads to printer ports. Sending PDF bytes via SendBytesToPrinter to a standard GDI printer will produce incorrect output or an error, because PDF is not a raw printer command language.

Technical Constraints

RawPrint is Windows-only. The OpenPrinter / WritePrinter API it wraps is a Windows Win32 API; it has no equivalent on Linux or macOS. Applications that need to print from Linux containers or cross-platform deployments cannot use RawPrint for printer dispatch. Additionally, the target printer must be configured as a named Windows printer queue — raw printing to IP-connected printers requires that printer to be added to the Windows print system with its port configured correctly.

Raw printing bypasses the printer driver's rendering pipeline. This means the application is entirely responsible for generating a byte stream that is valid for the specific printer model and firmware version. ZPL syntax, label dimensions, DPI settings, and command encoding must all be managed in application code. A payload that works on a Zebra ZT230 at 203 DPI may not produce the correct output on a ZT410 at 300 DPI without adjustments. The application owns this translation layer.

Support Model

Community-maintained NuGet packages in this category typically have no commercial support. Verify the current maintainer and support channel in the package repository. The Windows raw print API itself is well-documented by Microsoft, which partially compensates — experienced Windows print subsystem knowledge can resolve most integration issues without library-specific support.

Architectural Fit

RawPrint is architecturally suited for Windows-based applications that drive label printers, receipt printers, or other hardware that accepts native command language payloads (ZPL, ESC/POS, TSPL), where the application generates the command stream and the goal is delivering it to the printer without Windows rendering interference. It is not suited for PDF printing, document generation, cross-platform deployments, or any scenario where the printer is a standard GDI-compatible device.

Sending a Raw ZPL Label to a Zebra Printer

RawPrint — ZPL Label via Raw Byte Stream

using RawPrint;  // verify current NuGet package namespace

// RawPrint — send a ZPL label command stream directly to a Zebra printer
// The printer must be configured as a named Windows printer queue

string printerName = "ZebraZT230";  // Windows printer name — must match exactly
string docName     = "ShippingLabel-4412";

// Build a ZPL II label payload
// ZPL is the Zebra Programming Language — commands start with ^
// This example generates a 4"×6" shipping label at 203 DPI
string zplLabel = @"
^XA
^PW812
^LL1218
^LH0,0

^FO30,30^A0N,40,40^FDShip To:^FS
^FO30,80^A0N,30,30^FDAcme Corp^FS
^FO30,110^A0N,25,25^FD123 Main St, Chicago IL 60601^FS

^FO30,200^BY3^BCN,100,Y,N,N^FD1234567890^FS

^XZ";

// Convert ZPL string to bytes — Zebra printers expect ASCII/UTF-8
byte[] zplBytes = System.Text.Encoding.ASCII.GetBytes(zplLabel);

// Send raw bytes directly to the printer port — no GDI, no driver rendering
// Verify method signature in current RawPrint package documentation
Printer.SendBytesToPrinter(printerName, zplBytes, docName);

Console.WriteLine($"ZPL label sent to '{printerName}'.");
  • The printer name ("ZebraZT230") must exactly match the Windows printer queue name as it appears in the Windows print system — a mismatch silently fails or throws a Win32 exception.
  • ZPL commands (label width ^PW, label length ^LL, font ^A0N, field origin ^FO, barcode ^BC) are specific to Zebra firmware versions
  • System.Text.Encoding.ASCII is correct for most ZPL payloads; some advanced ZPL features require the printer's specific code page
  • RawPrint bypasses the printer driver entirely; if the printer driver's settings (DPI, darkness, speed) need to change per label, those changes must be embedded as ZPL commands (^PR, ~SD) within the payload — they cannot be set via print dialog.
  • Verify the exact method signature (Printer.SendBytesToPrinter vs IRawPrint.Print vs another variant) in the current version of the specific NuGet package in use — multiple packages wrap this API with different method names.

    .section { margin-bottom: 10px; }

IronPDF's GDI printing path requires that the printer has a Windows printer driver installed — raw-only printers without a rendering driver cannot receive GDI output. For label printers that support both ZPL raw mode and a Windows driver (many Zebra models do), IronPDF's approach keeps the label design in HTML/CSS and sends it through the driver. Sending an ESC/POS Receipt to a Thermal Printer

RawPrint — ESC/POS Receipt

using RawPrint;  // verify current package namespace
using System.Collections.Generic;
using System.Text;

// RawPrint — ESC/POS receipt for a thermal receipt printer (e.g., Epson TM-T88)
// ESC/POS uses escape sequences to control formatting and paper cutting

string printerName = "EpsonTMT88";  // Windows printer queue name

// Build ESC/POS command sequence as bytes
// ESC/POS commands: ESC @ = init, ESC a = align, ESC ! = font, GS V = cut
var receipt = new List<byte>();

// ESC @ — Initialize printer
receipt.AddRange(new byte[] { 0x1B, 0x40 });

// ESC a 1 — Center alignment
receipt.AddRange(new byte[] { 0x1B, 0x61, 0x01 });

// ESC ! 0x10 — Double-height emphasis for store name
receipt.AddRange(new byte[] { 0x1B, 0x21, 0x10 });
receipt.AddRange(Encoding.ASCII.GetBytes("ACME RETAIL\n"));

// ESC ! 0x00 — Reset to normal size
receipt.AddRange(new byte[] { 0x1B, 0x21, 0x00 });

// ESC a 0 — Left alignment for line items
receipt.AddRange(new byte[] { 0x1B, 0x61, 0x00 });
receipt.AddRange(Encoding.ASCII.GetBytes("--------------------------------\n"));
receipt.AddRange(Encoding.ASCII.GetBytes("Widget A            x2   $19.98\n"));
receipt.AddRange(Encoding.ASCII.GetBytes("Widget B            x1   $49.99\n"));
receipt.AddRange(Encoding.ASCII.GetBytes("--------------------------------\n"));

// ESC a 2 — Right alignment for total
receipt.AddRange(new byte[] { 0x1B, 0x61, 0x02 });
receipt.AddRange(Encoding.ASCII.GetBytes("TOTAL:          $69.97\n\n\n"));

// GS V 0 — Full paper cut
receipt.AddRange(new byte[] { 0x1D, 0x56, 0x00 });

// Send raw bytes to printer — bypasses GDI entirely
Printer.SendBytesToPrinter(printerName, receipt.ToArray(), "Receipt-8847");
Console.WriteLine("ESC/POS receipt sent.");
  • ESC/POS command byte values are defined by the Epson ESC/POS specification and may vary between printer models and firmware revisions — consult the specific printer's ESC/POS programming guide.
  • Encoding for line item text is typically ASCII or the printer's configured code page; Unicode characters outside the code page will print as the printer's substitution character.
  • The GS V paper cut command requires that the printer has a cutter installed and enabled — sending it to a printer without a cutter has no effect or may produce an error.
  • Alignment, font sizes, and line spacing commands (ESC 3) must be reset explicitly after use — ESC/POS is a stateful protocol and unintended state from a previous receipt carries into the next if the printer is not re-initialized.

Batch Raw Print from File

RawPrint — Batch Print ZPL Files

using RawPrint;
using System.IO;

// RawPrint — batch send multiple pre-generated ZPL files to a printer
// Each .zpl file contains a pre-formed ZPL label payload

string printerName = "ZebraZT230";
string labelFolder = @"C:\Labels\Pending";

// Enumerate ZPL files — each is a complete label payload
var zplFiles = Directory.GetFiles(labelFolder, "*.zpl");

int sent    = 0;
int failed  = 0;

foreach (var filePath in zplFiles)
{
    string docName = Path.GetFileNameWithoutExtension(filePath);
    try
    {
        // PrintRawFile sends the file's contents verbatim to the printer
        // Verify method signature in current RawPrint package documentation
        Printer.PrintRawFile(printerName, filePath, docName);
        Console.WriteLine($"Sent: {docName}");
        sent++;
    }
    catch (Exception ex)
    {
        Console.Error.WriteLine($"Failed: {docName} — {ex.Message}");
        failed++;
    }
}

Console.WriteLine($"Batch complete: {sent} sent, {failed} failed.");
  • PrintRawFile reads the file bytes and forwards them directly to the printer queue — the file encoding must match the printer's expected encoding (usually ASCII for ZPL).
  • Error handling on a per-file basis is important for batch operations — a failure on one label should not halt the entire batch.
  • Verify the exact method name (PrintRawFile vs SendFileToPrinter vs another variant) in the current package version.
  • Verify whether the method call blocks until the data is written to the spooler queue or until the printer confirms completion — Windows print spooler operations are typically queued, not synchronous to physical printing.

IronPDF — Batch Print PDFs

using IronPdf;
using IronPdf.Printing;
using System.IO;

// IronPDF — batch print PDF files via GDI pipeline
string pdfFolder   = @"C:\Labels\Pending";
var pdfPrintSettings = new PdfPrintSettings
{
    PrinterName    = "ZebraZT230",  // must have Windows driver
    NumberOfCopies = 1,
    PrintAllPages  = true
};

var pdfFiles = Directory.GetFiles(pdfFolder, "*.pdf");

foreach (var filePath in pdfFiles)
{
    using var pdf = PdfDocument.FromFile(filePath);
    pdf.Print(pdfPrintSettings);
    Console.WriteLine($"Printed: {Path.GetFileName(filePath)}");
}

IronPDF reuses the same PdfPrintSettings instance across the batch. The printing guide covers page range, duplex, and printer enumeration options.

Generating and Printing a PDF in One Pipeline (IronPDF; not applicable to RawPrint)

RawPrint's scope is byte delivery to a printer queue. Document generation — creating the PDF content — is entirely outside its scope. In workflows requiring both document generation and printing, a generation library must be used alongside RawPrint (if raw delivery is required) or IronPDF handles both steps.

using IronPdf;
using IronPdf.Printing;

// IronPDF — generate a PDF from HTML, then print it immediately
// No intermediate file write required; no subprocess; no separate library

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop    = 20;
renderer.RenderingOptions.MarginBottom = 20;

string html = @"
<!DOCTYPE html>
<html>
<body>
  <h1>Work Order #9912</h1>
  <p>Station: Assembly Line 3 | Priority: High</p>
  <table style='width:100%; border-collapse:collapse;'>
    <tr><th style='border:1px solid #ccc;padding:6px;'>Task</th>
        <th style='border:1px solid #ccc;padding:6px;'>Status</th></tr>
    <tr><td style='border:1px solid #ccc;padding:6px;'>Install bracket</td>
        <td style='border:1px solid #ccc;padding:6px;'>Pending</td></tr>
  </table>
</body>
</html>";

// Step 1: Generate PDF from HTML in memory — no file I/O
using var workOrder = await renderer.RenderHtmlAsPdfAsync(html);

// Step 2: Print immediately from the in-memory PdfDocument
workOrder.Print(new PdfPrintSettings
{
    PrinterName    = "OfficeHP4000",
    NumberOfCopies = 1,
    PrintAllPages  = true,
    Duplex         = Duplex.Simplex
});

// Step 3: Optionally archive
workOrder.SaveAs(@"C:\WorkOrders\wo-9912.pdf");

Generation, print dispatch, and archival operate in sequence on the same PdfDocument object — no temporary file path, no subprocess, no second library. The PDF reporting guide covers data-driven generation patterns for similar print-on-demand workflows.

Commonly Reported Limitations

  • The Windows raw print API requires the printer to be registered as a named queue in the Windows print system — printers connected directly via USB or serial without a Windows queue cannot be targeted; the Windows driver must install the queue even if raw printing bypasses the driver's rendering pipeline.
  • ZPL, ESC/POS, and TSPL command sequences are printer-model-specific and firmware-version-sensitive — a payload that prints correctly on one model may produce incorrect output on a different model or firmware revision, requiring the application to maintain separate command templates per printer type.
  • Error reporting from raw print operations is limited — the Windows WritePrinter API returns a success/failure indicator but does not distinguish between "data written to spooler queue" and "printer physically received and processed the data"; paper jams, ribbon errors, and printer offline states may not surface as exceptions.
  • Multiple NuGet packages in the .NET ecosystem wrap the Windows raw print API with similar names but different API surfaces, .NET target frameworks, and maintenance status
  • ESC/POS printer state is persistent across print jobs unless the printer is explicitly re-initialized (ESC @) at the start of each job — stale state from a previous job (unusual font sizes, alignment modes, bold on) will carry into the next job if not reset.

Conclusion

When RawPrint is technically reasonable

RawPrint is technically reasonable for Windows-based applications that dispatch label or receipt print jobs to printers accepting native command languages — ZPL for Zebra label printers, ESC/POS for thermal receipt printers, TSPL for TSC devices — where the application generates the command payload and the goal is delivering it verbatim to the printer port without GDI interference. It removes the need to write P/Invoke declarations manually, which is a genuine reduction in boilerplate for teams building in-house raw print dispatch code. Applications already generating ZPL or ESC/POS payloads that have working integrations on Windows have little reason to change.

When the architectural mismatch becomes significant

The mismatch becomes significant when the requirement is printing PDF documents rather than raw command payloads — RawPrint cannot render or deliver PDFs to GDI printers; when document generation (creating the content before printing) is part of the workflow; when cross-platform deployment (Linux, macOS, Docker) is on the roadmap and the Windows-only constraint is a blocker; or when the application needs both PDF generation and print dispatch under a single library dependency.

How IronPDF approaches the same problem space

IronPDF addresses the GDI-mediated printing scenario: generate a PDF from HTML or load an existing PDF, then dispatch it to a named printer via PdfDocument.Print() with typed settings — no subprocess, no P/Invoke, no external binary. It does not compete with RawPrint's raw byte dispatch model; teams that need both PDF printing and raw label printing will use both tools for their respective scenarios. The IronPDF documentation overview covers the full generation, manipulation, and printing surface.

For teams evaluating printer dispatch tooling: are the printers in the target deployment configured with Windows GDI drivers (enabling PDF-based printing via IronPDF), configured for raw-only mode (requiring ZPL/ESC/POS via RawPrint), or a mix of both — and does that distribution across printer types determine whether one tool, the other, or both are needed in the stack?
