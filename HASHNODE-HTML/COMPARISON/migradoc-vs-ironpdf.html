MigraDoc vs IronPDF: feature parity, trade-offs, and fit

what changes when you switch

Programmatic PDF construction — building a document by assembling paragraphs, tables, images, and sections through a document object model — was the dominant server-side PDF pattern in .NET for years before HTML-to-PDF rendering became viable. Libraries that implement this approach ask the developer to describe the document in code: define a section, add a paragraph, configure a table, set a font and color. The output is deterministic and the layout is explicit, which has real value for documents where precision matters and the structure is stable.

The emergence of HTML-to-PDF rendering libraries changed the calculus. For teams whose content lives as web templates — maintained by front-end developers, testable in a browser, using CSS for layout — the programmatic construction approach requires translating that content into a different representation language. Every styling change in the web view requires a corresponding change in the document model code. This translation burden grows with template complexity, and the document model code tends to become brittle in proportion to the sophistication of the layout it encodes.

MigraDoc and IronPDF represent these two approaches directly. MigraDoc is a document object model library; IronPDF is an HTML-to-PDF renderer with a surrounding manipulation layer. The comparison below examines where each fits, where one creates friction the other avoids, and what changes when a team considers switching.

What MigraDoc Is Designed To Do

MigraDoc is an open-source .NET library for programmatic PDF document creation, developed as part of the PDFsharp project. It provides a document object model (DOM) for describing a PDF: documents contain sections, sections contain paragraphs and tables, paragraphs contain text runs with formatting, and all layout properties are set in code. The library produces PDF output via the PDFsharp rendering layer.

MigraDoc is designed for use cases where a developer constructs a document entirely in code: reports assembled from data queries, contracts with field-populated sections, invoices built row-by-row. It does not use an HTML renderer; layout is computed by MigraDoc's own paragraph and table formatter. The library handles text flow across pages, header and footer repetition, table cell layout, and basic image placement.

MigraDoc and PDFsharp are open-source, NuGet-distributed, and have a long history in the .NET ecosystem. They target .NET Framework and later versions; current .NET 6+ compatibility should be verified in the latest PDFsharp/MigraDoc NuGet package. The library has no external dependencies and produces PDF without any rendering engine, browser, or native library.

What IronPDF Is Designed To Do

IronPDF is a .NET PDF library built around a Chromium rendering engine. Its primary workflow converts HTML, CSS, and JavaScript into PDFs. Teams that maintain content as web templates can use those templates directly for PDF generation — the same HTML that renders in a browser produces the PDF, which eliminates the gap between the two representations. The HTML string to PDF guide describes the central rendering path.

Beyond rendering, IronPDF provides a document manipulation layer: merge, split, page management, headers and footers, digital signatures with HSM support, encryption and permissions, PDF/A and PDF/UA compliance conversion, form creation and filling, text and image extraction, redaction, compression, linearization, and barcode embedding. The library targets server-side .NET workloads on Windows, Linux, macOS, and container environments. The docs overview maps the full rendering and manipulation surface.

Key Limitations of MigraDoc

Product Status

MigraDoc and PDFsharp are open-source projects maintained by the PDFsharp community. The projects are actively maintained and receive updates, with NuGet packages published regularly. Verify current .NET 6/7/8 support and release notes in the official PDFsharp GitHub repository. The open-source model means there is no commercial vendor behind the library, which affects support availability for production blocking issues.

Missing Capabilities

MigraDoc's document object model does not support HTML/CSS rendering. Teams whose content is authored as HTML templates cannot use MigraDoc to render those templates; the HTML must be re-expressed as MigraDoc DOM calls. CSS layout properties (Grid, Flexbox, custom properties), JavaScript-rendered content, and web fonts are not part of MigraDoc's capability set.

Post-render document operations that are outside MigraDoc's scope include: digital signatures, PDF/A compliance conversion, encryption and permissions, text extraction from existing PDFs, form filling, and redaction. These operations require PDFsharp's lower-level API or a separate library.

Technical Constraints

MigraDoc's table and paragraph formatter is its own implementation. Complex table layouts — merged cells, nested tables, variable-height rows across page breaks — can require workarounds or produce unexpected pagination behavior. The library's handling of right-to-left text, complex Unicode scripts, and advanced OpenType font features is limited compared to a browser's text rendering engine.

Image handling is basic: images are placed at specified positions with specified dimensions. Responsive image sizing, percentage-based layouts, and SVG rendering are outside the formatter's scope.

Support Model

Support for MigraDoc is community-driven: the PDFsharp GitHub issue tracker, discussion forums, and community samples. There is no commercial support, no SLA, and no vendor for escalation. For production systems where a rendering or pagination bug would be blocking, the resolution path is community engagement or internal workarounds.

Architectural Fit

MigraDoc fits well when: the document structure is simple and data-driven (tables of records, structured reports), the layout is stable and developer-maintained, web rendering fidelity is not required, and the team is comfortable working in a document object model rather than HTML. It fits less well when templates are complex, frequently updated, maintained by non-engineers, or when the content is already expressed as HTML and requiring two representations creates maintenance overhead.

Operation Comparisons

MigraDoc — Build a PDF Document from Code

using MigraDoc.DocumentObjectModel;
using MigraDoc.DocumentObjectModel.Tables;
using MigraDoc.Rendering;
using PdfSharp.Pdf;

// MigraDoc: construct the document object model in code
var document = new Document();
document.Info.Title   = "Monthly Report";
document.Info.Author  = "Reporting System";

// Define a paragraph style
var normalStyle = document.Styles["Normal"];
normalStyle.Font.Name = "Calibri";
normalStyle.Font.Size = 11;

// Add a section (equivalent to a page group in MigraDoc)
var section = document.AddSection();
section.PageSetup.PageFormat    = PageFormat.A4;
section.PageSetup.LeftMargin    = Unit.FromCentimeter(2.5);
section.PageSetup.RightMargin   = Unit.FromCentimeter(2.5);
section.PageSetup.TopMargin     = Unit.FromCentimeter(2);
section.PageSetup.BottomMargin  = Unit.FromCentimeter(2);

// Add a heading paragraph
var heading = section.AddParagraph("Monthly Report — October 2024");
heading.Style = "Heading1";

// Add a data table
var table = section.AddTable();
table.Style = "TableNormal";
table.Borders.Width = 0.5;

// Define columns
table.AddColumn(Unit.FromCentimeter(8));
table.AddColumn(Unit.FromCentimeter(4));

// Add header row
var headerRow = table.AddRow();
headerRow.Shading.Color = Colors.LightGray;
headerRow.Cells[0].AddParagraph("Item");
headerRow.Cells[1].AddParagraph("Amount");

// Add data rows from application data
foreach (var item in GetReportItems())
{
    var row = table.AddRow();
    row.Cells[0].AddParagraph(item.Description);
    row.Cells[1].AddParagraph(item.Amount.ToString("C"));
}

// Render to PDF using PDFsharp
var renderer = new PdfDocumentRenderer(unicode: true);
renderer.Document = document;
renderer.RenderDocument();
renderer.PdfDocument.Save("report.pdf");

Technical constraints:

  • All layout properties are specified in code; any design change requires a code change, build, and deployment.
  • CSS or HTML input is not supported; web templates must be re-expressed as MigraDoc DOM calls.
  • Complex table behaviors across page breaks (split rows, repeated headers) require explicit configuration and can produce unexpected output for edge cases.
  • Digital signatures, encryption, and PDF/A compliance are outside MigraDoc's API surface; PDFsharp provides lower-level access but with additional complexity.
  • Right-to-left text, ligatures, and complex script rendering depend on MigraDoc's text formatter rather than a browser engine.

IronPDF — Build an Equivalent Document from HTML

using IronPdf;

// The same report expressed as HTML/CSS
// Template can be edited in any HTML editor, previewed in a browser
string html = @"
<!DOCTYPE html>
<html>
<head>
<style>
  body       { font-family: Calibri, sans-serif; font-size: 11pt; margin: 0; }
  h1         { font-size: 16pt; margin-bottom: 12px; }
  table      { width: 100%; border-collapse: collapse; }
  th, td     { border: 0.5pt solid #888; padding: 6px 8px; }
  th         { background: #d0d0d0; font-weight: bold; }
  .amount    { text-align: right; }
</style>
</head>
<body>
  <h1>Monthly Report — October 2024</h1>
  <table>
    <tr><th>Item</th><th class='amount'>Amount</th></tr>
    <!-- rows injected from data -->
  </table>
</body>
</html>";

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginLeft   = 25; // mm
renderer.RenderingOptions.MarginRight  = 25;
renderer.RenderingOptions.MarginTop    = 20;
renderer.RenderingOptions.MarginBottom = 20;

using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("report.pdf");

IronPDF's Chromium engine applies the full CSS pipeline, meaning the HTML template can be developed and verified in a browser before use in PDF generation. The rendering options guide covers margin, viewport, paper size, and CSS media type settings. For templates with web fonts or external stylesheets, the base URLs guide describes how to configure the rendering context for asset resolution.

MigraDoc — Headers and Footers

using MigraDoc.DocumentObjectModel;
using MigraDoc.Rendering;

var document = new Document();
var section  = document.AddSection();
section.PageSetup.PageFormat = PageFormat.A4;

// MigraDoc header — defined on the section's header
var header = section.Headers.Primary;
header.AddParagraph("Confidential — Internal Use Only");

// Footer with page number
var footer        = section.Footers.Primary;
var footerPara    = footer.AddParagraph();
footerPara.AddTab(); // center
footerPara.AddPageField();  // current page number
footerPara.AddText(" of ");
footerPara.AddNumPagesField(); // total pages

// Add document content
section.AddParagraph("Document body content here.");

var renderer = new PdfDocumentRenderer(unicode: true) { Document = document };
renderer.RenderDocument();
renderer.PdfDocument.Save("output.pdf");

Technical constraints:

  • Header and footer content is defined as MigraDoc paragraphs; HTML or CSS-based layout is not available in the header/footer zone.
  • Image placement in headers requires MigraDoc's image API; relative sizing and CSS-based positioning are not available.
  • Different header/footer content for first page versus subsequent pages requires configuring section.Headers.FirstPage explicitly.
  • Dynamic data injection in headers (e.g., per-chapter title) requires script-based workarounds or multiple section definitions.

IronPDF — Headers and Footers

using IronPdf;

var renderer = new ChromePdfRenderer();

// HTML header — supports full CSS, images, dynamic tokens
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    HtmlFragment = @"
        <div style='font-size:9pt; color:#666; display:flex;
                    justify-content:space-between; padding:4px 20px;
                    border-bottom:1px solid #ccc;'>
            <span>Confidential — Internal Use</span>
            <span>Page {page} of {total-pages}</span>
        </div>",
    DrawDividerLine = false
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    HtmlFragment = "<div style='text-align:center;font-size:8pt;color:#999;'>Generated by Reporting System</div>"
};

using var pdf = renderer.RenderHtmlAsPdf("<html><body><p>Document content.</p></body></html>");
pdf.SaveAs("output_with_headers.pdf");

IronPDF supports full HTML and CSS in headers and footers, including images, flexbox layout, and dynamic page number tokens. The headers and footers guide covers margin interaction, first-page-only configuration, and the HTML headers and footers example demonstrates complex templates with logos and multi-column layouts.

MigraDoc — No Digital Signature Support

// MigraDoc has no digital signature API.
// PDFsharp has limited signing support in certain versions
// For production signing in a MigraDoc pipeline, a second PDF manipulation
// library is typically required.

// Pattern: save MigraDoc output to byte array, pass to signing library

var renderer = new PdfDocumentRenderer(unicode: true) { Document = document };
renderer.RenderDocument();

using var stream = new System.IO.MemoryStream();
renderer.PdfDocument.Save(stream, closeStream: false);
byte[] unsignedBytes = stream.ToArray();

// A separate signing library is required here.
// The architectural implication: two libraries, two integration surfaces,
// two dependency management concerns.

Technical constraints:

  • PDFsharp's built-in signing capability
  • For enterprise signing requirements (LTV, HSM, visible signature appearance), an additional library is typically necessary.
  • Maintaining two libraries for a single pipeline increases the surface area for version incompatibilities, particularly during .NET runtime upgrades.

IronPDF — Document Construction with Signing in One Pipeline

using IronPdf;
using IronPdf.Signing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Render the document from HTML
using var pdf = renderer.RenderHtmlAsPdf(BuildReportHtml(reportData));

// Apply digital signature — no second library required
var signature = new PdfSignature("company_cert.pfx", "cert_password")
{
    Reason   = "Report approved",
    Location = "Reporting pipeline"
};
pdf.Sign(signature);

// Set encryption and user permissions
pdf.SecuritySettings.OwnerPassword           = "ownerSecret";
pdf.SecuritySettings.AllowUserPrintDocument  = true;
pdf.SecuritySettings.AllowUserCopyPasteContent = false;

pdf.SaveAs("report_signed.pdf");

IronPDF's digital signatures guide covers PFX-based and HSM-backed certificates, visual signature appearance, and LTV configuration. The PDF permissions guide documents the available user capability restrictions — both available within the same library without an additional dependency.

Commonly Reported Limitations

MigraDoc:

  • Complex table layouts — particularly tables with merged cells, nested tables, or variable-height rows that must split across page boundaries — are a frequently cited source of unexpected output. Pagination behavior for tables with many rows and complex formatting requires careful testing and sometimes workarounds.
  • The document object model coding approach means that template changes require a developer, a build, and a deployment. Teams that need non-engineer involvement in document design report this as a significant constraint.
  • Right-to-left languages and complex script rendering (Arabic, Hebrew, Devanagari) are not fully supported; teams with multilingual document requirements report needing workarounds or alternative libraries.
  • PDF/A compliance and digital signature support in PDFsharp are limited relative to dedicated compliance and signing libraries; teams with archival or regulated signing requirements typically add a second library.
  • SVG rendering support is limited; documents that include data visualizations as SVG (chart libraries, D3.js exports) require conversion to bitmap images before embedding, which affects quality at higher zoom levels.

Conclusion

When staying on MigraDoc is technically reasonable

Teams with stable, developer-owned document templates that are structured and data-driven — tabular reports, fixed-layout certificates, structured data exports — will find MigraDoc's document object model appropriate. The open-source, zero-cost, zero-dependency profile is attractive for projects with no budget for commercial libraries and no requirement for HTML rendering fidelity. If digital signatures and PDF/A compliance are not required, or if PDFsharp's available support for these operations is sufficient, MigraDoc covers the generation scope without external dependencies.

When migration becomes a capability or architectural mismatch

When templates evolve to include CSS-based layouts, when front-end developers become involved in template design, or when the team wants to preview templates in a browser before PDF generation, MigraDoc's DOM-only approach creates a parallel maintenance burden. Any requirement for digital signatures with LTV, HSM support, PDF/A conversion at specific conformance levels, or programmatic text extraction from existing documents pushes the team to introduce additional libraries, increasing integration complexity. For high-throughput async batch generation, MigraDoc has no async rendering API.

How IronPDF approaches the same problem

IronPDF replaces the document object model approach with an HTML-first rendering path: templates are HTML and CSS, which means they can be authored in any editor, previewed in a browser, and tested before deployment without a rendering engine. The surrounding manipulation layer — signing, compliance, extraction, security — is part of the same library, reducing the multi-library integration pattern that MigraDoc pipelines often accumulate over time. For teams evaluating the transition, the IronPDF docs overview describes the full capability surface for mapping each MigraDoc operation to an IronPDF equivalent.
