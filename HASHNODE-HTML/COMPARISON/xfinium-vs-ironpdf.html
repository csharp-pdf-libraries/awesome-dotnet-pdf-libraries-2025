XFINIUM.PDF vs IronPDF: what changes when you switch

a technical comparison for modern .NET teams (2026)

Problem Framing

PDF generation libraries for .NET split broadly into two architectural families: those that render from a web technology (HTML, CSS, JavaScript via a browser engine) and those that construct PDF documents programmatically through a document object model. Libraries in the second family expose the PDF specification directly—pages, content streams, fonts, graphics operators, annotations, form fields—and require the developer to build the document structure in code or from a template model rather than from markup. For applications that need precise control over PDF structure, low-level manipulation of existing documents, or generation without any HTML intermediary, the document-model approach is appropriate.

XFINIUM.PDF is a commercial .NET library that operates in the document-model category. It provides a native PDF object model: pages, content streams, fonts, images, form fields, digital signatures, and document structure—all accessed through a C# API rather than through an HTML-to-PDF rendering pipeline. This places it in a different category from wkhtmltopdf wrappers or Chromium-based renderers. Teams choosing between XFINIUM.PDF and an HTML renderer are often choosing between precise programmatic control over document structure versus template-driven rendering with web technology skills.

The evaluation question is which model matches the application's dominant workflow. Programmatic document construction is well-suited for applications that build documents from structured data, fill form fields in pre-designed PDF templates, or need to manipulate the internal structure of existing documents without a browser intermediary. HTML-to-PDF rendering is well-suited for applications that already have HTML templates, need web-style layout features (Flexbox, Grid, web fonts), or want to reuse web-tier design work in document output. Neither model is universally better; the match to the actual requirement determines the appropriate choice.

A common mis-evaluation pattern occurs when a team builds a document-model library proof of concept with a simple two-column table and finds it straightforward, then discovers at production scale that rendering a five-page report with dynamic data, multi-level headers, and variable-length text blocks requires hundreds of lines of layout logic code. The coordinate model's simplicity in the demo becomes laborious at production complexity. The reverse pattern also occurs: teams that adopt an HTML renderer for a simple text certificate later discover they need to fill form fields in a pre-designed PDF—an operation the renderer does not support.

What XFINIUM.PDF Is Designed To Do

XFINIUM.PDF is a commercial .NET library from XFINIUM Software for creating, editing, and manipulating PDF documents through a native PDF object model. The library targets multiple .NET platforms including .NET Standard, .NET Framework, .NET Core, Xamarin, and .NET 6+. It is distributed as a NuGet package with no native binary dependencies—the library is a pure managed assembly.

The core API exposes the PDF specification directly: PdfFixedDocument (a complete PDF document), PdfPage (individual pages with content streams), PdfPen/PdfBrush for drawing, PdfFont for text rendering, PdfFormField subtypes for interactive forms, and classes for annotations, bookmarks, outlines, and document security. The document construction model is coordinate-based: content is placed at explicit (x, y) positions on the page. Text is drawn using font objects at specified positions; images are placed at explicit coordinates; lines, rectangles, and paths are drawn using graphics operators.

XFINIUM.PDF supports reading existing PDFs and modifying their content: adding pages, modifying form field values, applying digital signatures, encrypting with passwords and permission flags, extracting text and images, redacting content, and converting to PDF/A for archival. The pure managed assembly model means no native binary deployment complexity and smaller container image footprints compared to Chromium-based libraries. This is a meaningful advantage for teams operating in environments with strict native binary policies, AppContainer sandboxes, or microservice container size budgets.

The library's platform coverage is broader than most Chromium-based PDF libraries: Xamarin.iOS, Xamarin.Android, and .NET MAUI targets are supported, which enables PDF generation on mobile devices without server round-trips. Applications that need to generate PDFs locally on a device—offline invoicing apps, field service documentation, local report export—have very few library options with this platform breadth.

What IronPDF Is Designed To Do

IronPDF is a commercial .NET library for PDF generation from HTML and PDF document manipulation. Its rendering model is HTML-first: ChromePdfRenderer accepts HTML strings, file paths, and URLs and converts them to PdfDocument objects using a bundled Chromium engine. The HTML string to PDF guide documents the primary rendering path. Because Chromium handles layout, text measurement, font rendering, and CSS interpretation, the application's responsibility is to produce valid HTML rather than to manage page coordinates or content streams.

The resulting PdfDocument supports merge, split, encrypt, sign, annotate, form-fill, and extract operations. ChromePdfRenderer is thread-safe; PdfDocument implements IDisposable. IronPDF targets .NET Framework 4.x and .NET 6+ on Windows, Linux, and macOS, distributed as a single NuGet package with platform-native Chromium binaries resolved at restore time. The rendering options reference covers paper size, margin configuration, CSS media type, and JavaScript wait conditions.

Key Limitations of XFINIUM.PDF

Product Status

XFINIUM.PDF is an actively maintained commercial product from XFINIUM Software. Verify current version and support status at the XFINIUM Software website. The library has a long history and targets a broad .NET platform range. Licensing is per-developer and per-deployment; verify current licensing terms and edition differences at the vendor website.

Missing Capabilities

XFINIUM.PDF does not provide HTML-to-PDF rendering via a browser engine. Applications that generate documents from Razor views, HTML templates, or any HTML-producing source cannot use XFINIUM.PDF's document construction API directly for those inputs. The library's construction model is coordinate-based; replicating a web-designed layout in XFINIUM.PDF requires translating HTML/CSS design decisions into explicit coordinate placement, which is laborious and brittle when designs change. A CSS table with alternating row colours, sticky headers, and computed column widths is a few lines of CSS; the equivalent in a coordinate-model library is dozens of lines of measurement and positioning code.

Applications that need to render web content (JavaScript-rendered SPA pages, pages that use CDN-hosted web fonts, responsive CSS layouts) to PDF cannot use XFINIUM.PDF for that purpose without a separate HTML renderer. This creates a two-library pattern for any application that has both web-template PDFs and coordinate-constructed PDFs—each library covering a different generation model with separate lifecycle management and API surfaces.

Technical Constraints

Coordinate-based document construction requires the application to manage the layout explicitly: calculating text widths for wrapping, managing page breaks when content overflows, tracking the current drawing position across pages, and handling font substitution for characters outside a font's glyph coverage. These are responsibilities that an HTML renderer handles automatically based on CSS rules. For applications that need flexible, content-driven layout (tables that grow with data, text blocks that wrap to the next page), the coordinate model requires significant layout logic code.

The pure managed assembly model (no native binary) is a deployment advantage but means the library does not have access to a browser rendering engine. Font measurement, Unicode text shaping, and complex script rendering are implemented in the library rather than delegated to a platform font engine.

Support Model

XFINIUM Software provides commercial support for license holders. Community resources are available via the vendor's website and documentation. Verify current support tier options and response time commitments for the license being considered.

Architectural Fit

XFINIUM.PDF is appropriate for applications that need to: fill pre-designed PDF form templates programmatically, manipulate existing PDF documents (add pages, modify fields, sign, encrypt), generate structured documents from tabular data with explicit layout control, operate in environments where native binary deployment is restricted (pure managed assembly advantage), or target Xamarin and mobile .NET platforms. It is less appropriate for applications that generate PDFs from HTML templates, need web-style CSS layout, or prioritise developer productivity over layout control granularity.

Operation Comparisons

Creating a PDF Document from Scratch (Coordinate Model)

XFINIUM.PDF — Programmatic Document Creation:

// XFINIUM.PDF coordinate-based document construction
// Package: Xfinium.Pdf
using Xfinium.Pdf;
using Xfinium.Pdf.Graphics;

// Create a new PDF document
var document = new PdfFixedDocument();

// Add a page (A4: 595 x 842 points)
var page = document.Pages.Add();
page.Width = 595;
page.Height = 842;

// Set up font and brush
var font = new PdfStandardFont(PdfStandardFontFace.Helvetica, 14);
var titleBrush = new PdfBrush(new PdfRgbColor(0x1a, 0x3c, 0x6e));
var bodyBrush = new PdfBrush(PdfRgbColor.Black);

// Draw title at explicit coordinates (x=50, y=50 from top-left, in points)
page.Graphics.DrawString(
    "Invoice #INV-2025-0042",
    font,
    titleBrush,
    50, 50);  // explicit coordinate placement

// Draw body text — developer manages line spacing
var bodyFont = new PdfStandardFont(PdfStandardFontFace.Helvetica, 11);
page.Graphics.DrawString("Bill to: Acme Corporation", bodyFont, bodyBrush, 50, 80);
page.Graphics.DrawString("Amount due: $12,450.00", bodyFont, bodyBrush, 50, 100);

// Draw a horizontal line (separator)
var pen = new PdfPen(new PdfRgbColor(0xcc, 0xcc, 0xcc), 0.5);
page.Graphics.DrawLine(pen, 50, 120, 545, 120);

// Save to file
using var stream = new System.IO.FileStream("invoice.pdf", System.IO.FileMode.Create);
document.Save(stream);

Technical constraints:

  • All positions are in PDF points (1/72 inch) from the top-left origin; the developer is responsible for all coordinate arithmetic
  • Text wrapping requires measuring string widths (page.Graphics.MeasureString(...)) and splitting content into segments manually
  • Page overflow detection—when content exceeds the page height—must be implemented by the application; XFINIUM.PDF does not paginate automatically
  • Font metric calculations for multi-line text blocks, tables, and dynamic content add substantial layout logic code
  • Verify exact class names and constructor signatures in current XFINIUM.PDF documentation; the API has evolved across versions

IronPDF — HTML-Based Document Creation:

using IronPdf;

// Layout defined in HTML/CSS — no coordinate arithmetic
var html = @"<!DOCTYPE html><html><head>
<style>
  body { font-family: Arial, sans-serif; font-size: 12px; margin: 40px; }
  .title { color: #1a3c6e; font-size: 18px; font-weight: bold; margin-bottom: 16px; }
  .separator { border: none; border-top: 1px solid #ccc; margin: 12px 0; }
  .field { margin: 6px 0; }
  table { width: 100%; border-collapse: collapse; margin-top: 20px; }
  th { background: #1a3c6e; color: white; padding: 7px; text-align: left; }
  td { padding: 6px 7px; border-bottom: 1px solid #eee; }
</style></head><body>
<div class='title'>Invoice #INV-2025-0042</div>
<hr class='separator'>
<div class='field'>Bill to: <strong>Acme Corporation</strong></div>
<div class='field'>Amount due: <strong>$12,450.00</strong></div>
<table>
  <tr><th>Description</th><th>Qty</th><th>Unit Price</th><th>Total</th></tr>
  <tr><td>Consulting Services</td><td>10</td><td>$1,100.00</td><td>$11,000.00</td></tr>
  <tr><td>Software License</td><td>1</td><td>$1,450.00</td><td>$1,450.00</td></tr>
</table>
</body></html>";

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

IronPDF's rendering model delegates layout to the Chromium engine: text wrapping, table sizing, page breaks at block boundaries, and font rendering are all CSS-driven. The HTML string to PDF guide covers base URL configuration for external stylesheets. The developer maintains a CSS template rather than coordinate arithmetic.

Filling Form Fields in an Existing PDF

XFINIUM.PDF — Form Field Filling:

// XFINIUM.PDF form field access and fill
using Xfinium.Pdf;
using Xfinium.Pdf.AcroForms;

// Load an existing PDF with AcroForm fields
using var inputStream = new System.IO.FileStream("form-template.pdf",
    System.IO.FileMode.Open, System.IO.FileAccess.Read);
var document = new PdfFixedDocument(inputStream);

// Access AcroForm fields by name
var form = document.Form;

if (form != null)
{
    // Fill text fields
    foreach (var field in form.Fields)
    {
        switch (field.Name)
        {
            case "CustomerName":
                if (field is PdfTextBoxField textField)
                    textField.Text = "Acme Corporation";
                break;
            case "InvoiceDate":
                if (field is PdfTextBoxField dateField)
                    dateField.Text = DateTime.Today.ToString("yyyy-MM-dd");
                break;
            case "PaymentMethod":
                if (field is PdfComboBoxField comboField)
                    comboField.SelectedIndex = 1; // "Wire Transfer"
                break;
            case "AgreeToTerms":
                if (field is PdfCheckBoxField checkField)
                    checkField.Checked = true;
                break;
        }
    }

    // Optionally flatten fields — makes them non-interactive
    // form.FlattenFields(); // verify method name in current documentation
}

using var outputStream = new System.IO.FileStream("form-filled.pdf",
    System.IO.FileMode.Create);
document.Save(outputStream);

Technical constraints:

  • Field access by name requires that the PDF's AcroForm field names are known at development time; verify field names by inspecting the PDF or checking the form specification
  • PdfTextBoxField, PdfCheckBoxField, PdfComboBoxField and similar types require a type check before setting values; error handling for unexpected field types needs explicit code
  • Field flattening (converting interactive fields to static content) is a one-way operation; verify method availability in current XFINIUM.PDF documentation
  • Verify exact class names and property names in current documentation

IronPDF — Form Field Filling:

using IronPdf;
using IronPdf.Forms;

// Load the PDF with form fields
using var pdf = PdfDocument.FromFile("form-template.pdf");

// Access form fields collection
var form = pdf.Form;

// Fill by field name — type inference handled by IronPDF
form["CustomerName"].Value = "Acme Corporation";
form["InvoiceDate"].Value = DateTime.Today.ToString("yyyy-MM-dd");

// Check specific form field types for type-safe operations
if (form["AgreeToTerms"] is PdfCheckBoxField checkBox)
    checkBox.Checked = true;

// Flatten all fields — makes form non-interactive
pdf.Form.Flatten();

pdf.SaveAs("form-filled.pdf");

The edit forms guide documents field access patterns, flattening, and working with combo boxes, radio groups, and signatures fields. The same PdfDocument object can be encrypted after form filling without requiring a second library.

Applying Digital Signatures

XFINIUM.PDF — Digital Signatures:

// XFINIUM.PDF digital signature application
using Xfinium.Pdf;
using Xfinium.Pdf.Security;

using var inputStream = new System.IO.FileStream("document.pdf",
    System.IO.FileMode.Open, System.IO.FileAccess.Read);
var document = new PdfFixedDocument(inputStream);

// Load the signing certificate from a PFX file
var certificate = new System.Security.Cryptography.X509Certificates.X509Certificate2(
    "signing-cert.pfx", "certPassword");

// Create a digital signature
// Verify exact API in current XFINIUM.PDF documentation
var signature = new PdfDigitalSignature();
signature.Certificate = certificate;
signature.SignatureDigestAlgorithm = PdfDigestAlgorithm.Sha256;
signature.Reason = "Approved for distribution";
signature.Location = "Chicago, IL";
signature.ContactInfo = "compliance@example.com";

// Sign the document — the signature field page and position may need to be configured
document.Sign(signature); // verify exact method name

using var outputStream = new System.IO.FileStream("document-signed.pdf",
    System.IO.FileMode.Create);
document.Save(outputStream);

Technical constraints:

  • Visible signature appearance (position, size, page) requires a signature field to be present in the document or created programmatically
  • Timestamp authority (TSA) configuration for LTV (long-term validation) signatures
  • The exact class and method names for digital signatures have evolved across XFINIUM.PDF versions; verify against current documentation

IronPDF — Digital Signatures:

using IronPdf;
using IronPdf.Signing;

// Sign any PDF — generated from HTML or loaded from an existing file
using var pdf = PdfDocument.FromFile("document.pdf");

// PdfSignature accepts PFX path, X509Certificate2, or HSM configuration
var signature = new PdfSignature("signing-cert.pfx", "certPassword")
{
    SigningReason = "Approved for distribution",
    SigningLocation = "Chicago, IL",
    SigningContact = "compliance@example.com"
};

// Sign — mutates the PdfDocument
pdf.Sign(signature);
pdf.SaveAs("document-signed.pdf");

The digital signatures guide covers PFX, X509Certificate2, visible/invisible signature placement, and HSM-backed signing. The HSM signing guide documents hardware security module integration for high-assurance signing workflows. IronPDF can sign any loaded PDF—not only PDFs it generated.

// Convert to PDF/A-2b for long-term archival

Technical constraints:

  • PDF/A conversion requires all fonts to be embedded; verify that XFINIUM.PDF embeds fonts automatically during conversion or whether font embedding must be configured
  • Output intent (ICC color profile) is required for PDF/A-2 and higher conformance levels; verify configuration in current documentation
  • PDF/A-1b, PDF/A-2b, PDF/A-3b are the most common target conformance levels; verify which levels XFINIUM.PDF supports in the current version
  • Always validate PDF/A output with an independent validator (veraPDF, Adobe Preflight) regardless of the generating library

IronPDF — PDF/A Conversion:

using IronPdf;

// Convert any loaded or generated PDF to PDF/A
using var pdf = PdfDocument.FromFile("source.pdf");

// Save as PDF/A-3b for archival compliance
pdf.SaveAsPdfA("source-pdfa.pdf", PdfAVersions.PdfA3b);

// Or convert a freshly rendered HTML document directly to PDF/A
var renderer = new ChromePdfRenderer();
using var generated = renderer.RenderHtmlAsPdf(reportHtml);
generated.SaveAsPdfA("report-pdfa.pdf", PdfAVersions.PdfA2b);

The PDF/A compliance guide documents supported conformance levels and the conversion workflow. Independent validation with veraPDF is recommended for any archival workflow regardless of the generating library.

Commonly Reported Limitations

  • Coordinate layout overhead for dynamic content. The coordinate-based construction model is efficient for documents with known, stable layouts—forms, certificates, fixed-format reports. For documents where content length varies at runtime—customer-generated text, data tables with variable row counts, multi-paragraph descriptions—the developer must implement layout logic: measuring text, tracking the current Y position, adding new pages when overflow occurs, and repeating header rows across page breaks. This logic is non-trivial to write correctly and tends to accumulate edge cases over time.
  • No HTML renderer. For applications that generate documents from web templates, Razor views, or any HTML-producing source, XFINIUM.PDF requires a design translation step: the HTML layout must be reimplemented in the coordinate model. This translation is lossy for CSS-driven designs; features like Flexbox alignment, CSS Grid placement, media queries, and web font loading from CDN have no direct coordinate-model equivalent. Teams that maintain HTML/CSS skills for web output and want to reuse those for PDF output encounter friction with the coordinate model.
  • Template reuse complexity. Changes to document layout require changes to coordinate arithmetic in application code. Unlike HTML/CSS templates where a designer can modify a stylesheet independently, XFINIUM.PDF layout changes are embedded in C# code. For applications where document design changes frequently or is maintained by non-developers, this coupling between layout and code is a maintenance overhead.
  • Mobile and multi-platform targeting. XFINIUM.PDF's Xamarin and mobile .NET support is a genuine differentiator that no Chromium-based library offers. For applications that generate PDFs on iOS or Android devices (offline PDFs, local document generation without server round-trips), XFINIUM.PDF covers a target environment that IronPDF does not. Teams working in this context should weigh this platform coverage heavily.
  • Layout logic maintenance burden. For applications with a small number of stable document types, coordinate-model layout logic is manageable. For applications with many document types or frequently changing designs, the maintenance burden scales with both the number of documents and the frequency of design changes. Every design revision requires updating coordinate arithmetic rather than editing a CSS file. The coupling between layout and code—rather than layout and template—is an ongoing cost that becomes more significant as the document portfolio grows.

Conclusion

When staying on XFINIUM.PDF is technically reasonable

XFINIUM.PDF is the right choice for applications whose dominant PDF workflow is coordinate-model document construction, form field filling in pre-designed PDF templates, or manipulation of existing PDFs. The pure managed assembly advantage matters for deployment environments with native binary restrictions. The Xamarin and mobile .NET platform support is a genuine capability gap relative to Chromium-based libraries; applications that need offline PDF generation on iOS or Android devices have few alternatives.

When migration becomes a capability or architectural mismatch

The mismatch is clearest when the application's PDF output is defined by HTML templates—invoices built from Razor views, reports styled with Bootstrap or Tailwind, documents that share CSS with the web application. Translating those HTML designs into XFINIUM.PDF coordinate placement is laborious and requires ongoing maintenance as designs evolve. Applications that need Flexbox or Grid layout, CDN web fonts, or JavaScript-rendered chart content encounter firm rendering boundaries in the coordinate model.

How IronPDF approaches the same problem differently

IronPDF uses HTML as the template format, which means the application's web design skills and tooling apply directly to PDF output. The Chromium engine handles text wrapping, page breaks, table pagination, and font rendering automatically based on CSS—eliminating the layout logic that coordinate-model libraries require the developer to write. The PdfDocument result covers manipulation, signing, encryption, and PDF/A conversion in one library. The HTML string to PDF guide is the entry point for teams evaluating the HTML-first approach against the coordinate model.

The trade-off is concrete: IronPDF requires a Chromium binary (larger deployment artifact, platform-native dependency) and requires HTML as the template format. XFINIUM.PDF requires no native binary and supports mobile targets, but requires coordinate-based layout logic. For teams that are in both worlds—some documents are form-fill operations on pre-designed PDFs, others are HTML-template-driven invoices or reports—a two-library approach (XFINIUM.PDF for form operations, IronPDF for HTML rendering) is architecturally coherent. The two libraries serve different operations and do not overlap; the integration cost of both is lower than forcing one library to do work it was not designed for.

When you examine your PDF generation workload—what proportion involves filling known-structure forms versus rendering dynamically-sized content from HTML templates—and does that proportion affect which model's overhead is more acceptable?
