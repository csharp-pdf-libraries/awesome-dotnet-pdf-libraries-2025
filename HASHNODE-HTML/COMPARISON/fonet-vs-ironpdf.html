FO.NET vs IronPDF: from install to production — compared

from install to production — compared

XSL-FO is an XML vocabulary for describing document layout and pagination, defined by the W3C as part of the XSLT specification family. Processors that implement XSL-FO take an XML document conforming to that vocabulary and produce a formatted output — most commonly PDF — by interpreting the explicit layout directives embedded in the source markup. This approach is the opposite of HTML-to-PDF rendering: rather than inferring layout from a browser's CSS cascade, XSL-FO puts every layout property in the source document explicitly, making it deterministic but verbose.

Teams that encounter XSL-FO in .NET projects typically do so in one of two contexts: maintaining a legacy document pipeline built when XSL-FO was the dominant server-side PDF standard, or inheriting an existing XML data architecture where XSLT transformations already produce FO output. Building a new pipeline on XSL-FO in 2024 is uncommon; most new projects reach for HTML-to-PDF conversion because HTML templates are editable by front-end developers and testable in a browser. The tooling for XSL-FO in .NET is correspondingly sparse.

FO.NET and IronPDF address the server-side PDF generation requirement from entirely different starting points. FO.NET targets teams locked into an XSL-FO pipeline; IronPDF targets teams using HTML as the content representation. Understanding the trade-offs between these approaches matters when evaluating whether to migrate an FO-based pipeline or when choosing a tool for a new project.

What FO.NET Is Designed To Do

FO.NET is an open-source .NET library that processes XSL-FO documents and generates PDF output. It implements a subset of the XSL-FO 1.1 specification, allowing .NET applications to pass an XML document conforming to the FO namespace to the processor and receive a PDF stream or file in return.

The typical usage pattern in a FO.NET pipeline is: transform application data to XML using XSLT (or build the FO document programmatically), pass the FO XML to FO.NET's driver, and receive the rendered PDF. The library does not provide HTML rendering, a document object model for PDF manipulation, or post-generation operations. Its scope is the rendering of XSL-FO markup into a PDF byte stream.

FO.NET is an open-source project and has not seen active development for an extended period. It targets .NET Framework; modern .NET (Core, 5+) compatibility requires verification. The library's primary value is in scenarios where XSL-FO is already the established data format and a managed .NET processor is needed without licensing cost.

What IronPDF Is Designed To Do

IronPDF is a .NET PDF library built around a Chromium-based rendering engine. Its primary workflow converts HTML, CSS, and JavaScript into PDFs that reproduce browser-level rendering fidelity, which suits teams whose content originates as web templates. The HTML string to PDF guide describes the main entry point and configuration options for the rendering path.

Beyond rendering, IronPDF provides a document manipulation layer covering merge, split, stamping, headers and footers, digital signatures, encryption, permissions, PDF/A and PDF/UA compliance conversion, form creation and filling, text and image extraction, redaction, and barcode embedding. The library is self-contained — the Chromium engine runs in-process without external service calls — and targets server-side .NET workloads on Windows, Linux, macOS, and container environments. The docs overview describes both the rendering and manipulation tiers of the library.

Key Limitations of FO.NET

Product Status

FO.NET is an open-source project with no visible recent development activity. NuGet package history and GitHub repository activity — when available — indicate the project has been in maintenance stasis for years. Modern .NET runtime support (Core, .NET 5, 6, 7, 8) is not documented and should be verified empirically before any adoption. Teams building new systems on FO.NET take on the risk of an unmaintained dependency; any bugs encountered in the renderer are unlikely to be fixed by the upstream project.

Missing Capabilities

FO.NET's scope is XSL-FO rendering only. It provides no post-render document operations: no digital signing, no PDF/A compliance conversion, no encryption, no form field management, no text extraction, no merge or split, and no watermarking. A production pipeline that needs any of these operations alongside FO rendering requires a second library.

HTML-to-PDF conversion is not a capability of FO.NET; the library does not expose an HTML renderer. Teams whose content is authored as HTML templates would need a separate tool entirely.

Technical Constraints

FO.NET's implementation covers a subset of the XSL-FO specification, not the full standard. Complex FO features — advanced page sequencing, conditional page masters, certain table layout edge cases — may not render correctly or may be silently ignored. Testing FO.NET output against a compliant reference processor (such as Apache FOP) is advisable before committing FO.NET to production.

Performance under concurrent load is not documented. XSL-FO rendering is computationally expensive for complex documents; the library's threading model and memory characteristics under high throughput should be profiled.

Support Model

As an open-source project with inactive development, support is limited to community resources, historical issue trackers, and documentation that may not reflect the current codebase state. There is no commercial support, no SLA, and no vendor to contact for blocking issues. Production deployment of FO.NET effectively means the team owns the library.

Architectural Fit

FO.NET fits exclusively in pipelines that are already built around XSL-FO as the document format — typically XSLT-based transformation pipelines that produce FO output from XML data. For any new project, teams that control the content format have no technical reason to adopt XSL-FO over HTML; the tooling ecosystem, developer familiarity, and CSS rendering standards all favor HTML-based approaches. FO.NET is a legacy maintenance tool, not a new-project foundation.

Operation Comparisons

FO.NET — XSL-FO Document to PDF

using System.IO;
using Fonet;  // FO.NET namespace

// FO.NET: convert an XSL-FO XML document to PDF
// Verify Driver class name and method signatures in current documentation

// Load the FO document (produced by XSLT or authored directly)
string foXml = File.ReadAllText("document.fo");

// Create the FO driver and configure output
var driver = FonetDriver.Make();

using var outputStream = new FileStream("output.pdf", FileMode.Create);

// Process the FO document — exact method name: verify in FO.NET source / docs
driver.Render(new StringReader(foXml), outputStream);

Technical constraints:

  • Only a subset of XSL-FO 1.1 is implemented; complex FO constructs may not render or may render incorrectly.
  • No mechanism to apply digital signatures, encryption, or PDF/A conversion to the output — requires a second library.
  • .NET Framework dependency; .NET Core / .NET 5+ compatibility must be tested empirically.
  • Concurrent rendering is not documented; thread-safety of FonetDriver instances is unverified.
  • Font configuration may require explicit setup; missing fonts produce substitution without always warning.

IronPDF — Equivalent Rendering from XML Data

using IronPdf;
using System.Xml;
using System.Xml.Xsl;
using System.IO;

// In an XSL-FO migration scenario, XSLT produces HTML rather than FO.
// The HTML is then rendered by IronPDF's Chromium engine.

// Step 1: Transform XML data to HTML via XSLT
var transform = new XslCompiledTransform();
transform.Load("data-to-html.xslt");   // your XSLT producing HTML output

using var xmlReader = XmlReader.Create("data.xml");
using var htmlWriter = new StringWriter();
transform.Transform(xmlReader, null, htmlWriter);
string renderedHtml = htmlWriter.ToString();

// Step 2: Convert HTML to PDF with IronPDF
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

using var pdf = renderer.RenderHtmlAsPdf(renderedHtml);
pdf.SaveAs("output.pdf");

When migrating from an XSL-FO pipeline, the XSLT transformation step is typically retargeted to produce HTML rather than FO markup. IronPDF then renders that HTML using the Chromium engine, which applies full CSS3 and resolves external resources. The HTML string to PDF guide covers base URL configuration for relative asset resolution, and the rendering options guide describes paper size, margin, and CSS media type settings that parallel FO page layout properties.

IronPDF — Rendering with Immediate Post-Processing

using IronPdf;
using IronPdf.Signing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Render from HTML
using var pdf = renderer.RenderHtmlAsPdf(GetDocumentHtml());

// Apply digital signature in the same library, no second dependency
var signature = new PdfSignature("company_cert.pfx", "password")
{
    Reason   = "Document approval",
    Location = "Pipeline step 3"
};
pdf.Sign(signature);

// Encrypt and set permissions
pdf.SecuritySettings.OwnerPassword              = "ownerPass";
pdf.SecuritySettings.AllowUserCopyPasteContent  = false;

pdf.SaveAs("output_signed.pdf");

IronPDF performs rendering and all post-render operations within the same library. The digital signatures guide covers certificate loading, visual placement, and LTV options; the PDF permissions guide covers encryption and user capability restrictions — both within a single PdfDocument lifecycle.

Technical constraints:

  • No native merge means a three-library pipeline for render + merge + sign.
  • Byte array buffering between steps increases memory pressure for large documents.
  • Dependency on an unmaintained renderer as the first step creates a fragile pipeline foundation.

IronPDF — Merge Multiple Rendered PDFs

using IronPdf;

// Render two HTML sections as separate PDF documents
var renderer = new ChromePdfRenderer();

using var coverPage  = renderer.RenderHtmlAsPdf(GetCoverHtml());
using var bodyPages  = renderer.RenderHtmlAsPdf(GetBodyHtml());
using var appendix   = renderer.RenderHtmlAsPdf(GetAppendixHtml());

// Merge all into one document
using var merged = PdfDocument.Merge(coverPage, bodyPages, appendix);

// Add bookmarks for navigation
merged.Bookmarks.AddBookMarkAtStart("Cover", 0);
merged.Bookmarks.AddBookMarkAtStart("Body",  coverPage.PageCount);

merged.SaveAs("final_document.pdf");

IronPDF's merge and split guide covers merging two or more PdfDocument instances, including stream-based overloads and bookmark preservation. For pipelines that render sections independently and assemble them, this pattern avoids intermediate file writes and keeps all document state in memory until final save.

Commonly Reported Limitations

FO.NET:

  • The project's stale maintenance status is consistently cited as the primary concern. Teams report that bugs encountered in the renderer remain unfixed indefinitely, and the only resolution path is working around the issue in the FO markup.
  • XSL-FO specification coverage is incomplete; complex table layouts, certain block container behaviors, and advanced page sequencing features are reported as producing incorrect or absent output. Teams compare output against Apache FOP (the reference Java implementation) and note discrepancies.
  • Modern .NET runtime compatibility is a recurring operational concern. Teams that have upgraded their .NET Framework applications to modern .NET report that FO.NET requires compatibility shims or does not function without modification.
  • The absence of post-render operations means every production pipeline built on FO.NET has at least one additional library dependency, which compounds maintenance risk given FO.NET's inactive state.
  • Font handling requires explicit configuration and is reported as unintuitive; missing font mappings produce fallback substitution without clear error reporting.

Conclusion

When staying on FO.NET is technically reasonable

Teams with a functioning legacy pipeline whose FO markup is stable, whose deployment environment remains .NET Framework on Windows, and where the document templates are not changing have limited practical incentive to migrate. If the pipeline works, the FO markup is already authored and tested, and there are no requirements for post-render operations or modern runtime support, the switching cost is not easily justified by capability gains. The risk profile changes only when the platform must migrate to modern .NET, when new document types are needed, or when the pipeline must run on Linux.

When migration becomes a capability or architectural mismatch

Any requirement for digital signatures, PDF/A compliance, encryption, text extraction, or merge operations cannot be met by FO.NET and requires additional libraries — each of which is an additional maintenance burden. If the deployment environment moves to .NET 6+ or Linux containers, FO.NET's compatibility is uncertain. If templates need to be authored or modified by developers who work in HTML and CSS, requiring them to learn XSL-FO is a meaningful onboarding cost with no compensating technical benefit for new development.

How IronPDF approaches the same problem

IronPDF replaces the XSL-FO rendering step with an HTML-to-PDF path via Chromium, and provides the full post-render operation suite within the same library. XSLT pipelines can be retargeted to produce HTML output rather than FO markup, preserving the data transformation logic while gaining browser-level CSS fidelity and a maintained rendering engine. The IronPDF docs overview describes the complete API surface for teams evaluating the migration scope from an FO-based pipeline.
