Gotenberg vs IronPDF: what the docs do not cover

the engineering breakdown for .NET teams

Problem Framing

Containerised microservice architectures have changed how teams think about deploying heavy native dependencies. When a library requires a browser engine or an Office runtime, one approach is to run that dependency in a separate container and expose it as a service over HTTP. This pattern sidesteps the deployment complexity of embedding the native dependency in every application that needs it, enables the heavy process to scale independently, and lets the consuming applications remain thin—just an HTTP client sending a request and receiving a PDF in return.

Gotenberg is the most prominent open-source implementation of this pattern for PDF generation. It packages Chromium (for HTML-to-PDF) and LibreOffice (for document conversion) into a single Docker container and exposes a stateless HTTP API. Consuming applications make multipart form data requests to the /forms/chromium/convert/html or equivalent endpoints and receive rendered PDFs. The architectural appeal is clear: the complexity of Chromium deployment is concentrated in the Gotenberg container, and all application languages—.NET, Go, Python—get PDF generation through a standard HTTP call.

The trade-offs of this architecture are less visible in the documentation. HTTP-based rendering introduces network latency, serialisation overhead, and operational dependency on a running service. For .NET applications specifically, the service dependency pattern differs meaningfully from an in-process library: error handling, retry logic, payload size limits, and concurrency management are all different problems. Understanding where those differences are felt in production is what this article addresses.

What Gotenberg Is Designed To Do

Gotenberg is an open-source stateless API server for PDF generation and conversion, distributed as a Docker image (gotenberg/gotenberg). It wraps Chromium and LibreOffice in a container and exposes HTTP endpoints for operations including HTML-to-PDF conversion (using Chromium), URL-to-PDF conversion, Office document conversion to PDF (using LibreOffice), PDF merging, and image-to-PDF conversion. The API accepts multipart form data requests; consuming applications send HTML content, URL strings, or document files as form fields and receive the generated PDF as a binary HTTP response.

Gotenberg's design is language-agnostic; any client that can make HTTP requests can consume it. For .NET, this typically means using HttpClient with MultipartFormDataContent, or a community .NET client library that wraps the API. Gotenberg is actively maintained and is available under the MIT license. It is designed to run as a sidecar container or shared service within a Docker Compose, Kubernetes, or similar container orchestration environment.

What IronPDF Is Designed To Do

IronPDF is an in-process .NET library. It does not require a running service, a container, or an HTTP call. A ChromePdfRenderer instance is instantiated within the application process, and rendering occurs in that process via bundled Chromium binaries. The rendered PdfDocument is a managed .NET object with a full API surface for manipulation, returned directly to the caller without serialisation through an HTTP boundary.

PdfDocument implements IDisposable; ChromePdfRenderer is thread-safe and can be shared across concurrent requests. The async rendering guide covers RenderHtmlAsPdfAsync() and RenderUrlAsPdfAsync(), which integrate with ASP.NET Core's async pipeline without Task.Run() wrappers. IronPDF ships as a single NuGet package that resolves the correct platform-native Chromium binaries for Windows, Linux, and macOS at restore time, targeting .NET Framework 4.x and .NET 6+. There is no sidecar container to deploy, no service health check to monitor, and no HTTP payload size limit to manage.

Key Limitations of Gotenberg

Product Status

Gotenberg is an actively maintained open-source project. Its maintenance status is community and contributor-driven. Verify current release cadence and long-term maintenance commitment before adopting it as a critical production dependency.

Missing Capabilities

Gotenberg is a conversion service; it does not provide PDF manipulation operations on the result. After the HTTP response is received, the .NET application has a byte[] and no further API surface on that object. Merging generated PDFs, encrypting output, applying digital signatures, filling form fields, extracting text, or annotating the output all require a separate .NET library. Any workflow that goes beyond raw generation adds a second dependency with its own API, disposal semantics, and operational overhead.

Technical Constraints

Gotenberg is an external service. Every PDF generation operation in the .NET application involves at least one HTTP round trip, serialisation of the HTML payload as multipart form data, network latency, and deserialisation of the binary response. For large HTML payloads, the overhead is non-trivial. Under high concurrency, scaling Gotenberg independently of the application adds operational complexity—the application's request throughput is bounded by Gotenberg's pod count and rendering capacity. If Gotenberg is unavailable (container failure, deployment window, network partition), the application cannot generate PDFs and must handle that failure mode explicitly.

Support Model

Support for Gotenberg is community-driven via GitHub Issues and Discussions. There is no commercial support offering. Production incidents involving rendering behaviour require debugging through the Chromium version bundled in the Gotenberg image—which may differ from browser versions in the team's test environment. The .NET client libraries are community-maintained; verify their current status.

Architectural Fit

Gotenberg fits polyglot microservice environments where multiple services in multiple languages need PDF generation, and concentrating the Chromium deployment in one place reduces total operational overhead. It is a less natural fit for .NET-only applications where an in-process library eliminates the service dependency without adding operational complexity, or for applications that need post-generation manipulation in the same library.

Operation Comparisons

HTML String to PDF

Gotenberg — HTML to PDF via HTTP:

// Gotenberg HTML to PDF — using HttpClient
// No official first-party .NET SDK; using HttpClient directly
using System.Net.Http;
using System.Net.Http.Headers;

public class GotenbergPdfService
{
    private readonly HttpClient _http;

    // Inject HttpClient via IHttpClientFactory in production
    public GotenbergPdfService(HttpClient http)
    {
        _http = http;
    }

    public async Task<byte[]> HtmlToPdfAsync(string htmlContent)
    {
        // Gotenberg expects multipart/form-data with an index.html file
        using var form = new MultipartFormDataContent();

        var htmlBytes = System.Text.Encoding.UTF8.GetBytes(htmlContent);
        var htmlPart = new ByteArrayContent(htmlBytes);
        htmlPart.Headers.ContentType = new MediaTypeHeaderValue("text/html");
        form.Add(htmlPart, "files", "index.html");

        // POST to the Chromium HTML convert endpoint
        var response = await _http.PostAsync(
            "http://gotenberg:3000/forms/chromium/convert/html", form);

        response.EnsureSuccessStatusCode();

        return await response.Content.ReadAsByteArrayAsync();
    }
}

Technical constraints:

  • HTML content with external assets (CSS, images) requires sending those assets as additional form parts or providing fully self-contained HTML with inlined styles and base64-encoded images
  • Network latency between the application container and Gotenberg container adds to every render time
  • Gotenberg has configurable request timeouts; complex renders that exceed the timeout return a 504 error
  • The result is a byte[]; no further PDF manipulation API is available without a second library
  • If Gotenberg is unavailable, this call fails; the application must implement retry and fallback logic

IronPDF — HTML String to PDF (in-process):

using IronPdf;

// ChromePdfRenderer is thread-safe; can be a static or singleton instance
private static readonly ChromePdfRenderer Renderer = new ChromePdfRenderer();

public async Task<byte[]> HtmlToPdfAsync(string htmlContent)
{
    Renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
    Renderer.RenderingOptions.MarginTop = 15;
    Renderer.RenderingOptions.MarginBottom = 15;

    // In-process Chromium render — no network hop, no service dependency
    using var pdf = await Renderer.RenderHtmlAsPdfAsync(htmlContent);

    // PdfDocument carries the full manipulation API before byte extraction
    return pdf.BinaryData;
}

IronPDF renders in-process using the bundled Chromium engine; there is no container to manage or network call to make. The HTML string to PDF guide covers base URL configuration for resolving relative assets—useful for HTML templates that reference external CSS or images without requiring those assets to be inlined or sent as form parts.

URL to PDF

Gotenberg — URL to PDF via HTTP:

// Gotenberg URL to PDF
using System.Net.Http;

public async Task<byte[]> UrlToPdfAsync(HttpClient http, string url)
{
    using var form = new MultipartFormDataContent();
    form.Add(new StringContent(url), "url");

    // Gotenberg Chromium URL endpoint
    var response = await http.PostAsync(
        "http://gotenberg:3000/forms/chromium/convert/url", form);

    response.EnsureSuccessStatusCode();
    return await response.Content.ReadAsByteArrayAsync();
}

Technical constraints:

  • Gotenberg's Chromium instance fetches the URL; the URL must be reachable from the Gotenberg container's network namespace, not necessarily from the application container's namespace—a common source of "works locally, fails in K8s" problems
  • Authenticated URLs require cookies or auth headers to be passed via additional form fields; verify current API for cookie jar configuration
  • Wait conditions for JS-rendered SPAs are configured via form fields (e.g., waitDelay, waitForExpression)

IronPDF — URL to PDF (in-process):

using IronPdf;

var renderer = new ChromePdfRenderer();

// Inject cookies for authenticated pages
renderer.RenderingOptions.CustomCookies = new System.Collections.Generic.Dictionary<string, string>
{
    { "session_id", "abc123" }
};

// Wait for JS to finish rendering before snapshot
renderer.RenderingOptions.WaitFor.RenderDelay(500);

using var pdf = await renderer.RenderUrlAsPdfAsync("https://myapp.example.com/report");
pdf.SaveAs("report.pdf");

The URL to PDF guide covers cookie injection for authenticated pages, custom request headers, and the WaitFor API. In-process rendering means the URL is fetched from the application host's network namespace, which eliminates the container-network-boundary problem that affects Gotenberg deployments.

LibreOffice Document Conversion (Gotenberg) vs. Built-in DOCX (IronPDF)

Gotenberg — DOCX to PDF via LibreOffice:

// Gotenberg DOCX to PDF using LibreOffice
using System.Net.Http;
using System.Net.Http.Headers;

public async Task<byte[]> DocxToPdfAsync(HttpClient http, byte[] docxBytes)
{
    using var form = new MultipartFormDataContent();

    var docxPart = new ByteArrayContent(docxBytes);
    docxPart.Headers.ContentType =
        new MediaTypeHeaderValue("application/vnd.openxmlformats-officedocument.wordprocessingml.document");
    form.Add(docxPart, "files", "document.docx");

    // Gotenberg LibreOffice convert endpoint
    var response = await http.PostAsync(
        "http://gotenberg:3000/forms/libreoffice/convert", form);

    response.EnsureSuccessStatusCode();
    return await response.Content.ReadAsByteArrayAsync();
}

Technical constraints:

  • LibreOffice conversion fidelity depends on the LibreOffice version in the Gotenberg image and the document's use of proprietary Word features
  • The Gotenberg container must be built with LibreOffice support enabled (the full image, not the slim image)
  • Large documents may time out; configure Gotenberg-Chromium-Wait-Delay or equivalent timeout headers
  • Result is a byte[] with no further manipulation API

IronPDF — DOCX to PDF (in-process, no LibreOffice required):

using IronPdf;

// Convert DOCX directly — no LibreOffice installation or container required
using var pdf = PdfDocument.FromDocx("document.docx");

// Post-conversion manipulation available immediately
pdf.SecuritySettings.AllowUserPrint = true;
pdf.SaveAs("document.pdf");

IronPDF's DOCX conversion does not require LibreOffice or Office to be installed. The result is a PdfDocument on which all manipulation operations are immediately available—security settings, signing, merging—without an additional library or service call.

Merging PDFs After Generation

Gotenberg — Merging PDFs:

Gotenberg provides a /forms/pdfengines/merge endpoint for merging PDFs. This requires a second HTTP request to Gotenberg after the initial generation.

// Gotenberg PDF merge — requires a second HTTP call
using System.Net.Http;
using System.Net.Http.Headers;

public async Task<byte[]> MergePdfsAsync(HttpClient http,
    IEnumerable<(string Name, byte[] Bytes)> pdfParts)
{
    using var form = new MultipartFormDataContent();

    foreach (var (name, bytes) in pdfParts)
    {
        var part = new ByteArrayContent(bytes);
        part.Headers.ContentType = new MediaTypeHeaderValue("application/pdf");
        form.Add(part, "files", name);
    }

    var response = await http.PostAsync(
        "http://gotenberg:3000/forms/pdfengines/merge", form);

    response.EnsureSuccessStatusCode();
    return await response.Content.ReadAsByteArrayAsync();
}

Technical constraints:

  • Two HTTP calls required for generate + merge: one to render each document, one to merge
  • Total payload size grows with the number and size of source PDFs; large document sets may hit Gotenberg's request body size limit
  • Network latency is paid twice for two-step workflows; three or more steps compound further

IronPDF — Merge in the Same Library, No Additional HTTP Call:

using IronPdf;
using System.Linq;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Generate all sections in-process
var htmlSections = new[] { coverHtml, bodyHtml, appendixHtml };
var docs = htmlSections.Select(h => renderer.RenderHtmlAsPdf(h)).ToList();

try
{
    using var merged = PdfDocument.Merge(docs);

    // Apply encryption to the final merged document
    merged.SecuritySettings.OwnerPassword = "ownerPass";
    merged.SaveAs("final-document.pdf");
}
finally
{
    foreach (var doc in docs) doc.Dispose();
}

The merge and split guide documents the merge API in detail. Because all operations—render, merge, encrypt—happen in-process on the same PdfDocument objects, there is no HTTP round trip between steps.

Commonly Reported Limitations

  • Network boundary complexity for URL rendering. When Gotenberg renders a URL, it fetches from the Gotenberg container's network context. In Kubernetes deployments where service mesh policies, network policies, or internal DNS differ between the application pod and the Gotenberg pod, a URL that the application can reach may be unreachable from Gotenberg. This manifests as intermittent failures that are difficult to reproduce locally.
  • Asset delivery for HTML rendering. Self-contained HTML with inline CSS and base64-encoded images works reliably. HTML that references external files (stylesheets, images, fonts) requires either co-deploying those assets where Gotenberg can fetch them or inlining them before the API call. For complex templates with many assets, the inlining step adds pre-processing logic.
  • Byte array output with no manipulation API. Every post-generation operation—merge, encrypt, sign—requires either a second Gotenberg API call or a separate .NET PDF library. Teams often start with Gotenberg and discover they need a separate .NET library for manipulation anyway, ending up with two dependencies instead of one.
  • Operational dependency. Gotenberg must be running, healthy, and reachable for any PDF generation to succeed. This introduces liveness and readiness probe requirements, circuit breaker patterns, and fallback handling that an in-process library does not require.
  • Payload size limits. Gotenberg has configurable maximum request body sizes. Large HTML documents, many merged PDFs, or large DOCX files can hit the default limit. Tuning this requires configuration at the container level, which may not always be within the application team's operational control.

Conclusion

When staying on Gotenberg is technically reasonable

Gotenberg is architecturally well-suited for polyglot microservice environments where multiple services in different languages need PDF generation. Concentrating Chromium and LibreOffice in a single container rather than embedding native dependencies in each service is a genuine operational simplification in that context. For teams with strong Kubernetes operational capabilities, a centrally managed Gotenberg deployment provides PDF generation as a service to many consumers. The LibreOffice integration for Office document conversion is a genuine capability that IronPDF does not replicate for the full range of Office formats.

When migration becomes a capability or architectural mismatch

The service-dependency model creates friction for .NET-only applications where an in-process library is simpler to deploy, test, and operate. The byte-array-only output forces every post-generation manipulation—encrypt, sign, merge, annotate—through either additional Gotenberg endpoint calls (adding HTTP round trips) or a second .NET library (adding a dependency). For applications that need both generation and manipulation, the two-dependency/two-endpoint pattern often proves more complex than a single in-process library. Teams on .NET-only stacks building applications with moderate-to-high PDF complexity frequently revisit this trade-off.

How IronPDF approaches the same problem differently

IronPDF embeds the rendering, manipulation, and conversion capabilities in a single in-process library. There is no container to deploy, no HTTP call to make, and no service to monitor. The PdfDocument result of any rendering or loading operation carries the full manipulation API—merge, encrypt, sign, extract—without a second library or a second HTTP call. The async rendering guide covers the full async API surface; ChromePdfRenderer is thread-safe, enabling concurrent in-process rendering without the Kubernetes orchestration overhead of scaling a Gotenberg deployment.
