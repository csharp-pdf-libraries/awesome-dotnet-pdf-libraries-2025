Scryber.Core vs IronPDF: what the docs do not cover

a .NET engineer reference for 2026

Problem Framing

Document template formats for PDF generation span a broad spectrum: raw coordinate drawing, HTML/CSS rendering, proprietary XML schemas, and data-bound report engines. Libraries that use XML as a template format occupy an interesting middle position—they provide a declarative, structured authoring model that is closer to HTML than to coordinate drawing, but produces PDF output without requiring a browser engine. For .NET teams that need to define document templates in markup rather than code, XML-driven PDF libraries offer a specific trade-off: separable template files, structured data binding, and a layout model that does not depend on CSS.

Scryber.Core is an open-source .NET library that takes this approach. Templates are defined in XML (.pdfx files or inline XML) with a schema that covers pages, sections, paragraphs, tables, images, and style attributes. Data is bound to templates using a data model and binding expressions. The output is a PDF document. For teams that want a designer-friendly, non-code template format for structured documents—forms, certificates, structured reports with defined sections—this model has genuine appeal.

The comparison with IronPDF is not about which library is "better" in isolation, but about which architectural approach fits the team's requirements. XML template authoring separates content structure from rendering code; HTML/CSS rendering leverages the web skills and tooling most .NET teams already have. Understanding when each approach produces less friction is the evaluation question.

There is also a deployment dimension to this comparison. Scryber.Core is a pure managed assembly with no native binary dependencies. IronPDF bundles Chromium, which adds to the package size and introduces a platform-native binary that must be deployed with the application. For teams operating in environments with strict native binary policies—certain regulated industries, air-gapped systems, or containers with minimal image requirements—the pure managed option has practical value beyond aesthetics. Conversely, for teams that are already deploying Chromium-based applications and have no binary restrictions, the deployment difference is operational overhead rather than a policy constraint. These deployment characteristics should be evaluated alongside the template authoring model when choosing between the two approaches.

What Scryber.Core Is Designed To Do

Scryber.Core is an open-source .NET library (MIT/LGPL license

The library targets .NET Standard 2.1 and .NET 5+. It is distributed as Scryber.Core and related packages via NuGet. The rendering is entirely managed—Scryber implements its own layout engine, text measurement, and PDF output generation in C# without native binary dependencies. This is a meaningful deployment advantage in environments where native binary deployment is restricted.

Scryber.Core provides programmatic document construction as an alternative to XML templates for teams that prefer a code-first model. However, the XML template model is the library's distinctive feature and primary use case. Verify current feature coverage for advanced layout scenarios (complex multi-column content, running headers with dynamic content, precise typographic control) against current documentation.

What IronPDF Is Designed To Do

IronPDF is a commercial .NET library that uses a bundled Chromium engine to convert HTML, CSS, and JavaScript to PDF documents. The template model is HTML: any source that produces valid HTML—Razor views, Scriban templates, string builders, Markdown transpilers—is an acceptable input. The Chromium engine handles layout, text measurement, pagination, font rendering, and CSS interpretation; the application's responsibility is to produce the HTML. The HTML string to PDF guide documents the primary rendering path.

The PdfDocument result supports merge, split, encrypt, sign, annotate, form-fill, and extract operations on the same object without additional libraries. ChromePdfRenderer is thread-safe; PdfDocument implements IDisposable. IronPDF targets .NET Framework 4.x and .NET 6+ on Windows, Linux, and macOS, distributed as a single NuGet package. The rendering options reference covers paper size, CSS media type, margin configuration, and JavaScript wait conditions.

Key Limitations of Scryber.Core

Product Status

Scryber.Core is an actively maintained open-source project. The project has a single primary maintainer; verify recent commit activity and issue response patterns before committing to production adoption. The library has been in development since before the Scryber.Core name and represents a mature codebase for its approach.

Missing Capabilities

Scryber.Core does not provide HTML-to-PDF rendering via a browser engine. Applications that generate documents from Razor views, HTML templates, or any HTML-producing source must either rewrite their templates in Scryber's XML schema or add a separate HTML renderer alongside Scryber. The rewrite cost is non-trivial for complex templates; applications with extensive existing HTML templates may find the migration effort disproportionate to the benefit.

The library also does not provide digital signatures, HSM signing, or text redaction

Scryber's XML template model has a learning curve distinct from HTML/CSS. Teams with strong web development backgrounds may find the XML schema less familiar than HTML markup. Template development tooling—syntax highlighting, schema validation, live preview—for .pdfx files is less mature than for HTML in modern IDEs. The feedback loop for template development is slower: templates must be rendered by the library to see the output, whereas HTML templates can be previewed in any browser.

Technical Constraints

Scryber's pure managed assembly model (no native binary) is a deployment advantage but places all layout and text measurement logic in C#. For complex documents with precise typographic requirements—full justification, kerning, baseline grid alignment—the managed layout engine may have different behaviour than a browser-based renderer. Verify current text layout accuracy for the document types the application generates.

Performance for high-volume generation should be benchmarked against application requirements; a pure managed engine has a different performance profile than a Chromium-based renderer. Verify thread safety for concurrent PDF generation under ASP.NET Core load.

Support Model

Support is community-driven via GitHub Issues. There is no commercial support tier. For a free, actively maintained open-source project, community support is appropriate; teams should plan for self-sufficiency in debugging layout issues.

Architectural Fit

Scryber.Core is appropriate for applications that benefit from separating document template authorship from application code—teams where non-developers maintain template files, applications with many stable document types defined as discrete template files, or environments where HTML/CSS rendering engines cannot be deployed (due to size or native binary constraints). It is less appropriate for applications that already invest in HTML/CSS templates for web and want to reuse that knowledge for PDF output.

Operation Comparisons

Generating a PDF from an XML Template

Scryber.Core — XML Template to PDF:

// Scryber.Core XML template rendering
// Package: Scryber.Core
using Scryber.Components;

// Define the data model that binds to the template
public class InvoiceModel
{
    public string CustomerName { get; set; }
    public DateTime InvoiceDate { get; set; }
    public List<LineItem> Lines { get; set; }
}

public class LineItem
{
    public string Description { get; set; }
    public int Quantity { get; set; }
    public decimal UnitPrice { get; set; }
}

// -- Invoice.pdfx (XML template file, deployed with application) --
// <?xml version="1.0" encoding="utf-8" ?>
// <pdf:Document xmlns:pdf="http://www.scryber.co.uk/schemas/core/release/v1/Scryber.Components.xsd"
//               xmlns:styles="http://www.scryber.co.uk/schemas/core/release/v1/Scryber.Styles.xsd"
//               xmlns:data="http://www.scryber.co.uk/schemas/core/release/v1/Scryber.Data.xsd" >
//   <pdf:Pages>
//     <pdf:Page>
//       <pdf:Content>
//         <pdf:Label id="CustomerName" value="{@:Model.CustomerName}" />
//         <data:ForEach id="LineItems" select="{@:Model.Lines}" >
//           <pdf:Label value="{@:.Description}" />
//         </data:ForEach>
//       </pdf:Content>
//     </pdf:Page>
//   </pdf:Pages>
// </pdf:Document>

public byte[] GenerateInvoice(InvoiceModel model)
{
    // Load template from file or embedded resource
    using var doc = PDFDocument.ParseDocument("Templates/Invoice.pdfx");

    // Bind the model to the document parameters
    doc.Params["Model"] = model;

    // Render to stream
    using var ms = new System.IO.MemoryStream();
    doc.ProcessDocument(ms);
    return ms.ToArray();
}

Technical constraints:

  • .pdfx template files must be deployed alongside the application; layout changes require template file updates and redeployment
  • Binding expression syntax ({@:Model.Property}) is Scryber-specific and distinct from Razor or other .NET template syntaxes
  • Complex conditional rendering, custom formatting logic, or data aggregation in templates requires knowledge of Scryber's expression language
  • Verify current API stability—Scryber.Core has evolved significantly and some API surface has changed across versions
  • Thread safety for concurrent PDFDocument.ParseDocument() calls

IronPDF — HTML Template to PDF:

using IronPdf;
using System.Text;

// Data model
var model = new
{
    CustomerName = "Acme Corporation",
    InvoiceDate = DateTime.Today,
    Lines = new[]
    {
        new { Description = "Consulting", Quantity = 10, UnitPrice = 150.00m },
        new { Description = "Software License", Quantity = 1, UnitPrice = 2400.00m }
    }
};

// HTML template assembled in C# — Chromium renders all CSS3
var sb = new StringBuilder();
sb.Append(@"<!DOCTYPE html><html><head>
<style>
  body { font-family: Arial, sans-serif; font-size: 12px; margin: 40px; }
  .header { display: flex; justify-content: space-between; margin-bottom: 24px; }
  h2 { color: #1a3c6e; margin: 0; }
  table { width: 100%; border-collapse: collapse; }
  th { background: #1a3c6e; color: white; padding: 8px; text-align: left; }
  td { padding: 7px 8px; border-bottom: 1px solid #e8e8e8; }
  .total { font-weight: bold; background: #f5f8fc; }
</style></head><body>
<div class='header'>
  <h2>Invoice</h2>
  <div>" + model.InvoiceDate.ToString("yyyy-MM-dd") + @"</div>
</div>
<p>Bill to: " + model.CustomerName + @"</p>
<table>
  <tr><th>Description</th><th>Qty</th><th>Unit Price</th><th>Total</th></tr>");

decimal total = 0;
foreach (var line in model.Lines)
{
    var lineTotal = line.Quantity * line.UnitPrice;
    total += lineTotal;
    sb.Append($"<tr><td>{line.Description}</td><td>{line.Quantity}</td>" +
              $"<td>{line.UnitPrice:C}</td><td>{lineTotal:C}</td></tr>");
}
sb.Append($"<tr class='total'><td colspan='3'>Total</td><td>{total:C}</td></tr>");
sb.Append("</table></body></html>");

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

using var pdf = renderer.RenderHtmlAsPdf(sb.ToString());
pdf.SaveAs("invoice.pdf");

IronPDF accepts HTML from any source. For teams using Razor outside MVC, Scriban, or other .NET template engines that produce HTML output, the template file remains a familiar format. The HTML string to PDF guide covers base URL configuration for external CSS stylesheets.

// In the .pdfx template:
// <data:ForEach select="{@:Model.Rows}" >
//   <pdf:TableRow>
//     <pdf:TableCell><pdf:Label value="{@:.Name}" /></pdf:TableCell>
//     <pdf:TableCell><pdf:Label value="{@:.Amount}" /></pdf:TableCell>
//   </pdf:TableRow>
// </data:ForEach>

// In C#:
// doc.Params["Model"] = new { Rows = myDataList };
// doc.ProcessDocument(outputStream);

Technical constraints:

  • The ForEach data element iterates a bound collection; nested aggregation requires Scryber's expression language
  • Table pagination (a table that spans multiple pages) is handled by Scryber's layout engine; verify behaviour for very long tables
  • Dynamic column counts (where the number of columns is not known at template design time) require programmatic construction rather than a purely declarative template

IronPDF — Data-Bound Table via HTML:

using IronPdf;
using System.Text;
using System.Collections.Generic;

var rows = new List<(string Name, decimal Amount)>
{
    ("Service A", 1200m), ("Service B", 850m), ("Service C", 3400m)
};

var html = new StringBuilder();
html.Append(@"<!DOCTYPE html><html><head>
<style>
  table { width: 100%; border-collapse: collapse; }
  th { background: #2c5f8a; color: white; padding: 8px; }
  td { padding: 6px 8px; border-bottom: 1px solid #e0e4e8; }
  tr:nth-child(even) { background: #f8fafc; }
</style></head><body><table>
<tr><th>Service</th><th>Amount</th></tr>");

foreach (var (name, amount) in rows)
    html.Append($"<tr><td>{name}</td><td>{amount:C}</td></tr>");

html.Append("</table></body></html>");

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

using var pdf = renderer.RenderHtmlAsPdf(html.ToString());
pdf.SaveAs("data-table.pdf");

HTML table generation in C# using StringBuilder, LINQ, or a template engine is well-understood .NET code. Chromium handles table pagination across pages, including repeating header rows via CSS thead and page-break-inside: avoid. The page breaks guide documents CSS page break controls for managing multi-page tables.

//     <pdf:Label value="{@:PageNum} of {@:TotalPages}" />

// Programmatic construction in C#

// var page = new PDFPage();
// page.Header = new PDFPageHeader();
// // add content to header

Technical constraints:

  • Header and footer content is declared in the template, not at runtime; dynamic content (report title from runtime data) requires binding expressions
  • Verify the exact expression syntax for page number and total page count tokens in current Scryber.Core documentation
  • Multi-section documents with different headers per section require per-section header definitions in the template

IronPDF — Headers and Footers:

using IronPdf;
using IronPdf.Engines.Chrome;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 20;

// HTML header — full CSS3, no template file required
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    HtmlFragment = @"<div style='font-family:Arial;font-size:10px;
                     border-bottom:1px solid #ccc;padding-bottom:4px;
                     display:flex;justify-content:space-between;'>
                     <strong>Company Report</strong>
                     <span>{date}</span></div>"
};

// Text footer with page tokens
renderer.RenderingOptions.TextFooter = new TextHeaderFooter
{
    RightText = "Page {page} of {total-pages}",
    DrawDividerLine = true,
    FontSize = 8
};

string html = GetReportHtml(); // from any source
using var pdf = renderer.RenderHtmlAsPdf(html);
pdf.SaveAs("report-with-headers.pdf");

The headers and footers guide documents both text-based and HTML-based variants, first-page suppression, and the full token reference. Headers and footers are configured on the renderer at generation time, not in a separate template file, which means they can be constructed dynamically from runtime data without a binding expression language.

Commonly Reported Limitations

  • XML template learning curve. The .pdfx schema and Scryber's binding expression language are proprietary. Teams transitioning from HTML/CSS web development to Scryber templates must learn a new vocabulary and set of layout primitives. IDE support (syntax completion, validation, preview) for .pdfx files is less mature than for HTML in modern editors, which extends the template development feedback loop. Unlike HTML templates that render correctly in any browser, .pdfx templates can only be previewed by running the library—there is no separate design-time preview tool.
  • Advanced layout scenarios. Scryber's managed layout engine covers common document patterns well, but advanced typographic scenarios—justified text, complex multi-column flowing content, baseline grid alignment, sophisticated table layouts—may produce results that differ from browser-rendered output. Verifying layout accuracy against visual targets for complex designs requires careful testing. The managed engine must implement every layout algorithm in C#; browser engines have decades of investment in these algorithms that a community library cannot fully replicate.
  • Single-maintainer project risk. Scryber.Core is primarily maintained by a single contributor. While the project is active and the codebase is mature, the maintainer concentration creates a different risk profile than a library with a broader contributor base or commercial backing. Feature requests, bug reports, and .NET version compatibility updates depend on that contributor's availability and priorities. Teams should plan for the possibility of assuming maintenance responsibility if the project becomes inactive.
  • Feature scope uncertainty. The library has grown over time and some advanced capabilities (PDF/A compliance, digital signatures, manipulation operations like merge and encrypt) may be partially implemented, recently added, or in development. Verify current feature status in the latest release notes and GitHub issue tracker before building workflows that depend on these operations. Community forum discussions about feature availability sometimes reference development branches that are not yet in a published NuGet release.
  • Template file deployment management. .pdfx template files are separate deployment artifacts. Template updates require file system changes on the deployed host rather than a code deployment, which can be an advantage (non-developer template updates) or a management overhead depending on the team's deployment model. Embedded resource deployment of .pdfx files is possible but adds build configuration steps.

Conclusion

When staying on Scryber.Core is technically reasonable

Scryber.Core is a sound choice for teams that need a no-native-binary PDF generation library, whose document templates are stable and structured (suitable for an XML template model), and whose deployment environment has constraints on native binary deployment. The open-source MIT/LGPL license eliminates commercial licensing overhead. For applications where non-developers maintain document templates as XML files, the separation of template from code is a genuine workflow advantage. The pure managed assembly model also simplifies Docker container images and eliminates the platform binary management that Chromium-based libraries require.

When migration becomes a capability or architectural mismatch

The XML template model creates friction when document templates are complex, when they need to leverage the same CSS that the application uses for web output, or when the team's HTML/CSS skills make a browser-based renderer more natural than learning Scryber's XML schema. When compliance operations—PDF/A conversion, digital signatures, encryption—are required and Scryber's current feature set does not cover them, a library with those capabilities becomes necessary.

How IronPDF approaches the same problem differently

IronPDF uses HTML as its template format, which aligns with web development skills and tooling. The Chromium engine handles CSS layout, web fonts, SVG, and JavaScript without the managed layout engine constraints that a no-native-binary approach carries. The PdfDocument result carries a complete manipulation and compliance API—including the PDF/A compliance guide operations—that covers archival, security, and signing workflows in one library. The trade-off is a larger NuGet package with a bundled Chromium engine versus Scryber's zero-native-dependency deployment profile.

When your team evaluates document template formats—XML versus HTML—which factor weighs more heavily in practice: the template authoring experience (who writes and maintains templates), or the rendering fidelity (how closely the output matches the design intent)?
