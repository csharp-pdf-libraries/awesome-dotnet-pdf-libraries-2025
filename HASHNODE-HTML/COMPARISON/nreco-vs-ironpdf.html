NReco PDF Generator vs IronPDF: a technical comparison for modern .NET teams (2026)

what the docs do not cover

Problem Framing

Thin .NET wrapper libraries for wkhtmltopdf occupy a useful but constrained niche. They offer HTML-to-PDF capability with minimal setup, a small deployment footprint (relative to Chromium-based alternatives), and a simple API surface: pass HTML, get PDF bytes. The trade-off is that the rendering ceiling is set by the wkhtmltopdf engine—a WebKit-based renderer that has not received significant updates in several years—and the capabilities stop at the byte array boundary.

NReco PDF Generator is a .NET wrapper library in this category, similar in architecture to DinkToPdf and Rotativa. It wraps the wkhtmltopdf native binary and exposes an API for converting HTML strings and URLs to PDF byte arrays. For teams evaluating it against a more comprehensive library like IronPDF, the comparison is not primarily about the .NET API surface—it is about the underlying rendering engine and the capabilities that exist beyond byte-array generation.

Understanding where the wkhtmltopdf rendering ceiling sits, and what is absent in the manipulation layer, is more important than comparing method signatures for this pair of libraries.

What NReco PDF Generator Is Designed To Do

NReco PDF Generator is a commercial .NET library from NReco that wraps the wkhtmltopdf command-line tool (or its library variant) for HTML-to-PDF conversion. The library accepts HTML content (as a string) or a URL and produces a PDF as a byte array or output stream. It supports basic rendering configuration: paper size, orientation, margins, header and footer HTML strings, and wkhtmltopdf's web settings (encoding, JavaScript enable/disable, print media type). The library handles spawning the wkhtmltopdf process or calling the native library, capturing output, and surfacing errors.

NReco PDF Generator is distributed via NuGet and targets .NET Framework and .NET Core. The library ships the wkhtmltopdf native binaries for Windows (x86/x64) and Linux within the package; macOS binaries may require manual configuration

What IronPDF Is Designed To Do

IronPDF is a commercial .NET library that uses a bundled Chromium engine for HTML-to-PDF rendering, producing a PdfDocument object rather than a raw byte array. The Chromium engine supports the full range of modern CSS and JavaScript that wkhtmltopdf does not: Grid, Flexbox, CSS custom properties, ES6+ JavaScript APIs, web fonts via CDN, and SVG embedded in HTML. The PdfDocument result carries a complete manipulation API—merge, split, encrypt, sign, stamp, form-fill, annotate, extract text and images.

The HTML string to PDF guide documents the primary rendering path. ChromePdfRenderer is thread-safe and can serve concurrent requests; PdfDocument implements IDisposable and must be disposed via using blocks. IronPDF targets .NET Framework 4.x and .NET 6+ on Windows, Linux, and macOS, distributed as a single NuGet package that resolves platform-native Chromium binaries at restore time without requiring manual binary management. The async rendering guide covers the awaitable rendering API for ASP.NET Core integration.

Key Limitations of NReco PDF Generator

Product Status

NReco PDF Generator is an actively maintained commercial library. Verify current version and release cadence at the NReco website. The underlying wkhtmltopdf engine—which determines rendering fidelity—has been largely dormant upstream; the rendering capabilities are fixed at the version bundled in the NuGet package.

Missing Capabilities

NReco PDF Generator converts HTML to PDF byte arrays. It provides no capability for reading or manipulating existing PDFs, merging generated documents, applying encryption, digital signatures, form operations, text extraction, or any post-generation manipulation. Each of these operations requires a separate library. Additionally, modern CSS features (Grid, Flexbox, CSS custom properties) are not supported by the underlying wkhtmltopdf engine regardless of the .NET wrapper quality.

Technical Constraints

The wkhtmltopdf rendering engine does not support CSS Grid or Flexbox. JavaScript execution is limited by the WebKit engine version; async-rendered SPA content is frequently not captured. Web fonts loaded from CDN URLs may not load if the rendering process cannot make outbound network requests. Under concurrent load, the library's threading model—whether it serialises rendering calls or allows concurrent execution—should be verified, as the native wkhtmltopdf library has known concurrency limitations.

Support Model

NReco provides commercial support for the library. Community support resources are more limited than for larger-ecosystem libraries. Rendering issues that trace to wkhtmltopdf behaviour (rather than the .NET wrapper) are outside the wrapper vendor's control to fix.

Architectural Fit

NReco PDF Generator is appropriate for applications with stable, simple HTML templates that fall within wkhtmltopdf's rendering capabilities, where open-source licensing is not a requirement, and where post-generation manipulation is not needed. It is a poor fit for applications using modern CSS frameworks, JavaScript-rendered content, high-concurrency rendering, or any workflow requiring manipulation after generation.

Operation Comparisons

HTML String to PDF

NReco PDF Generator — HTML to PDF:

// NReco PDF Generator HTML to PDF
// Package: NReco.PdfGenerator
using NReco.PdfGenerator;

var htmlToPdf = new HtmlToPdfConverter();

// Configure rendering options
htmlToPdf.Orientation = PageOrientation.Portrait;
htmlToPdf.PageSize = PageSize.A4;
htmlToPdf.Margins.Top = 15;
htmlToPdf.Margins.Bottom = 15;
// NReco wraps wkhtmltopdf; wkhtmltopdf version determines CSS support
htmlToPdf.CustomWkHtmlArgs = "--enable-javascript --print-media-type";

// Convert HTML string — result is byte[] (no manipulation API)
var htmlContent = "<h1>Report</h1><p>Content here.</p>";
byte[] pdfBytes = htmlToPdf.GeneratePdf(htmlContent);

// Write to file or return in HTTP response
File.WriteAllBytes("output.pdf", pdfBytes);
// No IDisposable on HtmlToPdfConverter or on the byte[] result

Technical constraints:

  • HtmlToPdfConverter may not be thread-safe for concurrent calls
  • CSS Grid and Flexbox layout in the HTML template will not render correctly
  • JavaScript-rendered content is captured at a fixed point after load; async content may be missing
  • byte[] result has no further API surface; any post-generation operation requires a second library

IronPDF — HTML String to PDF:

using IronPdf;

// ChromePdfRenderer is thread-safe — singleton or static instance is fine
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 15;
renderer.RenderingOptions.MarginBottom = 15;
renderer.RenderingOptions.CssMediaType = IronPdf.Rendering.PdfCssMediaType.Print;

var htmlContent = "<h1>Report</h1><p>Content here.</p>";

// PdfDocument — not just a byte array; carries full manipulation API
using var pdf = renderer.RenderHtmlAsPdf(htmlContent);

// Access bytes for HTTP response, or save directly
byte[] pdfBytes = pdf.BinaryData;
pdf.SaveAs("output.pdf");

IronPDF auto-paginates HTML content with no chaining loop required. The HTML string to PDF guide covers the base URL parameter for resolving external CSS files, images, and fonts referenced in the HTML—eliminating the need to inline all assets into the HTML string.

URL to PDF

NReco PDF Generator — URL to PDF:

using NReco.PdfGenerator;

var htmlToPdf = new HtmlToPdfConverter();
htmlToPdf.PageSize = PageSize.A4;
htmlToPdf.Orientation = PageOrientation.Portrait;

// NReco supports URL input directly — wkhtmltopdf fetches and renders
byte[] pdfBytes = htmlToPdf.GeneratePdf(
    new Uri("https://example.com/report"), null);

File.WriteAllBytes("url-output.pdf", pdfBytes);

Technical constraints:

  • The URL is fetched in the wkhtmltopdf process; network access must be available from the process host
  • JavaScript-heavy SPAs may not fully render; wkhtmltopdf's execution wait behaviour is configurable via custom args but limited
  • Authenticated pages require cookie configuration via wkhtmltopdf arguments; this is not a first-class API
  • HTTPS certificate validation failures require explicit bypass arguments

IronPDF — URL to PDF:

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Wait for JavaScript to finish rendering before snapshot
renderer.RenderingOptions.WaitFor.RenderDelay(500);

// Inject cookies for authenticated URLs
renderer.RenderingOptions.CustomCookies =
    new System.Collections.Generic.Dictionary<string, string>
    { { "session_token", "abc123" } };

using var pdf = renderer.RenderUrlAsPdf("https://example.com/report");
pdf.SaveAs("url-output.pdf");

The URL to PDF guide documents cookie injection, custom request headers, and the WaitFor API for precisely controlling when Chromium captures the page state—including waiting for specific JavaScript conditions rather than a fixed time delay.

Generating PDF with Dynamic Data and Tables

NReco PDF Generator — Data-Driven HTML to PDF:

using NReco.PdfGenerator;
using System.Text;

// Build HTML with data — wkhtmltopdf constraints apply to CSS
var rows = new[] { ("Widget A", 120, 14.99m), ("Widget B", 85, 9.50m) };
var sb = new StringBuilder();
sb.Append(@"<!DOCTYPE html><html><head>
<style>
  /* IMPORTANT: avoid CSS Grid/Flexbox — not supported by wkhtmltopdf */
  body { font-family: Arial; font-size: 11px; margin: 30px; }
  table { width: 100%; border-collapse: collapse; }
  th { background: #336699; color: white; padding: 5px; }
  td { border: 1px solid #ccc; padding: 4px; }
</style></head><body>
<h2>Product Report</h2>
<table><tr><th>Product</th><th>Qty</th><th>Price</th></tr>");

foreach (var (name, qty, price) in rows)
    sb.Append($"<tr><td>{name}</td><td>{qty}</td><td>{price:C}</td></tr>");

sb.Append("</table></body></html>");

var htmlToPdf = new HtmlToPdfConverter();
htmlToPdf.PageSize = PageSize.A4;
byte[] pdfBytes = htmlToPdf.GeneratePdf(sb.ToString());
File.WriteAllBytes("products.pdf", pdfBytes);

Technical constraints:

  • CSS must be constrained to what wkhtmltopdf supports; modern layout approaches require workarounds or refactoring
  • Template development requires constant cross-checking against wkhtmltopdf's rendering behaviour, which differs from browser rendering
  • Long tables that span multiple pages rely on page-break CSS hints; verify behaviour with the specific wkhtmltopdf version bundled

IronPDF — Data-Driven PDF with Modern CSS:

using IronPdf;
using System.Text;

var rows = new[] { ("Widget A", 120, 14.99m), ("Widget B", 85, 9.50m) };
var sb = new StringBuilder();

// Modern CSS including Flexbox and Grid renders correctly via Chromium
sb.Append(@"<!DOCTYPE html><html><head>
<style>
  body { font-family: Arial, sans-serif; font-size: 11px; margin: 30px; }
  .header { display: flex; justify-content: space-between; margin-bottom: 20px; }
  table { width: 100%; border-collapse: collapse; }
  th { background: #2c5f8a; color: white; padding: 8px; text-align: left; }
  td { padding: 6px 8px; border-bottom: 1px solid #eee; }
  .total-row { font-weight: bold; background: #f0f4f8; }
</style></head><body>
<div class='header'>
  <h2>Product Report</h2>
  <span>Generated: " + DateTime.Now.ToString("yyyy-MM-dd") + @"</span>
</div>
<table><tr><th>Product</th><th>Qty</th><th>Price</th></tr>");

decimal total = 0;
foreach (var (name, qty, price) in rows)
{
    var lineTotal = qty * price;
    total += lineTotal;
    sb.Append($"<tr><td>{name}</td><td>{qty}</td><td>{price:C}</td></tr>");
}

sb.Append($"<tr class='total-row'><td colspan='2'>Total</td><td>{total:C}</td></tr>");
sb.Append("</table></body></html>");

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

using var pdf = renderer.RenderHtmlAsPdf(sb.ToString());
pdf.SaveAs("products.pdf");

Because Chromium handles CSS, the same template can use Flexbox for the header layout, CSS variables, and modern typography without workarounds. The responsive CSS guide covers how CSS media queries and print-specific stylesheets interact with the rendering pipeline.

Post-Generation Encryption (Additive IronPDF Capability)

NReco PDF Generator — Encryption:

NReco PDF Generator produces a byte[]. Encryption requires a separate library.

// NReco has no encryption API
// Encryption requires a second library dependency

// With NReco you have:
// byte[] pdfBytes = htmlToPdf.GeneratePdf(html);
// Then you need to pass those bytes to a separate PDF manipulation library
// to apply encryption — adding a second NuGet dependency, a second API to learn,
// and a second set of disposal semantics to manage.

Technical constraints:

  • Two separate library dependencies for generate + encrypt
  • Any breaking change in either library affects the pipeline independently
  • Error handling spans two different error models

IronPDF — Inline Encryption on Generated PDF:

using IronPdf;

var renderer = new ChromePdfRenderer();
using var pdf = renderer.RenderHtmlAsPdf(documentHtml);

// Encryption applied on the same PdfDocument object — no second library
pdf.SecuritySettings.OwnerPassword = "ownerSecret";
pdf.SecuritySettings.UserPassword = "userReadKey";
pdf.SecuritySettings.AllowUserPrint = true;
pdf.SecuritySettings.AllowUserCopyPasteContent = false;

pdf.SaveAs("encrypted-document.pdf");

The passwords and permissions guide documents the full permission flag set and encryption strength options. Because encryption is a method on PdfDocument, it composes naturally with generation, merge, and signing in any order without an additional library.

Commonly Reported Limitations

  • wkhtmltopdf rendering ceiling. The same limitations that affect all wkhtmltopdf wrappers apply to NReco: CSS Grid and Flexbox do not render correctly, JavaScript-async content is often missed, and web fonts loaded via CDN URLs may fail silently. These are engine limitations, not NReco wrapper limitations.
  • No post-generation manipulation. The byte[] output is final. For any post-generation operation—encrypt, sign, merge, watermark—a second .NET library is required. Teams accumulate multiple dependencies over time as requirements expand.
  • Concurrency model uncertainty. The thread safety of the underlying wkhtmltopdf library is a known concern for native PDF tools. Under ASP.NET Core concurrent request loads, the wrapper's serialisation behaviour should be verified through load testing before going to production.
  • Template development friction. Developing HTML templates for wkhtmltopdf requires testing in the wkhtmltopdf environment rather than a browser, because the rendering engine behaviour differs from Chrome or Firefox. CSS that looks correct in a browser may produce different output in wkhtmltopdf, requiring iterative adjustment.

Conclusion

When staying on NReco PDF Generator is technically reasonable

NReco PDF Generator is appropriate for applications with stable, simple HTML templates that are within wkhtmltopdf's CSS capabilities—table-based layouts, limited JavaScript, no Grid or Flexbox. For teams where the free evaluation tier meets volume requirements, where open-source licensing is not a concern, and where post-generation manipulation is genuinely not needed, NReco provides a functional HTML-to-PDF path with a straightforward integration model. If the existing integration is working and stable, migration cost is not justified unless requirements change.

When migration becomes a capability or architectural mismatch

The migration case crystallises when any of three events occur: the HTML templates adopt modern CSS that wkhtmltopdf cannot render (often triggered by a framework update or designer change), the application needs post-generation operations that require a second library, or concurrent rendering throughput becomes a bottleneck. All three frequently co-occur as an application matures.

How IronPDF approaches the same problem differently

IronPDF replaces the wkhtmltopdf rendering engine with Chromium, which eliminates the CSS compatibility ceiling. The result of rendering is a PdfDocument with a full manipulation API—merge, encrypt, sign, form-fill, extract—so post-generation operations do not require a second library. The async rendering guide covers the native async API for ASP.NET Core integration; ChromePdfRenderer is thread-safe without the concurrency concerns of wkhtmltopdf's native library.

When you audit the HTML templates your application currently sends to wkhtmltopdf, what percentage of them use table-based layout versus CSS Grid or Flexbox—and how does that distribution affect your confidence in the rendering ceiling?
