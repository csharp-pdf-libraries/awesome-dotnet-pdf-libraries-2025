PDFSharp vs IronPDF: a .NET engineer reference for 2026

the engineering breakdown for .NET teams

Problem Framing

PDF generation in .NET has two fundamentally different authoring models, and selecting the wrong one for a project creates friction that is expensive to undo once templates are built. The first model uses a drawing API: the developer places text, shapes, images, and lines on a page using coordinate-based method calls, controlling every element's position, size, and font directly in code. The second model uses HTML and CSS: the developer writes a template as a web document, passes it to a rendering engine, and the engine handles layout automatically. Both models produce identical-quality PDF bytes at the output, but they require completely different skills, produce different maintenance characteristics, and are the right choice in different application contexts.

PDFSharp is a drawing-API library. It is one of the most widely used .NET PDF libraries precisely because it is MIT-licensed, purely managed .NET with no native dependencies, and covers both drawing-based PDF creation and a manipulation surface for existing documents. Teams reach for PDFSharp when they need to create PDFs programmatically from code with explicit layout control, when they cannot or will not adopt a commercial library, and when their documents have structure that maps naturally to coordinate placement — labels, lines, tables with known column widths, barcodes, and images at fixed positions.

IronPDF uses the HTML/CSS model via embedded Chromium. The comparison between PDFSharp and IronPDF is therefore not primarily about output quality or PDF specification compliance — it is about authoring model, license model, and feature scope. Teams choosing between them are making a choice about how they want to describe document layout (coordinates in code vs. CSS in a template), what license constraints are acceptable (MIT vs. commercial), and whether a broad manipulation API from a single library or a focused drawing library plus optional add-ons better fits the project.

What PDFSharp Is Designed to Do

PDFSharp is an open-source .NET library for creating and processing PDF documents, distributed under the MIT license. It targets .NET Standard 2.0 and later .NET versions, has no native binary dependencies, and runs on Windows, Linux, and macOS as a purely managed assembly.

PDFSharp's creation API is centered on XGraphics — a drawing surface that accepts drawing calls analogous to GDI+ or System.Drawing. Developers create a PdfDocument, add PdfPage objects, obtain an XGraphics context for each page, and draw content using methods like DrawString(), DrawImage(), DrawRectangle(), DrawLine(), DrawPath(), and DrawPdf(). Fonts are specified via XFont, colors via XColor and XBrush. The coordinate system uses PDF points (1/72 inch) with the origin at the top-left of the page.

For reading and modifying existing PDFs, PDFSharp provides access to the PDF document object model — pages can be added, removed, and rotated; text can be extracted; existing PDFs can be stamped or merged. Encryption, password protection, and document metadata are also accessible.

MigraDoc Foundation is a companion project that provides a higher-level document model on top of PDFSharp: Document, Section, Paragraph, Table, Image objects whose layout is computed automatically rather than placed at explicit coordinates. MigraDoc is the appropriate layer for documents with reflowing text content; PDFSharp's raw XGraphics is appropriate for fixed-layout documents.

PDFSharp is maintained on GitHub and has an active community. It does not include an HTML-to-PDF renderer — there is no API to pass an HTML string or URL and receive a PDF. The library's scope is programmatic PDF creation and manipulation via a drawing API and document object model.

What IronPDF Is Designed to Do

IronPDF is a commercial .NET PDF library built on embedded Chromium for HTML-to-PDF generation, distributed as a managed NuGet package targeting .NET Standard 2.0 and above. ChromePdfRenderer accepts HTML strings, HTML files, and URLs and produces PDFs with full CSS3 fidelity — Flexbox, Grid, CSS variables, web fonts, SVG, and JavaScript execution with configurable wait conditions. The HTML string to PDF guide covers the full rendering configuration surface including viewport, base URL, JavaScript wait conditions, and custom CSS injection.

PdfDocument provides a manipulation API for loading, modifying, and saving existing PDFs: text extraction, image extraction, AcroForm reading and filling, form creation, document merge and split, page manipulation, password encryption and permission restrictions, digital signatures (X.509 PKCS#12 and HSM-backed), PDF/A and PDF/UA compliance output, metadata, watermarks, find-and-replace, redaction, annotations, bookmarks, compression, and linearization. License initialization is a one-time startup call; see the license setup guide. IronPDF supports Windows, Linux, macOS, and Docker containers.

Key Limitations of PDFSharp

Product Status

PDFSharp is an MIT-licensed open-source library maintained on GitHub with active community contributions and releases. The project has been active for many years and continues to receive updates. Verify the current NuGet version and .NET compatibility matrix (particularly .NET 8+ support) in the official PDFSharp repository — the community-maintained nature means release timing is not as predictable as a commercial vendor's release cycle.

Missing Capabilities

PDFSharp does not render HTML. There is no API for converting an HTML string, HTML file, or URL to PDF. Teams whose document templates are authored in HTML and CSS — the majority of modern .NET web application document workflows — must maintain a separate representation of those documents using PDFSharp's drawing API. This is a complete authoring model mismatch, not a minor feature gap. Templates cannot be previewed in a browser, CSS layout is not available, and each document must be manually constructed as drawing operations.

PDFSharp does not include digital signatures, PDF/A compliance output, PDF/UA accessibility tagging, HSM-backed signing, or redaction

Technical Constraints

PDFSharp's XGraphics drawing API requires explicit coordinate placement. Documents with variable-height content — text that wraps over multiple lines, tables with data-dependent row heights, dynamic content that changes length based on records — require custom layout calculation code in C#. There is no CSS engine to compute these layouts automatically; the developer must calculate element heights and positions in code, managing page overflow and continuation manually. This is manageable for documents with known, fixed structures but becomes substantial code for documents with dynamic, data-driven content.

MigraDoc's document model handles some of this layout calculation automatically, but MigraDoc does not expose XGraphics directly, so mixing precise coordinate drawing with document-model content requires careful layering. Verify current MigraDoc API capabilities and .NET version support.

Support Model

PDFSharp is community-supported via GitHub issues, Stack Overflow, and community forums. There is no commercial support tier, no SLA, and no guaranteed response time for production issues. Teams that require vendor-backed support with escalation paths and response commitments should factor this into their adoption decision. The community is active and the library is well-documented, which partially compensates for the absence of commercial support.

Architectural Fit

PDFSharp is well-suited for .NET applications that generate PDFs with fixed or well-defined layouts from programmatic data, where coordinate-based drawing is acceptable, where MIT licensing is a requirement or strong preference, and where the development team is comfortable with the drawing API model. It is less suited for applications generating PDFs from HTML/CSS templates, for teams whose authoring workflow is web-development-oriented, or for applications with compliance requirements (PDF/A, PDF/UA, digital signatures) that exceed PDFSharp's current feature scope.

Operation Comparisons

Creating a PDF Invoice (Drawing API vs HTML Template)

PDFSharp — Invoice via XGraphics Drawing API

using PdfSharp.Pdf;
using PdfSharp.Drawing;
using System.IO;

// PDFSharp — create an invoice using the XGraphics drawing API
// All layout is explicit: position (x, y), width, and height per element
var document = new PdfDocument();
document.Info.Title   = "Invoice #1042";
document.Info.Subject = "Customer Invoice";

// Add a page — A4 size in PDF points (1 pt = 1/72 inch)
var page       = document.AddPage();
page.Size      = PdfSharp.PageSize.A4;
var gfx        = XGraphics.FromPdfPage(page);

// Define fonts
var titleFont  = new XFont("Arial", 18, XFontStyleEx.Bold);
var bodyFont   = new XFont("Arial", 11, XFontStyleEx.Regular);
var boldFont   = new XFont("Arial", 10, XFontStyleEx.Bold);

// Page dimensions in points
double pageWidth  = page.Width.Point;   // A4 ≈ 595 pt
double margin     = 40;                  // 40pt ≈ 14mm

// Draw title — explicit coordinate placement
gfx.DrawString("Invoice #1042",
    titleFont,
    XBrushes.Black,
    new XPoint(margin, 60));  // x=40pt, y=60pt from top-left

// Draw customer line
gfx.DrawString("Customer: Acme Corp",
    bodyFont,
    XBrushes.Black,
    new XPoint(margin, 90));

// Draw a horizontal rule
gfx.DrawLine(XPens.DarkGray,
    new XPoint(margin, 105),
    new XPoint(pageWidth - margin, 105));

// Table header row — manual column layout
double col1X = margin,   col1W = 300;
double col2X = margin + col1W, col2W = 80;
double col3X = col2X + col2W;
double rowH  = 20;
double tableY = 115;

gfx.DrawString("Description", boldFont, XBrushes.Black, new XPoint(col1X, tableY + 14));
gfx.DrawString("Qty",         boldFont, XBrushes.Black, new XPoint(col2X, tableY + 14));
gfx.DrawString("Price",       boldFont, XBrushes.Black, new XPoint(col3X, tableY + 14));

// Table data row — one row for each invoice line
var lines = new[] {
    (Description: "Widget A", Qty: "10", Price: "$99.99"),
    (Description: "Widget B", Qty:  "5", Price: "$249.99")
};

double rowY = tableY + rowH;
foreach (var line in lines)
{
    gfx.DrawString(line.Description, bodyFont, XBrushes.Black, new XPoint(col1X, rowY + 14));
    gfx.DrawString(line.Qty,         bodyFont, XBrushes.Black, new XPoint(col2X, rowY + 14));
    gfx.DrawString(line.Price,       bodyFont, XBrushes.Black, new XPoint(col3X, rowY + 14));
    rowY += rowH;
}

// Save the document — PdfDocument does not implement IDisposable in older versions
// Verify current disposal pattern in the PDFSharp version in use
document.Save("invoice.pdf");
Console.WriteLine($"Saved: invoice.pdf");
  • Every element requires explicit coordinate placement — x, y, width, height in PDF points.
  • Variable-content rows (text wrapping, dynamic line count) require manual height calculation in code; PDFSharp does not reflow text automatically in XGraphics.
  • Multi-page support for variable-content tables requires detecting when rowY exceeds the page height and adding a new PdfPage — this logic is the developer's responsibility.
  • XFont on Linux requires fonts to be available on the host system; web fonts loaded via CSS are not accessible to the drawing API.
  • PdfDocument disposal semantics vary across PDFSharp versions

IronPDF — Invoice via HTML Template

using IronPdf;
using System.Linq;

// Data for the invoice
var lines = new[]
{
    (Description: "Widget A", Qty: 10,  Price: 99.99m),
    (Description: "Widget B", Qty:  5,  Price: 249.99m)
};
decimal total = lines.Sum(l => l.Qty * l.Price);

// Build HTML rows from data — production code uses Razor or Scriban
string rows = string.Concat(lines.Select(l =>
    $"<tr><td>{l.Description}</td><td>{l.Qty}</td><td>{l.Price:C}</td></tr>"));

string html = $@"
<!DOCTYPE html>
<html>
<head>
  <style>
    body   {{ font-family: Arial; font-size: 11pt; }}
    h1     {{ font-size: 18pt; margin-bottom: 4px; }}
    hr     {{ border: none; border-top: 1px solid #aaa; margin: 10px 0; }}
    table  {{ width: 100%; border-collapse: collapse; margin-top: 12px; }}
    th, td {{ border: 1px solid #ddd; padding: 5px 9px; }}
    th     {{ background: #f5f5f5; font-weight: bold; }}
    .total {{ text-align: right; font-weight: bold; margin-top: 8px; }}
  </style>
</head>
<body>
  <h1>Invoice #1042</h1>
  <p>Customer: Acme Corp</p>
  <hr/>
  <table>
    <thead><tr><th>Description</th><th>Qty</th><th>Price</th></tr></thead>
    <tbody>{rows}</tbody>
  </table>
  <p class='total'>Total: {total:C}</p>
</body>
</html>";

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop    = 20;
renderer.RenderingOptions.MarginBottom = 20;
renderer.RenderingOptions.MarginLeft   = 14;
renderer.RenderingOptions.MarginRight  = 14;

using var pdf = await renderer.RenderHtmlAsPdfAsync(html);
pdf.SaveAs("invoice.pdf");

The HTML template handles column layout, text wrapping, multi-page overflow, and styling via CSS. Adding a new line to the invoice requires adding one object to the data array — no coordinate recalculation. The HTML string to PDF guide covers full rendering configuration. Templates are previewable in any browser before rendering.

Merging and Splitting PDFs

PDFSharp — Merge PDFs

using PdfSharp.Pdf;
using PdfSharp.Pdf.IO;
using System.IO;

// PDFSharp — merge multiple PDFs by importing pages
// PdfReader.Open returns a PdfDocument for reading
var outputDoc = new PdfDocument();

// Import all pages from each source document
var sourcePaths = new[] { "document1.pdf", "document2.pdf", "appendix.pdf" };

foreach (var path in sourcePaths)
{
    // PdfDocumentOpenMode.Import is required for page importing
    using var sourceDoc = PdfReader.Open(path, PdfDocumentOpenMode.Import);
    for (int i = 0; i < sourceDoc.PageCount; i++)
    {
        // CopyPage adds the source page to the output document
        outputDoc.AddPage(sourceDoc.Pages[i]);
    }
}

outputDoc.Save("merged.pdf");
Console.WriteLine($"Merged {sourcePaths.Length} documents.");
  • PdfDocumentOpenMode.Import is required — opening with PdfDocumentOpenMode.Modify does not support page importing.
  • Large documents load all pages into managed memory — profile memory usage for merges involving many large source files.
  • Imported pages carry their annotations and form fields, but form field name conflicts between source documents require additional handling.
  • Splitting follows the reverse pattern: open a source document, copy a page subset to a new PdfDocument, save.

IronPDF — Merge and Split

using IronPdf;

// Merge — static method, any number of PdfDocument instances
using var doc1 = PdfDocument.FromFile("document1.pdf");
using var doc2 = PdfDocument.FromFile("document2.pdf");
using var doc3 = PdfDocument.FromFile("appendix.pdf");

using var merged = PdfDocument.Merge(doc1, doc2, doc3);
merged.SaveAs("merged.pdf");

// Split — extract page ranges from a single document
using var report = PdfDocument.FromFile("full-report.pdf");
// Extract pages 0–4 (first five pages) as a standalone document
using var summary = report.CopyPages(0, 4);
summary.SaveAs("summary-section.pdf");

PdfDocument.Merge() accepts any number of instances in a single call. The merge and split guide covers page-range operations, N-way merges, and document splitting. All disposal is handled via using blocks in a uniform pattern.

Password Encryption and Permissions

PDFSharp — Encryption

using PdfSharp.Pdf;
using PdfSharp.Pdf.Security;

// PDFSharp — apply password encryption to a document
var document = new PdfDocument();
var page     = document.AddPage();
var gfx      = XGraphics.FromPdfPage(page);
gfx.DrawString("Confidential Report",
    new XFont("Arial", 14, XFontStyleEx.Regular),
    XBrushes.Black,
    new XPoint(40, 60));

// Security settings on the document
var security = document.SecuritySettings;

// Set owner and user passwords
security.OwnerPassword = "owner-secret";
security.UserPassword  = "user-view-pass";

// Restrict permissions — user cannot print or copy text
security.PermitPrint   = false;
security.PermitCopyContent = false;
security.PermitAnnotations = false;

// Encryption level
security.DocumentSecurityLevel =
    PdfDocumentSecurityLevel.Encrypted128Bit;  // verify enum name

document.Save("confidential.pdf");
  • PdfDocumentSecurityLevel enum values and availability depend on the PDFSharp version
  • Verify PermitPrint, PermitCopyContent, and other permission properties in the current release, as property names have varied slightly across versions.

IronPDF — Password Encryption and Permissions

using IronPdf;

var renderer = new ChromePdfRenderer();
using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Confidential Report</h1></body></html>");

// Owner and user passwords
pdf.SecuritySettings.OwnerPassword = "owner-secret";
pdf.SecuritySettings.UserPassword  = "user-view-pass";

// Fine-grained permission restrictions
pdf.SecuritySettings.AllowUserPrinting        = false;
pdf.SecuritySettings.AllowUserCopyPasteContent = false;
pdf.SecuritySettings.AllowUserAnnotations     = false;
pdf.SecuritySettings.AllowUserFormData        = false;

pdf.SaveAs("confidential.pdf");

IronPDF's SecuritySettings provides typed properties for all standard PDF permission flags. The passwords and permissions guide covers encryption levels, permission combinations, and reading encrypted documents.

MigraDoc — High-Level Document Model

MigraDoc is PDFSharp's companion library for document-model-based creation. It is the appropriate layer when document content reflowing matters — paragraphs of text, multi-page tables, styled sections. Understanding where MigraDoc ends and XGraphics begins is important for PDFSharp integrations.

MigraDoc — Document with Paragraphs and Table

using MigraDoc.DocumentObjectModel;
using MigraDoc.DocumentObjectModel.Tables;
using MigraDoc.Rendering;
using System.IO;

// MigraDoc — higher-level document model layer over PDFSharp
var doc     = new Document();
var section = doc.AddSection();

// Page setup
section.PageSetup.PageFormat   = PageFormat.A4;
section.PageSetup.TopMargin    = "2cm";
section.PageSetup.BottomMargin = "2cm";
section.PageSetup.LeftMargin   = "2cm";
section.PageSetup.RightMargin  = "2cm";

// Title paragraph
var title      = section.AddParagraph("Quarterly Report");
title.Format.Font.Name = "Arial";
title.Format.Font.Size = 18;
title.Format.Font.Bold = true;
title.Format.SpaceAfter = "6pt";

// Body paragraph — text wraps automatically
var body      = section.AddParagraph("Revenue grew 12% year-over-year.");
body.Format.Font.Name = "Arial";
body.Format.Font.Size = 11;

// Table — MigraDoc handles row height and page overflow automatically
var table = section.AddTable();
table.Style = "Table";

var col1 = table.AddColumn("10cm");
var col2 = table.AddColumn("3cm");

// Header row
var headerRow = table.AddRow();
headerRow.Shading.Color = Colors.LightGray;
headerRow.Cells[0].AddParagraph("Description");
headerRow.Cells[1].AddParagraph("Amount");

// Data rows
var dataRow = table.AddRow();
dataRow.Cells[0].AddParagraph("Widget Sales");
dataRow.Cells[1].AddParagraph("$120,000");

// Render to PDF via MigraDoc's PdfDocumentRenderer
var renderer = new PdfDocumentRenderer(unicode: true)
{
    Document = doc
};
renderer.RenderDocument();
renderer.PdfDocument.Save("quarterly-report.pdf");
  • MigraDoc handles text wrapping and page overflow automatically — a significant improvement over raw XGraphics for content-driven documents.
  • Column widths in MigraDoc use string measurements ("10cm", "3cm") rather than PDF points directly.
  • MigraDoc does not accept HTML — the template must be constructed using MigraDoc's object model types.
  • Mixing XGraphics drawing with MigraDoc content is possible via MigraDoc.Rendering.MigraDocParagraphImageFormatCallback and related APIs
  • Styling in MigraDoc uses a style-sheet model; complex visual designs require more code than an equivalent CSS rule.

IronPDF — HTML with Reflowing Content

using IronPdf;

// Equivalent document via HTML — text wrapping, tables, and page breaks
// are handled by Chromium's layout engine automatically
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop    = 20;
renderer.RenderingOptions.MarginBottom = 20;
renderer.RenderingOptions.MarginLeft   = 20;
renderer.RenderingOptions.MarginRight  = 20;

string html = @"
<!DOCTYPE html>
<html>
<head>
  <style>
    body   { font-family: Arial; font-size: 11pt; }
    h1     { font-size: 18pt; font-weight: bold; margin-bottom: 6pt; }
    table  { width: 100%; border-collapse: collapse; }
    th, td { border: 1px solid #ccc; padding: 5px 9px; }
    th     { background: #e0e0e0; }
  </style>
</head>
<body>
  <h1>Quarterly Report</h1>
  <p>Revenue grew 12% year-over-year.</p>
  <table>
    <thead><tr><th>Description</th><th>Amount</th></tr></thead>
    <tbody>
      <tr><td>Widget Sales</td><td>$120,000</td></tr>
    </tbody>
  </table>
</body>
</html>";

using var pdf = await renderer.RenderHtmlAsPdfAsync(html);
pdf.SaveAs("quarterly-report.pdf");

Text wrapping, table cell sizing, and page overflow are handled by Chromium's layout engine — no manual calculation. Adding a column means adding a <th>/<td> to the HTML. The HTML string to PDF guide covers all rendering options.

Commonly Reported Limitations

  • PDFSharp's XGraphics drawing API requires manual layout calculation for all variable-content documents — multi-page text wrapping, dynamic table row heights, and conditional page breaks require significant custom code that HTML/CSS handles declaratively.
  • Font availability on Linux requires the fonts used in XFont to be installed on the host operating system; PDFSharp's drawing API cannot load fonts from URLs or Google Fonts. This is a common deployment issue when moving from a Windows development machine to a Linux container.
  • XGraphics.DrawString() does not wrap text automatically across line breaks — multi-line text requires measuring string width with gfx.MeasureString() and manually breaking text into segments, which is verbose for paragraph-length content. MigraDoc handles this, but MigraDoc is a separate integration layer.
  • Digital signatures, PDF/A output, and redaction are not confirmed as stable features across PDFSharp versions
  • Community support means production incident resolution time depends on community availability — issues that require deep library knowledge may have no guaranteed resolution path, unlike a commercially supported library with vendor escalation.

Conclusion

When PDFSharp is technically reasonable

PDFSharp is technically reasonable for applications that generate PDFs with fixed or well-defined layouts from code — invoices with known column widths, labels, barcodes, charts, and documents where the developer is comfortable expressing layout as coordinate drawing calls. It is the clear choice when MIT licensing is a hard requirement — the absence of commercial license cost and the ability to modify and redistribute the source under MIT terms are genuine differentiators. Applications that are already well-integrated with PDFSharp and MigraDoc and whose document templates are stable have little operational pressure to migrate.

When the architectural mismatch becomes significant

The mismatch becomes significant when document templates are authored in HTML and CSS — or when the team's skill set is web-development-oriented and maintaining drawing-API code for every document layout is a productivity drag. It also surfaces when advanced compliance requirements (PDF/A, PDF/UA, digital signatures) are needed and the current PDFSharp release does not cover them, when variable-height content makes layout calculation code disproportionately large relative to the document's actual complexity, or when async rendering under concurrent ASP.NET Core load is required.

How IronPDF approaches the same problem space

IronPDF uses HTML and CSS as the document authoring model — Chromium handles layout calculation, text wrapping, and multi-page overflow automatically, and templates are previewable in a browser before rendering. PdfDocument covers the manipulation surface — merge, split, sign, encrypt, form-fill, PDF/A — in a single commercial NuGet package with vendor-backed support. The IronPDF documentation overview covers both generation and manipulation.

For teams currently using PDFSharp: what fraction of the document layout code consists of manual coordinate calculations and MeasureString() calls that would be replaced by CSS if the authoring model shifted to HTML — and does that fraction, relative to the total document generation complexity, justify the model difference?
