iTextSharp vs IronPDF: side by side — capabilities, limits, fit

technical depth for .NET decision makers

Problem Framing

Few .NET PDF libraries have as long and complex a history as iTextSharp. Understanding that history is essential context for any current evaluation, because the library's past licensing model, its relationship to the Java iText library, and the deprecation of the iTextSharp package itself all directly affect how teams should think about adopting or continuing to use it. An evaluation that treats iTextSharp as a straightforward commercial library will miss the most important architectural considerations.

iTextSharp was a .NET port of the Java iText 5 library, released under the LGPL license for versions up to 5.x. That LGPL version is no longer maintained. iText has since released iText 7, which introduced a new AGPL license model: the library is available for free under AGPL, which requires that any application using it must also release its source code under AGPL — or purchase a commercial license. This licensing distinction has significant architectural implications for most commercial applications. Additionally, iText 7 for .NET is the active product; the legacy iTextSharp package on NuGet is a different, older codebase.

This article addresses both iTextSharp (the legacy iText 5 .NET port) and iText 7 for .NET (the current product), because teams evaluating "iTextSharp" in 2026 are often navigating the transition between them. The comparison to IronPDF applies to the current iText 7 product line, which is what teams would adopt for new development.

What iTextSharp / iText 7 for .NET Is Designed to Do

iTextSharp (legacy, iText 5 .NET port): iTextSharp was a .NET port of the Java iText 5 library. It provided comprehensive PDF creation and manipulation: document creation via a document object model (Document, PdfWriter, Chunk, Paragraph, Table), AcroForm reading and writing, digital signatures, encryption and permissions, PDF merging and stamping, text extraction, and metadata management. The last significant LGPL release was version 5.5.x. iTextSharp is no longer actively maintained — do not start new projects on iTextSharp; use iText 7 for .NET instead.

iText 7 for .NET (current product): iText 7 is a complete rewrite of the iText library released under AGPL for open-source use and a commercial license for proprietary applications. The .NET version (itext7 on NuGet) is a port of the Java iText 7 library. Core capabilities include: low-level PDF document creation via a new object model (PdfDocument, PdfPage, PdfCanvas), a higher-level layout API (Document, Paragraph, Table, Image) for content-driven generation, AcroForm field creation, reading and writing, digital signatures (including PAdES, LTV, and timestamp authority support), PDF/A and PDF/UA compliance creation and validation, text extraction, image extraction, document merging and splitting, encryption and permissions, metadata management, and bookmarks.

iText also provides add-on modules: pdfHTML (HTML-to-PDF via a CSS layout engine, not Chromium), pdfSweep (redaction), pdfOCR (optical character recognition), pdfRender (rasterization), and others. These are separate commercial packages. The pdfHTML module converts HTML and CSS to PDF using iText's own layout engine — it does not use a browser rendering engine, which means CSS support is limited to what iText has implemented; Flexbox, CSS Grid, and some web font features may not be fully supported. Verify current pdfHTML CSS coverage against your specific templates in official documentation.

Critical licensing note: iText 7 is licensed under AGPL. AGPL requires that any application that uses the library — including server-side web applications that access it over a network — must release its complete source code under AGPL, or purchase a commercial license from iText. Most commercial applications cannot use iText under AGPL without open-sourcing their codebase. This is not a minor compliance detail; it is a binary architectural constraint that must be resolved before adopting iText 7 in any commercial or proprietary application.

What IronPDF Is Designed to Do

IronPDF is a .NET PDF library built on embedded Chromium for HTML-to-PDF generation, distributed as a managed NuGet package with a commercial license that permits use in proprietary applications without any source-code disclosure requirement. ChromePdfRenderer generates PDFs from HTML strings, HTML files, and URLs using full Chromium rendering — CSS3, Flexbox, Grid, CSS variables, web fonts, SVG, and JavaScript execution are all supported. The HTML string to PDF guide covers the full rendering configuration surface.

PdfDocument provides a manipulation API for loading, reading, modifying, and saving existing PDFs: text extraction, image extraction, AcroForm reading and filling, form creation, document merge and split, page manipulation, password encryption, digital signatures (X.509 PKCS#12 and HSM-backed), PDF/A and PDF/UA compliance output, metadata read/write, watermarks, find-and-replace text, redaction, annotations, bookmark management, compression, and linearization. License initialization is a one-time startup call; the license setup guide covers configuration options. IronPDF runs on Windows, Linux, macOS, and in Docker containers. No source-code disclosure requirement exists for commercial use.

Key Limitations of iTextSharp / iText 7 for .NET

Product Status

iTextSharp (iText 5 .NET) is unmaintained — do not use it for new development. iText 7 for .NET is the active product, maintained by iText Group NV. iText 7 receives regular releases and tracks the Java iText 7 library. The .NET version is a port of the Java implementation, which means some API patterns reflect Java conventions. Verify the current .NET version support matrix (particularly .NET 6+ and .NET 8+) in official iText documentation.

Missing Capabilities

iText 7's HTML-to-PDF capability is provided by the pdfHTML add-on module, which uses iText's own CSS layout engine rather than Chromium. This means CSS coverage is limited to what iText has implemented: Flexbox support is partial, CSS Grid is not fully supported, and some web font loading edge cases may differ from browser rendering. Teams with templates authored for browser rendering should validate pdfHTML output against their specific CSS before committing to it. There is no URL-to-PDF feature in the core iText 7 library — URL rendering requires either pdfHTML with a fetched HTML string or a separate headless browser tool.

Technical Constraints

iText 7's API reflects its Java heritage. The PdfDocument, PdfWriter, PdfReader, and layout API types require explicit resource management — PdfDocument must be closed (not just disposed) before the output is written, and resource management patterns differ in some respects from idiomatic C# IDisposable patterns. Teams porting from iTextSharp to iText 7 will find the API significantly restructured; the migration is not a drop-in replacement.

The pdfHTML module's CSS engine is a custom implementation — rendering fidelity differences between pdfHTML and a Chromium-based renderer become apparent with complex CSS. Template validation against pdfHTML's specific CSS subset is required for templates that use modern CSS features.

Support Model

iText 7 is commercially supported by iText Group NV. Commercial support contracts, SLA tiers, professional services, and enterprise licensing are available. The community edition (AGPL) has community support only. iText has an active developer community, documentation, and Stack Overflow presence.

Architectural Fit

iText 7 is suited for applications requiring low-level PDF specification control — precise document structure, PAdES/LTV digital signatures, PDF/A creation and validation, XFA form processing, and complex AcroForm management — where a commercial license resolves the AGPL constraint. It is less suited for applications whose primary requirement is HTML-to-PDF generation from modern CSS templates (where pdfHTML's CSS limitations are relevant), for teams that need a self-contained library without add-on modules for common features, or for applications where the AGPL licensing model creates an unresolvable compliance problem.

Operation Comparisons

Creating a PDF Document (Low-Level API)

iText 7 — Low-Level PDF Creation

using iText.Kernel.Pdf;
using iText.Layout;
using iText.Layout.Element;
using iText.Layout.Properties;
using iText.IO.Font.Constants;
using iText.Kernel.Font;
using System.IO;

// iText 7 — create a PDF using the layout API
// PdfDocument wraps PdfWriter; Document provides the layout layer
// Both must be closed explicitly — Close() triggers final output flush

using var writer = new PdfWriter("invoice.pdf");
using var pdfDoc = new PdfDocument(writer);

// Document is the layout-API wrapper — must be closed before output is finalized
var document = new Document(pdfDoc);

// Add title paragraph
document.Add(new Paragraph("Invoice #1042")
    .SetFont(PdfFontFactory.CreateFont(StandardFonts.HELVETICA_BOLD))
    .SetFontSize(18)
    .SetTextAlignment(TextAlignment.LEFT));

// Add customer info
document.Add(new Paragraph("Customer: Acme Corp")
    .SetFont(PdfFontFactory.CreateFont(StandardFonts.HELVETICA))
    .SetFontSize(11));

// Add a table — iText 7 Table uses column width fractions
var table = new Table(UnitValue.CreatePercentArray(new float[] { 5, 2, 2 }))
    .UseAllAvailableWidth();

// Header cells
table.AddHeaderCell(new Cell().Add(new Paragraph("Description")
    .SetFont(PdfFontFactory.CreateFont(StandardFonts.HELVETICA_BOLD))));
table.AddHeaderCell(new Cell().Add(new Paragraph("Qty")
    .SetFont(PdfFontFactory.CreateFont(StandardFonts.HELVETICA_BOLD))));
table.AddHeaderCell(new Cell().Add(new Paragraph("Price")
    .SetFont(PdfFontFactory.CreateFont(StandardFonts.HELVETICA_BOLD))));

// Data row
table.AddCell(new Cell().Add(new Paragraph("Widget A")));
table.AddCell(new Cell().Add(new Paragraph("10")));
table.AddCell(new Cell().Add(new Paragraph("$99.99")));

document.Add(table);

// Close() must be called — Dispose() alone may not flush all content
document.Close();
  • Document.Close() (not just Dispose()) is required to finalize and flush the PDF output. In iText 7, the disposal and closing semantics differ from standard .NET IDisposable— forgetting Close() produces a corrupt or incomplete file.
  • PdfFontFactory.CreateFont() with standard font constants uses Type 1 fonts; embedding TrueType/web fonts requires additional configuration.
  • Column widths are expressed as percent arrays or point values — layout calculation is explicit, not CSS-driven.
  • iText 7's table model (Cell, Row, Table) is verbose per row but provides fine-grained control over cell padding, borders, and background color.

IronPDF — HTML Table to PDF

using IronPdf;

var invoice = new
{
    Id       = 1042,
    Customer = "Acme Corp",
    Lines    = new[]
    {
        new { Description = "Widget A", Qty = 10, Price = 99.99m }
    }
};

var rows = string.Concat(invoice.Lines.Select(l =>
    $"<tr><td>{l.Description}</td><td>{l.Qty}</td><td>{l.Price:C}</td></tr>"));

string html = $@"
<!DOCTYPE html>
<html>
<head>
  <style>
    body   {{ font-family: Arial; font-size: 11pt; }}
    h1     {{ font-size: 18pt; }}
    table  {{ width: 100%; border-collapse: collapse; margin-top: 14px; }}
    th, td {{ border: 1px solid #ddd; padding: 6px 10px; }}
    th     {{ background: #f0f0f0; font-weight: bold; }}
  </style>
</head>
<body>
  <h1>Invoice #{invoice.Id}</h1>
  <p>Customer: {invoice.Customer}</p>
  <table>
    <thead><tr><th>Description</th><th>Qty</th><th>Price</th></tr></thead>
    <tbody>{rows}</tbody>
  </table>
</body>
</html>";

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop    = 20;
renderer.RenderingOptions.MarginBottom = 20;

using var pdf = await renderer.RenderHtmlAsPdfAsync(html);
pdf.SaveAs("invoice.pdf");

The table is expressed as standard HTML/CSS — no column width arrays, no cell construction per row. The template is previewable in a browser. The HTML string to PDF guide covers full rendering configuration.

Digital Signatures (PAdES / LTV)

iText 7 has strong digital signature support including PAdES (PDF Advanced Electronic Signatures) profiles and LTV (long-term validation) — an area where iText has significant depth.

iText 7 — Digital Signature

using iText.Kernel.Pdf;
using iText.Signatures;
using Org.BouncyCastle.Pkcs;
using Org.BouncyCastle.X509;
using System.IO;

// iText 7 digital signature — PdfSigner API
// iText 7 uses BouncyCastle for cryptographic operations
// Load the PKCS#12 certificate store
using var certStream = File.OpenRead("company-cert.pfx");
var store = new Pkcs12Store(certStream, "cert-password".ToCharArray());
string alias = store.Aliases.Cast<string>().FirstOrDefault(
    a => store.IsKeyEntry(a));

var privateKey     = store.GetKey(alias).Key;
var certChain      = store.GetCertificateChain(alias)
                          .Select(e => e.Certificate).ToArray();

using var reader   = new PdfReader("unsigned.pdf");
using var signer   = new PdfSigner(reader,
    File.OpenWrite("signed.pdf"), new StampingProperties());

signer.SetFieldName("Signature1");

// IExternalSignature — BouncyCastle implementation
var signature = new PrivateKeySignature(privateKey, DigestAlgorithms.SHA256);

// Sign with chain — CRL/OCSP can be added for LTV
signer.SignDetached(signature, certChain,
    null,  // CRL list — add for LTV
    null,  // OCSP client — add for LTV
    null,  // TSA client — add for timestamp
    0, PdfSigner.CryptoStandard.CMS);
  • iText 7 uses BouncyCastle for all cryptographic operations — this is a significant additional dependency that must be managed separately.
  • LTV (Long-Term Validation) requires adding CRL/OCSP responses — iText 7 provides classes for this (ICrlClient, IOcspClient, ITSAClient).
  • PAdES profiles (B-B, B-T, B-LT, B-LTA) are supported via iText's signing API — this is genuine depth not available in all libraries.
  • The BouncyCastle API is Java-ported — X.509 certificate handling in C# is more idiomatic via System.Security.Cryptography.X509Certificates.

IronPDF — Digital Signatures

using IronPdf;
using IronPdf.Signing;

// Sign an existing PDF
using var pdf = PdfDocument.FromFile("unsigned.pdf");

var sig = new PdfSignature("company-cert.pfx", "cert-password")
{
    SigningReason   = "Approved for distribution",
    SigningLocation = "Chicago, IL"
};

// Sign using .NET X.509 — no BouncyCastle dependency
pdf.Sign(sig);
pdf.SaveAs("signed.pdf");

IronPDF's signing uses .NET's native System.Security.Cryptography.X509Certificates — no BouncyCastle dependency. The digital signatures guide covers certificate configuration, visible signature appearance, and HSM-backed signing. For PAdES/LTV requirements specifically, verify IronPDF's current support level against your compliance requirements.

PDF/A Compliance

iText 7 — PDF/A Creation

using iText.Kernel.Pdf;
using iText.Pdfa;
using iText.Kernel.Font;
using iText.Layout;
using iText.Layout.Element;
using System.IO;

// iText 7 — create a PDF/A-1B conformant document from scratch
// PdfADocument enforces PDF/A constraints during document construction
using var intentStream = File.OpenRead("sRGB_CS_profile.icm"); // color profile required
var intent = new PdfOutputIntent(
    "Custom", "", "http://www.color.org", "sRGB IEC61966-2.1",
    intentStream);

using var writer = new PdfWriter("output-pdfa.pdf",
    new WriterProperties().SetPdfVersion(PdfVersion.PDF_1_4));
using var pdfDoc = new PdfADocument(writer,
    PdfAConformanceLevel.PDF_A_1B, intent);

var document = new Document(pdfDoc);

// All fonts must be embedded — PdfADocument enforces this
var font = PdfFontFactory.CreateFont("arial.ttf",
    iText.IO.Font.PdfEncodings.WINANSI, PdfFontFactory.EmbeddingStrategy.FORCE_EMBEDDED);

document.Add(new Paragraph("Archived Document")
    .SetFont(font)
    .SetFontSize(12));

document.Close();
  • PDF/A requires an embedded color output intent (ICC color profile) — iText 7 enforces this constraint at document construction time.
  • All fonts must be embedded — iText 7's PdfADocument will throw if a non-embedded font is used.
  • A color profile file (.icm) must be available at the application's deployment location.
  • PdfADocument validates constraints during construction — PDF/A violations throw exceptions rather than producing non-conformant output.

IronPDF — PDF/A Compliance

using IronPdf;

// Generate from HTML and convert to PDF/A
var renderer = new ChromePdfRenderer();
using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Archived Document</h1></body></html>");

// SaveAsPdfA converts the rendered PDF to PDF/A conformance
pdf.SaveAsPdfA("output-pdfa.pdf");

// Or convert an existing PDF to PDF/A
using var existing = PdfDocument.FromFile("existing.pdf");
existing.SaveAsPdfA("existing-pdfa.pdf");

IronPDF's SaveAsPdfA() handles color profile embedding and font embedding automatically. The PDF/A guide covers conformance level options. The construction model is simpler — no manual color profile management required.

AcroForm Field Filling

iText 7 — AcroForm Field Filling

using iText.Kernel.Pdf;
using iText.Forms;
using iText.Forms.Fields;
using System.IO;

// iText 7 — fill AcroForm fields in an existing PDF
using var reader = new PdfReader("form.pdf");
using var writer = new PdfWriter("form-filled.pdf");
using var pdfDoc = new PdfDocument(reader, writer);

var form = PdfAcroForm.GetAcroForm(pdfDoc, false);  // false = don't create if absent

if (form != null)
{
    IDictionary<string, PdfFormField> fields = form.GetAllFormFields();

    // Set text field value
    if (fields.TryGetValue("CustomerName", out var nameField))
        nameField.SetValue("Acme Corp");

    // Set checkbox
    if (fields.TryGetValue("TermsAccepted", out var checkField))
        checkField.SetValue("Yes");  // verify: may require "On" or specific export value

    // Flatten to prevent further editing — locks field values in place
    form.FlattenFields();
}

pdfDoc.Close();
  • PdfDocument requires a separate PdfReader and PdfWriter for read-modify-save operations — cannot round-trip through a single object.
  • Checkbox values in iText 7 may require the specific export value ("On", "Yes", or a custom value defined in the field) rather than a generic string
  • PdfAcroForm.GetAcroForm(doc, false) returns null for documents with no form — null guards are required.
  • pdfDoc.Close() is required to finalize output, separate from Dispose().

IronPDF — AcroForm Field Filling

using IronPdf;

using var pdf = PdfDocument.FromFile("form.pdf");

// Enumerate all fields — unified collection, no type cast
foreach (var field in pdf.Form.Fields)
    Console.WriteLine($"{field.Name}: {field.Value}");

// Set by name — direct indexer
pdf.Form["CustomerName"].Value = "Acme Corp";
pdf.Form["TermsAccepted"].Value = "Yes";

// Flatten to lock values
pdf.Form.Flatten();

pdf.SaveAs("form-filled.pdf");

IronPDF's form API uses a direct indexer without requiring separate reader/writer objects. The edit forms guide covers all field types including checkboxes, radio buttons, and signature fields. pdf.SaveAs() finalizes the document — no separate Close() call needed.

Commonly Reported Limitations

  • AGPL licensing is the most reported operational limitation: teams adopting iText 7 without a commercial license face an AGPL viral copyleft obligation — any application accessing the library must release its complete source code under AGPL. This is a binary compliance issue, not a nuance. Verify your legal requirements against the AGPL terms before any production adoption.
  • iTextSharp (iText 5 .NET) is unmaintained and does not support modern .NET runtimes cleanly — migration to iText 7 is a rewrite, not an upgrade, as the API changed substantially.
  • iText 7's PdfDocument.Close() requirement is a common source of bugs in teams migrating from iTextSharp — the document must be explicitly closed to flush the output; relying on using/Dispose() alone is insufficient in some scenarios.
  • BouncyCastle is a required dependency for iText 7's signing API — it is a Java-ported cryptography library with its own versioning and NuGet management concerns.
  • The pdfHTML add-on's CSS coverage (Flexbox, Grid, CSS variables) is more limited than Chromium-based renderers — validate all HTML templates against pdfHTML specifically before production deployment.
  • iText 7 is a port of a Java library — the API surface reflects Java conventions (verbose method chains, Java type names in the .NET API) that may require adaptation for idiomatic C#.

Conclusion

When iText 7 for .NET is technically reasonable

iText 7 is technically reasonable for applications that have resolved the AGPL licensing constraint — either by operating under an AGPL-compatible open-source license or by purchasing a commercial iText license. Within that constraint, iText 7 is a strong fit for applications requiring deep PDF specification control: PAdES/LTV digital signatures with full chain validation, XFA form processing, PDF/A creation and validation with strict conformance enforcement, and precise low-level document model access. Its enterprise support model and the depth of its specification coverage make it a defensible choice for regulated industries where these specific capabilities are hard requirements.

When the architectural mismatch becomes significant

The mismatch becomes significant when HTML-to-PDF generation from modern CSS templates is the primary requirement — iText 7's pdfHTML add-on uses a custom CSS engine with coverage gaps relative to Chromium. It also becomes significant when the AGPL licensing constraint cannot be resolved without a commercial license that may be disproportionate to the use case, when the BouncyCastle dependency adds NuGet management complexity, when the Java-ported API requires substantial adaptation for idiomatic C#, or when a simpler self-contained library without add-on modules covers the requirement adequately.

How IronPDF approaches the same problem space

IronPDF approaches HTML-to-PDF generation with Chromium — full CSS3 fidelity with no CSS engine gap to manage — and pairs that with a PdfDocument manipulation API covering most of iText 7's manipulation surface in a single NuGet package. It is licensed commercially with no AGPL or open-source disclosure requirement for proprietary applications, and uses .NET native cryptography rather than BouncyCastle for signing. The IronPDF documentation overview covers the full capability surface across both generation and manipulation.

For teams evaluating iText 7: has the AGPL licensing constraint been formally reviewed against the application's commercial use requirements, and does the answer to that review determine whether a commercial iText license or an alternative library is the more appropriate path?
