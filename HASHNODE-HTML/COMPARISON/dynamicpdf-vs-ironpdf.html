DynamicPDF vs IronPDF: a .NET engineer reference for 2026

the engineering breakdown for .NET teams

Problem Framing

PDF generation libraries for .NET fall into two broad architectural categories: those that generate PDFs by rendering HTML and CSS (using a browser engine or a CSS layout engine), and those that generate PDFs via a document object model — an API where the developer constructs the document programmatically by adding elements to a page (text blocks, images, shapes, tables) using a library-specific type system. Both approaches solve the same output problem but require different authoring skills, produce different degrees of layout control, and have different maintenance characteristics when content or styling changes.

The HTML/CSS approach leverages existing web skills and tooling — the same CSS that styles a web page can style a PDF template, and the template is previewable in a browser before rendering. The document object model approach requires learning the library's own layout types and produces code that is more tightly coupled to the document structure. Teams that choose a document model library typically do so for fine-grained control over layout, for environments where HTML tooling is absent, or because their documents have highly structured, tabular content that maps naturally to a programmatic construction model.

DynamicPDF and IronPDF are representative of these two categories. DynamicPDF uses a document object model; IronPDF uses HTML-to-PDF via Chromium. The comparison is therefore as much about authoring model as it is about feature parity. Teams evaluating both should consider not just what each library can produce, but how the document authoring workflow integrates with their team's skill set and their document's change velocity.

What DynamicPDF Is Designed to Do

DynamicPDF is a suite of commercial .NET PDF libraries developed by ceTe Software. The suite is divided into multiple products: DynamicPDF Generator handles PDF creation, DynamicPDF Merger handles document combining and manipulation, DynamicPDF Rasterizer converts PDFs to images, and DynamicPDF PrintManager handles printing. Each product is a separate NuGet package; teams typically license the combination they need.

DynamicPDF Generator creates PDFs using a document object model. The developer constructs a Document object, adds Page objects, and populates pages with Element objects — Label, TextArea, Table, Image, Line, Rectangle, FormattedArea, CheckBox, and so on. Each element has properties for position, size, font, color, and content. The library calculates layout within the document model and outputs the PDF. DynamicPDF Generator is not an HTML renderer — it does not accept HTML strings or render CSS. It supports a wide range of element types including barcodes, QR codes, charts (via a charting add-on), and complex table layouts. The library is available for .NET Framework and .NET Core / .NET 5+; verify current .NET version support in ceTe documentation.

DynamicPDF Merger provides document manipulation: merging, splitting, page ordering, background overlays, watermarking, form filling, and outlines. It can overlay one PDF onto another — a common pattern for applying letterhead templates to generated content. The product suite is commercial with per-developer and per-server licensing; verify current terms with ceTe Software.

What IronPDF Is Designed to Do

IronPDF is a .NET PDF library built on embedded Chromium for HTML-to-PDF generation. ChromePdfRenderer accepts HTML strings, HTML files, and URLs and produces PDFs with full CSS3 fidelity — Flexbox, Grid, CSS variables, web fonts, SVG, and JavaScript execution. PdfDocument handles loading, modifying, and saving existing PDFs, covering merge and split, page manipulation, text and image extraction, form filling, digital signatures, encryption, PDF/A compliance, watermarks, redaction, and more.

The authoring model for document creation is HTML and CSS — the developer writes an HTML template (using string interpolation, Razor, or a template engine for data binding) and passes it to ChromePdfRenderer. The template can be previewed in a browser. The rendering options guide covers paper size, margins, orientation, headers, footers, and JavaScript wait conditions. Both ChromePdfRenderer and PdfDocument implement IDisposable. License initialization is a one-time startup call; see the license setup guide. IronPDF runs on Windows, Linux, macOS, and in Docker containers.

Key Limitations of DynamicPDF

Product Status

DynamicPDF is an actively maintained commercial suite. ceTe Software has maintained the product line across multiple .NET generations. Verify the current .NET version support and release cadence in official ceTe documentation. Each product in the suite (Generator, Merger, Rasterizer, PrintManager) is separately licensed and versioned.

Missing Capabilities

DynamicPDF Generator does not accept HTML input — it cannot render HTML strings, HTML files, or URLs to PDF. Teams whose document templates are authored in HTML/CSS must maintain a separate representation of those documents in DynamicPDF's element API. There is no way to use a web browser to preview a DynamicPDF Generator document before it is rendered — the development cycle requires rendering to PDF to inspect output. Modern CSS features (Flexbox, Grid, CSS variables, web font loading) have no equivalent in DynamicPDF's element model. DynamicPDF does not provide async rendering APIs comparable to RenderHtmlAsPdfAsync().

Technical Constraints

DynamicPDF Generator's layout model requires explicit element positioning. While the library handles some automatic layout (text wrapping within a TextArea, table row height) elements are placed at explicit coordinates or within a structured element hierarchy. Variable-content documents — where the amount of content on a page is data-dependent — require dynamic construction code that sizes and positions elements based on content length. This is more code than an equivalent HTML template where CSS handles the reflowing.

Table rendering in DynamicPDF is feature-rich but requires constructing CellDef, RowDef, and Cell objects explicitly — a verbosity that reflects the power of the API but requires more code per row than an equivalent HTML <table>. Charts require the DynamicPDF Charts add-on.

Support Model

ceTe Software provides commercial support for DynamicPDF. Support channel details, SLA terms, and enterprise options should be verified directly with ceTe. The multi-product structure means support queries may be scoped to a specific product (Generator vs. Merger) depending on the feature area.

Architectural Fit

DynamicPDF is well-suited for applications that generate highly structured, tabular documents where layout precision matters and HTML/CSS is not the desired authoring model. It is less suited for applications generating documents from existing HTML templates, for teams that want browser-previewable templates, or for applications where the document design is expected to change frequently and CSS-based iteration is faster than updating element API code.

Operation Comparisons

Generating a PDF Invoice (Document Object Model)

DynamicPDF — Invoice via Element API

using ceTe.DynamicPDF;
using ceTe.DynamicPDF.PageElements;

// DynamicPDF Generator — build a document via the element object model
var doc = new Document();

// Add a page — standard US Letter size
var page = new Page(PageSize.Letter, PageOrientation.Portrait);

// Add a title label — positioned at x=50, y=50 in PDF points
page.Elements.Add(new Label("Invoice #1042",
    x: 50, y: 50, width: 500, height: 24,
    font: Font.Helvetica, fontSize: 18));

// Add a customer line
page.Elements.Add(new Label("Customer: Acme Corp",
    x: 50, y: 85, width: 500, height: 16,
    font: Font.Helvetica, fontSize: 11));

// Add a table — DynamicPDF table with explicit column widths
var table = new Table2(x: 50, y: 120, width: 500, height: 0);
// Table2 supports dynamic row sizing based on content

// Define columns
table.Columns.Add(new Column(300));  // Description column
table.Columns.Add(new Column(100));  // Qty column
table.Columns.Add(new Column(100));  // Price column

// Header row
Row2 headerRow = table.Rows.Add(24);
headerRow.Cells[0].Add(new Label("Description", 0, 0, 300, 24, Font.HelveticaBold, 10));
headerRow.Cells[1].Add(new Label("Qty",         0, 0, 100, 24, Font.HelveticaBold, 10));
headerRow.Cells[2].Add(new Label("Price",       0, 0, 100, 24, Font.HelveticaBold, 10));

// Data row
Row2 dataRow = table.Rows.Add(20);
dataRow.Cells[0].Add(new Label("Widget A", 0, 0, 300, 20, Font.Helvetica, 10));
dataRow.Cells[1].Add(new Label("10",       0, 0, 100, 20, Font.Helvetica, 10));
dataRow.Cells[2].Add(new Label("$99.99",   0, 0, 100, 20, Font.Helvetica, 10));

page.Elements.Add(table);
doc.Pages.Add(page);

// Save to file
doc.Draw("invoice.pdf");
// Or to stream: doc.Draw(outputStream);
  • Every element requires explicit coordinate placement or structured container positioning.
  • Font is selected from DynamicPDF's built-in font set (Font.Helvetica, etc.) or loaded from a file — web fonts are not supported via this API.
  • Table2 rows must be explicitly constructed per row — dynamic content requires a loop over the data with one table.Rows.Add() call per record.
  • Previewing the document requires rendering to PDF — there is no browser-previewable template file.
  • Document.Draw() is synchronous; no async equivalent.

IronPDF — Invoice via HTML Template

using IronPdf;

// Data for the invoice
var invoice = new
{
    Id       = 1042,
    Customer = "Acme Corp",
    Lines    = new[]
    {
        new { Description = "Widget A", Qty = 10, Price = 99.99m },
        new { Description = "Widget B", Qty  = 5, Price = 249.99m }
    },
    Total = 1349.85m
};

// Build HTML from data — production code uses Razor or Scriban for complex templates
var rows = string.Concat(invoice.Lines.Select(l =>
    $"<tr><td>{l.Description}</td><td>{l.Qty}</td><td>{l.Price:C}</td></tr>"));

string html = $@"
<!DOCTYPE html>
<html>
<head>
<style>
  body  {{ font-family: Arial, sans-serif; font-size: 11pt; }}
  h1   {{ color: #2c3e50; margin-bottom: 4px; }}
  table {{ width: 100%; border-collapse: collapse; margin-top: 14px; }}
  th, td {{ border: 1px solid #ddd; padding: 6px 10px; }}
  th   {{ background: #f0f0f0; }}
  .total {{ text-align: right; font-weight: bold; margin-top: 8px; }}
</style>
</head>
<body>
  <h1>Invoice #{invoice.Id}</h1>
  <p>Customer: {invoice.Customer}</p>
  <table>
    <thead><tr><th>Description</th><th>Qty</th><th>Price</th></tr></thead>
    <tbody>{rows}</tbody>
  </table>
  <p class='total'>Total: {invoice.Total:C}</p>
</body>
</html>";

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.Letter;
renderer.RenderingOptions.MarginTop    = 20;
renderer.RenderingOptions.MarginBottom = 20;

using var pdf = await renderer.RenderHtmlAsPdfAsync(html);
pdf.SaveAs("invoice.pdf");

The same document is expressed as HTML and CSS — no coordinate calculation, font declarations, or element construction per cell. Data rows are injected via string interpolation or a template engine. The template is previewable in a browser before rendering. The HTML string to PDF guide covers full rendering configuration.

Merging PDFs and Applying a Background Overlay

DynamicPDF — Merge with Background (Merger)

using ceTe.DynamicPDF.Merger;

// DynamicPDF Merger — merge documents and apply a PDF background template
// MergeDocument is the primary type in the Merger product
var mergeDoc = new MergeDocument("report-content.pdf");

// Append a second document
mergeDoc.Append("appendix.pdf");

// Apply a letterhead PDF as background on all pages
// BackgroundPage applies a PDF page as underlay on each output page
var background = new BackgroundPage("letterhead.pdf");
mergeDoc.Background = background;

// Draw to file
mergeDoc.Draw("report-with-letterhead.pdf");
  • DynamicPDF Merger is a separate product from Generator — both must be licensed.
  • BackgroundPage applies a PDF underlay — a common pattern for company letterhead overlays.
  • Merger's MergeDocument.Append() adds all pages from the source document; verify partial-page-range API.
  • Draw() is synchronous.

IronPDF — Merge and Background Stamp

using IronPdf;
using IronPdf.Editing;

// Load content documents
using var content  = PdfDocument.FromFile("report-content.pdf");
using var appendix = PdfDocument.FromFile("appendix.pdf");
using var merged   = PdfDocument.Merge(content, appendix);

// Apply a letterhead PDF as background on all pages
using var letterhead = PdfDocument.FromFile("letterhead.pdf");
// Stamp the letterhead page onto every content page as a background
merged.AddBackgroundPdf(letterhead);

merged.SaveAs("report-with-letterhead.pdf");

IronPDF's AddBackgroundPdf() applies a PDF as underlay to all pages. The backgrounds and foregrounds guide covers background and foreground PDF stamping options. PdfDocument.Merge() handles N-way merges in one call.

Headers, Footers, and Page Numbers

DynamicPDF — Headers and Footers

using ceTe.DynamicPDF;
using ceTe.DynamicPDF.PageElements;

var doc = new Document();
var page = new Page(PageSize.A4, PageOrientation.Portrait);

// DynamicPDF — manual header placement
// There is no declarative header/footer section — elements are positioned manually
// at the top and bottom of each page, or a PageNumberingLabel is used for page numbers

// Header label at the top of the page
page.Elements.Add(new Label("Acme Corp — Confidential",
    x: 50, y: 20, width: 495, height: 16,
    font: Font.Helvetica, fontSize: 9));

// Page number using PageNumberingLabel
// PageNumberingLabel handles automatic page number substitution
page.Elements.Add(new PageNumberingLabel(
    "Page %%CP%% of %%TP%%",  // %%CP%% = current page, %%TP%% = total pages
    x: 200, y: 800, width: 150, height: 14,
    font: Font.Helvetica, fontSize: 9));

page.Elements.Add(new Label("Report content here.",
    x: 50, y: 60, width: 495, height: 200,
    font: Font.Helvetica, fontSize: 11));

doc.Pages.Add(page);
doc.Draw("report.pdf");
  • Headers and footers are not declarative sections — they are page elements positioned at the top/bottom of each page.
  • For multi-page documents, header and footer elements must be added to each page individually, or a template page mechanism used
  • PageNumberingLabel with %%CP%% / %%TP%% tokens handles page number substitution.

IronPDF — Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize   = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop   = 22;
renderer.RenderingOptions.MarginBottom = 15;

// Declarative HTML headers — applied to every page automatically
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height       = 14,
    HtmlFragment = "<div style='font-size:9px; font-family:Arial; " +
                   "text-align:right; padding:0 14px;'>Acme Corp — Confidential</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height       = 10,
    HtmlFragment = "<div style='font-size:8px; font-family:Arial; " +
                   "text-align:center;'>Page {page} of {total-pages}</div>"
};

using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><p>Report content here.</p></body></html>");
pdf.SaveAs("report.pdf");

Headers and footers are declared once on RenderingOptions and applied automatically to every page. The {page} and {total-pages} tokens inject page numbers. The headers and footers guide covers HTML fragment styling, heights, dividers, and per-page options.

PDF/A Compliance Output

DynamicPDF — PDF/A

using ceTe.DynamicPDF;

// DynamicPDF Generator — PDF/A output
// Verify the exact API for PDF/A conformance in current ceTe documentation
// DynamicPDF has supported PDF/A-1b output in some versions

var doc = new Document();
// doc.PdfVersion = PdfVersion.PdfA1b; // verify property name and enum
// or: doc.Conformance = PdfConformance.PdfA1b; // verify

var page = new Page(PageSize.A4);
page.Elements.Add(new Label("Archived Document",
    x: 50, y: 50, width: 400, height: 20,
    font: Font.Helvetica, fontSize: 12));

doc.Pages.Add(page);
doc.Draw("archived.pdf");
// Verify that the output passes an independent PDF/A validator
  • DynamicPDF's PDF/A support should be verified in current ceTe documentation — the supported conformance levels and required configuration vary.
  • Font embedding and color space requirements for PDF/A must be satisfied at the document construction level; verify that DynamicPDF handles these automatically or requires explicit configuration.

IronPDF — PDF/A Compliance

using IronPdf;

// Generate a PDF from HTML and immediately save as PDF/A
var renderer = new ChromePdfRenderer();
using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Archived Document</h1></body></html>");

// SaveAsPdfA converts the rendered document to PDF/A conformance
pdf.SaveAsPdfA("archived-pdfa.pdf");

// Or convert an existing document:
// using var existing = PdfDocument.FromFile("existing.pdf");
// existing.SaveAsPdfA("existing-pdfa.pdf");

SaveAsPdfA() converts any PdfDocument to PDF/A conformance. The PDF/A guide covers conformance level options and validation.

Commonly Reported Limitations

  • DynamicPDF Generator's element API requires explicit coordinate placement or structured containers — variable-content documents require custom layout logic to handle dynamic element sizing and positioning, which adds code proportional to the complexity of the document layout.
  • The Generator and Merger products are separate licenses and separate NuGet packages — teams needing both generation and manipulation must manage two product line versions and two license allocations.
  • Multi-page documents require header and footer elements to be applied per page (or via a template mechanism) — this is more verbose than a declarative header/footer declaration that automatically applies to all pages.
  • Document.Draw() is synchronous — there is no native async rendering API; wrapping in Task.Run() is a common workaround in ASP.NET Core contexts.
  • Cross-platform support (Linux, Docker) for DynamicPDF should be verified in current ceTe documentation — some older versions had Windows-only dependencies.

Conclusion

When DynamicPDF is technically reasonable

DynamicPDF is technically reasonable for applications that generate highly structured, tabular documents where element-level control over layout is important and HTML/CSS is not the intended authoring model. The barcode and QR code generation built into DynamicPDF Generator is a specific capability that many HTML-to-PDF libraries require workarounds to reproduce. Teams with long-established DynamicPDF integrations and stable document templates where the element API is already fully built out have little motivation to migrate — the code works, the templates are stable, and the rewrite cost is real.

When the architectural mismatch becomes significant

The mismatch becomes significant when document templates need to reflect modern CSS layouts (responsive, Flexbox, web fonts), when the development team's skills are HTML/CSS-oriented and maintaining element API code is a productivity drag, when variable-height content produces complex layout calculation code, when async rendering under concurrent load is required, or when the separation between Generator and Merger creates friction in workflows that require both in the same pipeline.

How IronPDF approaches the same problem space

IronPDF uses HTML and CSS as the document authoring model — the template authoring workflow matches web development skills, templates are browser-previewable, and CSS handles dynamic content layout automatically. Post-render manipulation (merge, sign, compress, form-fill) is available on the same PdfDocument type without a separate product license. The IronPDF documentation overview covers both generation and manipulation in a single API surface.

For teams evaluating DynamicPDF: how much of the current document generation code consists of layout calculation logic (coordinate math, element sizing, row construction) that would be replaced by CSS if the authoring model shifted to HTML — and would that reduction in code complexity affect the evaluation?
