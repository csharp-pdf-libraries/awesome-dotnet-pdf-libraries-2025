HiQPdf vs IronPDF: side by side — capabilities, limits, fit

an architecture-first comparison

Problem Framing

When two libraries use the same underlying rendering engine — Chromium-based HTML-to-PDF conversion — the feature comparison shifts from rendering fidelity to everything around the renderer: API surface, manipulation capabilities, deployment model, licensing, and long-term maintenance posture. Teams evaluating two Chromium-based libraries are essentially asking: given that both can render modern CSS correctly, which library's broader feature set, integration model, and operational characteristics better fit our application?

HTML-to-PDF libraries built on Chromium share a rendering baseline that was not possible with earlier QtWebKit-based tools. Flexbox, CSS Grid, CSS variables, web font loading, and JavaScript execution are all supported at the browser level. The differentiation between Chromium-based libraries therefore lies in how they expose the Chromium rendering pipeline — what configuration surface they provide, what their async story is, whether they also cover PDF manipulation operations (forms, signatures, compliance), and how they behave under concurrent load in ASP.NET Core applications.

HiQPdf and IronPDF both fit this category. Both are commercial .NET libraries offering HTML-to-PDF via Chromium, with different levels of coverage across the PDF manipulation surface, different API designs, and different support and licensing models. The comparison in this article focuses on those differentiators rather than on rendering quality, which is largely determined by the shared Chromium foundation.

What HiQPdf Is Designed to Do

HiQPdf is a commercial .NET HTML-to-PDF library. Current versions use Chromium for HTML rendering, providing CSS3 fidelity including Flexbox, Grid, web fonts, and JavaScript execution. Earlier versions of HiQPdf used a WebKit-based engine

The library's primary class is HtmlToPdf, which accepts HTML strings, HTML file paths, and URLs for conversion. Configuration is applied via a HtmlToPdfOptions object covering paper size, margins, page orientation, custom headers and footers, page numbers, JavaScript wait delay, PDF version, encryption, and metadata. HiQPdf also includes a PDF tools API for merging documents and appending pages. The library is distributed as a NuGet package for .NET Framework and .NET Core / .NET 5+. Licensing is per-developer or per-deployment server; verify current terms and .NET version support in official HiQPdf documentation. The library targets Windows and Linux deployments; verify current platform support matrix.

What IronPDF Is Designed to Do

IronPDF is a .NET PDF library built on embedded Chromium, distributed as a NuGet package targeting .NET Standard 2.0 and above. ChromePdfRenderer generates PDFs from HTML strings, HTML files, and URLs with full CSS3 fidelity. PdfDocument provides a manipulation API for loading and modifying existing PDFs. Both implement IDisposable.

Beyond HTML-to-PDF generation, IronPDF's PdfDocument covers: text extraction, image extraction, AcroForm reading and filling, form creation, document merge and split, page add/copy/delete/rotate, password encryption and permission restrictions, digital signatures (X.509 PKCS#12 and HSM-backed), PDF/A and PDF/UA compliance output, metadata read/write, watermarks, stamps, find-and-replace text, redaction, annotations, bookmark management, compression, and linearization. The rendering options guide covers IronPDF's HTML rendering configuration. License initialization is a one-time startup call; see the license setup guide. IronPDF supports Windows, Linux, macOS, and Docker containers.

Key Limitations of HiQPdf

Product Status

HiQPdf is a commercially maintained library. Verify the current release version, .NET version compatibility matrix (particularly .NET 6, 8, and later), and release cadence in official HiQPdf documentation. As a commercial library from an independent vendor, confirm the vendor's commitment to long-term maintenance and Chromium update cadence before planning a multi-year dependency.

Missing Capabilities

HiQPdf's manipulation API is limited relative to IronPDF's. The library includes document merging and page appending but lacks a broad manipulation surface: text extraction from existing PDFs, image extraction, AcroForm field filling, form creation, digital signatures, PDF/A compliance output, PDF/UA accessibility, redaction, find-and-replace text, and advanced annotation management are either absent or limited

Technical Constraints

HiQPdf's HtmlToPdf converter creates a new conversion context per instance in typical usage

Support Model

HiQPdf is commercially supported by an independent vendor. Support channel availability, response times, and SLA commitments should be verified directly with the vendor. The depth of community resources (public documentation, Stack Overflow presence, example repositories) is a factor in evaluating the practical support experience.

Architectural Fit

HiQPdf is a well-matched fit for applications whose primary requirement is HTML-to-PDF conversion with a straightforward API and where post-generation manipulation is limited to basic document merging. For applications that also require post-render text extraction, AcroForm filling, digital signatures, PDF/A output, or redaction — and want to handle all PDF operations from a single library — the manipulation API gap may require a second dependency.

Operation Comparisons

HTML String to PDF

HiQPdf — HTML String to PDF

using HiQPdf;

// HiQPdf HtmlToPdf — primary converter class
// Verify thread-safety model: confirm whether one instance per request
// is required or whether singleton DI registration is safe
var converter = new HtmlToPdf();

// Configure options on the converter
converter.Document.PageSize      = PdfPageSize.A4;
converter.Document.PageOrientation = PdfPageOrientation.Portrait;
// Margins in points
converter.Document.Margins.Top    = 10;
converter.Document.Margins.Bottom = 10;
converter.Document.Margins.Left   = 10;
converter.Document.Margins.Right  = 10;

// JavaScript wait delay in milliseconds
converter.TriggerMode = ConversionTriggerMode.WaitTime;
converter.WaitBeforeConvert = 1000;  // 1 second; verify property names

string html = @"
<!DOCTYPE html>
<html>
<head>
  <style>
    body  { font-family: Arial; font-size: 11pt; }
    .grid { display: grid; grid-template-columns: 1fr 1fr; gap: 12px; }
    .card { border: 1px solid #ddd; padding: 10px; }
  </style>
</head>
<body>
  <h1>Invoice #1042</h1>
  <div class='grid'>
    <div class='card'>Customer: Acme Corp</div>
    <div class='card'>Total: $1,599.00</div>
  </div>
</body>
</html>";

// ConvertHtmlToMemoryStream returns the PDF as a byte array (or stream)
// Verify exact return type and method name in current HiQPdf docs
byte[] pdfBytes = converter.ConvertHtmlToMemoryStream(html).ToArray();
System.IO.File.WriteAllBytes("invoice.pdf", pdfBytes);
  • Verify whether HtmlToPdf instances are thread-safe for singleton reuse in ASP.NET Core, or whether a new instance is required per conversion.
  • ConversionTriggerMode.WaitTime is a fixed delay
  • Verify property names (Document.Margins, WaitBeforeConvert, etc.) against current HiQPdf documentation — these have varied across versions.
  • HiQPdf's conversion is synchronous; verify whether a native async API is available.

IronPDF — HTML String to PDF

using IronPdf;

// ChromePdfRenderer — thread-safe as a singleton in DI
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize        = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.PaperOrientation = IronPdf.Rendering.PdfPaperOrientation.Portrait;
renderer.RenderingOptions.MarginTop        = 10;
renderer.RenderingOptions.MarginBottom     = 10;
renderer.RenderingOptions.MarginLeft       = 10;
renderer.RenderingOptions.MarginRight      = 10;

// Wait for a specific DOM element — condition-based rather than fixed delay
renderer.RenderingOptions.WaitFor.HtmlElement(".grid");

string html = @"
<!DOCTYPE html>
<html>
<head>
  <style>
    body  { font-family: Arial; font-size: 11pt; }
    .grid { display: grid; grid-template-columns: 1fr 1fr; gap: 12px; }
    .card { border: 1px solid #ddd; padding: 10px; }
  </style>
</head>
<body>
  <h1>Invoice #1042</h1>
  <div class='grid'>
    <div class='card'>Customer: Acme Corp</div>
    <div class='card'>Total: $1,599.00</div>
  </div>
</body>
</html>";

// Native async — no Task.Run() wrapper required
using var pdf = await renderer.RenderHtmlAsPdfAsync(html);
byte[] pdfBytes = pdf.BinaryData;
System.IO.File.WriteAllBytes("invoice.pdf", pdfBytes);

ChromePdfRenderer is thread-safe as a singleton. The WaitFor.HtmlElement() condition waits for a specific DOM element rather than a fixed delay — more reliable for dynamic content. The HTML string to PDF guide covers all rendering options including viewport, base URL, and custom CSS injection.

URL to PDF

HiQPdf — URL to PDF

using HiQPdf;

var converter = new HtmlToPdf();
converter.Document.PageSize = PdfPageSize.A4;

// JavaScript wait for URL-based renders
converter.TriggerMode        = ConversionTriggerMode.WaitTime;
converter.WaitBeforeConvert  = 2000;  // 2s for JS to execute

// Verify cookie/auth injection API in current HiQPdf docs
// Some versions support custom HTTP headers via converter.CustomHttpHeaders
// converter.HttpCookies.Add(new HiQPdf.HttpCookie("session", "token")); // verify

// ConvertUrlToMemoryStream renders the URL using HiQPdf's Chromium
byte[] pdfBytes = converter.ConvertUrlToMemoryStream(
    "https://reports.example.com/q3").ToArray();
System.IO.File.WriteAllBytes("q3-report.pdf", pdfBytes);
  • Verify the exact API for custom cookies and HTTP headers in the current HiQPdf version — method and class names have varied.
  • ConversionTriggerMode.WaitTime uses a fixed delay

IronPDF — URL to PDF

using IronPdf;
using System.Collections.Generic;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Session cookie forwarding for authenticated URLs
renderer.RenderingOptions.CustomCookies = new Dictionary<string, string>
{
    { "session_id", "current-session-token" }
};

// Wait until the page's network activity is idle (better than fixed delay)
renderer.RenderingOptions.WaitFor.NetworkIdle();

using var pdf = await renderer.RenderUrlAsPdfAsync("https://reports.example.com/q3");
await System.IO.File.WriteAllBytesAsync("q3-report.pdf", pdf.BinaryData);

IronPDF's WaitFor.NetworkIdle() waits until network activity settles rather than using a fixed delay — more reliable for pages that load data asynchronously. The URL to PDF guide covers authentication, cookie injection, and all wait condition types.

IronPDF — HTML Headers and Footers

using IronPdf;
using IronPdf.Editing;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize    = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop    = 22;  // room for header
renderer.RenderingOptions.MarginBottom = 15;

renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    Height       = 14,
    HtmlFragment = "<div style='font-size:9px; font-family:Arial; " +
                   "text-align:right; padding:0 14px;'>Acme Corp — Confidential</div>",
    DrawDividerLine = true
};

renderer.RenderingOptions.HtmlFooter = new HtmlHeaderFooter
{
    Height       = 10,
    HtmlFragment = "<div style='font-size:8px; font-family:Arial; " +
                   "text-align:center;'>Page {page} of {total-pages}</div>"
};

using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><p>Report content.</p></body></html>");
pdf.SaveAs("report.pdf");

IronPDF's HtmlHeaderFooter.HtmlFragment accepts any HTML with inline CSS. The {page} and {total-pages} tokens inject page numbers. The headers and footers guide covers height, dividers, per-page control, and advanced HTML header templates.

IronPDF — Digital Signatures

using IronPdf;
using IronPdf.Signing;

// Sign a newly rendered PDF
var renderer = new ChromePdfRenderer();
using var pdf = renderer.RenderHtmlAsPdf(
    "<html><body><h1>Contract</h1><p>Terms here.</p></body></html>");

var sig = new PdfSignature("company-cert.pfx", "cert-password")
{
    SigningReason   = "Approved for distribution",
    SigningLocation = "Chicago, IL",
    SigningContact  = "legal@example.com"
};
pdf.Sign(sig);
pdf.SaveAs("signed-contract.pdf");

// Or sign an existing PDF
using var existingPdf = PdfDocument.FromFile("unsigned.pdf");
existingPdf.Sign(sig);
existingPdf.SaveAs("unsigned-signed.pdf");

IronPDF's PdfSignature accepts PKCS#12 certificates and supports visible signature appearance, multi-signature workflows, and HSM-backed signing. The digital signatures guide covers all certificate configuration options.

Commonly Reported Limitations

  • HiQPdf's manipulation API (text extraction, form filling, digital signatures) is reported as limited relative to full-featured PDF libraries
  • Thread-safety of the HtmlToPdf converter for concurrent ASP.NET Core requests should be verified explicitly — some versions have required per-request instantiation, which affects DI registration strategy and per-request overhead.
  • HiQPdf's documentation depth and community presence (Stack Overflow, GitHub examples, public issue tracker) are more limited than larger commercial PDF SDKs — factor into estimates of time-to-resolution for production issues.
  • Chromium binary distribution: verify the footprint of the NuGet package and any Chromium binary included — some Chromium-based libraries bundle a full Chromium executable that adds significant size to Docker images and deployment artifacts.
  • Earlier HiQPdf versions used a WebKit-based engine with significantly different CSS coverage than Chromium

Conclusion

When HiQPdf is technically reasonable

HiQPdf is technically reasonable for applications whose primary requirement is HTML-to-PDF conversion and where the post-generation manipulation surface is narrow — limited to document merging, basic encryption, and straightforward document operations. Teams already integrated with HiQPdf on a stable .NET Framework or .NET Core application, with working CSS rendering and no pending requirements for text extraction, form filling, digital signatures, or compliance output, have little architectural pressure to migrate.

When the architectural mismatch becomes significant

The mismatch becomes significant when the application requires post-generation PDF manipulation beyond basic merging — particularly text extraction from existing documents, AcroForm filling, digital signatures, PDF/A compliance, redaction, or find-and-replace operations — and HiQPdf's manipulation API cannot cover those requirements. It also becomes significant when the thread-safety model for concurrent rendering is unclear, when a condition-based JavaScript wait (rather than a fixed delay) would improve reliability on dynamic pages, or when a broader manipulation surface from a single library is the architectural goal.

How IronPDF approaches the same problem space

Both libraries share a Chromium rendering foundation — the rendering quality baseline is comparable. IronPDF pairs that rendering path with a broad PdfDocument manipulation API covering the full range of post-generation operations in a single NuGet package. The IronPDF documentation overview covers both the generation and manipulation surfaces. ChromePdfRenderer is documented as thread-safe for singleton DI registration, and RenderHtmlAsPdfAsync() provides native async rendering without a Task.Run() wrapper.

For teams currently on HiQPdf: which specific post-generation PDF operations — form filling, signatures, PDF/A, text extraction — are currently handled by a second library, and would consolidating those operations under the same library as the renderer change the dependency management story for the project?
