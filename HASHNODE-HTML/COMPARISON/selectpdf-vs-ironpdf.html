SelectPdf vs IronPDF: what the docs do not cover

the engineering breakdown for .NET teams

Problem Framing

HTML-to-PDF conversion in .NET has been a solved problem in principle—but the implementation quality varies enormously by rendering engine. A library that wraps a capable engine can produce consistent output for a wide range of HTML inputs; a library whose engine cannot handle modern CSS will produce correct output for simple templates and silently wrong output for complex ones. The problem is that simple templates tend to dominate the early integration work, so rendering limitations surface only after a library is embedded in production code and the template complexity grows.

SelectPdf is a .NET HTML-to-PDF library with both a free and a commercial tier. The free community edition has been available for a long time and is widely encountered in legacy .NET applications. Teams evaluating it today need to distinguish between what the free tier supports—which is limited—and what the commercial tier provides. More importantly, they need to understand the rendering engine at the core: whether it is a browser-grade engine or a lighter alternative, what CSS features it handles, and how it behaves under concurrent ASP.NET Core load.

Understanding these questions before committing to integration—or before inheriting a codebase that already uses SelectPdf—is more practical than discovering them after template development is underway. This article covers the operational details that the getting-started guide does not.

What SelectPdf Is Designed To Do

SelectPdf is a .NET library for HTML-to-PDF conversion distributed by SelectSoftware Tools. It comes in two editions: a free community edition with a limitation on PDF page count per render and a full commercial edition without those restrictions. The library accepts HTML strings, HTML files, and URLs as input and produces PDF byte arrays or files. Configuration covers paper size, orientation, margins, header and footer HTML, CSS media type selection, and JavaScript enable/disable.

SelectPdf targets .NET Framework 4.x and .NET Standard 2.0. The library bundles a rendering engine—the specific engine and its capabilities are the most important evaluation point; verify whether the current version uses a WebKit-based engine, a custom renderer, or another approach, as this determines CSS support depth. Rendering engine modernity determines whether the library can handle CSS Grid layouts, Flexbox containers, CSS custom properties, and modern JavaScript APIs that contemporary .NET web templates rely on. SelectPdf does not provide PDF manipulation beyond generation: there is no merge, encrypt, sign, form-fill, annotate, or text extraction API in the base library. The free community edition additionally carries page count restrictions that make it unsuitable for production documents of arbitrary length.

The library is distributed via NuGet as Select.HtmlToPdf. SelectPdf also provides a cloud API option for HTML-to-PDF conversion via an external service endpoint; this is architecturally distinct from the in-process library and has different operational characteristics including network latency, external service dependency, per-request cost, and capability parity with the in-process edition. The two products should be evaluated independently rather than assuming they are interchangeable.

SelectPdf has been available since the ASP.NET WebForms and early MVC era. Its longevity means it appears in many inherited codebases; teams encountering it may be evaluating it as a new tool choice or assessing whether to continue using it in an existing application. Both evaluation contexts are addressed in this comparison.

What IronPDF Is Designed To Do

IronPDF is a commercial .NET library for PDF generation and manipulation. The ChromePdfRenderer class accepts HTML strings, file paths, and URLs and converts them to PdfDocument objects using a bundled Chromium engine. Chromium's CSS engine supports Grid, Flexbox, custom properties, web fonts, SVG, and JavaScript execution—the same rendering surface as Chrome. The HTML string to PDF guide documents the primary rendering entry point.

PdfDocument implements IDisposable and carries a complete manipulation API: merge, split, encrypt, sign, annotate, form-fill, and text/image extraction. ChromePdfRenderer is thread-safe and can be shared across concurrent requests. IronPDF targets .NET Framework 4.x and .NET 6+ on Windows, Linux, and macOS, distributed as a single NuGet package with platform-native Chromium binaries resolved at NuGet restore time. The async rendering guide documents the awaitable API for integration with ASP.NET Core async pipelines.

Key Limitations of SelectPdf

Product Status

SelectPdf is a commercially maintained library with an active free community edition. Verify current release cadence and .NET version compatibility at the SelectSoftware Tools website. The community edition's page count restriction is a product-tier constraint, not a bug; verify current limits before using the free edition for any production document of variable length.

Missing Capabilities

SelectPdf is an HTML-to-PDF conversion library. It does not merge PDFs, encrypt documents, apply digital signatures, fill form fields, extract text or images, redact content, or perform any post-generation manipulation. These operations require a second library. Applications that start with SelectPdf for generation and later need manipulation encounter the standard two-library dependency accumulation pattern. The SelectPdf cloud API is a separate product with a different integration model; it does not eliminate these capability gaps in the in-process library.

Technical Constraints

The rendering engine in use determines CSS and JavaScript support. If the library uses a WebKit or custom engine rather than a current Chromium engine, CSS Grid, Flexbox, and modern JavaScript will not render correctly. This is the most significant technical constraint for templates that use contemporary CSS frameworks. Additionally, the free community edition's page limit creates a class of runtime error—document generation that succeeds in testing (short documents) fails in production (long documents)—that is difficult to catch with standard unit tests.

Concurrent rendering throughput under ASP.NET Core load depends on the engine's threading model. Verify whether the library serialises concurrent render calls or allows true parallel execution; serialisation creates a request queue under high throughput scenarios.

Support Model

The commercial edition carries vendor support; the community edition is free with community-only support. Verify current support tier options and response time commitments for the commercial license. For production applications, the free community edition's page limit restriction and community-only support model are typically disqualifying factors.

Architectural Fit

SelectPdf is appropriate for ASP.NET applications that need HTML-to-PDF conversion where the template CSS is compatible with the library's rendering engine, where post-generation manipulation is not required, and where the commercial license is acceptable. The free edition is appropriate for evaluation and short-document generation where the page limit is not reached. For applications that need modern CSS rendering, post-generation manipulation, or a single library to cover both generation and security operations, SelectPdf's scope creates gaps.

Operation Comparisons

HTML String to PDF

SelectPdf — HTML String to PDF:

// SelectPdf HTML to PDF conversion
// Package: Select.HtmlToPdf
using SelectPdf;

// HtmlToPdf is the converter entry point
var converter = new HtmlToPdf();

// Configure rendering options
converter.Options.PaperSize = PdfPageSize.A4;
converter.Options.PaperOrientation = PdfPageOrientation.Portrait;
converter.Options.MarginTop = 20;
converter.Options.MarginBottom = 20;
converter.Options.MarginLeft = 15;
converter.Options.MarginRight = 15;
// Render using print CSS media type
converter.Options.CssMediaType = HtmlToPdfCssMediaType.Print;

var htmlContent = @"
<!DOCTYPE html><html><head>
<style>
  body { font-family: Arial, sans-serif; font-size: 12px; }
  /* WARNING: CSS Grid and Flexbox support depends on engine version
  table { width: 100%; border-collapse: collapse; }
  th { background: #2c5f8a; color: white; padding: 7px; }
  td { padding: 6px; border-bottom: 1px solid #e0e0e0; }
</style></head><body>
<h1>Report</h1>
<table>
  <tr><th>Item</th><th>Value</th></tr>
  <tr><td>Revenue</td><td>$142,000</td></tr>
</table>
</body></html>";

// ConvertHtmlString returns a PdfDocument object (SelectPdf's own type)
var doc = converter.ConvertHtmlString(htmlContent);

// Save to file
doc.Save("output.pdf");
// Explicit close
doc.Close();

Technical constraints:

  • HtmlToPdf creates a new converter per use; verify whether it implements IDisposable and requires explicit disposal
  • The free community edition limits output to a fixed page count; documents exceeding this limit produce truncated output without an exception in some versions
  • CSS rendering accuracy depends on the bundled engine version
  • Concurrent access: verify whether HtmlToPdf is thread-safe or requires one instance per request; serialisation under load is a known concern for native-backed converters

IronPDF — HTML String to PDF:

using IronPdf;

// ChromePdfRenderer is thread-safe — safe to use as a singleton or static instance
var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 20;
renderer.RenderingOptions.MarginLeft = 15;
renderer.RenderingOptions.MarginRight = 15;
renderer.RenderingOptions.CssMediaType = IronPdf.Rendering.PdfCssMediaType.Print;

var htmlContent = @"
<!DOCTYPE html><html><head>
<style>
  body { font-family: Arial, sans-serif; font-size: 12px; }
  /* Full CSS3 support — Grid, Flexbox, custom properties all render correctly */
  .header { display: flex; justify-content: space-between; margin-bottom: 16px; }
  table { width: 100%; border-collapse: collapse; }
  th { background: #2c5f8a; color: white; padding: 7px; }
  td { padding: 6px; border-bottom: 1px solid #e0e0e0; }
</style></head><body>
<div class='header'>
  <strong>Report</strong>
  <span>2025-Q4</span>
</div>
<table>
  <tr><th>Item</th><th>Value</th></tr>
  <tr><td>Revenue</td><td>$142,000</td></tr>
</table>
</body></html>";

// PdfDocument is not a byte[] — it carries full manipulation API
using var pdf = renderer.RenderHtmlAsPdf(htmlContent);
pdf.SaveAs("output.pdf");

The Chromium engine renders Flexbox and Grid layout in the HTML header div without any workaround; the same markup that renders correctly in a browser renders correctly in the PDF. The HTML string to PDF guide covers base URL configuration for resolving external stylesheets and font files referenced in the HTML.

URL to PDF

SelectPdf — URL to PDF:

// SelectPdf URL to PDF conversion
using SelectPdf;

var converter = new HtmlToPdf();
converter.Options.PaperSize = PdfPageSize.A4;
// Configure JavaScript wait delay for SPA content
converter.Options.JavaScriptEnabled = true;
converter.Options.RenderingEngine = RenderingEngine.WebKit; // verify current options
// Community edition page limit applies to URL conversion as well

// ConvertUrl fetches the page and renders it
var doc = converter.ConvertUrl("https://example.com/report");
doc.Save("url-output.pdf");
doc.Close();

Technical constraints:

  • The URL is fetched by the rendering engine inside the converter process; network access from the server must reach the target URL
  • JavaScript-heavy SPA pages may not fully render depending on the engine's JavaScript execution model and configurable wait delays
  • Authenticated pages require cookie or header injection via converter options
  • Community edition page limit applies to URL conversion

IronPDF — URL to PDF:

using IronPdf;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;

// Wait for JavaScript frameworks to finish rendering before capture
renderer.RenderingOptions.WaitFor.RenderDelay(500); // 500ms delay

// Inject session cookie for authenticated pages
renderer.RenderingOptions.CustomCookies =
    new System.Collections.Generic.Dictionary<string, string>
    {
        { "session_token", "abc123" },
        { "auth_role", "viewer" }
    };

// Full Chromium execution — SPA content renders as it would in Chrome
using var pdf = renderer.RenderUrlAsPdf("https://example.com/report");
pdf.SaveAs("url-output.pdf");

The URL to PDF guide covers cookie injection, custom HTTP request headers, and the WaitFor API. The WaitFor API supports both fixed time delays and condition-based waits (waiting for a specific DOM element or JavaScript variable) to capture SPA content at the correct render state rather than guessing a delay duration.

Headers and Footers

SelectPdf — Headers and Footers:

// SelectPdf HTML header and footer configuration
using SelectPdf;

var converter = new HtmlToPdf();
converter.Options.PaperSize = PdfPageSize.A4;
converter.Options.MarginTop = 30; // leave room for header

// HTML-based header — rendered by the same engine
converter.Header.DisplayOnFirstPage = true;
converter.Header.HtmlToPdfPage = new HtmlToPdfPage();
converter.Header.HtmlToPdfPage.HtmlString =
    "<div style='font-family:Arial;font-size:9px;padding:4px;'>" +
    "Company Report | Confidential</div>";

// Text-based footer with page number token
converter.Footer.DisplayOnFirstPage = true;
converter.Footer.TextRight = "Page {page_number} of {total_pages}";
converter.Footer.TextRightFontSize = 8;

// Verify exact property names and token format in current SelectPdf documentation
var doc = converter.ConvertHtmlString(reportHtml);
doc.Save("report-with-headers.pdf");
doc.Close();

Technical constraints:

  • Header and footer HTML is rendered by the same engine as the main content; CSS limitations apply equally
  • Token syntax ({page_number}, {total_pages}) is SelectPdf-specific
  • DisplayOnFirstPage = false suppresses the header/footer on the first page, useful for cover page scenarios
  • Verify whether the header height is automatically calculated from the HTML content or must be set explicitly

IronPDF — Headers and Footers:

using IronPdf;
using IronPdf.Engines.Chrome;

var renderer = new ChromePdfRenderer();
renderer.RenderingOptions.PaperSize = IronPdf.Rendering.PdfPaperSize.A4;
renderer.RenderingOptions.MarginTop = 20;
renderer.RenderingOptions.MarginBottom = 20;

// HTML header — full CSS3, no external URL required
renderer.RenderingOptions.HtmlHeader = new HtmlHeaderFooter
{
    HtmlFragment = @"<div style='font-family:Arial;font-size:10px;
                     display:flex;justify-content:space-between;
                     border-bottom:1px solid #bbb;padding-bottom:4px;'>
                     <strong>Company Report</strong>
                     <span>Confidential | {date}</span></div>",
    // Suppress header on first page (cover page)
    DrawDividerLine = false
};

// Text footer with page number and total pages
renderer.RenderingOptions.TextFooter = new TextHeaderFooter
{
    RightText = "Page {page} of {total-pages}",
    LeftText = "Q4 2025",
    FontSize = 8,
    DrawDividerLine = true
};

using var pdf = renderer.RenderHtmlAsPdf(reportHtml);
pdf.SaveAs("report-with-headers.pdf");

The headers and footers guide documents text-based, HTML-based, and mixed header/footer variants; the full token reference ({page}, {total-pages}, {date}, {url}); and the FirstPageNumber setting for documents that start numbering after a cover page. HTML headers accept inline Flexbox layout for split-column designs without an additional URL endpoint.

Post-Generation Encryption (SelectPdf Gap)

SelectPdf produces a PdfDocument object (its own type) or a byte array; neither carries an encryption API. Encryption requires a second library. This operation is included because it represents the most common capability gap encountered when SelectPdf is used in production workflows that require compliance or access control.

SelectPdf — Encryption (Gap):

// SelectPdf has no encryption API.
// The generated PDF must be passed to a separate library for encryption.

using SelectPdf;

var converter = new HtmlToPdf();
var doc = converter.ConvertHtmlString(invoiceHtml);
byte[] rawBytes;

// Get the bytes from the SelectPdf document
using (var ms = new System.IO.MemoryStream())
{
    doc.Save(ms);
    rawBytes = ms.ToArray();
}
doc.Close();

// rawBytes must now be passed to a second library for encryption.
// This second library introduces additional NuGet dependencies,
// a second disposal lifecycle, and a second error model to handle.

Technical constraints:

  • Two-library pattern for every post-generation operation (encrypt, sign, merge, watermark)
  • SelectPdf's PdfDocument type has no interoperability with other libraries' document types
  • As requirements expand, the number of secondary library dependencies grows with each new operation

IronPDF — Inline Encryption:

using IronPdf;

var renderer = new ChromePdfRenderer();
using var pdf = renderer.RenderHtmlAsPdf(invoiceHtml);

// Encryption on the same PdfDocument returned by the renderer
pdf.SecuritySettings.OwnerPassword = "ownerSecret";
pdf.SecuritySettings.UserPassword = "userKey";
pdf.SecuritySettings.AllowUserPrint = true;
pdf.SecuritySettings.AllowUserCopyPasteContent = false;
pdf.SecuritySettings.AllowUserAnnotations = false;

// Digital signature on the same object — no second library
var signature = new IronPdf.Signing.PdfSignature("cert.pfx", "certPass")
{
    SigningReason = "Approved for distribution"
};
pdf.Sign(signature);

pdf.SaveAs("invoice-secured.pdf");

The passwords and permissions guide documents the full permission flag model. Because encryption and signing operate on the same PdfDocument instance, generation → sign → encrypt → save is a sequential operation on one object with no intermediate handoff to a secondary library.

Commonly Reported Limitations

  • Community edition page cap. The free community edition limits output PDF page count per conversion. Documents that exceed this limit produce truncated output rather than throwing an exception in some versions, which means the failure mode is silent: the PDF is generated, appears valid, but is missing pages beyond the limit. Applications that generate documents of variable length may pass testing with short documents and fail silently in production with longer ones. This is the most commonly reported friction point with the free tier, and it is categorically different from a thrown exception—it requires explicit page count validation in test suites.
  • CSS rendering uncertainty. The rendering engine's CSS support level is a critical evaluation question that is not prominently documented in the getting-started materials. Templates that appear to render correctly in simple cases may produce layout failures for Flexbox containers, CSS Grid sections, or CSS custom property references. The engine version bundled in a specific NuGet release determines the CSS ceiling, and this version does not automatically update when a developer runs dotnet restore. Verifying the engine version and CSS feature matrix before template development begins is essential for avoiding late-stage rework.
  • No manipulation API. SelectPdf is a generation library with no post-generation operations. Teams that discover they need to merge generated documents, apply password protection, or sign PDFs for compliance after committing to SelectPdf must evaluate and integrate a second library. The two-library accumulation is a recurring pattern reported in community forum discussions: SelectPdf for generation, iTextSharp or another library for security and signing, a third library for merge operations if the application combines multiple generated documents.
  • Concurrent request behaviour. Under ASP.NET Core concurrent load, the rendering engine's threading model determines whether response times degrade. If the converter serialises concurrent requests internally—a common pattern for native-backed HTML renderers—request queue depth grows under sustained throughput and tail latency increases. This behaviour is not prominently documented and typically surfaces only during load testing with realistic concurrent request volumes, not during development testing.
  • Cloud API vs. in-process library. SelectPdf offers both an in-process library and a cloud API. The two have different capability sets, different integration models, and different operational characteristics (network latency, external service availability, per-request cost, data privacy implications). Teams that evaluate the cloud API during a proof of concept and assume the in-process library has equivalent capabilities may discover gaps when building the production integration.

Conclusion

When staying on SelectPdf is technically reasonable

SelectPdf is a reasonable choice for applications that need HTML-to-PDF conversion within a CSS feature set that the library's rendering engine supports, where the commercial license is in place (eliminating the community edition page limit), and where post-generation manipulation is not required. For simple, table-based document templates—invoices, reports with straightforward layouts, structured data output—that do not rely on Flexbox or Grid, SelectPdf can produce adequate output with a straightforward integration model.

For teams already using SelectPdf in production with stable, working templates, migration cost should be weighed against actual requirement gaps. If the current integration is delivering correct output and no new requirements are driving change, the case for migration is weak.

When migration becomes a capability or architectural mismatch

The migration case is clearest when: CSS templates adopt Flexbox or Grid (framework upgrade, designer change, component library introduction); post-generation operations (encrypt, sign, merge) are added as requirements; Linux or Docker deployment is needed but the in-process library's native binary support on those platforms is uncertain; or the community edition page limit causes silent truncation in production.

The two-library accumulation pattern is a slow forcing function: each additional operation that SelectPdf does not support adds a dependency and an API surface to maintain. Teams that reach three or more additional libraries for PDF-related operations have effectively built a custom multi-library PDF stack that a comprehensive single library could replace.

How IronPDF approaches the same problem differently

IronPDF uses a bundled Chromium engine, which means the CSS feature ceiling matches current Chrome rather than an older WebKit or custom engine. Grid, Flexbox, web fonts, SVG, and JavaScript-rendered content all render as they would in a browser, which means a template that passes visual review in a browser is a reliable predictor of PDF output quality. There is no separate CSS compatibility matrix to learn.

The PdfDocument result covers the full operation space—merge, encrypt, sign, form-fill, extract—in one library, eliminating the accumulation pattern that SelectPdf's generation-only scope creates. ChromePdfRenderer is thread-safe and handles concurrent ASP.NET Core requests without serialisation. The async API integrates with the standard async/await pipeline—the async rendering guide documents RenderHtmlAsPdfAsync() for controllers and background services. The HTML string to PDF guide is the entry point; the manipulation capabilities are on the same PdfDocument that the renderer produces.

For teams currently using SelectPdf's community edition and encountering the page limit, the migration path to IronPDF's commercial edition is: replace new HtmlToPdf() with new ChromePdfRenderer(), replace converter.ConvertHtmlString(html) with renderer.RenderHtmlAsPdf(html), replace doc.Save(path) with pdf.SaveAs(path), and add using disposal to the PdfDocument. The API surface change is small; the rendering engine change is significant and typically resolves CSS layout issues that the previous engine could not handle.

When you audit the CSS in your current PDF templates, what proportion uses features that depend on the rendering engine's capabilities—and at what point does that proportion make rendering engine modernity a practical rather than theoretical concern?
